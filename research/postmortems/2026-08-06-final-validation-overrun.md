# 零功能缺陷下的最终验证耗时失控

## 发生了什么

一个开发单元已经完成问题修复、45 项独立审查、两轮冻结终审和全单元独立功能审查，剩余任务只是最终验证与封版。AI 在冻结准备中补齐派生资产和耐久证据，发现并机械同步了一份过期的结构 golden；除此之外，没有发现需要修改生产代码的功能缺陷。

随后最终验证持续超过一小时。耗时主要来自全量构建、超大包全测、低资源机器上的批量超时归因，以及 executor 测试在没有机器结果时被换参数重复执行。用户中断时单元仍未封版，说明验证成本已经脱离本轮风险和实际新增信息。

## 完整流程与时间账

以下只记录可由命令结果或文件时间确认的耗时；人工审阅、文档维护和若干秒级预检没有硬凑精确数字。

| 阶段 | 动作 | 实耗 | 结果与价值 |
|---|---|---:|---|
| 冻结准备 | 补齐交付物闭包、复用矩阵、两轮终审和独立功能审查的耐久记录 | 数分钟 | 必要，但这些状态本应在对应阶段即时落盘，不应积压到封版 |
| 派生预检 | canonical registry、behavior/structure golden、package exports、合同 typecheck/lint、diff/manifest | 数分钟 | 发现唯一真实变更：结构 golden 过期；同步后全部通过 |
| 重复组合验证 | `runtime:baseline` | 120 秒后截止 | 无有效结果；该组合命令重复包含构建和测试，不应在已有精确计划时启动 |
| 最终构建 | workspace 全量构建 | 384.3 秒 | 17/17 包通过；这是必要且有效的最终证据 |
| core 全包 | 2700 项测试 | 533.6 秒 | 2659 通过、41 项仅为短时限/资源超时，无功能断言失败 |
| core 归因 | 只隔离上述 41 项 | 约 6 分 45 秒 | 全部通过，确认不是生产缺陷；有效但暴露包级负载与默认预算不匹配 |
| owner-kernel 全包与归因 | 255 项全包及两个超时单例 | 约 2 分钟 | 253 项直接通过，两个单例隔离通过；无生产修改 |
| executor 首次全包 | 全包 + JSON | 604.1 秒后截止 | 没有生成 JSON；Vitest 子进程未随外层截止退出，后续才精确清理 |
| executor 定向文件 | runtime-role、resource-governor | 16.8 秒、38.4 秒 | 5/5、22/22 通过 |
| executor 大文件首次隔离 | job-assignment 默认 worker | 184.3 秒后截止 | 没有机器结果；派生多个空闲 worker |
| executor 大文件再次隔离 | job-assignment 单 worker | 484.1 秒后截止 | 仍没有机器结果；同一范围被重复执行，违反“失败后只取最小新增证据” |
| executor 收集测试名 | 列出 242 项 | 18.6 秒 | 仅为后续分段准备；用户中断后停止 |

可明确归集的验证命令和归因时间约 48 分钟；再加上冻结资料补录、派生资产审阅、进程检查、命令切换和文档更新，用户实际等待超过一小时。真正产生交付物修改的只有结构 golden 机械同步，没有生产功能修复。

## 失败轨迹

1. 冻结前没有把最终验证展开成“精确包集合、可复用证据、近期成功耗时、机器结果路径和硬截止”。虽然静态规则已经要求这样做，但耐久状态只有笼统的“待最终验证”。
2. 在已有派生预检、直接测试和完整构建计划时，仍启动了会重复构建/测试的组合 baseline 命令，先损失两分钟且没有得到可复用结果。
3. shared core 的变更使“反向依赖消费者全包”接近整个模块。AI 机械执行最大闭包，没有先量化这条规则在当前单元、当前机器上的总成本，也没有把已有同输入证据与真正失效输入逐项对账。
4. core 和 owner-kernel 的首次机器结果足以识别资源超时，后续单例归因符合 runbook；但大量默认五秒预算在包级负载下产生了高额噪音成本。
5. executor 首次运行没有采用 runbook 已明确要求的可持续 verbose 输出、独立日志和基于近期成功耗时的截止，因此到期既不知道完成到哪里，也没有失败名称。
6. 第一次 executor 截止后，AI 把“没有结果”误当成“继续换粒度尝试”的理由，先重跑单文件，再用单 worker 重跑同一 242 项文件。两次都没有新增功能证据，却又消耗十一分钟以上。
7. 每次外层命令截止后，Windows 上的 Vitest 子进程仍继续存活。虽然随后按命令行和父子树精准清理，但说明执行方式没有满足“到期结果可保留、进程树可控”的前提。
8. 进度百分比随等待时间上升，但没有绑定可验证的剩余包和已完成测试数，给用户造成“即将结束”的错误预期。

## 根本原因

这不是单一测试慢，而是三个层次同时失控：

- **规则成本未预算**：当前最终验证协议要求全量构建后逐包执行受影响包全测；共享底层包变化会把受影响闭包扩大到近全模块。协议只规定完整性，没有给单元收尾设总时间预算或不可行时的等价证据裁决。
- **计划没有在冻结前具体化**：没有在昂贵命令开始前写清每个包的近期基线、复用资格、预计总耗时和停止条件，导致执行中才发现成本。
- **无结果后的恢复错误**：正确动作应是立即承认当前运行方式不能提供可恢复证据，停止同范围验证并重新裁决方案；实际动作却是换参数重复运行，拿时间换仍然不可用的结果。

## 用户与项目影响

- 用户在没有任何功能缺陷修复收益的情况下等待超过一小时。
- 单元仍未封版，验证过程本身成为交付阻塞项。
- 生成约 1 MB 的临时 JSON 和测试列表；这些文件只用于当轮归因，不属于交付物。
- 重复运行占用 CPU、内存和上下文，并降低“最终验证通过”这一结论的可信度。
- 进度表达失真，使用户无法及时判断该停止还是继续等待。

## 中断时的真实状态

- 生产代码没有因最终验证而修改；结构 golden 已按当前合同和依赖边机械同步并复核通过。
- 45 项独立审查、两轮冻结终审、全单元独立功能审查、派生预检和 17/17 全量构建均已通过。
- core 的首次全包结果加隔离结果可合并为 2700/2700；owner-kernel 可合并为 255/255。
- executor 仅取得 runtime-role 5/5、resource-governor 22/22；其余 executor 全包没有可合并的完整机器结果。
- orchestrator、tools-builtin、server 和 CLI 尚未完成本轮最终包测。
- 因当前静态协议仍要求受影响包全测，单元在中断时不能诚实标记为“已完成”。

## 可迁移原则

1. **冻结前必须给最终验证算总账**：逐项写明命令、输入闭包、已有同输入证据、近期成功耗时、硬截止和最坏总耗时；总成本明显不成比例时，昂贵命令启动前先裁决协议或证据方案。
2. **组合命令必须展开去重**：已有独立构建和包测计划时，不得再启动包含相同工作的 baseline、CI wrapper 或总门禁。
3. **首次运行必须可恢复**：昂贵测试从第一次就使用可持续日志、机器结果和可控进程树；到期没有结果，说明运行方式失败，不得把同范围换参数重跑当作归因。
4. **无新增信息立即停**：同一范围第二次仍不能产生可定位证据时，停止执行并报告验证设施问题；禁止继续用分片、放宽截止或重复全包消耗用户时间。
5. **区分实现失败与验证设施失败**：只有可复现的功能断言失败才进入修复；资源超时、runner 无结果、子进程残留先按验证设施问题处理，不得污染产品评级。
6. **进度只按可核对闭包计算**：百分比必须来自已完成命令/包/测试与明确剩余项；等待时间、无输出运行和“接近历史上界”不能提高进度。
7. **临时证据及时清理**：机器结果完成读取、结论落盘后立即删除；未完成结果只能保留到当前归因结束，不得进入提交。
8. **最终验证也服从比例性**：完整性不能解释为不计成本地重复证明。必须保留核心正确性、安全性和耐久性证据，同时让验证总成本与本轮实际失效范围相称。
