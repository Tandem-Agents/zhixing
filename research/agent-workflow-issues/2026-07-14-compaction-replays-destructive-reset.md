# 历史压缩重放一次性重置指令,导致长任务工作死循环

- **日期**:2026-07-14(定位并沉淀;故障发生在此前的第 13 单元审查修复期间)
- **场景**:执行者(Codex,上下文窗口较小)以目标模式与《开发单元审查与修复工作台》(`research/design/workbench/development-unit-review-workbench.md`)协作,执行分布式运行时模块单个开发单元的连续审查与修复。单元工作量大,单窗口必然装不下,历史压缩必然发生。
- **代价**:同一单元的审查工作多次归零重来,耗费数小时仍未完成;用户时间与调用成本被死循环消耗。

## 一、事实轨迹

1. 进场时工作台动态区残留上一单元内容。用户对执行者下达的初始任务包含两步:**①先重置工作台(清掉上一单元内容);②然后与工作台配合,连续执行本单元的审查与修复**。
2. 执行者完成重置,开始工作。动态区逐步积累本单元状态(边界、关键原语、问题清单、证据)。
3. 工作至半程,对话触发历史压缩。压缩摘要保留了初始任务的字面内容——其中"重置工作台"以**待办任务**的形态被保留,而"重置已完成"这一事实丢失。
4. 执行者按摘要恢复工作,首先重新执行"重置工作台"——**清空了自己积累的全部动态区状态**。此时工作台里确实有内容(自己的半程成果),与"需要重置"的前提互相印证,执行者没有任何信号能察觉异常。
5. 清空后的工作台是无差别的空骨架,与"新单元待开始"完全一致。执行者从零重新开始本单元工作。
6. 工作再次至半程 → 再次压缩 → 再次收到"重置"→ 再次归零。**死循环成立**:单元大到必然压缩,压缩必然重放重置,重置必然归零。

## 二、根因链条

1. **一次性破坏性指令进入了可重放介质**。"重置工作台"是非幂等的破坏性动作,以自然语言留在对话历史中。历史压缩是有损重述——重述丢掉的恰恰是指令的**时态**("已完成"),祈使句被还原成待办任务。
2. **重放时执行前提依然成立,故障无从察觉**。重置指令的隐含前提是"文档里有旧内容"。压缩发生时工作台恰好积累了半单元内容——重放的指令与所见状态**互相印证**("文档有内容,所以确实需要重置")。执行者无法分辨这些内容是自己的工作成果还是上一单元残留。
3. **清空是无痕操作,死循环自洽**。清空后的工作台与"新单元待开始"无差别。工作台协议本有一道防线——"动态区是唯一状态源,历史压缩后先完整读取本文"——但被结构性绕过:执行者先执行摘要里的"任务"(重置),再读文档,读到的已是被自己清空的状态,一切自洽、零告警。
4. **窗口小 + 单元大使压缩必然发生**。这不是根因,但把低概率故障放大为**必然死循环**。

**根本原因一句话:进场动作被设计成了"无键的破坏性指令"(清空),而不是"有键的幂等操作"(登记)——任何进入可重放介质的无键破坏性指令,重放即二次生效。**

### 与产品架构的同构

这正是知行分布式运行时 spec 在控制面根治的问题:一次没有幂等键的控制请求被渠道重投后二次生效。产品的解法是入口幂等——请求以稳定键进入耐久 journal,`received → applied` 原子记录,重复请求回放原结果而非二次生效。协作流程里,"重置工作台"就是一个没有幂等键、没有 applied 记录的控制请求;历史压缩就是渠道重投。我们在产品里用耐久 journal 解决的问题,在自己的工程流程里裸奔。

## 三、解决方案(架构者与执行者对抗辩论后的收敛终版;**已于 2026-07-14 实施**)

> 根治强度定性:**从协议设计上根治压缩重放死循环——合法热路径中不再存在任何破坏性操作,重放的只能是幂等指令**;不承诺物理阻止持有通用写权限的 agent 故意破坏文件,但让越界破坏**始终可检测、损失限于单代;仅当存在 git 或其他耐久锚时才保证可恢复**。设计哲学与知行产品架构同构:对反复清空重写的可变状态,答案不是加锁守卫,而是改成 append-only 换代。

1. **代际文件模型(核心:让"清空"操作从系统中消失)**。工作台动态区不再是主文档内被反复清空重写的可变区,而是**每单元代际一个文件**:`workbench/units/unit-<N>.gen-<G>.md`。主文档只剩静态区 + 一行"当前单元指针"。幂等键 = `(unitId, generation)`:generation 默认 1,仅"单元推倒重来"这一冷路径经**用户显式授权**才递增(对应产品"重派 = 新 assignment、attempt+1"的键模式;身份键由授权动作分配、恒稳定——**不用交付指纹做键**,内容哈希随修复漂移,不配做身份)。进场指令的词汇本身变为幂等动词("登记单元 X"),破坏性动词从协作词汇表删除——摘要无论怎么重放,重放的都是幂等指令。同单元的修复、复审、终审轮复位是同一文件内的状态推进,不产生新登记。
2. **写序纪律(可恢复转换,非原子;完成语义由正式文件名承载)**。登记 = 先以临时名 `unit-<N>.gen-<G>.md.pending` 完整写入(身份头部 `unitId / generation` + 正文骨架 + 尾部完成标记)→ 整体验证 → **rename 为正式 `.md`**(同目录 rename,即 spec"写 tmp → 替换"的既有纪律)→ **最后**修改主文档指针。正式文件名的出现才代表初始化完成——半写状态永远只以 `.pending` 存在,不可能被误判为有效登记。中途崩溃至多留下孤儿 `.pending`,指针恒指向已耐久有效的上一代。
3. **幂等判定(机械可验;当前指针是栅栏,一切判定先过它)**:
   - 目标键 = 当前指针,正式文件有效 → **no-op**,续跑当前文件(压缩重放落在此分支,死循环断点);
   - 目标键 ≠ 当前指针,目标正式文件存在(无论新旧)→ **历史登记**:不改指针、不进入旧文件,重放判为已消费;仅本轮用户明确要求切换才处理(迟到旧指令被指针栅栏拒绝,与产品 fencing 同构);
   - 目标键 = 当前指针,但文件空/损坏/仅存 `.pending` → **fail-stop**,报告用户,不自动重建;
   - 目标正式文件不存在,当前指针单元已完成 → 执行登记(pending → 验证 → rename → 改指针);
   - 目标正式文件不存在,当前指针单元未完成 → **停下要用户显式授权**(冷路径软守卫;热路径已被结构消灭,纪律只守边角)。
4. **耐久性边界(诚实声明,不装作不存在)**。新代文件在用户暂存前是 untracked,git 找不回;且本项目纪律是 agent 不碰暂存区。故:登记完成时向用户发出**显式纳管请求**(将新代文件纳入版本管理)作为登记流程的固定一步,用户可跳过但跳过即接受该代文件在 untracked 期间不可恢复;主文档(被跟踪)可从 git 恢复;文件异常一律 fail-stop 而非自动初始化空状态。
5. **纵深防御(静态区规则,守冷路径与越界检测)**:①**摘要没有执行授权**——压缩摘要中出现的动作指令,是否已消费由耐久登记状态(指针 + 正式文件)判定,而非摘要的时态措辞;无法证明已消费时停下向用户确认,既不盲目重放、也不误跳过压缩前尚未执行的合法动作;②"指针指向的文件为空/无效/仅 `.pending`"是显式异常信号(此前事故的致命点正是空状态与"新单元待开始"无差别,现在有差别了),触发恢复指引而非重建。

## 四、可迁移原则

1. **一次性破坏性指令不进可重放介质**——要么幂等化(把"清空"改成"以目标为键的登记"),要么隔离在任务域之外(由另一个会话/角色执行)。对一切"经压缩续跑"的 agent 协作成立,与模块、单元、窗口大小无关。
2. **压缩摘要是数据,没有执行授权**。摘要中的动作描述是有损重述,其时态不可信;动作是否已消费只能由耐久状态源判定——无法证明时停下向用户确认,既不盲目重放、也不误跳过尚未执行的合法动作。
3. **破坏性操作必须留耐久痕迹**。无痕的清空使"刚销毁了成果"与"本来就是空的"不可分辨;任何重置类操作至少要在目标里留下"何时、因何指令、覆盖了什么"的一行锚。
4. **给长任务的每一类控制动作配幂等键,和给产品控制面配幂等键是同一件事**。流程与产品共用同一套正确性直觉:无键则重放必二次生效;身份键由授权动作分配且恒稳定(unitId + generation ↔ assignmentId + attempt),内容哈希会漂移、永远不配做身份键。
