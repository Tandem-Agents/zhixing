# Agent Workflow Issues — 人机协作工作流程问题集

> **专放用户与 Agent 协作过程中发现的工作流程结构性问题**——不是某次代码 bug、也不是某次诊断失败,而是协作机制本身(上下文压缩、指令传递、状态源、任务交接、工具协议)的故障模式。记录事实轨迹、定位根本原因、沉淀解决方案与可迁移原则,让同类流程故障不再重演。

## 这是什么

Agent 协作依赖一组隐式机制:对话历史、历史压缩、状态文档、目标模式续跑、任务指令的下达与消费。这些机制自身会以结构性的方式失效——典型形态:

- 历史压缩后,已完成的指令被当作待办任务重放
- 状态文档与对话摘要冲突时,agent 选错了权威
- 长任务跨窗口续跑时,工作状态丢失或被自己销毁
- 任务边界/授权语义在多轮交接中漂移

每个案例的目标不是"这次怎么救回来的",而是暴露**协作机制的设计缺陷**,把修复落到机制层(协议、文档、幂等化),而非依赖 agent 或用户"下次小心"。

## 与 postmortems 的分工

- `research/postmortems/`:AI **诊断认知**失败——AI 怎么想错了、漏了哪个角度(猜测代替观测、多轮试错耗用户时间)。
- 本目录:**协作流程机制**失败——机制怎么把双方都带进坑里(压缩重放、状态源倒置、指令时态丢失)。前者修"AI 的思考方式",后者修"协作的基础设施"。

## 何时新增一篇

满足以下任一条件:

- 一次协作故障的根因落在流程机制(压缩/状态/指令/交接),而非代码或认知
- 同一流程故障出现第二次,或可预见会在其他模块/其他 agent 上重演
- 用户为某次机制性故障付出了显著的时间/成本代价

写作时间:定位根因后**立即写**,趁事实轨迹清晰。

## 写作原则

1. **诚实记录事实轨迹**——按实际发生顺序写,不美化、不省略"故障期间没人发现"这类尴尬事实。
2. **根因落到机制,不落到人**——"agent 应该更小心"不是根因;机制允许这个故障发生才是。
3. **解决方案标注实施状态**——已实施/待裁决/未实施,与真实进度一致,防止文档声明面领先生效面。
4. **提炼可迁移原则**——每篇至少一条能应用于任何模块、任何 agent、任何窗口大小的原则。
5. **成本显式化**——记录这次故障消耗了多少轮工作、多长时间,让流程故障的代价可见。
6. **避免引用易变标识符**——机制描述不依赖单元号/commit hash 等会过期的锚点,案例事实中可如实提及。
