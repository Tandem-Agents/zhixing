# 架构审查问题收集

## 使用规则

- 本文骨架固定保留：`使用规则`、`维护原则`、`问题条目结构`、`排除问题条目结构`、`提示词文本块结构`、`来源`、`本轮审查问题`、`已排除问题`、`用户使用的提示词`。
- 清理时只清空动态内容，不删除骨架标题、说明和格式。
- `用户使用的提示词` 属于用户权限内容，不参与清理；除非用户明确要求，不得修改、清空或删除其中任何文本块。

## 维护原则

本文用于收集一轮架构审查中发现的问题，目标是在当前事实与认知下尽可能把这一轮能发现的问题收集完整，直到除本文已记录的问题之外，本轮已经无法再发现新的问题。

这不表示这些问题解决后未来不能再发现问题。问题修复本身可能暴露新的问题，或引入新的设计约束，这是正常且接受的事实。

这里的“本轮收集完成”只表示：除本文动态部分已经记录的问题外，当前这一轮审查暂时没有新的可发现问题，可以结束本轮审查。

新增问题必须满足两个条件：第一，问题必须基于事实真实成立；第二，不能与动态区已有问题重复、重合或冲突。若只是同一问题的不同表述，应合并到既有条目，而不是新增。

新增问题还必须区分“架构阶段必须定死的问题”和“实现阶段自然会处理的细节”；后者不进入问题列表，避免审查变成无限挑刺。

## 清理节奏

1. 来源：随当前模块更新而更新，修改频率低。
2. 本轮审查问题：按轮次更新；每轮审查找出所有问题，解决并清理后，该轮问题清零。
3. 已排除问题：跨轮次有效；本轮、下一轮及后续轮次继续积累并用于避免重复验证，更新时机与来源更新时机一致。
4. 用户使用的提示词：不随轮次或模块清理，只有用户明确要求时才可改动。

## 问题条目结构

动态区每个问题条目固定包含三部分：

1. 编号标题：一句话指出问题本质。
2. 问题说明：说明真实事实、风险和为什么这是问题。
3. 解决方案：以 `解决方案：` 开头，写执行者认可的最优解决方案，要求精简、可执行。

## 排除问题条目结构

已排除问题使用列表维护，每项固定包含两部分：

1. 什么问题：说明被核查但排除的问题。
2. 为什么排除：说明排除依据，便于后续审查避免重复验证。

## 提示词文本块结构

底部「用户使用的提示词」使用独立文本块维护；每个文本块下方必须紧跟 `---` 分割线，空文本块也必须保留分割线。

## 已排除问题

- 什么问题：现有源码还没有 `messagePrefix`、`runtimeKind`、`reportLifecycleWarning` 等新接口。
  为什么排除：这是本架构待实现内容，主文档已列入明确落点；不能把“尚未实现”重复记成新的架构问题。

- 什么问题：段压缩摘要请求不带 guidance 会导致与主对话完整 provider 请求不再完全 byte-equal。
  为什么排除：这是已定死的产品取舍；摘要请求必须隔离 guidance，避免约定内容进入 summary / snapshot / memory，不能为了 cache 命中牺牲隔离。

- 什么问题：`llm:request_start.messages` 含 providerMessages 后会把 guidance 透给 UI / RPC。
  为什么排除：server 的 `session-events` 投影已裁掉 messages / systemPrompt / tools，只转发摘要字段；本地 EventBus 保留完整请求是诊断面，不是公网 UI 契约。

- 什么问题：capability 校验必须前移到含 messagePrefix 的完整 providerMessages。
  为什么排除：第 2 条已把 `messagePrefix` 边界钉死为纯文本、角色安全、不可变快照；非法贡献在 lifecycle 边界失败，provider capability 校验不需要重复覆盖 prefix。

- 什么问题：Task/sub-agent 是否会误生效 `ZHIXING.md` guidance。
  为什么排除：子 agent 走 `subagent/loop-runner.ts` 直接调用 `runAgentLoop`，不经 `createAgentRuntime` 和 lifecycle；主文档 §6 已按 by-construction 排除。

- 什么问题：`ZHIXING_HOME` 若设为相对路径，会不会让全局 `ZHIXING.md` 重新绑定运行地址。
  为什么排除：`ZHIXING_HOME` 是既有 `getZhixingHome()` 的显式全局 home 覆盖行为，不是本架构新增的 cwd 项目语义；是否统一绝对化属于全局路径基础设施议题，应独立审查。

- 什么问题：大文件 `ZHIXING.md` 是否必须设置专用上限或自动截断。
  为什么排除：全量注入、不截断是已定死的产品语义；`ZHIXING.md` 是用户主动维护的有界约定文件，静默截断会破坏声明面=生效面。病态大文件属于未来独立 UX 需求。

- 什么问题：run 外 `checkBudget/contextBudget` 不模拟 `turnContextInjector` 是否会导致预算不准。
  为什么排除：run 外没有 run 级动态上下文，预算只统计当前窗口固定成本；run 内 `context:tokens_snapshot` 使用含 turn-context 的 `providerMessages`。强行模拟会把预算查询做成半个 run 入口。

- 什么问题：`AgentRuntime.callText` / `callTextWithUsage` / `runOrchestrationV1` 是否也应自动注入 guidance。
  为什么排除：这些是单发维护通道或 child-agent 编排通道，不是有注意力窗口生命周期的 user-facing 主对话；需要背景时由调用方显式组织 prompt / contextSnapshot，不能自动继承 `ZHIXING.md`。

- 什么问题：`ConversationManager.getOrCreate(..., { ephemeral: true })` 的 ephemeral 会话是否应按 `runtimeKind === "ephemeral"` 跳过 guidance。
  为什么排除：这里的 ephemeral 是会话持久化状态（临时未落盘 / 待晋升），仍有 conversationId 和注意力窗口，runtimeFactory 仍发放 conversation/workscene runtime；`runtimeKind === "ephemeral"` 只指 `RuntimeHost.createEphemeralRuntime()` 这类无窗口的一次性执行体。
