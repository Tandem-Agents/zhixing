# 多视角发散收敛架构

## 需求区

### 多视角发散收敛

- **本质需求**：复杂、关键、易误判问题需要一种内功能力：临时拉起多个隔离子 agent，从不同视角独立产出、交叉吸收，再收敛出唯一最终版本回主线。中间过程瞬时、不持久化、不污染主线。
- **地基**：以文件化可编排基础设施为基础——本需求的流程是固定的，产物是一份内置编排文档，不写死进代码。基础设施是公用的，绝不为本需求定制耦合；能力不足时（如节点级模型档位）从基础设施视角做通用增强。
- **唤醒**：`@` 行首后跟空格，或行中前后皆空格，后接问题正文即触发并发；`@` 后无正文不触发，避免误伤 `email@x.com`。并发数量写在自然语言问题里。手动 `@` 是第一阶段发起者，未来 AI 自动触发等多种发起方式复用同一机制，注意架构设计。
- **分配节点**：唤醒后先经分配节点，依据问题内容决定视角集合；用户未要求时默认 3 个，上限 5 个（提示词声明 + 系统层强制，超出按 5 处理）。提示词内置常见场景示例（思考需求、审查代码各有哪些视角）作分配参考。
- **模型档位**：main 必有、power 可选。仅 main 时列表全为 main；配置了 power 则以 main 起始与 power 交替。不同档位模型参与不同视角，用视角 × 档位双重多样性提高结果质量。
- **流程**：第一轮并发——各视角基于同一主注意力窗口只读快照独立产出；第二轮并发——每个节点拿到其余节点的结果（提示词告知这是他人结果），判断优劣并融合出自己的最优版本；收敛节点——从各最优版本收敛出唯一最终版本回主线。第二轮的 token 成本是明确接受的需求。

## 架构内容

### 0. 设计裁决

多视角发散收敛不是新模式、新界面或新会话形态。它是**消息的一种回答方式**：用户用 `@` 把一个问题交给一场评议——多个隔离视角独立产出、相互批判吸收、收敛出唯一最终版本——主线只留下一问一答。

核心裁决：

- **多视角流程是该对话的一个普通 turn（一等 turn 裁决）**。触发后经 `ConversationManager.admitTurn` 进入同一串行队列，`PendingTask.execute` 闭包内完成快照捕获 → 分配 → 装配 → 编排执行 → 收敛产物落盘。推导：串行化、busy 占位、排队、abort、observer 组播、usage 计量全部免费复用；快照在串行点捕获，窗口天然稳定；被否的备选是「控制面带外流程、结果以事件交付不落盘」——评议结论不进对话历史等于后续轮次失忆，最终版本必须成为对话事实，才配得上"回主线"。
- **触发面与发起面分离**。`@` 语法解析只住接入面（CLI 输入预处理，与 `/` 命令检测同层）；wire 协议上是 `session.send` 的发起意图参数；执行住 server 侧多视角门面。未来 AI 自动触发、其它渠道触发都是直接调用同一门面，不经 `@` 解析——多种发起方式、单一执行机制。
- **两段式装配消解动态性**。分配节点决定视角数量与内容，而编排 DAG 是静态的——矛盾在实例化时刻消解：分配是编排外的一次强 schema LLM 调用（可替换 strategy），其产物（视角列表 + 档位序列）作为**有界参数**填入内置编排文档模板，实例化出节点数已固化的静态 DAG，再进全量校验管线执行。这正是基础设施 §3.2 预设的「可信模板填参」形态，基础设施零特判。
- **基础设施增强恒为通用语义**。本需求暴露两个真实通用缺口：模板层缺「有界数组展开」（任何 N 个同构节点的编排都需要）、节点策略缺「模型角色声明」（任何编排都可能想按节点指定档位）。两项都以基础设施自身语义扩展（见 §6），定义与实现中不出现任何多视角字面量。
- **中间过程零持久化**。分配产物、各视角产出、交叉版本全部瞬时，存活于一次 execute 闭包内；落盘只有用户原文与最终版本。RunRecord 带 run 级来源元数据（视角数、编排 id）供显示与追溯——这是对结论的注记，不是过程持久化。
- **业务语义外置纪律照守**。视角、交叉、收敛只存在于编排文档的节点 instruction 与门面装配逻辑里；基础设施只看见节点、依赖、契约。

### 1. 范围

本文定义多视角发散收敛的系统架构：触发解析、发起协议、分配、模板装配、编排执行、结果回主线、事件呈现、基础设施通用增强与实施路径。

不在本文展开：

- 文件化可编排基础设施本身，见 [`file-based-orchestration-infrastructure.md`](./file-based-orchestration-infrastructure.md)；本需求即其 §16 单元 4（首个真实消费者）与单元 5（产品接入）的落地。
- 单个智能体唤醒（`@名字`）、角色系统、动态生成编排文档。
- 消息通道（飞书等）的多视角投影形态。

### 2. 现有地基判断

- 基础设施单元 1–3 已实现：core 编排内核（parse / validate / normalize / plan / template / caps）、`snapshotAttentionWindowV1`（`full_or_fail` / `tail`）、`runChildAgent.backgroundMessages` 注入通道、`OrchestrationRunner` + `AgentNodeExecutor`（DAG 调度、maxParallel、fail-fast、abort 级联、输出契约、`orchestration:*` 事件已随 per-run EventBus 发射）。
- `ConversationManager.admitTurn` 的 `makeTask: (managed) => PendingTask` 是通用 turn 准入协议，`PendingTask.execute` 不绑定 main runtime——多视角 turn 可作为一等 turn 挂入，无需改 owner。
- `LLMRoles = { main, light, power }` 已解析于装配层；power 未显式配置时 resolved 回落 main 实例（合理默认非降级）——「仅 main 时全 main、有 power 交替」在执行层自动等价，无需特判。
- `AgentNodeExecutorOptionsV1` 已持有 `llmRoles`，但节点执行恒用 executor 级单一 `provider/model`——节点级档位是真实缺口。
- 模板实例化是 `{{param}}` 值替换——表达不了「按数组展开 N 个同构节点」，动态视角数无法落进静态模板——数组展开是真实缺口。
- CLI 输入预处理已有 `/` 命令检测层，`@` 触发解析插同层；`orchestration:*` 事件的 CLI 投影尚无消费者。

### 3. 终态拓扑

```text
CLI 接入面
├─ @ 触发解析（输入预处理层，与 / 命令同层）→ session.send + engage 参数
└─ 进度投影（orchestration:* 事件）+ 历史来源标记

server 编排层
├─ ConversationManager（会话 owner / 串行点，零多视角语义）
├─ PerspectivesController（多视角门面，与 AdvancementController 并列）
│  ├─ PerspectiveAllocationStrategy（分配：问题 → 视角列表，可替换）
│  ├─ 内置编排文档模板（deliberation 模板资产，JSONC 文本）
│  ├─ 装配：视角×档位序列 → 模板参数 → instantiate → executable
│  └─ 结果落盘：一问一答 RunRecord + run 级 perspectives 元数据
└─ orchestrator: runOrchestrationV1 + AgentNodeExecutor（既有，含两项通用增强）

core 基础设施（通用增强，无多视角语义）
├─ 模板有界数组展开（template 层）
└─ 节点 modelRole 声明（schema / normalizer 层）
```

职责分界：

| 组件 | 职责 | 不做 |
| ---- | ---- | ---- |
| CLI `@` 解析 | 识别触发语法、剥离出问题正文 | 不理解视角与流程 |
| PerspectivesController | 分配、装配、执行编排、落盘结果 | 不写主线中间过程、不改 owner 串行语义 |
| AllocationStrategy | 问题 → 视角集合（强 schema） | 不决定档位、不参与执行 |
| 编排基础设施 | 校验、调度、节点执行、事件 | 不认识"视角/交叉/收敛" |
| ConversationManager | 串行、busy、abort、落盘接受协议 | 不内嵌多视角语义 |

### 4. 核心数据模型

#### 4.1 发起协议（wire）

`session.send` 参数扩展发起意图（命名示意，实施时对齐 wire 惯例）：

```typescript
interface SessionSendParams {
  // 既有字段...
  engage?: { kind: "perspectives" };
}
```

- 用户消息**原文落盘**（含 `@` 触发语法——它是用户表达的事实）；编排 run input 用剥离触发语法后的问题正文。
- `engage` 是显式处理方式指令：无推进会话时，该输入不过推进准入分类（用户已指定怎么回答，自动分类没有裁决空间）。
- **与推进会话共存的边界（如实定死）**：active 推进会话下，输入照走既有分类分层，被放行执行时 engage 生效（多视角回答作为主线事实照常进验收）；awaiting 阶段的既有语义是「非降级/取消的输入不执行、只重投确认面」——engage 输入同规则，@ 意图随消息不执行而不生效。不为多视角开旁路特例；若未来 awaiting 支持旁路咨询，多视角随普通输入自然通行（改进归 advancement 模块）。
- 返回与普通消息一致（immediate / queued），不新增 RPC method——发起意图是消息的属性，不是新动作。

#### 4.2 分配产物

```typescript
interface PerspectiveAllocation {
  perspectives: Array<{
    name: string;        // 视角名（如"用户体验""安全边界"）
    charge: string;      // 该视角的评议职责描述
  }>;
}
```

- 分配 strategy 输出经强 schema 校验（与推进准入/草案生成同构：LLM 单发 + 结构化输出，禁止宽松解析）。
- 数量三层强制：分配 prompt 声明「默认 3、上限 5」并内置场景示例（思考需求、审查代码各有哪些视角）；门面装配 clamp 到 5；实例化后节点总数仍受 `caps.maxNodes` 校验。用户在问题里要 7 个，系统按 5 处理。
- 分配调用用 main 档：分配质量决定整场评议质量，单次调用成本相对全流程可忽略。

#### 4.3 档位序列（门面装配逻辑，不进基础设施）

- 视角档位序列：main 起始，与 power 交替（`main, power, main, power, main`）。power 未显式配置时 resolved 恒回落 main，序列自动等价全 main——装配不特判；呈现层不标注模型档位（避免 fallback 时误导），只标视角。
- 收敛节点档位：power（收敛是全场最重的判断，显式配置了更强档就用在这里）；未配置时自动回落 main。交叉节点档位随各自视角在序列中的档位（同视角两轮同档）；分配调用恒 main（§4.2）。

#### 4.4 落盘形态

多视角 turn 完成后走既有 `recordTurn` 接受协议（先持久化后入窗），构造完整 RunRecord：

```typescript
// RunRecord 既有字段之上的 run 级元数据扩展
interface RunRecord {
  // 既有字段...
  perspectives?: {
    definitionId: string;      // 内置编排文档 id
    perspectiveCount: number;  // 本场视角数
  };
}
```

- `messages` = [用户原文 user 消息, 最终版本 assistant 消息]——一问一答，主线窗口自然增长，后续轮次能引用评议结论。
- `usage` = 全编排汇总（分配 + 全部节点），成本对统计与保险丝口径诚实。
- `source` 沿用 `interactive`（用户发起）；元数据走 run 级，不进 `Message role/content`（与 advancement 同纪律）。

### 5. 生命周期流程

#### 5.1 触发

1. CLI 输入预处理识别 `@`：行首 `@` 后跟空格，或行中 `@` 前后皆空格，且后有正文——触发；`@` 后无正文不触发（`email@x.com` 天然不命中）。
   - **与既有 `@` 语义的共存边界（已核实正交）**：CLI 现有 `@` 文件补全（FileProvider typeahead）与 `@file:path` 内容引用（resolveFileRefs）均为 `@` 后跟**非空格**；并发触发恒为 `@` 后跟**空格**——空格即判别符，互不侵占。实施时补全面板对 `@ + 空格` 不弹出（触发细化），`@file:` 引用在同一消息内照常先行解析。
2. 命中后照常 `session.send`，携带 `engage: { kind: "perspectives" }` 与消息原文。
3. server 侧 send 编排：advancement 门（awaiting/active 分层规则）先行 → `admitTurn`，`makeTask` 构造多视角 PendingTask。busy 时排队，与普通消息同权。

#### 5.2 执行（PendingTask.execute 闭包内，全程瞬时）

1. **快照**：从 managed 会话活窗口 `snapshotAttentionWindowV1` 捕获一次只读快照，策略 `tail`（有界尾部；评议不该因窗口超限而失败），上限走 caps。串行点捕获，窗口稳定。
2. **分配**：AllocationStrategy 以问题正文 + 快照尾部投影为输入，产出视角列表；clamp 上限 5，默认引导 3。
3. **装配**：视角列表 + 档位序列 + 问题正文 → 模板参数 → `instantiateTrustedOrchestrationTemplateV1`（数组展开在此发生）→ 全量校验 → executable。
4. **编排执行**：`runOrchestrationV1`。拓扑固化在内置编排文档里：
   - 第一轮 N 个发散节点：同一快照 + 问题正文 + 各自视角 charge，独立产出（互不可见）。
   - 第二轮 N 个交叉节点：每个节点 dependsOn 全部第一轮节点，instruction 告知「这是其他视角的结果、你是视角 X、你的第一轮版本是哪份」，判断优劣并融合出自己的最优版本。
   - 收敛节点：dependsOn 全部第二轮节点，从各最优版本收敛出唯一最终版本。
   - 三层节点均声明 `includeContextSnapshot`，共享同一份快照（基础设施保证）。
5. **回主线**：最终版本作为 assistant 消息，与用户原文构成一问一答，`recordTurn` 落盘入窗；发既有 complete 事件，CLI 整块渲染（评议无流式，进度由 §9 事件承担）。

#### 5.3 失败与中断

- 分配失败 / 模板校验失败 / 编排 fail-fast / 收敛输出违约：turn 以结构化错误结束，向用户解释失败环节；不落盘任何半成品（中间产物随闭包消亡）。
- 用户 abort（Esc / 新输入抢占）：走既有 turn abort 通道，runner parent abort 级联中止全部在跑节点；turn 归 aborted，主线零残留。
- **fail-fast 的产品代价（已知边界）**：任一节点结论性失败即全场废弃，用户重来 = 重发一次 `@` 消息。首版照守基础设施 `fail_fast` 唯一语义，不为本需求急建重试；本需求是基础设施「有界重试」扩展点（其 §13）的第一个真实消费者——届时按基础设施视角通用落地。
- 多视角 turn 落盘后若该对话有 active 推进会话，`afterTurnCommitted` 照常验收——它是主线事实，不特判（一致性优先；评议问答对裁判而言就是一轮普通进展）。

### 6. 基础设施通用增强（两项，站在基础设施视角）

#### 6.1 模板有界数组展开

模板节点可声明按数组参数展开（语法示意，实施时定案）：

```jsonc
{
  "id": "diverge-{{item.index}}",
  "expandForEach": "perspectives",   // 数组参数名
  "groupId": "diverge",              // 供其它节点依赖整组
  "instruction": "视角:{{item.name}}\n职责:{{item.charge}}\n...",
  "policy": { "modelRole": "{{item.modelRole}}" }
}
```

- 实例化时按数组长度展开为 N 个节点，`{{item.*}}` 是逐项参数作用域，id 注入序号保证唯一。
- 前提协议放宽（已核实现状）：现行模板参数仅允许 string——params 协议扩展为 `string | 有界结构化数组`（数组元素为 string 叶子的平面对象，深度与长度受校验约束），仍全量经参数校验，不放开任意 JSON。
- 展开组必须显式声明 `groupId`，不得由 id 模板隐式推导；`groupId` 使用与节点 id 相同的命名规则，重复或与真实节点 id 撞名时校验拒绝。
- `nodes[].dependsOn` 引用 `groupId` 时替换为全部展开实例 id（「依赖整组」是展开的自然语义）；替换只作用于节点依赖字段，不递归改写 schema / metadata 等任意同名字段。
- `expandForEach` 与 `groupId` 是模板控制字段，实例化后不会进入最终 definition。
- 展开只发生在 template 层：产物是普通静态 definition，validator / normalizer / planner / runner **零改动**；展开后节点数照常受 `caps.maxNodes` 硬校验——展开有界性由既有校验兜底。
- 通用性：任何「N 个同构节点」编排（多路检索、分片处理、评审小组）都消费此能力。

#### 6.2 节点模型角色声明

- `OrchestrationNodePolicyV1` 新增可选 `modelRole?: "main" | "light" | "power"`——声明**系统档位角色**而非具体模型名（定义是资产，不该绑死某个模型字符串；档位是系统概念，随用户配置解析）。
- schema 枚举校验、normalizer 展开缺省（缺省 = executor 级既有 model，行为向后兼容）。
- `AgentNodeExecutor` 已持有 `llmRoles`：按节点 `modelRole` 选取对应 role 的 provider/model 实例，无声明时走既有 executor 级配置。
- 通用性：任何编排都可按节点声明轻/重档（轻量抽取节点用 light、关键判断节点用 power）。

两项增强的定义、schema、错误码、测试中不得出现「视角 / perspectives / 多视角」等业务字面量。

### 7. Cache 与上下文边界

- 主线：多视角 turn 落盘只追加一问一答到 messages 尾部，system / tools / 历史前缀不动，cache 前缀稳定；无任何注入进主线窗口。
- 子节点：快照经 `backgroundMessages` 进子 loop messages 前缀，system prompt byte-equal 纪律照守（基础设施单元 2 已保证）。
- 中间产物（分配、节点输出）只存活于 execute 闭包与编排 run state，不进任何 store。

### 8. 事件与产品显示

- 复用 runner 既有 `orchestration:*` 事件（validation_failed / run_start / node_start / node_end / run_end），经 per-run EventBus 与 lineage 冒泡——发端零新增。缺两段：多视角 turn 的 execute 闭包须建立与普通 turn（`runTurnWithCommit`）同构的 per-run 事件桥接入既有 RPC 投影通路；CLI 侧缺 `orchestration:*` 消费者。
- CLI 投影原则：用户看到的是**评议进度**，不是编排协议。示意：触发后「N 个视角并行思考中…」→「交叉吸收中…」→「收敛中…」→ 最终版本整块呈现。节点粒度细节不默认展示。
- 历史渲染：带 `perspectives` 元数据的 run，assistant 回复带来源标记（如「◇ 多视角评议 · N 视角」），实时与历史同源（run 级元数据），与 advancement 来源标记同款纪律。
- 失败呈现：指明失败环节（分配 / 某视角 / 收敛）与结构化原因，不甩协议错误码。
- 可发现性：藏在语法里的能力零引导等于不存在——`/help` 收录 `@` 触发说明，与既有命令帮助同面呈现（随 P4 验收）。

### 9. 包与代码落点

| 包 | 新增 / 改造 | 说明 |
| ---- | ---- | ---- |
| `@zhixing/core` | template 数组展开；node policy `modelRole` | 通用增强，无业务语义 |
| `@zhixing/orchestrator` | `AgentNodeExecutor` 按节点 modelRole 选 role 实例 | 消费 llmRoles 既有持有 |

- 内置编排文档以完整 JSONC 文本存于门面模块内单一文件（如 `deliberation-template.ts` 导出模板常量）——语义上就是"一份编排文档"，物理上随构建产物零打包风险；不用代码拼 definition 对象绕过模板与校验管线。
- wire：`SessionSendParams.engage`、RunRecord `perspectives` 元数据透传（history / RPC / CLI 同源）。

### 10. 测试拓扑

必须覆盖：

- `@` 解析：行首 / 行中空格规则、无正文不触发、`email@x.com` 不误伤、剥离正文正确；与既有 `@` 语义共存——`@file:path` / `@名称` 不误触发并发，同一消息内 `@file:` 引用照常解析。
- 模板数组展开：N=3/5 展开正确、id 唯一、组依赖替换、超 maxNodes 拒绝、`{{item.*}}` 作用域、非数组参数拒绝。
- modelRole：schema 校验、缺省回落 executor 级、executor 按 role 选实例。
- 分配：强 schema 校验、超 5 clamp、失败结构化不执行编排。
- 端到端（执行器可替身）：一问一答落盘、messages[0] 恒用户原文、中间产物零持久化、usage 汇总、perspectives 元数据透传、abort 级联后主线零残留、fail-fast 后不落盘。
- 快照：三层节点共享同一份、tail 标记、快照进 backgroundMessages 不进 system prompt（基础设施既有锚，消费侧回归）。
- 推进闭环交互：engage 输入不过准入分类；active 推进会话下多视角 turn 照常进验收。
- CLI：进度投影事件消费、历史来源标记、失败呈现。

### 11. 不变量

1. `@` 触发解析只住接入面；发起协议与执行门面对触发源无感知——未来任何发起方式复用同一门面。
2. 多视角 turn 是普通串行 turn：不绕队列、不绕 busy、不绕 abort、不绕落盘接受协议。
3. 中间过程零持久化；落盘只有用户原文与最终版本一问一答，messages[0] 恒为用户原文。
4. 编排恒经内置编排文档模板实例化 + 全量校验管线；不得代码内联 definition 绕过校验。
5. 基础设施增强恒为通用语义，不出现多视角业务字面量；基础设施不为本需求定制耦合。
6. 视角数默认 3、上限 5，提示词声明 + 装配 clamp + caps 校验三层强制。
7. 快照一次捕获、全场共享、只读；子 agent system prompt byte-equal。
8. 主线 cache 前缀不受多视角流程影响。
9. 失败与中止不落盘半成品。
10. 视角、交叉、收敛等业务语义只存在于编排文档 instruction 与门面装配，不进基础设施抽象。

### 12. 提交与审查拆分计划

带依赖的可执行提交链，每单元独立构建、测试、审查：

| 单元 | 内容 | 依赖 |
| ---- | ---- | ---- |
| P1 | core 模板有界数组展开（含 params 协议放宽为有界结构化数组、组依赖替换、caps 兜底、测试） | 无 |
| P2 | core 节点 `modelRole` + orchestrator executor 按 role 选实例（测试） | 无 |
| P3 | server perspectives 门面：分配 strategy、内置编排文档、装配（档位序列 / clamp / caps 定值）、快照捕获、一等 turn、落盘与元数据、事件桥与透传（测试含端到端替身） | P1、P2 |
| P4 | wire `engage` + CLI：`@` 解析、进度投影、历史标记、失败呈现（e2e） | P3 |

P1 与 P2 可并行；P3 是门面集成单元；P4 是用户可见收口，对应基础设施文档 §16 单元 5 的「消费场景接入」。落盘承载已核实：`ConversationManager.recordTurn(conversationId, record: RunRecordInput, ...)` 接受自由构造的 RunRecordInput、不绑 main runtime——一等 turn 无结构障碍；P3 另须建立与 `runTurnWithCommit` 同构的 per-run 事件桥（§8）。
