# 草稿｜会话首屏历史、右侧滚动条与输入框上方提示

## 一、当前问题

1. **首屏让人误以为已经看到了全部消息。** 图一是刚进入会话的主页面。屏上只看到最近几条消息，没有可见的滚动条，也看不出上面还有历史。用户试着向上滚动鼠标滚轮后，更早的消息和滚动条才出现，如图二。用户如果不记得之前聊过什么，也没有主动试滚，就容易错过历史。
2. **应用滚动条与窗口右边缘有一段明显的距离。** 图二中，应用滚动条偏在里面，看起来别扭。图三中，鼠标移到最右侧，终端原生滚动条显现；这时仍能清楚看到应用滚动条和原生滚动条之间的空白。截图显示了间距，间距的成因有待查明。
3. **输入框左上方的提示组合起来不自然。** 图二、图三中，“下方还有内容 · Ctrl+End 回到最新”和“已恢复最近对话。”之间空了一行。按用户观察，这一区域目前看起来有三个提示位置，其中有些只在特定条件下出现。当上下两条出现、中间一条没有出现时，会留下明显的空档。这也暴露出一个需要整体考虑的问题：这一区域到底该告诉用户什么，又该怎样排布？

## 二、要求与完成条件

1. **首屏加载多少，要兼顾历史可发现性与启动速度。** 继续懒加载，不在启动时处理全部消息。重新判断首屏应加载、展示多少内容，以及怎样让用户在第一次滚动之前就能看出还有更早的消息。用户不需要靠记忆或试滚来判断；确实没有更多历史时，也应能分辨。
2. **先调研其他智能体终端怎么做，再为知行重新设计滚动方式。** 查清实际产品采用的是隐藏滚动条但保留滚动、应用自定义滚动条、直接使用终端原生滚动条，还是其他方式，以及相应的架构和实际使用效果。调研清楚后，再根据知行的需求决定怎么做。实现方式开放，判断标准是用户用起来顺手，并且不再出现图二、图三中滚动条离右侧有一段距离的别扭效果。无论沿用还是更换实现，都要守住已经解决的问题：滚动不能卡顿，滑块长度、位置及其计算要正确，不能闪烁，原有阅读和滚动功能要保留。
3. **先梳理信息价值，再重新设计整个输入框左上提示区。** 逐项梳理现在会显示哪些信息、每项在什么情况下对用户有价值、帮助用户知道什么或做什么。然后决定需要显示哪些内容、分成几行、每行放什么、何时出现和消失、同时出现时如何排列。行数由设计决定，不预设为现在看到的三行。方案要给出具体显示示例，至少能看清只有一条提示、多条同时出现，以及中间一项缺席时各是什么样。需要显示的提示应自然相邻，不能空出一行；也不能为了紧凑而砍掉功能或让用户错过重要信息。
4. **保住既有体验，按真实操作验收。** 启动和首发性能不能因这次调整回退。实施后的验收要在真实终端里看首次进入、上滚、鼠标移到最右侧、返回最新位置和提示切换的实际效果，并覆盖短会话、长会话及窗口大小变化。
5. **工作方式与停止点。** 当前先审查这两部分。用户确认后，总控和负责人按先后顺序，各自独立分析同样三个问题，分别提出根本原因和解决方案，再交叉质询、有分歧就补证，不限轮次。以符合需求、体验和架构为准，不以改动量决定方案。双方认可后向用户报告，再由用户决定是否实施。

## 三、会话阅读设计（2026-11-04）

本节记录三个问题的根因、设计取舍与验收条件。本轮交付到设计，产品改动与实机效果验收在实施阶段。

### 1. 恢复会话时，首屏就让用户知道还有没有历史

**根因。** 在线、离线恢复都按固定的少量片段取首页，一次传输最多四片。片数与用户能看到几行无关。生产阅读视图原本会在内容不足一屏时请求邻页，但它比较的是已经被布局撑到至少一屏的内容高度，严格小于视口的条件无法识别短尾。与此同时，界面知道源端可能还有更早消息，却只提示下方内容。欢迎框接上最后几条消息，画面就像完整会话。用生产渲染器做独立对照，209×52 下短尾内容高度和视口同为 46 行，碰滚轮前自动取旧页 0 次，上滚一次后取 1 次；120×40 下也复现了两者同高、没有补读。

**首屏显示。** 保留有界首页，不为凑满屏幕多等一次读取。从首个可读正文帧起，只要有可向上阅读的正文，就显示可点的“↑ 上方还有内容”。判断依据有三处：屏内顶端以上的正文、已挂载窗口之前的可读缓存、源端已知还有的历史。同一条长回复的前半段即使分属不同传输页，措辞和动作也一样。欢迎装饰不算历史。确认到头才在第一条消息前标出“对话从这里开始”；空新会话省略，尚未查明或读取失败时保留相应状态和动作。离开最新且下方有内容时提供“↓ 回到最新”。两方向共用一行。

**后台准备量。** 可输入之后才根据当前宽度下的正文自然行高补邻页，以已显示和已备妥的连续内容合计，目标为一屏正文加约一屏阅读余量。已经备好、尚未挂载的页也计入目标与内存上限；欢迎头和撑高留白不计。先用缓存，再按需向源端逐批读。每次进入有独立的读取量与步数上限（自动补读片段初值最多 40），空页和准备步骤也计入预算；沿用现有传输和阅读窗口上限（1 MiB、256 片、8192 节点）。达到目标、到头、无进展、失败或达限即停止自动补读，仍有历史时入口保持可用。

**何时上屏。** 首个正文帧一旦可读，即保护其中的文字，静默阅读也适用。图一这种顶部对齐、内容不足一屏的情况，邻页准备好后先留在缓存，保留当前画面。只有插入点已在屏外、能按原文锚点维持可见正文所在行列和选区时，才允许被动并入；不能保证就暂存。滚轮、触控板、翻页键或点击向上入口时，才按用户动作揭示旧内容。缓存已准备好时，第一次上翻直接显示内容，不再请求同一页。尚未备好时记住这次翻页意图，与在途读取合并；读取成功即完成原动作，无须再滚一次，失败可重试。由实时新消息引起的跟随仍按原阅读意图处理。这样高窗口里的短会话首屏可能仍有留白，但能立刻看出上方是否还有内容，也不会挪动眼前那句话。

N（终端应用适配）复用同一读者、游标和有界显示存储；U（终端视图）在现有阅读窗口预算内区分已准备和已显示的范围。预取不能改当前显示游标、关闭跟随或重置补丁基准。输入、提交、导航和选择优先，发送路径不等待预取。切会话或反向导航使旧意图失效，迟到结果不能改变新画面。

### 2. 会话不画应用滚动条，滚动功能照常

**根因。** 两人分别测得应用滑块已位于可绘字符网格的最后一列（209 列的第 208 列、120 列的第 119 列，均从 0 编号）。第三张原图中应用滑块占 x=1880…1888，宿主滚动条自 x=1904 开始，中间实有 15 像素空白。可绘网格与宿主窗口右缘是两个边界，网格右侧是宿主自己的文本内边距与原生滚动条槽，不在应用可绘的字符网格内。[Windows Terminal 外观设置](https://learn.microsoft.com/en-us/windows/terminal/customize-settings/profile-appearance) 因此只要应用在网格内画竖条，它就一定落在宿主槽的左侧、与窗口右缘隔一段；鼠标移到最右时，宿主原生条出现，两根并排。换列、换字符、只在滚动或悬停时显示、放进带框的局部区域，都改变不了这一点。

**同类终端。** OpenCode 会话源码默认隐藏应用竖条，仍由应用处理纵向滚动。Claude Code 全屏模式和 Codex CLI 全屏阅读也提供应用内翻页及回到最新。各产品采用这些做法的具体原因不必相同。知行已有固定输入框、流式更新和有界历史读取；保留现有阅读方式即可解决实测的双条间距问题，无需改用宿主回滚。[OpenCode 会话源码](https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/tui/src/routes/session/index.tsx) · [Claude Code 全屏阅读](https://code.claude.com/docs/en/fullscreen) · [Codex CLI 两种阅读方式](https://github.com/openai/codex/discussions/49129)

**设计。** 对话页和历史阅读页在静止、滚动、悬停窗口最右缘和拖选文字时，都不画应用滚动条。原先预留的一列还给正文，测量、折行和鼠标命中使用同一宽度。宿主自身的滚动条仍由宿主绘制，不改宿主设置。配置、技能等其他页面的列表滚动条不在本项范围，保持原样。

**滚动功能照常（底线）。** 以下操作全部保留，行为不变：
- 鼠标滚轮与触控板上下滚动；
- PgUp/PgDn 翻页；
- 点“↑ 上方还有内容”上翻一页，并按需读取更早内容；
- 点“↓ 回到最新”或按 Ctrl+End，回到最新并恢复跟随；
- 选区与复制；
- 离开最新后有新回复，不抢走阅读位置；
- 缩放后按原文锚点保持阅读位置。

上下是否还有内容、怎样回到最新，由第 1 节的阅读行表达。

**取舍。** 会话不再提供拖动滑块或点击轨道。上下翻一页保留 PgUp/PgDn 和滚轮；向上提示翻一页，向下提示直接回到最新。滑块长度与位置的验收随会话滑块取消；滚动流畅、不闪烁以及其余阅读功能的要求不变。

### 3. 正文导航与输入状态分别排布，只让有价值的提示占行

**根因。** 无待办或任务全部结束时，任务列表会返回合法的“已就绪、摘要为空”。视图把空摘要加入细节列表，过程区按列表项数算高，于是空字符串实占一行。生产组件对照中，无摘要时“下方还有内容”和“已恢复最近对话”在第 46、47 行；只改为就绪空摘要，便显示在第 45、47 行。另有一处无文案也占行的固定阅读提示。保留“已就绪”的成功语义，呈现时过滤空条目，避免空任务列表被误判为读取失败。

| 信息 | 何时有用 | 显示位置与动作 |
| --- | --- | --- |
| 上方内容、下方内容、回到最新 | 该方向确实还有可读正文，也可能仍在同一条消息内 | 正文下沿的一行阅读导航；可点击方向提示、在正文内上下滚动 |
| 历史读取中、失败、正文待恢复 | 正在等待用户需要的内容，或需要重试 | 阅读导航保留方向及有效的重试动作，故障优先，恢复后撤掉 |
| 当前操作、恢复回执、提交结果、未接纳原因与草稿保留 | 用户需要知道刚发生什么，以及下一步能做什么 | 紧邻输入框，普通回执由下一次操作替换；未解故障和必要动作持续可见 |
| 运行、核对、有效任务与子任务、工具进展 | 实际有工作在进行，或有失败需要处理 | 按需排在当前状态上方；无有效摘要占零行 |
| 终态、用时和用量 | 本轮终结且有对应数据 | 在终态显示；空间不足时先保必要结果、失败和处置入口 |

导航行在正文外，不遮住最后一行文字或选区。无阅读信息就把空间还给正文；用不含导航行时的可用高度判断是否需要它，同次布局保护阅读锚点，避免显隐反复触发重排。状态区不预设三行，空闲且没有信息可以为零行；多项相邻排列，重要的长说明可折行或沿现有入口完整查看，去除重复文案。输入下方快捷键、候选和确认功能保留。

| 场景 | 输入框上方实际看到的内容（从上往下） |
| --- | --- |
| 短会话已全部在屏内，只有恢复回执 | 一行“◆ 已恢复最近对话。” |
| 已上翻、无任务摘要 | “↑ 上方还有内容　↓ 回到最新”，下一行紧接“◆ 已恢复最近对话。” |
| 已上翻，有有效任务正在执行 | 阅读导航、实际任务进度、“◐ 正在处理…”三者相邻 |
| 正文读失败，同时输入未被接纳 | 可点的阅读重试，以及紧邻输入框的未接纳原因、草稿保留和下一步，两项都能看到 |

### 实施后的验收门槛

用同一构建、原宿主、固定资料和既有冷热分组，对比首个可输入帧和立即首发的系统等待。同时记录补页到目标耗时、实际读取量，以及与立即发送撞车时的等待。不能用后来才出现的提示冒充首屏可发现，也不能把后台工作的耗时算作已消除。

在真实终端亲看空/短、恰一屏、短尾有旧页、单条长回复、长历史和预算耗尽。分别操作轮滚、触控板、键盘翻页、点击两端提示、悬至最右、缩放、选区复制、候选显隐、切会话、收到新消息、回到最新及读取失败重试。逐项核对无应用竖条、提示相邻、无文字被盖、滚动流畅且不闪烁、启动及首发性能不回退。

针对图一，记录首个可读帧的可见原文与行列，保持窗口和业务内容不变，整个预取期间不碰键鼠；逐帧核对这些文字原位保留。分别在缓存已备好、读取在途时只上翻一次，核对前者无需再读、后者读取完成即兑现这次动作。另用跨传输页的单条长回复，验证上下提示准确，“回到最新”的目标清楚可辨。在已有选区及实时输出时分别验证老页晚到不会覆盖选区、打断跟随或让已上翻的用户跳回底部。

针对图二、图三，在真实 Windows Terminal → CMD → zz 中，分别在短会话和长会话里走查：
- 用滚轮、触控板、翻页键和两端提示回看，再回到最新；
- 在静止和滚动中，把鼠标移到窗口最右。

逐项核对：
- 任何状态下都没有应用竖条，最右只出现宿主自身的滚动条；
- 原竖条列已还给正文；
- 正常宽度、窄窗及缩放后，滚动流畅、不闪烁、阅读位置不跳；
- 输入框与草稿不受影响。
