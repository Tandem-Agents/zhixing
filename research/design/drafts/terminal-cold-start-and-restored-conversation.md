# 草稿｜真实冷启动等待与恢复对话后的消息区留白

## 一、当前问题

**1. 从输入 `zz` 到真正可以发消息，用户等了约 14～15 秒，可能更久。** 2026-11-03，用户在 Windows 的 `cmd` 中运行 `zz`。体感上，回车后约 3 秒完全没有反馈，随后终端页面显示启动或加载约 10 秒甚至更久，最后又显示会话准备约 1～2 秒。进入后恢复了最近的对话。这是已有配置和历史资料的冷启动，与首次安装后的空白配置向导是两种场景。

负责人用真实资料和真实 `zz.cmd` 复现过一次。启动前已确认原 Host（后台服务）退出。以下是同一次启动的连续阶段：

| 用户经历的阶段 | 本段耗时 | 自发起起累计 |
| --- | ---: | ---: |
| 发起启动，到第一帧可见 | 2.255 秒 | 2.255 秒 |
| 第一帧可见，到 Host 就绪 | 8.259 秒 | 10.514 秒 |
| Host 就绪，到最近对话恢复、首屏历史就位、界面真正可发送 | 5.692 秒 | 16.206 秒 |

这组复现包含新建 `cmd` 窗口约 0.9 秒，文件缓存也可能已热，因此不能把这三个数字逐段套到用户原例上。此前验收的 4.583 秒、4.877 秒分别是固定条件下短、长历史冷启动组的中位数。两个结果需要解释。原例的完整分段日志已不可查；复现中观测到后台恢复与前台准备重叠、前台等待队列和锁，但整段耗时的根因及各项净影响尚未获双方确认。[原验收记录](../../../docs/tasks/terminal-migration-delivery-plan.md)

**2. 恢复对话后，欢迎框和第一条消息之间空出了大半个消息视口。** 用户截图中，欢迎框在顶部，已有消息集中在下方，输入框在底部。双方已独立定位到布局原因：主会话跟随最新消息时，如果正文不足一屏，界面会在欢迎框和正文之间插入一个空白块，高度取视口高度减去内容自然高度。现有原生测试还把这种留白写成了期望。这个现象可以由布局直接解释，无须假设聊天记录多了空行或文字被画成黑色。[渲染实现](../../../packages/terminal-ui/src/body-view.tsx) · [原生布局用例](../../../packages/terminal-ui/src/__tests__/reading.native.tsx)

## 二、要求与完成条件

- **按用户实际使用方式定位和验收。** 在已打开的 `cmd` 中输入真实 `zz`，使用有配置、有最近对话的真实资料；启动前确认目标 Host 已退出，记录运行入口、制品、上次停机方式和已知缓存条件。从回车开始，分别记录首次可见反馈、加载、会话准备、真正可发送。隔离实验可以用来验证某个机制；空资料、同 Host 热入、刚连续运行过的重复冷启动分别标注，不能替代主对照。
- **同时解决无反馈和可用过慢。** 回车后要及时出现明确反馈，或直接进入页面。可用时间沿用同条件冷启动中位约 5～7 秒的目标，保留并解释严重慢例。提前显示一句提示只解决无反馈；仍要验证页面可发送时首条消息确实能被接纳，启动成本没有被推到首发之后。[启动性能口径](../../../docs/tasks/terminal-startup-performance.md)
- **修正短对话布局并亲看结果。** 恢复短对话时，正文从欢迎框下按正常间距开始。恢复长对话时仍能跟随最新消息，向上阅读、缩放和输入区位置保持正常。用真实终端画面验收这两种情况。
- **两个人串行独立解决同一组问题。** 总控先对启动三个阶段和布局问题分别形成完整的根因判断、证据和修复方案；负责人随后对同一组问题独立完成同样的工作。双方都完成后再交换、质疑。证据不够或方案不彻底，就按相同顺序继续下一轮。架构取舍以能否彻底解决问题并守住正确性、安全性和体验为准，不以工作量裁剪方案。
- **当前停止线是报告。** 双方明确认可根因和方案后，先交用户审查。生产修改须等用户后续决定；实施时由负责人执行。

## 三、双方诊断结论与修复方案（2026-11-04，v8 工程独审通过）

总控和负责人分别调查了同一组问题，并交叉核对了证据。双方确认了下表四个具体问题。**真实冷启动复现耗时 16.206 秒，主导这次长等待的原因仍未证实。** 分派回放的 CPU 采样来自另一次 7.631 秒冷启，扩展归档的差值来自局部对照。两者都说明有可消除的工作，不能合计为此次慢例的解释。入口提早显示只能缩短无反馈时间；短历史留白有独立的布局根因。

**当前决定（11 月 3 日 19:31）。** 用户已同意负责人先完成已证实的修复。短历史布局、入口反馈和扩展验证复用已产生代码变更；负责人记录的针对性检查已过，仍有依赖构建产物的用例及真实终端验收。分派账本已开始修改。其首步方案仍逐条读取、归约旧记录，只复用已验证前缀的验签结果。因此即使重复验签消失，也只能确认这项收益；要判定冷恢复工作量已与历史长度解耦，还须在当前状态相同、历史长度不同的对照下核实实际读取和归约量。

**关闭条件。** 负责人交付后，总控分别裁决四项修复效果和真实冷启动整链。只有前者通过时，只关闭相应单项。若同条件复测仍有同类长等待，或证据仍不足以解释整链改善，总控先定位、负责人再独立定位，双方核对后继续处理。完整关闭须满足本节末尾的整体验收条件。

| 问题 | 已确认的机制与证据 | 建议修法 |
| --- | --- | --- |
| 回车后没有反馈 | 默认交互入口在校验、恢复进程准入和 UI 握手完成后才出现第一个产品画面。已打开的真实 cmd 中，隔离对照基线首次出现产品文字为 1.149 秒；只在入口提前给出提示的诊断原型，156 毫秒便可见。后者只测首反馈。 | 在默认交互入口尽早给出最小启动反馈，由同一时刻唯一的输出方负责；UI 接管、失败、取消、退出都要正确交还屏幕。普通命令和重定向保持原输出。可发送仍以真实准入为准。 |
| 冷恢复的工作随历史增长 | 执行账本首次触及某个未缓存分派时，从空状态开始重放该分派的历史信封。真实 Host 的采样栈显示，它在归约时重新校验控制租约签名、规范化数据。在一次 7.631 秒的诊断冷启中，可发送前两个不重叠的阶段窗口内约有 1.07 秒采样落在这条回放链上。固定当前分派状态，已有续租记录为 2、8、20 条时，生产账本的冷查询分别触发 3、9、21 次租约验证，紧接着再查均为 0 次。 | 启动只读取足以作当前决定的、有界的已验状态。可复用的状态要绑定日志身份、已验证的位置、分派身份和归约规则版本；对新增事实继续完整校验。资源回执、租约时钟、导入和灾备等校验边界继续成立。历史证据按需读取，不能把完整历史换成一个同样不断增长的快照。 |
| 随包扩展的条件性启动开销 | 对已经收编且匹配分发种子的扩展，通道激活会读取整份源码归档并同步解析 JavaScript。在已收编但停用的随包扩展上，生产激活的 A/B/A 对照为 460 / 57 / 470 毫秒；B 仅复用整份归档逐字节一致、且已完整验证过的结论。这个局部差值不能直接从 16.206 秒中扣除。 | 由负责收编、修复和使用归档的组件维护与完整内容、校验规则版本绑定的验证结论。启动复用时保留可执行制品和准入校验；首次收编、归档缺失、内容被替换、编辑和回滚都要验证。 |
| 恢复后消息区上半屏空白 | 主会话跟随最新消息时，布局在欢迎框和短正文之间插入剩余高度的占位块，原生测试也明确断言该位置应当留白。 | 去掉这段额外占位，让短正文自然紧接欢迎框；过一屏仍跟随最新，保留滚动位置、选择和输入区。同步更新原生断言并亲看真实短、长对话。 |

**尚未证明的部分。** 真实慢例的「服务就绪 → 可发送」为 5.692 秒。记录中的 1345 毫秒是一次后台操作的锁内墙钟，1487 毫秒是随后六次前台读的合计锁等待，两者不能直接配成持锁方与等待方。此前分段记录不足以还原原例的具体持锁者或重放条数。慢例的部分阶段 CPU 时间较高，不能据此认定当时降频。两个隔离场景各空闲 180 秒未观察到分派目录净增长，不能认定空闲必然持续追加续租。恢复让行仅在能复现竞争、验证净收益且不推迟首发或遗漏恢复义务后考虑；空闲日志的持续读写另行归因。

**整体验收。** 在同一候选、目标 Host 确已退出、已配置且有最近对话的真实环境，从已打开的 cmd 回车起，分报可见反馈、服务就绪、会话准备、首屏历史、真正可发送，以及立即发送首条消息后的系统等待。按原目标检验冷启动中位约 5～7 秒，保留并解释严重慢例。以长短续租历史对照检验恢复工作量，以损坏或失效的证明、在途取消及已接纳工作检验拒绝行为和恢复终态。如仍出现同类数秒等待，就按同一次运行关联前台请求、队列与实际持锁操作继续定位，不用快样本放行。

**11 月 3 日 20:31 阶段审查。** 首反馈和短历史布局已通过第一轮独审。该轮连续六次退出 Host 后启动，到可发送的中位约 6.2 秒；构建后第一次的 9.79 秒属于提示编码修正前的样本。隔离首发的六次边界对照均显示输入并只发起一次主请求，原有一次丢键观察未复现。扩展归档返修后，总控直接调用当前源码复验：正确归档可识别，种子源码不匹配清单摘要时不能快速放行，合法归档 B 放在 A 的目录时快速核对与完整读取均拒绝。该项待最终构建复核。分派账本仍处于只减少重复验签、仍读整段历史的阶段。负责人已撤回不能解决历史增长的检查点草案，正在按启动实际所需数据重新设计；整链尚未关闭。
