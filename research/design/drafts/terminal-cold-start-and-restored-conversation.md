# 草稿｜默认打开与切换对话后的历史、空正文与欢迎块

## 一、当前问题

1. **同一个有内容的对话，两种进入方式表现不同。** 用户默认打开时能看到已有消息；从对话列表切回“日常问候寒暄”，画面仍有部分消息，并提示“↑ 上方还有内容”。向上滚轮后，出现图一的“读取未完成 · 点击或原方向翻页重试”。要查清提示所指的更早内容是否存在，以及这次操作为什么没有读出来。
2. **切到“打招呼问候”后，正文和欢迎块都消失。** 图二仍显示“已切换到 打招呼问候”、输入框和快捷键，输入框以上的主体区域全空。需要分别查明该会话本来有没有可见消息、欢迎块为什么消失。
3. **列表里另外几个对话切过去只有欢迎块。** 用户目前只在第一个对话看到了消息，其他有欢迎块的对话有可能本来就是空的，也有可能应有的历史没有显示。需逐个核对，不能依据名称、目录条数或界面空白推断有没有正文。

## 二、要求与完成条件

1. 按真实用户路径定位。对照同一会话的默认恢复、从列表切入、切走再切回及上翻一次。分别记录目标会话、权威来源是否有可见正文、历史页返回情况、终端实际呈现和阅读提示，区分用户实测、独立复现及尚未证实的解释。
2. 对已有消息的会话，切换后应显示属于该会话的内容，确有更早正文时第一次上翻就应有效。查清是历史边界报错、读取失败还是显示失败。真实故障要保留可重试提示和当前正文；只改提示文案不能解决正常切换中的异常。
3. 对确实没有可见正文的会话，欢迎块与输入框应正常显示。不同会话不能串用旧正文、历史边界、游标、选区或迟到的读取结果。把正常空会话、读取尚未完成和读取失败区分开。
4. 保留有界懒加载、静默阅读保位、滚轮与键盘翻页、回到最新和输入体验。保护启动与立即首发性能。按实际切换和滚动过程验证，资料核对使用产品的只读入口，以必要的计数、边界和错误作证据。
5. 总控先独立定位这些问题、形成并冻结根因与方案，再将同一组问题和两张原图交给负责人独立定位。各自完成后交换证据、交叉质询；有反例继续核实，直到双方认可可落地的最优解决方案，再向用户报告。当前交付到诊断和方案，实施由用户决定。

## 三、根因与修复方案（双方定稿，2026-11-04）

**真实资料核对。** 总控通过产品已认证的本机只读接口，取完会话目录并逐个读取可见历史至结束。下列数字是来源片段数，一条消息可以占多个片段。

| 可见正文 | 会话 |
| --- | --- |
| 12 片，首页之后还有内容 | 日常问候寒暄 |
| 各 4 片，有正文 | 本机验收-20260924、chat-20260922-3174 |
| 0 片，已确认到头 | 打招呼问候、默认对话、lock-test、chat-20260922-214f、收尾验收-20260924 |

1. **“日常问候寒暄”上翻失败。** 列表切换时，终端应用重新构造当前会话视图，漏掉启动路径建立的就绪状态。首页能读到，界面也知道还有历史，但应用随后据此拒绝继续向来源取页。两人分别复现。在隔离真实入口中一次上翻触发五次无进展回复，期间请求历史源 0 次，最终界面提示重试。在同一游标上恢复读取条件后，真实只读接口能再返回 4 片。
2. **“打招呼问候”连欢迎块都不显示。** 它确实没有可见消息。切换时界面先重置阅读状态，却仍用上一段正文的起点初始化新会话的最早位置。旧起点为 −4、新空页起点为 0 时，欢迎块被错误隐藏。按同一构建依次切换“有正文 → 空 → 另一个空”，第一个空会话不显示欢迎块，第二个显示。负责人也独立核对了六次显隐。
3. **另外两个有正文的会话。** 对“本机验收-20260924”和“chat-20260922-3174”，总控分别将产品只读接口返回的数据送入生产历史投影和渲染组件。按普通切换时身份先到、首页随后到的顺序，两者的欢迎块都可见，首页 4 个片段也各自全部在屏上得到辨识。此项检查不复原用户当时的点击和逐帧时序，不能断言当时是哪一步造成空白，也不能据此推断用户选错了。

**必须覆盖的重建边界。** 普通前台切换在发布目标视图并得到确认后才发首页；不能把任意交换两种消息的实验当成上述两个会话的现场归因。前台确认或其他页面可挡住主视图发布；同一会话被清空或来源要求重新读取时，正文会重建而会话 ID 不变。现行界面只看 ID 变化来重置窗口。总控在生产渲染器中送入同 ID 的四片正文、清空页、再送两片负序号首页，先复现欢迎块消失，随后复现两片全部被旧空窗口裁掉。另一个独立反例是只补切换就绪标志：负责人的隔离对照实测，两片短对话会只显示回答，提问被留到下一次上翻。仅改就绪标志或仅调消息发布顺序均不足以覆盖这些情形。

**修复方案。**

- **由终端应用管理每次正文重建。** 默认打开、切换、清空及确实要求重建的重新连接，均为目标建立新的阅读代次。改名和普通刷新沿用原代次。切换后正确发布输入就绪状态；能否取更早内容由该代首页是否落定决定。首页按既有预算一次读取，未落定前不逐片发布、不启动预读，期间到达的实时内容按原有来源顺序接续。
- **在现有正文通道建立一次完整基准。** 用现有整页消息携带会话身份、阅读代次、基准修订号和“是否还有更早内容”。该代后续补丁只引用这个基准或其后续修订，兼顾首屏信息与已有流量上限。新代首个完整页直接安装，即使起点为负数也不得按旧窗口裁剪。只有同代次的静默预读保护已显示内容的位置。相关翻页请求和回复都绑定代次，过期请求不推进新会话游标。
- **界面只维护一个正文窗口。** 当前视图声明期望的会话和阅读代次；只有两者都匹配才显示正文。新代完整页负责一次重置阅读窗口、欢迎块起点、补丁基准、选区、位置和过期读取意图。正文先到，安装在同一窗口，待匹配视图到达才显示；视图先到，则显示目标欢迎区和加载态。旧代迟到不覆盖新代。仅来源确认零片且到头才进入正常空态；首页失败在目标欢迎区给重试，后续翻页失败保留当前正文。首页可读、可上翻之后，第一次上翻须兑现；切换前旧会话的上翻不带到新目标。

**确保返回后能看见正文。** 发布阅读视图时，根据它实际要显示的会话取得当前期望代次。保存页面以便返回时，不保存这个代次。每份仍然有效的完整首页，都必须最终有一份身份和代次严格相等的阅读视图送达。若确认页、选择页等暂时挡住主视图，关闭前台页时重新发布当前目标视图；期间已被替换的首页无需补发旧视图。

**实施后的验收。** 用同一构建从默认恢复和真实选择列表分别进入多页、两片短正文及确认空的会话；核对目标身份、正文唯一标记和首页/上翻的实际来源调用。覆盖 A→空 B→空 C→有正文 D→A、同 ID 清空/重建、快速切换时旧响应晚到、正文与视图两种到达顺序、先有加载占位再交付首页。单屏两片应一次显示完整；多页只上翻一次就显示更早正文；空会话始终保留自己的欢迎块与输入框。另验真实失败重试、静默预读不移动正文、缩放和回到最新，核对冷启动与立即首发的同口径耗时。

同 ID 原地清空后检查欢迎块，再发送一条消息看其是否正常显示。确认页在前台时发生切换，返回后只应看到目标会话。另验首页读取失败和后续页失败各自的重试，并确认离线历史不会因此取得在线发送许可。

还须走通两条返回路径：确认页在前台时同 ID 会话被清空，再关闭确认页；进入 F2 离线历史期间发生正文重建，再按正常路径返回。终点应是目标正文或已确认的空态，不能一直显示“读取中”。
