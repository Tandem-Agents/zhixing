## 开发单元审查分片机制

### 一、问题来源

案例来自“知行”项目的 **distributed-runtime 模块第 13 单元：conversation 取消、结果不明裁决与三分续跑**。

该单元横跨 3 个代码包、15 个交付文件，约 1.1 万行生产代码变更、7153 行测试变更，总变更约 1.83 万行。单次上下文难以同时容纳完整架构、实现和验证事实，压缩后反复重建认知，造成约一天半的开发审查周期。局部路径虽然通过，但跨生命周期、跨执行点和恢复重放问题多轮后才被发现，形成重复审查修复。

这只是机制产生的案例，不是机制适用范围的限定。

### 二、机制作用

本机制有两层价值：

1. **跨窗口复用**：同一审查轮中，已完成切片不因压缩或续跑而重建证据链。
2. **跨轮次复用**：后续审查轮中，局部封版切片不再重复深审。

两者只跳过切片级重复工作；每轮完整单元横向审查始终保留。

### 三、核心方案

采用：

**一个架构验收单元 + 可选审查切片 + 两维状态 + 每轮完整单元横向审查。**

切片不改变架构单元的编号、范围和验收责任，也不产生独立通过结论。

- **切片纵向深审**：展开闭包细节，产出局部结论、对整体的保证、适用边界、证据索引和重开条件。
- **完整单元横向审查**：消费切片结论，核查全部需求、不变量、切片边界、跨片链路和组合场景；有疑问时可下钻任何细节。
- **协作关系**：切片封版信息包 → 完整单元横向审查 → 无疑问则复用，有疑问则下钻，确认问题或结论失效则重开切片。

### 四、分片时机与适用条件

初次判定在单元边界锁定后、问题盘点前；每轮审查开始前按实际交付物确认。只判断“是否需要分片”，不划分小、中、大等级，也不设置通用数量门槛。

同时满足以下条件才启用：

1. 不分片会使已完成的局部审查在续跑时被重复建立。
2. 审查对象能够按事实与合同闭包拆开，并明确依赖和失效范围。
3. 完整单元不变量与跨切片场景可以预先登记，且每轮仍保留横向审查。

任一条件不成立，沿用现有完整审查流程。

### 五、具体执行方式

有效切片遵循四条规则：

1. 一片只承载一个可独立裁决的合同或不变量闭包。
2. 该闭包的生产端、消费者、异常路径和测试必须在同一片内；同一事实链不得拆开。
3. 依赖、输入基线、局部验收和重开条件必须明确；跨片组合登记为完整单元必审项。
4. 若一片仍需重读大部分其他切片，或切片间事实高度重叠，则合并切片或不分片。

执行流程：

1. 先建立完整单元的不变量、覆盖矩阵和跨切片必审场景，再按上述规则定义切片；禁止按文件数机械均分。
2. 每个切片同时维护：
   - **本轮进度**：`待审查、审查中、已完成、失效`。
   - **收敛状态**：`未收敛、待修复、待复核、局部封版`。
3. 同一轮续跑只恢复“待审查/审查中”，跳过“已完成”；进入下一轮时只为非局部封版切片建立本轮任务。
4. 审查无问题转“已完成 + 待复核”；发现问题转“已完成 + 待修复”；修复并通过直接验证后，以新基线转“待审查 + 待复核”。待复核在同一输入下获得一次独立无新增确认后局部封版，确认可来自后续切片复核或明确覆盖该切片的完整单元横向审查。
5. 每轮切片阶段结束后执行完整单元横向审查。整体默认消费封版信息包，有疑问时可下钻细节；疑问消除则保持封版，确认问题、证据不足或适用前提失效则重开。
6. 输入或依赖变化转“失效 + 未收敛”，登记新基线后转“待审查”；横向审查确认真实问题时转“待修复”。冻结指纹变化使对应终审轮整体失效。
7. 切片纵向深审与完整单元横向审查结束后才统一裁决、集中修复。全部切片局部封版、两轮完整终审及最终验证通过后，单元才能完成。

### 六、与工作台的关系

本机制嵌入现有流程，不另建平行流程：

- 主工作台在边界锁定后增加“分片判定”。
- 单元文件以“分片决定 + 两维状态账本 + 横向审查记录”保存进度，仍是唯一权威状态源。
- 同轮续跑只恢复未完成切片；新一轮只激活非局部封版切片。进入横向审查或转换阶段前完整读取单元事实包。
- 切片使用单元内编号，不拥有独立 generation、冻结指纹或完成资格。
- 只有完整架构单元可以冻结并宣布通过。
