### U34-04、U34-09 最优方案执行合同

- **U34-04**：从当前 `planned-anchor-installed`、signed commit/trust record 和安装后 log checkpoint 生成独立、不可变的 `InstalledAuthorityGeneration`；`MeshRuntimeBootstrap` 无论 private post-install progress 是否仍存在，都向两个 current-anchor profile交付该 tuple，`plannedAnchorPostInstall` 仅表示尚待消费/cleanup，二者不得复用可选性。`setupAuthorityRuntime` 初启与 live `onInstalled` 共用一个 planned-only、无动态注册 API 的显式协调器：固定 named record 覆盖 F34-24/25 exact-set，先在既有 planned/current-owner gate 内停新写并等待各 owner 串行安全点，再一次更新 runtime epoch、清旧 external cursor/cache、从新 composite prefix恢复 substrate，最后重建 scheduler lazy children并调用既有 conversation/delivery恢复。每个 named participant须回报同一 tuple；六类 obligation逐项读回后才清 private progress和开放 surface。任何失败保留 installation、gate和未完成回执供 live/启动重驱；禁止把 `flush()`、callback成功、进程重启或单 consumer reset当成完成。
- **U34-09**：target-wide candidate journal成为 remote prepare 与 signed abort 的唯一先后点。prepare decision须保存完整已验证 `anchor-prepared` 可重放对象；abort decision须保存完整 signed `AnchorTransferAbort`。收到 abort 后先验证外层 command 与内层 abort均由 candidate source签名，并全等反绑 request/transfer/source/target/sourceEpoch、candidate home/trust及stored ReadyProof；这是历史身份/签名校验，不重跑会过期或漂移的 readiness 准入。transfer issuer key若仍存在必须与stored proof全等，若已不存在按幂等cleanup继续。无 prepared decision/per-transfer phase时直接耐久 signed aborted；prepared decision已赢但 phase尚未物化时，先从其原对象补写原 prepared，再走既有 abort reducer；已有 phase原样走 reducer；committed/released/异 identity均零副作用拒绝。cleanup只消费已耐久 terminal，恢复同时扫描 candidate与phase journal，claim-only exact replay直接返回所存 signed abort，禁止伪造 target prepared、回退 unsigned release或新增通用锁。
