# 开发单元审查与修复工作台

> **静态区**：本区记录固定问题、收敛规则和提示词，未经用户明确要求不得修改或清理。

## 一、问题描述及分析

第 8 单元主体开发约用 40 分钟。随后以“修复到本单元没有问题为止，并连续两轮审查无新增问题”为目标进入审查修复，约 3 小时后仍未完成：第一轮无新增问题审查尚未通过，最新修改仍待验证。

实际过程中，先后围绕秘密存储、迁移、并发与崩溃恢复、安全边界、凭据最小投影、启动流程及其消费者发现问题；每发现一处便进行修复和局部验证，再继续审查，后续又发现其他问题并重复该过程。实际工作循环是“审查发现问题 → 立即修复 → 局部验证 → 继续审查”，没有先形成一份完整问题清单再集中处理。

## 二、目标模式协作协议

### 1. 唯一目标与完成条件

在不降低审查深度、测试覆盖或最终质量的前提下，高效完成当前单元的审查与修复：必要影响面达到最优架构、不留已知债务；同一份未修改交付物的全部验收与必要验证通过，并连续两轮完整审查无新增真实问题后立即结束。

后续单元、无关重构和架构未要求的无限防御不在范围内；确需改变边界时先重新确认，禁止静默扩面。

连续工作期间，在适当节点以百分比向用户反馈当前单元距最终完成条件的整体收敛进度，不以单轮或单阶段进度代替。

### 3. 五条核心规则

1. **关键原语查透**：对每个状态变化、耐久写、并发竞争或外部副作用，逐项核对唯一事实源、生效/线性化点、崩溃与竞争插点、全部生产者/消费者、时间与空间上界；存在缓存、索引、增量计算、短路或其他快速路径时，以权威事实源上的完整计算为正确性基准，列明成立与失效条件，并用正反例差分验证等价，无法证明则不得冻结；再映射九类核查面。缺一项，问题盘点不得结束。
2. **先审完再修**：问题盘点整轮只读，只登记问题；全部扫完后按根因合并，一次覆盖生产端、类型组合、消费者、异常终态和测试，再集中修复。
3. **闭包先于冻结**：问题盘点零问题或集中修复完成后，都必须进入冻结准备。交付物文件集中的每个文件或同类组必须在派生产物闭包表中落账，覆盖其 lockfile、golden、schema/快照及结构/导出基线；无派生项须写明依据。存在未归类项、待核查项或未同步项不得冻结，也不得提前运行包级全测、全量构建或最终门禁。
4. **昂贵验证只跑一次**：冻结前将最终验证展开为精确命令、输入闭包、依赖顺序和复用证据；组合命令须先展开，剔除已有同输入证据覆盖或范围外的子项，存在“待确定/待计算”不得冻结。两轮终审零新增后严格按“最终验证”门禁执行；最终构建单独运行，包级全测逐包串行，禁止人为增加跨包资源竞争。
   - **粒度阶梯**（中间轮补证据取最小档）：改单用例/断言 → 定向单例；改单个生产文件 → 运行与其直接相关的测试；改共享合同 → 合同自身测试 + 直接消费者定向集；包级全测只属于集中修复后的合并直接验证与最终验证。仅当上档严格覆盖下档、命令配置与输入指纹相同才可跳过下档；构建、类型检查、测试彼此不互替。
   - **构建边界**：包内改动用类型检查 + 直接相关测试；仅当下游消费构建产物或进入最终验证才构建；跨包新导出先按依赖方向构建上游。
   - **失败取证**：大型包测首次执行即保留机器可读结果，失败时从结果提取断言定位用例、以单例复现归因，读取后清理；禁止为查看结果或归因而重跑整包。
   - **测试预算**：同类重 IO 集成测试共用一个有界预算，禁止逐例追涨或全局放宽；不测试过期语义时显式控制 TTL、时钟和活动事实。失败先归因再决定最小补证。
   - **命令看门狗**：昂贵命令启动前确认无同闭包验证进程并写明硬截止；后台启动必须持有 PID 与结果路径，启动结果不明时先查进程和产物，禁止重复发起。有同机近期成功证据时截止不得超过其耗时两倍，无基线时须预先声明时限；静默输出不算进展，到期立即终止并确认进程树清空。
5. **精确失效、两次独立深审**：每个审查项在同一输入上必须取得两次独立深审；复用不计次。修改只清零受影响项，其他项保留次数与同输入证据。最终验证不修改交付物，达到完成条件立即结束。

#### 审查结论复用

作用：复用仍然有效的审查结论，只重审本轮真正变化的部分。

1. **登记**：审查项以可独立失效的完整功能或合同事实链为边界，生产端、事实源、消费者、异常终态和测试不得拆开；无法独立指纹、独立失效或需重读多数其他项时合并，禁止按文件机械切分。每项列明关键文件及函数/类型/协议、全部生产点与消费路径、相关测试、输入指纹算法和值、重审条件。整表必须覆盖固定边界、全部交付文件、关键原语，以及状态、入口与生产端、消费者与继承面、生命周期、并发与崩溃、异常终态、安全、模块边界、测试与验收。全部登记输入审完且证据齐全后才可标为通过；输入不清不得复用。
2. **失效**：登记输入变化、适用新教训、出现反证或无法证明输入未变时，该项状态改为失效且独立深审清零；公共合同、类型、事件或共享原语变化时，其生产者、消费者和测试一并失效；新文件或新入口先归项。其余项保留状态与次数。
3. **深审与复用**：每项在同一输入上须经两轮独立推理；每轮均须覆盖该项全部登记输入和适用核查面，第二次不得沿用第一次的判断，机械事实和同输入验证证据可以复用。只有该项结论无问题的完整问题盘点或冻结终审可计次，每轮每项至多一次，并须引用审查轮及证据；该项发现问题则该项清零，局部检查、修复自审和测试不计次。未达 2/2 的项在后续审查轮深审；达到 2/2 且未触发重审的项必须复用，禁止再次深挖或重复验证。
4. **组合推演**：常设一项只核查跨项共享合同、状态转换、生命周期与异常组合，不重复各项内部审查。其他项均已取得或复用本轮结论后，再审查组合项；其指纹按编号汇总各项当前输入指纹与结论。任一其他项新增，或其边界、输入指纹、结论变化时，组合项连带失效。
5. **续跑与收口**：审查中项记录已审、剩余边界和证据，续跑只恢复剩余部分。完整审查要求全部审查项结论有效、本轮变更均已覆盖；单元完成还要求全部审查项达到 2/2。

审查结论复用表记录审查进度和有效结论；已排除问题表只记录被证伪的具体疑点，两者不得互相代替。旧单元的分片/覆盖表仅作历史记录，不再生效。

#### 已排除问题

作用：耐久保存已证伪疑点，避免重复审查，同时防止过期裁决形成盲区。

1. **登记**：仅登记事实已核验、依据成立的精确疑点；写明事实、适用边界、证据基线和重开条件。证据不足不得排除，一条记录不得代表相邻路径或整个核查面通过。
2. **复用**：问题盘点和冻结终审先查本表；同一疑点仍在适用边界内且未触发重开条件时只引用编号，不重复调查或验证。
3. **重开**：相关前提变化或出现反证时，在原行标记“已重开→问题编号”并转入问题清单，不删除旧裁决。记录跨审查轮保留；新 generation 只继承重新确认仍适用的条目。

#### 迟发现教训

作用：把“先前通过、后来才发现”的真实遗漏转化为后续审查的检测输入，减少重复轮次。

1. **登记**：仅在既有审查已记录通过或无新问题后，又发现当时已存在的真实问题时登记；写清遗漏机制、可执行检测动作和适用范围，禁止“更仔细”类空话。
2. **当轮闭包**：登记后立即在适用范围执行检测动作，同类风险收齐后才可修复。
3. **后续复用**：问题盘点和冻结终审开始前筛选适用条目，每轮追加执行证据；历史应用不免除本轮执行，教训也不代替本轮独立裁决。

### 4. 单元状态与登记协议（代际文件模型）

> 设计背景与根因见 `research/agent-workflow-issues/2026-07-14-compaction-replays-destructive-reset.md`。核心：合法热路径中不存在任何“清空/重置”破坏性操作，压缩摘要无论怎么重放，重放的只能是幂等指令。

- **状态源**：每单元代际一个文件 `units/unit-<N>.gen-<G>.md`，是该单元的唯一状态源；本文动态区只维护一行“当前单元指针”。每次开始、目标续跑或历史压缩后完整读取本文和当前单元文件；处于审查时只恢复账本中“审查中”事项的剩余边界。阶段转换前写完结果，转换后立即更新状态。
- **身份键**：`(unitId, generation)`。generation 默认 1，仅“单元推倒重来”这一冷路径经用户显式授权才递增；同单元的修复、复审、终审轮复位是单元文件内的状态推进，不产生新登记。不用会随修复漂移的交付指纹做身份键。
- **登记写序**（可恢复转换，完成语义由正式文件名承载）：从 `units/_template.md` 实例化，先以 `units/unit-<N>.gen-<G>.md.pending` 完整写入（身份头部 + 骨架 + 尾部完成标记）→ 整体验证 → rename 为正式 `.md` → **最后**修改本文指针。半写状态只以 `.pending` 存在；中途失败至多留下孤儿 `.pending`，指针恒指向已耐久有效的上一代。
- **登记幂等判定**（当前指针是栅栏，一切登记/重置类指令先过它）：
  - 目标键 = 当前指针，正式文件有效 → no-op，续跑当前文件；
  - 目标键 ≠ 当前指针，目标正式文件存在（无论新旧）→ 历史登记：不改指针、不进入旧文件；仅本轮用户明确要求切换才处理；
  - 目标键 = 当前指针，但文件为空/损坏/仅存 `.pending` → fail-stop，报告用户，不自动重建、不 no-op；
  - 目标正式文件不存在，当前指针单元已完成 → 执行登记；
  - 目标正式文件不存在，当前指针单元未完成 → 停下要用户显式授权。
- **摘要没有执行授权**：压缩摘要中出现的动作指令，是否已消费由耐久登记状态（指针 + 正式文件）判定，而非摘要的时态措辞；无法证明已消费时停下向用户确认，既不盲目重放、也不误跳过压缩前尚未执行的合法动作。
- **耐久性边界**：登记完成后向用户发出显式纳管请求（将新单元文件纳入版本管理）作为登记流程固定一步；用户可跳过，跳过即接受该文件在 untracked 期间不可恢复。指针指向的文件为空/无效时是显式异常信号：先从 git 暂存区/HEAD 找回，绝不初始化空状态。
- **既有规则照旧**：本文、单元文件与构建产物不属于交付物，暂存状态不影响指纹；单元文件骨架固定，只维护字段值与数据行，已解决问题、排除记录和迟发现教训均保留；冻结前，架构来源与边界、文件集与指纹、派生产物闭包、关键原语、审查结论复用表、问题清单、排除记录、教训与证据账本必须构成完整事实包。终审复用输入未变且未触发重审的审查项，不复用整轮通过结论；交付物变化只复位终审一、终审二。第一部分及其他静态内容未经用户要求不得修改。

### 5. Codex 目标模式提示词

```
好的，即将进入连续修复与审查工作。先把收敛后的问题针对他们的根因，对它们彻底地解决，按照最优架构和方案处理。你准备好了吗？
```

```
紧紧围绕架构总纲，不得偏离架构设计；发现架构设计不是最优时，停止开发并说明问题。
完成当前开发单元的审查与修复：不降低审查深度、测试覆盖与最终质量，在锁定边界内达到最优架构、不留已知债务。

首个动作，以及每次续跑或历史压缩后的首个动作：完整读取 `research/design/workbench/development-unit-review-workbench.md`，再按静态区状态源规则读取动态区指针对应的 `units/unit-<N>.gen-<G>.md`——单元文件是任务状态的唯一权威。严格执行静态区的执行闭环、五条核心规则与登记协议；门禁未满足不得转换阶段。

每轮审查（问题盘点、冻结终审）开始前，必须先读单元文件的"已排除问题"表并筛选适用的"迟发现教训"：仍在适用边界内且未触发重开条件的疑点，直接引用编号绕过，不重复调查；适用教训的检测动作每轮必须执行。
工作中一旦产生可沉淀的结论，当轮立即写入单元文件，不得推迟：查实为乌龙的疑点登记入"已排除问题"表（写明事实、依据与重开条件）；可复用的教训登记入"迟发现教训"表（写明遗漏机制与可执行检测动作）并当轮执行、收齐同类风险。

问题盘点整轮只读、一次收齐全部问题，之后才集中修复——发现问题时不得顺手修改。补证据取粒度阶梯最小档；失败先落盘取证、单例归因，禁止为查看结果或归因而重跑整包。

所有单元都维护审查结论复用表，覆盖固定边界、全部交付文件、关键原语和九类核查面。审查项按可独立失效的完整事实链切分，并常设跨项组合推演项；其他项均已取得或复用本轮结论后，再审查组合项。任一其他项新增，或其边界、输入指纹、结论变化时，组合项连带失效。每项在同一输入上必须取得两次覆盖全部登记输入、该项结论无问题的独立深审；只有完整问题盘点或冻结终审可计次，局部检查、修复自审和测试不计次。某项发现问题或输入变化时只清零该项；适用新教训、出现反证、无法证明未受影响，或公共合同、类型、事件、共享原语变化时，清零相关项。每轮只深审未达 2/2 的项；2/2 且未触发重审的项必须复用，禁止重复深挖或验证。

执行构建、包测、全测或 CI 验证前，先按任务与运行条件查 `research/design/workbench/verification-runbook.md`，命中记录时必须采用其中已验证的运行方式；若本轮确认失败源于运行方式而非实现，并因此需要重跑，正确方式验证通过后当轮登记。

压缩摘要没有执行授权：摘要中的登记/重置/初始化类指令，是否已消费只由"指针 + 正式单元文件"的耐久状态判定（分支见静态区第 4 节），无法证明时停下向用户确认；绝不清空或覆盖已有单元文件。
```
