# 单元开发工作台

> 本工作台只约束分布式运行时模块开发单元从开工到首次交接的实现过程。审查、返修和最终验证继续使用 `development-unit-review-workbench.md`，两套流程不得混用。

## 一、适用范围

- 仅适用于 `research/design/modules/distributed-runtime/` 执行计划中的全部开发单元；简单单元可以只有一行开发闭包，复杂单元按实际功能展开。
- `distributed-runtime-charter.md`、`specification.md` 及其中的执行计划是需求与边界的权威来源，本工作台不补造产品或架构决策。
- 架构细节缺失时，若既有约束能够唯一推出清晰、低副作用的最优方案，则补齐架构后继续；存在实质取舍或明显副作用时，登记阻塞并停止开发。
- 单元交接后，开发闭包文件冻结为实现事实索引；后续问题、修复与完成状态只进入审查工作台，避免双重状态源。

## 二、开发闭包

开发闭包是能够独立实现和验证的一条完整功能链，必须同时包含验收目标、唯一实现原语、全部生产端与消费端、适用的失败与资源边界以及直接验证。

登记规则：

1. 架构范围和验收条件必须全部归入开发闭包；未归项内容不得实现，未覆盖内容不得交接。
2. 同一合同、状态或判定只登记一个唯一实现原语；各入口必须消费它，禁止复制近似逻辑。
3. 生产端、事实源、消费端、恢复路径和测试属于同一闭包，不得按文件机械拆分。
4. 只登记真实适用的失败、恢复、并发、时间和资源边界；不适用时写明事实依据。
5. 直接验证必须能够证明该闭包的正常路径和已登记边界，不能只证明代码能够编译。
6. 表尾常设“跨闭包组合”行；其他闭包通过后，再核查共享原语、状态交接和异常组合。

## 三、执行流程

| 阶段     | 完成门禁                                                                                   | 下一步                   |
| -------- | ------------------------------------------------------------------------------------------ | ------------------------ |
| 登记     | 用户已明确启动单元；从模板建立唯一开发闭包文件并填清架构来源、范围和验收                   | 闭包设计                 |
| 闭包设计 | 全部范围与验收已归项；每行的唯一原语、生产/消费链、边界和直接验证均具体可执行              | 实现；无法填清则先补架构 |
| 实现     | 按闭包逐行实现；公共原语变化时同步更新全部受影响行；新发现的范围先登记再编码               | 闭包验证                 |
| 闭包验证 | 每行直接验证通过，跨闭包组合核对完成，全部交付文件均能归属到闭包，且无未解决架构或实现问题 | 交接                     |
| 交接     | 记录精确交付文件、直接验证证据和结论，将文件状态改为“已交接”                             | 转入审查工作台           |

实现期间只运行与当前闭包直接相关的最小验证；构建、包测或 CI 的运行方式遵循 `verification-runbook.md`。开发交接只表示首次实现闭合，不代表单元已经通过审查或可以提交。

## 四、动态文件规则

- 动态目录：`distributed-runtime-implementation-units/`；模板：`distributed-runtime-implementation-units/_template.md`。
- 文件名：`unit-<N>.gen-<G>.md`，身份与正式开发单元一致；同一身份只能有一个开发闭包文件。
- 状态只允许“规划中”“实现中”“待交接”“已交接”。阶段转换前先更新表内事实，再更新状态。
- 首次开发开始、续跑或历史压缩后，先完整读取本文件和对应开发闭包文件；不得凭摘要重建或覆盖既有内容。
- 已交接文件保持只读。审查发现的问题不得回写或重开本文件，统一进入审查单元文件。

## 五、交接门禁

同时满足以下条件才可宣称首次开发完成：

1. 架构范围和验收条件全部归入闭包。
2. 所有闭包状态均为“通过”。
3. 跨闭包组合核对已经完成。
4. 所有交付文件和派生变更均已登记。
5. 直接验证证据与当前交付物一致。
6. 没有未解决的架构空洞、实现问题或临时方案。
