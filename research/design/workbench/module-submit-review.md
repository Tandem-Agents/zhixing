# 模块独立审查工作台

> **维护原则**
>
> - 以文件中唯一且独占一行的 `## 审查清单` 为界：此前为静态区，保存长期稳定的规则；该标题及其后为动态区，保存当前模块的独立审查内容。定位时必须整行全等匹配；匹配数不是 `1` 时立即停止。
> - 动态区只固定“当前状态”“来源覆盖”“审查项”“P0/P1 阻断问题列表”“非阻断级问题列表”及其空表。来源分类、审查分区和审查项均须按当前模块重新生成，不得继承其他模块。
> - 两类问题表是本模块唯一正式问题列表。问题从发现、价值裁决、方案收敛、修复到验证关闭均在原行维护，一个根因只保留一行；已验证问题保留原行，删除问题移入“已删除问题的价值裁决记录”。模块审查完成后，动态区按重置协议整体归档。
> - 历史动态区统一归档到 `research/design/workbench/module-review-checklists/<module-id>/gen-<G>.md`。
> - 重置步骤：从独占一行的“审查清单”标题起，将当前动态区原样写入同路径的 `.pending` 文件，完整校验模块身份、全部数据行及两类问题列表（包括空表）后原子改名为正式归档；正式归档已存在时，内容一致则复用，不一致则停止。归档完成后，才将当前状态改为下一模块，删除全部来源分类、审查分区和数据行，只保留固定空表，并将进度恢复为 `0%`。
> - 只允许修改动态区中的模块数据；固定标题、顺序、状态协议、表头、问题列表空表及原有格式必须原样保留。修改完成后必须复核骨架和格式，发现漂移立即恢复。
> - 提示词是静态资产：已定义提示词的标题与正文代码块必须保留，不得因问题为空、阶段完成或范围变化而清空、删除或改成占位；仅可在用户明确授权时更新。修改完成后必须检查 `## 审查清单` 之前的差异，除本轮明确授权的提示词内容外，任何静态区变化都须恢复。

## 一、定位、范围与质量责任

本工作台审查完整模块，而非开发过程或局部实现。清单必须从模块目标、权威架构、需求与体验合同、性能合同及当前完整交付物独立推导；全部通过即表示模块可以交付使用，并满足范围内的功能、体验、性能、架构、正确性、安全性、耐久性、兼容性和资源要求。

审查服从当前版本锁定的**最小完整产品范围**：范围内必须达到完整、优秀且无已知结构债务；范围外的未来能力、通用框架、纯观测或 benchmark、诊断设施、推测风险和非必要增强不得成为交付门禁。覆盖完整只指权威来源与模块边界确定的有限闭包。

清单不得拼接既有局部清单，也不得以历史通过状态替代模块级判断。历史材料只作为事实线索和反证来源；每项必须直接反绑模块权威要求、完整用户旅程、生产装配关系或当前可达失败，并以模块整体行为作为通过对象。

全部规范来源必须逐章判定“适用”或“不适用”；适用章内的规范性条款、表格行和枚举行逐条归入审查项，不适用项写明事实依据。已有映射、历史结论、测试结果和实现现状均不能替代来源完整性判断。

清单必须双向闭合模块功能链：从用户目标和规范正向追到真实生产者、状态、消费者、公开终态和证据；再从完整交付物、组合根、公共出口和派生资产反向归项。有限范围至少覆盖用户入口与受支持场景、生产与消费、共享原语、装配与拓扑、事实源与身份、状态与恢复、并发、安全与隐私、性能与容量、资源上界、非默认与边界场景、兼容演进、安装更新移除、公开错误与用户行动及交付证据。任一未判定来源、要求、旅程、生产链或交付路径均属范围缺失。

每项必须明确对象、适用变体、边界、停止条件和可复核证据；开放表述必须改写为有限集合或矩阵，无法独立判定的要求必须拆分。只有事实证明不适用或完全重复时才能删除。

审查项只描述稳定的产品、架构、性能与风险通过条件。命令结果、任务进度、指纹及 Git 状态只作流程状态或证据；模块回归和测试可以提供证据，但不能代替对生产行为与用户终态的独立判断。

每轮必须完成全部应审项后再归并同根问题，不得因发现问题提前结束。存在未审、未判定或未归项范围时，不得给出通过结论。

## 定稿与重定稿条件

清单满足以下条件即定稿并停止扩充：

1. 模块全部适用规范、完整用户旅程、生产装配、状态与异常链、性能与资源合同、交付路径均有承载项；不适用项有事实依据；没有超出模块边界的条目。
2. 每个审查项范围有限、无重复、可独立判定，并能记录可复核证据。
3. 已知失败模式、排除项重开条件、历史反证和迟发现教训中适用于模块整体的检测动作均有落点。

定稿审查只接受范围遗漏、范围越界和条目不可判定；更换视角、润色措辞、假设未知风险或提出非必要增强不能推动扩张。三类问题清零即结束。

### 清单重定稿

已定稿清单只对生成时的完整交付物有效。模块功能链、公共合同、权威来源、生产装配、性能边界或交付闭包发生实质变化时：将变化的旧 `[!]` 和受影响的 `[x]` 改为 `[~]`，新增项标为 `[ ]`，只保留可证明未受影响的 `[x]`，并作废旧证据；重新定稿后才能继续审查。

## 问题等级与通过标准

| 等级    | 含义                                                                                                             |
| ------- | ---------------------------------------------------------------------------------------------------------------- |
| P0 阻断 | 导致受支持的核心旅程无法完成，或造成权限失守、数据丢失、耐久性破坏、不可恢复停摆、模块无法交付；交付前必须解决。 |
| P1 严重 | 在明确受支持场景造成重要功能、产品体验、性能或架构合同失败；核心路径可能仍可运行，但交付前必须解决。             |
| P2 一般 | 局部影响健壮性、性能、资源回收或可维护性，不破坏核心正确性、安全性、耐久性和主要体验。                           |
| P3 轻微 | 仅影响低价值体验、诊断或代码质量，不影响功能正确性和模块交付。                                                   |

问题状态固定为 `待收敛 → 待修复 → 修复中 → 待验证 → 已验证`；只有真实完成对应阶段才能推进，禁止以方案闭合代替修复或以修复自报代替验证。审查项完成且无未关闭 P0/P1 时标为通过；发现 P0/P1 时标为有问题并登记。P2/P3 只进入非阻断问题列表，不改变审查项的通过状态。全部审查项完成、全部 P0/P1 均为 `已验证` 且受影响项重新审查通过，才判定模块独立审查通过。

登记任何等级的问题都必须给出工作量评估，说明解决该问题所需的预计投入；不得因问题具有阻断性而省略。

### 产品体验、性能与验收设施的判定门禁

发现体验、性能、测试、runner、golden、账本、见证或证据链缺口时，先裁定问题属于哪一层：

1. **产品或生产行为错误**：受支持场景中的功能、体验、性能、正确性、安全性、耐久性或架构合同本身错误，按实际影响评级。
2. **必要证据缺失**：核心合同没有任何成比例的直接证据，导致无法安全交付；只有这种情况才可能因证据缺口评为 P0/P1。
3. **要求过度**：真实行为已有直接测试或结构证据，只是自报标签、重复元数据、benchmark 或验收措辞宣称了非必要的更强结论；应删除或简化要求，不得据此建设新的见证、采集、诊断或通用框架。

把此类问题评为 P0/P1 或“工作量：大”前，必须同时证明：不处理会出现的当前可达用户损失、违反的必要合同、现有证据为何不足，以及修正规则或复用既有机制为何不能解决。任一项无法证明，升级无效。

## 二、模块独立审查提示词

### 2.1 生成模块独立审查清单

```text
完整读取当前模块的三份权威交付文档：需求文档、架构总纲和执行规则或可执行规格；不得以摘要、历史结论或既有清单代替全文。需求文档确定用户价值、产品体验和性能目标，架构总纲确定模块边界、整体结构与不可破坏的设计约束，执行规则确定生产行为、状态、异常和验收合同。继续读取三者直接引用的规范来源、上下游合同、验收要求及当前完整交付物，确认模块身份、交付边界、生产装配和真实用户入口。三份文档存在冲突或不足以唯一确定产品、架构、性能或边界时，明确登记空洞并停止定稿，不得用实现现状补齐。

按照本工作台“定位、范围与质量责任”，从模块整体而非开发过程或局部实现推导审查清单并写入动态区。清单全部通过必须足以证明整个模块可以交付给用户：需求完整落地，产品思路经得起真实使用和时间检验，产品体验达到首席产品官与乔布斯式判断所要求的价值、简洁、一致、自然和克制，架构是锁定范围内最简单完整、职责清晰、可维护且无已知结构债务的方案，性能、正确性、安全性、耐久性、兼容性和资源边界均满足权威合同。

把握模块级颗粒度：一个审查项只承载一个完整用户结果、模块级架构不变量、端到端生产闭包或有限质量合同。文件、包、函数、入口、状态阶段和历史改动只能作为项内变体或证据，不得据此拆成局部清单；也不得把“全模块正确”“全部体验良好”等不可独立判定的宏大目标塞入一项。跨入口、拓扑、状态和故障的同一产品结果应以有限矩阵收束在同一项中，每项都必须有明确对象、边界、停止条件和可复核证据。

先枚举全部规范来源并逐章判定“适用”或“不适用”；适用章内每条规范性条款、表格行和枚举行都必须映射到审查项，不适用项写明事实依据。随后从用户目标正向贯穿默认与非默认旅程、生产者与消费者、共享原语、组合根与拓扑、事实源与身份、状态生命周期、异常恢复、并发、安全隐私、性能容量、资源上界、兼容演进、安装更新移除、公开反馈与用户行动；再从当前完整交付物、公共出口、派生资产和交付路径反向归项。缺少权威要求的实现同样必须形成审查项，不得借现状缩小范围。

产品判断必须从用户整体体验而非功能数量出发：核心价值是否直接可得，默认路径是否无需理解内部结构，必要状态是否可见而正常状态是否保持安静，选择是否必要且可理解，失败是否保护用户并给出唯一可执行行动，跨场景语言、行为和心智模型是否一致。没有当前用户价值的未来能力、通用预留、诊断、遥测、benchmark 和非必要增强一律排除；“经得起时间检验”不得被解释为提前建设范围外框架。

架构判断必须从模块整体生产关系出发：权威事实是否唯一，职责与依赖方向是否清楚，装配和运行拓扑是否闭合，身份、线性化点、状态终态和恢复责任是否一致，局部方案是否造成全局重复、旁路、隐式耦合或资源失控。只符合现有实现但偏离权威架构，或局部可用但整体架构并非最优，均须成为可独立判定的审查项。

只更新动态区中的模块数据；固定标题、顺序、状态协议、表头、问题列表空表及原有格式必须原样保留。存在未判定来源、章节、条款、枚举行、用户旅程、生产链或交付路径，存在范围遗漏、越界、重复、含糊或无法独立判定的条目，清单不得定稿。完成后复核清单：每项均为模块级、全部通过确实足以判定模块可交付、明确排除不含当前必要义务，并确认固定骨架与格式未被修改；发现问题先修正。

本任务只生成并定稿模块独立审查清单，不执行审查、不修改实现、不运行构建或测试；完成后立即停止。
```

### 2.2 目标模式：审查并定稿“模块独立审查清单”

```text
目标：通过多轮“独立推导—集中修正—受影响范围复审”，将当前模块的独立审查清单定稿。清单全部通过必须足以判定整个模块可以交付给用户，并满足三份权威交付文档确定的产品体验、性能、架构及生产质量合同；既不能遗漏模块级真实问题，也不能把局部实现细节或范围外增强变成交付门禁。

首个动作及每次续跑或历史压缩后的首个动作：完整读取本工作台静态规则、当前模块独立审查清单、需求文档、架构总纲、执行规则或可执行规格及清单已列的其他权威来源，并核对当前完整交付物。只依据文件中的当前状态继续，不得沿用生成清单时的范围判断或会话记忆；本次清单定稿过程中，事实未变化且未受修正影响的范围判断可以复用，历史局部审查结论不得替代模块级判断，封版冷启动复审不得复用任何前轮范围结论。

持续执行：

1. 首轮抛开现有分类，从三份权威交付文档正向重建模块应有审查范围：逐章核对全部规范性条款、表格行和枚举行，再沿完整用户旅程、模块级架构不变量、性能与资源合同、生产端与消费端、组合根与拓扑、事实源与身份、状态与恢复、安全边界及交付证据推导审查项，最后从当前完整交付物、公共出口和派生资产反向归项。整轮完成后一次性归并清单问题，不得边发现边零散修补。
2. 专门校准模块级颗粒度：以完整用户结果、模块级架构不变量、端到端生产闭包或有限质量合同为审查项；文件、包、函数、入口和阶段只作为项内变体或证据。合并按局部实现切碎但服务同一整体结论的条目，拆分无法独立判定的宏大条目；合并不得吞掉规范落点、适用变体、停止条件或证据要求。清单不得退化为局部清单汇总，也不得只保留抽象口号。
3. 只修改动态区的来源判定、审查项和范围说明，集中修正范围遗漏、范围越界、颗粒度错误、重复和条目不可判定；不得执行模块独立审查、修改实现或运行构建与测试。修正后只复审变化项及其直接交界，未受影响且事实未变化的结论继续复用；历轮反证不得无依据消失。每个新增或扩写项必须反绑权威来源和当前模块交付必要性，并具有有限对象、明确停止条件和可复核证据；无当前用户价值的未来能力、通用预留、诊断、遥测、benchmark、推测风险和非必要增强一律排除。
4. 准备封版时，对同一份未修改清单执行四路相互独立的冷启动对抗复审，不得复用前轮范围结论：
   - 产品与体验：以首席产品官和乔布斯式判断，从用户价值、默认路径、心智模型、反馈可见性、失败保护和唯一行动重新推导应有范围，判断清单全部通过是否真的代表产品好用且经得起实践与时间检验。
   - 整体架构：从事实唯一性、职责和依赖方向、组合根与拓扑、身份与线性化点、状态终态、恢复责任、复杂度和结构债务重新推导应有范围，判断清单能否证明锁定范围内架构最优。
   - 性能与生产质量：从用户感知性能、容量与资源上界、并发、异常恢复、安全、耐久性、兼容性及非默认场景重新推导应有范围，判断必要质量合同是否都有有限落点。
   - 来源与交付闭包：从三份权威文档的全部条款正向对账，再从完整交付物、公共入口、生产装配、派生资产和交付路径反向对账，检查遗漏、越界和无当前价值条目。
   四路只审查清单范围与可判定性，不执行清单。发现真实缺口后必须集中修正，并对同一份新清单重新执行全部四路复审。

只有三份权威交付文档之间存在无法消解的冲突或空洞，且会改变产品需求、用户体验、性能目标、整体架构或模块边界时才暂停；其余清单组织和颗粒度选择按锁定范围内的最优方案自主收敛。

完成条件：同一份未修改清单通过四路冷启动对抗复审；全部适用来源、章节、条款、枚举行、完整用户旅程、模块级架构不变量、性能与资源合同、生产链和交付路径均已判定；所有审查项均为模块级、有限、无重复、无歧义、可独立判定并能记录证据；不存在范围遗漏、范围越界、颗粒度错误、不可判定条目或未处置反证。最后复核固定骨架和原格式未被修改。满足后明确回复“模块独立审查清单通过”并立即停止；不得继续增加视角、扩充范围或开始执行模块独立审查。
```

### 2.3 执行模块独立审查

```text
完整读取本工作台静态规则、当前模块的需求文档、架构总纲、执行规则或可执行规格、清单已列的其他权威来源、当前完整交付物及已定稿的“模块独立审查清单”，以清单当前状态确定本轮范围。开始时若存在 `[!]`，说明阻断问题尚未完成收敛、修复、验证或状态更新，立即停止并报告；否则审查全部 `[ ]` 和 `[~]` 项，直接复用 `[x]` 项，禁止重复审查。若发现某个 `[x]` 的权威输入、生产交付物或证据基础已经变化，不得直接改成 `[!]` 或顺带复审；按“清单重定稿”协议将受影响项改为 `[~]`、作废旧证据并停止，待清单重新定稿。

逐项从模块整体而非单元、文件或最新改动判断。每项都沿“权威要求 → 真实生产者与组合根 → 唯一事实、身份和线性化点 → 状态与异常恢复 → 消费者与公开终态 → 直接证据”闭合，并覆盖该项列明的全部有限拓扑、入口、状态、故障、并发、安全、性能、容量、兼容和非默认变体。历史单元结论、账本、自报状态、mock 终态和测试通过只能作为线索或证据，不能替代当前生产行为与用户结果；也不得把模块项拆回单元清单或按包、函数、阶段重复审查。

问题判断以模块完整交付给用户后的受支持场景为准。完整实现投入使用后存在可达失败，或违反当前必要的产品体验、整体架构、性能、正确性、安全性、耐久性、兼容性或资源合同，即登记为当前问题；不存在可达失败且不违反必要合同，即明确排除。不得以功能尚未交付、尚未发生事故、默认路径可用、正常 producer 当前给出合法数据或已有局部测试作为“无问题”依据；也不得登记未来可能、理论不完美、通用预留、诊断、遥测、benchmark、推测风险或无当前用户价值的增强。不属本模块但已有确定交付义务的事项只更新既有全局计划，无确定义务的直接排除，均不得进入本模块问题列表。

逐项完成全部应审内容，不得跳项、合并或因发现问题提前结束。审查期间不得修改实现；只运行判定该项所需且成比例的只读检查，构建或测试须先遵守验证手册，且不得重复运行事实未变化的同一证据闭包。每完成一项，立即在原行写入凝练、可复核的当前独立证据并更新状态与清单计数：存在 P0/P1 时标为 `[!]`；不存在 P0/P1 时标为 `[x]`，P2/P3 不改变该项通过状态。只修改动态区的状态、证据、问题表和结论，固定骨架、来源判定、审查对象、通过条件、表头及原格式不得改变。

审查期间不登记问题列表。全部应审项完成后，统一分析本轮发现的问题，将同一根因及其跨项上下游影响合并为一个问题，避免重复登记表象；一项问题影响多个审查项时只保留一行并列全相关项。P0/P1 写入“P0/P1 阻断问题列表”，P2/P3 写入“非阻断级问题列表”，每项写明事实与证据、根因、完整影响、最优解决方案、工作量、评级和相关审查项。若审查暴露真实模块级范围遗漏或不可判定条目，完成本轮已有应审项后停止并报告清单需要重定稿，不得把缺口硬塞进旧项、登记成实现问题或给出通过结论。

```

#### 对抗复核问题价值

```text

裁决标准只有两个且必须同时满足：一是当前范围内的整体用户体验最优，二是模块整体架构最优。不得用低成本牺牲体验、恢复能力或安全边界，也不得为架构形式完整保留无用户价值的复杂度。判断必须站在完整模块和交付旅程上，不能因局部实现方便、单项测试可过或某个包结构整齐而接受全局次优方案。

凡裁决导致事实、根因、影响、范围、评级、工作量、方案或处置结论变化，必须在问题描述中追加“价值裁决记录”，完整写明原结论、推翻或收窄它的事实、新决定及可验证的重开条件。裁决为删除且没有确定未来交付义务的，从问题列表移出并登记到“已删除问题的价值裁决记录”；已确定未来必须交付但不属本模块的，只核对并更新既有全局计划后移出，不得留在模块问题或已删除记录中。禁止保留“后置”“可能需要”“看情况”等未落定事项。

全部问题独立裁决后，统一合并同一根因及其跨审查项上下游影响，每个根因只保留一行，独立根因不得互相遮蔽；同步修正两类问题列表、相关 MIR 状态、清单计数和模块审查结论。保留 P0/P1 的相关项继续为 `[!]`；只剩 P2/P3 或问题删除的已审项改为 `[x]`。只修改动态区的状态、问题记录和结论，固定骨架、表头及原格式必须保持不变。
```
