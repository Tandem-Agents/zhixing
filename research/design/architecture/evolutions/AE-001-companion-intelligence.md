# AE-001：伴身智能架构演进

> **状态**：构想中
> **目标**：以知行自身的架构核心为基础，优雅吸收外部优秀架构带来的产品价值，推动通用个人助手向伴身智能演进。

## 一、原始构想

```text
我们做这个智能体的初衷，包括产品定位，是定位在通用智能体个人助手。长期看的话，还想把它定位成更高级的“伴身智能”——陪伴的伴，身体的身，就是随时在用户身边，可以在多个设备同时协作，然后可以把消息推送到离用户最近的设备上，这种智能体验。

然后中间的一些架构选择，包括你说的那个跨端的事情，它都是一部分，它绝对不是我们整个的核心。所以我感觉目前因为跨端这个事做的比较多、做的比较重，反而让它突出来了，就感觉很奇怪。因为我们本身不是专门去做一个跨端的东西，而是我们要做一个个人助手，然后有那个需求，所以做了那个功能。

所以目前的话，我们在考虑是我们架构的短板在哪里。或者说，我们已经知道了他们几个的架构部分优点、缺点就不说了，就他们的架构优点也很清晰的情况下，我们有没有可能去汲取他们的优点为我们所用？也就是说，对架构进行一次进化。

我们并不是说像缝合怪一样，把他们各个部分架构的一部分代码拿过来，粘在一起，粘成一个新的一个智能体的架构或者产品，这不是我们想要的。
而是我们整个架构的起点，一定得从我们整个产品的定位开启。我们是一个通用个人助手，面向未来设计，而且发展方向还是伴身智能，在用户身边 24 小时存在，可以在多个设备协作。就我们的初心、我们的需求，也就是以我们的需求为基础，去开启我们架构的这个设计。
所以目前各个智能体架构对比的那个文档里面的东西很有价值，但我们并不是要做缝合怪，而是分析出他们的架构的优点以及产品的优点，对我们的需求和目标有价值的部分。并不是说他们好，他们某一个角度肯定都有各自的优点，但并不是说他们好我们就要拿过来，而是说他们好的那一部分和我们整个产品的思路和方向一致的，才是对我们有价值的好的部分。
也就是说，他们的优点得和我们的产品方向、需求一致才有价值，提炼出来之后，再去思考我们的产品以及架构优化。

比如那个 DeepSeek Harness 的插件式组合运行时，对吧？它那个底层和咱们就不一样，包括好几个优点，底层和咱们都不一样。咱们要直接照他们做的话，就得推倒重来，这绝对不是我们要采取的方案，对我们来说甚至是退步的一个方案。

所以对我们来说，他们的优点我们是需要的。所以是以我们自己的架构核心为基础，然后再考虑如何在此基础上，那绝对也不是说乱拼乱凑，而是找到一种非常优雅的方式，把他们的优点集成到我们的架构中。

我们能不能也做插件式的思想？插件式的思想关键不是为了技术而做技术，而是能不能给用户提供那种插件式的思想所对应的产品能力。比如说它可以热插拔更新，就是让用户可以自定义这个智能体的一些前端组件。对普通用户来说，他能看到的就是组件。

然后对于智能体的核心工作流程，这些部分我认为反而虽然你也能插拔，但我认为不应该暴露给用户。因为一个智能体如何达到一个最优的工作状态，它是清晰的，这应该是不向用户暴露的，也不应该让用户去修改。

所以真正我认为这个插件组合运行时，它真正的优点是能让用户去自定义一些自己的使用偏好，包括前端的偏好，而不是整个系统的核心。系统的核心我认为不需要插拔，关键就是它自己的用户偏好可以插拔，所以我们要汲取的是这些优点。

然后还有就是 Pi，就你说的那个 Pi 极简的那个 Agent，它的优点是它目前有人反映说说它的写代码能力更强，因为约束更少，相当于对整个大模型的约束更少。它很极简，反而让大模型通过 Agent 发挥出了更多能力，所以很多人对这个 Pad 智能体的评价很好。
我觉得这个优点我们可以汲取。我认为这个架构和我们本身不是很冲突，它的优点我们可以汲取过来。

比如其他优点，我指的是我们并不是要东拼西凑乱七八糟成一个混合怪，我们不要这样的东西。而是以我们核心的架构思想为核心，去提取他们能提供给用户的优点，然后反向去映射到我们架构该怎样去优化。

就以我们自己架构为核心，去理解他们架构所带来的产品优点，反向去推导我们的架构该如何去做。不要缝合怪，但是我们要以很优雅的方式把架构进行升级。我并不希望别人看到我们汲取了各家的优点之后，一进来让人觉得很不专业、乱七八糟的全都有，而是以一种很优雅的架构呈现。比如别人看到 DeepSeek Harness 插件式的设计会眼前一亮，我们也需要这种优雅的架构。我们的目标是让架构升级，要求是优雅地升级。

还有一个问题，我觉得我们目前的架构虽然代码量已经写了大半，但整体架构并不清晰。我们需要一套即使是世界顶级架构师/智能体专家/前沿智能体研究员 也会欣赏，想要分析，思考甚至借鉴的架构设计和架构思路以及架构实现。我们把产品的定位/需求搞明白了，你来为项目整体架构负责。
```

## 二、本文边界与架构命题

本文只解决架构问题：如何在不降低现有能力、不阻断首个版本发布的前提下，把知行整理成一个责任清楚、可长期演进的个人智能体基座。

本文不设计或承诺任何新增能力。个人连续性增强、主动触达、受控学习、新设备体验和生态化都可以在未来单独立项，但不能作为本次架构演进的阶段、退出门或完成收益。它们在本文中最多只用于检验目标架构是否留出了正确边界。

知行当前并不缺少成为首个完整版本的核心能力。当前需要解决的是：这些能力已经形成，却横向散落在组合根、协议处理、运行时、Owner 和基础设施之间；如果继续直接叠加新功能，未来每增加一项能力都可能再次穿透所有层。

目标架构的核心命题是：

> **薄核纵切，单宿主同协议；事实归域，能力外接，拓扑下沉。**

- **薄核**：Agent Loop、上下文窗口、模型调用和工具闭环保持封闭、有限，不吸收产品领域。
- **纵切**：对话、推进、调度、记忆、工作场景和投递等现有能力，各自形成从产品合同到权威事实的完整垂直模块。
- **单宿主**：只有一个应用组合根负责装配、启动、回滚、换代和关闭；CLI 不再兼任产品后端。
- **同协议**：CLI、消息通道和未来产品面消费同一套与传输无关的产品合同，不复制运行行为。
- **事实归域**：每项事实只有一个领域责任者和一个写入权威，其他位置只持投影或端口。
- **能力外接**：Provider、工具、MCP、通道和执行环境通过窄端口接入，不能反向控制核心正确性。
- **拓扑下沉**：本机或远端、Anchor 或 Executor 只改变部署与执行位置，不改变产品领域语义。

原始构想中的“一心多身”由此获得纯架构解释：“一心”是一套共同的产品事实、应用行为和智能内核；“多身”是多个产品表面和执行拓扑。未来是否以及如何实现“随境而现”，属于独立能力设计，不属于本次架构迁移。

## 三、当前生产实现的事实判断

本节以生产源码、包依赖、组合根和真实调用关系为准，既有设计文档只作旁证。

### 3.1 已经形成的架构资产

| 资产 | 当前生产事实 | 应保留的架构价值 |
|---|---|---|
| 智能执行内核 | `AgentRuntime` 已承载模型—工具循环、上下文窗口、子 Agent、安全执行和运行生命周期 | 不重造 Harness；通过收窄公共合同使其成为可嵌入内核 |
| 运行体工厂 | `RuntimeHost` 已按会话、工作场景和任务发放隔离实例，共享稳定装配资产 | 它是未来 Runtime Assembly 边界的直接起点 |
| 权威与耐久底座 | Owner、Journal、Run、Assignment、全局状态、恢复和明确终态已进入生产主链 | 继续作为所有领域共享的正确性底座，不上升为产品中心 |
| 受控效果链 | 工具、MCP、权限、确认、资源治理、工作区和执行分配已有正式边界 | 模型提出行动，系统裁决和落实效果的原则已经成立 |
| 多拓扑执行 | Anchor、Executor、Mesh 与本机直连拓扑共享经过验证的合同 | 部署形态可替换，产品层无需感知网络细节 |
| 多产品入口 | CLI、Server/RPC 和消息通道已经共享大量会话与运行事实 | 已具备建立统一产品协议的现实基础 |
| 专门领域 | Conversation、Advancement、Schedule、Memory、Workscene、Delivery 等均有真实实现 | 不合并成巨型模型；应按垂直责任重新归位 |

distributed-runtime 是知行走向伴身智能所需的一项基础能力，但知行不为 distributed-runtime 而存在；distributed-runtime 为知行而存在。

### 3.2 当前真正的结构问题

1. **CLI 成为事实上的应用后端。** `@zhixing/cli` 依赖几乎全部生产包；`cli/src/serve` 不只负责命令和呈现，还持有组合根、领域实现、分布式适配、恢复流程和维护责任。
2. **组合与业务没有形成正式边界。** `runServeCommand` 内存在大规模装配、可变引用和顺序耦合；`ApplicationHost` 尚未成为可独立测试、可复用、可完整关闭的生产对象。
3. **协议宿主仍在承担应用语义。** Server 的大上下文聚合多种领域服务，部分 RPC 方法同时解析传输、编排用例、读取权威事实并投影结果，导致其他产品面难以复用同一应用行为。
4. **现有能力按技术层横向散落。** 一项能力经常同时分布在 `core`、`owner-kernel`、`owner-services`、`server` 和 `cli/src/serve`；责任边界只能靠调用图理解，不能从模块所有权直接判断。
5. **核心公共面过宽。** `@zhixing/core` 同时导出运行原语、协议、持久化以及多个产品领域；`AgentRuntime` 也向宿主暴露部分安全和存储内部对象。公共接口正在固化实现细节，而不是稳定能力。
6. **领域、运行与拓扑仍有反向渗透。** `RuntimeHost` 直接知道工作场景、调度和专用工具装配；CLI 直接装配 Owner、Executor 与 Mesh，Server 则直接聚合多个 Owner 和领域服务。未来新增能力仍容易再次穿透全栈。

因此，现状不是“能力不足”或“底座失败”，而是：**关键机制已经足够强，接下来必须把它们从偶然形成的调用关系，收敛成可验证的架构边界。**

## 四、目标母架构

```text
            ApplicationHost（创建、连线、启停，不进入用例主链）
                                  │
                                  ▼
┌──────────────────────── 产品表面 ────────────────────────┐
│ CLI · 消息通道 · 未来原生应用 · 专业业务产品             │
└──────────────────────────┬───────────────────────────────┘
                           ▼
                  Product Protocol
           版本化 Command / Query / Event 合同
                           │
┌──────────────────────────▼───────────────────────────────┐
│ 垂直能力模块                                                │
│ Conversation · Advancement · Schedule · Memory            │
│ Workscene · Delivery                                      │
└─────────────────┬──────────────────────┬─────────────────┘
                  │ Kernel Port          │ Authority/Effect Ports
        ┌─────────▼───────────┐  ┌───────▼────────────────┐
        │ Intelligence Kernel │  │ Authority & Effect     │
        │ Model · Loop        │  │ Owner · Journal        │
        │ Window · Tool Loop  │  │ Security · Resource    │
        │ SubAgent            │  │ Persistence · Recovery │
        └─────────┬───────────┘  └───────┬────────────────┘
                  └───────────┬──────────┘
                              │ 基础设施端口
┌─────────────────────────────▼────────────────────────────┐
│ Provider · Tool · MCP · Channel · Storage · Executor · Mesh│
└──────────────────────────────────────────────────────────┘
```

这不是按代码目录堆出的分层图，而是三条必须正交的演进轴：

| 轴 | 回答的问题 | 不得渗透的内容 |
|---|---|---|
| 产品领域轴 | 知行当前提供什么行为、事实由谁负责 | 不知道模型 SDK、RPC、设备拓扑和文件路径 |
| 智能执行轴 | 一次推理与行动如何运行、终止和释放 | 不知道记忆、调度、工作场景等产品领域 |
| 部署接入轴 | 行为从哪里进入、在哪里执行、如何传输 | 不重新定义产品规则，不成为第二事实源 |

未来能力优雅加入的关键，不是提前为它写通用框架，而是让它只扩展其中一条轴，并通过既有稳定端口与另外两条轴协作。

### 4.1 垂直能力模块：能力各自闭环，底座只共享正确性

现有产品能力不再按“类型、服务、RPC、CLI”横向分散，而按领域纵向拥有自己的完整责任。每个能力模块必须同时回答：

```text
产品合同：外部可以请求什么、观察什么
应用服务：用例如何编排
领域事实：状态和不变量是什么
权威边界：谁能写、如何提交与恢复
运行投影：需要怎样调用智能内核
协议投影：怎样暴露给各产品表面
生命周期：怎样启动、换代、停机和清理
```

Conversation、Advancement、Schedule、Memory、Workscene 和 Delivery 保持不同领域，不因“统一架构”被压进一个万能 Task、Session 或 Personal State。跨领域协作只能调用对方公开应用端口或消费已提交事件，不得直接读写对方存储。

这里的“模块”首先是编译期责任边界，不等于动态插件。只有当一个边界已经稳定、有独立替换价值并确实需要独立发布时，才进一步拆成包。

### 4.2 Intelligence Kernel：封闭、有限、可嵌入

智能内核保留知行已经形成的模型—工具执行优势，但其公共责任收敛为：

- 接收一次已经装配完成的运行信封，包括模型上下文、允许能力、资源预算、取消信号和调用身份。
- 驱动模型、工具、子 Agent、上下文窗口与中断闭环。
- 产生结构化运行事件、受控效果请求和明确终态。
- 保证一次运行内部资源可释放、事件可观察、失败可归因。

智能内核不拥有 Conversation、Memory、Schedule、Workscene、Delivery 或设备身份，也不向 CLI、Server 暴露 `SecurityPipeline`、权限存储等内部实现。管理产品需要的安全、用量和状态信息，必须通过窄查询端口取得。

产品消息与模型消息之间建立显式投影边界：产品模块拥有丰富业务对象，智能内核只消费有限的模型输入。这样既吸收 Pi 的薄内核价值，也避免让 Prompt 或某家 Provider 的消息格式反向定义知行产品。

减少语言约束与加强系统边界不是新增能力，而是内核责任原则：模型负责推理，代码负责授权、事实、资源、效果和终态。

### 4.3 ApplicationHost：唯一组合根，不是新的上帝对象

`ApplicationHost` 是目标架构中唯一可以同时看见能力模块、运行内核、权威底座和基础设施适配器的位置。这里的“唯一”是指每个生产进程角色只有一个组合根；不同设备或 Anchor/Executor 角色可以各有一个遵循同一 Host 合同的实例。它只负责：

1. 读取并冻结启动配置与非公开依赖。
2. 按显式依赖图创建 Authority、能力模块、Runtime 和适配器。
3. 把模块的 Command、Query 与 Event 端口绑定到产品协议。
4. 选择单机或分布式部署适配，不改变上层应用合同。
5. 统一执行启动回滚、代际换代、排空、关闭和残留清理。

Host 不实现会话、记忆、调度、推进或设备管理用例，不持有业务状态，也不通过任意字符串服务定位器让组件在运行期寻找依赖。生命周期允许借鉴 DeepSeek Harness 的依赖、作用域和可逆 Effect 思想，但初始实现应是静态、类型化、可追踪的装配图，而不是“Everything is a Plugin”。

组合顺序本身必须成为可测试合同：依赖先启动、消费者后开放；新流量先停止、在途责任后排空；资源按所有权逆序释放。任何组件创建的 listener、timer、child process、临时目录和连接，都由同一个生命周期作用域负责清理。

### 4.4 Product Protocol：一套行为，多种表面

产品协议是应用能力的传输无关外观，不等于 JSON-RPC，也不要求重命名现有产品概念。它由版本化的 Command、Query 和 Event 组成：

- Command 表达用户或系统希望发生的动作，由应用服务负责准入和提交。
- Query 读取稳定投影，不返回内部对象、物理路径或拓扑细节。
- Event 表达已经成立的应用事实和可观察进展，不直接透传内部日志。

RPC、进程内调用和未来其他传输只是协议绑定。Server 负责认证、连接、编解码、订阅和错误映射；CLI 与 Channel 负责输入、呈现和表面特有交互。三者都不实现领域状态机，也不拥有 Agent Loop。

Codex 与 OpenCode 最值得吸收的不是具体 Thread 或 Session 模型，而是：一套行为所有者通过稳定协议服务多个产品面，Harness 隐藏在真正的产品背后。

### 4.5 Authority 与 Effect：事实只能提交，效果只能受控发生

Owner、Journal、Security、Confirmation、Resource、Persistence、Recovery 和 Assignment 是共享正确性底座，不是一个新的业务领域。它们提供有限原语：

- 事实的单写入权威、修订和耐久提交。
- 效果的准入、幂等、取消、未知终态和恢复。
- 权限、资源与执行身份的系统级约束。
- 本机与远端执行结果进入同一权威链的规则。

通用 Authority Kernel 不应知道 Schedule 或 Workscene 的业务字段；领域 Reducer、状态机和不变量归对应能力模块。反过来，能力模块不得自己重造日志、锁、确认、资源治理或分布式提交。

### 4.6 可替换边缘：只组合变化，不开放正确性

Provider、工具、MCP、Channel、Storage、Executor 和 Mesh 属于可替换边缘。它们按家族实现窄端口，共享必要的身份、版本、生命周期和效果元数据，但不强行塞进一个万能 `Capability` 接口。同一个 Channel 实现可以同时承担产品表面和投递适配器，但必须分别实现两个端口，不能因代码复用混淆责任。

架构明确分为两区：

- **封闭区**：Agent Loop、事实权威、安全准入、恢复、资源治理和终态；扩展不能拦截或替换。
- **可组合区**：Provider、工具实现、MCP、通道、产品表面渲染和部署适配；在受控生命周期内替换。

这吸收了 DeepSeek Harness 的组合与回收能力，也保留知行作为成品个人助手所需的统一行为和安全下限。可组合性服务项目维护者和未来产品，不把组装系统的责任交给普通用户。

### 4.7 拓扑下沉：distributed-runtime 永远是基础设施

单设备与多设备必须实现同一组应用和运行端口。差异只存在于 Host 选择的适配器：

```text
单设备：Application Port → Local Owner / Local Executor
多设备：Application Port → Owner / Assignment → Mesh → Executor
```

能力模块不知道 Anchor、epoch、配对协议或传输连接；智能内核不知道当前工具在本机还是远端执行；产品协议不暴露拓扑作为正常使用前提。这样既保护单设备首版，也保证未来增加设备时不需要重写产品能力。

## 五、依赖规则与唯一所有权

### 5.1 唯一允许的依赖方向

```text
Surface Adapter ───────────────► Product Protocol
Transport Binding ─────────────► Application Ports
ApplicationHost ───────────────► Modules + Kernel + Adapters
Capability Module ─────────────► Kernel Port + Authority/Effect Ports
Intelligence Kernel ───────────► Model/Tool Contracts
Infrastructure Adapter ────────► Its Port Contract
```

只有 ApplicationHost 可以依赖具体实现。端口定义放在需求方稳定边界，适配器实现端口；任何底层包不得反向导入 Host、CLI、Server 或具体产品表面。

### 5.2 明确禁止的依赖

- CLI、Channel 或 Server 直接读写领域存储、Owner 日志或 Mesh 状态。
- Intelligence Kernel 导入产品领域、RPC、Channel 或设备拓扑。
- 一个能力模块绕过公开端口读取另一个模块的仓库。
- Infrastructure Adapter 生成用户界面文案或决定产品流程。
- 为复用方便从巨大根 barrel 导入未声明的跨域实现。
- 通过全局单例、可变 lazy ref 或运行期服务定位隐藏必需依赖。
- 迁移期双写两个权威，或以“兼容”为由永久保留两条生产主链。

### 5.3 所有权矩阵

| 对象 | 目标所有者 | 其他层的权利 |
|---|---|---|
| 产品命令、查询与事件合同 | Product Protocol | 传输绑定与表面只编码、调用、订阅和呈现 |
| 领域规则与状态机 | 对应能力模块 | Host 只装配，Kernel 只被调用 |
| Conversation / Run 事实 | Conversation 模块及其 Authority | 其他模块持引用或读取公开投影 |
| Schedule、Memory、Workscene、Advancement、Delivery 事实 | 各自能力模块及其 Authority | 不得经 CLI/Server 旁路写入 |
| 模型—工具运行状态 | Intelligence Kernel | 应用只观察有限事件与终态 |
| 权限、资源和效果准入 | Authority & Effect Substrate | 模型和表面只能提交请求或决定 |
| 设备与传输事实 | Executor / Mesh 适配器及相应 Authority | 上层只消费与拓扑无关的执行端口 |
| 启停与组件所有权 | ApplicationHost | 组件只管理自身作用域内资源 |

## 六、对现有包的演进定位

先形成边界，再决定物理搬迁；包名不是架构成果。

| 当前包或目录 | 目标责任 | 演进重点 |
|---|---|---|
| `@zhixing/core` | 最小公共原语、稳定合同和纯 Reducer | 停止扩大根导出；按领域和端口使用明确 subpath，逐步移出需要具体装配的实现 |
| `@zhixing/orchestrator` | 封闭的 Intelligence Kernel | 收窄 `AgentRuntime` 公共面；移除产品领域知识和宿主管理内部对象 |
| `@zhixing/runtime-host` | Runtime Assembly / Runtime Factory | 接收已经解析的运行信封和模块贡献，不直接认识 Workscene、Schedule 等专用领域 |
| `@zhixing/owner-kernel` | 通用 Authority、提交、恢复与效果原语 | 通用机制留在内核，领域状态机逐步回到对应能力模块 |
| `@zhixing/owner-services` | 现有垂直能力模块的第一承载区 | 先在包内按领域形成完整边界；规模和依赖证明需要后再拆包 |
| `@zhixing/rpc` | 产品协议的 RPC 绑定与流投影 | 不拥有应用用例；传输合同与应用合同分离 |
| `@zhixing/server` | 认证、连接、协议宿主和订阅网关 | RPC handler 只做解析、调用、错误映射和推送，不编排领域逻辑 |
| `@zhixing/cli` / Channel | 产品表面和进程入口 | 移出生产后端、领域服务与分布式实现，只保留输入、呈现、命令和启动选择 |
| `@zhixing/executor` / `@zhixing/mesh` | 执行与传输适配器 | 只实现上层端口，不感知产品领域和表面 |
| `cli/src/serve` | 当前事实组合根与大量适配实现 | 先形成 `ApplicationHost` 内部边界，再按所有权迁移；禁止为了目录整齐一次性搬迁 |

若边界稳定后确需新增物理包，优先只考虑两个：传输无关的 Product Protocol，以及不对外发布的 ApplicationHost。不能为每个概念预建包，也不能把现有大杂烩原样搬进一个新包。

## 七、对外部架构的纯架构吸收

| 来源 | 吸收的架构原则 | 在知行中的落点 | 明确拒绝 |
|---|---|---|---|
| Codex | Harness 后置；控制与事件协议服务多个专业产品面 | Intelligence Kernel + Product Protocol | 把 Coding Thread 或具体产品能力变成知行中心 |
| Pi | 模型层、Agent Core、产品装配和 UI 分层；应用消息显式投影到模型消息 | 薄内核 + Run Envelope / Event 边界 | 把安全、耐久和统一默认交给任意扩展 |
| DeepSeek Harness | 声明式依赖、作用域生命周期和可逆 Effect | ApplicationHost 与可替换边缘的资源所有权 | Everything is a Plugin；让插件进入封闭区 |
| OpenCode | 一个行为与状态所有者，通过协议服务多个客户端 | 应用端口 + Product Protocol + 表面适配器 | 让过渡期双模型和兼容桥长期存在 |
| OpenClaw | 常驻 Host 收拢入口、路由、Runtime 和投递的产品闭包 | 单一 ApplicationHost 与通道适配端口 | 把 Gateway 做成持有全部领域逻辑的上帝对象 |
| Hermes | 多入口共享同一运行内核；配置作用域与会话状态分离 | 共享 Intelligence Kernel 与显式运行装配 | 把动态注册、学习闭环或广泛功能作为本次目标 |
| NVIDIA AVO | 行动者、评价者和事实准入彼此分离 | 保持现有 Advancement 的执行与证据边界 | 引入持续学习、成果进化等新增能力 |

吸收标准只有三个：它必须收敛现有结构问题；必须能落到唯一责任者；必须替代旧路径而不是增加平行框架。否则即使外部设计先进，也不进入本次架构。

## 八、架构不变量

1. 当前产品能力、协议行为、数据和终态在架构迁移中不得改变；任何能力增强另行立项。
2. 一个事实只有一个写入权威；缓存、索引、摘要、UI 和协议响应都是投影。
3. 一项产品能力只有一个垂直模块负责其规则、状态和应用用例。
4. 只有 ApplicationHost 可以依赖具体实现；Host 不拥有领域事实和产品流程。
5. Intelligence Kernel 不知道产品领域、产品表面和部署拓扑。
6. Surface 与 Transport 只能消费 Product Protocol，不能复制应用状态机。
7. Server 是协议宿主，不是应用服务定位器；CLI 是产品表面，不是生产后端。
8. 模型不能扩张权限、资源、事实权威或效果范围；适配器也不能绕过同一控制链。
9. 单设备始终是完整一等拓扑；多设备不能把复杂度泄漏到产品领域。
10. 扩展只能进入可组合区，不能替换安全、权威、恢复、资源和终态机制。
11. 任何新抽象必须至少收敛两个现有分散机制，且有可执行的依赖规则证明其边界。
12. 任何迁移必须删除或封存旧入口，不以兼容名义永久保留双主链。

## 九、架构适应度验证

架构不能只靠文档约定，必须由持续门禁证明。

| 门禁 | 必须证明什么 |
|---|---|
| 依赖图门禁 | 包和关键源码目录无环，禁止依赖规则不可绕过 |
| 公共 API 门禁 | Kernel、Protocol、Authority 和模块端口的导出面有限且经过合同测试 |
| 垂直所有权门禁 | 每个现有能力的写入口、状态机和权威归属唯一，无 CLI/Server 旁路 |
| 多表面一致性门禁 | 不同表面调用同一应用端口，产品行为不由各自重新实现 |
| Host 生命周期门禁 | 启动失败可回滚，关闭按依赖逆序，listener、timer、进程、连接和临时资源无残留 |
| Runtime Conformance | 对话、任务、本机与远端 Runtime 都服从同一有限运行合同 |
| 拓扑透明门禁 | 同一应用合同可绑定本机或分布式适配器，上层无拓扑分支 |
| 回归门禁 | 现有直接测试、根级门禁、打包和首版产品旅程在同一基线上成立 |

目录、包数量和代码行数不构成架构完成证据。只有责任转移、旧入口清理、依赖门禁和现有行为回归同时成立，边界才算建立。

## 十、目标架构迁移序列

本节是架构检查点的先后关系，不是功能路线，也不能直接当开发计划。每个检查点实施前仍需单独设计执行单元，明确当前调用图、迁移范围、兼容窗口、旧入口删除和直接验证。

所有检查点只允许结构变化，不新增产品能力；当前首版发布不以完成本架构迁移为前提。

### 检查点 0：冻结能力基线与依赖事实

- 固定当前公开行为、生产调用图、唯一权威和组合生命周期基线。
- 建立第一批禁止依赖与公共 API 适应度门禁。
- 把能力需求、架构迁移和实现修复分成不同任务来源。

**退出门：** 后续任何迁移都能证明只是责任搬迁；首版能力和发布边界没有被扩大。

### 检查点 1：建立应用端口与 Host 外壳

- 从现有生产行为中提取传输无关的 Command、Query 和 Event 端口，不发明新产品语义。
- 在 `cli/src/serve` 内先形成可独立创建和关闭的 `ApplicationHost` 外壳。
- 让现有 CLI、Server 和 Channel 经适配器调用同一应用端口，内部实现暂时仍可委托旧路径。

**退出门：** 产品表面不再直接定位领域实现；Host 生命周期有完整合同；行为逐字节或逐事件等价。

### 检查点 2：分离协议宿主与应用行为

- 将 ServerContext 的领域服务聚合拆为明确应用端口。
- RPC handlers 只保留认证后的解析、调用、错误映射和订阅投影。
- 将 CLI 中的领域控制器与呈现、命令解析分开。

**退出门：** Server 和 CLI 都不能成为领域事实写入者；同一应用用例可由进程内或 RPC 绑定调用。

### 检查点 3：封闭 Intelligence Kernel

- 收窄 `AgentRuntime` 公共合同，管理查询经专用端口暴露。
- 建立产品对象到模型输入、运行事件到应用结果的显式投影。
- 将 Workscene、Schedule 等领域装配从 RuntimeHost 移到对应模块贡献或运行信封生成方。

**退出门：** Kernel 和 RuntimeHost 不导入产品领域、表面或拓扑实现；所有现有运行形态通过同一 Conformance Suite。

### 检查点 4：按垂直切片归位现有能力

- 先选择边界较小的现有能力验证模块模板，再逐项迁移 Conversation、Advancement、Schedule、Memory、Workscene 和 Delivery。
- 每次只迁移一个能力的应用服务、权威规则、协议投影和生命周期。
- 迁移完成立即删除旧写入口；不得等待全部模块结束后统一清理。

**退出门：** 每项现有能力都能从模块入口追踪到唯一权威；`core`、`server` 和 `cli/src/serve` 不再横向拥有其业务实现。

### 检查点 5：收束 Host、边缘与拓扑

- 把 Provider、工具、MCP、Channel、Storage、Executor 和 Mesh 绑定到明确家族端口。
- 用类型化依赖图替代组合根中的隐式顺序、可变引用和运行期寻找。
- 边界稳定后再决定是否物理提取 Product Protocol 与 ApplicationHost 包。

**退出门：** 单机与分布式只在 Host 适配层分叉；Host 只剩装配和生命周期；适配器不能反向依赖领域实现。

### 检查点 6：删除迁移结构并冻结架构

- 删除委托旧路径的适配桥、根级宽泛导出和无主公共接口。
- 完成依赖、生命周期、协议、Runtime、拓扑及全量回归门禁。
- 更新模块索引和架构决策，使生产代码与文档互相可验证。

**退出门：** 所有架构不变量和适应度门禁成立；当前能力与首版体验无回退；不存在第二组合根、第二应用行为或第二权威。

## 十一、未来能力如何优雅进入

本节不是能力清单，只用变化影响面检验架构是否面向未来：

| 未来变化 | 合理影响范围 | 不应修改 |
|---|---|---|
| 新增一种产品能力 | 新垂直模块、对应 Product Protocol 扩展、Host 静态装配 | Intelligence Kernel、其他能力存储、Mesh 协议 |
| 新增一种产品表面 | 新 Surface Adapter 和呈现 | 应用状态机、Agent Loop、权威存储 |
| 新增 Provider、工具或 MCP | 对应家族适配器与受控注册 | 产品协议、领域模块、Owner 规则 |
| 新增设备或执行拓扑 | Host 拓扑装配、Executor/Mesh 适配器 | 产品领域、模型上下文结构、表面流程 |
| 更换模型循环实现 | 新 Kernel 实现并通过 Conformance Suite | 应用模块、协议、领域数据 |
| 增加用户可组合界面 | Product Protocol 之上的组件和 Surface 生命周期 | 权威、安全、恢复和核心运行闭环 |

如果未来能力必须同时修改 CLI、Server、Agent Loop、Owner、Mesh 和多个领域存储，说明目标架构没有建立成功，而不是这项能力天然复杂。

## 十二、项目治理规则

每个架构执行单元必须提交：当前责任与调用图、要建立的不变量、最小迁移范围、兼容窗口、旧入口删除、适应度门禁和现有行为回归证据。

执行遵守：

- 先以源码证明结构问题，再设计边界；不根据过时文档搬迁代码。
- 先在现有目录形成边界，再决定拆包；不以移动文件伪装架构进展。
- 一次只改变一个责任所有权，保持每个中间状态可构建、可运行、可发布。
- 允许短期单向适配，禁止双写、双权威和双状态机。
- 先迁移较小能力验证模式，再处理 Conversation 等高耦合主链。
- 架构迁移只衡量依赖、不变量、生命周期和旧路径清理，不借机补功能。
- 当前首版的正确性、安全性和体验问题优先于本架构迁移；架构愿景不能成为延迟发布的理由。

## 十三、明确不做

- 不新增 Self、Commitment、Presence、Attention、Learning 或其他未来产品对象作为本次迁移前提。
- 不增强记忆、学习、主动触达、多设备体验或生态能力。
- 不推倒重写 AgentRuntime、Owner 或 distributed-runtime。
- 不把 distributed-runtime、多 Agent、插件、沙箱或任何单项技术提升为架构中心。
- 不把所有现有能力合并成万能 Task、Session、Capability 或 Personal State。
- 不建立第二套 Conversation、Run、Schedule、Memory 或全局状态事实源。
- 不把所有实现动态插件化，也不预建市场、通用插件平台或自修改框架。
- 不为了“未来可能需要”增加没有两个现有消费者的新抽象。
- 不要求首个版本等待架构演进完成后才能发布。

## 十四、最终判定

知行当前的能力并不弱，真正稀缺的是已经形成的智能执行、受控效果、耐久权威和多拓扑基础。下一代架构不再横向增加一个更大的产品概念，而是让这些资产各归其位，并建立一种可以长期控制复杂度的增长方式：

> **水平底座只提供不可重复建设的正确性，产品能力以垂直模块独立闭环；一个 Host 负责组装，一套协议服务所有表面，任何设备拓扑都不能反过来定义知行。**

对用户，这次演进理应没有新增学习成本，甚至不应被感知；对未来开发，它必须产生一个清晰结果：增加能力不再穿透整个系统，更换模型、表面或设备也不再迫使产品语义重写。
