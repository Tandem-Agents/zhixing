# AE-001：伴身智能架构演进

> **状态**：设计已收敛
> **目标**：以知行自身的架构核心为基础，优雅吸收外部优秀架构带来的产品价值，推动通用个人助手向伴身智能演进。

## 一、原始构想

```text
我们做这个智能体的初衷，包括产品定位，是定位在通用智能体个人助手。长期看的话，还想把它定位成更高级的“伴身智能”——陪伴的伴，身体的身，就是随时在用户身边，可以在多个设备同时协作，然后可以把消息推送到离用户最近的设备上，这种智能体验。

然后中间的一些架构选择，包括你说的那个跨端的事情，它都是一部分，它绝对不是我们整个的核心。所以我感觉目前因为跨端这个事做的比较多、做的比较重，反而让它突出来了，就感觉很奇怪。因为我们本身不是专门去做一个跨端的东西，而是我们要做一个个人助手，然后有那个需求，所以做了那个功能。

所以目前的话，我们在考虑是我们架构的短板在哪里。或者说，我们已经知道了他们几个的架构部分优点、缺点就不说了，就他们的架构优点也很清晰的情况下，我们有没有可能去汲取他们的优点为我们所用？也就是说，对架构进行一次进化。

我们并不是说像缝合怪一样，把他们各个部分架构的一部分代码拿过来，粘在一起，粘成一个新的一个智能体的架构或者产品，这不是我们想要的。
而是我们整个架构的起点，一定得从我们整个产品的定位开启。我们是一个通用个人助手，面向未来设计，而且发展方向还是伴身智能，在用户身边 24 小时存在，可以在多个设备协作。就我们的初心、我们的需求，也就是以我们的需求为基础，去开启我们架构的这个设计。
所以目前各个智能体架构对比的那个文档里面的东西很有价值，但我们并不是要做缝合怪，而是分析出他们的架构的优点以及产品的优点，对我们的需求和目标有价值的部分。并不是说他们好，他们某一个角度肯定都有各自的优点，但并不是说他们好我们就要拿过来，而是说他们好的那一部分和我们整个产品的思路和方向一致的，才是对我们有价值的好的部分。
也就是说，他们的优点得和我们的产品方向、需求一致才有价值，提炼出来之后，再去思考我们的产品以及架构优化。

比如那个 DeepSeek Harness 的插件式组合运行时，对吧？它那个底层和咱们就不一样，包括好几个优点，底层和咱们都不一样。咱们要直接照他们做的话，就得推倒重来，这绝对不是我们要采取的方案，对我们来说甚至是退步的一个方案。

所以对我们来说，他们的优点我们是需要的。所以是以我们自己的架构核心为基础，然后再考虑如何在此基础上，那绝对也不是说乱拼乱凑，而是找到一种非常优雅的方式，把他们的优点集成到我们的架构中。

我们能不能也做插件式的思想？插件式的思想关键不是为了技术而做技术，而是能不能给用户提供那种插件式的思想所对应的产品能力。比如说它可以热插拔更新，就是让用户可以自定义这个智能体的一些前端组件。对普通用户来说，他能看到的就是组件。

然后对于智能体的核心工作流程，这些部分我认为反而虽然你也能插拔，但我认为不应该暴露给用户。因为一个智能体如何达到一个最优的工作状态，它是清晰的，这应该是不向用户暴露的，也不应该让用户去修改。

所以真正我认为这个插件组合运行时，它真正的优点是能让用户去自定义一些自己的使用偏好，包括前端的偏好，而不是整个系统的核心。系统的核心我认为不需要插拔，关键就是它自己的用户偏好可以插拔，所以我们要汲取的是这些优点。

然后还有就是 Pi，就你说的那个 Pi 极简的那个 Agent，它的优点是它目前有人反映说说它的写代码能力更强，因为约束更少，相当于对整个大模型的约束更少。它很极简，反而让大模型通过 Agent 发挥出了更多能力，所以很多人对这个 Pad 智能体的评价很好。
我觉得这个优点我们可以汲取。我认为这个架构和我们本身不是很冲突，它的优点我们可以汲取过来。

比如其他优点，我指的是我们并不是要东拼西凑乱七八糟成一个混合怪，我们不要这样的东西。而是以我们核心的架构思想为核心，去提取他们能提供给用户的优点，然后反向去映射到我们架构该怎样去优化。

就以我们自己架构为核心，去理解他们架构所带来的产品优点，反向去推导我们的架构该如何去做。不要缝合怪，但是我们要以很优雅的方式把架构进行升级。我并不希望别人看到我们汲取了各家的优点之后，一进来让人觉得很不专业、乱七八糟的全都有，而是以一种很优雅的架构呈现。比如别人看到 DeepSeek Harness 插件式的设计会眼前一亮，我们也需要这种优雅的架构。我们的目标是让架构升级，要求是优雅地升级。

还有一个问题，我觉得我们目前的架构虽然代码量已经写了大半，但整体架构并不清晰。我们需要一套即使是世界顶级架构师/智能体专家/前沿智能体研究员 也会欣赏，想要分析，思考甚至借鉴的架构设计和架构思路以及架构实现。我们把产品的定位/需求搞明白了，你来为项目整体架构负责。
```

## 二、本文边界与核心命题

本文只解决一个问题：在不改变当前正式能力、不阻断首个版本发布的前提下，怎样把知行整理成一个能够从通用个人助手长期演进为伴身智能的架构基座。

本文不设计或承诺新增能力。个人连续性增强、主动触达、受控学习、新设备体验和生态化只能在未来独立立项，在这里最多用于检验边界。旧 Memory 模块已经退出正式基线；未来接入 OWNWARD、重建记忆能力或长期无记忆都属于独立产品决策，本文不预建任何记忆抽象。

知行当前并不缺少首个完整版本所需的核心能力。真正的问题是：产品能力、智能执行、权威提交、协议接入和设备拓扑已经形成，却仍由偶然的包位置与调用关系粘在一起；继续直接叠加功能，会让每项新增能力再次穿透全栈。

目标架构只有一个中心命题：

> **“一心”不是一个模型、进程、Host 或设备，而是由唯一的产品语义、权威事实与共同应用行为构成的逻辑产品身份；智能内核是其受控且可替换的认知执行者。“多身”只是这套身份与行为在不同表面、设备和执行位置上的呈现与兑现。**

由此得到全部架构规则：

- 产品领域拥有语义、合同和事实，不能由模型、RPC、CLI 或设备拓扑定义。
- 模型与 Agent Runtime 受托推理和执行，但产出首先是提议、事件或证据，不能自行成为产品事实。
- 事实经唯一权威提交，外部效果经统一控制链发生；投影、缓存、界面和传输都不成为第二真相。
- Host 只选择实现并管理生命周期，不进入产品用例主链。
- 表面共享同一产品合同，执行位置共享同一能力端口；更换模型、界面或设备不改写产品含义。

这不是追求永不变化的实现。真正要稳定的是产品语义、事实归属和责任规则；模型、运行内核、存储、协议绑定、产品表面与设备拓扑都应当在各自边界内可替换。

## 三、当前生产实现的事实判断

本节以当前源码、包依赖、组合根和真实调用链为准，既有设计文档只作旁证。

### 3.1 已经形成的架构资产

| 资产 | 当前生产事实 | 应继承的价值 |
|---|---|---|
| 智能执行 | `AgentRuntime` 已完成模型—工具循环、上下文窗口、子 Agent、安全执行、中断与明确终态 | 不重造 Harness；收窄为可嵌入、可替换的智能执行内核 |
| Runtime 装配 | `RuntimeHost` 已按对话、工作场景和任务发放隔离实例并复用装配资产 | 保留统一 Runtime 生成路径，移除其中的产品领域知识 |
| 权威与耐久 | Owner、Journal、Run、Assignment、全局状态、恢复与终态已进入生产主链 | 作为共享正确性原语保留，不上升为产品中心 |
| 受控效果 | 工具、MCP、权限、确认、资源治理、工作区与执行分配已有正式链路 | 延续“模型提出、系统裁决、受控兑现”的边界 |
| 宿主生命周期 | `access-surface`、`StartupRollback`、`CleanupRegistry` 和 shutdown chain 已实现有序装配、启动补偿与逆序清理 | 它们是 ApplicationHost 的迁移起点，不应被重写或误当成最终边界 |
| 多表面 | CLI、Server/RPC 和消息通道已共享会话、运行事件与大量事实 | 已具备建立统一产品合同的现实基础 |
| 多拓扑 | Anchor、Executor、Mesh 与本机路径共享经过验证的权威和执行合同 | 部署位置可以下沉为适配选择 |
| 结构门禁 | RPC 注册表、S7 exact-set/golden、包导出和制品检查已有可执行结构证据 | 可扩展为目标架构适应度门禁 |
| 产品领域 | Conversation、Advancement、Schedule、Workscene、Delivery 以及 Trust、Skill、Device 管理等均有真实生产行为 | 按事实所有权归位，不压进万能 Session、Task 或 Control 对象 |
| 已退场能力 | 旧 Memory 的生产、协议、存储和公开面已删除 | 不作为待迁移模块，未来方案另行决策 |

distributed-runtime 是知行走向伴身智能所需的一项基础能力，但知行不为 distributed-runtime 而存在；distributed-runtime 为知行而存在。

### 3.2 当前真正的结构问题

1. **CLI 仍是事实上的应用后端。** `@zhixing/cli` 依赖全部主要生产包；`cli/src/serve` 同时持有组合根、领域服务、Owner、恢复、Mesh、设备管理和协议适配。
2. **已有宿主机制尚未形成宿主边界。** `runServerProcess`、`AssemblyContext` 和接入面单元已经解决大量启动与清理问题，但共享上下文仍聚合众多具体类型、可变产物和 lazy ref；装配顺序仍能泄漏成运行期耦合。
3. **协议宿主仍在承担应用语义。** `ServerContext` 聚合会话、推进、场景、信任、技能、设备、迁移、投递和 Runtime 控制；部分 RPC handler 同时解析传输、编排用例、读取权威事实并生成产品结果。
4. **产品合同与领域所有权分离。** 公开 RPC 方法集中注册在 Server，领域类型与端口大量集中在 `core`；产品语义容易由传输层或公共大包事实定义，而不是由行为所有者定义。
5. **产品能力按技术层横向散落。** 同一能力常跨越 `core`、`owner-kernel`、`owner-services`、`server` 和 `cli/src/serve`；只有沿调用图才能知道谁负责规则、提交和恢复。
6. **智能内核公共面过宽。** `AgentRuntime` 除执行合同外还暴露安全管线、权限存储、工作区解析、管理查询和多种产品装配入口；`RuntimeHost` 直接认识 Workscene、Schedule 和专用工具。
7. **公共依赖中心过重。** 几乎所有生产包依赖 `@zhixing/core`，其根导出同时包含运行原语、领域、持久化、安全、调度和界面辅助；CLI 与 Server 也导出或聚合超出自身责任的实现。
8. **产品设备事实与物理拓扑尚未完全分开。** 用户可见的配对关系、设备移除和值班迁移是产品管理语义；连接、epoch、Assignment、Mesh 与执行位置是基础设施语义，二者当前仍在 CLI/Server 装配中交织。

因此，现状不是底座失败，而是：**关键机制已经足够强，必须把它们从“能正确协作的实现”收敛成“不能错误依赖的架构”。**

## 四、目标母架构

```text
产品表面：CLI · 消息通道 · 未来原生应用 · 专业产品
                         │
             in-process / RPC / future bindings
                         ▼
               Product API Catalog
       （只组合各领域拥有的 Command / Query / Event）
                         │
┌────────────────────────▼─────────────────────────┐
│ 垂直领域单元                                       │
│ Conversation · Workscene · Schedule · Advancement│
│ Delivery · Trust Admin · Skill Catalog · Device Admin│
└──────────────┬──────────────────────┬─────────────┘
               │ Intelligence Port    │ Authority / Effect Ports
      ┌────────▼─────────┐   ┌────────▼────────────────┐
      │ Intelligence     │   │ Correctness Substrate   │
      │ Kernel           │   │ Commit · Journal        │
      │ Model · Loop     │   │ Security · Confirmation │
      │ Window · Tool    │   │ Resource · Recovery     │
      └────────┬─────────┘   └────────┬────────────────┘
               └───────────┬──────────┘
                           ▼
 Provider · Tool · MCP · Storage · Channel · Executor · Mesh

ApplicationHost ── 仅创建、连线、启动、换代、排空和关闭上述组件
```

ApplicationHost 被刻意画在用例主链之外。它可以看见具体实现，但产品请求开始后，行为只能沿领域公开端口推进，不能回到 Host 寻找服务或编排业务。

母架构包含三条正交变化轴：

| 轴 | 稳定内容 | 可替换内容 | 不得渗透 |
|---|---|---|---|
| 产品领域轴 | 产品语义、应用行为、事实归属 | 新领域单元及其合同实现 | 模型 SDK、RPC、文件路径和物理拓扑 |
| 智能执行轴 | 有限运行合同、事件与终态 | 模型、Provider、Loop 实现和工具实现 | Conversation、Schedule、Workscene 等产品规则 |
| 接入部署轴 | 绑定合同、身份和生命周期 | 产品表面、传输、存储与设备拓扑 | 领域状态机和第二事实源 |

面向未来不是提前制造万能框架，而是保证一次变化只沿其所属轴扩展，并通过稳定端口与其他两轴协作。

### 4.1 垂直领域单元：语义、合同与事实由同一责任者拥有

每个现有产品领域形成一个编译期责任闭包：

```text
领域拥有的 Command / Query / Event 合同
应用用例与准入规则
领域状态机、Reducer 与不变量
权威提交和恢复的领域适配
面向 Intelligence Kernel 的 Run Envelope 投影
面向表面的稳定投影
组件生命周期贡献
```

产品合同不能由中央 Protocol 包重新定义。领域单元拥有其合同与语义；`Product API Catalog` 只把这些合同组合成供表面发现、调用和订阅的统一外观，不拥有业务规则，也不成为第二个领域模型。

Conversation、Workscene、Schedule、Advancement 和 Delivery 保持不同事实边界；Delivery 拥有“结果需要被交付及其终态”的产品义务，Channel 只实现发送效果。管理行为也不合并成无边界的“管理模块”：Trust Administration 拥有用户可管理的信任规则，Security Substrate 负责执行；Skill Catalog 拥有技能资产与生命周期，Kernel 只消费不可变投影；Device Administration 拥有用户可见的设备关系、移除与值班迁移，Executor/Mesh 只实现物理效果。

跨领域协作只能调用对方应用端口或消费已经提交的事件，不能直接读取对方仓库、日志或内部状态。同步依赖必须保持无环；需要反向响应时优先消费已提交事件，不能用互相回调形成隐式双向所有权。

“领域单元”首先是源码所有权、依赖和测试边界，不等于一个 npm 包，更不等于运行时插件。只有独立发布、故障隔离或复用事实证明需要时才拆包。

### 4.2 Product API：一套行为，多种表面

Product API 是领域合同的传输无关组合：

- **Command** 表达希望发生的动作，进入唯一应用服务并返回接纳、拒绝或明确终态。
- **Query** 读取稳定投影，不返回内部对象、物理路径、Owner 日志或拓扑细节。
- **Event** 分为两种明确语义：Fact Event 只表达已经提交的产品事实；Progress Event 只表达带运行身份的瞬时进展，不能成为恢复或查询事实。二者都不直接透传内部日志或 Provider chunk。

同一合同可以由进程内绑定直接调用，也可以由 RPC 等传输绑定编码；本机默认路径不为架构整洁强行打开端口或承担序列化成本。Server 只负责认证、连接、编解码、订阅和错误映射；CLI、Channel 与未来表面只负责输入、呈现和表面特有交互。任何表面都不能复制应用状态机。

这使 Harness 隐藏在真正的产品背后：用户面对的是对话、工作场景、任务和结果，而不是 Thread Runtime、Host、Mesh 或插件容器。

### 4.3 Intelligence Kernel：强智能，薄责任

智能内核的公共责任限定为：

- 接收已装配的 `Run Envelope`：模型输入、允许能力、资源预算、调用身份、取消信号和受控效果端口。
- 驱动模型、工具、子 Agent、上下文窗口、中断与本次运行的资源释放。
- 产生结构化运行事件、效果提议、证据和明确终态。
- 通过有限查询端口暴露用量、安全结果和运行状态，不泄漏内部对象。

Kernel 不拥有 Conversation、Schedule、Workscene、Delivery、设备关系或产品文案；不向宿主暴露 `SecurityPipeline`、权限存储等内部实现；不把 Prompt、某家 Provider 消息或当前工作区结构变成产品合同。产品对象到模型消息、运行事件到产品结果都由显式投影完成。

“薄”不是削弱模型，而是减少围绕模型的固定脚手架：模型负责开放式推理，代码只在事实、权限、资源、效果和终态这些不会因模型变强而消失的地方保持刚性。

### 4.4 Correctness Substrate：共享机制，不是共享业务

Owner、Journal、Security、Confirmation、Resource、Persistence、Recovery 和 Assignment 构成一组共享正确性原语，而不是一个新领域或单一上帝服务。它们提供：

- 单写入权威、修订、耐久提交与重放。
- 效果的准入、幂等、取消、未知终态和恢复。
- 权限、资源、执行身份和设备能力的系统约束。
- 本机与远端结果进入同一权威链的规则。

通用原语不认识 Schedule、Workscene 等业务字段；领域 Reducer、状态机与用户语义归领域单元。领域单元也不能自行重造日志、锁、确认、资源治理或分布式提交。

对具有外部后果的动作，统一责任链是：

```text
意图 → 领域决定 → 权威提交 → 受控效果 → 证据/结果提交 → 产品事件投影
```

模型可以参与提出意图和生成候选，但不能跳过其中任何一个系统责任者。

### 4.5 ApplicationHost：唯一跨边界组合根

每个生产进程只有一个 ApplicationHost 实例；一个进程可以同时承载多种设备角色，但不能出现第二组合根。Host 只负责：

1. 读取并冻结配置、身份、秘密投影和非公开依赖。
2. 依据静态、类型化依赖图创建领域单元、Kernel、正确性原语和适配器。
3. 选择进程内或远端绑定以及单机或分布式适配，不改变上层合同。
4. 管理启动补偿、开放入口、换代、拒新、排空、逆序关闭和残留清理。

Host 不实现会话、调度、推进、投递或设备管理用例，不持有领域事实，不作为运行期服务定位器。组件内部可以依赖自己的具体实现；跨责任边界只能依赖公开合同，只有 Host 可以在边界之间选择具体实现。

现有 `access-surface`、`StartupRollback` 与 shutdown chain 应被收编为 Host 的生命周期资产，但不能把当前巨型 `AssemblyContext` 原样命名成新架构。动态插件化不是目标：初始生产图应静态、类型化、可追踪，只有真实可选边缘使用受控组件贡献。

### 4.6 可替换边缘与封闭区

Provider、工具实现、MCP、Channel、Storage、Executor 和 Mesh 按家族实现窄端口，不强行统一成万能 `Capability`。同一实现可以承担多个角色，但必须分别实现对应端口，不能因代码复用混淆责任。

- **封闭区**：领域事实与规则、Agent Loop、权威提交、安全准入、恢复、资源治理和终态。扩展不能拦截或替换这些正确性责任。
- **可组合区**：Provider、工具实现、MCP、通道、产品表面渲染、存储和部署适配。替换必须服从同一身份、合同和生命周期。

可组合性首先服务可靠默认产品和项目维护者；普通用户可以改变真正有价值的偏好与产品表面，但不承担组装核心流程或维护系统正确性的责任。

### 4.7 设备产品语义与执行拓扑分离

用户可见的设备名称、配对关系、永久移除和值班迁移属于产品管理合同；Socket、epoch、ticket、Assignment、Mesh 路由和执行位置属于拓扑基础设施。前者通过领域应用端口表达，后者实现其所需的有限端口，二者不能共享一套内部对象作为产品 API。

单设备与多设备实现同一组应用和运行端口：

```text
单设备：Application Port → Local Authority / Local Executor
多设备：Application Port → Authority / Assignment → Mesh → Executor
```

领域单元不知道 Anchor、epoch 或连接；Kernel 不知道工具最终在本机还是远端运行；正常产品使用不要求用户理解拓扑。单设备始终是一等完整形态，多设备只是同一知行获得更多“身体”。

## 五、状态归属与依赖规则

### 5.1 状态只能属于一个稳定责任者

| 状态 | 唯一所有者 | 其他部分只能做什么 |
|---|---|---|
| Conversation、Workscene、Schedule、Advancement、Delivery 等产品事实 | 对应领域单元及其权威 | 持引用、调用应用端口、消费已提交事件 |
| Trust、Skill、用户可见设备关系等产品管理事实 | 对应管理责任者及其权威 | 表面呈现，基础设施执行有限请求 |
| 当前 Turn、模型上下文和工具调用 | Intelligence Kernel | 领域与表面观察有限运行事件并接收结果 |
| Progress Event | 对应运行活动的生产者，以领域合同声明身份与顺序 | 消费者只作瞬时观察，发现缺口后重新 Query 权威投影，不据此重建事实 |
| 权限决定、确认义务、资源租约、效果义务和恢复水位 | 对应 Correctness Substrate owner | 领域提交请求或引用结果 |
| 连接、路由、物理执行位置和 Mesh 临时状态 | 基础设施适配器及其权威 | 上层消费拓扑无关端口 |
| UI 选择、布局和瞬时输入 | 对应 Surface | 不改写产品事实 |
| 配置来源与秘密材料 | 专责 Configuration / Secret Provider | Host 只取得启动所需的只读投影；领域、Kernel 与 Surface 不读取来源 |
| 本进程冻结配置投影与组件生命周期 | ApplicationHost | 组件只接收自身所需的不可变值并管理内部资源，不反向查询 Host |

压缩摘要、索引、缓存、协议响应和界面状态都是投影，不能因为更方便查询就获得写入权威。

### 5.2 允许的跨边界依赖

```text
Surface ───────────────► Product API Client
Transport Binding ────► Product API Dispatcher
Product API Catalog ──► Domain-owned Contracts
Domain Unit ──────────► Other Domain Application Port / Kernel Port / Correctness Ports
Intelligence Kernel ──► Model / Tool / Runtime Contracts
Infrastructure ───────► Port It Implements
ApplicationHost ──────► Concrete Components（仅装配和生命周期）
```

端口由需要稳定语义的一方拥有，适配器实现端口。跨领域调用必须显式；领域内部无需为了形式纯洁把每个函数都接口化。

### 5.3 明确禁止

- CLI、Channel、Server 或 RPC handler 直接读写领域存储、Owner 日志或 Mesh 内部状态。
- Product API Catalog 重新定义领域语义，或成为装有全部业务对象的中央模型。
- Kernel 导入产品领域、产品表面、RPC 或设备拓扑。
- 一个领域绕过应用端口读取另一个领域的仓库或 Reducer。
- Infrastructure 生成产品流程、用户文案或领域决定。
- Host 在用例执行期间充当服务定位器或业务编排器。
- 用巨大根 barrel、全局单例、可变 lazy ref 或任意字符串注册隐藏必需依赖。
- 迁移期双写两个权威，或以兼容为由永久保留双主链、双状态机和双协议语义。

## 六、对现有包与代码的演进定位

先形成边界，再决定物理搬迁；文件移动、包数量和命名都不是架构成果。

| 当前落点 | 目标责任 | 演进重点 |
|---|---|---|
| `@zhixing/core` | 最小公共原语与明确 subpath 合同 | 停止扩大根导出；领域合同随领域归位，具体装配和产品实现退出公共中心 |
| `@zhixing/orchestrator` | 封闭 Intelligence Kernel | 收窄 `AgentRuntime`；移除产品领域知识和宿主管理内部对象 |
| `@zhixing/runtime-host` | Runtime Assembly / Factory | 只消费已解析 Run Envelope 与组件贡献，不直接认识 Workscene、Schedule 等领域 |
| `@zhixing/owner-kernel` | 通用 Authority、Commit、Recovery 与 Effect 原语 | 保留通用机制，领域 Reducer、状态机和用户语义回到领域单元 |
| `@zhixing/owner-services` | 当前领域单元的候选承载区 | 先在包内形成独立源码边界；不得把全部产品能力重新聚成服务大包 |
| `@zhixing/rpc` | Product API 的 RPC 绑定与运行事件投影 | 不拥有领域合同和应用用例 |
| `@zhixing/server` | 认证、连接、编解码、订阅和协议宿主 | 以 Product API dispatcher 取代巨型领域上下文；handler 不编排业务 |
| `@zhixing/cli` / Channel | 产品表面与进程入口 | 移出领域实现、Owner、Mesh 和生产后端，只保留输入、呈现、表面交互与启动选择 |
| `@zhixing/executor` / `@zhixing/mesh` | 执行与拓扑适配器 | 实现上层端口，不感知产品领域和表面 |
| `cli/src/serve` | 当前组合根、生命周期资产与大量暂居实现 | 原地形成 ApplicationHost 边界后按所有权迁出；不一次性搬迁 |

只有同时满足下列事实才新增物理包：边界已经稳定；存在独立消费者、发布、生命周期或故障隔离价值；拆包能够消除一条受门禁约束的错误依赖。否则优先用目录、subpath 和包内可见性建立边界。

## 七、对外部架构的选择性吸收

| 来源 | 吸收 | 在知行中的落点 | 拒绝 |
|---|---|---|---|
| Codex | Harness 后置；稳定控制/事件边界服务专业产品面 | Kernel + Product API + Surface | 把 Coding Thread、通用聊天框或 Runtime 变成知行的产品中心 |
| Pi | 模型层、Agent Core、产品装配和 UI 分离；应用消息显式投影到模型消息 | 薄 Kernel + Run Envelope / Event 投影 | 把安全、耐久和统一默认交给任意扩展 |
| DeepSeek Harness | 声明式依赖、作用域生命周期和可逆 Effect | Host 的类型化装配与边缘资源所有权 | Everything is a Plugin、运行期任意重写封闭区 |
| OpenCode | 一个行为所有者同时支持进程内和远端客户端 | 领域拥有合同、Product API 组合、多种 binding | 为目标架构长期维持 V1/V2 双轨或强制本机走网络 |
| OpenClaw | 常驻 Host 收拢入口、路由、Runtime 和投递生命周期 | 单一 ApplicationHost 与通道/设备适配 | 让 Gateway/Host 持有所有领域逻辑或成为产品身份 |
| Hermes | 多入口共享同一 Runtime，模型与执行位置分离 | 共享 Kernel 与显式执行端口 | 动态注册、学习闭环和功能广度进入本次架构目标 |
| NVIDIA AVO | 行动者、评价者、证据与成果准入分离 | 保持 Advancement 的执行—评价—提交边界 | 引入持续学习、成果进化或研究 Harness |

吸收项必须同时满足四个条件：有可靠事实；符合知行产品方向；解决当前真实结构问题；替代旧路径并落到唯一责任者。否则即使先进也不进入。最终设计必须看起来只能从知行的需求中长出来，而不是七套架构的平均值。

## 八、架构不变量

1. 当前产品能力、公开行为、数据、安全和终态在迁移中不变；能力增强另行立项。
2. 产品语义和权威事实不属于模型、Kernel、Host、Surface 或设备拓扑。
3. 一个事实只有一个语义所有者和一个写入权威；其余形态都是投影。
4. 每个领域同时拥有自己的合同、应用用例、规则和事实归属；Product API 只组合，不重定义。
5. 模型输出是提议或证据，不能扩张权限、资源、事实权威或效果范围。
6. Host 只装配和管理生命周期，不能进入用例主链或持有领域事实。
7. Kernel 只负责智能执行，不知道产品领域、表面和部署拓扑。
8. Surface 与 Transport 只能消费 Product API，不能复制应用状态机。
9. Server 是协议宿主，不是应用服务定位器；CLI 是产品表面，不是生产后端。
10. Correctness Substrate 只提供通用机制，不拥有领域规则；领域也不重造正确性机制。
11. 单设备始终是完整一等拓扑；多设备不能把 Anchor、Mesh 或连接复杂度泄漏给产品领域。
12. 扩展只进入可组合区，不能替换权威、安全、恢复、资源、终态或领域不变量。
13. 新抽象必须收敛当前真实分散责任，并能被依赖或合同门禁验证；未来想象不能单独证明其必要性。
14. 每次责任迁移都必须删除旧入口；兼容只能单向、有时限、无双写。

## 九、架构适应度门禁

架构只有被代码持续证明才成立。

| 门禁 | 必须证明什么 |
|---|---|
| 依赖方向 | 包与关键源码目录无环；禁止依赖在编译或静态检查中不可绕过 |
| 合同所有权 | 每项 Command/Query/Event 由对应领域定义，Catalog、RPC 和 Surface 不重定义语义 |
| 公共 API 预算 | Kernel、Domain、Correctness 和 Binding 的导出面有限，无内部对象与根 barrel 旁路 |
| 事实所有权 | 每项产品事实的写入口、Reducer、Authority 和恢复路径 exact-set 唯一 |
| 多表面一致性 | 进程内、RPC、CLI 和 Channel 调用同一应用用例并获得等价行为 |
| Host 生命周期 | 依赖先启动、入口最后开放；拒新后排空；资源逆序释放；故障注入无 listener、timer、进程、连接或临时残留 |
| Kernel Conformance | 对话、任务、本机和远端运行形态服从同一有限 Run Envelope / Event / Terminal 合同 |
| Authority / Effect | 有外部后果的动作不能绕过决定、提交、准入、结算和恢复链 |
| 拓扑透明 | 同一应用合同可绑定本机或分布式适配器，上层没有物理拓扑分支 |
| 变化影响面 | 代表性新增表面、Provider、设备或领域只修改允许区域；跨轴穿透即失败 |
| 产品回归 | 现有直接测试、根级门禁、打包和首版旅程在同一基线上成立 |

目录变整齐、接口数量增加、测试使用 mock 或旧入口仍可达，都不能证明架构完成。

## 十、目标架构迁移序列

本节只定义架构检查点的依赖关系，不是开发计划。每个检查点实施前必须另建执行单元，重新核对生产调用图、迁移范围、兼容窗口、旧入口删除和直接证据。

所有检查点只允许结构变化；首个版本发布不以完成本迁移为前提。

### 检查点 0：冻结行为与结构基线

- 固定公开行为、产品旅程、事实 owner、生产调用图、包依赖和生命周期基线。
- 建立第一批禁止依赖、公共 API 与 exact-set 门禁。
- 将能力需求、缺陷修复和架构迁移分开管理。

**退出门：** 后续改动能够证明是责任搬迁而非产品变化。

### 检查点 1：收束 ApplicationHost 生命周期边界

- 从现有 `access-surface`、启动回滚和关闭链中提取一个可创建、可启动、可排空、可关闭的 Host 对象。
- 用显式组件贡献和类型化依赖替代组合根内新增的可变引用与隐藏顺序，但不冻结当前巨型 `AssemblyContext`。
- Host 外壳仍可委托旧实现，不搬迁领域代码，不进入用例主链。

**退出门：** 每个生产进程只有一个组合根；完整启动失败和关闭可独立验证；Host 没有新增产品逻辑。

### 检查点 2：用一条真实垂直切片证明模块模型

- 从当前依赖事实选择边界最小、行为完整的现有领域，不预先指定名称。
- 让它同时拥有合同、应用用例、规则、权威适配、投影和生命周期贡献。
- 让一个现有表面经进程内或 RPC binding 调用同一领域端口；迁移后立即删除旧写入口。

**退出门：** 模块边界由生产行为和门禁成立，不靠新目录、接口空壳或双轨委托自证。

### 检查点 3：建立组合式 Product API 与纯绑定

- 从已经证明的领域合同逐步形成 Product API Catalog，不先设计全局万能协议。
- 将 ServerContext 的领域聚合拆成 dispatcher 与有限 binding 依赖。
- RPC handler、CLI controller 和 Channel adapter 只保留认证后的解析、调用、错误映射和呈现。

**退出门：** Catalog 只组合领域合同；Server 与 Surface 不再成为领域事实写入者；本机调用不被迫经过网络。

### 检查点 4：封闭 Intelligence Kernel

- 以当前运行形态建立最小 Run Envelope / Event / Terminal 合同和 Conformance Suite。
- 收窄 `AgentRuntime` 公共面；安全、权限和工作区内部对象不再泄漏给宿主。
- 把 Workscene、Schedule 等领域装配移到对应领域的运行信封生成方，RuntimeHost 只做通用装配。

**退出门：** Kernel 与 RuntimeHost 不导入产品领域、表面或拓扑实现；所有现有运行形态行为等价。

### 检查点 5：逐领域归位现有能力

- 按依赖从小到大迁移 Conversation、Workscene、Schedule、Advancement、Delivery 与现有管理责任。
- 每次只改变一个事实所有权，连同合同、应用服务、权威适配、表面绑定和直接测试一起闭合。
- 迁移一项立即删除其在 `core`、`server` 和 `cli/src/serve` 的旧业务入口。

**退出门：** 每项现有能力都能从领域合同追踪到唯一权威；跨领域协作只经过公开端口或已提交事件。

### 检查点 6：收束边缘与拓扑

- 将 Provider、工具、MCP、Channel、Storage、Executor 与 Mesh 绑定到各自家族端口。
- 把用户可见设备管理合同与物理拓扑实现分开。
- 让单机和分布式只在 Host 的适配选择处分叉。

**退出门：** 适配器不能反向定义产品语义；领域和 Kernel 没有拓扑分支；正常使用不暴露内部部署概念。

### 检查点 7：删除迁移结构并冻结架构

- 删除旧委托桥、无主公共接口、根级宽泛导出、lazy-ref 旁路和临时兼容。
- 完成依赖、合同、所有权、生命周期、Kernel、拓扑、变化影响面和产品回归门禁。
- 更新正式架构与模块索引，使文档和生产代码可以双向验证。

**退出门：** 不存在第二组合根、第二应用行为、第二状态机或第二权威；全部架构不变量由同一代码基线证明。

## 十一、未来变化的影响边界

本节不是能力路线，只检验目标架构是否允许未来变化优雅发生。

| 未来变化 | 合理影响范围 | 不应修改 |
|---|---|---|
| 新增产品领域 | 新领域单元、其合同、必要 binding 与 Host 静态贡献 | Kernel、其他领域存储、Mesh 协议 |
| 新增产品表面 | 新 Surface 与 Product API client/binding | 领域状态机、Agent Loop、Authority |
| 新增 Provider、工具或 MCP | 对应家族适配器与受控注册 | 产品合同、领域规则、Owner 语义 |
| 新增设备或执行拓扑 | Host 适配选择、Executor/Mesh 实现 | 产品领域、模型消息、表面流程 |
| 更换模型循环 | 新 Kernel 实现并通过 Conformance Suite | 领域合同、应用用例和产品事实 |
| 增加用户可组合界面 | Product API 之上的组件与 Surface 生命周期 | 权威、安全、恢复和智能执行闭环 |
| 更换存储技术 | 对应领域仓储或 Correctness 适配器及迁移 | 产品合同、Kernel、Surface |

如果一种普通变化必须同时修改 CLI、Server、Agent Loop、Owner、Mesh 和多个领域存储，说明架构边界没有建立成功，而不是变化天然复杂。

## 十二、项目治理规则

每个架构执行单元必须给出：当前责任与调用图、要建立的不变量、最小迁移范围、单向兼容窗口、旧入口删除、适应度门禁和现有行为回归证据。

- 先用源码证明结构问题，再设计责任边界；不按过时文档搬代码。
- 先在现有目录形成所有权，再决定拆包；不以文件移动冒充架构进展。
- 一次只改变一个责任所有权，保持每个中间状态可构建、可运行、可发布。
- 允许短期单向适配，禁止双写、双权威、双状态机和无期限兼容。
- 先用最小真实垂直切片验证模式，再迁移 Conversation 等高耦合主链。
- 只按真实失效闭包验证；最终基线再运行全量门禁，不用重复全测制造安全感。
- 架构迁移只衡量责任、依赖、生命周期、旧路径和行为等价，不借机补功能。
- 首版正确性、安全性和体验问题优先；架构愿景不能成为延迟发布的理由。

## 十三、明确取舍与不做

本设计选择领域拥有合同而非中央业务模型，选择静态类型化装配而非运行时万能插件，选择进程内与远端共享语义而非一切网络化，选择单设备完整而非多设备优先。这些取舍牺牲了一部分任意组合自由度，换取产品一致性、可追踪责任和可靠默认体验。

- 不新增 Self、Commitment、Presence、Attention、Learning 或其他未来产品对象作为迁移前提。
- 不决定或实现任何记忆方案，不增强学习、主动触达、多设备体验或生态能力。
- 不推倒重写 AgentRuntime、Owner 或 distributed-runtime。
- 不把 distributed-runtime、多 Agent、插件、沙箱、协议或任何单项技术提升为架构中心。
- 不把所有能力合并成万能 Task、Session、Capability、Control Plane 或 Personal State。
- 不建立第二套 Conversation、Run、Schedule 或全局事实源。
- 不把全部实现动态插件化，不预建插件市场、自修改框架或远程微服务体系。
- 不为没有当前事实依据的未来变化增加抽象。
- 不要求首个版本等待架构演进完成后发布。

## 十四、最终判定

知行下一代架构的原创价值，不是再增加一个更大的“核心”，而是重新定义什么才是知行本身：

> **知行存在于唯一的产品语义、权威事实与共同应用行为中，而不寄生于任何模型、运行时、进程、界面或设备。领域负责“知行是什么意思、能够做什么”，智能内核负责“怎样思考和行动”，正确性底座负责“什么真正成立”，Host 负责“这些部分怎样可靠共存”，多种身体只负责“知行在哪里出现”。**

这套架构对用户不增加学习成本，甚至不应被感知；对开发必须产生可验证的变化：新增能力不再穿透全栈，更换模型不改产品语义，增加表面不复制行为，增加设备不引入第二个知行。只有这些结果同时由依赖、合同、所有权、生命周期和产品回归门禁证明，架构演进才算完成。
