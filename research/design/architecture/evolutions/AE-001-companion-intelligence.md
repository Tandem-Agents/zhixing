# AE-001：伴身智能架构演进

> **状态**：构想中
> **目标**：以知行自身的架构核心为基础，优雅吸收外部优秀架构带来的产品价值，推动通用个人助手向伴身智能演进。

## 一、原始构想

```text
我们做这个智能体的初衷，包括产品定位，是定位在通用智能体个人助手。长期看的话，还想把它定位成更高级的“伴身智能”——陪伴的伴，身体的身，就是随时在用户身边，可以在多个设备同时协作，然后可以把消息推送到离用户最近的设备上，这种智能体验。

然后中间的一些架构选择，包括你说的那个跨端的事情，它都是一部分，它绝对不是我们整个的核心。所以我感觉目前因为跨端这个事做的比较多、做的比较重，反而让它突出来了，就感觉很奇怪。因为我们本身不是专门去做一个跨端的东西，而是我们要做一个个人助手，然后有那个需求，所以做了那个功能。

所以目前的话，我们在考虑是我们架构的短板在哪里。或者说，我们已经知道了他们几个的架构部分优点、缺点就不说了，就他们的架构优点也很清晰的情况下，我们有没有可能去汲取他们的优点为我们所用？也就是说，对架构进行一次进化。

我们并不是说像缝合怪一样，把他们各个部分架构的一部分代码拿过来，粘在一起，粘成一个新的一个智能体的架构或者产品，这不是我们想要的。
而是我们整个架构的起点，一定得从我们整个产品的定位开启。我们是一个通用个人助手，面向未来设计，而且发展方向还是伴身智能，在用户身边 24 小时存在，可以在多个设备协作。就我们的初心、我们的需求，也就是以我们的需求为基础，去开启我们架构的这个设计。
所以目前各个智能体架构对比的那个文档里面的东西很有价值，但我们并不是要做缝合怪，而是分析出他们的架构的优点以及产品的优点，对我们的需求和目标有价值的部分。并不是说他们好，他们某一个角度肯定都有各自的优点，但并不是说他们好我们就要拿过来，而是说他们好的那一部分和我们整个产品的思路和方向一致的，才是对我们有价值的好的部分。
也就是说，他们的优点得和我们的产品方向、需求一致才有价值，提炼出来之后，再去思考我们的产品以及架构优化。

比如那个 DeepSeek Harness 的插件式组合运行时，对吧？它那个底层和咱们就不一样，包括好几个优点，底层和咱们都不一样。咱们要直接照他们做的话，就得推倒重来，这绝对不是我们要采取的方案，对我们来说甚至是退步的一个方案。

所以对我们来说，他们的优点我们是需要的。所以是以我们自己的架构核心为基础，然后再考虑如何在此基础上，那绝对也不是说乱拼乱凑，而是找到一种非常优雅的方式，把他们的优点集成到我们的架构中。

我们能不能也做插件式的思想？插件式的思想关键不是为了技术而做技术，而是能不能给用户提供那种插件式的思想所对应的产品能力。比如说它可以热插拔更新，就是让用户可以自定义这个智能体的一些前端组件。对普通用户来说，他能看到的就是组件。

然后对于智能体的核心工作流程，这些部分我认为反而虽然你也能插拔，但我认为不应该暴露给用户。因为一个智能体如何达到一个最优的工作状态，它是清晰的，这应该是不向用户暴露的，也不应该让用户去修改。

所以真正我认为这个插件组合运行时，它真正的优点是能让用户去自定义一些自己的使用偏好，包括前端的偏好，而不是整个系统的核心。系统的核心我认为不需要插拔，关键就是它自己的用户偏好可以插拔，所以我们要汲取的是这些优点。

然后还有就是 Pi，就你说的那个 Pi 极简的那个 Agent，它的优点是它目前有人反映说说它的写代码能力更强，因为约束更少，相当于对整个大模型的约束更少。它很极简，反而让大模型通过 Agent 发挥出了更多能力，所以很多人对这个 Pad 智能体的评价很好。
我觉得这个优点我们可以汲取。我认为这个架构和我们本身不是很冲突，它的优点我们可以汲取过来。

比如其他优点，我指的是我们并不是要东拼西凑乱七八糟成一个混合怪，我们不要这样的东西。而是以我们核心的架构思想为核心，去提取他们能提供给用户的优点，然后反向去映射到我们架构该怎样去优化。

就以我们自己架构为核心，去理解他们架构所带来的产品优点，反向去推导我们的架构该如何去做。不要缝合怪，但是我们要以很优雅的方式把架构进行升级。我并不希望别人看到我们汲取了各家的优点之后，一进来让人觉得很不专业、乱七八糟的全都有，而是以一种很优雅的架构呈现。比如别人看到 DeepSeek Harness 插件式的设计会眼前一亮，我们也需要这种优雅的架构。我们的目标是让架构升级，要求是优雅地升级。

还有一个问题，我觉得我们目前的架构虽然代码量已经写了大半，但整体架构并不清晰。我们需要一套即使是世界顶级架构师/智能体专家/前沿智能体研究员 也会欣赏，想要分析，思考甚至借鉴的架构设计和架构思路以及架构实现。我们把产品的定位/需求搞明白了，你来为项目整体架构负责。
```

## 二、初步架构方案

可行，而且不需要推倒重来。正确方向不是“把各家架构装进知行”，而是先重新确立知行唯一的架构中心，再让外部优点成为这个中心自然长出来的能力。

你说得对：我前一次分析把近期投入最大的“跨端执行网络”误当成了知行的核心。它其实只是知行的身体和神经系统，不是知行本身。

## 当前架构的真实情况

基于现有架构、组合根和生产调用关系，当前知行可以准确描述为：

> 知行以每个会话的权威 Owner 和耐久 Run 为状态中心，由 RuntimeHost 装配独立 AgentRuntime，再通过 Anchor、Executor 与 Mesh 将完整运行投送到本地或远端环境，并通过 CLI、Server 和 Channel 呈现给用户。

这句话描述了现在的工程架构，但还没有表达知行为何存在。

当前不是“没有架构”，而是存在三个都很强、却没有被一个更高概念统一起来的中心：

- AgentRuntime：负责认知、上下文、工具和任务执行。
- Owner/Authority：负责状态权威、提交、恢复和单飞。
- Anchor/Executor/Mesh：负责跨设备执行、连接和投递。

跨端部分合同最完整、投入最大，因此反客为主，遮住了“个人助手”这个产品中心。顶层架构文档也没有完整统合后来的 Owner、Executor、Mesh 和耐久恢复体系。

## 应当确立的新架构核心

我建议把知行的母架构定义为：

> **一心多身、随境而现：一个持续存在的个人智能，通过多个设备、工具和通道获得能力，并在最适合用户的界面上自然出现。**

更技术化的一句话是：

> **知行以一个持续存在的个人智能为中心，由精简而固定的智能内核驱动认知与行动，把设备、工具和通道作为受控能力接入，把界面与偏好作为可组合体验呈现，并由隐藏的权威与执行网络保证它在单机和多设备间连续存在。**

这才是知行自己的架构思想。跨端协作只是“多身”的实现；用户只有一台设备时，它自然退化为“一心一身”，完全不感知拓扑。

可以进一步浓缩为两条架构原则：

> **内核固定，能力受控，体验可组装。**
> **一个智能，多种身体，同一连续体验。**

## 目标结构

```text
用户感知：始终是同一个个人助手
                    │
        体验组件层：界面、卡片、输入方式、偏好
                    │
        在场与注意层：何时、何地、在哪台设备出现
                    │
        能力网络：设备、工具、模型、通道、执行环境
                    │
        个人智能：认知、记忆、任务、身份、安全边界
                    │
隐藏基础设施：Owner、Journal、Anchor、Executor、Mesh
```

这里最重要的边界是：

- 智能内核不向普通用户开放任意插拔。
- 安全、权威提交、恢复和状态机不允许插件介入。
- 用户可以组合的是体验、偏好和被授权的能力。
- 分布式机制隐藏在产品背后，不能成为用户心智负担。

## 如何吸收各家的优点而不成为缝合怪

### DeepSeek Harness：吸收“组合”，不复制“万物皆插件”

值得吸收的是：

- 声明式组件关系。
- 明确的依赖与生命周期。
- 可替换、可回滚、可独立换代。
- 内建组件和外部组件遵循相同接入合同。

但只应该用于适合变化的边缘：

- 界面组件。
- 卡片和信息呈现。
- 输入方式。
- 通知样式。
- 用户偏好组合。
- 受权限约束的能力适配器。

不应该插件化：

- Agent Loop。
- Owner 权威提交。
- 安全决策。
- 耐久恢复。
- 核心记忆语义。
- 运行一致性。

因此知行不是“Everything is a Plugin”，而是：

> **Everything user-shaped is composable; everything correctness-critical is sealed.**
> 一切由用户塑造的体验都可组合，一切决定正确性的核心都保持封闭。

这比全插件化更符合个人助手产品。

### Pi：吸收“模型自由度”，不删除工程安全

Pi 真正值得借鉴的不是简单地“约束少”，而是模型面对的永久负担更少。

知行应该：

- 缩小永久系统提示词。
- 每轮只暴露当前任务需要的工具和知识。
- 消除重复、冲突和低价值规则。
- 把权限、并发、恢复和一致性放在确定性代码里，不让模型靠提示词维持。
- 让模型专注理解、推理、创作和决策。

这不是放弃安全，而是：

> **减少对智能的语言束缚，增加系统边界的确定性。**

它与知行现有架构并不冲突，反而能让已经很强的工程底座减少对模型能力的压制。

### OpenCode、Codex、OpenClaw、Hermes

可以分别吸收：

- OpenCode：一个运行协议服务所有客户端，避免 CLI、桌面端和通道各走旁路。
- Codex：把任务、运行、事件、权限确认和子智能体作为明确协议对象，但应映射到现有 Conversation/Run/Event，不能另造第二套事实。
- OpenClaw：成熟的通道、设备在场和消息投递体验；Gateway 只能是入口，不能成为个人状态权威。
- Hermes：长期记忆、个性与经验积累的产品价值，但所有学习必须可解释、可撤销、受用户控制。

这些都能放进上述层次，不需要增加平行内核。

## “伴身智能”还缺的关键架构能力

现在最明显的短板不是跨端能力不足，而是以下内容尚未成为顶层一等概念：

1. **个人连续性**

   身份、记忆、任务、偏好和关系应共同描述“这个智能是谁”，而不是分别散落在运行机制中。
2. **在场模型**

   不只是设备在线，而是知道用户当前可触达的表面、设备能力、隐私环境和打扰成本。
3. **注意力路由**

   “离用户最近”不能只等于网络距离。它应综合设备是否正在使用、消息紧急程度、隐私、交互能力和重复打扰风险，最终只产生一次合适投递。
4. **统一的体验组件合同**

   目前工具、MCP、Provider、Channel、技能和生命周期都有扩展点，但它们是不同年代长出来的局部机制，还没有被一个“用户体验贡献”模型统一。
5. **模型侧复杂度预算**

   知行的确定性工程能力很强，但需要审计这些能力是否把过多规则、工具和上下文永久压给模型。否则底座越强，模型反而越难发挥。

## 防止架构成为缝合怪的硬标准

任何外部架构思想进入知行前，都必须同时通过五项判断：

1. 能明确说出它给用户带来的结果。
2. 能用知行自己的架构语言表达，不依赖原项目概念。
3. 在目标架构中只有一个明确归属层和责任所有者。
4. 必须替代、合并或简化已有机制，不能增加平行事实源。
5. 单机默认用户完全感知不到新增复杂度。

只要其中一项不成立，就不应吸收。

## 最优演进顺序

现在不应立即开发插件系统。最优顺序是：

1. 完整重建当前架构事实图：包、组合根、事实源、生命周期、依赖方向、扩展点和模型上下文。
2. 定稿“一心多身、随境而现”的目标架构总纲，明确封闭内核与可组合边缘。
3. 找出当前三个中心之间的重复、旁路和职责漂移。
4. 先做模型侧减负，让确定性规则回归代码，只投影当前任务所需能力。
5. 建立有限的类型化体验组件合同，先覆盖界面和偏好，不碰智能内核。
6. 在现有 Mesh、Delivery 和设备事实之上建立在场与注意力路由。
7. 等合同稳定后再调整包边界，避免为了“架构升级”进行无价值重写。

结论是：**可行，而且现有代码并不是包袱，反而已经具备智能内核、权威连续性和多设备执行这三个很难补齐的基础。真正需要的不是推倒重来，而是重新确立中心、封闭核心、统一边缘、降低模型负担。**

如果这条路线完成，知行的架构辨识度不会是“集成了很多智能体的优点”，而会是一个清晰、独立的命题：

> **一个持续存在的个人智能，多种受控身体，体验随用户而变，核心不因扩展而失序。**
