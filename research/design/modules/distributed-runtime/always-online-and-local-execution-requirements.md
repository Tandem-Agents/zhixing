# 持续在线与本地执行：需求与信息核验

> 架构设计见：[知行分布式运行时架构总纲](./distributed-runtime-charter.md)。

## 一、我的核心问题

个人智能体应如何部署，才能既保持随时在线，又能进入用户真实的工作环境完成任务？

困难在于：部署在用户电脑上虽有真实工作环境，却会随电脑关机而离线；部署在服务器上虽能持续在线，却脱离了用户真实的工作环境，执行能力会大打折扣。

## 二、对方回复的信息整理

以下内容仅是对方回复所提供信息的提炼，不代表我的意见，也不代表项目或任何其他人的意见；其正确性尚未核实，后续必须逐条审核，不能直接作为事实或标准答案使用。

1. 对方称，OpenClaw 在逻辑上将负责对话、规划和调度的 Gateway 与负责实际操作的执行节点分开，两者既可部署在同一台电脑，也可分开部署。
2. 对方称，系统始终只有一个 Gateway 维护对话、记忆、任务和最终回复，手机等入口只连接 Gateway，执行节点不拥有独立会话，也不直接回复用户。
3. 对方提出，可将 Gateway 部署在持续在线的设备上，将执行节点部署在用户电脑上，以兼顾持续待命和使用真实工作环境，并在电脑离线时暂存依赖该电脑的任务。
4. 对方称，一个 Gateway 可以连接多个执行节点，并依据节点身份、在线状态和能力信息进行定向派发或自动选择。
5. 对方认为，单机部署与分开部署不是两套系统，而是同一逻辑架构的不同部署形态：前者门槛较低，后者适合有持续在线或多设备需求的用户。
6. 对方判断，长期产品形态可能是统一的调度与对话中枢配合分布在真实设备上的执行节点，同时应向用户隐藏底层部署和调度复杂度。

## 三、执行者核实后的真实信息

核验时间：2026-07-10。以下信息以 OpenClaw 官方文档和官方源码仓库为准。

1. OpenClaw 的 Gateway 是控制中枢，Node 是可选的远程能力节点；Gateway 可以把命令转到其他设备执行，但单机运行时工具默认可直接在 Gateway 所在主机执行，并不要求额外启动 Node。（[Nodes](https://docs.openclaw.ai/nodes)、[官方仓库说明](https://github.com/openclaw/openclaw)）
2. 会话、状态和渠道由 Gateway 持有，渠道消息先到 Gateway，Node 只接收节点调用并返回结果，不直接接收渠道消息或独立回复用户；一个 Gateway 可以承载多个 Agent 和多个会话。（[Remote access](https://docs.openclaw.ai/gateway/remote)、[Session management](https://docs.openclaw.ai/session)）
3. 官方支持将 Gateway 放在常开主机或 VPS、将个人电脑接成 Node；协议也提供离线节点的持久待处理工作接口，但普通本地任务是否自动排队和恢复仍取决于具体调用流程，不能视为所有任务的默认保证。（[Remote access](https://docs.openclaw.ai/gateway/remote)、[Gateway protocol](https://docs.openclaw.ai/gateway/protocol)）
4. 一个 Gateway 可以连接多个 Node，并识别其身份、名称、连接状态、权限和能力，也可以明确指定执行节点；官方未提供通用自动负载均衡或分布式锁保证，`host=auto` 也不会自动选择 Node。（[Nodes](https://docs.openclaw.ai/nodes)、[Exec tool](https://docs.openclaw.ai/tools/bash)）
5. 单台电脑、常开家庭主机和远端常开 Gateway 都是官方列出的部署拓扑；它们属于同一产品的不同部署选择，但官方没有把它们定义为固定的“新手模式”和“高级最优模式”。（[Remote access](https://docs.openclaw.ai/gateway/remote)、[FAQ](https://docs.openclaw.ai/help/faq)）
6. 官方资料只能证明“统一 Gateway + 可选分布式 Node”是 OpenClaw 当前支持的架构，无法证明它是未来五到十年的唯一终局，也不能据此直接推出知行应采用云端唯一中枢。

对照判断：对方第二点基本准确；第一、三、四、五点方向存在，但加入了未被官方完整支持的机制或定性；第六点属于产品观点，无法按事实判真伪。

## 四、架构者审核与分析结果

核验时间：2026-07-10。独立于第三部分重新核对，来源为 OpenClaw 官方文档、官方仓库与社区部署指南。逐条对应第二部分：

1. **部分属实，关键定性错误**。Gateway 与 Node 分离属实：Node 是以 `role:"node"` 接入 Gateway 的伴随设备（companion device），"nodes are peripherals, not gateways"。但"Gateway 管思考、执行节点管实际操作"的二分不成立：默认部署下工具直接在 Gateway 所在主机执行（"tools run on the host for the `main` session"），单机默认不需要、也不会自动运行 Node（用户仍可选择在同机额外跑一个 Node）——对方"单机部署天然就是 Gateway+Node 两进程经 127.0.0.1 通信"是把可选形态说成了默认机制。（[Nodes](https://docs.openclaw.ai/nodes)、[官方 README](https://github.com/openclaw/openclaw)）
2. **属实**。"All session state is owned by the gateway; UI clients query the gateway for session data"；会话与 transcript 落盘于 gateway 侧 `~/.openclaw/agents/<agentId>/sessions/`；一个 Gateway 可承载多 agent、多会话；Node 无会话态、不独立回复。（[Session](https://docs.openclaw.ai/concepts/session)）
3. **拓扑属实，自动化叙事夸大**。官方 VPS 页明确支持"Gateway 留在云端 + 本地设备配对为 node"；协议层有离线节点的持久待处理队列（`node.pending.enqueue` / `node.pending.drain`，"durable pending work for offline/disconnected nodes"）。但"Gateway 自动判断任务需本机 → 自动排队并告知用户 → 开机自动续跑"是把协议原语升格为默认产品行为，官方无此端到端编排保证。（[Linux server/VPS](https://docs.openclaw.ai/vps)、[Gateway protocol](https://docs.openclaw.ai/gateway/protocol)）
4. **定向派发属实，自动调度编造**。多 Node、签名设备身份 + 配对审批、"节点声明 + 网关允许清单"双闸均属实；但落到本机执行必须显式选 `host=node`（`host=auto` 只在 sandbox / gateway 之间解析、永不自动选 node）；节点选择上官方仅说明"多节点时经 `exec.node` / `tools.exec.node` 或 per-call 参数指定目标"，未定义省略节点 id 时的自动路由行为，浏览器工具则可自动路由到唯一可用的浏览器节点（`gateway.nodes.browser.mode: "auto"`）；准确定性是：官方没有通用的多节点智能调度——无轮询、负载均衡、分布式锁。（[Nodes](https://docs.openclaw.ai/nodes)、[Exec tool](https://docs.openclaw.ai/tools/exec)、[Browser tool](https://docs.openclaw.ai/tools/browser)）
5. **"同一产品不同拓扑"属实，人群定性编造**。官方并列三种拓扑（tailnet 内常开主机 / 家用台式机 / 单笔记本），无"新手默认 vs 高级最优实践、90% 深度用户"之说；所查到的社区 VPS 指南呈现的形态是"整套 Gateway 上云做全能力 agent、笔记本只作控制入口"，未见支撑"90% 深度用户云脑 + 本地手脚"的依据（样本有限，不作主流定性）。（[Remote access](https://docs.openclaw.ai/gateway/remote)、[RamNode OpenClaw 系列](https://ramnode.com/guides/series/openclaw/introduction-architecture)）
6. **观点，不判真伪；补一个对方回避的机制硬伤**：Gateway 上云后，agent 的默认执行面与 workspace 随 Gateway 落在云端（"The Gateway runs on the VPS and owns state + workspace"）；本地 Node 暴露的是受控、可扩展的远程能力面（screen / camera / canvas / `system.run`、浏览器代理等），但不是完整 agent 工具面——"执行环节依然跑在本机、与本机部署一模一样、性能零缩水"与官方机制不符。OpenClaw 的真实形态是"单机全能力为默认、分布式为可选扩展"，而非"分离是原生设计目标、单机只是特例"。（[Linux server/VPS](https://docs.openclaw.ai/vps)、[官方 README](https://github.com/openclaw/openclaw)）

综合判断：第 2 条为真；第 1、3、4、5 条方向存在但机制与定性大量加工，系统性偏差是把"协议支持的可选能力"一律升格为"官方推荐的默认产品行为"；第 6 条是产品观点。对知行的可用结论：「常驻中枢 + 跨机执行节点」作为方向值得独立研究，但 OpenClaw 现状不构成"云端唯一中枢是最佳实践"的证据；若知行做跨机执行，必须正面解决对方叙事跳过的两个核心问题——远端执行面的能力完整性（受限命令面 vs 完整工具面）与任务排队 / 恢复的端到端语义。

## 五、归纳：龙虾在"随时在线 vs 真实工作环境"上的真实现状

龙虾的真实形态是：Gateway 是唯一的大脑兼默认的手脚——它持有全部会话、记忆和工具执行面，部署在哪台机器，agent 的完整能力（文件读写、命令执行、workspace）就在哪台机器，单机运行默认不需要 Node。官方支持把 Gateway 放在常开主机或 VPS、再把个人电脑配对为 Node，所有入口只连 Gateway、不存在双脑消息冲突；此时云端大脑确实能进入真实电脑环境——Node 经 `system.run` 可在本机执行命令、操作文件与软件（受本机审批门控），浏览器工具还能自动路由到本机浏览器。但这与 Gateway 直接跑在本机不等价：agent 的默认执行面与 workspace 仍留在云端，Node 只是按调用触达的命令面，离线任务只有协议级排队原语、没有"自动判断-排队-续跑"的端到端闭环，也没有通用的多节点调度。所以对我们最初的问题，龙虾的现状是在"能力连接"层面部分解决：持续在线与真实工作环境可以兼得一部分，但在完整能力等价、自动选机、通用离线排队与可靠续跑上尚未形成无缝闭环。

## 六、我的想法

```text
首先，我说的是需求啊，需求说明白就行
对于用户来说，我认为倒不一定分主次。什么意思呢？就是有的用户只需要在一个电脑上部署和使用，这就够了。有的用户需要一个 24 小时在线的智能体，同时希望能在电脑上完成工作，但电脑无法 24 小时开机。这个需求比较契合我们第一部分提到的问题。但我想核心表达的意思是：用户在一台电脑上完成任务和工作，这是一个正常需求，甚至可能是很大一部分需求；另一部分需求也和这个问题相关，同样是正常需求。

这两个需求在设计架构时需要同时满足，分主次不是最重要的，关键是在架构设计上能很好地支持这两种形态。
而且我心中一直有一个疑惑的点，就在于如果用户是通过飞书这种接入面去使用的话，那我的理解是：在云端部署一个最小接入面，用于这个智能体，然后在工作电脑上放一个“手和脚”。

这听起来没有问题，因为说白了用户使用飞书的话，飞书的消息是先到飞书的服务器，然后飞书的服务器其实是和用户云端的那个最小核心保持长连接的。它是这样的一种结构。这种结构在使用飞书这个接触面的时候没有什么问题，很正常。因为即使不在云端，它在用户本地的话，它也是这样的结构。就是飞书的消息，它总得先到飞书的服务器，然后飞书的服务器再连接这个运行时的这一部分。
但是如果说在电脑上工作的话，因为在电脑上工作它是一个非常常见啊，甚至可能是主流，就这个不好分主次的，因为这对用不同用户来说对吧，这这就没有主主次之分，有的用户他就是完全是在电脑上工作的啊，呃所以如果是在电脑上工作的话，他使用的是接入面比如说是终端。终端并不是我们在电脑上唯一的接入面，这只是现阶段目前唯一的接入面。未来我们可能会自己去做桌面端的应用，那这也是一个接入面啊，就是和我们现在架构是不冲突的，它都只属于一个接入面，只是说现在在电脑这个平台上目前只有终端，就是我们是渐进式开发的。
我想表达的意思是：如果是在电脑上使用，无论是现在的终端还是未来的桌面客户端，用户的消息通过终端先发送到远程，再由远程传回终端，感觉多此一举，不是最优结构。

这和飞书不同，飞书因为涉及第三方 APP，确实需要经过第三方服务器。但如果是自己电脑上的接入端（如终端或未来客户端），数据还要先飞到自己的云端，再从云端飞回来，感觉有点别扭，和飞书不是一码事，结构感觉不对劲。
所以我想的是，它能不能既满足用户 24 小时随时唤醒使用的需求，又能满足用户在桌面端终端或客户端界面上自然、高效地使用。比如通过终端使用，再把消息发送到云端，然后消息再回到终端，听起来它就不是一个高效的架构。
我们描述的这个需求，和其他模块在需求层面并不直接冲突。虽然架构上可能涉及修改甚至重构，其他模块也可能因此需要重构，但其他模块的需求本身是清晰且不变的，重构后仍需满足同样的需求，因此不需要重新描述已有模块的需求。

简单来说：这个需求是真实需要做的，但它涉及架构层面的改动，而其他模块的业务需求保持不变。

我认为我把我内心的想法的需求说明白了
```

## 七、价值质疑与定论

> 记录时间：2026-07-16。此质疑曾一度动摇是否继续做本模块，故与定论一并存档。

**质疑**：这个产品终究要求工作电脑开机才能干活。电脑开着，值班设备似乎多余；电脑关着，值班设备只能响应、无法真正工作。两头都不成立，价值存疑。

**定论**：质疑隐含一个把产品窄化的前提——把"有价值的事"等同于"必须在工作电脑环境里干的事"。拆开二分的两半：

- **电脑关机时**，锚点不是只会应答的留言机：对话、记忆、提醒、定时任务、联网研究等不依赖工作环境的能力完整（锚点可同时运行普通执行宿主）；环境绑定的任务被诚实排队、开机自动续跑、完成通知——请求永不丢失，"现在干不了"被变成"到时候一定干"，这本身就是产品价值。没有锚点的对照组是：人不在电脑前，话发过去就丢了。
- **电脑开机时**，数据面直连、体感与单机一致，锚点对用户近似零成本、不可见。开机时它不占任何交互路径，关机时它是智能体活着与死了的区别——这个不对称本身就是答案。
- **质疑成立的窄面如实承认**：若某用户的使用百分之百是环境绑定的本地工作，锚点对他的增量确实薄（排队、通知、定时任务）。但这已被架构消化：两种形态平权、单机用户不为分布式付任何代价、角色是配置不是版本——锚点是给"需要随时在线"用户的可选形态，不是强加给所有人的成本。

**价值命题的准确表述**：不是"电脑关机也能干活"（违反物理；把工作环境搬上云则丢掉真实工作环境，本文核验已看清该代价），而是——**智能体永远活着：能答、能记、能跑不挑环境的活；挑环境的活接住不丢，等环境回来自动续上**。对一个要成为"数字分身"而非"开发工具"的产品，这个命题成立，且正是它与"打开才存在的工具"的分界线。

后台运行选择必须同时诚实处理“以后是否自动拉起”和“当前实例是否仍在运行”：用户关闭某台设备的后台角色后，新请求先停止准入，已接受工作按现有安全停机链收束，旧实例不能继续冒充可用；公开状态必须从同一次当前配置、真实系统服务与运行就绪事实产生。纯接入面或空角色设备仍保持零本机常驻，但它是完整产品入口：只把受支持的第一方请求经认证链路送到当前值班设备，值班设备换代或离线时不得回退旧设备，也不得在本机偷偷拉起宿主。

后台收敛与纯接入面恢复还必须有清晰上界：同一 home 的后继唤醒若恰好加入一个失败中的收敛任务，只允许在共享失败后再合并出一次后继任务，持续故障不得形成自激重试；纯接入面的当前值班设备轮询在短暂断线或忙碌后应自行恢复，不要求用户再发一条命令，关闭、换代或稳定错误又必须精确停止旧轮询。连接级关闭只由当前轮询 controller 持有，每次 poll attempt 只借用其 signal，任意成功次数下长期 callback/controller 必须保持 O(1)。系统服务 start 的权限、manager/session 不可用、有文档依据的不存在和其他失败必须给出稳定行动含义，并以实际运行回读而不是命令返回值宣称成功。

Windows 后台服务的系统回读不得依赖本地化展示文本或宽松 XML 片段：只接受 numeric task state、当前用户有限身份集合与完整 typed trigger/action exact-set 的严格投影；`RegisteredTask.Enabled` 与 `Definition.Settings.Enabled` 必须一致，冲突时拒绝投影，一致值只表示动态 future-enabled，不参与 immutable definition identity。配置换代要求 explicit drain 先收束既有 accepted work；关闭非 managed 选择时，future launch 必须在等待旧 endpoint turnover 和连接新代之前关闭，而任一 reconcile 唤醒都不得凭 trigger 或 service id 终止当前实例，current stop 只接受既有 graceful completion 或 exact stale endpoint/lock 事实。跨平台 fake-runner 的文件副作用证据必须落在每例唯一的宿主临时目录，禁止把 guest 语义路径当成宿主物理路径。

主动停机、设备移除和永久卸载都必须先把已接受工作变成可重放的确定结果，再结束精确的旧宿主或撤销身份。停机不能只看 PID，托管实例还须同时匹配完整运行端点、服务定义和系统管理器回读，后继实例不得被误停。设备移除应在任何转移或销毁前展示无副作用的真实本地工作摘要；确认后若集合漂移须重新展示，目标与签发端的取消、就绪、撤销、清理和终态在断线或重启后仍只能收敛到一个结果。永久卸载选择恢复备份时，首份与最终备份都必须用用户恢复包从冻结目标真解封，最终备份覆盖退役决定后才可清理；清理按固定小批次进行，设备身份密钥最后删除。公开入口对未知或错误字段稳定拒绝，不把内部身份、拓扑和恢复细节交给用户判断。

## 八、值班设备迁移的当前产品要求

用户可以把值班职责主动迁往另一台已经配对、在线且完成值班配置的设备。产品只展示“值班设备”和目标设备名称：列表必须由无密钥、无 staging 副作用的就绪投影产生；交互终端按可用设备的名称与序号选择，非交互调用只接受唯一设备名，重名稳定拒绝且不得要求或展示内部设备 ID。准备阶段明确缺少的本地配置，收束与传输期间显示正在进行，真正切换前允许取消；一旦开始接管，旧设备不能因断线或结果不明自行恢复值班，用户只能用同一迁移编号继续，完成后如需迁回则重新发起一次迁移。迁移不复制任何设备秘密、环境值、工作区原始路径或缓存；目标设备必须依靠自身配置和本地秘密独立服务。任何失败都必须诚实区分“仍可取消”和“只能继续”，不得向用户暴露内部角色、epoch、签发密钥或权威目录术语。
