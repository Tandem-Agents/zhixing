# 终端架构迁移 · 多角色工作方案

本文只定义本次迁移的角色、工作方式与交付门槛，不预定技术选型。独立于既有跨会话协作体系设计，不继承其角色、决策流程或登记机制；只吸收并调整有效沟通经验，项目常驻规则仍适用。角色会话、当前任务和执行闸门登记在本机 `collab/terminal-migration/index.md`，不把动态状态写入本方案。

**执行版本：v2.3（2026-10-04）。** 保留连续执行权、独立验收及主动交接；明确提交单元小于迁移单元，在开发中持续形成可独立回滚的批次。生效与角色接收状态由当前任务索引记录，安排在当前改动的安全收束点接续，不强行打断未闭合操作。

## 一、共同目标

在智能体核心独立于界面的前提下，重建可靠的终端底座，完整承接已有功能、页面与有效体验，消除旧架构债务和已知交互故障。必须证明用户获得实质改善，不能只换框架、目录或外观。

- **关系正确：** 终端通过产品合同接入；会话、执行、权限与持久化归核心。终端拥有可重建的显示与交互状态，不建立第二套业务权威。
- **范围完整：** 首次配置、主界面、配置编辑、各类信息输入、选择与确认等全部实际入口和往返流程均须清点；这里的举例不是封闭清单。既有视觉成果默认保留，旧故障与妥协不作为必须保留的需求。
- **改善可见：** 滚轮、右键粘贴、选择复制能共存；历史可以随尺寸变化重新排版，流式输出不中断；切页返回后输入与显示状态正确；启动、响应、长对话资源占用不发生无依据的退步。
- **架构有标杆：** 以 OpenCode 为架构质量标杆，目标整体更好：关键维度不落后，并有可验证的明确优势。比较状态与视口模型、输入与事件协调、多页面生命周期、性能与资源边界、可维护性及扩展影响面；不能仅因旧问题修好了就宣称架构达标，也不以功能数量、点击效果或框架名称判断高低。

**本次只交付已有功能迁移、债务清理与问题修复，以及使这些目标和架构质量成立的必要底座。** 新架构的未来能力不是本次功能清单：OpenCode 的点击等能力只作为调研材料，不自动要求照搬；已有鼠标交互仍须保留并修好。未来扩展只检查是否会穿透无关层、复制状态或迫使重做底座，不提前实现尚无需求的能力；范围约束不限制必要重构的深度。

核心边界依据[架构概述](../../research/design/architecture/overview.md)；现状从 [CLI 总体架构](../modules/cli/architecture.md)、[屏幕能力](../modules/cli/screen-rendering.md)、[首次引导](../modules/secrets/onboarding.md)及生产入口双向核实。文档与实现冲突必须查证，不把现有实现自动当成需求。

## 二、五个角色与决策权

按结果责任分工，不按动作数量拆角色：**总控管方向与取舍，产品管用户合同，架构管技术方案，工程管可交付实现，验收管独立证据。** 构建、测试和提交同属工程交付；总控对结果负责，不代表亲自代办各岗位的工作。

| 角色 | 唯一主责与交付物 | 权限与边界 |
|---|---|---|
| **总控（当前主智能体）** | **唯一负责方向、范围、优先级和最终放行**：围绕剩余用户结果安排关键依赖，裁决路线、成本与跨角色冲突，主动纠正体系失效；维护简短索引、决策及[探索记录](multi-role-collaboration-exploration.md) | 不代写设计、代码、详细测试或提交信息，不兼任验收者；新增阻塞须说明依据、影响范围和解除条件，接受其他角色对其必要性的质疑。改变需求、已接受体验或支持范围交用户决定 |
| **产品与体验负责人** | **唯一负责需求还原与产品设计文档**：执笔需求梳理、产品设计、页面／旅程清单、交互与体验验收条件；迁移后校准相关产品说明 | 对需求遗漏及归类负责；不以旧实现限制新设计，不自行删功能、改既定视觉或把竞品功能变成本次需求。由验收方查覆盖、总控确认范围 |
| **架构负责人** | **唯一负责技术方案及其文档**：交付调研取舍、OpenCode 对标、核心／终端边界及终端内部架构，提出验证实验、迁移单元依赖与旧路径退役方案；落地后同步正式架构文档 | 对可行性和准确性负责；不代替产品定义用户需求，不接管工程师的合同内实现选择。方案由验收方查证、总控批准采用；不自批方案或预建未来功能 |
| **实现工程师** | **唯一负责完整工程交付**：在已授权单元内持续完成实现、集成、修复、自测、构建与清理，直到真实入口、使用及退出后的结果可供验收；整理提交分组及证据 | 同一工作区唯一生产代码及 Git 写入角色；局部实验完成不终止执行权。新增阻塞或预计无法按节点产出有效结果时，同时通知总控与验收。不能自行放行、改合同或降低断言；Git 仍须独立验收、总控放行及用户授权 |
| **独立验收负责人** | **唯一负责独立证据与验收结论**：检查需求、架构、实现及范围，复验修复，核对提交；收到阻塞争议或进展预警时，独立检查其合同、风险与证据依据 | 不参与被审方案执笔或实现，不代修代码、不操作 Git。阻塞检查不扩成每步审批，也不接管排程；总控据结论裁决。作者自测不能替代验收；涉及质量门的体系调整也由其独立检查 |

**责任不能悬空：** 新增要求或问题由总控指定一个主负责人、交付物和验收人后再派发，不能只追加到公共原则。协助者不替代主负责人；跨角色问题由总控拆清交界，明确移交被接收前原负责人继续跟进。尚无归属的事项由总控接住，不允许角色间来回推脱。

**按影响介入，不层层会签：** 总控确认结果目标、权限与依赖，负责人提出具体工作卡和成本，总控只裁决冲突与优先级。产品负责需求和体验取舍，架构负责技术合同；既定合同内的实现由工程师自主决定、验收方检查。只有用户行为或架构合同发生变化、存在歧义时才召回对应设计角色，不要求每个单元五人全量重审。任何角色都可直接报告反证，但不能绕过既定负责人自行改变合同。

**连续执行与阻塞规则：**

- 授权单位是完整用户结果，内部实验、实现步骤和普通修复不逐项重新申请。任务卡可细化既定边界，不能无依据收回连续执行权；候选实验仍受目录、资源及动作范围约束，不自动扩大为生产迁移或正式采用。
- 正式采用、独立验收、用户授权和安全边界照常生效。额外暂停须在现有任务卡或索引写明“依据／受影响动作／解除条件／处理负责人”。发现真实风险先停直接受影响动作再补记，无关且已授权工作继续；审查尚未完成本身不构成所有工作停顿的理由。
- 工程被新增前置条件阻塞、预计不能在约定节点产出有效结果时，直接向总控和验收发送同一简短预警。连续两轮交接既未缩小交付缺口、也未排除关键错误假设时，任一角色可触发同样纠偏。通知只带当前缺口、依据及下一步建议，不另建报表或定时巡查。
- 验收只核对所涉阻塞的必要性，不代写解决方案、不审批普通步骤；总控接报后在安排下一轮同类工作前，明确继续的依据、换路线或撤销无效依赖。等待裁决不扩大暂停范围，超时不视为授权或通过，也不能以降标消除阻塞。

**文档也是交付物：** 启动设计时由总控指定唯一模块设计文档，沿用“需求梳理／产品设计／架构设计”三部分：前两部分由产品负责人执笔，第三部分及调研取舍由架构负责人执笔。共享文件按章节归属、错开写入，只保留影响决策的结论与证据。正式迁移依据须经审查接受；候选方案允许在总控批准的有限实验范围内验证，不把样机成功写成正式采用。方案改变由作者同步修订，验收方核对文档与实现一致，总控核对交付是否闭合。

总控做最终交付裁决，独立验收提供必要质量结论；两者不能互相替代。有争议先明确可证伪的问题，由未涉入争议的角色补证，必要时使用新会话冷审；不按人数投票，也不无限辩论。冷审按需替换验收会话，不增设常驻角色。

## 三、工作顺序与通过条件

| 阶段 | 主要产出 | 进入下一阶段的条件 |
|---|---|---|
| **1. 还原需求与现状** | 产品负责人建立“需求来源 → 页面／场景 → 入口 → 当前行为／问题 → 验收动作”清单；架构负责人核对核心边界及同类债务 | 验收方从生产入口反查遗漏；有效需求、已知故障、旧妥协与待决取舍分清。设计前清点全范围，各单元实施前再深入其细节 |
| **2. 设计并证明新底座** | 架构方提出候选及有限实验；总控确定实验范围，工程师做样机，验收方独立验证；随后确定正式架构 | 对标维度、版本、场景和判据先明确，不把整套智能体的启动负担当作终端架构差异。样机验证长历史、持续输出、缩放、鼠标／复制／粘贴、中文输入及切页返回。对标达标，且相较现状及合理局部修复收益成立，才接受正式方案并迁移 |
| **3. 按完整旅程迁移** | 架构方提出责任边界与依赖，工程师持续完成单元，总控安排关键依赖；验收方独立检查 | 覆盖入口、使用、退出／取消／失败及返回；构建可运行，直接消费者不回退。内部实验与集成连续推进；完整审查结束后，工程依清单在原授权内统一修复。跨单元的采用依赖须通过相应质量门，不能将内部步骤机械拆成反复放行的单元 |
| **4. 整体验收与退役** | 全旅程覆盖证据、核心边界与性能证据、旧实现及临时资产清理 | 无未解决的范围内缺陷或必要证据缺口；旧入口、重复机制、迁移兼容与临时开关清理完成。未参与设计实现的新验收会话对冻结版本完整终审；发现问题先完成本轮审查，再统一修复、重新冻结并完整终审，通过后总控报告可交付 |

迁移以用户旅程和责任边界拆分，不按文件数拆。过渡期必须登记旧路径的替换单元与退出条件，同一交互入口同时只有一个屏幕及输入控制者；不得长期双写或维护两套业务事实。新方案无法满足目标时明确停止扩大迁移，不用已投入工作量证明它值得继续。

## 四、在 Codex 中如何执行

1. **职责写进会话入口。** 按用户授权建立独立角色会话与通信关系。每个角色的首条任务包含本文路径、角色名、允许写入的文件、任务边界和通过条件；角色先核对并简述自己的责任，不能只靠会话标题或“顶级专家”称号约束。初始化与正式执行分开：只获准备授权时，确认就绪后结束回合，不能自行启动任务。五种职责不要求五个角色同时运行，按依赖唤醒。
2. **一张任务卡驱动完整单元。** 总控给出用户结果与依据、边界、责任及连续执行权限；负责人在现有计划中明确下一个可检验结果、预计节点和停止条件。局部实验用于消除不确定性，不自动产生审批门。新增事项须绑定已有需求、债务、故障或必要底座责任；越界或影响其他单元才提交裁决。预计失约即按 §二预警，不能到收尾才报告，也不能凭局部完成比例推进整体状态。
3. **一处记录当前事实。** 总控维护唯一任务索引：生效规则、角色映射、当前完整单元、真实阻塞、裁决与证据链接。需求、设计、工程及验收各自维护本职产物，总控不搬运细节。每次接单、恢复或换会话先读索引及本职产物；新版本明确替代哪些旧指令，历史任务卡和回执仅作证据，不因仍在磁盘上而恢复旧授权或旧阻塞。
4. **被审版本停止写入。** 同一工作区同时只有一个生产代码写者；其他角色对代码只读，各自产物分开写。验收前固定源码、制品与环境，验收期间不得修改被审输入；不依赖该结论且写入隔离的已授权工作可继续。新改动进入后续版本，既有证据按适用范围复用，不沿用失效结论。构建与重测试统一排期；样机和数据隔离，不改用户真实配置与历史。
5. **独立性靠输入和行为保证。** 验收方先读需求、被审版本和已知故障证据，独立列出检查路径，再看作者报告并核查。按“验收项、实际结果、证据、影响”报告缺陷，不把偏好或未来增强冒充阻塞项；不因读过方案就参与代写。工程问题由工程师修复，需求或架构问题回对应作者；验收方复验，总控只处理争议和放行。
6. **有缺口才继续。** 修复使哪些证据失效就重取哪些，最终终审覆盖整模块；未变输入的有效证据可复用。没有新证据时停止重复讨论或重跑，改进取证方法；不能为了赶进度降标。遇到前提被反证或超出任务边界，保存可接续现场交总控裁决。
7. **总控直接纠正失效的协作方式。** 停止失效路径、保留现场，无关工作继续；在授权内决定职责、流程或排程调整并推动执行，不等待用户逐步指挥。总控更新本方案与[探索记录](multi-role-collaboration-exploration.md)，各负责人更新受影响任务卡；明确生效版本，相关角色按新职责接续，旧指令退场。下次交接核验效果，无效再调整。不取消独立验收、降标或扩面；改变写权隔离或验收机制须经独立检查，常规调度不增加审批。总控接住问题是确保有人解决，不是把专业工作全部接到自己身上。

角色交接只需：**版本／范围、已证用户结果、证据、剩余缺口、下一可检验结果**。总控仅在实质进展时报告整体进度；文件、实验或局部通过数量不能代替整体结果，不让角色各自向用户索要重复确认。

### 角色间沟通规则

借鉴[既有协作经验](cross-session-collaboration.md)的明确回信、异步通知和持久交接，不搬入其整套流程：

1. **先保存，再通知。** 任务、决定和结果写入现有任务卡或角色产物；消息只带定位信息与必要摘要，不反复粘贴长报告。简单澄清不另造文档，改变交付依据时再回填。每次恢复只读取自己未结事项及必要材料，不扫描全部角色历史。
2. **发后按依赖处理，不空等。** 派发需要后续接续的任务时，必须同时明确实际唤醒路径。当前采用已授权的跨会话消息主动投递；本会话最终回复、文件落盘和接收方主动调用 `wait_threads` 是三种不同动作，前两者不会代替跨会话通知。主动回信已约定时可结束回合；只有采用完成事件回收的临时交接才保持平台等待，不结束后假定等待仍在。禁止 sleep、高频轮询或另造定时监控。
3. **终态主动交接。** 完成、无法承担或需要他方裁决时，先保存结果，再通过当前会话消息工具通知任务指定接收者，最后结束本会话；预警与完成都适用。消息只带任务／轮次、结果、制品版本／位置和未决项，普通进度不重复发送。发送失败或结果未知记“通知未确认”，不能声称已交接；重发沿用相同任务轮次和制品标识。接收者按该标识去重，将接收及下一步记入已有索引并推进已授权工作，不因重复消息重复派工，也不额外制造确认循环。最终回复供人阅读，不能替代这一步。
4. **身份、轮次与迟到回复清楚。** 使用登记的会话 ID 和任务 ID／轮次；同一请求重复投递不重复执行，已完成则引用原结果。变更任务须更新轮次，旧轮次回复不能推进新任务。到约定回报时点仍无结果，在事件或自然恢复时核实后提醒或改派，不把沉默当同意；移交写权前确认旧写者已停止。
5. **沟通不改变权责。** 角色可在用户授权的通信范围内直接澄清事实和接口；改变范围、已接受合同、跨单元依赖或写权才交总控裁决。§二的阻塞预警同时送达总控和验收，各角色完成交付主动通知总控；后续执行与验收仍按已授权任务安排，消息本身不授予写权或放行。用户要求、事实与推断分开，独立审查前不夹带推荐；“请回复”本身不构成通信授权。

需回复消息采用以下最小格式；回复沿用同一任务 ID／轮次。实际发送接口以当前 Codex 工具为准，不沿用旧环境的工具名或唤醒参数。

```text
任务：<ID／轮次>｜类型：<执行／咨询／独立审查／结果／知会>
发件：<角色、会话 ID> → 收件：<角色、会话 ID>
事项：<要完成或回答什么；是否阻塞后续工作>
依据：<任务卡／产物绝对路径及版本；必要事实>
回复约定：<需回复／免回复>；<有时限才写回报时点>
请用当前会话消息工具回复 <角色、会话 ID>，使其接续处理；
内容：结论／结果 + 证据位置 + 未决项；无法承担则回复原因。
```

知会和无需进一步裁决的结果回信写“免回复”，省略最后两行；详细边界与验收条件留在任务卡，不在通知中重复。

### 提交与 Git 责任

**工程师准备并执行，总控把控范围、授权与放行，验收方独立判断可提交性。** 不新增提交角色；任何阶段只有一个指定 Git 写者，禁止各角色各自提交。

**提交单元与迁移单元分开。** 提交围绕一个明确的修复、重构或功能增量，形成适当大小、可独立理解／构建／测试／回滚的终态子集；可以尚缺后续能力，不能留下半升级语义或依赖后续提交补救。U1等迁移单元及整个模块的完整验收保持，不能把它们全部完成当成准备或提交每个小批次的前提。每批检查结论只覆盖本批，后续集成与整体验收复用有效证据并检查新增交界，不以已提交代替完整交付。

**工程主动成批，总控负责触发与跟进。** 一个上述改动闭合、正式文档定稿时，工程即整理候选，不等大单元结束；总控在自然交接安排独立检查，并在现有索引登记范围、负责人、所欠条件及下一节点。批次应有单一清楚目的，文件多或混合多个目的时必须检查能否按功能及不变量继续拆，不能以“属于同一U1”整体打包，也不以凑文件数切断生产者／消费者。实验、普通进展和作者自测不等于可直接提交。只冻结被审批次及其必要依赖，无关实现可继续；提交检查不收回工程的连续执行权。

1. **工程师准备提交批次。** 每个已闭合的适当大小改动，按项目[提交规范](../../.agents/skills/git-commit-generator/SKILL.md)交代目的、不变量、父基线、文件／补丁范围、验证及信息草稿；尚未闭合的依赖指出具体所欠，不能笼统等待整个U1。生产者、消费者、合同、必要测试及同步生效文档不能切成半升级。不按角色、文件类型或单元数量机械拆散；保留有价值的设计与探索文档，排除无关变更及临时运行态。
2. **验收方检查交付与拆分。** 对明确版本及分组给出结论，不能只证明最后一个提交叠加后的工作树可用。拆分导致代码或合同变化时，交工程师处理并补验；不得靠后续提交修补前一提交的中间债务。
3. **总控放行，工程师执行。** 总控确认批次符合范围、独立验收通过且已有用户明确授权，再交工程师执行；未获授权先备齐可审查批次，最后再请用户授权。准备与验收不以取得 Git 写授权为前提。待授权只暂停本批 Git 写入，不扩大为无关工作的停顿；继续修改涉及待提交范围时，须更新该批版本并由验收判断证据是否仍适用。工程师操作前冻结本批写入，核对 staged／unstaged／untracked，只暂存约定内容，不覆盖用户的暂存安排；逐组读取完整 staged diff，与已验版本及分组不符则退回核对，不边提交边补代码。
4. **工程师核对并回报。** 信息采用 `type(scope): subject`，英文祈使句、小写开头、不加句号，正文中文，多单元分段，只描述实际提交内容。提交后回报 ID、范围、对应验收版本及剩余变更；总控核验提交结果与已批准批次一致，不重新代做整套实现审查。提交不等于发布，推送另需明确授权。

## 五、验收纪律与结束标准

- **先验证能测，再投入迁移。** 验收方提前确认真实终端的观测与操作手段。Windows Terminal／ConPTY 为当前故障必验环境，其他环境按现有支持承诺确定；PTY 字节注入不能冒充真实鼠标、选择复制或输入法验证。无法取得的必要证据明确标为未验，不默认为通过。
- **构建后测真实入口。** CLI 改动先 `pnpm cli:build`，上游改动先 `pnpm build`；用新产物运行 `zz`，覆盖首次配置、日常使用和页面往返。页面截图、单元测试和 HTML 演示均不能单独证明终端可交付。
- **比较用户结果。** 保留既有功能与视觉约定，逐项消除登记的故障和债务；核对历史重排、流式连续性、输入交接、退出恢复，以及冷／热启动、长对话响应和资源占用。性能阈值在实验前依据现状与用户目标明确，不能看完结果再降低标准。
- **证明核心独立。** 终端经产品合同及明确的本机配置端口接入，不复制业务规则；显示重建不改业务事实，终端替换不改变飞书及后台任务语义。首配无模型可用、宿主断线与重连等路径仍正确，不把后台服务装配误当终端组件删除。
- **架构承诺有实物依据。** 终验核对实现是否兑现已接受的对标结论，不能拿设计稿或“以后可以支持”代替；未来功能没有实现不构成缺陷，必要的架构边界没有落地则构成缺陷。
- **通过即结束。** 所有范围内需求有实现与必要证据，问题闭合，旧路径和无价值临时资产退役，正式文档与实现一致，冻结版本独立终审通过。不得以无限扩充角色、测试框架或候选方案延长任务；本方案文档本身不代表迁移已获验收。
