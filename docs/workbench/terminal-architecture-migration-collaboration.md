# 终端架构迁移 · 多角色工作方案

本文只定义本次迁移的角色、工作方式与交付门槛，不预定技术选型。独立于既有跨会话协作体系设计，不继承其角色、决策流程或登记机制；只吸收并调整有效沟通经验，项目常驻规则仍适用。角色会话、当前任务和执行闸门登记在本机 `collab/terminal-migration/index.md`，不把动态状态写入本方案。

**方案版本：v3.1（2026-10-05）。** 保留交付与实现分工，允许经证实相互独立的工程闭包有限并行，避免把防冲突的单写纪律扩大为全项目串行。生效版本、角色接收和写权交接以当前索引为准；本文更新不自动恢复暂停、增加写者或转移 Git 写权。

## 一、共同目标

在智能体核心独立于界面的前提下，重建可靠的终端底座，完整承接已有功能、页面与有效体验，消除旧架构债务和已知交互故障。必须证明用户获得实质改善，不能只换框架、目录或外观。

- **关系正确：** 终端通过产品合同接入；会话、执行、权限与持久化归核心。终端拥有可重建的显示与交互状态，不建立第二套业务权威。
- **范围完整：** 首次配置、主界面、配置编辑、各类信息输入、选择与确认等全部实际入口和往返流程均须清点；这里的举例不是封闭清单。既有视觉成果默认保留，旧故障与妥协不作为必须保留的需求。
- **改善可见：** 滚轮、右键粘贴、选择复制能共存；历史可以随尺寸变化重新排版，流式输出不中断；切页返回后输入与显示状态正确；启动、响应、长对话资源占用不发生无依据的退步。
- **架构有标杆：** 以 OpenCode 为架构质量标杆，目标整体更好：关键维度不落后，并有可验证的明确优势。比较状态与视口模型、输入与事件协调、多页面生命周期、性能与资源边界、可维护性及扩展影响面；不能仅因旧问题修好了就宣称架构达标，也不以功能数量、点击效果或框架名称判断高低。

**本次只交付已有功能迁移、债务清理与问题修复，以及使这些目标和架构质量成立的必要底座。** 新架构的未来能力不是本次功能清单：OpenCode 的点击等能力只作为调研材料，不自动要求照搬；已有鼠标交互仍须保留并修好。未来扩展只检查是否会穿透无关层、复制状态或迫使重做底座，不提前实现尚无需求的能力；范围约束不限制必要重构的深度。

核心边界依据[架构概述](../../research/design/architecture/overview.md)；现状从 [CLI 总体架构](../modules/cli/architecture.md)、[屏幕能力](../modules/cli/screen-rendering.md)、[首次引导](../modules/secrets/onboarding.md)及生产入口双向核实。文档与实现冲突必须查证，不把现有实现自动当成需求。

## 二、六个角色与决策权

按结果责任分工：**总控管整体收敛，产品管用户合同，架构管技术合同，工程管正确实现，交付管版本闭合，验收管独立结论。** 新增交付负责人从开发前介入，消除实现者反复切换到集成与提交整理的负担；不增加一道审批，不接管产品和架构决策。

| 角色 | 唯一主责与交付物 | 权限与边界 |
|---|---|---|
| **总控（当前主智能体）** | **唯一负责方向、范围、优先级和最终放行**：围绕剩余用户结果管理关键依赖、在制范围与成本，批准交付批次及执行条件，裁决跨角色冲突，纠正体系失效；维护简短索引和[探索记录](multi-role-collaboration-exploration.md) | 不代写设计、代码、详细测试或提交信息，不逐项搬运证据；常规批次按已批准条件接续，异常才回总控。改变需求、已接受体验或支持范围交用户决定 |
| **产品与体验负责人** | **唯一负责需求还原与产品设计文档**：执笔需求梳理、产品设计、页面／旅程清单、交互与体验验收条件；迁移后校准相关产品说明 | 对需求遗漏及归类负责；不以旧实现限制新设计，不自行删功能、改既定视觉或把竞品功能变成本次需求。由验收方查覆盖、总控确认范围 |
| **架构负责人** | **唯一负责技术方案及其文档**：交付调研取舍、对标、核心／终端边界及内部架构、必要实验和退役方案；明确跨层合同与迁移依赖，判定存在争议的批次是否可独立闭合；落地后同步正式架构文档 | 对可行性和准确性负责；不代替产品定义需求，不接管合同内实现选择。方案由验收方查证、总控批准采用；不自批方案或预建未来功能，也不逐批重新会签 |
| **实现工程师** | **负责所分配闭包的正确实现**：在已批准批次内连续完成生产代码、必要回归测试、局部集成、自测和清理，交出可构建的完整改动及已知缺口；修复集成或验收发现的问题 | 默认一位实现者；仅在下述并行条件成立时增加一位有限工程实例，每个文件始终一个写者，跨层接合指定一个工程负责人。均无 Git 权；不把代码返修甩给交付，不自批、改合同或降低断言 |
| **集成交付负责人** | **唯一负责版本闭合**：开发前提出批次目的、依赖及退出条件；开发中维护交付清单，准备冻结候选、准确构建与可复用证据；独立通过后按授权规范拆分、写信息并提交，回报实际版本及余量 | 完成交接后为唯一 Git 写者；只写交付产物，不改生产代码、产品或架构合同，不自批验收。集成失败先区分候选／环境问题与产品缺陷：前者由其处理，后者交工程，不另设验收前审批门 |
| **独立验收负责人** | **唯一负责独立证据与验收结论**：检查需求、架构、实现及范围，复验修复，核对提交；收到阻塞争议或进展预警时，独立检查其合同、风险与证据依据 | 不参与被审方案执笔或实现，不代修代码、不操作 Git。阻塞检查不扩成每步审批，也不接管排程；总控据结论裁决。作者自测不能替代验收；涉及质量门的体系调整也由其独立检查 |

**责任不能悬空：** 新增且没有归属、跨越既有职责的事项，由总控指定一个主负责人、交付物和验收人；已批准批次内的普通缺陷由原负责人连续处理，不逐项等待重新派发。协助者不替代主负责人；明确移交被接收前原负责人继续跟进。尚无归属的事项由总控接住，不能只追加到公共原则或让角色来回推脱。

**按影响介入，不层层会签：** 总控批准结果目标、批次边界和权限；交付与工程在现有合同内直接协调实施、取证和提交，独立验收给质量结论。只有用户行为或架构合同变化、存在歧义时才召回相应设计角色，不要求六人全量会签。任何角色都可报告反证，不能自行改变合同。

**连续执行与阻塞规则：**

- 授权覆盖完整迁移目标，当前实施受已批准交付批次约束；批次内部的实验、实现和普通修复不逐项重新申请。范围内发现的必要缺陷由工程连续修复；扩大批次或改变依赖交总控裁决，不能把“完整 U1 授权”解释为任意同时摊开多个未闭合用途。候选实验仍不自动扩大为生产迁移或正式采用。
- 正式采用、独立验收、用户授权和安全边界照常生效。额外暂停须在现有任务卡或索引写明“依据／受影响动作／解除条件／处理负责人”。发现真实风险先停直接受影响动作再补记，无关且已授权工作继续；审查尚未完成本身不构成所有工作停顿的理由。
- 工程或交付预计不能在约定节点产出有效结果、被新增前置条件阻塞时，通知总控及直接接续者；涉及质量门争议同时通知验收。连续两轮交接既未缩小交付缺口、也未排除关键错误假设时，立即重判路线或依赖，不能继续同类试验。通知只带缺口、依据与建议，不另建报表或定时巡查。
- 验收只核对所涉阻塞的必要性，不代写解决方案、不审批普通步骤；总控接报后在安排下一轮同类工作前，明确继续的依据、换路线或撤销无效依赖。等待裁决不扩大暂停范围，超时不视为授权或通过，也不能以降标消除阻塞。

**文档也是交付物：** 启动设计时由总控指定唯一模块设计文档，沿用“需求梳理／产品设计／架构设计”三部分：前两部分由产品负责人执笔，第三部分及调研取舍由架构负责人执笔。共享文件按章节归属、错开写入，只保留影响决策的结论与证据。正式迁移依据须经审查接受；候选方案允许在总控批准的有限实验范围内验证，不把样机成功写成正式采用。方案改变由作者同步修订，验收方核对文档与实现一致，总控核对交付是否闭合。

总控做最终交付裁决，独立验收提供必要质量结论；两者不能互相替代。有争议先明确可证伪的问题，由未涉入争议的角色补证，必要时使用新会话冷审；不按人数投票，也不无限辩论。冷审按需替换验收会话，不增设常驻角色。

## 三、工作顺序与通过条件

| 阶段 | 主要产出 | 进入下一阶段的条件 |
|---|---|---|
| **1. 还原需求与现状** | 产品负责人建立“需求来源 → 页面／场景 → 入口 → 当前行为／问题 → 验收动作”清单；架构负责人核对核心边界及同类债务 | 验收方从生产入口反查遗漏；有效需求、已知故障、旧妥协与待决取舍分清。设计前清点全范围，各单元实施前再深入其细节 |
| **2. 设计并证明新底座** | 架构方提出候选及有限实验；总控确定实验范围，工程师做样机，验收方独立验证；随后确定正式架构 | 对标维度、版本、场景和判据先明确，不把整套智能体的启动负担当作终端架构差异。样机验证长历史、持续输出、缩放、鼠标／复制／粘贴、中文输入及切页返回。对标达标，且相较现状及合理局部修复收益成立，才接受正式方案并迁移 |
| **3. 按完整旅程迁移** | 架构明确边界与依赖，交付据此安排可闭合批次，工程持续实现，验收独立检查；总控管理在制范围和关键依赖 | 覆盖入口、使用、退出／取消／失败及返回。小批次形成可独立回滚的增量，迁移单元验收仍覆盖完整旅程；整轮审查结束后统一修复。批次通过即按既定条件提交，不等整个单元，也不把实验变成反复放行的关卡 |
| **4. 整体验收与退役** | 全旅程覆盖证据、核心边界与性能证据、旧实现及临时资产清理 | 无未解决的范围内缺陷或必要证据缺口；旧入口、重复机制、迁移兼容与临时开关清理完成。未参与设计实现的新验收会话对冻结版本完整终审；发现问题先完成本轮审查，再统一修复、重新冻结并完整终审，通过后总控报告可交付 |

迁移以用户旅程和责任边界拆分，不按文件数拆。过渡期必须登记旧路径的替换单元与退出条件，同一交互入口同时只有一个屏幕及输入控制者；不得长期双写或维护两套业务事实。新方案无法满足目标时明确停止扩大迁移，不用已投入工作量证明它值得继续。

### 批次如何落地

**先划可交付边界，再扩大实现。** 交付负责人提出短清单，工程确认可实施性；已有合同足够则不再请架构会签。每批只留六项：**目的及需求依据、包含／不包含、父基线与必要依赖、负责人、通过条件与预计交验节点、当前缺口／证据**。总控批准优先级和边界；不可独立构建、验证或回滚就调整依赖，不能靠文案把半成品称作完整批次。

- **粒度看完整用途。** 同一用途的生产者、消费者、合同和必要测试一起交付；不按文件数硬切，也不每改几处就提交。一个批次通常对应一笔提交；确有多个独立终态才拆成有序少量提交，每个中间态都成立。缺少未来能力可以，依赖未来补救当前错误不可以。
- **控制同时摊开的范围。** 默认一个修改中批次、一个冻结交验批次。只有已核实文件不重叠、接口与依赖稳定、可独立验证、且能缩短实际关键路径的完整工程闭包，才可由总控指定第二位实现者并行；不按目录或空闲人数拆活。最多两个修改中闭包和一个冻结交验批次；每个闭包的返修优先，不再摊第三个。共享文件和最终接合只归一位工程负责人；跨所有权修改直接协调移交，未确认停止前不得写入。重资源及 Git 仍串行，独立验收不变。
- **先碰最危险的真实交界。** 工程在批次早期接通必要的身份、权限、持久化、进程归属与退出链，尽早证伪关键假设，再补页面细节；验证只覆盖本批可达路径，不为每批重复整套平台试验。
- **证据随同一个版本流转。** 工程交候选及自测；交付核候选完整性、组织准确构建并直接送验收；验收先完成本轮检查，再统一交工程修复。未失效的证据复用；产品缺陷、夹具错误、过期制品、环境限制分别处理，不能混成无限产品排障。
- **过关立即接续。** 符合既定提交条件就执行并交下批，不等总控再转发一次“可以继续”。实际发生范围／父基线冲突、质量争议或授权变化才回总控；整模块最终放行仍归总控。

**整体进度须有固定分母。** 产品清单和 U0–U4 是依据；首次发布新版整体百分比前，交付将已完成及剩余成果映射为有限交付项及权重，总控确认估算依据。恢复只需当前批次的边界、依赖、负责人及通过条件明确，不以全量权重整理阻塞实施或已批准提交。分别显示“实现交验／独立通过／已提交”，整体完成率只计独立通过的交付范围，同一义务不因拆批重复加分。范围变化公开重算；此前无分母的局部百分比不沿用为整体进度。只利用交付清单，不另建统计系统。

## 四、在 Codex 中如何执行

1. **职责写进会话入口。** 按用户授权建立独立角色会话与通信关系。每个角色入口包含本文路径、角色名、允许写入的文件、任务边界和通过条件；角色核对自己的责任及接续对象。初始化与正式执行分开：只获准备授权时确认就绪即结束，不能自行启动工程。六种职责按需运行，产品和架构无待决事项时保持空闲。
2. **完整目标下按批连续执行。** 总控保留整单元目标，交付清单承载当前批次及下一个候选，不为每个内部步骤另造任务卡。工程在已批准边界内自主实施；新增事项须绑定需求、债务、故障或必要底座，影响其他批次才提交裁决。预计失约即按 §二预警，不到收尾才报告。
3. **一处记录当前事实。** 总控维护简短当前索引：生效规则、角色映射、当前批次、真实阻塞、下一动作和证据链接；交付清单由交付负责人维护，其他角色只维护本职产物。已闭合历史保留作证据，与当前行动区隔开，不复制每份报告或逐次哈希到索引。接单、恢复先读当前索引及本职未结事项；历史消息不恢复旧授权或旧阻塞。
4. **生产写入、冻结与 Git 分离。** 每个生产文件只归索引登记的一位工程实现者；共享接合文件也须明确唯一负责人，交付是唯一 Git 写者。捕获候选、修改共享 Git 状态时，只暂停涉及范围，形成不可变快照后才能继续该范围的下一版；其后编辑不能被提交操作覆盖或误收入。验收只读冻结输入，不对仍在修改的工作区下通过结论。Git 操作串行、不得顺手 checkout/reset 工程工作区；已冻结候选的实际父链须成立，后续实现不能补救它的缺陷。写权移交先确认旧写者停止，冲突仅暂停相关动作。
5. **重资源串行，轻工作并行。** 交付负责构建／重测试排程，使用前确认上一持有者已释放；工程局部验证与验收独立执行遵循同一排程，结束主动交还。复用与候选及环境匹配的现有产物，不能让不同构建覆写被审 dist。隔离候选优先使用现有机制；不得为协作新造构建平台、整套快照系统或大规模制品副本。等待重资源时可做已授权静态工作，不改用户真实配置与历史。
6. **独立性靠输入和行为保证。** 验收方先读需求、被审版本和已知故障证据，独立列出检查路径，再看作者报告并核查。按“验收项、实际结果、证据、影响”报告缺陷，不把偏好或未来增强冒充阻塞项；不因读过方案就参与代写。工程问题由工程师修复，需求或架构问题回对应作者；验收方复验，总控处理争议及最终放行。
7. **有缺口才继续。** 修复使哪些证据失效就重取哪些，最终终审覆盖整模块；未变输入的有效证据可复用。没有新证据时停止重复讨论或重跑，改进取证方法；不能为了赶进度降标。遇到前提被反证或超出任务边界，保存可接续现场交总控裁决。
8. **总控直接纠正失效的协作方式。** 停止失效路径、保留现场，无关工作继续；在授权内决定职责、流程或排程调整并推动执行。总控更新本方案与[探索记录](multi-role-collaboration-exploration.md)，负责人更新受影响任务卡；明确生效版本和旧指令退场。下次实际交付核验是否减少等待、返工和在制积压，无效再调整。改变写权隔离或验收机制须经独立检查，常规调度不增加审批；不取消独立验收、降标或扩面。

角色交接只需：**版本／范围、已证用户结果、证据、剩余缺口、下一可检验结果**。总控仅在实质进展时报告整体进度；文件、实验或局部通过数量不能代替整体结果，不让角色各自向用户索要重复确认。

### 角色间沟通规则

借鉴[既有协作经验](cross-session-collaboration.md)的明确回信、异步通知和持久交接，不搬入其整套流程：

1. **先保存，再通知。** 任务、决定和结果写入现有任务卡或角色产物；消息只带定位信息与必要摘要，不反复粘贴长报告。简单澄清不另造文档，改变交付依据时再回填。每次恢复只读取自己未结事项及必要材料，不扫描全部角色历史。
2. **发后按依赖处理，不空等。** 派发需要后续接续的任务时，必须同时明确实际唤醒路径。当前采用已授权的跨会话消息主动投递；本会话最终回复、文件落盘和接收方主动调用 `wait_threads` 是三种不同动作，前两者不会代替跨会话通知。主动回信已约定时可结束回合；只有采用完成事件回收的临时交接才保持平台等待，不结束后假定等待仍在。禁止 sleep、高频轮询或另造定时监控。
3. **终态主动交接。** 完成、无法承担或需要他方裁决时，先保存结果，再通过当前会话消息工具通知任务指定接收者，最后结束本会话；预警与完成都适用。消息只带任务／轮次、结果、制品版本／位置和未决项，普通进度不重复发送。发送失败或结果未知记“通知未确认”，不能声称已交接；重发沿用相同任务轮次和制品标识。接收者按该标识去重，将接收及下一步记入已有索引并推进已授权工作，不因重复消息重复派工，也不额外制造确认循环。最终回复供人阅读，不能替代这一步。
4. **身份、轮次与迟到回复清楚。** 使用登记的会话 ID 和任务 ID／轮次；同一请求重复投递不重复执行，已完成则引用原结果。变更任务须更新轮次，旧轮次回复不能推进新任务。到约定回报时点仍无结果，在事件或自然恢复时核实后提醒或改派，不把沉默当同意；移交写权前确认旧写者已停止。
5. **直接接续，不经总控逐次中转。** 已获用户授权的角色间可直接澄清事实和接口。工程交候选给交付，交付送验收，验收将整轮结论给交付及需返修的原作者；就绪、通过和阻塞同步知会总控，不等待其重复转发。预警通知总控和直接接续者，涉及质量门争议再送验收；范围、已接受合同、跨批依赖或写权变化才请总控裁决。后续动作仍受原授权和暂停约束，消息本身不授予写权。用户要求、事实与推断分开，独立审查输入不夹带推荐；“请回复”不构成通信授权。

需回复消息采用以下最小格式；回复沿用同一任务 ID／轮次。实际发送接口以当前 Codex 工具为准，不沿用旧环境的工具名或唤醒参数。

```text
任务：<ID／轮次>｜类型：<执行／咨询／独立审查／结果／知会>
发件：<角色、会话 ID> → 收件：<角色、会话 ID>
事项：<要完成或回答什么；是否阻塞后续工作>
依据：<任务卡／产物绝对路径及版本；必要事实>
回复约定：<需回复／免回复>；<有时限才写回报时点>
请用当前会话消息工具回复 <角色、会话 ID>，使其接续处理；
内容：结论／结果 + 证据位置 + 未决项；无法承担则回复原因。
```

知会和无需进一步裁决的结果回信写“免回复”，省略最后两行；详细边界与验收条件留在任务卡，不在通知中重复。

### 提交与 Git 责任

**交付负责准备和执行，验收负责独立结论，总控预先确定条件并处理例外。** 人类授权不能由角色消息替代。当前唯一 Git 写者以索引中的已完成交接为准；不能因新方案发布就出现两个写者。

**提交单元与迁移单元分开。** 提交围绕一个明确的修复、重构或功能增量，形成适当大小、可独立理解／构建／测试／回滚的终态子集；可以尚缺后续能力，不能留下半升级语义或依赖后续提交补救。U1等迁移单元及整个模块的完整验收保持，不能把它们全部完成当成准备或提交每个小批次的前提。每批检查结论只覆盖本批，后续集成与整体验收复用有效证据并检查新增交界，不以已提交代替完整交付。

**提交条件随批次预先确定。** 总控在批准批次时登记所覆盖的用户本地 Git 授权、范围、顺序和独立验收门槛；交付据此准备，验收直接回报交付与总控。精确候选、实际父基线及完整提交信息通过，且没有暂停／变更指令时，交付立即按批准条件执行，无须再等待总控转发。范围扩大、依赖或父基线改变、结论冲突、授权不明才回总控；不能把这条规则当成全仓任意提交许可。

1. **交付准备。** 按[提交规范](../../.agents/skills/git-commit-generator/SKILL.md)固定目的、不变量、实际父基线、精确补丁、必要验证及完整信息；工程交代尚未闭合的依赖。必要生产者、消费者、合同、测试及同步文档不能切成半升级；有价值的设计／探索文档纳入适当批次，临时运行态不入库。
2. **验收独立检查。** 核对实际父链上每笔中间态，而非只验最后的完整工作树。已有精确版本结论直接复用；新父基线或改动使哪些证据失效就补哪些，不自动重审全仓。拆分需要修改代码或合同，回原作者修订后重新冻结，不由交付边拆边改。
3. **交付执行。** 条件齐备后，短暂冻结相关写入，核对 HEAD、staged／unstaged／untracked 与已审候选；只操作批准内容并保全其余暂存和工作区，不以整份 staged 代表授权，不全仓 add/reset/stash。发现不明变化先停止冲突动作；不得覆盖他人暂存安排。未获用户授权先完成准备与验收，最后申请；等待仅阻断对应 Git 动作。推送始终另需授权。
4. **交付核验并回报。** `type(scope): subject` 使用英文祈使句、小写开头、不加句号，正文中文；提交后核对实际 parent/tree/diff/message 与候选一致、未纳入内容得到保全，回报提交 ID、验收引用和剩余批次。总控核对结论及异常，不重复制作整套哈希和逐文件报告；验收保留独立抽查与质疑权。提交不是整个模块通过，也不是发布。

### 角色调整的交接

新角色先读取目标、现行合同、已交付与未结清单，确认写入边界与接续对象；其实际会话映射及接收结果进入索引。在工程停止 Git 操作、交付已就绪且总控登记切换之前，旧写者仍是唯一 Git 写者。暂停期间可准备方案，不能自动执行移交或提交；恢复后已有精确通过且放行的批次可由原写者先闭合，不等待新角色初始化，更不重复有效验收。移交完成后旧写者的 Git 权限明确终止。

新方案替代旧方案中“工程独自承担交付与 Git”“逐笔等待总控转发”和未限制在制范围的安排；既有需求、技术合同、独立验收、用户暂停与授权边界保持。效果用后续实际批次验证：成熟成果是否及时提交、未闭合范围是否收敛、工程是否减少交付整理造成的切换；无改善就调整，不将增加角色本身当作成功。

## 五、验收纪律与结束标准

- **先验证能测，再投入迁移。** 验收方提前确认真实终端的观测与操作手段。Windows Terminal／ConPTY 为当前故障必验环境，其他环境按现有支持承诺确定；PTY 字节注入不能冒充真实鼠标、选择复制或输入法验证。无法取得的必要证据明确标为未验，不默认为通过。
- **构建后测真实入口。** CLI 改动先 `pnpm cli:build`，上游改动先 `pnpm build`；用新产物运行 `zz`，覆盖首次配置、日常使用和页面往返。页面截图、单元测试和 HTML 演示均不能单独证明终端可交付。
- **比较用户结果。** 保留既有功能与视觉约定，逐项消除登记的故障和债务；核对历史重排、流式连续性、输入交接、退出恢复，以及冷／热启动、长对话响应和资源占用。性能阈值在实验前依据现状与用户目标明确，不能看完结果再降低标准。
- **证明核心独立。** 终端经产品合同及明确的本机配置端口接入，不复制业务规则；显示重建不改业务事实，终端替换不改变飞书及后台任务语义。首配无模型可用、宿主断线与重连等路径仍正确，不把后台服务装配误当终端组件删除。
- **架构承诺有实物依据。** 终验核对实现是否兑现已接受的对标结论，不能拿设计稿或“以后可以支持”代替；未来功能没有实现不构成缺陷，必要的架构边界没有落地则构成缺陷。
- **通过即结束。** 所有范围内需求有实现与必要证据，问题闭合，旧路径和无价值临时资产退役，正式文档与实现一致，冻结版本独立终审通过。不得以无限扩充角色、测试框架或候选方案延长任务；本方案文档本身不代表迁移已获验收。
