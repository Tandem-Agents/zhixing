# 问题处理工作台

本工作台用于贯穿系统生命周期的持续优化。总控与负责人沿真实用户的使用流程，持续发现、修复并验证现有功能与体验中的真实缺陷，让系统更可靠、更顺畅地完成用户任务。

问题按批次处理，每轮维护在授权的时间和资源范围内持续推进，完成一批后继续下一批。用户要求结束或达到本轮时间、资源边界时，按 D 收尾并留下接续依据。

工作方式与当前进度分开维护：

- **静态区：** 已定稿的工作方式，分四块：A 问题处理流程、B 问题发现流程、C 批次留存约定、D 维护轮次退出。A 已由用户封版。B、C 与 D 同样只在用户明确授意时修改。更新其他任何区域，都不得顺带改动静态区。
- **动态区：** 只登记当前批次，以及历史批次的入口。

## 静态区

**每轮入口**

每轮开工前，总控须让 Antigravity + Gemini 4 Carbon (High) 负责人先深入理解[高效工作方法](../engineering/antigravity-gemini-4-carbon-high-efficiency.md)，并要求其在后续工作中遵照执行。（动态）

每轮以目标主线的最新版本建立临时工作分支，检查工作台的待处理清单。

**有待处理问题：按最新版本复核 → 更新清单 → 进入 A 逐项处理。**

- 逐项核对问题是否仍存在，现象和影响是否变化；复用仍有效的证据，只补必要核验。
- 据此更新清单及核对版本：仍成立的保留，已不成立的注明依据后退出；待核或受阻项如实保留，不能仅凭一次未复现关闭偶发问题。
- 复核仅限旧清单，不扩展发现或补扫其他范围；完整根因定位与方案设计留在 A。旧批尚未冻结，也走这条路径。

**没有待处理问题：进入 B 完整发现一批，冻结后再进入 A。**

复核后待处理清单为空，同样走这条路径。

本批问题全部处理并验收后，按 C 归档；本轮未进入退出阶段时，直接进入 B 发现下一批。

### A 问题处理流程（已封版）

本块由用户定稿封版，原文逐字保留。未经用户明确授意，不修改其中的字词、标点、顺序或编号。

**通用要求**

- 按真实用户的操作顺序，在构建后的终端中核对用户实际看到的画面。区分用户报告的现象、独立复现的结果和已证实的根因。
- 保留历史懒加载、阅读位置、翻页、回到最新和输入体验；已验收的能力不回退，守住已验收的启动与首次发送性能。
- 本批问题从问题 1 开始，按编号逐个处理。同一时间，总控与负责人围绕同一个问题工作；这一项的修复结果独立验收通过后，才转到下一项。每一项按以下顺序进行：
  1. 定位与方案：总控与负责人串行、各自独立定位，分别给出对这个问题的根因判断和可落地的最优解。各自完成后再交换证据、互相质询；有分歧或反例就继续查，直到双方都认可根因和最优方案。
  2. 方案终审：形成共识后，由总控独立终审，分别判断根因是否真正解释了实际问题、方案是否真正是满足需求的最优解。发现缺口就回到本项继续论证；终审通过后，交负责人实施。
  3. 实施与验收：负责人完成并自查后，交总控独立审查实际修复效果。有问题就退回负责人修复，再重新交审，直到通过，才关闭这一项、开始下一项。方案终审与实现验收是两次不同的判断。

**效率门禁（动态）**

- 每一项进入“1. 定位与方案”前，以及“2. 方案终审”通过进入“3. 实施与验收”前（含每次退回返修前、中断或上下文压缩续接前），Antigravity + Gemini 4 Carbon (High) 负责人须重读[高效工作方法](../engineering/antigravity-gemini-4-carbon-high-efficiency.md)全文，不凭记忆或摘要代替：
  - **定位与方案前：** 对照落实一手契约与调用面核查、同类受影响入口清点、独立查读并行合并与精炼成稿，不凭印象猜测，不向已封装底层盲目扩查。
  - **实施与每次返修前：** 复盘上一阶段低效苗头或退回原因，从共享机制根源闭合而非叠局部补丁；先自审并跑通最低成本定向验证（确认实际执行数非零），再做必要构建与终端实测，复用输入未变的有效证据。
  - **门禁核对：** 负责人在执行中严格遵守，并在该步交接中附一行落实说明（不另写长篇复盘）；总控在派发、交实施与退回时同步提醒，收件时核对门禁已执行。

### B 问题发现流程

用途：待处理清单为空时，按真实用户的环境与使用路径（方法同[真实使用验收](../engineering/user-workflow-acceptance.md)），成批发现明显的功能异常，以及破坏正常使用的呈现错误。发现期间不修；本批发现结束、冻结后进入 A。

**分工**

- **负责人主操系统扫查：** 按范围逐项真实操作，提交原始画面与过程记录，做第一遍判读；准备并复原测试对象。执行中遇到驱动障碍，先改用已有的可靠方式，必要时交接，不让整批卡在排障上。
- **总控是独立的一方，负责本批是否完成：**
  - 开跑前独立核对范围，与负责人的范围做差集；
  - 整屏判读负责人交来的画面，不以负责人的结论为前提；
  - 亲自做连续使用补查，专选负责人没走过的入口、状态与顺序，不重复全量。
- **资源：** 双方实际操作串行，同一时间只有一方占用窗口与 heavy 槽，按原子流程占槽、释放。

**范围**

- **一批的范围是有限的，由三方核对确定：**
  - 运行中的菜单：屏上的命令候选、键位提示、选项、面板底行；
  - 有效需求与旧义务；
  - 源码声明：命令注册表的静态项与运行时可见项、按键与鼠标处理、候选操作。

  三方不一致的地方，先按合同核实（可能是可见性、权限或当前条件造成的），再判断是不是缺陷。
- **覆盖底线：** 从真实用户常见任务出发，覆盖公开可达的启动/独立子命令与交互终端完整操作，包括首次引导、主会话、候选面板、各命令的二三级页、弹层、阅读与输入、取消/中断及键鼠操作。不因为陌生或以前没报过错就跳过，也不让已有测试或命令表单独定义范围。
- **条目写法：** 每条写清入口、要完成的操作、预期可见结果的依据（需求、合同或已接受的体验）、适用状态与条件。同一页面里，保存、取消、失败恢复、键盘与鼠标入口走不同分支的，分开列。
- **条件按适用功能、共用呈现路径和已知风险选代表：**
  - 状态与输入：覆盖既有存量配置与历史数据（不只用开发者现造的空目录和规范化输入），兼顾空、短、多页长会话，配置未设与已设，任务有与无，以及普通输入习惯、合法边界与失败恢复。
  - 窗口宽度与主题：历史故障用来提高优先级，但不是唯一准入条件。共用的布局要包含真实支持的窄宽度；共用的配色路径，要在浅色下取代表页面。
  - 不要求每个页面都乘所有条件。

**效率门禁（动态）**

- 正式开跑本批系统扫查前（刚在“每轮入口”读过且中间未经历旧清单复核、前序批次或上下文压缩的，不重复空读；由旧清单复核转入、按 C 归档后开启下一批，以及分波次续扫、遇驱动障碍调整或中断/压缩续接前须执行），Antigravity + Gemini 4 Carbon (High) 负责人须重读[高效工作方法](../engineering/antigravity-gemini-4-carbon-high-efficiency.md)全文，对照落实原生入口与既有可靠驱动复用、独立准备与横向核对合并，以及“登记即止、不耗在外围工具建设或根因排障”；交接扫查记录时附一行落实说明，由总控在派发与收件时核对。

**执行：走真实使用流程，做到结束状态**

- **测试对象：** 符合用户交付形态的同一构建与公开入口（如 `zz` 及正式子命令），记下候选身份，不绕过公开入口或替掉受检产品链。发现期间不改产品，不重建。
- **默认环境：** 正常使用和可以复原的操作（切换后切回、输入后清掉），在已授权的默认环境做，写明复原方式，用户原有的数据不改不删。删除、清空、配置写入这类操作，只对专为测试准备的对象执行。
- **隔离环境：** 需要时使用，仍走真实构建、真实入口、真实实现，并还原真实存量配置、数据与宿主条件。自动驱动须确认动作实际进入目标场景生效。
- **夹具模型：** 只能证明限定的终端交互链，不能代证真实模型、外网、外部账号及其权限链。
- **操作链：** 保留用户真实经历的启动、配置、等待、返回与接续，每项做“进入 → 主要动作 → 看结果 → 返回或下一步 → 继续使用”；涉及可取消操作或持久状态时，一并核对取消/中断后的可用性及重启回读。再做几条交叉的连续操作，让前一次动作的残留有机会暴露，例如：
  - 切换后输入；
  - 改名后回到列表；
  - 配置保存后重新进入或重启核对。

  只打开、只取消、只收到成功提示，都不算完成。
- **观察时点：** 触发、状态转换、完成、下一步，这四个时点都要有画面，并记录从触发到真正可继续操作的实际等待（排查明显卡顿与无响应）。转换期间连续采样，捕捉闪动、暂时错位和几秒无反馈。
- **截图方式：** 字符帧证明状态；空框、裁切、焦点、颜色这类问题，用宿主窗口的像素图。无可用宿主画面时按“尚未验证完成”如实保留，不得用文本或状态转储代证界面正常。

**判读与登记**

- **整屏判读：** 站在真实用户视角看整屏是否能看懂、知晓下一步操作、等待合理、状态真实且数据守恒，以及前一次动作是否留下错误状态，不只核对预期的那一句提示。
- **异常的认定：** 一个异常必须指出具体受损的操作或可用性，并给出依据；妨碍正常使用的既有缺陷同样登记，不借“原来就有”放行。合法的成功提示、合同允许的空态或省略，不算异常。只是可以更好看或更好用的，记入体验建议，不进本批的问题清单。
- **三种失败分开记：**
  - 产品异常；
  - 驱动失败：要有证据，例如按键没有发出、窗口尺寸不符；
  - 缺依赖。

  输入没送达、没有响应，不能直接判为驱动失败。分不清的标“待核”，不算正常。
- **登记即止：**
  - 一次真实捕获就是证据，不要求稳定复现，只在判断真伪需要时做最小复现；
  - 保留异常发生前的状态与对象身份，记下最短步骤、预期与实际、条件、画面；
  - 不分析根因，不改代码。

**同类问题**

- **横向核对：** 发现一处异常，就主动核对同类页面、同类层级，以及相同交互的其他入口，记录真实受影响的范围。例如某个页面的页头是空框，就要核对二级、三级等所有同类页头，不能只登记这一个页面，也不能把例子当作全部范围。
- **问题族：** 同类发现集中记录为一个可交接的问题族，列出全部受影响入口，不按页面机械地拆成多项、各走一套流程。症状相同只先标“关联”；根因没有证实之前，不认定为同一原因。
- **交给方案阶段：** 问题族的受影响范围，交给 A 的方案阶段，从整体架构判断最优修法：
  - 适合公共机制的，在公共实现处修正或抽取复用，让相关消费者一起正确；
  - 不适合的，不硬抽象，不为复用预建框架，也不在各处复制局部补丁；
  - 确认同根的，统一方案、一起修复；不同根的，按实际分开。

**结束与冻结**

- **三态结论：** 范围内每一项落在三态之一，每项都写原因与后续归属：
  - **已操作正常；**
  - **已确认异常：** 有原始证据、发生条件和可交接的操作记录；能复现的附步骤，不能稳定复现的也保留。
  - **尚未验证完成：** 分为“未执行或被阻断”和“已观察但待核”。待核不算正常。
- **阻断：**
  - 遇到阻断，记下它挡住的下游路径，继续走其他可走的项；
  - 属于测试准备的缺口，先补齐；
  - 连入口都进不去的，如实形成阻断批次，转入 A。
- **冻结条件：** 每项都有三态结论，总控的范围差集与独立补查都已完成，每个问题条目都有原始证据与可交接的操作记录。
- **冻结前后：** 冻结前发现原定范围的漏项，补进本批。冻结后不再横向找新问题；修复带来的直接回归，或同一项没有闭合的部分，仍在该项内闭环。只有独立的新问题，才进入下一批。

**衔接**

- **冻结产物：** 一份问题清单（按问题族），加一份覆盖记录（每项三态及证据位置）。它不证明产品已无缺陷；即使发现 0 项，也要有真实操作的覆盖依据。
- **登记：** 问题登记到动态区，写法沿用历史批次：
  - 用户的操作；
  - 屏上每个元素，以及与操作前的对照；
  - 画面路径；
  - 要求。

  按依赖与影响排序。
- **处理：** 按 A 逐项处理。修复后，按实际影响复验受影响的链和必要的连续使用，仍然有效的证据直接复用。

### C 批次留存约定

- **发现结束：** 只冻结问题清单并进入处理，此时不归档。
- **何时归档：** 本批纳入的问题全部按 A 处理并验收之后，把当时工作台全文的快照存为 `docs/tasks/archive/<日期>-terminal-ux-batch-<序号>.md`。快照包括：问题、对应要求、当时适用的工作方式、处理与验收结果、版本依据。未验证的项、用户尚未亲自验收的情况，都如实写，不因归档而算作通过。
- **版本依据：** 已有提交的，记提交号；尚未提交的，记验收所用的构建或候选标识，并注明未提交。归档不以提交为前提，也不触发或授权暂存、提交、推送。
- **生成快照时的链接：** 快照保留当时的正文和状态，只按归档位置调整必要的相对链接，并核对链接可达。例如工作台中的 `../tasks/archive/...`，放进 `docs/tasks/archive/` 后要改为同目录的相对路径。这一调整只在生成快照时进行，不允许事后按现行规则改写历史快照。
- **归档不改：** 历史快照不随当前规则或新批次重写。新批次只更新动态区，历史批次的入口始终保留。

### D 维护轮次退出

用途：维护随系统长期进行，每一轮只在资源允许时推进。需要恢复正常业务时，按本块结束这一轮：交付已完成的收益，清理临时资源，留下接续所需的内容。本轮退出不表示本批问题已全部解决，也不表示长期维护终止。

**选择退出方式**

- **常规收束：** 默认方式。当前在办项完成并验收后，只处理分流认定的必修项，然后集成与收尾。
- **紧急暂停：** 用户明确要求立即让出资源时使用。在最近的可恢复边界停下并释放运行资源，只交付已完整验收、可独立应用的成果，其余全部保留待续。

**一、收束**

- 停止发现新问题，不再按 B 开新批。
- **常规收束：**
  - 当前在办项按 A 完成并通过独立验收。
  - **分流：** 总控与负责人对剩余已知问题（动态区未结的条目、候选、环境与验证待办）各自独立分流，再交换核准。分流只核对严重性：复用仍有效的证据，只补影响分流判断的必要核实，不展开普通问题的完整根因研究或无关的全量验证。
  - **必修准入：** 只有已有证据表明不修就会阻断正常业务、或严重影响用户使用的问题，才纳入本轮。“是真缺陷”“可能有风险”“可以顺便优化”都不足以纳入；一般缺陷、轻微体验问题和假设风险滞留。待核项不冒称正常，也不把假设风险升级为必修。
  - 必修项按 A 串行处理。不借关联纳入独立的普通问题；同一问题未闭合的部分和修复的直接回归，仍按 A、B 闭合，不以收束为由留下本项已知缺口。
  - **时间：** 收束只占用有限时间。真实必修项明显超出短时收束时，先向用户报告具体影响、数量和预计耗时，按用户决定执行；不自行拖长，也不为赶时间把严重问题降级。
- **紧急暂停：**
  - 在最近的可恢复边界暂停，保存在办改动，全部待办写入动态区。
  - 同时释放可以安全释放的运行资源（进程、测试环境、资源槽），不因提交授权、集成或构建尚未完成而继续占用；半成品与续办所需的环境保留。
  - 交付范围只含已完整验收、可独立应用的成果；半成品不进入交付。
- 两种方式都在动态区写明：本轮完成项、必修项（含 0 项）、滞留项及理由、环境与验证待办，以及本轮所处的阶段。每个问题的事实只写一处。

**二、成果集成**

分支、提交、集成与清理按[分支管理技能](../../.agents/skills/branch-management/SKILL.md)执行。本块只补维护场景的衔接：

- **划清交付范围：** 完整成果及其必要依赖，与半成品分开；未完成内容独立保留，不混入交付。不属于本轮交付的暂存内容和其他改动保持原样，不混入提交。
- **提交与合入：** 交付内容先整理成提交计划，在有效授权内提交并合入目标主线。没有相应授权时，准备好计划，停在需要授权的那一步。
- **核验：** 在实际交付的版本上构建并核验，确认合入内容与验收候选一致。
- **状态：** 本地提交、合入目标主线、远程同步三者分别记录是否完成。
- **事后记录：** 集成之后再更新工作台等记录，作为新的提交；不为保持提交数量改写已共享的历史。

**三、资源收尾与续办**

- **清理临时资源：** 交付成果的归属明确后（已合入目标主线，或已按授权保留），清理不再需要的临时分支、worktree 登记及其实体目录、测试环境，释放仍在运行的进程与资源槽。删除按[删除资源技能](../../.agents/skills/delete-resources/SKILL.md)执行。
- **分别核实：** 登记与实体分别核实结果；只清掉登记、目录仍在，不算完成。
- **保留项：** 半成品、滞留问题、续办所需的证据与工具，写明位置、负责人和恢复条件。
- **续办：** 下一轮按“每轮入口”复核并分流；有未完成修复时，一并核对其基线与完成状态，保留必要成果，接续仍需处理的部分。本批未处理完的事项继续登记，不提前按 C 归档。
