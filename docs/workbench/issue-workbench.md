# 问题处理工作台

本工作台承载终端问题的成批发现与逐项处理，分为静态区和动态区：

- **静态区：** 已定稿的工作方式，分三块：A 问题处理流程、B 问题发现流程、C 批次留存约定。A 已由用户封版。B 与 C 同样只在用户明确授意时修改。更新其他任何区域，都不得顺带改动静态区。
- **动态区：** 只登记当前批次，以及历史批次的入口。

## 静态区

### A 问题处理流程（已封版）

本块由用户定稿封版，原文逐字保留。未经用户明确授意，不修改其中的字词、标点、顺序或编号。

**通用要求**

- 按真实用户的操作顺序，在构建后的终端中核对用户实际看到的画面。区分用户报告的现象、独立复现的结果和已证实的根因。
- 保留历史懒加载、阅读位置、翻页、回到最新和输入体验；已验收的能力不回退，守住已验收的启动与首次发送性能。
- 本批问题从问题 1 开始，按编号逐个处理。同一时间，总控与负责人围绕同一个问题工作；这一项的修复结果独立验收通过后，才转到下一项。每一项按以下顺序进行：
  1. 定位与方案：总控与负责人串行、各自独立定位，分别给出对这个问题的根因判断和可落地的最优解。各自完成后再交换证据、互相质询；有分歧或反例就继续查，直到双方都认可根因和最优方案。
  2. 方案终审：形成共识后，由总控独立终审，分别判断根因是否真正解释了实际问题、方案是否真正是满足需求的最优解。发现缺口就回到本项继续论证；终审通过后，交负责人实施。
  3. 实施与验收：负责人完成并自查后，交总控独立审查实际修复效果。有问题就退回负责人修复，再重新交审，直到通过，才关闭这一项、开始下一项。方案终审与实现验收是两次不同的判断。

### B 问题发现流程

用途：主动、成批地发现明显的功能异常，以及破坏正常使用的呈现错误，不靠用户逐个指出。整批发现结束、冻结之后，才按 A 逐项处理；发现期间不修。

**分工**

- **负责人主操系统扫查：** 按范围逐项真实操作，提交原始画面与过程记录，做第一遍判读；准备并复原测试对象。执行中遇到驱动障碍，先改用已有的可靠方式，必要时交接，不让整批卡在排障上。
- **总控是独立的一方，负责本批是否完成：**
  - 开跑前独立核对范围，与负责人的范围做差集；
  - 整屏判读负责人交来的画面，不以负责人的结论为前提；
  - 亲自做连续使用补查，专选负责人没走过的入口、状态与顺序，不重复全量。
- **资源：** 双方实际操作串行，同一时间只有一方占用窗口与 heavy 槽，按原子流程占槽、释放。

**范围**

- **一批的范围是有限的，由三方核对确定：**
  - 运行中的菜单：屏上的命令候选、键位提示、选项、面板底行；
  - 有效需求与旧义务；
  - 源码声明：命令注册表的静态项与运行时可见项、按键与鼠标处理、候选操作。

  三方不一致的地方，先按合同核实（可能是可见性、权限或当前条件造成的），再判断是不是缺陷。
- **覆盖底线：** 当前交互终端可达的入口与主要完整操作，都在范围内，包括主会话、候选面板、各命令的二三级页、弹层、阅读与输入、键鼠操作。不因为陌生或以前没报过错就跳过。
- **条目写法：** 每条写清入口、要完成的操作、预期可见结果的依据（需求、合同或已接受的体验）、适用状态与条件。同一页面里，保存、取消、失败恢复、键盘与鼠标入口走不同分支的，分开列。
- **条件按适用功能、共用呈现路径和已知风险选代表：**
  - 数据：空、短、多页长会话；配置未设置与已设置；任务有与无，按功能需要选取。
  - 窗口宽度与主题：历史故障用来提高优先级，但不是唯一准入条件。共用的布局要包含真实支持的窄宽度；共用的配色路径，要在浅色下取代表页面。
  - 不要求每个页面都乘所有条件。

**执行：走真实使用流程，做到结束状态**

- **测试对象：** 同一构建、同一入口（构建产物中的 `zz`），记下候选身份。发现期间不改产品，不重建。
- **默认环境：** 正常使用和可以复原的操作（切换后切回、输入后清掉），在已授权的默认环境做，写明复原方式，用户原有的数据不改不删。删除、清空、配置写入这类操作，只对专为测试准备的对象执行。
- **隔离环境：** 需要时使用，但仍要走真实构建、真实入口、真实实现，并还原相关的数据与宿主条件。
- **夹具模型：** 只能证明限定的终端交互链，不能代证真实模型、外网、外部账号及其权限链。
- **操作链：** 每项做“进入 → 主要动作 → 看结果 → 返回或下一步 → 继续使用”。再做几条交叉的连续操作，让前一次动作的残留有机会暴露，例如：
  - 切换后输入；
  - 改名后回到列表；
  - 配置保存后重新进入核对。

  只打开、只取消、只收到成功提示，都不算完成。
- **观察时点：** 触发、状态转换、完成、下一步，这四个时点都要有画面。转换期间连续采样，捕捉闪动、暂时错位和几秒无反馈。
- **截图方式：** 字符帧证明状态；空框、裁切、焦点、颜色这类问题，用宿主窗口的像素图。

**判读与登记**

- **整屏判读：** 看状态是否真实、是否可辨认、能否操作和继续、数据是否守恒，不只核对预期的那一句提示。
- **异常的认定：** 一个异常必须指出具体受损的操作或可用性，并给出依据。合法的成功提示、合同允许的空态或省略，不算异常。只是可以更好看或更好用的，记入体验建议，不进本批的问题清单。
- **三种失败分开记：**
  - 产品异常；
  - 驱动失败：要有证据，例如按键没有发出、窗口尺寸不符；
  - 缺依赖。

  输入没送达、没有响应，不能直接判为驱动失败。分不清的标“待核”，不算正常。
- **登记即止：**
  - 一次真实捕获就是证据，不要求稳定复现，只在判断真伪需要时做最小复现；
  - 保留异常发生前的状态与对象身份，记下最短步骤、预期与实际、条件、画面；
  - 不分析根因，不改代码。

**同类问题**

- **横向核对：** 发现一处异常，就主动核对同类页面、同类层级，以及相同交互的其他入口，记录真实受影响的范围。例如某个页面的页头是空框，就要核对二级、三级等所有同类页头，不能只登记这一个页面，也不能把例子当作全部范围。
- **问题族：** 同类发现集中记录为一个可交接的问题族，列出全部受影响入口，不按页面机械地拆成多项、各走一套流程。症状相同只先标“关联”；根因没有证实之前，不认定为同一原因。
- **交给方案阶段：** 问题族的受影响范围，交给 A 的方案阶段，从整体架构判断最优修法：
  - 适合公共机制的，在公共实现处修正或抽取复用，让相关消费者一起正确；
  - 不适合的，不硬抽象，不为复用预建框架，也不在各处复制局部补丁；
  - 确认同根的，统一方案、一起修复；不同根的，按实际分开。

**结束与冻结**

- **三态结论：** 范围内每一项落在三态之一，每项都写原因与后续归属：
  - **已操作正常；**
  - **已确认异常：** 有原始证据、发生条件和可交接的操作记录；能复现的附步骤，不能稳定复现的也保留。
  - **尚未验证完成：** 分为“未执行或被阻断”和“已观察但待核”。待核不算正常。
- **阻断：**
  - 遇到阻断，记下它挡住的下游路径，继续走其他可走的项；
  - 属于测试准备的缺口，先补齐；
  - 连入口都进不去的，如实形成阻断批次，转入 A。
- **冻结条件：** 每项都有三态结论，总控的范围差集与独立补查都已完成，每个问题条目都有原始证据与可交接的操作记录。
- **冻结前后：** 冻结前发现原定范围的漏项，补进本批。冻结后不再横向找新问题；修复带来的直接回归，或同一项没有闭合的部分，仍在该项内闭环。只有独立的新问题，才进入下一批。

**衔接**

- **冻结产物：** 一份问题清单（按问题族），加一份覆盖记录（每项三态及证据位置）。它不证明产品已无缺陷；即使发现 0 项，也要有真实操作的覆盖依据。
- **登记：** 问题登记到动态区，写法沿用历史批次：
  - 用户的操作；
  - 屏上每个元素，以及与操作前的对照；
  - 画面路径；
  - 要求。

  按依赖与影响排序。
- **处理：** 按 A 逐项处理。修复后，按实际影响复验受影响的链和必要的连续使用，仍然有效的证据直接复用。

### C 批次留存约定

- **发现结束：** 只冻结问题清单并进入处理，此时不归档。
- **何时归档：** 本批纳入的问题全部按 A 处理并验收之后，把当时工作台全文的快照存为 `docs/tasks/archive/<日期>-terminal-ux-batch-<序号>.md`。快照包括：问题、对应要求、当时适用的工作方式、处理与验收结果、版本依据。未验证的项、用户尚未亲自验收的情况，都如实写，不因归档而算作通过。
- **版本依据：** 已有提交的，记提交号；尚未提交的，记验收所用的构建或候选标识，并注明未提交。归档不以提交为前提，也不触发或授权暂存、提交、推送。
- **生成快照时的链接：** 快照保留当时的正文和状态，只按归档位置调整必要的相对链接，并核对链接可达。例如工作台中的 `../tasks/archive/...`，放进 `docs/tasks/archive/` 后要改为同目录的相对路径。这一调整只在生成快照时进行，不允许事后按现行规则改写历史快照。
- **归档不改：** 历史快照不随当前规则或新批次重写。新批次只更新动态区，历史批次的入口始终保留。
