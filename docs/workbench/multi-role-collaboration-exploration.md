# 场景化多角色协作 · 探索记录

**维护负责人：总控（当前主智能体）。** 记录在具体任务中如何设计、检验和调整角色职责及工作流程，为下次面对不同场景提供证据与经验。本文不是通用协作协议，不要求以后照搬本次角色配置；当前执行规则以各任务的工作方案为准。

## 记录与使用规则

- 各角色发现体系短板时提供事实与证据；总控负责停止失效路径、制定并直接落实调整、通知相关角色按新版接续，再核验效果。记录与干预同时进行，不能以登记代替纠正；下一次相关交接核验结果，无效则继续调整。
- 每项只留：**场景与原安排 → 观察及证据 → 原因（已查明／待核）→ 调整及负责人 → 验证结果与代价 → 适用边界**。有效做法也可记录，不只收失败。
- 区分“设计期发现”“执行中证实”“调整后验证”。写进规则不等于有效，未验证如实标注；反证与失败尝试保留核心结论，不复制聊天、进度流水或完整工作方案。
- 总控在阶段结束和最终交付时凝练可复用经验；只复用现有工作证据，不为研究协作本身额外造任务。下一场景先判断目标、风险、依赖、工作量与工具能力，再选择适用经验及所需角色。

## 案例一：知行终端架构迁移

**场景：** 在核心与界面解耦的前提下，迁移全部既有终端功能与页面、解决架构债务和交互缺陷；架构以 OpenCode 为标杆，未来功能不进入本次交付。初始[工作方案](terminal-architecture-migration-collaboration.md)采用总控、产品、架构、实现、独立验收五种职责；后续调整及验证按时间记录于下文。

**证据阶段：2026-10-02。** 下表记录设计期缺口；文末另记角色初始化与首轮需求发现的实测结果。尚未开展生产迁移，不把角色就绪或文档通过当成交付证明。

### 准备阶段验证

- **观察：** 四个独立角色会话均成功创建，读取相同版本方案，分别写入职责与权限回执并结束回合；总控通过平台完成事件取得全部结果。详细身份和证据在本机 `collab/terminal-migration/index.md`。
- **采用的接续方式：** 本次使用“总控派发 → 角色落盘并完成 → 总控等待完成事件”，无需角色另外发消息回信。不假定其他会话完成后会自动唤醒已结束的总控；也不把任务创建授权扩大成任意角色互发权限。
- **经验：** 角色规则须适配宿主实际的回报方式；初始化应当有明确停止点，准备完成不能自行转成正式执行。会话创建成功、产物正确与回合完成分别核对。
- **验证边界：** 已证明角色初始化和结果回收可用；尚未验证复杂任务交接、长时间中断恢复或迁移质量，正式第一阶段仍须验证真实终端取证手段。

### 首轮发现与审查

- **覆盖独立性：** 验收方先保存 15 类生产入口地图，产品完成 45 项需求／29 个交互面／16 条旅程后再反查；未发现整类遗漏，但查出视觉约定、恢复含义及输入反馈须明确。总控在完整审查结束后统一裁定、交产品修订，验收不代写。
- **合同不能只看现状：** diff／子任务展示是明确义务的接入缺口；频度排序是尚未落地的保留目标；授权换代则涉及安全寿命歧义。先由架构查权威与生产链、验收复核，再由总控定范围，避免把所有未接线代码都升级成迁移任务。代价是增加一轮有明确问题的查证；无需重做完整清单。
- **工具初始化不等于能取证：** 正式电脑工具初始化成功，但未枚举到任务自有 Windows Terminal；系统确认进程存在也不能替代可操作窗口和真实交互证据。有限夹具已自动退出并核实进程清理；阻塞原因未明，不归咎于产品。总控允许无关只读研究继续，保留真实宿主采用门槛，不无限重试同一枚举。
- **先查方法是否完整，再认定能力限制：** 首轮把“启动接口没有参数”视为路线不可行，遗漏了接口支持显式 exe 的事实。总控要求按公开接口做一次有边界的核实，实际启动宿主得到产品策略拒绝，才收口自动化路线。没有把源码事实或模拟事件冒充真实交互；也没有在拒绝后改名、包装或另造输入旁路。初始化成功、方法遗漏和真实工具限制必须分开。
- **运行约束须精确：** “用户无须另装运行时”不等于“每个组件只能直接运行在同一解释器”；选型应评价自足组件的真实分发、生命周期和资源成本，不能凭标签排除候选。
- **先证伪架构假设，再扩大迁移：** 有限样机中，IPC 主动断开能清理，真实父进程退出却使子进程来不及执行回调。工程保留失败；总控将原型冻结交独立验收，并由架构负责人重审进程归属与终端恢复，未因静态设计已通过而扩大迁移。两种事件必须分别验证；进程消失不等于资源和终端状态已恢复。修正效果尚待后续实验。
- **交接不能滞留在收尾：** 首轮原型验收的结论、报告和冻结核验已齐备，角色仍未及时结束回合，等待方无法接续。总控将后续任务的结束点明确为“必要证据齐备即交接”，复用未失效证据，不为措辞、排版或重复确认重开检查。生命周期纠正复核已按此完成交接；后续工程与复验继续检查这一约束的实际效果。
- **人工验收交付也要适配实际入口：** 总控给出PowerShell命令，用户实际使用CMD，程序启动前即被`&`语法阻断。改为明确标注shell的CMD命令后，用户完成滚轮、缩放、中文输入、切页、复制粘贴及正常退出验证。可运行制品之外，还须交付适合用户入口的命令；用户验收按实际要求的动作入案，不外推未做的异常退出，也不要求重复已通过交互。
- **成功断言须越过最后一个副作用主体：** 离屏和进程/资产测试通过后，用户在只结束UI时发现CMD方向键失效。自有console取证发现恢复helper内部SetConsoleMode成功，但Bun原生退出又覆盖结果；同样补查父死亡，证明两个进程退出后仍有raw模式。总控暂停采用，派工程一次查完整机制、架构修正恢复责任、验收独立核对证据。函数返回、进程退出、资产清理和用户终端恢复是不同结果；恢复断言必须在最后一个可能改模式的进程退出后成立。实际修复仍待后续验证，不能以反事实实验已成功代替交付。
- **故障模型须有产品来源，候选承诺不能递归扩面：** 恢复提案为保护新增owner又引入脚本尾声，独立审查发现该脚本自身仍可被结束；有限入口实验还证实了中断提示及安装/参数问题。总控先请产品核对原合同：UI/Node执行侧死亡和既有退出动作必须保留，但没有任意外部强杀最后恢复者仍成功的无限保证。随后按有限模型重新选最简单机制，先证伪发行入口再投入整套实现；不能以改名排除旧动作，也不能为候选自加承诺不断叠守护层。修订效果待实验，不以合同澄清直接关闭缺陷。

- **技术判据须反绑用户结果，不能固化失败路线：** 正确配对切屏在真实 ConPTY 缩放后仍回到旧行号。总控请产品区分“坐标与未切屏对照相同”这一技术推导和“已有内容完整、shell 可用”的用户结果；架构与验收分别从原始单元格确认随后提示符实际覆盖文字，故原 FAIL 保留，不能降标放行。产品允许守住内容前提下的必要新行和有限视口移动，架构据此另找最小机制。经验是先核实失败是否伤及用户结果，再调整实现或判据；未采用的技术选择不应反过来锁死产品呈现。新方案尚待实证，合同澄清不算修复完成。

### 异常退出修复：局部证明取代整体收敛

**观察与证据（2026-10-03）：** F8 根因上午已查清：恢复调用成功后，运行时退出再次覆盖终端模式。随后入口机制的有限实验通过，真实 UI 交接仍未闭合，集成又暴露缩放后覆盖原有文字等缺陷。证据见本机 `collab/terminal-migration/` 下的 `f8-recovery-diagnosis.md`、`recovery-entry-review-r2.md`、`recovery-ui-review-r2.md`。审查发现的缺陷真实存在，不能把必要审查都算作浪费；但多轮局部产物完成并未及时形成用户可用的修复。

**本质：总控把“各岗位产物获得通过”当成推进依据，没有持续以“完整用户结果还差什么”决定下一步。** 既有方案已要求按完整旅程交付、合同内自主实现、不逐项会签，执行仍退回逐个实验交接放行，说明根因不是缺少角色或规则，而是总控没有落实整体收敛责任。具体表现为：

- **验证边界切早了：** 检查恢复调用与资源回收，却未跨过最后一个副作用进程，验证 CMD 的真实后续使用。局部正确不能自然合成为整体正确，遗漏被推迟到集成或用户手中才暴露。
- **决策依据偏移了：** 派生的技术判据被当成不可变目标，未及时区分用户必须获得的结果与候选实现的选择，导致在局部路线内反复加固、返工。
- **结果责任被流程稀释了：** 总控逐步变成派发与转交者，未持续判断新增实验、审查和文档是否消除关键不确定性、是否真是后续工作的前提。角色各自交付了材料，整体关键路径仍停滞；串行交接过多是这一失守的结果。

**纠偏及责任：**

1. **总控以完整用户结果组织交付。** 工程负责人持续负责从真实入口到退出后继续使用的完整链路；中间实验只是查证手段，不自动成为新的审批关卡。每次交接明确剩余结果缺口、当前动作要消除的不确定性及真正的依赖；只报局部完成比例不能推动整体状态。
2. **总控裁决取舍，专业角色保留职责内自主权。** 用户合同有歧义才找产品，技术合同或可行性前提被反证才找架构；普通实现缺陷由工程查齐并修复。派生判据失效时核对实际用户损害，再决定换实现还是修正判据，不降低内容保护、可用性等真实要求。
3. **让独立审查服务完整交付。** 高风险假设用最小实验尽早证伪；其余围绕冻结的完整链路审查，整轮结束后统一修复，复用未失效证据。只有确实依赖审查结论或会改动被审版本的工作才等待。连续交接仍未减少关键缺口时，总控必须重判路线和排程，不能继续追加同类流程。

**验证结果与边界：** 上述原因是本轮执行复盘结论，纠偏效果尚待后续完整交付验证；不虚构各环节浪费时长。适用于存在多层运行时、跨角色集成及异常生命周期的任务，不取消独立验收、必要实验或版本隔离，也不以赶时间掩盖已发现的真实缺陷。

**体系落地（2026-10-03）：** 已将纠偏写入[工作方案 v2](terminal-architecture-migration-collaboration.md)的角色权责、连续执行和阻塞规则，替换当前任务卡中逐段申请 UI 接入的限制，并在索引明确旧指令退役。工程获得完整单元执行权；新增阻塞须举证，预计失约直接同时通知总控与验收。四个角色均已接收，非执笔验收方核对规则、任务卡与有效索引后给出 PASS，未发现权限扩张或质量门削弱。证据留在本机 `collab/terminal-migration/coordination-v2-review.md` 及索引。已验证的是一致性与角色接收；实际提效和预警效果仍以随后工程结果检验，不把文档发布等同于缺陷修复。

**首次执行反馈：** 工程完成首条真实 F8 有限自查后，主动将启动预算预警同时送达总控与验收，并继续其他故障路径。验收只读确认慢段及计时口径缺口；总控保留预算、允许合同内查证修复，未重开设计或停止全部集成。这次证明双送预警与局部处置实际可用；尚不能据此宣称总体效率或完整交付已达标。

**终态接续反例与纠正：** 工程于 2026-10-03 19:55 完成 r4 并冻结，按总控明确指令仅在自己的会话最终回复；总控此前已结束回合，未在等待完成事件，验收仍停在旧预警。回放该工程回合只见两次主动预警发送，没有完成通知。根因是把“产物已保存／会话已结束”当成“下游已获知”，且把主动通知只用于异常、遗漏正常完成；接收路径依赖总控持续在线，设计不能在其结束回合后继续驱动任务。v2.1 统一规定终态先落盘、主动通知指定接收者再结束，最终回复不充当通知；去重及接收状态留在已有索引，不新增角色、轮询或确认循环。早期准备阶段的完成事件方式只适用于接收方正在等待的回合，不能外推为后台自动接续。通知失败不得标记交接完成，纠正效果以真实交付通知和下一任务接续核验。

### 门槛误用：数值真实，不等于失败分类成立

**观察（2026-10-04）：** 人工运行出现两次真实启动等待，验收与总控将其直接套入“新包/新根首次 ≤3s”门槛，阻断采用并追加定位。后续独立核对发现：同一制品和受管根此前已完成准备运行，这两次也不属于约定的连续五暖样本；原规定样本通过。等待数值没有错，错在未核实适用条件，就把体验异常升级成选型否决。证据与纠正留在本机 `collab/terminal-migration/startup-route-review.md`，原始慢样本及旧报告未删除。

**本质与责任：** 总控和验收只核对数值可信，没有核对“合同条件 → 实际样本 → 失败影响”的完整推理链，把有限工程验证误扩大为无条件运行保证。错误阻塞进一步诱导系统诊断和运行时替换，导致投入偏离产品交付。收到更多技术材料不能代替重查决策前提。

**可复用做法：** 新增阻塞必须同时说明合同、样本/版本/环境及起止口径、真实损害和直接受影响工作；不满足适用条件的观察仍应记录并处理，但不能自动否决整条路线。既不拿快速样本洗掉真实异常，也不靠扩大门槛阻止所有推进。发现推论错误时保留原证据、显式更正分类、撤销无效依赖；未解决的实际用户问题分配给明确工程单元和验收负责人。纠正判据不等于宣布问题已修复。

**复用验证：** 随后的 E-RPC 告警以 UTF-16 估算推导逻辑池超额，而冻结合同规定规范化 UTF-8 计费、物理放大另验 RSS。总控在扩大改造前发现口径差异，独立验收查证后撤回该扩面依据；工程连续实施，真实副本准入与容量验收仍须补齐。此例验证了“先核合同与推论，再定受影响动作”的纠偏方式，没有用算式纠正代替实现通过。

### 提交积压：有负责人，缺少触发和跟进

**观察与原因（2026-10-04）：** 工作方案已指定工程准备并执行、验收检查、总控放行，但没有把提交准备绑定正式设计定稿或完整成果交付；总控在设计通过后也未安排批次。随后生产迁移继续积累，用户再次提醒。缺少 Git 执行授权不能解释为何没有先准备可审查批次；作者局部自测也不能代替独立验收直接提交。

**再次纠正：** v2.2虽补了触发责任，仍把“完整工程交付”作为准备节点，实际索引更明确等整个U1冻结；用户再次指出这种粒度仍会积累大批变更。根本问题是混淆完整用户旅程的验收边界与可回滚提交的工程边界。

**调整与责任：** v2.3由工程在适当大小的修复／重构／功能增量闭合时主动成批，总控安排本批独立检查和授权执行；保留整个迁移单元与最终整体验收。每批一个清楚目的，可缺后续能力但无半升级债务；按不变量合并必要生产者、消费者与测试，不以同属U1包办百余文件。只冻结相关批次，无关实现继续，已有证据按版本复用。当前积累在工程完成手头改动的安全收束点优先整理，不能继续等U1全部完成。

**后续验证：** 至10月5日已形成14笔提交，批次准备、独立验收及实际提交链可运行；同时仍有107个变更路径，说明“能提交”不等于“能及时闭合”，原因和进一步调整见下一节。

### 持续积压：交付边界后置与实现职责过载

**观察（2026-10-05复盘）：** 前一工作日及当夜已形成14笔提交，不能说没有推进；中断现场仍有107个已暂存变更路径，其中18个属于已验收、已放行而未执行的r15，另有52个新终端核心路径及37个接合路径。工程同一长回合承担实现、调试、夹具、构建集成、冻结候选及拆分提交；跨层权限、身份和生命周期问题在真实集成中继续出现。现场及证据留在本机索引。回合时长包含等待，不能当作有效编码时间；此前35%／44%没有统一分母，不能据此计算整体推进量或效率。

**根因判断：** 总控虽改为允许小批提交，仍在宽泛U1授权下持续铺开实现、成果成熟后才倒推拆分；没有管理未闭合用途和下一可交付边界。工程承包从实现到入库的全部细务，总控又重复搬运与核对回执，导致瓶颈集中。提交积压不只是漏提醒或缺执行授权，新增一个收尾时才工作的“提交员”也解决不了。

**v3调整：** 新增集成交付主责，开发前安排批次和必要依赖，开发中组织冻结、准确构建及证据复用，独立通过后按预定条件提交。工程专注实现和返修；总控控制在制范围、关键依赖与例外，不逐笔转发。默认一个修改中批次加一个冻结交验批次；先验证高风险真实交界。工程唯一写生产代码，交付在明确移交后唯一写Git；验收仍不参与作者工作。实际暂停和旧写者状态优先，已通过批次不因角色调整重复验收。

**验证与适用边界：** 本轮交付的是可执行规则，不宣称已证明提效。恢复后用实际批次检查成熟成果等待是否消失、在制范围是否减少、工程是否少做交付整理；不另建统计平台，不以降低验收或遗漏需求换速度。适用于实现、集成及持续版本交付已构成不同工作负载的任务；小任务不应机械照搬六角色。

**方案审查的再纠偏：** 初稿又将全量权重整理设为恢复开发前提，且通用通知仍偏向总控中转；独立整轮审查确认两处P2。统一改为百分比报告前完成分母，已明确批次可先恢复；完成／阻塞直接交接下一责任人并知会总控，只有质量争议进入验收裁决。同时澄清普通缺陷由原负责人连续处理。经验是每新增一项管理规则，都要检查它是否无意增加了生产前置或串行交接，不能以解决效率问题之名重新制造等待。
