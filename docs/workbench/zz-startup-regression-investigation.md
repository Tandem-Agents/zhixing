## 根因定位方法（静态区域）

**目标：建立“触发条件 → 底层机制 → 用户表象”的可验证因果链。耗时排名、源码疑点或一次变快，都不能单独证明根因。**

1. **复现真实入口。** 使用实际安装产物、用户数据和真实终端运行 `zz`；记录版本、运行目录、后台是否存在及系统负载。区分刚构建后的首次启动、后台不存在时的再次启动、热接入，保留慢样本，不能用清空数据或局部导入替代。
2. **还原同一次启动。** 从命令发起连续观测到完整可交互，分别标记首次可见文字、输入就绪、业务就绪。关联前台、Host、worker 的身份与时间；按依赖关系还原关键等待链，区分执行、排队和并行重叠，不能混拼不同轮次或直接相加。
3. **逐层追问等待来源。** 先粗分阶段，再只细查尚未解释的关键阶段。等待要找到谁占用资源、为何未释放、是否反复执行；执行要区分 CPU、模块装载、文件访问、子进程及外部调用。“锁竞争”“初始化慢”只是继续追查的入口。
4. **保住首次失败，控制观测干扰。** 在错误归类、跨进程传递和重试覆盖前，保存脱敏的原始错误类型／错误码、操作、阶段及后续变化。诊断通道独立于被调查的日志写入链，有界且不新增产品写者；用无探针对照检查观测开销和行为变化。
5. **用反证验证因果。** 每轮明确一个假设及能支持或推翻它的结果。在相同条件下做最小单变量对照，必要时恢复原条件复验；既检查异常阶段是否按预期变化，也检查用户表象是否随之变化。合成复现用于证明机制，不能冒充本次历史故障归因。
6. **以证据闭环收束。** 两个问题分别给出触发条件、因果链、证据和未解释部分，再判断是否同源；沿已证实机制检查相关路径。无法恢复的历史证据明确标注，通过后续复现补证；未复现、日志恢复或某次启动变快，都不等于根因已查清。

## 调查结论（动态区域）

### 已关闭的日志与交付问题（2026-10-02）

本轮日志收尾、构建和全仓结构门禁已完成；原始 56 秒历史缺证与启动性能优化分别登记，不能合称全部启动问题已解决。前轮将“固定基线同样失败、零新增”视为收尾的结论已撤回。

| 根因 | 已完成的修复与验证 |
| --- | --- |
| core 声明生成与打包集中在同一 worker，默认堆 OOM | 声明生成和打包顺序分离，释放类型检查器，保持公开产物；标准 `pnpm build` 无额外堆／串行参数成功。固定旧提交也复现 OOM，仅用于确认来源，不作为豁免。 |
| 查询／策略及并发路径漏接可信写者声明；PID 校验存在时间窗口 | 清点与声明验证作为不可拆分的依赖，接受证明前复核出生身份；四项原失败场景在新版其他 home 写者持续存活时通过。未知或不可读的存活写者继续保守阻断。 |
| Windows WMI 短暂保留已退出进程的空命令行行，误判库存不可用 | 仅在 OS 证明退出后排除残留行；保留有限失败类别与 PID，不采集命令行正文。真实退出压力清点由 30 次中 10 次受阻降为零。 |
| 入口、主解析器与写者分类的参数／数据根规则不一致 | 统一分隔符归一化、等号参数、重复参数及策略写入识别；早期失败归入本次选择的数据根。 |
| 首因在 IPC／重试中丢失，协调者正常交接误记失败 | 有限错误分类和原生码贯通，保留首次失败、后续变化与实际宿主身份；观察通知失败隔离，提交成功和后续清理失败分别记录。 |
| 小批次形成微分段、治理反复发布且末次回收不复查 | 活动段按容量／年龄封段、有界批量治理、合并发布及末次实际容量复查；保留预算硬顶、未知写入和缺口语义。 |

验证和平台边界统一见[日志模块收尾记录](../tasks/runtime-logging-and-diagnostics.md)。不保留已失效的多轮“最终通过”流水；以下保留性能调查仍有价值的因果证据。

### 同次时间链与复测

全局 CLI 指向本仓库 `packages/cli/dist`，Node 24.19.0，原始故障调查使用 2026-10-01 构建；下表属于该次历史证据。旧记录见 [zz 启动与真实使用问题核实](../tasks/zz-startup-investigation.md)，其性能判断不作为本轮下限。

| 原始故障阶段 | 同次证据 |
| --- | --- |
| 前台准备 | 界面模块导入 10.056 秒；前台启动后 12.136 秒才创建 Host。 |
| Host 入口 | 创建至 `runtime.started` 约 7.99 秒。 |
| Host 检查 | `prepare-service` 6.858 秒，`check-configuration` 0.282 秒。 |
| Host 装配与恢复 | 约 28.93 秒后连接成功，距前台启动约 56.22 秒；随后取得界面数据。 |
| 日志异常 | 最终保存的是 `initialize / writer-busy`，失败窗口 15:40:50.691—15:41:02.226，共 3 次；首次通用提示的底层错误未保存。 |

约 12 秒空白包含在总耗时内，不能再相加。调查阶段两次**无探针冷启动**首次文字均约 1.17 秒，输入就绪分别 **16.64／16.44 秒**；轻量观测为 17.18 秒，定点 Authority 观测为 17.32 秒，均未出现前台降级。全量 await 探针达到 22.74 秒，因观测干扰排除其绝对耗时。少量复测不能代表 p90，也没有重现 56 秒慢样本。

### 已证实的原因与对应方案

**1. 后台恢复重复处理同一份历史，不只是排队慢。** 在 17.32 秒这一轮的界面就绪前，六份 Authority 日志初始合计约 3 MiB，却累计读取约 **108 MiB**，发生 **48 次全量恢复**；其中约 1.28 MiB 的一份被全量恢复 32 次。183 次 Authority 操作的时间区间并集约 **8.45 秒**，扫描／前缀校验并集约 **5.00 秒**，进程内队列等待累计仅 **0.30 秒**。嵌套时间不能相加，并集也不等于可直接节省的时间。

[commit-log.ts](../../packages/core/src/authority/commit-log.ts) 中，`readSnapshot/readStream` 全量恢复，新消费者没有游标时再次全扫，已有投影遇到新增提交时重读旧前缀；各消费者分别进入排他操作。CPU 采样也证实 WAL 解码、哈希、恢复是热点。**解决方向：在 Authority 边界内统一组织恢复，同一受验证前缀集中重放、分别归约，后续按新增提交推进。** 受验证视图必须明确代际与失效条件，继续发现跨进程写入、替换、截断及损坏；仅将读移出锁或跳过校验均不解决根因。

**2. 重依赖装载挡住反馈，也推迟 Host 创建。** REPL 导入链约 465 个文件模块／5.8 MB，包括 193 个高亮模块、110 个 `undici` 模块。前台仅为代理描述引入网络总入口，带入完整 HTTP 实现；Host 装载链约 1379 个模块／14.6 MB，也包含终端高亮。首次提示依赖主线程 700 ms 定时器，模块解析、编译和注册阻塞它及异步服务发现后续；轻量观测捕获前台约 1.34 秒、Host 约 1.73／1.70 秒的事件循环停顿。

**解决方向：轻入口先反馈并拉起后台，拆开配置描述与网络实现、Host 装配与终端渲染的静态依赖，减少无关装载。** 保留完整历史呈现和已启用能力，不能把必要等待挪到首次发送。Windows 平台准备另有固定成本：一轮 Host 的 PowerShell 进程身份查询约 0.75 秒、首次凭据 worker 约 0.97 秒；应在保持身份与秘密隔离合同的前提下收敛 helper 启动。原始导入为何放大到 10.056 秒仍未归因。

**3. 日志小批次变成小文件，回收放大成长期持锁，并存在确定误报。** 现场约 3.2 MiB 已占 1022 个文件，含 1017 个分段，中位分段约 1.4 KiB，逼近默认 1024 文件上限。[storage.ts](../../packages/core/src/logging/storage.ts) 每批最多 8 条，按连续层级各建新段；`segmentAgeMs` 未驱动封段。每次写入清点目录，逐段回收又反复发布全量状态与耐久同步，均处于共享锁内。

生产 Store／Windows 文件桥、默认策略、临时合成数据的单写者对照：

| 操作 | 10 个分段 | 1017 个分段 |
| --- | ---: | ---: |
| 追加 1 条，持锁 | 0.099 秒 | 0.825 秒 |
| 追加 8 条、两层交替，持锁 | 0.173 秒，成功 | 3.516 秒，报回收未完成 |

后一事务产生 **24 次状态发布、128 次同步、56 次目录列举**，其他写者却只允许等锁 2 秒。更直接的错误是：`#makeRoom` 第 8 次回收后不复查容量，直接抛异常，worker 再将其归为通用存储故障。**单变量反证：只在临时加载副本增加末次复查，同一场景即成功，但仍持锁 3.11 秒。** 所以误报与写入放大必须一起处理；该 append 复现不等于原始 initialize 故障归因。

**解决方向：逻辑批次与物理分段解耦，落实容量／年龄封段；有界批量回收、合并状态发布，保持预算硬顶和崩溃恢复；补末次复查，明确区分治理待续、等待与真实失败。** 延长锁等待、提高文件上限或隐藏提示都只是绕过表象。

**4. 新进程加入会阻塞已有日志写者，首次错误又被重试覆盖。** 三轮真实冷启动均捕获前台 `migration-blocked`，单次约 0.39—1.22 秒：新 Host 尚未登记，`#refreshMigration` 就把整个日志根重新判为迁移阻塞，Host 重装载进一步延长登记窗口。[store-worker.ts](../../packages/cli/src/logging/store-worker.ts) 丢失未分类异常的具体类别，[recorder.ts](../../packages/core/src/logging/recorder.ts) 重试又覆盖最后原因，导致首次提示与最终保存的原因可以不同。

**解决方向：版本化写者登记前置于重装配，区分正在加入的新写者与不兼容旧写者，保留真实旧写者的预算隔离；保存有界、脱敏的首次失败分类、阶段、错误码和后续变化。** 不能直接取消兼容性保护。

### 尚未闭合的归因

- **原始 56 秒为何额外放大：** 已还原阶段，未取得当时 CPU／文件访问／调度证据，当前重跑未复现。不能归咎于杀毒、缓存或资源压力。当前 MCP 均未启用，排除“连接 MCP 等了几十秒”。
- **原始首次通用降级的具体错误：** 首因未被保存，不能从最终 `writer-busy` 反推，也不能拿上述 append 合成复现代替。

以上机制已有修复依据，但**本轮不能宣称两个原始现象已完整归因，也不能承诺修后 5–6 秒**。结案须覆盖实际入口、原有历史、冷／热接入、构建后首次启动、接近容量上限与并发写者，同时验证完整可交互、业务恢复和日志持久化；保住慢样本及首次错误，不能凭几次正常重跑宣布解决。

### 最终真实验收（2026-10-02）

- **功能**：原有历史和预算、真实全局 `zz`、ConPTY、空运行目录；冷／热接入均能执行帮助并正常退出，没有日志降级、启动失败或新增运行目录文件。没有调用模型。
- **追溯**：只用 `zz logs --offline` 完整分页，取得本次 61 条 runtime、84 条 Authority 记录。前台首次输出、就绪、阶段、退出与宿主实际 PID 交接一致；日志健康异常为零。历史淘汰及证据不足的缺口如实保留。分页游标正常推进；验收脚本初始页数上限不足不等于查询死循环。
- **故障反证**：隔离数据根制造原生目录打开失败，业务仍继续；解除后由正式离线入口读回首个原生错误码、`files.open`、初始化阶段、首次尝试和恢复。该证据证明首因保留，不冒充历史故障归因。
- **慢样本**：本次冷启动首次文字 1.85 秒、输入就绪 33.72 秒，热接入 3.96 秒。产品日志定位到后台准备 4.919 秒、角色装载 3.690 秒、主服务装配 16.897 秒；前台等后台 28.933 秒，与上述阶段重叠，不能相加。
- **底层工作量**：对应冷／热时间窗共 48 次 Authority 恢复、约 123 MiB 物理读取；`readSnapshot` 18 次即恢复 18 次，`transactProjection` 156 次含 24 次恢复。其累计排队、锁等待、执行分别约 1.04／2.38／7.03 秒；这是操作汇总，不是关键路径独占耗时。再次支持“重复恢复／读取”方向，不把总耗时归咎于日志或猜测系统负载。
- **边界**：日志与交付门禁可以收尾；第 1、2 项性能机制仍待专项优化，原始 56 秒的缺失历史证据无法补回。临时调查文档因此保留，不能以删除记录代替解决问题，也不能承诺未验证的启动秒数。
