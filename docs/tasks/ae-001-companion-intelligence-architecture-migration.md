# AE-001 伴身智能目标架构迁移

> 状态：待执行<br>
> 当前检查点：A0：冻结产品行为与架构事实基线<br>
> 完成度：0/8<br>
> 职责：在保持知行当前全部正式能力与首版发布边界不变的前提下，把生产实现完整迁移到 AE-001 定义的目标架构，并删除全部旧责任路径。
> 权威设计：[《AE-001：伴身智能架构演进》](../../research/design/architecture/evolutions/AE-001-companion-intelligence.md)

## 一、任务目标

在同一最终代码基线上达成以下结果：

1. 知行的产品语义、权威事实与共同应用行为形成唯一逻辑产品身份；模型、Runtime、Host、协议、进程和设备都不再反向定义知行。
2. Conversation、Workscene、Schedule、Advancement、Delivery 及现有管理责任分别形成真实的垂直领域边界，由同一责任者拥有合同、用例、规则和事实归属；Product API 只组合这些合同。
3. Intelligence Kernel、Correctness Substrate、ApplicationHost、产品表面和基础设施适配器的职责、依赖、状态与生命周期完整闭合，单机和多设备只在部署适配处发生差异。
4. 当前全部正式能力、公开行为、协议语义、持久化数据、安全边界、异常终态和首版产品体验保持不变；本任务不给用户增加新的概念、配置或操作负担。
5. 迁移完成后不存在旧业务入口、第二组合根、第二应用行为、第二状态机、第二事实源、双写、永久兼容桥、服务定位器旁路或以新名称保留的旧结构。
6. 目标架构由生产调用图、依赖方向、合同与事实所有权、生命周期、直接测试、制品和产品回归共同证明，而不是由目录、包名、接口数量或文档自报证明。

本任务只迁移架构，不增加产品能力。完成本任务不以新增个人连续性、主动触达、受控学习、记忆、多设备体验或生态能力为收益。

## 二、权威、对象与硬边界

### 2.1 权威关系

1. AE-001 的“一、原始构想”是最高产品依据，正文是本任务唯一目标架构权威；本文只负责执行范围、状态、证据和结束裁决，不得重新定义目标架构。
2. 当前生产源码、组合根、调用与消费链、状态写入、测试和制品用于证明现状、迁移可行性与行为基线，不能反向降低 AE-001 的目标。
3. 既有其他设计文档可能滞后，只作旁证。本文与 AE-001 冲突时必须修正本文；生产事实暴露 AE-001 无法唯一裁决的产品或架构问题时，停止对应工作包并把唯一决策点交给用户，不得在实现中暗自改写架构。

### 2.2 本任务迁移的对象

本任务迁移的是生产责任和依赖，而不是一组预设文件：

- 产品合同、应用用例、领域规则、状态机、权威适配和产品投影的所有权；
- Agent Runtime、RuntimeHost 与产品领域、宿主管理、安全内部对象之间的边界；
- CLI、Channel、Server/RPC 与应用行为之间的边界；
- Owner、Journal、Security、Confirmation、Resource、Persistence、Recovery、Assignment 与领域语义之间的边界；
- Provider、Tool、MCP、Storage、Channel、Executor、Mesh 与其上层端口之间的边界；
- 生产组合根的创建、启动、入口开放、换代、拒新、排空、关闭和残留清理；
- 单机与分布式拓扑的适配位置；
- 证明上述边界的依赖门禁、合同测试、结构证据、回归和现行架构文档。

实施必须从真实生产入口双向追踪，不能把本节当成封闭文件清单。

### 2.3 必须保护的产品与工程基线

除纯内部责任归位外，以下现有合同均不得回退或产生无授权的可观察变化：

- 模型—工具循环、上下文窗口、子 Agent、显式编排、多视角发散/收敛、任务列表、中断、取消、错误和明确终态；
- Conversation、历史持久化与恢复、Workscene、Schedule、Advancement、Delivery；
- Trust、Skill、用户可见设备关系及其现有管理行为；
- 工具、MCP、权限、确认、资源治理、工作区、安全拒绝和受控效果；
- Owner、Journal、Run、Assignment、全局状态、恢复和异常重驱；
- CLI、Server/RPC、消息通道及其公开命令、方法、事件和错误语义；
- 单机、Anchor/Executor、Mesh 与当前分布式运行时的正常和异常行为；
- 首次配置、Provider/MCP 管理、恢复备份与灾难恢复、维护/卸载，以及配置、秘密边界、构建、包导出、安装、Windows x64 制品与当前首版产品旅程。

### 2.4 明确排除

- 不新增、恢复或重建 Memory，也不接入 OWNWARD；未来记忆方案继续保持未决。
- 不新增个人连续性、主动触达、受控学习、新设备体验、插件市场、自修改或其他产品能力。
- 不把 distributed-runtime、多 Agent、插件、沙箱、协议或任何单项技术提升为产品或架构中心。
- 不推倒重写 AgentRuntime、Owner 或 distributed-runtime，不为了目标图一次性搬迁代码。
- 不预建万能领域、万能 `Capability`、动态插件内核、微服务体系或没有当前事实依据的扩展框架。
- 不把架构迁移变成首个版本发布的前置条件；发布问题和架构迁移分别管理。

## 三、建任务时的生产事实基线

本节记录开始迁移前必须重新验证的入口，不代表最终边界已经由文件名决定：

| 当前生产事实 | 目标迁移方向 |
|---|---|
| `@zhixing/cli` 依赖全部主要生产包，`cli/src/serve/command.ts` 是事实组合根 | 原地形成 ApplicationHost 后按责任迁出，CLI 回到进程入口与产品表面 |
| `access-surface`、`StartupRollback`、`CleanupRegistry` 和 shutdown chain 已有启动、补偿与逆序清理能力 | 作为 Host 生命周期资产继承，不把当前 `AssemblyContext` 原样改名成目标架构 |
| `ServerContext` 聚合会话、推进、场景、信任、技能、设备、迁移、投递和 Runtime 控制 | 逐步收敛为 Product API dispatcher 与有限 binding 依赖，handler 不再编排业务 |
| `AgentRuntime` 公共面包含安全、权限、工作区和管理查询等宿主内部对象 | 收窄为有限 Run Envelope / Event / Terminal 与查询端口 |
| `RuntimeHost` 直接认识 Workscene、Schedule 和专用工具 | 产品投影回到对应领域，RuntimeHost 只做通用运行装配 |
| 产品行为横跨 `core`、`owner-kernel`、`owner-services`、`server` 和 `cli/src/serve` | 先在现有目录形成垂直责任边界，再按真实需要决定 subpath 或拆包 |
| 几乎所有生产包依赖 `@zhixing/core`，根导出包含多类产品和基础设施实现 | 收紧公共 API 与依赖方向，领域合同随领域归位 |
| 用户可见设备管理与连接、epoch、Assignment、Mesh、执行位置在 CLI/Server 装配中交织 | Device Administration 与 Executor/Mesh 拓扑适配分离 |

旧 Memory 已经退场，不进入迁移登记表。A0 必须重新建立生产调用图、状态所有权表和公开行为基线；发现名称与真实职责不一致时按调用链裁决。

A0 不是一次笼统“调研”，而是以下七类可分别派发、最终相互闭合的基线责任：

1. 生产进程角色、入口、组合根、组件生命周期及其 create/start/open/replace/drain/close 链；
2. CLI 与 REPL 命令、RPC、Event、工具/Profile、配置 schema、包导出和制品入口的可执行 exact-set；
3. 当前产品旅程、默认值、错误、终态、持久化、恢复与跨表面行为；
4. 每项产品事实的语义 owner、写入口、Reducer、Authority、恢复路径和全部直接消费者；
5. AgentRuntime/RuntimeHost 公共面、全部运行形态、产品投影和本机/分布式分叉；
6. 包与关键源码目录依赖、临时旁路、公共 API 预算及首批禁止依赖；
7. 直接测试、已存在结构门禁、最终制品证据和已经复现的基线失败。

每项当前能力都必须归入 Domain、Product API binding/Surface、Intelligence Kernel、Correctness Substrate、ApplicationHost 或 Infrastructure 中唯一合适的责任者；没有独立产品事实的运行方式、交互模式和运维动作不得为了表格完整被虚构成新领域。A0 的每个工作包须更新第九节实时台账并留下稳定证据引用；七类基线未能从生产入口与反向消费者双向核对前，A0 不得完成。

## 四、实施状态

每项 `[x]` 表示该检查点的生产责任、全部直接消费端、旧路径删除、保护性回归、必要文档和当前基线证据已经同时闭合。只移动文件、增加接口、通过编译或完成局部测试不得勾选。

- [ ] **A0　冻结产品行为与架构事实基线。** 完整读取 AE-001 和验证手册；按第三节七类基线从每个生产入口追踪组合、调用、状态写入、效果、恢复和关闭链，再从公开出口、消费者与制品反查。建立带稳定标识的“当前责任 → 目标责任 → 迁移检查点 → 保护基线 → 直接证据”矩阵；所有公开 exact-set、生产进程角色、事实 owner/写入口/恢复、Kernel 公共面、生命周期、单机/分布式分叉和已知基线失败均须有可追溯证据。A0 可拆成多个 2～4 小时工作包，但只能建立基线和必要门禁，不得夹带后续责任迁移；任何正式行为、状态、写入口或生产角色未归类前不得完成。退出证据是可双向核对且登记在第九节的基线，不是搜索结果或文件清单。
- [ ] **A1　收束 ApplicationHost 生命周期边界。** 从现有 `access-surface`、启动回滚、清理注册和关闭链形成每个生产进程唯一的 Host 对象与类型化组件贡献；明确 create/start/open、换代、拒新、排空、close 和失败补偿，组件只管理自身内部资源。配置来源和秘密材料继续由专责 Provider 拥有，Host 只冻结并下发组件所需的最小只读投影，领域、Kernel 和 Surface 不读取来源。Host 可以暂时委托旧领域实现，但不得新增产品逻辑、领域状态、运行期服务定位或第二组合根。以完整启动失败、部分启动回滚、并发关闭、在途排空和零资源残留直接证明生命周期。

- [ ] **A4　封闭 Intelligence Kernel。** 基于全部现有运行形态冻结最小 Run Envelope / Event / Terminal 合同和 Conformance Suite；收窄 `AgentRuntime` 公共面，隐藏安全管线、权限存储、工作区解析和宿主管理内部对象。产品对象到模型输入、运行事件到产品结果均经显式投影；模型输出只能形成提议、证据和运行终态，必须经领域决定与权威提交后才成为产品事实。A4 只负责 Kernel 合同及其边界：把 Workscene、Schedule 等产品特有装配移出 RuntimeHost，交给当前唯一产品责任者生成信封；尚未完成 A5 的领域可以通过登记退场点的最短单向端口提供投影，但不得在 A4 复制其状态机、权威或 Product API。RuntimeHost 只消费通用运行合同，对话、任务、本机、远端、取消、失败和资源释放行为必须等价。

## 五、工作包与状态维护规则

1. 本文是迁移任务的唯一执行与状态契约，AE-001 是目标架构权威。协调者每轮先读取二者、第九节实时台账、执行记录和目标对话最新状态，独立核对仓库事实后再派发当前价值最高的一条问题链；执行者自报不能代替复核。实时台账记录当前裁决，追加记录保留历史证据；二者冲突时必须先按仓库事实纠正台账，不能靠翻阅对话猜测状态。
2. A0～A7 是阶段验收门，A5 各行是领域验收单元，都不是默认可整包派发的工作包。只有当前事实证明某个阶段或领域的全部剩余工作同时满足本节颗粒度上限、单一责任和单一验证闭包时，才允许整体派发；不得直接把“A0”“A4”“迁移某领域”等标题当成工作包。
3. 工作包必须写清：对应 A 项、当前检查点与基线、要改变的唯一责任、生产端与全部直接消费端、保护边界、明确不做、旧路径处置、最窄直接证据、完成条件和安全交接点。一个包以一个可独立证伪的架构结果为结构边界，例如一次 owner/写权转移、一条生命周期责任闭合或一项依赖反转；可以跨文件和包，但不得同时改变多个相互独立的事实所有权、生命周期或问题链。
4. 默认工作包按 **2～4 小时真实有效工作量**设计。短于两小时的剩余工作，只能与同一责任链的必要前后步骤合并；不得为凑时长合并无关事项。派发前出现以下任一情形必须继续拆分：预计超过四小时；包含多个独立 owner、写权或生命周期转移；存在两个以上可以分别失败的未知或根因假设；需要彼此独立的验证闭包；跨越 A 项或 A5 领域边界；无法说清四小时内可到达的安全交接点。
5. 执行开始后不得无界探索。到达约四小时仍未满足完成条件时，必须在当前可构建、可运行且单一真相成立的安全检查点停止，记录已完成事实、未完成闭包、失败路径、有效证据和唯一下一步并反馈协调者；连续两条实质技术路径失败、影响面显著超出派发基线、出现未预期跨领域依赖或原任务假设被反证时，应提前触发同样的止损。唯一例外是已经启动、输入已冻结且没有安全中断点的单次确定性验证，可以等待该命令结束，但结束后不得顺带继续新工作。
6. 为控制颗粒度允许使用有明确退场点的最短单向适配，把同一责任迁移拆成相邻工作包；每个中间包仍必须只有一个事实源、一个写入口和可发布状态，禁止双写、双权威或半条不可运行生产链。工作包必须登记临时桥的唯一退场包，桥未删除前不得勾选对应 A 项或领域行；协调者应优先连续派发该责任链，不让临时结构长期存在。
7. 协调者派发前必须在第九节登记活跃工作包、派发基线和安全交接点。工作包只在真实完成、安全止损、出现必须决策的阻塞或用户询问时反馈；不得按分钟汇报或把局部测试进度冒充整体进度。协调者收到反馈后必须先独立复核，再更新当前接受基线、活跃/下一责任链、临时桥、失效证据和阻塞，随后决定提交、纠正或下一包；不能因执行时间尚短而跳过验收，也不能因执行时间已长而放宽边界。

## 六、实施约束

1. **行为等价优先。** 每次迁移只改变责任和依赖，不改变产品语义、默认值、错误、终态、持久化与恢复。确需改变公开行为或数据合同必须另行取得用户授权。
2. **一个时刻只有一个真相。** 允许为了安全拆包保留最短单向适配，但禁止双写、双权威、双状态机、双业务协议和无期限兼容；新路径接管后在同一工作包或预先登记的紧邻工作包删除旧入口，未退场前对应阶段不得完成。
3. **先边界，后搬迁。** 优先在现有目录用可见性、subpath、端口和依赖门禁形成责任；只有独立消费者、发布、生命周期、故障隔离或复用事实证明必要时才拆包。
4. **不制造新上帝对象。** Product API Catalog 不重定义领域；ApplicationHost 不编排用例；Correctness Substrate 不认识业务字段；Intelligence Kernel 不持有产品事实；`core` 不继续吸收新产品实现。
5. **静态、类型化、可追踪。** 初始生产图不用任意字符串注册、全局单例、可变 lazy ref 或运行期服务定位隐藏必需依赖；动态插件化不是本任务目标。
6. **产品复杂度不外泄。** 普通用户不需要理解 Host、Kernel、Owner、Mesh、设备角色或协议拓扑，不承担组装核心流程和维护系统正确性的责任。
7. **数据与安全不降级。** 内部格式如需迁移，必须提供有界、可恢复、单向且无双写的升级路径；权限、确认、秘密、资源、沙箱/执行边界和 fail-closed 语义不得为了解耦而放宽。
8. **不以架构名义补能力。** 迁移过程中禁止恢复 Memory、引入未来对象、扩展插件面、增加诊断/benchmark/遥测框架或实施与当前责任转移无关的重构。
9. **不阻断首版交付。** 每个中间检查点必须可构建、可运行、可发布；若迁移与首版问题冲突，先保持首版基线，架构任务停在安全检查点。

## 七、验证策略

执行任何验证前必须读取 [《跨单元验证运行手册》](../../research/design/workbench/verification-runbook.md)，遵守当前 Windows 低资源机器的串行、一次取证、失效闭包和上游先构建规则。

1. **渐进验证：** 工作包先跑能识别本次责任变化的最窄静态门禁、直接测试和受影响包构建；上游源码改变后先生成新 `dist` 再测下游。失败先归因，只重跑失效闭包，不并发运行构建、类型检查或重型测试。
2. **依赖与公共面：** 用可执行门禁证明包和关键源码目录无环，禁止依赖不可绕过；Kernel、领域、Correctness 与 binding 的公共 API 有预算，无根 barrel、内部对象或旧 subpath 旁路。
3. **合同与事实所有权：** 每项 Command/Query/Event 只由对应领域定义；每项事实的写入口、Reducer、Authority 与恢复路径 exact-set 唯一，Catalog、Server、CLI、Channel 和基础设施不能成为旁路写入者。
4. **多表面与 Host：** 进程内、RPC、CLI 和 Channel 命中同一应用用例并保持等价行为；依赖先启动、入口最后开放，拒新后排空，资源逆序释放，故障注入无 listener、timer、child process、连接或临时残留。
5. **Kernel 与正确性链：** 全部现有运行形态通过 Run Envelope / Event / Terminal Conformance；有外部后果的动作不能绕过领域决定、权威提交、安全/确认/资源准入、效果结算和恢复。
6. **拓扑透明：** 同一应用和 Kernel 合同可绑定本机或分布式适配器；领域、模型消息和 Surface 没有物理拓扑分支，设备管理与执行拓扑的测试分别具有识别力。
7. **产品回归：** A0 冻结的全部正式行为、协议、数据、异常终态和首版旅程按受影响闭包持续验证；CLI/REPL、RPC、Event、工具/Profile、配置 schema、持久记录族和包导出的 exact-set 必须能识别未授权增删或语义漂移。不得用改 snapshot、放宽超时/业务断言、增加豁免、删除保护性测试或 mock 命中代替生产路径。
8. **最终同基线门禁：** A0～A6 完成后冻结交付物，先以 `pnpm build` 生成当前源码对应的完整产物，再串行执行架构新增门禁、`pnpm contracts:typecheck`、`pnpm contracts:lint`、`pnpm runtime:baseline`、`pnpm runtime:package-exports`、根级 `pnpm lint`、`pnpm test` 和 canonical `pnpm package:check`。复用本轮机器结果和产物，不为了收集日志重复全测；纯观测或 benchmark 不得成为同步退出门。

## 八、最终退出门

只有以下条件在同一未修改产品基线上全部成立，技术工作才算完成：

- [ ] A0～A7 全部为 `[x]`，A5 当前登记表中的全部领域/管理责任均为 `[x]`，执行记录与当前工作区事实一致。
- [ ] AE-001 的核心命题和全部架构不变量均有生产实现、依赖或合同门禁及直接回归的可追溯证据，不存在只落实名称或目录的条款。
- [ ] 每个生产进程只有一个 ApplicationHost 组合根；配置/秘密来源归专责 Provider，Host 只消费最小只读投影且不持有领域事实、不编排产品用例、不提供运行期服务定位，启动、换代、排空和关闭无资源残留。
- [ ] 每项产品合同、应用用例、规则、事实、写入权威和恢复路径归属唯一领域；Product API Catalog 只组合，所有 Surface/Transport 只绑定和呈现。
- [ ] Fact Event 与 Progress Event 语义分离；投影、缓存、摘要、协议响应和 UI 状态不能成为事实源，跨领域同步依赖无环。
- [ ] Intelligence Kernel 只依赖模型、工具和运行合同，不导入产品领域、Surface、RPC 或设备拓扑；现有全部运行形态通过同一 Conformance Suite。
- [ ] Correctness Substrate 只提供通用提交、效果、安全、确认、资源、持久化与恢复机制，不拥有领域规则；任何领域也没有重造这些机制。
- [ ] Device Administration 与 Executor/Mesh 拓扑事实彻底分离；单机和分布式只在 Host 适配选择处分叉，distributed-runtime 没有成为产品或架构中心。
- [ ] CLI 不再是生产后端，Server 不再是应用服务定位器；不存在第二组合根、旧业务写入口、双权威、双状态机、永久兼容桥、根 barrel 旁路、可变 lazy ref 或等价改名残余。
- [ ] A0 七类基线在第九节均有当前证据引用且没有未分类生产角色、公开行为、状态、写入口或消费链；CLI/REPL、RPC、Event、工具/Profile、配置 schema、持久记录族、包导出和制品入口 exact-set 无未授权漂移。
- [ ] 当前全部正式能力、数据、权限、安全、异常终态、恢复、单机/分布式行为和首版产品旅程无回退，用户没有新增架构学习与维护负担。
- [ ] 包依赖、公共 API、合同所有权、事实 exact-set、Host 生命周期、Kernel、Authority/Effect、拓扑透明和变化影响面门禁全部通过且能真实识别反向错误。
- [ ] contracts typecheck/lint、runtime baseline/exports、根级 lint/test/build 和 canonical package check 均在最终同一基线上通过；Windows x64 tarball 使用正式制品验证，无旧 `dist`、workspace 源码或 mock 替代。
- [ ] 正式架构、模块索引和必要工程文档与生产事实一致；任务没有把能力增强、未来记忆、插件平台或范围外重构写成已交付结果。
- [ ] A7 六面对抗具有实际动作、证据和结论，未发现未处置 P0/P1、资源残留或可推翻完成结论的反证。

满足后将本文状态更新为“待用户确认”，保留全部状态与证据并停止。未经用户确认不得把任务标记为“已完成”，不得继续完善架构、增加能力、暂存、提交、推送或发布。

### A7 六面对抗

1. **产品行为攻击：** 从不了解迁移的用户视角走查 A0 冻结的所有正式入口、异常与恢复，至少覆盖对话/历史、工作场景、调度、推进、多视角、任务列表/编排、投递、信任、技能、设备、恢复备份/灾难恢复、配置/MCP 和维护/卸载，主动寻找内部术语外泄、行为漂移、错误/终态改变、exact-set 漂移和多表面不一致。
2. **合同与所有权攻击：** 抛开任务勾选，从生产入口重新枚举 Command/Query/Event、事实、写入口、Reducer、Authority 和恢复路径，寻找中央业务模型、重叠 owner、旁路写入、事件冒充事实和跨域环。
3. **Host 与依赖攻击：** 从每个进程入口重新追踪创建、启动、开放、换代、排空与关闭，注入分阶段失败，寻找第二组合根、隐藏顺序、服务定位、反向依赖和资源泄漏。
4. **Kernel 与效果攻击：** 沿真实模型—工具调用攻击领域渗透、内部对象泄漏、取消/失败/未知终态、权限/确认/资源绕过及本机/远端结果不一致。
5. **拓扑、表面与制品攻击：** 对照进程内/RPC/CLI/Channel、单机/分布式与 Windows tarball，证明测试没有只命中 mock、旧 `dist`、workspace 源码、错误组合根或非正式入口。
6. **残留、变化影响面与范围攻击：** 反查旧入口、桥、别名、根导出、lazy ref、双轨和临时兼容；再只在隔离临时副本或门禁自带的负向 fixture 中实施最小反向变异，分别尝试让新增 Surface、Provider、设备拓扑或领域穿透其允许轴，证明变化影响面门禁能识别跨轴修改，不得改动冻结交付物或把变异内容带回工作区；同时确认迁移没有夹带新能力、Memory/OWNWARD 决策、动态插件框架或其他范围外结构。

任一对抗面发现真实问题，立即恢复对应 A 项、领域行和受影响退出门为 `[ ]`，状态退回“执行中”；任何交付物修改都会使本轮完整对抗失效。修复并重取失效门禁后，必须在新的同一未修改基线上重新执行全部六面，直至没有未处置反证。
