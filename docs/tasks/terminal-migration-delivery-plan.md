## 一、已确认的方案

**保留现有主架构和产品契约，不插入独立的单机/跨端解耦项目，不替换存储引擎；完成仍成立的有界状态、恢复和终端功能体验缺口。**

必须守住用户的顶层要求：架构面向未来、品质优秀；用户用得简单、便捷，不承担内部复杂度；既有单机与跨端功能及体验不降低。普通启动、打开会话、首发准备不能反复处理全部累计历史；冷启动同条件中位数约5～7秒，允许波动。性能、功能、安全、耐久及终端与核心解耦必须同时成立。

本次长期收尾中，能够明确识别的工作主要涉及原有全量历史重放/物化的读取与恢复结构迁移；跨端相关责任是其中一部分，重复验证、错误归因、方案返工和接力又增加了成本。尚无完整工时分解，不把这一判断伪装成精确比例，也不以提交触及包数证明跨端是普通迭代的主要放大源。

选择当前路线，是因为独立解耦的额外净收益尚未得到足够证明，而激活、迁移和双路径维护成本明确存在；现有领域端口和持久索引可以承接已确认的改进。这仍包含查询、状态及恢复边界的架构修复，不是只改流程，也不是认定现架构完美。

共同责任、信任域责任、拓扑适配作为责任检查框架，不新建三套平台，不按机器数量或字段名删除本机仍需的权限、票据、代际隔离、资源准入与恢复。跨端功能及其验收义务完整保留；是否已做真机验证不作为架构方向选择依据。

**重开条件：** 实际普通需求被证实必须穿透不相关领域，或当前结构不能满足增长/体验要求时，按具体证据重开对应关键边界。普通实现问题自行闭环，不因每个困难重新讨论整套架构。

### 关键执行边界

- 允许为有界读取必需的异步精确授权：Promise不能当true，决定完成前不放行；真实拒绝与暂时准备/容量不足区分，取消可退出。受影响握手与服务派发调用方一起闭合，不另建泛化鉴权平台。
- 旧home兼容复用和转换优先，只有真正新增/不兼容投影才初建。初建随所属包验证，读取量/耗时单列、诚实反馈、可中断续做、普通二开有界；普通升级不冒充灾备。
- 真正一次性初建没有另定秒数上限，也不接受任意长等待。先优化复用、转换和交互；若仍须明显等待，带必要性、实测耗时与可行方案交用户具体取舍，不先问抽象阈值阻塞工作。
- E29先核对实际控制读取、执行端及容量准入闭包；probe-unavailable可能只是catch的错误分类，不能单凭字符串把探测过期当已证根因。为关闭E29必需的责任随1a完成，其余仍由原包负责。
- 大历史集合退出标量checkpoint、保存/停止成本随领域包处理，不留到末尾；当前必要活跃工作集与已结束历史分别计量。

## 四、共同完成门与成本控制

- **普通与升级分开**：现有索引复用/兼容转换、新索引初建、损坏修复分别记录。新二进制不等于全部新索引；不因版本号变化机械全库重建。
- **增长责任在本包关闭**：固定当前选择/活跃量/内容预算，增加已完成历史；有界读取、物化与保存/停止成本都要有依据。只对受影响增长机制做规模证明，不要求纯接线/UI包也全套做。
- **性能持续观察**：每个影响启动的后端包复用真实旅程取得可比冷启/常驻Host热启样本及阶段账；不固定复制3～5次，按可疑回退/判断不清再扩样。各包允许保留后续负责的明确成本，但不得丢失归属；7承接整链成本。
- **样本可比且不丢证据**：样本标明真实构建身份，版本对照保持夹具/配置可比，不与构建测试争抢资源；同版中位数不混构建。无钩子样本用于体验与验收统计，诊断插桩数据单独列账用于定位，不能混入达标中位数，也不能删除慢样本。
- **验收后的代码回退点**：每包验收后形成可审查、可按提交规范独立保存的成果；已有明确Git授权则依授权执行，没有授权则保留并交用户决定，不自动stage/commit/push，也不重复索要已获授权。不机械一任务包一提交，不新增逐包必停审批。代码回退点不等于承诺用户数据可降级。
- **变更必须随责任包收口**：每包交付时列明本包文件/变更块、验收状态与可提交范围；不能只关闭问题名称，却留下无法独立提交的半成品。跨包依赖须明确承接，当前包仍要构成完整终态。最终交付前核对全部范围内产品变更，不能留下归属不明、未完成或验收未通过的产品代码。“可提交但尚未获Git授权”与“不能提交”必须区分。文档按内容价值处置：长期有价值的需求、决策、根因、方案及未完成责任归入正式文档随成果提交；重复聊天、过时交接和无价值临时内容删除，不继续留下既不提交也不清理的资料。
- **每包自审后集中构建验证**：修改上游按现有要求全量构建，随后确认实际入口产物；不每个小改动构建，不在总控审查时继续改候选。
- **独立且完整**：总控审查覆盖全部义务与交界，复用未失效的既有测试，独立执行必要反例和用户路径；不以抽查代替完整责任，不机械复跑全部命令。
- **功能与运行形态**：相关运行/assignment、生命周期/授权及权限/安装边界在所属包完成本机/mesh等价与相应故障回归；真实用户路径依既有终端交付边界执行。跨端未验收不作为方向依据；缺少其他物理设备不新增当前模块阻塞，不能据此声称已实测。产品发布的其他平台/跨端真机与npm流程仍归既有发布计划。
- **停止条件**：范围内已知可达问题闭合，必要验证及当前性能/增长要求成立，总控整轮验收通过即结束；不继续为未来假设增强。没有证据的旧疑虑区分为未知，不冒充现存缺陷，也不冒充已经通过。

### 已验收增长约束的持续保持（强制）

依据用户2026-10-17明确要求：先彻底消除累计信息增长造成的准备放大，允许随后继续优化固定开销，但不能在两类问题之间反复折返。本规则适用于后续所有相关任务包及包7的整链优化。

1. **关闭后成为后续约束。** 每个增长机制验收关闭时，记录已关闭范围、有界条件及对应证据。后续修改必须保持这些约束；尚未处理的领域继续按既定任务包闭合，不把局部通过写成全部增长问题已经解决。
2. **优化不得重新引入历史依赖。** 后续可以优化装配、重复操作、等待和必要读取，不能重新引入全部累计历史的扫描、重放、物化或整份缓存加载，也不能将其转移到打开会话、首次发送、运行控制或保存/退出。功能、体验、安全与耐久义务同时保持。
3. **回归由引入它的整轮负责修复。** 修改触及已关闭机制时，工程师须在整轮集中验证中复用其回归用例和工作量对照，必要时补反例；总控独立核验。发现增长约束被破坏，该轮不得验收通过，必须修复并复验，不能留到以后重新立项。新证据推翻旧结论时须如实更正，不能以曾经通过掩盖缺陷。
4. **验证成比例，不制造重复劳动。** 固定当前配置、活跃量和内容预算，增加已结束历史，核对受影响路径的读取、物化及保存工作量；没有影响的有效证据继续复用。不为每个小改动全量构建或重复完整性能批次，不以耗时偶然较快替代增长证明。
5. **同一版本同时交付两项目标。** 增长改造后的阶段版本可以继续收敛固定耗时，但已关闭的增长约束持续有效。最终同一候选必须同时满足增长约束、冷启动同条件中位数约5～7秒（允许波动）及完整功能体验；旧版本的达标成绩不能替代新版本验收。工程师提供证据，总控据此放行。

## 五、角色、交接与终点

- **总控：** 把控宏观进度；负责架构设计、任务安排、整轮代码审查、问题汇总交付及最终验收。
- **工程师：** 负责执行，在已确认边界内思考实现方案，完成整轮实现、自审、集中构建与验证；对总控负责，只联系总控，不自行协调其他角色。
- **智能体架构师：** 与总控平级贡献独立判断，参与关键决策、关键选择、架构选择、关键问题分析及执行路线与任务拆分的把关；不承担普通实现细节。

**凡属关键事项，总控必须让智能体架构师参与。** 不仅限于推翻既有方案或重大变更，也不能因额度、成本或沟通次数跳过。总控仍须独立分析，双方按事实与需求共同得到最优解，不为一致而妥协，不把对方当作确认者；既定边界内的普通细节由总控与工程师闭合。

总控与工程师严格串行：整轮实现交回→总控独立完整审查→集中交付问题→整轮返修与复审，不并行改动候选。工程师只对接总控：Codex工程师使用既有原生会话通道，外部工程师使用已登记通信桥；执行者以用户最新指定为准。总控与智能体架构师继续沿用已接受的手动通信协议。

终点是整个终端迁移按既有需求可交付，而非只完成某个索引、某个启动样本或计划表。达到范围内完成门后结束，不追加未来功能与无依据增强。
