# 外部 APP 自主接入

> **当前状态（2026-09-22）**：宏观审查及本机实测发现的代码、文档问题已修复，原飞书账号的新制品通过真实连接、双向收发和本人确认。经用户授权复用 OpenCode 中的 DeepSeek 凭据后，在线模型生成／修正适配源码及受管运行样例已补验。本轮工程修复可提交；模型样例的人工反馈、驱动职责和未覆盖范围见第五节，不把有限样例写成任意平台的自主交付保证。

## 一、需求梳理

知行保留连接外部 APP 的通用能力，将具体平台适配从主产品中独立出去，以让用户在常用 APP 中更省心地使用同一个知行为目标，必须提升接入和持续使用体验，既有功能、交互、可靠性与安全性不得退化，绝不能以减少开发维护工作为由牺牲用户体验。用户正常使用已发布的知行时，只需说明想连接哪个 APP，由知行自主完成连接包的获取或准备、配置与接入，用户仅参与确实无法代办的登录、授权、凭据填写等必要账号或平台操作，无须理解技术细节。适配外置只是手段，知行仍须完成真实双向收发验证并承担后续连接维护，自动处理重启、断线等可恢复问题；受阻时明确告知状态、原因及可行下一步，不把找包、修包、升级和兼容处理转嫁给用户，也不把一次连通视为长期可靠。接入能力以平台开放条件、账号权限和实际验证为准，没有成熟连接包时可以自主准备，但未经验证不能宣告可用，无法可靠接入时应如实说明限制并在有可行替代方式时提供选择，不承诺任意 APP 都能接通。该能力遵循核心封闭、边缘可扩展的架构理念，复用统一的会话、执行与安全机制，会话事实、权限、投递终态和恢复责任仍由核心承担，用户不承担组装系统或维护系统正确性的责任。

## 二、产品设计

**知行交付稳定的核心与可持续扩展的能力。用户提出需要，知行负责让外部能力接得上、用得住、坏了能修，而不是让用户寻找和维护插件。**

接入、运行、更新、停用与恢复由共用底座承接；具体平台和场景的实现独立于主产品，由知行按需获取、准备和维护。外置的是具体实现，不是可靠性与安全责任；核心不交给扩展或模型任意改写。本次交付这一共用基础，以外部 APP 接入作为首个完整应用，其他能力不在本次交付范围。

1. **说出意图，交付可用能力。** 用户说“以后在飞书里找你”，知行查证接入方式，获取现成适配或自行准备，完成配置与实际双向收发验证，不以主产品是否预装该平台为边界。只澄清影响结果的账号或用途歧义，完成后直接告知使用入口，不把安装成功当作交付。
2. **必要配合，一次说清。** 登录、扫码、授权或凭据填写需要本人操作时，提供直接入口和清晰指引；凭据在安全界面填写，不进入对话。准备期间用户可以继续其他事情，原对话结束或知行重启后仍能接续；本人操作完成后自动继续，不要求重述需求或逐步催促。
3. **扩展能力，不另建助手。** 新 APP 仍连接同一个知行，用户可以交办事情、接收结果并完成必要确认，已有账号绑定、对话和任务不因接入或换版而重建。接入后的能力持续可用，不依赖发起接入的对话存活；用户可用自然语言查询或停用，主动停用后不得自行重新启用。
4. **日常维护安静完成。** 知行主动发现连接异常并尝试恢复，能自行解决就不打扰用户。无法恢复且影响使用时，在用户仍可访问的知行入口说明影响、处理进展及必要配合，不只向已失效的渠道发送通知；恢复以实际可用为准，不以重试或重启成功为准。
5. **一句报障，负责修到可用。** 用户说“飞书收不到消息了”，知行接手定位、修复和收发验证，必要时自行修正适配；已有信息自行获取，不让用户找日志、改配置或重装连接包。只有缺少用户才能提供的现象或必须本人操作时才询问；修复不得擅自更换账号、扩大授权、增加功能或清除历史，结束时明确告知已恢复，或尚未恢复的原因与下一步。
6. **独立更新，不打断整个知行。** 用户说“更新飞书连接”，知行自行检查兼容性、准备新版本、完成切换并验证可用，保留配置与使用习惯；失败时恢复上一可用版本，不能损坏已有数据。在核心兼容范围内，无须升级或重启整个知行，切换只影响目标能力并尽量缩短其中断，不打断其他连接和任务。主动升级由用户决定，日常故障的自主修复不以用户提出升级请求为前提。

## 三、架构设计

### 3.1 封闭核心，共用扩展底座

沿用[核心架构](../../research/design/architecture/overview.md)及 [AE-001](../../research/design/architecture/evolutions/AE-001-companion-intelligence.md)的领域所有权、薄内核与唯一组合根。**核心固定装配扩展管理、受管运行组件和能力类型绑定；外部实现通过这些稳定入口动态接入。共用的是扩展生命周期，不是所有能力的业务语义。**

扩展管理决定接入与换版，运行组件执行已提交决定，能力类型定义怎样工作、交接和验证；外部实现承接具体平台差异。核心的事实、权限、资源、恢复与终态不可被扩展替换，Host 不成为运行期服务定位器，Kernel 不增加渠道或插件管理分支。

本次交付共用底座与 Channel 首个完整实现。已支持类型内的兼容扩展可在发布后独立接入、修复与换版；新增 APP 不修改主产品的平台登记。未来新增能力类型，由核心中的需求方补齐类型合同与消费绑定，复用管理生命周期；新的业务语义仍归该领域，不塞入通用底座。外部包不能自行扩张核心接口，数据更新也不必包装成代码插件。以下是目标设计，不代表现有实现。

### 3.2 一套管理事实，各自拥有业务

| 责任 | 唯一所有者 |
|---|---|
| 扩展管理领域 | 拥有扩展实例身份、启用意图、候选与生效版本绑定、操作及恢复检查点；通过固定的 Product API 提供准备、接入、查询、更新、修复和停用，模型工具与界面共用同一应用 |
| 受管扩展运行组件 | 管理制品落位、执行环境、进程及资源作用域，执行启停、换代和有限故障恢复；状态与回执是观察证据，不是第二份管理事实 |
| 能力类型绑定 | 由核心中该能力的需求方提供业务合同、配置校验、交接条件及可用性验证；本次 Channel 桥连接既有 Conversation、Delivery 和确认入口，不另建渠道安装、版本或修复状态机 |
| 外部扩展 | 按声明实现对应类型协议，只获得必要的配置、凭据和受控入口；不取得核心内部对象、任意服务查找或 Product API 注册权 |

管理领域复用既有 Authority、Commit、Run、安全及恢复端口，不自建日志、权限或调度系统。Host 只装配与关闭这些组件，零扩展时仍保留管理入口。扩展身份与包、版本和运行代际分离；同一制品可被多个实例引用，更新一个实例不改变其他实例的版本。

Configuration／Secret Provider 继续拥有配置来源和秘密；管理领域只持与候选匹配的配置修订、凭据引用及代际。分别保存后，二者均匹配才允许激活，部分保存不覆盖旧生效绑定。运行组件只取得目标实例的不可变投影，局部刷新不依赖过期启动快照，也不重启整个 Host；原配置入口不得绕过管理应用双写生效状态。秘密仅在目标设备安全入口录入，不进入模型、扩展包或跨设备迁移。

### 3.3 管理协议统一，业务接口按类型定义

扩展声明分两部分：**共同部分**描述扩展标识、固定版本与摘要、运行环境、入口、管理协议版本及所实现的能力类型／合同版本；**类型部分**描述该类型允许的配置、凭据字段与能力。Channel 的收发、确认、重投和幂等属于类型部分，不进入通用管理状态机。字段声明驱动安全录入与配置界面，schema、兼容规则与业务语义由核心校验，扩展不能自行声明已获授权。

运行组件处理共同的启动握手、状态、停止和资源释放；类型绑定提供配置与能力检查、消费连接、交接及实际验证。协议版本不兼容时在启用前拒绝，不猜测兼容。类型绑定是核心的有限、类型化贡献，不是外部包注册任意回调；新版本仍须满足已有消费者所需能力。

本次外部可执行适配使用独立受管进程，经版本化协议连接类型桥；每个运行代际拥有自己的进程、定时器、连接及路由，停用、换版失败和宿主关闭均可完整释放。HTTP 回调按实例与代际绑定，过期进程不得重新注册或产生新的有效输入。进程隔离用于故障与生命周期管理，不冒充安全沙箱；安装、构建及运行仍经过既有安全与确认链。

制品、依赖与必要运行环境按固定版本保存，自主编写适配的源码与构建说明随版本保留，供后续修复使用。候选在独立位置准备，不原地覆盖生效目录或修改主产品依赖。系统承担环境准备，用户不编译安装；摘要校验不替代来源与执行准入。回退和重启复用已保存制品，不重新解析浮动依赖。

### 3.4 发布后自主准备、接入与使用

正式安装产物提供与当前支持版本匹配的扩展合同、声明 schema、适配编写指引和本地校验入口；不要求取得知行源码才能制作扩展。中文内置技能按需引导模型读取这些资料并使用统一管理工具，不把平台教程或开发手册塞入常驻提示词。

管理应用先耐久接纳请求，再通过既有有限 Run 查证来源、获取现成包或自主编写适配；第三方 SDK 不符合合同时包装为适配。获取与自主准备走相同的候选、准入、验证和激活路径。模型可以修改候选并提交证据，不能直接改生效文件或凭据，也不能用自述替代系统验证。

原请求、操作身份、目标实例、候选、等待条件与结果去向持久保存。缺少凭据时提供目标设备安全入口；录入、确认或执行完成后核对操作仍有效，再自动接续。等待释放原 Run，原对话结束或重启不丢任务；不复制 MCP 的主对话接入限制。工具接纳与最终完成分开，结果仍交付原请求。

底座负责协议与环境检查，类型绑定负责验证实际业务能力并接入原有消费者；安装成功、进程存活不等于可用。Channel 须核实本人身份、回复目标、真实双向收发和必要确认回路，再开放正常使用；需要本人配合时提供直接入口，允许同等身份校验的文本确认，不强制平台具有按钮。

### 3.5 局部热插拔与耐久恢复

接入、更新和修复复用一套管理流程：准备并检查候选，耐久提交启用／切换意图，按类型合同交接并验证，再提交生效绑定；失败则恢复旧绑定或明确受阻。安装、试运行及在线验证同样先记录操作阶段，再执行受控效果，不以“预检”为名绕过管理。操作进度与当前可用性分开，更新受阻不等于旧能力失效。

每个实例只串行提交短时决定，不持锁等待模型、网络或本人操作，停用可及时生效。异步结果按操作修订与运行代际核对后接纳；崩溃后依据已提交阶段和实际证据继续，不凭文件指针推断完成。

底座负责换代顺序、资源释放和恢复，类型绑定负责调用准入与交接：先暂停目标实例的新业务调用，已发出的调用归原代际与尝试；候选只开放验证通路，验证并提交生效后才承接正常业务。等待与重试仍由业务原责任者处理，不在底座另建业务队列。Channel 同一账号的新旧实例不得并行消费，未发送义务留在 Delivery；不能靠直接杀进程实现可靠替换。

切换不等待原业务 Run 结束或其未决确认完成，不停止其他扩展；共享制品不使其他实例隐式升级。若扩展向模型提供能力，新能力进入后续 Run 的正常投影，不改写已发放 Run 的工具与授权快照；实现换代不等于扩大运行权限。

旧制品、配置及必要恢复状态在新版本验证完成前保留；新候选不能破坏性改写旧状态。回退恢复实现与绑定，不倒退业务事实、消息水位或已发生的外部效果。迟到结果按原尝试身份交原责任者结算，不能因换代直接丢弃；未知效果不当作未执行盲目重放。旧版或原凭据也不可用时如实受阻。

扩展实例纳入既有值班所有权与恢复链，不另建分布式协调器。目标设备具备匹配制品、环境及本机凭据后才接管，旧运行代际停止接受新工作；操作可续接，秘密不随制品或权威事实转移。

### 3.6 自主维护共用入口，不另造智能体

运行组件依据进程和类型健康信号做有限退避与恢复，不用模型轮询，不把没有用户消息当作故障。自动恢复失败与用户报障进入同一管理操作，按实例合并故障，以脱敏证据启动有预算的 Run；诊断、修改候选、换版及实际验证复用前述链路，不为每种能力另造维护流程。

用户要求更新时准备新版本；自主修复只恢复既有能力，不擅自换账号、增加功能、扩大授权或清除历史。取消未完成操作不等于停用：撤销候选的后续执行与激活资格，保留或恢复原生效绑定；停用则撤销实例启用意图并关闭运行资源。两者均耐久生效，迟到的修复、录入或确认结果不能恢复已撤销的意图；缺少资源或本人操作时明确受阻，不无限唤醒。

状态与结果可从其他已有知行入口查询，必要通知交既有 Delivery；无可达入口时保留待告知结果，下次访问呈现。维护责任不因扩展外置而转给用户。

### 3.7 Channel 首个实现与既有接入承接

Channel 桥保留既有会话绑定、身份校验和控制通路。普通入站携带稳定的平台事件身份，收到 Conversation 的耐久接纳结果后才确认接收或推进消费游标；重投复用原身份，不能把 `onMessage(): void` 或适配内存去重当作耐久接管。

普通出站继续经 Delivery，发送尝试、幂等键及回执贯穿扩展协议；确认与取消不排在等待它们的 Run 或普通回复之后。签名 challenge、应答身份、投递终态及未决义务仍归原责任者，不因适配换版失效或重新创建；扩展只转换平台协议。

[固定渠道工厂](../../packages/cli/src/serve/channels.ts)由通用受管运行组件与 Channel 桥替代，[平台字段登记](../../packages/cli/src/registries/channels.ts)改为消费经校验的扩展声明。先准备并校验独立飞书制品，续接原配置、凭据引用、连接身份和交互，再清退主产品的平台实现与依赖；承接可恢复、失败保留原数据，不要求用户重新配号或重新建立助手，不保留内置／外置双主链。

复用现有 [MCP 接入](../modules/mcp/onboarding-and-management.md)中适用的发现、安全录入与接续机制，不复制其整套流程，也不把 MCP 传输当作渠道协议。本次不顺带改造其他能力类型；共用管理与运行部分不得依赖 Channel 业务字段或平台分支，渠道仅通过类型合同接入。后续能力沿同一边界复用，不再复制安装、换版和恢复系统。
