# 智能体运行时自我认知能力

> 类型：模块开发

## 一、需求与目标

智能体在运行过程中，需要对自身所处的运行时系统具备准确的自我认知（Runtime Self-Awareness）：需要一套供智能体自身掌握和使用的机制，使其能够按需了解知行系统与服务用户相关的各个层面——包括知晓系统具备的能力与调用方式、在对话报错或系统异常时开展问题定位与自诊断，以及其他服务用户所需的系统认知。这些底层细节面向智能体自身开放，目的是让智能体自主调动系统能力、排查运行问题以更好服务用户，用户既无须感知这套机制，也不必理解系统底层细节；同时这是产品内智能体运行期的能力，而非仓库开发协作者使用的工程技能。

向智能体开放自我认知具有明确的边界，绝不是将整个系统作为透明白盒或完整内部说明书全盘交给智能体：只向智能体提供服务于用户正当使用诉求所需的部分，凡不服务于用户的系统内部实现无需提供，凡越过用户合规与安全边界的系统内部内容绝不向智能体暴露。

本任务对具体的承载形态、表达方式与架构形式不设前置限制（不局限于内置技能）。需要先核查清楚知行当前是否已具备这类自我认知或相近机制及其实际边界，并研究业界一流智能体的成熟实践与边界取舍；最终以宏观[愿景](../vision.md)和[架构演进方向](../architecture/evolution-direction.md)作为唯一顶层指引与硬性标准，围绕本需求倒推、审视[现行核心架构](../architecture/overview.md)相关部分，系统设计适合知行的架构能力、暴露边界、承载机制与产品体验。

## 二、系统现状

### 2.1 审查标准

> **现状梳理审查标准（定稿）**
>
> 1. **范围完整，定性准确。** 完整覆盖知行作为智能体运行的各实际路径（交互主对话、后台与跨会话运行、子 Agent 等）中，除用户原始消息外一切由系统提供并送入模型的内容——包括完整的系统提示词、用户消息内的无感知动态插入、消息序列中系统构造或包装的非用户内容（含恢复/摘要消息、工具结果外层系统包装及按需加载入流的内置技能正文等），以及承载知行自身机制或自诊断说明的相关工具提示（常规基础工具的普通参数定义与单一窄用途的内部辅助模型调用仅划清边界、不混同展开，但其产物若进入智能体输入仍纳入核查）。按实际来源而非消息角色区分用户输入与系统注入，不把仓库协作者技能或未实现文档混作产品运行时能力；明确整体现状定性及这一构成要素所提供的自身相关信息，绝不将现有提示注入等同于完整的运行时自我认知体系。
> 2. **构成、职责与生效机制讲透。** 逐类说清供给模块、职责性质，以及实际送达模型的具体传达要点、标签/结构形态与体量或重复情况（不以空泛类别标签代替实质内容）；同时分别查清内容何时生成或加载、保存在哪一层视图或存储中（如当次发送视图、当前运行内消息、跨运行注意力窗口或仅留存历史记录），以及后续哪些模型请求仍会实际携带它。客观呈现各运行路径间的异同及其中与运行时自我认知相关的内容与空白，不在现状梳理中越界预写后续精简或迁移的设计方案。
> 3. **证据扎实，核心无盲区。** 关键判断均须有明确版本的生产源码支撑，从内容定义、宿主与上下文装配一路核对至最终发往模型的请求载荷（涉及跨轮或后续请求可见性的判断，须核对相应后续请求的最终输入），不凭孤立模板常量、未接线代码或文档描述推定现状；生产调用链足以判定的可直接举证，存在条件分支或运行期裁剪、折叠难以仅靠静态读码判明的表现，须有对应条件下的实测或调用链验证佐证；认定某项内容缺失或受限时，须写明已核查的范围与依据，不留“待核实”空白。
> 4. **结构清晰，精炼自足。** 围绕模型输入层级、智能体运行路径与内容职责组织正文，提炼关键结构与必要例证以辨明实际差异；不按源码目录堆砌流水账，不整段照贴冗长提示词原文，也不混入与模型提示输入无关的底层实现细节。表述准确凝练、独立自足，读者无须回翻源码即可仅凭正文零歧义掌握知行当前的真实状况。
>
> 以上四项须同时满足，共同构成现状梳理的优秀通过标准；有充分依据确认相关内容缺失或受限，同样符合本标准。

### 2.2 现状正文

#### 现状总览

以下结论基于 `develop@8886b384` 的生产源码，以及隔离环境下的运行体装配验证与构建版 CLI / 宿主实际出站请求捕获。

在本次核查的产品运行期输入链中，知行**尚未建立**独立的“智能体运行时自我认知能力”概念、统一知识模型或跨领域自诊断入口。原系统中实际落地的，是该能力体系下的**一个局部基础构成要素**：除用户原始输入外，由宿主、上下文管理、执行循环与工具层组装并送往模型的系统提示词、消息序列动态注入与机制类工具说明。这一提示注入支线分布在角色画像、工具声明、技能索引与按需正文、运行上下文及系统生成的续接消息中，已在局部向智能体告知身份原则、当前可用工具与专项管理流程（如受管扩展开发包指引、跨对话通信方法、运行日志查询工具等），但它仅是运行时自我认知体系的一小部分构成因素，不能等同于完整的运行时自我认知体系。

核查范围按实际执行性质划分为三类边界：
- **智能体运行路径（本文核查主体）：** 涵盖主控（Anchor）主对话（`main` 角色，覆盖交互、RPC、受管通道与跨会话来信；另有工作场景回退用的隔离支持会话 `isolated`）、工作场景对话（`power` 角色 / `work` 技能模式）、耐久定时与后台智能体作业（`job`，以 `runtimeKind: "ephemeral"` 单次运行装配；区别于仅供内部 `llm.complete` 复用的管理用 ephemeral 运行体）、非主控远端执行器运行（`ExecutorRuntimeSubstrate`，含设备本机对话 `local-*`），以及 `Task` 子 Agent 与多视角评议等声明式编排节点（`runOrchestrationV1`）。
- **内部窄用途辅助模型调用（划清边界，仅追踪回流至智能体输入的产物）：** ① 段切换摘要器（`roles.light`）**沿用当前运行体的 `systemPrompt` 与 `tools`**，对不含发送前缀与逐次时钟的可摘要 `state.messages` 追加 `<summarize-instruction>` 生成摘要，产物以 `compact-summary` 回流后续注意力窗口；② 任务推进独立裁判（`DefaultAdvancementRuntime`）使用专用裁判 `systemPrompt`、单一 `advancement_submit_review` 工具及拼入用户原任务、已确认 Rubric、本轮执行摘要、既往评审窗口与独立证据的审查消息，其 `failed` 结论经模板拼装为代理消息回流执行对话；③ 对话自动命名、Rubric 起草/修订、`web_fetch` 页面蒸馏（`roles.light`）、`admit_skill` 独立安全审查（`callText("main")`）、AI 安全管家（`consultSteward`）、多视角分配（`buildAllocationPrompt`）、工作场景创建辅助与 MCP 接入推断各自使用专一提示词或有界 JSON 工具循环，其中网页蒸馏、技能审查与安全管家结论仅在触发时经对应 `tool_result` 回流当次运行。
- **非产品运行时资产（明确排除）：** 仓库中的 `.agents/skills/*`、`AGENTS.md`、`collab/` 及未实现的设计文档仅供仓库开发协作者使用，不进入知行产品运行期模型请求。

#### 1. 系统提示词（`systemPrompt`）构成、路径差异与出站表现

`buildSystemPrompt` 按固定槽位顺序输出 **`静态段序列（非 null 段以 \n\n 连接） + 字面分隔符（\n__ZHIXING_CACHE_BOUNDARY__\n） + ## Environment 动态段`**。体量随角色画像、授权工作区及实际挂载工具变化：在构建版真实 CLI 无工作区回环样本中，主对话（20 个工具）出站 `system` 为 6,100 UTF-8 字节（3,628 Unicode 字符），新建工作场景（21 个工具）为 5,861 字节，`Task` 子 Agent（3 个工具）为 2,997 字节；在挂载主控有工作区标准会话工具集（27 个工具）的合成运行体样本中，主对话 `systemPrompt` 为 4,070 Unicode 字符（约 6.6 KB UTF-8，随工作区路径与宿主环境字符串微幅浮动）。

- **三维生命周期与协议出站映射：**
  1. **何时生成或重建：** 会话运行体维护实例级 `authoritativePrompt` 与单次运行级 `localPrompt` 双层持有。运行体首启（`instance-start`）、`run` 内自动段切换（`segment-transition`，含首轮调用前 `runTurnBegin` 与每轮结束后 `runTurnEnd`）以及 `run` 外维护换窗（`/clear`、`/resume`、手动 `/compact`）均触发窗口换代重建；此外，新窗口的首个 `run` 若携带 `globalQuery` 且投影出更高 `windowPrompt.revision`，会在首轮调用前同步刷新一次 `skill-index` 段。同一窗口其余模型调用严格逐字节复用。子 Agent 在 `runChildAgent` 入口构造一次，子运行全程不变。
  2. **保存在哪一层：** 仅保存在当前运行体内存持有槽中，不写入 `LoopState.messages`、`AttentionWindow` 或持久 `Transcript`。
  3. **后续请求可见性与四协议线上载荷：** 同一窗口后续每次主循环请求及段切换摘要请求均完整携带。四个 Provider 适配器的线上映射分别为：`anthropic-messages` 置于顶层 `system: [{ type: "text", text, cache_control: { type: "ephemeral" } }]`；`openai-compatible` 插入为 `messages` 首项 `{ role: "system", content }`；`openai-responses` 按型号匹配器对 GPT-6.2 及更新代际前置为 `input[0]` 的 `{ type: "message", role: "developer", content }`，对较早型号置于顶层 `instructions`；`google-interactions` 置于顶层 `system_instruction`。**四个适配器均不解析或剥离 `\n__ZHIXING_CACHE_BOUNDARY__\n`**，出站载荷中均原样包含该字面分隔符。

#### 2. 消息序列（`messages`）中的系统动态注入与非用户内容

内核 `Message.role` 仅包含 `"user"` 与 `"assistant"`。进入 `ChatRequest.messages` 的非用户系统内容按从前到后的组装层级分为五类，各自具有不同的生成时机、存储归宿与跨轮留存表现：

**（1）窗口级前置消息对：`ZHIXING.md` 分层工作约定（`contributeMessagePrefix`）**

- **供给模块与实质内容：** `createZhixingGuidanceLifecycle` 与 `loadLayeredGuidance` 读取全局 `ZHIXING_HOME/ZHIXING.md`（渲染 `# 全局约定`、`scope: global`、`source: ZHIXING_HOME/ZHIXING.md` 及文件正文），并在绑定了工作目录解析器的工作场景运行体中继续读取 `workdir/ZHIXING.md`（`# 工作场景约定`、`scope: workscene`、`source: workdir/ZHIXING.md`），由 `buildGuidanceMessagePair` 封装为 `user`: `<system-meta kind="guidance">...</system-meta>` 与 `assistant`: `<system-meta kind="ack">已阅读约定</system-meta>`。`readGuidanceFile` 仅校验作用域边界与普通文件属性，**整文件按 UTF-8 直读且无字节或字符截断上限**；无非空约定文件时不生成消息，`runtimeKind === "ephemeral"`（定时作业等）、`isolated` 支持会话与子 Agent 不注入此项。
- **三维生命周期：** ① 在运行体窗口开启钩子 `onWindowOpen` 时读取磁盘生成——同一常驻运行体在同一窗口内跨 `run` 复用已捕获前缀，而窗口换代（`run` 内 `segment-transition`，或 `run` 外 `/clear`、`/resume`、手动 `/compact`）或按指派新建运行体实例执行（如 `ConversationAssignmentWorker`）时会重新读取磁盘最新约定；② 仅驻留运行体内存前缀槽，不写入 `LoopState.messages`、`AttentionWindow` 或磁盘 `Transcript`；③ 在当前窗口每次主模型请求时前置为 `messages[0..1]`（段切换摘要请求不携带该前缀）。

**（2）注意力窗口首部 `<system-meta>` 消息对：恢复装填与段切换摘要/截断说明**

- **供给模块与实质内容：**
  1. **恢复装填对（`startup-bootstrap`）：** 既有历史会话建窗时存在两条生产装填路径：一是传统分片装填器 `buildStartupBootstrap`，以 $\min(\lfloor\text{optimalMaxTokens}/4\rfloor, 24000)$ 为预算基准倒读近期 `RunRecord`（最近一轮必装，超基准时降级为首条意图前 600 字加末尾 4 条消息的压缩核，连贯底线可顶起总预算；普通渲染保留用户/助手文本原文，将工具调用与结果压为 `助手：[调用工具 <name>]` 与 `[工具结果] <前200字符>`），并配入严格早于原文起点的最新未退役快照摘要（上限 800 字），拼成 `〔接续既有对话：以下是此前对话的回顾，按时间从早到晚排列〕`、`== 更早内容的摘要 ==` 与 `== 最近对话原文 ==`；二是设备本机 `local-*` 对话及协议恢复页路径（`access-surfaces`、`local-conversation-owner`），直接取 `protocol.recoveryPage({ mode: "context" }).text`。两条路径均封装为 `<system-meta kind="startup-bootstrap">...</system-meta>` + `<system-meta kind="ack">已接续此前对话</system-meta>`。
  2. **段切换摘要对与应急截断说明对（`compact-summary`）：** 上下文估算超阈值触发切段时，`SegmentManager` 将 `roles.light` 生成的三段摘要（要求总长 ≤ 500 字的 `<facts>`/`<state>`/`<active>`）压平封装为 `<system-meta kind="compact-summary">...</system-meta>` + `<system-meta kind="ack">已阅读摘要</system-meta>`。若摘要失败且已超 `riskMaxTokens`（未取消），`applyEmergencyFloor` 按实际移除范围生成中文说明 `因上下文超限且摘要生成失败，…已从上下文移除；完整原文保存在对话历史中。`，**同样经 `buildCompactSummaryPair` 以 `kind="compact-summary"` 标签发出**，仅将窗口首部内部标记设为 `"note"`（区别于真实摘要的 `"context"`，避免无内容增益的重复摘要）。
  3. **死代码与残留符号核实：** 本提交中不存在 `buildDroppedTurnsMessage` 函数，`dropped-turns` 仅保留在类型、识别分支与 `[系统元信息标签]` 提示文案中；系统元标签模块导出的 `buildWorksceneDigestMessage`（`kind="workscene-digest"`）在全仓生产代码中无调用点，当前运行期不会发出这两类标签。
- **三维生命周期：** ① `startup-bootstrap` 在会话建窗时生成；`compact-summary` 在每次 `run` 首轮模型调用前的 `runTurnBegin`（针对已拼入 `<context>` 的输入做预检，使超长恢复对话或超大首条输入在首调前即完成压缩换窗）、每轮结束后的 `runTurnEnd` 自动切段，或 `run` 外手动 `/compact` 时生成（推进裁判窗口超限时也会对自身评审窗口生成摘要对）；② 保存在跨 `run` 的 `AttentionWindow` 首部（单 frontier 折叠：新摘要对在运行内立即替换 `LoopState.messages` 首部并裁去被覆盖单元，在运行被窗口接受时取代此前全部 `bootstrap` / `summary` 及前序被折叠配对；持久 `Transcript` 分片原文不被改写）；③ 位于 `guidance` 之后随每次后续请求持续发送，直至下一次切段折叠替换或 `/clear` 清空。

**（3）单次运行级无感知前置块：`<context>...</context>`（`requiredUserContext` + `injectUserContext`）**

- **供给模块与实质内容：** `prependContextBlock` 在运行入口先收集宿主指派的 `requiredUserContext` 再收集 `onBeforeRun` 钩子贡献，当前生产用于**任务推进（Advancement）**：① 耐久来源带 `advancementExecution` 标记的非程序来源运行，由 `executionTurnContext` → `readAdvancementExecutionContext` 注入冻结材料——仅在 `mode === "advancement"`（确认推进模式）下包含 `renderAcceptanceConditions`（`本任务经用户确认的验收条件（完成判定以此为准，由推进侧独立核验）：` + 通过标准 + 证据要求及核验路径；降级执行模式不带 Rubric），若会话来自提议（`session.proposal` 存在）则另附 `renderAdvancementOriginalTask`（原任务、提议阶段补充及附图序号说明）；② 主控 `RuntimeHost` 下的普通会话运行（无 `advancementExecution` 标记），当所属会话存在 `status === "active"` 且已确认 Rubric 的推进会话时，由 `createAdvancementAcceptanceLifecycle` 在 `onBeforeRun` 中注入同一 `renderAcceptanceConditions`（非主控 `ExecutorRuntimeSubstrate` 未挂载此钩子）。
- **三维生命周期：** ① 在 `runtime.run()` 开始时拼装一次，以 `<context>\n...\n</context>\n\n` 前置到本次 `run` 最后一条 `user` 消息的首个文本块（有原任务附图时追加 `ImageBlock`）；② 存在于当前 `run` 的内存 `loopMessages` / `LoopState.messages` 中，而 **`buildRunRecord` 使用注入前的 `originalUserMessage` 生成记录**，故持久记录与跨运行 `AttentionWindow` 均不含该块；③ 在**同一次 `run()` 后续工具往返请求**（及同 `run` 内切段摘要器读取的 `state.messages`）中保持可见，下一 `run` 不会从上一轮历史中继承旧 `<context>`。

**（4）逐次调用级无感知动态块：`<turn-context>...</turn-context>`（`TurnContextInjector` 与追加式前缀投影）**

- **供给模块与实质内容：** 每次主循环调模型前依次调用活跃 Provider，将各段格式化为 `[<title>] <body>` 后以**单个换行 `\n`** 连接包入 `<turn-context>\n...\n</turn-context>`：① `TimeProvider`（`createAgentRuntime` 内建注册，除子 Agent/编排节点外所有 `AgentRuntime` 实例均具备）输出 `[当前时间] <zh-CN full日期+medium时间> (<时区>)`；② `SchedulerProvider`（仅主控 `RuntimeHost` 注入；宿主先以 `!isInternal` 过滤系统内部维护任务，再由 `computeStatusSummary` 统计已启用活跃任务及默认**最近 30 分钟内**的完成与失败任务；三类全空时整段跳过）输出 `[定时任务（仅在用户主动询问任务相关话题时提及，不要主动提起）]` 加概览计数，并按默认上限分别列出最多 **10 条活跃**（`⏳` 含计划与下次时间）、**5 条最近完成**（`✅` 含时间、100 字内摘要与投递标记）和 **3 条最近失败**（`❌` 含时间与错误）；③ `TaskListProvider`（仅主控 `RuntimeHost` 注入；无会话绑定或列表为空时跳过）输出 `[当前任务列表（你已通过 task_list 工具维护的计划，set 时请保留历史项）]` 及按 1 起始序号排列的 `1. [x]/[~]/[ ] <content>`（**不含任务项 `id`**）。非主控远端执行器未注册后两项 Provider，仅注入 `[当前时间]`；子 Agent 与编排节点不运行 `TurnContextInjector`。
- **双协议投影差异与三维生命周期：**
  - **常规覆盖式协议（`appendOnlyTurnContext: false`：`anthropic-messages`、`openai-compatible`、`google-interactions`）：** ① 每次调用前在 `prepareSendView` 实时生成；② **仅存在于当次发送副本 `PreparedSendView.providerMessages`**，先剥离最新 `user` 消息首文本块上的旧 `<turn-context>` 再前置新块（首轮位于 `<context>` 之前；工具返回或收到运行中追加输入后，选中目标移至最新的 `tool_result` 载体 `user` 消息或新追加 `user` 消息上；在 `openai-compatible` 出站转换中，与 `tool_result` 同处一条内部 `user` 消息的 `<turn-context>` 文本会在 `role: "tool"` 消息之后拆成一条独立 `role: "user"` 消息发送），不写入 `LoopState.messages`、`AttentionWindow` 或持久历史；③ 仅当次模型请求可见，下次调用即被替换。
  - **追加式前缀敏感协议（`appendOnlyTurnContext: true`：`openai-responses`）：** ① 每次调用前生成为末尾一条独立的普通 `role: "user"` 消息；② 不写入 `LoopState.messages`、`AttentionWindow` 或持久历史，但当次调用真正产出 `assistant` 消息后，`AppendOnlyTurnContextState` 将该条 `<turn-context>` 锚定在运行体内存槽位表中；③ **在同一运行体实例的同一前缀代际内（同 `run` 工具续轮及未换窗/压缩/回退的后续 `run`），前序已锚定的旧 `<turn-context>` 独立 `user` 消息继续按原位随请求发送**，尾部再附本次实时 `<turn-context>`；发生切段压缩、窗口换代、新建运行体实例或历史长度回退时重置锚点表，并通过 `invalidatedPrefixBeforeIndex` 让适配器省略失效前缀之前的加密推理状态。

**（5）输入正文包装、系统生成输入、工具结果包装与按需技能正文**

- **本地材料包装（`<file>`）、多模态图片与技能斜杠输入：** 交互终端与 CLI 文本会话解析本地文本材料或 `@file:` 引用时（普通 RPC 直发不经此步），`resolveInputMaterial` 与 `resolveFileRefs` 按单文件默认上限 `100 KiB` 将内容展开为 `<file path="..."><UTF-8正文></file>` 文本块并附内部 `material` 元数据；四个 Provider 适配器出站及 `buildStartupBootstrap` 渲染时经 `coalesceUserMaterialTextBlocks` 剥离 `material` 并合并连续文本块，成功提交后保存在持久 `RunRecord.messages[0]` 与 `AttentionWindow` 中跨 `run` 可见直至被压缩。本地图片材料按单图默认上限 `5 MiB` 转为 Base64 `ImageBlock`；若消息含 URL 型 `ImageBlock`，`anthropic-messages` 适配器出站降级为 `[Image: <url>]` 文本块，其余三个适配器直接透传图片 URL。此外，交互终端与文本会话输入已注册的 `/<skill_id>` 命令时，命令分派器不自动展开技能正文，而是将字面 `/<skill_id>` 原样作为普通用户文本发往会话，由 `load_skill` 工具描述引导模型再调用 `load_skill`。
- **跨会话、外部程序与受管通道来信的线上可见性：** 内部 `conversation` 工具 `send` 与本机外部程序 `conversation.program.send`（`zz conversation send`）投递的输入，在内部 `ChatRequest.messages` 对象上可携带结构化 `Message.inputIdentity`（或在会话账本上标记 `programOrigin`）；受管消息通道入站（如内置飞书通道经事件归一化剥去 `@bot` 占位符后交由 `InboundRouter` 准入）则在运行上下文记录 `turnOrigin`（含渠道标识、群/私聊目标与发送者 `open_id`）。但**四个 Provider 适配器序列化线上载荷时只读取 `role` 与 `content` 块，默认出站请求中均不包含发送方 `conversationId`、渠道名称、外部发送人标识或“来自对话 / 来自外部程序”等可见文本标记**（终端 `◇ 来自对话 ...` 仅为界面展示）。两类历史读口的返回结构亦不同：模型可调用的内部工具 `conversation(action: "read")` 返回 `runs` 与 `inputsOutsideHistory`（跨会话来信在对应消息上携带 `inputIdentity.source.conversationId`；程序来信对已入历史运行按条件返回 `programOriginRunIds` 列表，首页历史外输入条目也可直接标记 `programOrigin: true`，两者均不含外部智能体会话 ID），而外部程序/CLI 读口（`conversation.program.read` / `zz conversation read`）则在条目上映射为 `sourceConversationId` 或 `programOrigin: true`。此外，运行中在 Turn 边界经 `inputPort` 收取的追加消息虽进入当次 `run` 后续请求的 `LoopState.messages` 并在运行成功提交后落入 `RunRecord.messages`，但 `AttentionWindow.acceptRun` 只保留 `[runMessages[0], 移除 tool_use 后的末条 assistant]`，因此**普通下一 `run` 的内存窗口不携带上一轮中途追加的输入消息**（后续若重开会话装填近期记录或主动调工具查历史则仍可获知）。
- **系统生成的会话续接输入与子运行/作业任务输入：**
  1. **面向会话的系统续接与代理输入消息：** 工作场景进入/退出、工作目录切换与 `mcp_connect` / `mcp_delegate` 续接投递 `继续已获准交接的任务。以下是原任务的交接说明，不是新的权限……\n<handoff JSON>`（四元组 `handoff` 序列化总长上限 `32,000` 字符、单字段上限 `8,000` 字符），受托结果回传原对话时投递 `受托工作返回以下运行结果，请结合原目标核实并继续交付……\n<result>`（被拒时投递未接纳说明）；受管扩展各阶段由 `createExtensionContinuation` 向原对话或回退对话投递含状态 JSON 的操作指引（准备阶段指示加载《外部能力接入》技能并用 `extension` 系列工具推进，配置/验证阶段指示引导用户到 `/config` 操作并结束本轮，终态要求按真实实例状态汇报）；推进验收未通过时按 Rubric `failureHandling` 模板拼装 `【验收判定】` 逐条归因块作为代理 `user` 消息投递。上述消息作为新 `run` 首条输入并在运行成功提交后，写入 `Transcript` 并随问答对进入 `AttentionWindow`（特例：受管扩展续接向 `local-*` 对话投递时走内部通信 `send`，若目标正在支持补充输入的在途 `run` 中被当轮追加消费，则按上文追加输入规则进入当次 `LoopState.messages` 与已提交 `RunRecord`，不单独进入下一 `run` 的首末配对）。
  2. **不进入父会话窗口的子运行任务消息与独立作业输入：** `Task` 子 Agent 由 `DefaultSubAgentFactory` 以单条 JSON 文本 `{"kind":"sub_agent_task","description":"...","prompt":"..."}` 作为子循环初始 `user` 消息；声明式编排节点按节点策略可选前置冻结只读 `backgroundMessages`，并在 `sub_agent_task.prompt` 内拼装 `You are executing orchestration node "<id>".` 及 `<instruction>`、`<context_snapshot>`、`<run_input>`、`<dependency_outputs>`（含 `<node_output>`）、`<output_contract>` 标签块，子运行结束后子消息序列即销毁；耐久定时智能体作业则将调度任务保存的 `instruction.prompt` 作为单条 `user` 消息送入一次性 `ephemeral` 运行体，不绑定持久会话窗口。
- **工具结果外层包装、按需技能正文与四协议映射：**
  1. **按需技能正文（`load_skill`）：** 调用后作为 `tool_result` 返回 `# <技能名>\n\n<正文>`（无 `maxResultChars` 限制；4 项内置技能单篇为 536～905 Unicode 字符 / 1,178～2,211 UTF-8 字节，合计 2,780 字符 / 6,622 字节）。4 项内置技能正文分别给出受管通道候选构建与基于脱敏故障证据排障（《外部能力接入》）、展示草稿经同意后保存技能（《提炼技能》）、独立安全审查与二段 token 确认（《接入技能》），以及跨对话发现/新建/读取/发送/观察与外部程序来信协作规则（《对话通信》）。
  2. **执行管线外层包装与错误/中断占位：** 工具输出先经安全执行器 `createSecureExecuteTool` 按字节上限截断（超限追加 `\n\n[输出被截断: 原始 X, 截断到 Y]`），再经 `executeToolCall` 按工具 `maxResultChars` 字符截断（非错误超限追加 `\n\n[truncated: showing first X of Y chars, Z chars omitted]`）；`committedToUser` 为真时追加 `[Commitment already sent to user. Do not restate.]`；排他初始控制批次门拒绝、超单轮调用上限或工具未找到时合成英文错误结果；执行异常时区分内部故障（加 `Tool execution failed: ` 前缀；外部 MCP 工具调用失败在适配器内包装为 `<toolName> failed: <reason>`）与面向模型的 `SecurityBlockError`（策略拦截、安全管家升级拦截、用户拒绝及反馈、确认取消/超时、`logOnly` 越权均原样返回中文说明）；`Task` 返回父模型时附加 `<usage>status, tokens, tool_uses, duration_ms, sub_id</usage>` 并在失败/中止时冠以 `[Task "<desc>" failed (<type>): <msg>]` / `aborted` 及可选 `Partial output:`；运行中断时由中断清理与消息组装逻辑为未执行工具生成 `[Tool execution cancelled: <reason>]` 占位结果，并在非空半截助手文本末追加 `[interrupted]`。在线上协议层，`tool_result` 分别映射为 Anthropic 的 `user` 内容块、OpenAI Chat Completions 的 `role: "tool"` 消息、OpenAI Responses 的 `function_call_output` 项及 Google Interactions 的 `function_result` 步骤。
  3. **三维生命周期：** 工具往返与 `load_skill` 正文在产生后立即进入当次运行内存 `LoopState.messages`，供**同一次 `run()` 后续模型调用直接读取**（同 `run` 内若触发切段，保留末尾 `bufferUnits` 步内的工具轮）；在耐久会话中，唯有运行成功提交后才写入会话 `Transcript`（失败/取消的未提交指派、一次性定时作业与子 Agent 循环各自独立收束，不入父会话历史）；**已接受运行的跨 `run` `AttentionWindow` 默认剥离全部工具往返与 `tool_use` 块，普通下一 `run` 不再重发完整技能正文或工具输出**，但此后若会话重开触发恢复装填（如 `buildStartupBootstrap` 对选中近期记录渲染每块前 200 字工具结果摘录）或模型再次调用工具，相关内容或摘录仍可能再次进入模型请求。

#### 3. 承载自身机制与自诊断说明的工具提示、体量及跨通道重复情况

智能体路径的每次主循环请求及段切换摘要请求均在 `ChatRequest.tools` 中全量重发当前运行体实际装配的工具声明（按会话冻结 `executionProfile`、作业 `capabilities.tools`、子 Agent `SUB_AGENT_ENABLED_TOOLS` 交集或编排节点 `policy.tools` 筛选）：**常驻工具声明体量约为 `systemPrompt` 的 3～4 倍**——主控主对话在有授权工作区挂载标准 27 个工具时，`tools` 序列化 JSON 为 25,177 UTF-8 字节；无授权工作区挂载 20 个工具时为 19,037 字节；`Task` 子 Agent 在有工作区（6 个工具）与无工作区（3 个工具）下分别为 4,688 字节与 1,998 字节。剔除常规基础文件/命令/网页工具的普通参数 schema 后，承载**知行自身机制、连接态势或问题自诊断说明**的工具层提示及各路径装配边界如下：

#### 4. 运行时自我认知视角下的现有覆盖与事实空白

综合核查后的产品默认提示注入、按需展开工具与实际出站请求，知行当前在智能体自身认知这一局部要素上的覆盖边界与空白如下：

1. **已具备若干专项能力与受管流程指引，但缺乏跨领域的系统全景与边界说明：** 在当前产品输入链中，智能体可从身份与环境段得知基本协作边界和当前工作区授权状态，从工具声明（含 `mcp__<serverId>__<tool>` 前缀）与内置技能按需获知已连接外部 MCP 工具、受管扩展接入/排障（`extension` +《外部能力接入》）、跨对话通信（`conversation` +《对话通信》）、技能保存/准入、工作场景切换、MCP 公开候选提交及定时/推进工具用法。但核查范围内未发现任何常驻或按需机制向智能体统一说明知行的整体运行架构与职责边界——例如多设备 `anchor`/`executor`/`surface` 拓扑与 `local-*` 本机对话归属、模型三角色（`main`/`light`/`power`）与选模覆盖规则、权限分类与确认生效范围、用户侧斜杠命令（`/config`、`/mcp`、`/work`、`/clear`、`/resume`、`/compact`）与智能体工具的协作分工，以及本机配置与数据目录边界（`globalConfigPath` 虽传入运行体但未渲染）。
2. **已提供专项状态动作与通用日志查询工具，但缺少跨模块自诊断索引与排障指引：** 受管扩展已有结合 `extension(status)` 脱敏故障证据与 `extension_source` 排查的专项指引，主/子运行路径（在装配了日志工具时）也具备 `log_search`、`log_read` 及父侧 `Task(logOnly: true)`。但对于通用运行日志与跨模块异常（如模型调用报错、`mcp_discover(status)` 剥离 `error` 字段后的连接故障、定时作业失败、跨设备派发或确认受阻等），现有提示词、工具描述与内置技能中均未给出合法日志 `source` 清单、`ref.kind` 关联标识约定或从用户侧报错定位根因的自诊断路径。
3. **跨会话、外部程序及受管通道来信的默认线上输入与来源元数据分离：** 跨会话 `send`、外部程序发信与受管通道（如飞书）入站在四个 Provider 适配器的默认出站消息正文中均不附带发送方会话标识、渠道名称或发送人提示——跨会话来信虽在内部消息上存有 `inputIdentity.source.conversationId`，但模型不调 `conversation(action: "read")` 就无法在默认出站消息中直接看到发送方对话 ID（与《对话通信》技能文案的预设存在落差）；外部程序来信即使经内部读口 `conversation(action: "read")` 查询，也仅能在历史运行的 `programOriginRunIds` 列表或首页历史外输入条目的 `programOrigin: true` 上标识程序来源，不提供外部智能体会话身份；受管通道的 `turnOrigin` 仅留存运行元数据而不进入模型可见消息。同时，运行中经 `inputPort` 收取的补充输入不进入普通下一 `run` 的 `AttentionWindow` 首末配对。

## 三、调研所得

### 3.1 审查标准

> **调研独立审查标准（定稿）**
>
> 1. **查透系统自身认知的内容版图与开放边界。** 围绕运行期智能体了解宿主系统自身以更好服务用户这一核心目的，查清代表性系统实际上向智能体提供了哪些层面的自身认知、开放到什么深度，以及智能体如何按需发现、取得并运用这些认知自主调动系统能力，或在对话报错与系统异常时查证依据、定位问题（分清供给关于系统自身结构、能力与查证途径等客观认知，与编写“遇到某类报错该怎么办”的死板排障步骤；按来源严格区分产品原生系统认知、用户或仓库协作者自定的上层工作约定、以及某次运行中实时查得的观测事实）。同时按证据讲清开放边界与生效方式：各系统实际提供和保留了什么，如何区分服务于用户正当使用诉求的系统认知、无需提供的纯内部实现细节以及越过用户合规与安全边界绝不向智能体暴露的内容（涉及受限信息或操作时，按证据区分内容取舍、宿主访问控制及其局限），绝不把系统透明白盒或完整内部说明书等同于运行时自我认知。
> 2. **摸清本机原生样本，按调研准则开放确立世界一流标杆。** 本机可直达的一手样本与开放广域调研各司其职：对本机运行环境中的 Codex 与 Antigravity，一手拆解其自身内置的相关技能或等效原生机制（核清版本、真实名称、触发描述、组织结构、完整内容范围及实际生效方式，含公开介绍未提及的内置机制，作为必查近旁样本而不预设为最优答案）；广域调研则严格遵循调研技能的方法、开放范围与收敛标准，不预先锁定候选名单，不以学科、行业、年代或资料形态划界，也不凭名气或表面宣传选样——围绕可能改变核心判断的决定性问题先宽后窄，开放追查同类领先成果与前沿研究、开源与极客实践、基础理论、经典系统设计及卓越贡献者的一手认识，不被初始线索锁死，不满足于找到可用答案即停止，按实质解释力与原创贡献择优确立世界一流标杆，写明标杆领先在何处、强在哪里，以及关键候选的比较范围与排除理由。采用跨领域经验时，写明对应关系、成立前提与失效边界。
> 3. **一手证据扎实，严守证明边界。** 每条关键判断均须追到亲自核读的一手材料（本机内置资产原件、明确版本的开源源码、协议与配置规范、官方文档、原始文献或受控最小实证），注明对象、版本、成立条件与证明范围，严格区分来源主张、核实事实与自身推断，并分别举证“材料写了什么”与“智能体实际能否取得并据此行动”（闭源产品无法直接观测的内部机制须标明证据边界）。判定能力缺失或不可行，须锁定对象、版本与条件，先核查相关原生途径与最有力反例并给出直接依据，单次未搜到或未见公开宣传不构成否定证据；断言固有短板须追到具体机制而非偶发配置；判定某路线更优或没有更好方案，须在同约束下与最强可信候选对照，证据不足时如实写明在已查范围内尚未证实。
> 4. **不设限深比承载形态、提示词分工判据与产品体验取舍。** 不对承载形态、表达方式与架构形式设前置限制（不局限于内置技能），将不同代表性承载路线放进同一有区分力的高要求场景（如首次调用陌生系统能力、原因未知的对话报错或系统异常查证定位、长对话多轮演进与版本更新同步等）横向对比：拆解各路线把哪些内容常驻、哪些按需提供，常驻系统提示词在其中承担什么定位与职责，智能体怎样知道何处可查并准确触发，并讲透在相应条件下选择常驻、按需或组合承载的判据（比较改变放置方式对任务效果与系统成本有无实质影响及在何种条件下显现）；同时从产品与使用体验角度比较任务可靠性、对用户的无感知程度（无须用户感知底层机制或理解内部细节，同时不混淆必要的安全授权确认）、常驻上下文开销、防越界安全性及长期维护代价，讲透各自的真实收益与固有代价。主动用最强可信反例或竞争解释挑战核心判断，指明什么条件改变会使结论反转。
> 5. **形成可超越洞察，独立精炼交付。** 穿透具体实现外壳，指明哪些原理与结构设计解决了什么根本问题、在何种条件下成立；发现一流方案仍有局限时，指明具体局限、机制成因、可改善的实际结果及检验方法；若充分比较表明某项成熟做法已适合相应条件，讲清保留它的依据及强行改变的代价，同样成立。如实交代仍影响判断的分歧或未决边界，以及何种新证据会改变当前判断。独立于知行现有实现开展研究，不以本系统现状框定问题与视角，也不提前做具体方案设计；围绕决定性问题精炼自足成文，不堆砌浏览流水账或以资料数量充当深度。
>
> 以上五项须同时满足，共同构成调研阶段的优秀通过标准。双方先各自对照同一份调研正文独立审查并记录依据，再交换质询；凡有足以改变核心认识的遗漏、薄弱证据或未处置反例，均按调研方法定向补研并复核，直至完全达标。标准经确认后固定，不因已有结论或后续方案而放宽。

#### 研究总览

围绕“运行中的智能体如何准确认识其所处的宿主系统以自主服务用户，同时守住安全合规边界与多轮上下文效率”这一核心目的，本研究独立于知行现有实现，聚焦四个决定性问题开展取证与比较：**代表性系统向运行期智能体开放了哪些层面的“系统自身知识”，这些客观结构、契约与查证途径凭什么支撑智能体自主调用能力并在异常时定位根因；服务用户的正当认知、无需提供的内部实现细节与绝不暴露的安全合规禁区如何划界，内容取舍与宿主访问控制各自能证明什么、有何局限；跳出单一内置技能预设后，不同承载形态在触发发现、用户无感知体验、多轮请求成本与版本一致性上如何取舍；常驻系统提示词与按需认知机制依什么条件分工，何种证据会使结论反转。**

为防止概念混同，全文按来源与时效严格划开三类不同性质的信息：① **产品原生系统认知**——宿主面向运行期智能体提供的自身能力版图、配置与扩展契约、运行边界及可观测查证途径；② **用户或仓库协作者自定的上层工作约定**——如项目级 `AGENTS.md` 研发规范、多智能体角色分工或团队流程（属宿主能力之上的用户自定义层，不属产品内置自我认知）；③ **单次运行按需查得的实时观测事实**——具体某次执行中的状态快照、调试记录或日志条目（属按需取证的对象，而非预先写进静态自我认知文档的内容）。

研究截至 `2026-11-24`，严格区分四类证据及其证明边界：① **本机内置资产原件、宿主工具目录与受控只读核验**（Windows 应用包 `OpenAI.Codex 26.1120.5083.0`、命令行 `codex-cli 0.149.0`、桌面宿主 `Antigravity.exe 2.34.0.0` 及其磁盘内置原件与当前会话可见目录，附 SHA-256 指纹，结论严格限定于所核版本与环境）；② **固定提交的开源源码、协议规范与公开议题**（`openai/codex@758ef40f`、`badlogic/pi-mono@f8149d1a`、`NousResearch/hermes-agent@5725d1d3`、`openclaw/openclaw@41dce562`、`aaif-goose/goose@03a343f9`、GNU Emacs `636f166c`、MCP `2025-11-25` 与 MCP Apps 规范、Agent Skills 规范、GraphQL `September2025` 及 `anthropics/claude-code#34730`）；③ **闭源厂商公开文档声明与工程受控评测**（Claude Code、Claude Developer Platform、OpenAI API、Google Antigravity、Apollo Server 官方文档，以及 Anthropic `2025` 与 Vercel `2026` 发布的受控评测报告，行内逐处标明属厂商声明或其特定实验口径，不外推未公开服务端实现或跨任务普适排名）；④ **跨学科原始文献**（Saltzer & Schroeder `1975`、Stallman `1981`、Hardy `1988`、Pike et al. `1995`、Bracha & Ungar `2004`、Levy et al. `ACL 2024`、Gloaguen et al. `2026`）。

**1.2 本机近旁样本二：Google Antigravity（`2.34.0`，`builtin/skills/` 15 个目录、26 份原件与宿主工具契约）**

本机 `Antigravity.exe` 文件版本为 `2.34.0.0`，磁盘 `~/.gemini/antigravity/builtin/skills/` 直接包含 **15 个子目录、26 个普通文件**（目录名与技能公开 `name` 可不同，如 `antigravity_guide` 公开名为 `antigravity-guide`，`native_swarm` 公开名为 `swarm`）。综合实盘原件核读与本机原生会话工具目录观测，其自我认知由四部分协同组成，并在**“谁看得见、谁能调用”**上划出了精细边界：

1. **会话常驻最小线索、宿主原生只读自省工具与规则预算降级：** 当前会话常驻层提供三项基础路标——① 用户界面专属斜杠命令列表（如 `/goal`、`/compact`、`/schedule`、`/plan` 等，明示智能体自身不可执行、仅可按场景推荐）；② 已对模型暴露的技能 `(名称, SKILL.md 路径, 触发描述)` 目录；③ 当前会话轨迹日志路径及“先读紧凑版、遇截断字段再按行读全量版”的两级自查规则（仅覆盖本会话已产生步骤）。在 26 份公开技能原件之外，当前原生会话的宿主工具目录还直接挂载了只读自省工具 **`list_plugin_accounts`**（按该工具声明契约，可查询已绑定插件提供方、登录状态、身份标识及所驱动 CLI 等元数据，以便在运行插件 CLI 前或鉴权失败时准确告知用户去 Plugins Manager 重连对应提供方，**不返回原始凭据值**；本轮仅核对工具契约而未查询用户绑定账户，且须注意账户标识本身仍具隐私含义，“已绑定”亦不足以推出对每个下游资源或动作均获授权）与 **`search_marketplace`**（检索市场目录，与本地已装盘点、当前会话可调列表分答不同问题）。此外，`agy-customizations/docs/rules.md` 规定单文件 `24,000` 字节上限（展开 `@[...]` 引用后按行截断），以及 `always-on`/全局规则共享的 `20,000` tokens `defaultRulesBudget`（超限用户规则自动由全文内联降级为文件路径指针改按需读取，内置插件规则豁免该预算）。
2. **显式配置挂载与两项正交可见性开关（破除“在盘 = 模型可自选 = 用户菜单可见 = 工具在场”的混同）：** `agy-customizations/SKILL.md` 第 36–37 行写明 `Built-in customizations are not found this way: the agent config names the ones it mounts`。进一步逐份核查 15 个内置技能的 frontmatter 发现两项公开概览未展开的独立开关：① `native_swarm/SKILL.md` 第 8 行声明 **`disable-model-invocation: true`**——压制模型自主激活该高配额集群技能（故未进入当前会话的 `<skills>` 模型选型列表，但当前会话工具表实际已独立挂载同名原生 `swarm` 工具）；② `ui-plugin-navigation:4`、`swarm_narrator:7`、`swarm_monitor:7`、`swarm_pane:7` 四份原件声明 **`disable-slash-command: true`**——将仅供智能体内部或特定集群子角色使用的技能从用户 `/` 斜杠菜单隐藏。两个开关分别作用于“模型隐式选型”与“用户斜杠菜单”，并非互斥权限；当前原生会话 `<skills>` 见到 12 项是由挂载配置与隐式调用开关共同决定的，不能仅凭某项缺席唯一反推未挂载或无其他显式入口。
3. **产品全景地图与扩展机制契约正交拆分：**

#### 2. 自身认知内容版图、四类权威来源与开放边界生效机制

**2.1 服务用户的系统自身认知五维版图与四类不可互替的权威来源**

围绕“智能体需知晓什么、去何处查证、从而免去用户何种额外负担”，代表性系统向运行期智能体开放的自身认知覆盖五个互补层面：① **产品界面、运行模式与人机操作边界**——区分 CLI、桌面、IDE、SDK 或受管通道的能力差异及仅限用户操作的斜杠命令/面板开关，使智能体准确代办或给出精确入口而不错调不可执行命令；② **系统能力、扩展协议与多维可见性边界**——涵盖工具、技能、插件、MCP 传输与 `ui://` 扩展、生命周期钩子的契约与覆盖优先级，并分清“磁盘已装、模型目录可自选、用户斜杠菜单可见、界面前端可调、当前会话工具表在列”五件独立事实；③ **配置层级、凭据绑定元数据与生效就绪条件**——拆开项目设置、全局偏好、管理策略与账户权益，提供不含秘密明文的连接/登录状态自省（如 `list_plugin_accounts` 核查绑定提供方或区分 API Key 与连接器授权），并明示配置写入后究竟即时生效还是须下一轮/新会话/重启刷新；④ **会话历史、上下文压缩/缓存规律与指令优先级**——说明历史活动视图与持久记录的差异、前缀缓存条件，以及“显式提示优先于记忆、记忆仅作偏好背景而不充当当前外部事实源”（如 Codex `openai-docs` 与 `codex-self-knowledge.md` 所列，但知晓该规则不等于某段历史或记忆此刻已在上下文中）；⑤ **后台无人值守、跨执行端拓扑与可观测自诊断途径**——区分当前轮计时、跨会话发信、每次拉起无记忆新会话且仅按全局权限/预设与已登记作业授权放行的定时自动化，以及服务宿主（如 `app-server`）与远端工作区执行端分离时的配置落点，并给出健康检查、状态快照与轨迹/运行日志的查询路径及时间覆盖范围。

深查能力调用与异常排障全过程可见，**真正的运行时自诊断既不是预写“遇到某报错该怎么办”的死板排障步骤，也不是把动态运行状态塞进静态文档，而是让智能体分清四类不可互替的权威事实源并按需交叉取证**：

1. **概念、拓扑与查找路由看产品指南/手册（回答“系统一般支持什么、该去哪查”）：** 如 Codex `codex-self-knowledge.md` 的承载面选型表、Antigravity `agy-customizations` 的五级覆盖优先级、Hermes `SKILL.md` 的网关与模块路由表。手写或摘要式指南存在笔误与滞后风险（如 Claude Code `#34730` 中 `claude-code-guide` 误答提示型 `Stop` hook schema，用户写入后触发配置校验跳过，反而导致整套项目钩子失效）。[Hermes 指南路由表](https://github.com/NousResearch/hermes-agent/blob/5725d1d390ac4b7cfe157ea32bd6f4db1a280368/skills/autonomous-ai-agents/hermes-agent/SKILL.md#L33)
2. **当前安装版本接受的参数与字段结构看随包合同/Schema 自省（回答“这台机器的这个版本声明什么”）：** 本机实证已表明在线手册列出的 `codex doctor --network-only` 被本机 `codex-cli 0.149.0` 的 `--help` 直接拒绝；OpenClaw `schema.lookup` 按裁剪深度返回当前版本公开配置字段结构、Codex `statusline.d.ts` 由源码 `ts-rs` 自动导出、Kubernetes `kubectl explain` 直接查询集群当前 API schema，均从源头抑制静态散文随版本漂移。[Kubernetes kubectl explain](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_explain/)
3. **当前会话此刻能否执行看运行期能力目录与许可裁决（回答“本次运行是否有权且可调”）：** 如 Codex `mcp-diagnostics.md` 明示配置写入不等于已运行会话可调、本机桌面会话暴露 `send_message_to_thread` 而公开手册零命中；OpenClaw 用 `session_status` 查本会话能力，Kubernetes 将字段说明（`explain`）与动作许可（`kubectl auth can-i`）拆成两个独立查询。[Kubernetes kubectl auth can-i](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_auth/kubectl_auth_can-i/)
4. **这一次为什么失败看按需受限运行证据，且受采样时段与脱敏范围约束（回答“此处实际发生了什么”）：** Hermes 诊断参考中真正可迁移到未知故障的是网关、插件、进程与日志取证路径而非已知个案处方；同时按 Claude Code 厂商文档声明，内置 `/debug` 技能在会话中途开启时才启动调试记录，**此前已发生的异常不会凭空补出日志**，智能体必须掌握证据的覆盖时段边界，不能把“未见记录”误判为“未发生故障”。[Hermes 诊断参考](https://github.com/NousResearch/hermes-agent/blob/5725d1d390ac4b7cfe157ea32bd6f4db1a280368/skills/autonomous-ai-agents/hermes-agent/references/troubleshooting.md#L56) · [Claude 配置与调试诊断文档](https://code.claude.com/docs/en/debug-your-config)

**2.2 三层开放边界、内容取舍与宿主访问控制的作用及固有局限**

向运行期智能体开放自我认知绝非将系统作为透明白盒全盘托出。核查各代表性实践与安全原典，开放范围分为三层：**第一层（面向智能体开放、对用户保持无感）**为服务用户正当诉求与排障所需的公开契约、配置结构、就绪门规则及获准观测途径，智能体内部查清后直接交付结果而不向用户倾倒 `sidecar.json` 等底层细节；**第二层（无需提供的纯内部实现细节）**为不服务用户任务的内部调度实现、私有源码树、未公开实验开关及未过滤巨型全量转储（如 `codex-self-knowledge.md` 禁查无关缓存与私有源码树，Antigravity `plugin` 强制 `jq` 投影）；**第三层（越过合规与安全红线绝不暴露或代越权的禁区）**为原始密钥/令牌、未获授权的跨主体数据、防线绕过细节及未经授权的状态/权限变更。

涉及受限信息或操作时，完整安全边界必须分别回答三个独立问题——**① 允许哪个主体访问哪类资源；② 同一资源中哪些字段或视图对当前排障/任务确有必要；③ 取得诊断结果后是否获准向当前接收方披露**——单靠内容取舍或单靠粗粒度访问控制均存在明确局限：

- **内容取舍与导航约定的作用及局限：** 在文档与自省目录中剔除内部实现和敏感示例能减少无谓暴露与上下文噪声；但 `/llms.txt` 明确自身只是推理期导航索引而非访问控制，GraphQL 规范定义的 `__schema` 内省（只返已暴露 schema 的类型定义，不返实例值或执行权）在 Apollo Server `NODE_ENV=production` 下默认关闭——将这一部署取舍**跨领域类比**到接触外部不可信材料的智能体会话可见，收敛不必要的内部结构暴露可缩小测绘面，但**文档不写或关闭内省本身绝不阻止对底层文件或接口的直接访问**。[llms.txt 规范](https://llmstxt.org/) · [GraphQL 内省规范](https://spec.graphql.org/September2025/#sec-Introspection) · [Apollo 生产内省默认策略](https://www.apollographql.com/docs/apollo-server/api/apollo-server#introspection)
- **宿主访问控制的作用及其两重固有局限：** 按 Saltzer 与 Schroeder（`1975`）的**最小权限**与**完全仲裁**原则及 MCP `2025-11-25` 安全规范，所有资源读取与状态变更须在宿主/服务端执行层独立校验，按策略分别直接拒绝越权动作、放行已获授权动作或交受控入口由用户确认（如 Antigravity `plugin` 技能记载子进程受限调用写状态 RPC）。然而核查源码与安全原典同样证实，**简单的整文件/整工具放行或阻断仍无法替代前文第②、③问**：
  1. **粗粒度资源放行/阻断无法表达同一对象上的受限诊断投影：** 若配置文件或状态快照同时混存公开结构与秘密值/内部状态，整文件放行通用 `read` 会连带暴露秘密，整文件封禁又会使智能体在配置校验报错时丧失排障依据。积极实证来自 OpenClaw `41dce562` 的 `redact-snapshot.ts`：对外输出配置快照前先剥离内部迁移残留，对合法配置区分 `parsed`、`raw`、`resolved` 等视图并按 schema 敏感标记与路径规则遮蔽秘密，配置校验失败时则拒绝返回原文或解析内容，仅保留受限诊断所需的错误结构（同时该机制依赖 schema 标记与规则匹配，不能仅凭单一脱敏函数推定对任意未知新字段或旁路日志实现绝对零泄露）。[MCP 工具安全规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#security-considerations) · [Saltzer & Schroeder 1975 原文](https://web.mit.edu/Saltzer/www/publications/protection/Basic.html) · [OpenClaw 配置快照脱敏源码](https://github.com/openclaw/openclaw/blob/41dce5629f2703bb894a5409b0e6692fd4dd2ef3/src/config/redact-snapshot.ts#L296)
  2. **“获准本地读取供自诊断”不等于“获准向任意接收方转交诊断内容”：** 对照 Hardy（`1988`）困惑副手原理，当运行体同时持有宿主本地诊断读取权与对外回复/跨会话发信能力时，仅校验“该进程能否读此日志或状态”无法回答当前动作究竟代表谁、结果发往何处（如外部渠道或低信任跨会话调用方）；因此自诊断读取结果的外传仍须受当前任务目标、接收主体与跨边界披露规则约束，必要时只返脱敏摘要、拒绝外带或交用户决定。

**3.2 多轮请求序列下的四层状态与成本分解（破除“逻辑上下文 = 网络重传字节 = 缓存账单 = 磁盘档案”混同）**

判断改变放置方式何时产生实质影响，不能只贴“常驻/按需”静态标签，而须沿一段真实多轮请求序列拆开四个可独立变化的层面：

1. **网络传输载荷 vs 模型起始可见输入：** 如 Claude Developer Platform 官方工具检索合同所示，启用 `defer_loading: true` 后客户端每次 API 请求仍按合同提交全部延迟工具定义，平台服务端在构造模型输入时将其排除在起始前缀外，待搜索命中后以消息流 `tool_reference` 块按需展开——说明**“网络请求仍携带定义”与“节省模型可见上下文且不重排顶层 `tools` 前缀”可以同时成立**。[Claude 平台工具检索合同](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
2. **前缀缓存分层命中 vs 窗口空间占用：** 按 Claude 官方缓存失效规则，前缀按 `tools → system → messages` 严格顺序匹配——修改已缓存的 `tools` 定义会使后续 `system` 与 `messages` 缓存一并失效，而修改 `system` 时不必推翻未变的 `tools` 层；OpenAI 亦按相同前导前缀自动复用缓存，且即使使用 `previous_response_id` 链式续接或 WebSocket 增量模式省去客户端重传历史字节，前序上下文仍按 API 规则计入模型输入（两家在断点声明、TTL 与计费细则上各有独立合同，不能混同）。关键约束在于：**前缀缓存命中能显著降低预填充计算成本与首字延迟，但命中缓存的常驻内容在每一轮仍实打实占用模型上下文窗口与注意力预算**。[Claude 缓存失效规则](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache) · [OpenAI 提示缓存指南](https://developers.openai.com/api/docs/guides/prompt-caching) · [OpenAI 会话状态与计费说明](https://developers.openai.com/api/docs/guides/conversation-state) · [OpenAI WebSocket 增量模式](https://developers.openai.com/api/docs/guides/websocket-mode)
3. **主会话按需留存、切段压缩与磁盘持久档案分离：** 源码核实显示，Pi（`f8149d1a`）在磁盘上以追加式 JSONL 树完整留存会话记录，但每轮送入模型的仅是当前分支的活动视图——触发压缩后，模型见到压缩摘要、自 `firstKeptEntryId` 起的保留区条目及后续消息；Codex（`758ef40f`）本地压缩重建历史与远端压缩替换路径亦各自裁剪模型可见历史。这意味着：**① 按需读入主会话的结果只要仍留在当前活动分支或压缩保留区内就会继续占窗且逐字可见，跨过压缩边界的更早条目则通常只由摘要代表（启用磁盘持久化时，旧档案仍在盘与模型当前窗口可见是两件独立的事）；② 若中途版本或权限变更，历史旧摘要或旧读入文本仅代表当时快照，继续依赖会失准**。[Pi 持久层 JSONL 源码](https://github.com/badlogic/pi-mono/blob/f8149d1abde50b31c8cb5aed09e89319b927f247/packages/coding-agent/src/core/session-manager.ts#L987) · [Codex 本地压缩源码](https://github.com/openai/codex/blob/758ef40f50c1a458425c7cfbf1eb12cbc07af0b0/codex-rs/core/src/compact.rs#L351) · [Codex 远端压缩源码](https://github.com/openai/codex/blob/758ef40f50c1a458425c7cfbf1eb12cbc07af0b0/codex-rs/core/src/compact_remote.rs#L270)
4. **直观逻辑窗口占用对照（仅计单份说明在模型逻辑输入中的累计呈现量，不含目录、检索调用与输出，非账单或实测值）：** 在一段连续 `8` 次模型调用的会话中，一份体量为 `D` tokens 的认知材料若全程常驻，累计进入模型逻辑窗口 `8D`；若第 `3` 次调用前才按需读入主会话且始终留在活动上下文中，累计为 `6D`；若第 `6` 次调用前跨过压缩边界被折叠为 `S` tokens 摘要且后续无需复读，则为 `3D + 3S`；若在整段会话中从未用到，按需放置为 `0`（仅付极薄路由线索成本），常驻仍付 `8D`。由此清晰可见：**能力越低频、篇幅 `D` 越大，按需或窄节点查询的窗口节省越显著；反之若某条核心边界几乎每轮必用且体量极小，常驻反而免去了额外检索往返与压缩丢失风险。**

**3.3 方向相反的受控实证交锋、常驻/按需自洽判据与结论反转条件**

两组方向相反的一手受控评测进一步验证了上述权衡边界（各研究的任务域、模型与基线不同，不能拼成跨产品总分）：

- **挑战“纯按需技能天然够用”的实证（Vercel `2026` Next.js 16 Agent Evals）：** 在模型预训练未覆盖的新版 Next.js API 特定评测中，将文档做成默认按需调用的 Skill 时，**56% 的用例完全未触发该技能**，通过率仅 **53%**（与无文档基线 53% 持平）；显式提示要求先用技能后升至 **79%**；而将压缩至约 **8 KB** 的文档目录索引直接常驻进 `AGENTS.md`（正文仍留 `.next-docs/` 按需读取），在该评测集上通过率达 **100%**。该实验直接证明：**参考资料处于可调用状态并不保证模型实际发起调用**；至于未触发源于业务措辞未唤醒查证意识、还是模型误以为既有知识够用等机制解释，仍需专门对照消融实验分别验证。[Vercel 受控评测报告](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- **挑战“大段全量常驻稳赚不赔”的实证（Anthropic `2025` 平台工具检索评测、ETH Zurich `2026` `AGENTbench` 与 Levy et al. `ACL 2024`）：** Anthropic 在 Claude Developer Platform 报告中给出 50+ 大型 MCP 工具示例：原始工具定义约 `72K` tokens、推高初始总上下文至约 `77K` tokens，启用 `defer_loading` + `ToolSearch` 后初始总上下文降至约 `8.7K` tokens（作者报告约缩减 **85%** 用量），内部 Opus 4.5 MCP 评测准确率从 **79.5% 升至 88.1%**，同时作者明言小而高频的工具集直接常驻更合适、延迟加载收益有限。ETH Zurich `AGENTbench`（`arXiv:2602.11988`）评测仓库级常驻上下文文件（`AGENTS.md` / `CLAUDE.md`）发现，冗长概述使自动生成版任务解决率降约 **3%**、人工编写版仅微增约 **4%**，却使**平均推理成本增加超过 20%**；Levy 等人（`arXiv:2402.14848`）亦受控证实，远在触及上下文窗口上限前，额外无关输入就会拉低多步推理表现（后两项测的是仓库上下文与输入长度效应，未直接评测宿主自诊断按需机制）。[Anthropic 平台工具检索报告](https://www.anthropic.com/research/advanced-tool-use) · [ETH AGENTbench 论文](https://arxiv.org/abs/2602.11988) · [Levy et al. ACL 2024 论文](https://arxiv.org/abs/2402.14848)

**常驻、按需与组合承载的自洽分工判据及反转条件：**

某项系统自身信息放在何处，同时取决于**遗漏后果与隐蔽度、使用频率、相对总能力面的体量占比、以及随版本或会话动态变化的程度**四个条件：
1. **优先常驻的条件：** ① 每轮均约束行为的安全与交互边界（如不可代执行的 UI 命令、受管变更红线）；② 能力面极小且固定系统中高频共现的核心说明；③ 复杂系统中用于唤醒查证意识的**极薄路由线索**——即普通业务目标或无名异常下模型易漏查盲猜，且线索很短、字节稳定并已与当前运行体实际可达的读取/查询入口配对。
2. **优先按需（分层参考、同源窄节点 Schema/状态查询或独立子上下文）的条件：** 低频、篇幅大、强绑定特定界面或扩展子域的操作细则与大型工具库定义，以及必须反映当前安装版本字段结构或当次运行受限现场的状态与日志证据（单个字段核验优先走窄节点查询，多源大篇幅检索再按延迟预算权衡独立子上下文）。
3. **结论反转条件：** ① 若宿主工具与规则总量极小且高频使用，直接常驻核心说明省去检索往返与压缩丢失风险，强拆多层按需反而劣化延迟与召回；② 若未来模型与检索路由在隐含诉求下消除漏触发，常驻路由索引可进一步缩减；③ 在多运行路径、多受管扩展与多源日志并存的系统中，全量常驻拉高窗口占用与漂移风险，零常驻路标又易漏调——此时按运行体实际可用能力条件装配的**“稳定薄路标 + 同版本按需参考/窄节点结构自省 + 受限运行期取证”**组合更具综合优势。

#### 4. 跨领域经典原理：对应关系、成立前提与失效边界

- **GNU Emacs“自文档化可扩展系统”原理（Stallman `1981`；GNU Emacs `30.2` `636f166c`）：由活绑定反向发现优于静态外置手册。** Stallman 指出高度可定制系统的帮助应直接从当前生效的命令表与绑定实时解析；Emacs `30.2` 允许在不知命令名时从按键、局部行为或关键词（`describe-key`、`apropos`）反向查到当前实际绑定的文档字符串并跳往手册。映射到智能体自我认知：当工具集、配置项或日志分类随版本、平台与角色动态变化时，从代码真实注册表或同源导出契约反向提供查询，比单独手写静态清单更不易过期。**成立前提与失效边界：** Emacs 运行在单一受信用户的本地进程内且查询起点明确；语言模型面对模糊自然语言目标未必主动发起查询，且在含外部不可信输入的会话中绝不能无封装反射全部内部符号表。[Stallman 1981 原始论文](https://www.gnu.org/software/emacs/emacs-paper.html) · [GNU Emacs 30.2 帮助原典](https://github.com/emacs-mirror/emacs/blob/636f166cfc86aa90d63f592fd99f3fdd9ef95ebd/doc/emacs/help.texi#L223)
- **Mirrors 元层反射设计三原则（Bracha & Ungar, `OOPSLA 2004`）：封装、分层与静态/动态时间对应性。** 元层自省通过独立于基础对象的 Mirror 能力提供，遵循：① **封装性**——元层实现被其抽象接口封装，不泄漏私有表示；② **分层性**——自省与基础执行分离，基础运行不常驻背负元层载荷；③ **时间与结构对应性**——严格区分定义期静态结构元数据与运行期动态实例状态，并按信任主体发放不同粒度的 Mirror。这从理论上支撑了“静态结构契约与单次运行态观测分离、按会话角色发放不同自省粒度”。**成立前提与失效边界：** 传统程序由开发者显式编码调用 Mirror；语言模型若在基础层对元层存在“彻底零线索”（过度分层），会在需要自省时静默跳过。[Mirrors 原始论文](https://bracha.org/mirrors.pdf) · [ACM 出版记录](https://doi.org/10.1145/1028976.1029004)
- **Plan 9 合成文件系统与进程私有命名空间（Pike et al. `1995`）及困惑副手授权归属（Hardy `1988`）：命名空间视图裁剪与代执行目的约束。** Plan 9 原典将内核与服务接口统一表示为合成目录树文件（兼有状态读取与控制写入接口），并按进程构建私有命名空间裁剪可见路径；Hardy（`1988`）则揭示当代办程序同时持有不同来源的权限时，动作是否合法取决于其此刻代表谁、向何处使用哪份授权。**结构类比与失效边界：** 借鉴到智能体系统，可将获准开放的系统认知与脱敏诊断投影为按运行体身份裁剪的统一**只读**视图（将原典中的写控制剥离至受管工具），并对诊断结果向外部或跨会话主体的传递做独立目的校验；但层级路径面对模糊意图仍需简短索引配合，路径裁剪不替代旁路子进程/网络鉴权，且 Hardy 原文针对操作系统能力授权归属而非直接评测大模型提示注入，仍须结合宿主具体工具与出站策略落实。[Plan 9 原始论文](https://9p.io/sys/doc/9.html) · [Hardy 1988 原始论文](https://cseweb.ucsd.edu/~dstefan/cse291-fall16/papers/confused-deputy.pdf) · [Hardy ACM 出版记录](https://doi.org/10.1145/54289.871709)

#### 5. 可超越洞察：根本原理、成熟边界与可检验改进方向

**5.1 穿透实现外壳的四条根本原理（归纳判断）**

1. **运行时自我认知的本质是“可行动的宿主本体地图 + 多源查证路由”，而非症状排障剧本或实时状态展板。** 智能体缺失的是预训练之外的宿主专有事实（能力与界面边界、配置与扩展契约、就绪门与记忆/执行端边界、观测入口及覆盖时段）。供给客观结构与查证路由能让智能体对未知异常自主形成“定位权威源—取证—核验”闭环；死板排障菜谱在根因变化时会误导操作，动态运行态写进静态文档则会立即失真。
2. **文档声明、本机版本合同、当前会话可调目录与受限运行证据四源分立，且“在盘、模型可自选、用户菜单可见、界面可调、工具获准”彼此正交。** 任一层的存在都不能替代其余层的核验；当通用文档与本机契约或当前会话实测入口冲突时，必须以当前安装契约与本会话实测可达能力为准。
3. **放置方式须沿多轮请求序列同时权衡“触发召回、前缀缓存稳定性、活动窗口占用与压缩/升级保鲜”。** 小规模高频核心规则可直接常驻；复杂宿主中常驻层应保持字节稳定以保护前缀缓存，仅承载安全交互红线与按当前可用能力条件装配的薄路由线索，将大型低频规约、版本化字段结构与实时运行证据交由按需读取、窄节点查询或独立子上下文承担。
4. **开放边界须同时闭合“谁能读、暴露哪些脱敏字段、结果能否向目标接收方传递”三道门。** 服务用户的系统认知对智能体无感开放、纯内部实现不予提供；对含秘密或跨主体风险的资源，既不能靠文档隐瞒代替鉴权，也不能只靠整文件放行/封禁一刀切，而须通过字段级脱敏/结构投影配合宿主执行与外传仲裁共同守住红线。

**5.2 成熟做法的适用边界与强行改变的代价**

在条件匹配时，保留经验证的简洁做法优于盲目堆叠复杂机制：
- **能力面极小且随包固定的轻量运行体**：直接在稳定系统提示中给出精炼边界说明或随包短路径（类似 Pi 默认路线在显式询问下的做法），免去额外检索往返与压缩后细节丢失；强拆多层技能或指南子代理只会徒增延迟与维护负担。
- **能力存在性与提示入口的双条件配对回退**（如 Hermes 核验 `skill_view` 与目标技能同时在场才提示调技能，否则回退文档路径）：在多运行路径工具集差异明显的宿主中，以极低复杂度消除了向受限会话投放不可达工具指引。
- **源码同源契约生成与分视图脱敏/结构查询**（如 Codex `ts-rs` 生成 `statusline.d.ts`、OpenClaw `schema.lookup` 与 `redact-snapshot`）：对单字段确认或配置排障，直接查代码同源结构或受限脱敏快照，既免去手写双份文档腐烂，又无需放行整份含密钥原件或拉起高延迟子代理。

**5.3 现有一流方案中经实证确认的局限与可检验改进方向**

对照本轮核实的本机样本与广域标杆，领先实现中仍存在三类有明确证据支撑的真实局限，可作为后续改进与实验验证的客观靶标：

| 已核实的具体局限与机制成因 | 可检验的改善目标 | 可证伪的检验方法 |
| --- | --- | --- |
| **1. 按需认知入口存在未触发风险，或受限运行体出现不可达指引。** 纯按需技能在特定评测任务中可能完全未被调用（如 Vercel Next.js 评测中默认技能 56% 未触发）；反之若不核对当前会话实际工具集与隐式调用开关就静态写入提示，受限会话/子代理会收到无法执行的入口。 | 在保证受限运行体不出现不可达自省工具指引的前提下，通过按当前可用能力条件装配且字节稳定的薄认知路标，降低隐含诉求任务下的漏查盲猜率。 | 构造一组不出现宿主专有功能名的隐含用户目标及受限子运行体用例，在同一模型下对比“纯按需无路标”“无条件静态指引”与“能力配对薄路标”三组的首次自主查证触发率、无效工具调用数、多轮缓存命中表现与任务完成率。 |

## 四、体系设计

### 4.1 审查标准

**提示词（首次）**

```text
请你和搭档先厘清本任务的核心目标、真实问题与边界，以宏观《愿景》与《架构演进方向》为指引，结合调研结果制定设计审查标准。注意我们要的是“审查标准”，全面覆盖架构、系统、产品与用户体验的基础正确性及世界一流卓越性要求，不预设具体方案，严禁脱离本质臆造无关要求而误导后续设计与审查。全程以结果为导向：成稿后双方须对照任务目标与要求独立审查，严守诚实底线、杜绝“为了达标而达标”；凡未通过就继续进行优化和修复并重新审查，直至真正符合要求后再落入文档交付。
```

> **设计独立审查标准（定稿）**
>
> 1. **紧扣核心本质，主支与完整任务闭环。** 方案紧扣产品运行期智能体自我认知这一真实问题：从首次发现陌生系统能力，到深入查阅权威契约、完成复杂扩展或方法定制并验证启用，再到对话报错或系统异常时依托系统结构、能力契约、就绪条件与可观测途径自主查证定位，均以用户的实际任务完成结果判定。方案须阐明常驻系统提示、当次动态注入、按需渐进式认知/方法参考与按需实时运行状态自省各自的定位，依据起效时机、遗漏后果、变化频率、内容纵深与多轮代价审定现有注入项与工具说明的留驻、精简、迁移或移除，形成双向闭环——核心身份与必要规则去重后继续生效，删减或下沉后各真实运行路径不丢安全约束与查找入口，所需权威资料与配套操作在适用运行环境真实可达，能清楚区分理解、准备操作身份、制作、验证与启用，动态注入与跨轮回放如实反映来源事实且不污染持久原文。凡混入仓库开发协作者工程技能、固化用户上层分工约定、把瞬时运行态塞进静态说明、把自诊断退化为死板报错处方、将大段静态参考与实时状态混塞同一窄接口、交付当前运行无法打开的路径，或只做外挂叠加的，不予通过。
> 2. **契合顶层指引，正本清源不妥协。** 方案严格符合[愿景](../vision.md)与[架构演进方向](../architecture/evolution-direction.md)这一唯一顶层标准：面向模型的认知呈现、工作流引导与分层专题参考保持轻量、支持由浅入深按需展开且可随模型演进独立替换，并与执行内核和会话持久状态解耦（严守内核包单向依赖边界）；底层的能力契约、事实权威、来源隔离、状态与可观测支撑做重做实，跨模型演进持续成立；核心状态、安全边界与持久执行稳固收敛在受控底座内、默认不向任意修改开放——在既有核心契约不变时，外围能力、受管扩展、命令或运行形态增减调整，相关认知随单一权威事实源在对应职责边界内收敛更新，不因同步认知牵动无关底座或散落多处手工同步。以目标最优结构倒推审视[现行核心架构](../architecture/overview.md)及生产实现（现行架构仅作现状参照而非妥协借口）：当阻断闭环的根因位于现有基础能力时，须以同一完整任务比较直接演进该底座与其他可行路线；凡绕开本次必须解决的底座根因、另造平行重复权威、留下断裂使用路径或升级即复发的结构债务，或脱离本需求预建无关通用框架的，不予通过。

#### 方案总览

本节为基于 `develop@8886b384` 生产基线的待实施设计，未经用户明确授权不改动生产源码。

核查生产基线可见，阻断智能体运行时自我认知闭环的根因不在“少几段提示文案”，而在六处底座短板：① 技能目录仅支持单文件且同名用户条目直接遮蔽官方内置技能，缺少正交可见性与多成员版本一致性锁；② 受管扩展 `extension(guide)` 直接暴露宿主机安装物理路径，无工作区与跨设备制作链路断裂；③ 用户配置的 `/trust` 访问规则（`PermissionStore` `deny`）仅匹配原始字面串且跳过非 `"confirm"` 工具，相对路径、符号链接与省略 `path` 的 `glob`/`grep` 子树枚举存在穿透缺口；④ `@zhixing-ai/orchestrator` 子运行与恢复编排缺少只读系统认知注入槽及完备 `RunContext` 继承/重建；⑤ 外部受管通道私聊共享 `"default"` 会话，缺少统一的窄运行态自省门控；⑥ `McpHub.callTool` 双错误路径与历史 `mcp:1`/`kernel:1` 日志附件会回显含密原始异常，跨会话、通道与系统续接来信在模型输入层丢失可验来源且扩展准备存在并发双跑。

遵循 `4.1` 长期价值准则，本方案**既不采用“绕开技能底座另造八节静态百科工具”的妥协外挂，也不在本模块内跨十余个领域预建“由单次技能读取触发全会话污点传染与五出口拦截”的错位包袱**（技能库定位为用户知行实例内常规任务可复用的方法资产，并非秘密保险箱或整机离线沙箱；秘密阻断在入口前置完成，全量本地离线隔离留归未来独立环境沙箱层统一承载），收敛为**三支柱正交架构**：

1. **精简恒定的常驻提示词与贯通 `@zhixing-ai/owner-kernel` 的五分支防伪来信投影：** 移除字面 `CACHE_BOUNDARY`、死标签 `dropped-turns` 与跨通道重复段，使单窗口常驻前缀逐字节恒定；将消息真实来源扩充为 `user`、`conversation`、`program`、`channel` 与受信宿主 `system` 五分支互斥契约，剥离续接展开旧身份、修复扩展准备并发双跑并在发送视图层做碰撞转义，宿主权限只认耐久元数据。
2. **带限定命名空间、正交可见性与确定性版本锁的统一 `Skill Package` v2 渐进披露底座：** 系统内置认知、受管扩展开发包闭包与用户纯文本多成员方法统一收敛至 `Skill Package`（`system:<id>` / `user:<id>` 限定身份消除同名劫持，配齐 v2 工具族 `skill_read` / `skill_save` / `skill_admit` / `skill_materialize` 与工作区静态校验 `extension_validate`）；支持正交 `visibility`、`≤ 12 KiB` 双偏移分页、强制 `expectedVersion` / `expectedRevision` 防跨版混读与并发覆写、新旧节点四路径兼容协商及多设备 `≤ 256 KiB` 断点续传，同时保持底层物理 WAL 帧格式（`FRAME_VERSION = 2`）与核心会话状态机零无关膨胀。
3. **全栈归一化 `/trust` `deny` 文件策略、窄实时自省 `runtime_inspect` 与 MCP/日志无秘密自诊断闭环：** 保持 `@zhixing-ai/orchestrator` 零产品依赖；分离 `filePathArgumentKeys` 并基于 `resolvedAccess.paths` 打通全等级 `/trust` `deny` 与免配额子树过滤；交付 `≤ 6 KiB` 纯 JSON 窄探针 `runtime_inspect`（按固有通道 ID 与当轮通道出入站并集严控表面边界）；闭合 `McpHub.callTool` 双错误路径白名单 `McpPublicFailure` 及 `mcp`/`kernel` 新旧日志附件脱敏。

**2.1 由顶层指引推导的目标结构与长期边界取舍**

遵循[愿景](../vision.md)与[架构演进方向](../architecture/evolution-direction.md)，全局职责沿三条正交边界收敛：

#### 3. 核心契约与系统机制设计

**3.1 统一 `Skill Package` v2 模型、分页版本锁、整包保存/准入与混合版本同步**

1. **包结构、限定身份与正交可见性契约**
   - **不可变纯文本包归档（`SkillPackageArchive v1`）：** 系统与个人技能包成员严格限定为无 NUL 字节的合法 UTF-8 文本/源码（零二进制成员）。`SkillCatalogEntryV2` 在原 12 键基础上扩充 `visibility: { modelAutoIndex: boolean, userSlashCommand: boolean }` 与可选 `packageRef: ArtifactRef`（确定性无压缩归档，含根 `"SKILL.md"` 与附属成员清单 `[{ path, mediaType, offset, bytes, sha256 }]` 及连续字节，整包修订改变任意子页均更新 `packageRef` 与条目 `digest = protocolDigest("SkillCatalogEntry", 2, entry)`，经 `FileArtifactStore.readRange` 区间复核；硬预算：总成员数 `≤ 64`［根 + 最多 `63` 个子资源］、单成员 `≤ 512 KiB`、封装后整包 `≤ 2 MiB`［`2,097,152 B`］、路径深度 `≤ 6`、规范化相对路径 `≤ 256` UTF-8 字节）。
   - **限定前缀、顶层 `disabled` 总闸与正交可见性：** 先剥离 `"system:"` 或 `"user:"` 前缀再对局部名调用 `skillNameToId`；系统包固定 `userSlashCommand: false`；`SKILL.md` frontmatter 支持解析 `disable-model-invocation`（映射 `modelAutoIndex = !val`）与 `disable-slash-command`（映射 `userSlashCommand = !val`，缺省均为 `true`）。**顶层 `disabled: true` 为硬禁用总开关**——无论传 `user:<id>`、`/<id>` 还是调 `skill_materialize`，遇 `disabled === true` 一律硬拒（返 `skill-disabled`）；而 `disabled: false && !visibility.modelAutoIndex` 仅从自动索引隐藏，仍允许按显式 ID 或 `/<id>` 读取。`SkillCommandSource`（消费 `skill.listV2`）按 `!disabled && visibility.userSlashCommand` 暴露 `/` 菜单，用户首词输入非保留命令 `/<id>` 直达未禁用 `user:<id>`；仅顶层耐久指派首次成功读 `user` 根入口幂等记 `1` 次 `skill-usage`。

2. **`skill_read` 版本延续与全响应 `≤ 12 KiB` 双偏移分页**
   - **输入契约：** `{ id: string, resource?: string, expectedVersion?: string, cursor?: string }`（`additionalProperties: false`）。资源路径仅接受规范化包内相对路径（禁绝对路径、`..`、URL、重解析点与大小写冲突）。
   - **打开包根入口（省略 `resource` 且省略 `cursor`）：** 允许省略 `expectedVersion` 取当前有效版（显式传入时亦做比对），返回 `{ id, packageVersion, revision?, readTemplate: { id, expectedVersion: packageVersion }, writeTemplate?: { expectedVersion: packageVersion, expectedRevision: revision }, content, navigation, nextCursor?, eof }`（对 `user:<id>` 同时返回当前条目 `revision` 与可直接带入 `skill_save` 的写回基准 `writeTemplate`；只读 `system:<id>` 不返回 `writeTemplate`）。`navigation` 列出成员目录 `{ resource, kind, mediaType, bytes, summary }`（`summary ≤ 160 B`），中间专题页同样返回包内 `referencedResources`，使无通用文件工具的运行无需预知文件名即可逐级发现全部成员。
   - **读取子资源（传入 `resource`）：** **`expectedVersion` 为必填参数**（仅确属不依赖前序页面的独立首次直达读取才可显式传字面量 `"latest"`）。当发生更新或切机导致 `packageVersion !== expectedVersion` 时，立即阻断无声混读并返回严格受整包 `Buffer.byteLength(json, "utf8") <= 12288` 约束的 `version-mismatch`：
     - 若新旧两版归档清单均在本机在场且含完整 `changedResources` 的 JSON 装入 `12,288 B` 预算内，返回 `{ error: "version-mismatch", diffStatus: "complete", currentPackageVersion, changedResources: [{ resource, change: "added" | "modified" | "removed" }] }`；
     - 若旧版已被 GC 回收、当前节点仅持新版或差异超出 `12,288 B`（如 63 个长路径成员全量变更），统一降级返回 `{ error: "version-mismatch", diffStatus: "unavailable", currentPackageVersion }`，指引调用方经当前版根 `navigation` 与标准 `nextCursor` 重核补读（补读或翻页途中再次变版同样拦截）。
   - **全响应 `≤ 12,288 B` 双偏移游标：** 整份序列化 JSON 严格 `≤ 12,288` UTF-8 字节——编码器优先装填当前资源文本切片（单行或单声明块超剩余预算时按合法 UTF-8 码点边界强制推进非零 `textByteOffset` 并标 `partialBlock: true`），再用剩余预算装填导航条目；满页签发 `nextCursor = encode(namespace, id, packageVersion, resource, textByteOffset, navIndex)`，保证每页严格正向推进，仅当正文与全部导航条目枚举完毕才返回 `eof: true`。

3. **自有整包保存（`skill_save`）、权威提交保活与三阶段可见性**
   - **工具能力表对齐与确认展示：** 在 [factories.ts](../../packages/tools-builtin/src/factories.ts) `BUILTIN_TOOL_CAPABILITIES`（及 [tool-display-names.ts](../../packages/core/src/tool-display-names.ts)）完整登记 v2 工具族——对齐现行 `load_skill: { authorityWrite: false }` 的注册表语义，将 `skill_read`、`skill_materialize`、`extension_validate` 标为 `authorityWrite: false`，将 `skill_save` 与 `skill_admit` 标为 `authorityWrite: true`。`skill_save` 支持单文件或附带纯文本 `resources` 整包，并废除现行 `catalog-application.ts:337-362` 在保存时静默读取当下最新 `revision` 补填的做法，建立公开读写基准合同：① **新建技能**可省略写回基准，但仅限目标 `user:<id>` 尚不存在（若同名条目已存在而未传基准，立即拒绝并要求先调 `skill_read` 核对或由本人在确认卡片中显式选择覆盖）；② **更新已有技能**必须传入从 `skill_read` 取得的写回基准（`expectedRevision` 及/或 `expectedVersion`），在**打开 `ConfirmationBroker` 确认卡片前及最终暂存/权威提交时双阶段检验该基准**（无论并发变更 `A → B` 发生在读后确认前还是确认后提交前，均确定性返 `revision-conflict`，绝不把基于 `A` 的草稿静默写到 `B`）；③ **仅改根保留原附件**——更新已有多文件包而省略 `resources` 时默认沿用已核基准的既有附属成员，显式传入 `resources` 增删改时才变更附件。保存维持经 [request-builder.ts](../../packages/core/src/confirmation/request-builder.ts) `ConfirmationBroker` 批准：确认卡片完整展示名称、说明、模式、`visibility`、所基于的基准版本、`SKILL.md` 全文及最终附属 `resources` 清单与正文，已知高置信凭据经 [secret-scrubber.ts](../../packages/core/src/security/secret-scrubber.ts) 自动抹除并如实回报计数。
