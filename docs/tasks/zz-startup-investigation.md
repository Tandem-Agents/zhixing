### 2. P1：主要慢在已经失败后的恢复等待

通过正式日志读取应用取得本次事件，时间为本机 UTC+8；使用事件发生时间而非落盘时间计算：

| 时间 | 已记录的事件 |
| --- | --- |
| 12:09:01.758 | 前台 `runtime.started`，mode=`repl` |
| 12:09:09.770 | 子进程 `runtime.started`，mode=`on-demand` |
| 12:09:11.458 | `runtime.hostStarted` |
| 12:09:16.147 | 宿主清理结束，`runtime.failed` 与 `stopped`；原因见 P3 |
| 12:09:43.943 | 前台 `host-connection-failed`，仍称“旧的服务状态已失效，新的知行服务仍在启动” |

**已证实**：从前台开始到失败共 42.185 秒；宿主已经记录失败并结束清理后，前台又等了 27.796 秒。

**根因**：[daemon.ts](../../packages/cli/src/serve/daemon.ts)只在最初默认 5 秒 handshake 内跟踪 child exit，超时后返回 `starting` 快照；[core-host-connection.ts](../../packages/cli/src/runtime/core-host-connection.ts)据此再进入默认 30 秒恢复窗口，只重新发现 endpoint，未继承这次启动的子进程终态。后续失败不能及时结束等待，最后仍显示先前的“启动中”原因。原生构建类的注入时钟探针复现了 30,000 ms 模拟等待、122 次发现调用后返回旧原因；此探针没有真实启动宿主或连接网络。

**复审核验**：再用真实 Node 子进程与实际构建的 `CoreHostConnection` 验证，缩短时间窗而不替换时钟：231 ms 返回 starting，子进程在 630 ms 以非零码退出，前台仍到 1,454 ms 才失败，并继续显示 starting。子进程只执行定时退出，不启动业务服务。此实验补实了“进程真实退出后，连接恢复仍消费旧快照”的因果关系。

**同路径问题**：启动进度提示在 4 秒后固定切为“首次启动可能需要几秒”，并没有首次启动判断；降级浏览器接收 `error` 却不呈现安全原因摘要。当前 `zz status` 将 on-demand 的 stopped/stale 投影成“不需要后台运行”，无法帮助用户区分正常未运行和刚刚启动失败。

**未确定**：前台到子进程开始的 8.012 秒尚无足够阶段证据，不能分别归因于凭据解锁、托管状态协调或模块加载；也没有这次子进程的精确 OS exit 时间。上述差额不全部记成资源探测耗时。

### 3. P2：正常写者竞争也触发不可用警告，且恢复证据缺失

**已证实**：此后实际日志读取成功，保存了本次前后台错误；`source=logging` 查询为空。前台第一条事件延迟约 4.969 秒落盘，子进程第一条约 5.402 秒落盘，说明存在初始化／缓冲阶段，不能据此单独判断具体失败。

**根因中的确定部分**：[Recorder](../../packages/core/src/logging/recorder.ts)在持久步骤外层使用无参数 `catch`，把异常统一降为 `storage-unavailable`；[运行入口](../../packages/cli/src/logging/runtime.ts)再把健康回调统一显示为用户看到的那句话。恢复后清除 `lastFailure`，却不发恢复回调；补记健康事件仅由 `lost/unconfirmed` 增长触发。于是一次“暂时写前拒绝→原记录后来全部落盘”的降级，会留下警告、丢掉原因，查询也没有这段降级／恢复经过。

**复现**：以真实构建 `LogRecorder` 配合纯内存 sink，让 initialize 首次抛错、下一次成功。结果为：一次 `degraded/storage-unavailable` 通知；最终 ready、队列 0、丢失 0；落盘只有原业务观察，没有故障原因或恢复事件。此为机制验证，不是假称复现了用户当时的首个异常。

**复审补出的触发机制**：[LocalLogStore](../../packages/core/src/logging/storage.ts)写步骤使用一次 `tryLock()`；拿不到锁便抛“日志存储正在维护”，Recorder 将正常竞争与存储故障走同一降级分支。前台与后台各有 Recorder、共同写一个日志根，竞争是合法运行形态。原方案只补错误记录，仍会让正常启动产生同样的不可用警告，不能算完整修复。

**真实 Windows 文件链复现**：同一隔离日志根内启动两个真实入口 Recorder，使用实际文件进程、OS 锁、写者观察和容量实现；只包装存储方法收集异常，不注入失败。A 在约 3,215 ms 因锁忙告警，随后重复两次锁忙，约 5,767 ms 初始化成功，原事件成功追加；B 后续也在并发追加时因锁忙告警，重试后成功。证明“警告→后来日志可读”可以由正常写者竞争产生。该实验没有复用用户数据，也没有模拟历史原始异常。

**未确定**：现存证据无法确定警告当时究竟由准入拒绝、跨进程锁忙、文件 owner 或其他存储错误触发。P3 的磁盘采样问题是同链候选原因，不能未经证实就认定 P2 与 P3 完全共因。原始异常已被当前实现丢弃，继续扫描旧日志不能恢复不存在的证据。

### 4. P3：共享容量适配把磁盘采样缺失误报成内存背压

**直接失败证据**：子进程的 `runtime.failed` 记录为：

```text
reason: host-or-preflight-failed
error: Storage maintenance was not admitted: backpressured:memoryReservationBytes
```

**已复现的根因机制**：

1. [日志入口](../../packages/cli/src/logging/runtime.ts)以 `createDirectory:false` 创建容量运行时；[Host 入口](../../packages/cli/src/serve/topology-command.ts)复用 `logging.capacity`，因此它实际承担整个业务启动的资源准入。
2. [device-capacity-runtime.ts](../../packages/cli/src/serve/device-capacity-runtime.ts)让 `createDirectory` 同时决定采样实现。false 会启用 250 ms 新鲜期的异步磁盘缓存；冷启动／缓存过期时 `read()` 抛错，零等待请求只触发刷新而不能等到结果。
3. [资源仲裁器](../../packages/core/src/resources/device-capacity.ts)将任一探测异常转换为全部为零的压力快照，随后按第一维报告 `memoryReservationBytes`。磁盘信息缺失被误解释为真实内存不足。
4. [存储维护合同](../../packages/core/src/resources/storage-maintenance.ts)要求持锁／串行段零等待准入。两者的组合使正常设备在采样空窗被拒绝。拒绝是否最终导致启动失败，还取决于恢复 owner 能否推进；只复现一次拒绝不足以判定完整根因，复审结果见下文。

**原生构建探针**：同一真实本机数据根，只申请资源、不执行任何文件写入。在用户目录中，冷态／过期的零等待请求均拒绝，允许采样完成的请求均通过。随后从项目目录走真实 `runHoldingMaintenanceExclusion → runStorageMaintenanceStep`：cold 与 expired 精确抛出上述 `StorageMaintenanceAdmissionError`，ready 成功；拒绝期间 OS 可用内存约 6.57 GB，操作体没有执行。由此证明该错误可以由探测状态制造，并不表示机器只有零可用内存，也不依赖调用目录。

**证据边界**：原进程未保存压力采样和具体维护步骤调用栈，不能断言历史当刻绝无真实内存压力，也不能指定哪个维护叶步骤是唯一触发点。已确定的是本次直接失败原因，以及同一生产适配链上能精确复现它的合同缺陷。冷态零等待保守拒绝本身可以合理；错误在于虚构资源维度、未闭合采样就绪与锁外接续，而不是应把所有请求无条件放行。

#### 复审：为什么已有锁外重试仍可能失败

先做反证：实际构建的 `setupAuthorityRuntime` 在隔离目录中，使用真实异步容量实现，遇到冷态／过期拒绝后仍能成功。再生成 160 条 anchor、89 条 executor 的合成 Authority 记录，装配也通过。因此撤回“有这个报错就已经证明整次启动根因”的推断。

随后沿同一生产恢复链定位到可重复的停滞：

```text
SurfaceAssetCoordinator.recover（外层串行段，锁外重试，5 秒期限）
  → ledger.load / synchronize
  → ArtifactLifecycleIndex.initialize
  → 依次取得两个 Authority originCheckpoint
  → FileDurableProjectionIndex.initialize
  → projection-scrub 零等待准入
```

[生命周期索引](../../packages/core/src/authority/artifact-lifecycle-index.ts)只有内部索引初始化成功才保存 `sources`。若准入被拒绝，下一轮会重新读取两个 origin；[表面资产恢复](../../packages/core/src/authority/surface-assets.ts)虽在锁外等 25 ms，但容量采样没有独立刷新进度。如果恢复前缀超过样本 250 ms 的有效期，每一轮到达准入时样本都再次过期，形成“刷新成功→重走前缀→样本过期→再次拒绝”。延长重试时间不能消除这个循环。

**因果实验**：在真实构建的装配链中，只给 `originCheckpoint()` 的正常返回增加每次 300 ms 的异步延迟，模拟有限 I/O 延迟；不注入准入错误、不改资源限额。同一隔离 home 上，同步采样对照成功（1,797 ms）；日志入口采用的异步采样失败（5,148 ms），累计 8 次 `projection-scrub` 背压，最终抛出与用户记录相同的错误，OS 可用内存约 6.29 GB。没有模型或平台调用。

**方案反证实验**：保留同样的 I/O 延迟、250 ms 样本有效期、原资源策略和零等待准入，仅在诊断进程内让异步采样按生命周期独立刷新（100 ms，单在途，结束后停止），真实装配 1,823 ms 成功、无拒绝。这验证了应修复采样的推进机制；实验参数不是未经评估就写死的产品配置。此为隔离设计验证，产品代码未修改。

这次复审补齐的是**可达失败链及其修复方向**。延迟为明确注入条件，不能宣称历史那次正好卡在这一叶步骤；原始日志没有留下能作此判断的证据。

## 解决方案与验收

### 实施顺序与责任

| 顺序 | 根本修复 | 同机制覆盖与约束 |
| --- | --- | --- |
| 1 | **修正共享容量采样合同与推进机制。** 目录是否创建仅控制文件副作用，不再隐含切换准入语义。容量运行时拥有统一异步采样器；在其有效生命周期内单在途、提前刷新，未就绪／失败／过期与有效压力值分开表达。 | 不能只预热一次或依赖失败请求触发采样，否则较慢恢复前缀仍会使每轮样本过期。保留有限样本年龄及真实内存、磁盘安全余量；未知压力保守拒绝，但不得伪造零内存。进入持锁步骤后仍零等待，锁外恢复负责有界接续。入口拥有容量生命周期，Host 复用，业务和 Recorder 排空后关闭采样；失败、取消、只读命令也须释放所有者。不得另开仲裁器、让日志关闭共享容量或盲目重放已有部分效果的业务。 |

### 新增 P12：真实主动取消被呈现为模型错误（待定位）

本机测试对话 `chat-20260924-e85b` 的运行 `run:6ba01c4b-bbc9-498e-96b0-d614a224445f`，在 UI 已显示思考后按 Esc。实际权威状态为 running → cancel-requested → cancelled（14:58:07／10／12 UTC），消息未进入已提交历史；但 CLI 显示 `错误 (provider_error)`，取消事实与用户反馈不一致。此前两次取消操作发生在完成之后，不能算取消成功证据；本次才是已运行阶段的取消实证。继续核对 provider abort、Kernel 终态、owner cancel 与前台 error/end 投影，查明共同机制后修复，不改写真实 provider 故障或取消权威。

P12 根因与方案（修复前）：Kernel 的真实错误为 `Executor usage id was reused with different content`，发生在 owner 宣告 cancelled 后约四秒。本机 executor 直接暴露 ledger.cancel，先把未完成的模型用量按预留额结算并出具 halted 证明，之后才由 ConversationManager 中断会话 runtime；实际执行的是另外创建的 assignment runtime，未被这个中断命中。真实模型随后报告实际用量，与已结算的相同 usageId 内容冲突。Mesh conversation 分支也先 ledger.cancel 再 worker.abort，具有相同错误顺序；job 分支已经使用 begin→停止→finish，不改其语义。

修复复用既有两阶段取消合同：先耐久登记取消 fence，再中断**本次 assignment 的实际执行体**，只在 Kernel generator 及其清理已结束后结算用量、产生停止证明。执行中返回 cancel-requested，沿既有 owner 接续再次完成；不得持 owner 终态锁等待整个业务提交，也不得阻塞运行内部发起的取消形成自等待。执行登记仅为进程内生命周期，不新增事实源；已取消且尚未启动的执行不得再调用模型。远端 worker 同时补齐 generator.return 清理，取消尾声不能把已接受的 owner 取消改判为执行失败。核验同机制的 batch、ticket、恢复、消费者提前退出与 supersede（其只 fencing 未开始的执行，不停止已运行 assignment）。保留用量身份一致性校验，用受控的实际资源预留／延迟消费回归证明取消不会提前结算，再以真实模型主动取消及后续正常命令验收。

### 已确认的机制缺陷与尚未查清的部分

1. **首屏与计时的起点过晚。** `index.ts` 先导入 Providers／日志设施，再等待 `startup`、完整 `repl` 与连接模块加载；此后才创建进度组件，直到开始连接才调用 `begin()`。加载期间没有界面，时间也不计入等待提示。这是确定的入口时序缺陷。
2. **前台加载边界过宽。** REPL 通过配置编辑、本机 workspace 管理、只读失败浏览等静态依赖带入后台实现；打包产物实测印证，不能仅凭入口静态 import 白名单判为轻量。应按实际使用时机加载配置、故障浏览及管理实现，收窄公共导入，避免为展示并连接已有服务预先装入完整后台。
3. **日志事务仍依赖业务事件循环推进。** `LocalLogStore.#step` 在业务进程取得跨进程锁后，由同一线程逐步等待文件调用、执行校验与治理，直到 `finally` 解锁。独立 native 文件进程只隔离单个物理调用，没有隔离整个事务；模块加载／恢复占用事件循环时，已持锁事务仍会被拖住。它是源码可证实的结构耦合，不能宣称前轮已经从架构上解除。**当次具体是谁持锁、卡在哪一步尚缺直接证据，不能直接把这一机制判作当次等待的唯一原因。**
4. **初始化错误证据过粗。** `storageFailureReason` 将非专用类型、非少数系统错误码统一压成 `storage-unavailable`。因此后台那次失败无法区分文件操作、native 会话超时、治理校验等原因；继续声称已经找到该次失败底层原因是不客观的。

### 处理方向与闭环条件

- 启动最外层先提供轻量反馈，连续计量加载、连接和恢复直到可交互；拆开真实前台依赖边界，以正式构建的加载图及真实入口验证，不只移动提示位置。
- 日志正常初始化／队列等待与真正存储故障分别呈现；故障仍如实告知。正常启动反复受阻不能作为默认产品体验，也不能靠提高降级门限、清空日志或只改文案闭环。
- 先用只包含操作名、稳定错误类别、持锁区间和耗时的临时探针取得受阻持有者证据；核对碎片化及临界文件数下的实际事务成本。根据证据决定日志事务整体隔离、分段写入及治理边界的具体改法，保留耐久、总预算、权限和崩溃恢复合同，不能未经验证便把候选方案当作已完成根因分析。
- 验收必须从全局命令进程启动开始，测到首个反馈和可交互，分别记录冷／热条件；同时核查前后台日志是否确有未确认／丢失、反复初始化和告警。现有证据不足以再次宣布本问题收尾。本轮未停止用户正在使用的前台／后台、未调用模型、未改变配置或提交 Git。

### 授权修复与实施前裁定

用户随后明确授权同时彻底修复启动慢与日志降级。经正式 `zz stop` 安全停止后，原 home、真实 ConPTY 的带探针冷启动到欢迎界面 25.656 秒；该轮未复现告警。方法计时确认前台托管检查约 2.998 秒、Host 配置检查 3.247 秒、Authority 装配 2.389 秒、会话服务装配 1.805 秒。Host 模块加载产生 931／938 ms 事件循环停顿，日志持锁最长 2.383 秒；每批文件数临界回收有多次完整治理发布。探针不记录业务正文或凭据，探针时长不作为最终性能验收。

实施采用同一套现行权威合同：前台以窄 client／types 入口接入，编辑、离线故障浏览和管理实现按使用时机加载；界面加载与已有连接建立不再串行重复准备。日志把完整 Store 写事务移到专用执行进程，仍用原 Store、原跨进程互斥、原预算及恢复规则，主线程 Recorder 的有界队列不变；资源许可在持锁前由原容量 owner 预留，写进程内计量、解锁后结算，不在持锁期间往返依赖业务线程。初始化错误保留有限的操作／错误类别，不传任意异常正文。此方案处理已证实的主线程耦合，不能反推为已找到 11:21 那次笼统错误的唯一原因；正常启动和故障注入须共同证明整改后的行为。

实施复测补充：线程原型在真实 Windows 冷启动中使凭据进程退出后的等待停住，日志 native helper 仍存活；同一配置在没有该并行线程时能完成启动。这与 Windows 同进程多线程创建子进程的可继承管道竞态相符，不能用超时掩盖。最终采用独立写进程隔离操作系统句柄表，容量预留合同不变，写者观察沿用所属入口 PID；入口 IPC 断开时写进程必须关闭存储并退出。线程方案不进入交付。构建时也必须先关闭旧版入口，避免 Windows 正在执行的 native 制品无法替换，随后统一使用新构建验收。

独立进程版已真实启动及退出，无日志告警；但无探针冷启动仍为 31.656 秒，不能收尾。CPU 采样显示 Host 的 45 秒观测窗有约 13 秒处于执行，其中热点集中于 Authority WAL 的信封解码、逐帧扫描和重复哈希。现有 `readSnapshot/readStream` 每次从头扫描，`readProjectionTail` 在追加后也全量重验；8192 项校验摘要缓存只省 schema 校验，未省磁盘重读、帧链重验。现有真实 WAL 已是 versioned，不是旧格式迁移问题。

下一步在现有锁与物理身份校验下复用**有界、已验证的不可变 WAL 字节与边界证明**，读取仍返回新解码对象；文件身份、长度、mtime/ctime 任一变化即失效，缺文件、替换、损坏和半帧仍走原校验／恢复。缓存仅属该日志实例，不落盘、不存可变业务对象、不改变 fsync 成功边界。先覆盖篡改、替换、追加、调用方修改回放对象和容量边界，再用真实入口核验收益；没有实际收益的优化不保留。

进一步因果实验纠正了凭据耗时归因：同机相同隔离调用，短的 DPAPI 脚本约 0.4 秒；现有同时包含 probe/protect/unprotect 和 Base64 转换的长脚本，单是 Windows CreateProcess 返回就约 1.5–2.3 秒，DPAPI 输出只再需约 0.4 秒。不能笼统归罪于 DPAPI 或进程隔离，也不更改系统安全策略。将脚本收敛为单次确定操作，管道直接传 32 字节密钥，去掉 PowerShell 内重复 Base64 转换及不可达分支；原 DPAPI CurrentUser、已保存密文、隔离进程、缓冲擦除与失败关闭合同保持不变。用既有密文重开、二进制往返及真实启动证明兼容与收益。

WAL 全量已验证字节缓存的实机收益不足（31.656→31.141 秒，不能排除测量波动），撤回该候选实现与专属测试；保留扫描器已完成前缀验证后去掉重复链计算这一等价简化。前台启动订阅回放还会为多个历史终态分别请求同一份输入历史；后续只合并同时待查的终态输入，查询期间新到的终态必须再查，不缓存查询结果，也不省略来信／失败／取消展示。

进一步核查缓存候选的失效原因：自身每次耐久追加也会使整份已验证前缀失效，恰好是启动恢复／接续的高频路径；采样中 WAL 扫描累计约 6 秒 CPU 时间。改为复用同一已验证前缀，并且仅对本实例持锁、成功 fsync、追加前后物理身份均一致的已知新帧延伸证明；其他变化仍全量重验。将恢复、反篡改、容量上限、追加后命中及回放对象隔离一起验收，不以仅首次扫描后静态重复读的微测代替实机收益。

轻量计数探针进一步定位到读取放大：一次冷启动及界面恢复出现 760 次 `transactProjection`，前台同一订阅回放触发 5 次历史查询。`inspectMessage`、`messageInputsOutsideHistory` 和 Mesh ownership 仅判断一个会话，却调用 `listSessions` 并逐一读取所有会话权威；已有 `sessionExists` 可以保留身份、归属与删除检查而只读取目标。前台每条历史 Final 各自读取同一页历史；同一事件批次、同一会话及同一游标的读取可合并，查询开始后到达的新事实必须重新查询，不能把进行中的旧快照当成新事实的证据。按这两个明确调用边界修复并验证缺失／删除会话、分页、迟到通知及输入展示；不省掉权威校验、不缓存业务决定。

上述修复后冷启动仍需 23.610 秒。更底层的问题是**只读投影被建模成写事务**：会话 `#select/#selectPublish/#selectFinal` 即使持有覆盖完整未变 WAL 的已验证游标，也通过 `transactProjection` 创建、fsync、发布、删除排他锁文件，然后才发现无需重放。恢复时数百次只读调用重复这一写入协议。增加明确的只读投影端口：仍经实例串行队列，在原游标的路径／日志身份／inode／长度／mtime／ctime 全部吻合时，以该次 stat 为读取时点返回已验证投影；不调用决定函数、不允许追加。任何变化、缺文件、无游标或未知身份均退回原持锁校验／恢复流程。所有能追加的事务继续取得排他锁并在锁内重新裁决。验证并发追加、半帧、文件替换／损坏、读写次序与无锁命中，再测真实启动；这不是用超时缓存牺牲一致性。

该机制同时覆盖资源账本和 Delivery 的纯同步读取；资源账本在每次协调前后都会同步，它们也不能反复创建写锁。另一次广泛回归暴露了整份 WAL 字节缓存候选在快速尾部修复／篡改序列中未拒绝损坏，独立重跑未稳定复现；不以重跑通过关闭该风险，已撤回整份字节缓存及追加延伸。保留现行完整扫描、原有不变游标校验和明确的只读端口，并继续执行篡改／恢复回归。
