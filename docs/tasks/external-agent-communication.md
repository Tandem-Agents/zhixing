# 外部智能体通信与消息接收能力

> 类型：模块开发 · 范本

## 一、需求与目标

跨智能体通信是一体两面：主动给其他智能体发消息，本质只是调用工具去使用对方已有的入口，动作本身并不特殊；真正决定通信能否成立的底层关键，在于智能体系统自身如何让外部给自己发消息、对外提供了怎样的消息接收能力。从 OpenCode、Kimi Code、ZCode 到 Codex、Claude Code、Antigravity 等经过实际验证的智能体来看，支撑跨智能体通信的底层接收能力已成为广泛趋势。更关键的是，无论外部如何演进，这项能力本身就是跨智能体通信与协作必不可少的基石；如果知行缺乏这一能力，就会构成明显短板。

因此，需要先核查清楚知行整个系统当前是否已经具备这样的外部消息接收能力或类似能力，摸清现有机制的实际用法、适用条件与能力边界。

在核清真实现状并研究一流实践的基础上，以宏观[愿景](../vision.md)和[架构演进方向](../architecture/evolution-direction.md)作为唯一顶层指引与硬性标准：无论当前尚不具备（需设计整套方案），还是已具备相近能力（需评估升级与优化），都围绕本需求分析应当提供怎样的架构能力、系统功能、产品体验与用户体验，并据此倒推、审视[现行核心架构](../architecture/overview.md)中与本需求相关的部分。现行核心架构只是当前现状而非上位指引——若相关主体仍契合顶层要求，就聚焦需求涉及处做局部演进；若推演表明现有结构确需较大调整，也在严格符合愿景与架构演进方向的前提下渐进式升级，既不拿现状反过来限制设计，也不脱离本需求空谈全局重构。

## 二、系统现状

### 2.1 审查标准

> **现状梳理审查标准（定稿）**
>
> 1. **全貌查清，定性准确。** 覆盖整个系统的相关入口与底层模块，明确回答知行当前是否已具备外部消息接收能力或相近能力，以及实际具备到什么程度。分别写明哪些入口可供外部直接调用、哪些入口受特定条件限制、哪些机制仅在系统内部起作用，不拿单一路径代表全系统，也不把仓库开发工具或未实现的文档设想混作现有产品能力。
> 2. **架构、功能与实际用法讲透。** 如实呈现知行与该能力相关的现行架构结构、模块职责与功能机制，并说清已有或相近入口的适用条件、实际调用方式、处理结果及受限止步点；确实没有的部分直接指明缺位事实，使现有全貌与能力边界一目了然。
> 3. **证据扎实，核心无盲区。** 关键判断均须有明确版本的生产源码依据：判定某项能力可用，须核实从入口到处理结果的真实调用链；单条路径受限，须指出具体止步位置；全系统不具备，须说明已核查的相关范围与依据。仅靠读码无法确定的运行表现须补充实际验证，不凭接口名称或文档描述推定可用；结论严格对应证据覆盖范围，影响核心判断的事实必须查实，不留“待实测”空白。
> 4. **结构清晰，精炼自足。** 围绕能力实质组织内容，不按源码目录堆砌流水账，不混入无关模块细节。表述准确凝练、独立自足，读者仅凭正文即可零歧义掌握知行当前的真实状况。
>
> 以上四项须同时满足，共同构成现状梳理的优秀通过标准；有充分依据确认能力缺失或受限，同样符合本标准。

### 2.2 现状正文

#### 现状总览

以下内容基于 `develop@c1b4277e` 的生产源码、既有自动化测试及隔离环境下的构建版实测，经双方独立核查并交叉复核确认。

在已配置可用模型的单机知行上，**具备本机当前用户权限的外部程序（含同机运行的外部智能体）已经可以向知行发送消息、定位已有对话或创建新对话，并取得运行结果**。这一能力通过两条现成的本机客户端入口成立：核心宿主的本地 WebSocket JSON-RPC（`/ws` 的会话与工作场景方法）与知行 CLI 的非交互标准输入文本会话（管道调用 `zz` / `zhixing`）。

与此同时，**知行当前没有面向外部智能体或跨产品会话的独立身份、寻址目录、按外部会话地址主动回投的协议、内置通用 HTTP 发信接口或单次 CLI 发信子命令**；通过这两条现成入口提交时，外部程序以知行客户端身份调用，从连接通知、标准输出或对话历史中取得结果。全系统其余相关路径按实际边界分为三类：受管消息通道扩展与配对设备 Mesh **受特定外部平台或设备配对条件限制**；知行内部的“对话通信”与扩展阶段延续通知 **仅在系统内部对话或受管流程间起作用**；MCP 模块、交互终端多进程内部传输及仓库开发期协作脚本 **不提供产品侧外部消息接收能力**，仓内文档中的未实现接入面设想亦不构成现有入口。

#### 1. 相关架构与运行机制

- **核心宿主与接入面分离。** 单机默认以 `anchor + executor` 角色运行核心宿主（`zhixing serve`），默认监听回环地址 `127.0.0.1` 上按 `ZHIXING_HOME` 派生的确定性端口，并在 `ZHIXING_HOME` 下维护 `server.pid`、`server.port` 与共享认证令牌 `server.token`。交互终端、CLI 文本会话与外部 RPC 客户端均作为接入面连向宿主，无需操纵现有终端界面进程；CLI 按需拉起的后台宿主（`on-demand` 模式；显式 `zhixing serve` 与 `--managed` 托管模式除外）在连续两个 60 秒检查周期无活跃 RPC 连接、无在线通道且无已启用定时任务时自动发起排空停机，正在执行的普通对话轮次本身不计入常驻保活条件。多设备拓扑下，各节点按角色（`anchor`、`executor`、`surface`）、本机对话归属与配对状态提供本机处理或向当前值班主控设备转发受支持的第一方会话方法（纯 `surface` 角色不启动本地 WebSocket 服务）。
- **统一对话准入、单对话排队与输入边界。** 对外会话 RPC、CLI 文本会话与受管通道最终汇入宿主装配的 `ProductApiDispatcher`、`ConversationManager` 与 `ConversationProtocolRuntime`。每个 `conversationId`（主对话、`ws:<sceneId>:<localId>` 工作场景对话、`local-<prefix>-<ULID>` 设备本地对话）独立维护注意力窗口、耐久运行账本、单对话串行门、有界待处理队列（默认最多 5 条普通待处理输入）及独立于运行体存活的观察者名册（`observers`）。对外会话 RPC 与 CLI 管道提交的是普通用户轮次（`admit-agent-turn`）：目标对话空闲时立即启动运行；目标对话正忙时作为**新的独立运行**入队，待前序运行结束后顺序执行，不会并入正在生成的模型请求，遇队列满或场景/目录切换期则拒绝。唯有携带内部 `MessageInputIdentity` 的消息，才可在支持补充输入的在途运行边界被当轮消费。
- **多端旁观与权限确认裁决。** 多个已认证连接可同时订阅同一对话，实时接收流式增量与运行终态通知。运行中触发工具权限确认时，`ConfirmationHub` 与 `ConfirmationBridge` 按轮次来源和接入面信任级裁决：观察者连接可收到待确认摘要，但普通 RPC 轮次的完整确认载荷与 `confirmation.resolve` 应答权仅归匹配的发起接入面（本机回环已认证连接可提交含持久规则在内的完整决策，非回环连接仅限单次允许或拒绝），旁观终端不能代为应答。

#### 2. 可直接调用的本机入口与实际用法

**（1）核心宿主 WebSocket JSON-RPC（`/ws`）**

- **适用条件：** 本机核心宿主已在运行（独立 RPC 连接不会自动拉起宿主），目标环境已完成模型配置，且外部程序具备读取目标 `ZHIXING_HOME` 下 `server.port`（或 `server.pid`）与 `server.token` 的本机文件权限。
- **实际调用方式：** 连接 `ws://127.0.0.1:<port>/ws` 发送 JSON-RPC 2.0 请求：先调用 `auth` 传入共享 `token` 及合法稳定的 `client.id`（省略 `client.id` 虽可通过 `auth` 查询列表，但调用 `session.send` 等写操作会因缺少稳定接入面身份被拒绝；使用独立 `client.id` 可与在场 `zz` 终端并存，重用相同 `client.id` 会以 `4001` 关闭旧连接）；再定位或准备目标对话——通过 `session.list` 查找用户域对话（主对话与渠道对话）、通过 `session.new` 新建主对话，工作场景对话不包含在 `session.list` 中，未预先持有 `ws:...` 全域键时需按 `workscene.list` → `workscene.enter({ sceneId, requestId })` 获取当前 `conversationId`；最后调用 `session.send({ conversationId, turnId, text })`（或传入结构化 `input`；输入不经 CLI 斜杠命令解析，多行与前导 `/` 均原样送入会话；省略 `conversationId` 时自动新建主对话；耐久模式下 `turnId` 必填且须稳定唯一）。
- **处理结果：** 普通轮次立即返回 `{ conversationId, sessionId, turnId, runId }` 表示已接纳，并将发起连接加入该对话观察者，在线期间实时推送 `session.delta`、`session.complete`、`session.final`（耐久运行不随连接断开而取消）；中途连接或以相同 `client.id` 重连后调用 `session.subscribe` 会补发已提交的 `session.final` 但不回放错过的流式 `session.delta`，也可直接用 `session.history` 分页倒读落盘结果，或持原 `client.id` 调用 `session.inputReceipt` 核对提交状态（`accepted` 仅证明输入已耐久接纳而非回复已生成，`unknown` 表示尚未查到记录而非明确拒收）。若目标对话正处于任务推进（Advancement）待确认准则或提议阶段，`session.send` 会返回 `awaiting-rubric-confirmation`、`advancement-proposal`、`contract-failed` 等对应控制结果。
- **受限止步点：** 宿主未运行或按需宿主空闲停机后无法直接建连；`turnOrigin` 仅记录 `rpc` 渠道与连接/接入面标识，不识别外部智能体会话身份，也无法向外部地址主动回投；运行中若触发工具权限确认，须由发起端自行监听 `confirmation.pending` 并调用 `confirmation.resolve`，无人应答则阻塞该工具调用直至过期按超时处理后继续本轮。

**（2）CLI 非交互标准输入文本会话（`zz` / `zhixing`）**

- **适用条件：** 外部程序可在同机启动 `zz` 或 `zhixing` 子进程，且目标环境已完成模型配置；不带子命令且标准输入或标准输出非 TTY 时，入口自动跳过四进程交互终端，进入 `startTextSession` 文本会话。
- **实际调用方式：** 向子进程标准输入按行写入 UTF-8 文本（单行上限 1 MiB）。若核心宿主未在运行，`CoreHostConnection` 会静默拉起后台按需宿主；启动后默认恢复最近主对话或新建主对话，也可先输入 `/resume <conversationId>` 切换到精确匹配的已有用户域对话，或在主对话下输入 `/work <场景 ID 或唯一名称子串>` 进入对应工作场景对话（`/resume` 只检索用户域目录，无法匹配 `ws:...` 工作场景对话；已在工作场景内时须先 `/exit` 返回主对话才能再切换场景），随后在后续行输入消息内容。
- **处理结果：** `stdout` 按纯文本（剥离终端控制字符）依次输出会话标题横幅、恢复或切换既有对话时回放的最近数轮历史摘要（含已接纳但尚未入历史的输入）、思考块、模型流式文本、工具执行状态及轮次结束提示行，不提供结构化帧或仅输出本轮回复正文的参数模式；错误信息写入 `stderr`。读到 `EOF` 且在途轮次结束后进程退出（成功退出码为 `0`，发生命令或运行错误为 `1`）。
- **受限止步点：** 标准输入按换行切分轮次，普通多行消息按行写入会被拆成多轮提交，且无命令行参数可直接传入目标 `conversationId` 或消息正文；以 `/` 开头的非空行先经命令分派（本地命令本地执行，已注册的技能命令转交模型，未知命令向 `stderr` 记错并跳过该行、后续行仍继续处理且最终退出码置 `1`），普通行中的 `@file:` 引用还会按当前工作区做文件材料解析（解析出错则该行不发送）；非交互模式下遇到工具权限确认会立即拒绝，遇到启动受限继续确认、模态选择或待确认推进准则时不会将后续管道行当作确认输入；若 `/resume` 或 `/work` 未命中精确 ID 且查询不能唯一确定目标，选择页在非交互下直接返回空且不中止循环，后续输入行仍会发往切换前的原对话。

#### 3. 受限入口、内部机制与缺位边界

| 路径或模块 | 类别定性 | 实际机制与止步位置 |
| --- | --- | --- |
| 受管消息通道扩展与 `/channels/{id}/...` | 特定条件受限 | 已安装、已配置凭据并连接的通道扩展将外部平台事件交给 `InboundRouter`，经对话准入执行后由 `DeliveryOutbox` 回投原通道。仓库唯一内置通道 `@zhixing-ai/channel-feishu` 经飞书 `WSClient` 接收 `im.message.receive_v1` 事件，`normalizeMessage` 仅接纳带 `open_id` 的合法非空文本并显式丢弃 `sender.sender_type === "bot"`；可选路由 `/channels/feishu/challenge` 仅为加密签名确认卡回调。其他受管扩展虽可注册各自实例前缀下的回调路由，但均取决于已部署的具体扩展，不存在面向外部智能体的通用发信通道。 |
| 宿主 HTTP REST 接口 | 无通用发信能力 | 默认内置 HTTP 路由仅开放无需认证的只读 `GET /api/health` 与 `GET /api/status`；其余非受管通道回调路径的请求（含任意通用 `POST` 发信尝试）均直接返回 `404`。 |
| 配对设备 Mesh 传输 | 特定条件受限 | `@zhixing-ai/mesh` 基于配对邀请建立双向 mTLS 连接，仅在同一知行部署内已配对的成员设备间承载任务派发、状态同步、第一方会话转发与跨设备内部通信，不对未配对的外部程序或智能体开放。 |
| 知行内部对话通信 | 仅系统内部可用 | 领域服务 `ConversationCommunicationApplicationService`、模型工具 `conversation` 与配对设备间 `conversation.communication` 服务支持 `discover`、`read`、`send`、`observe`，绑定真实来源对话身份（`source = { kind: "conversation", conversationId }`），支持跨主对话、工作场景对话与设备本地对话双向发信及在途补充输入消费。止步位置：`conversation` 工具强校验当前运行上下文 `runContextStorage` 中的本方 `conversationId` 且禁止自报身份；Product API 的发送命令未注册进对外 `/ws` 方法表（外部调用返回 `-32601 Method not found`，对外仅 `session.history` 在内部复用其只读查询）。 |
| 扩展操作延续通知 | 仅系统内部可用 | `createExtensionContinuation` 复用对话准入与内部通信端口，仅在受管扩展接入、更新或修复流程中将阶段结果回注至原发起对话或回退对话，不接受外部任意输入。 |

## 三、调研所得

### 3.1 审查标准

> **调研独立审查标准（定稿）**
>
> 1. **答透会话级通信基石能力。** 围绕消息如何进入指定对话并完成交互这一底层能力，分别核实同一智能体内部跨会话通信、外部主体向目标会话发信的实际做法、成立条件与可确认结果，按证据说明内外路径在哪些环节相通、在哪些环节设限或分化，不把内部互通直接外推为外部可调（闭源对象无法直接观测的内部结构须标明证据边界）。结合真实案例讲清底层架构与关键链路：目标会话如何标识与寻址发现，目标处于空闲、正在运行（回合内引导与回合间排队）或未激活及宿主未运行状态时的实际处理结果，以及只能发起单次独立任务、能进入指定既有会话继续交流、能向来源会话回信各自如何成立。
> 2. **以世界一流标准确立标杆。** 不满足于“能用”的做法，不凭名气或表面宣传选样。优先核实代表性智能体的原生入口与可追溯的实际调用机制（含公开介绍未提及的底层通道与用法），并围绕可能改变核心判断的问题，开放追查开源与极客实践、基础理论、经典系统设计、卓越贡献者的一手认识及跨领域一流成果，按实质解释力与原创贡献择优深入，说明标杆领先在何处、强在哪里，以及关键候选的比较范围与排除理由。采用跨领域经验时，写明对应关系、成立前提与失效边界。
> 3. **一手证据扎实，严守证明边界。** 每条关键判断均须追到亲自核读的一手材料（明确版本的源码、协议与接口规范、官方文档、原始文献或受控最小实证），注明对象、版本、成立条件与证明范围，严格区分来源主张、核实事实与自身推断。判定能力缺失或不可行，须锁定对象、版本与条件，先核查相关原生途径与最有力反例并给出直接依据，单次失败或未见公开宣传不构成否定证据；断言固有短板须追到具体机制而非偶发配置；判定某路线更优或没有更好方案，须在同约束下与最强可信候选对照，证据不足时如实写明在已查范围内尚未证实。
> 4. **同场景深比机制、体验与取舍。** 将代表性路线放进同一高要求场景（如目标会话正在执行任务时收到另一会话发来的消息、跨进程或跨智能体并发介入、断连重投等）横向对比，从接收方、调用方与使用者角度拆解工作机制、可确认状态，以及开箱可用性、多轮往返顺畅度、原对话上下文秩序与权限安全控制等产品与使用体验，讲透各自的真实收益与固有代价。主动用最强可信反例或竞争解释挑战核心判断，指明什么条件改变会使结论反转。
> 5. **形成可超越洞察，独立精炼交付。** 穿透具体实现外壳，指明哪些原理与做法解决了什么根本问题、在何种条件下成立；发现一流方案仍有局限时，指明具体局限、成因、可改善的实际结果及检验方法；若充分比较表明某项成熟做法已适合相应条件，讲清保留它的依据及强行改变的代价，同样成立。独立于本系统现状开展研究，不以既有实现框定问题与视角，也不提前做具体方案设计；围绕决定性问题精炼自足成文，不堆砌浏览流水账或以资料数量充当深度。
>
> 以上五项须同时满足，共同构成调研阶段的优秀通过标准。双方先各自对照同一份调研正文独立审查并记录依据，再交换质询；凡有足以改变核心认识的遗漏、薄弱证据或未处置反例，均按调研方法定向补研并复核，直至完全达标。标准经确认后固定，不因已有结论或后续方案而放宽。

#### 研究总览

#### 1. 研究范围、标杆与排除边界

选样按对会话级接收机制的实质解释力与原创贡献确定，而非按产品热度或宣传声量罗列，同时覆盖公开文档化的跨智能体协议与公开介绍未提及但经实测可追溯调用的底层通道：

- **常驻会话控制面标杆：OpenClaw。** 单个常驻 Gateway 统一持有会话路由、准入队列、跨会话可见性/只发授权及外部精确返回地址，可将“跨会话发信—忙时引导或排队—原调用关联回信”放在同一控制面内具体对照。
- **原生跨智能体会话服务标杆：Kimi Code（KAP）与 OpenCode。** 新版 TypeScript `kimi-code`（CLI `≥2.7.0`、Desktop `≥1.4.0`）发布《Using in Other Agents》，明确区分一次性 `print`、面向 IDE 的 `ACP` 与专供其他智能体多轮交互的本地 `KAP` 服务（`kap-server`），支持发现活实例、按需启动及忙闲双分支投递，使单次任务、编辑器内嵌与程序间多轮对话职责分明；OpenCode 则展示项目级本地 HTTP/SSE 服务如何让界面、SDK 与外部程序共享同一 `session.prompt` 准入，同时保留内部父子会话专属回报链。
- **忙时双队列、轮次前置校验与桌面底层通道对照：Codex 与 Pi。** Codex 开源仓以状态化 `Thread` 与提交/事件双队列统一承载内部多代理、TUI 跨线程工具与外部 `app-server`（内部区分“仅入队”与“唤醒运行”，外部以 `expectedTurnId` 防止回合内引导串入新轮次），而闭源桌面端则提供了“公开宣传未提及、但本机同用户进程可实际调用”的外层命名管道实例，适合对照公开协议合同与私有外层传输的可靠性边界；Pi 则在最小内核中清晰划开工具批次结算后的 `steer` 与当前工作结束后的 `followUp`。
- **进程隔离、受管环境与跨重启策略对照：Claude Code、Antigravity Sidecar 与 ZCode。** Claude Code 展示无中心守护进程的单会话模型如何通过本机共用 `inbox socket`、外部 `Channels` 插件与云会话入队分别提供接收能力，并建立 `delivered/held/refused` 入站安全控制；Antigravity Sidecar 代表宿主注入受管环境的能力门限及宿主换代时的孤儿进程风险；ZCode V4 则提供“发现范围大于写权限”及“重启后未执行输入显式置 `discarded`”的强反例。
- **协议规范、异构极客实践与跨领域经典基石：** 以 **ACP v2** 检验“公开内部子会话是否等于允许外部直写”与接纳回执语义；以 **Google A2A v1** 对照“暴露任务而非暴露对话”的跨服务边界；以开源 **MCP Agent Mail** 检验脱离宿主原生会话的独立持久邮箱路线；并引入 **Jupyter 消息协议 v5**、**Erlang/OTP 信箱及 OTP-24 EEP 53** 与 **Norm Hardy（1988）困惑副手理论** 追清多端因果归属、迟到回信治理与跨主体权限错配的底层边界。

**2.1 内外路径何时相通、在何处设限或分化**

**2.3 单次独立任务、进入指定既有会话与向来源会话回信的成立条件**

这三类交互结果各自依赖不同的底层要素，且并非严格线性递进，核验时必须分别确认：

- **发起单次独立任务：** 只需接收方提供一个可创建新执行上下文的入口（如各 CLI 的一次性 `print`/`exec`、Google Sidecar 的 `agentapi new-conversation` 或 A2A 新建 `task`）并返回输出或任务状态，无需既有会话寻址、并发输入协调或回信地址。
- **进入指定既有会话继续交流：** 要求目标标识能解析到同一对话上下文，并发输入具有可确定的归属与次序，且具备明确的忙闲接纳与入站权限裁决（若需跨进程或重启继续，还须具备可恢复的会话状态），使新消息真正进入该对话上下文而非静默新建分支或破坏在途状态。
- **向来源会话关联回信：** 除接收方产出结果外，还须同时具备**可识别的原发送方身份、可达的返回通路与请求—响应关联依据**（可通过兑现挂起中的原调用、向原会话注入带关联标识的新输入，或写入约定邮箱实现）。**“能进入既有会话”与“能向来源会话回信”互不自动蕴含：** 一方面，按 Claude Code 厂商文档声明，从另一台机器向云会话发信虽能进入该既有云会话，但云会话不能用 `SendMessage` 原路回复，发送方只能查阅其 transcript；发往跨机 `Remote Control` 会话时，若发送方发信前未先连上 `Remote Control`，对端同样没有回信地址；Claude `--channels` 若要双向回送，也必须在通知注入之外另配 `reply` 工具与明确目的地。另一方面，开源 `MCP Agent Mail` 的 `reply_message` 可依据原消息 ID 默认回给原发件人，在独立邮箱内完成双向关联往返，但邮箱写入与确认本身并不代表消息已进入或唤醒目标智能体的原生模型会话。[Claude 跨机与云会话回信限制声明](https://code.claude.com/docs/en/cross-session-messaging#replies-from-other-machines-and-cloud-sessions) · [Claude Channels 双向回送要求](https://code.claude.com/docs/en/channels-reference#notification-format) · [MCP Agent Mail 按原消息回信](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/9138f34b1ed220235dbfeaa3f1fc9fe4444f4e72/src/mcp_agent_mail/app.py#L8486)

**场景二：消息已获接纳后连接中断，目标宿主 `B` 随后重启（竞争解释与反转条件）**

同一故障窗口下，开源核实的 **ZCode V4** 与 **OpenClaw** 给出了两种完全相反却各自自洽的工程选择：

- **ZCode V4（未入执行则显式丢弃，交人重判）：** 以稳定 `commandId` 标识提交、ACK 报告命令裁决、`sourceCommandId` 关联后续会话投影，靠输入账本完成去重与“转入执行”的原子切换；一旦 CLI 重启，账本中**已接纳但尚未转入执行阶段的输入明确置为 `discarded`**，由使用者决定是否重发。[ZCode V4 写入与重启丢弃](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/docs/zcode-protocol.md#L52) · [ZCode 回执结构](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/packages/shared/src/zcode-protocol-v4/command.ts#L542)
- **OpenClaw（条件满足时自动恢复投递，等待者降级）：** 已被 Gateway 接纳但尚未消费的普通 peer 消息，在重启后若原收发两端仍存在且授权仍有效，会按原身份继续投递（目标已归档或授权已撤销则终止）；外部 `conversations_turn` 的底层投递同样可恢复，但原进程内的同步等待者已随重启消失，迟到回复改为按普通入站消息处理。[OpenClaw 已接纳输入恢复](https://github.com/openclaw/openclaw/blob/41dce5629f2703bb894a5409b0e6692fd4dd2ef3/docs/concepts/session-tool.md#L333) · [OpenClaw 重启后外部等待者降级](https://github.com/openclaw/openclaw/blob/41dce5629f2703bb894a5409b0e6692fd4dd2ef3/docs/concepts/session-tool.md#L259)

**结论反转条件（基于上述机制的比较推断）：** 哪一种更优取决于**消息意图与现场依赖度**。若消息是**自足的异步工作交接**（如“核验已完成，请按此结论推进下一步”），有条件恢复投递能避免长链路协作静默停摆及人工漏发、重发；若消息是**强依赖刚才那一轮瞬时现场的纠偏指令**（如“停一下，别改第二个文件”），重启后原活跃轮次已不存在，自动重投到下一轮反而会篡改无关任务，此时显式标为 `discarded` 或因轮次标识失效而拒收更为安全。同理，若合作双方的真实需求只是**委派独立黑盒任务并取回制品**、且希望隐藏接收方内部对话细节，Google A2A v1 以 `contextId` 聚合 `taskId`（终态任务不再收信，同一 `contextId` 下可另起新任务，经轮询、流或可选推送返回任务更新）反而比直接暴露内部会话更契合边界。[A2A 终态与任务更新](https://github.com/a2aproject/A2A/blob/5f931b8a25fe66789f987ec4a55fc16ee9fe41ee/docs/specification.md#L145)

#### 4. 跨领域经典原理：对应关系、成立前提与失效边界

- **Jupyter Kernel Messaging Protocol v5：多发送者因果归属与控制/确认分流。** Jupyter 面向多前端共享同一有状态执行核，规范明确请求回复（`Shell`）必带 `parent_header`，广播副作用（`IOPub`）通常也借 `parent_header` 归因到触发请求（无父事件时为空），并在内核重启时更换 `session` 标识提示执行实体已换代；同时把紧急中断（`Control`）和内核反向索取用户输入（`stdin`）从普通执行队列拆开。由此对照智能体会话可见：多个外部会话共享同一目标对话 `B` 时，若仅按“读取 `B` 最新一条回复”配对结果，在并发交错下就会串线；且宿主重启换代必须让外部桥接及时感知（与本机 Antigravity 孤儿 Sidecar 持失效旧宿主上下文争抢消息的实测现象互为印证）。**成立前提与失效边界：** Jupyter 假定持有同一内核连接凭据的各前端代表同一用户主权，且单个代码单元执行中无自然语言动态变向；其广播与 `parent_header` 机制本身不提供跨主体权限分级或跨系统回信授权。[Jupyter 消息头与换代标识](https://github.com/jupyter/jupyter_client/blob/e8043c08887a26ae1186b7547512e9c8ad8706e2/docs/messaging.rst#L133) · [Jupyter parent_header 因果关联](https://github.com/jupyter/jupyter_client/blob/e8043c08887a26ae1186b7547512e9c8ad8706e2/docs/messaging.rst#L170)
- **Erlang/OTP 信箱选择性接收与 OTP-24 EEP 53：临时返回别名与迟到回复治理。** Erlang 将“消息入信箱”与“进程按当前状态匹配消费”解耦；Rickard Green 在 OTP 24 落地的 EEP 53 进一步用一次性进程别名（`alias` 配合 `reply_demonitor`）替代永久 `Pid` 作为请求返回地址，一旦调用超时或连接断开即停用该别名，使晚到的过期回复由运行时直接丢弃而不污染调用方后续轮次。**成立前提与失效边界：** 撤销返回地址适用于“调用方超时即放弃原请求”的短周期同步调用；在耗时长、成本高的智能体异步协作中，若一刀切丢弃所有超时后的迟到成果会浪费已完成的工作，反之若将所有迟到回信无条件注入原对话又会干扰新任务——需要区分“超时作废的同步询问”与“迟到仍需留存或转异步通知的任务交接”。此外，迟到消息一旦进入大语言模型对话上下文便可能改变后续生成（影响持续多久取决于系统的历史与上下文管理策略），不具备传统 Actor 消费单条消息后天然不留对话痕迹的特性。[EEP 53 原始提案](https://www.erlang.org/eeps/eep-0053)
- **能力安全与困惑副手（Confused Deputy）：跨会话输入来源与代执行权限的分离。** Norm Hardy（1988）指出，当拥有高权限的程序（副手）根据另一调用方指定的目标或请求行事，却直接动用自身持有的环境权限而非调用方获授的权限时，就会发生越权代理。映射到智能体会话：目标对话往往持有用户本人的文件修改、命令执行或外部发信权；若来自另一会话或外部智能体的请求在执行层无条件触发目标对话的全部工具与免批特权，低信任或受外部材料污染的发信方即可借目标对话产生越权副作用。OpenClaw 的 `send-only` 授权恰好提供了区分“信息可见性”与“代理执行权”的反例式实证：上游文档明文指出，仅允许发信并取回本次回复只能限制调用方直接列举或读取历史，**目标会话仍可凭自身权限执行动作或在回复中披露数据，该授权并不隔离高权限目标的行为**；按 Claude Code 厂商文档声明，其对免批会话收到未验证跨会话消息时置为 `held` 待人工确认、规定“跨会话文本不代表用户批准”，则是从目标入站与审批侧抑制此类错配的控制手段。**成立前提与失效边界：** 该原理针对“调用来源权限低于目标会话环境权限”的副作用场景；消息在上下文中以何种角色字段呈现本身不单独决定是否越权，真正起决定作用的是目标入站裁决与工具执行/审批层是否独立核对触发来源的权限边界。[Hardy 1988 原始论文](https://www.cs.utexas.edu/~witchel/S25-380L/papers/hardy88confused.pdf) · [ACM 出版记录](https://doi.org/10.1145/54289.871709) · [OpenClaw send-only 明示界限](https://github.com/openclaw/openclaw/blob/41dce5629f2703bb894a5409b0e6692fd4dd2ef3/docs/concepts/session-tool.md#L315)

#### 5. 可超越洞察：根本原理、成熟边界与可检验的改进方向

**5.1 穿透外壳的四条底层原理（归纳判断）**

1. **输入协调与单一界面存活解耦，决定既有对话的可达范围与跨版本稳定性。** 仅需单次存活期协作时，绑定在活跃会话进程上的受控本地信箱即可满足同机互通；若要跨界面关闭或进程重启继续进入同一对话，则需要独立于单一前端窗口的协调端与可恢复会话状态；而借道未公开合同的桌面外层私有传输虽能实现即时互通，但无法替代版本化的正式接收协议与宿主换代感知。
2. **会话发现、发信、读历史、代执行权限与外部回信地址彼此正交。** 能发信不代表可读历史，限制读历史也不自动约束高权限目标代为执行的动作，服务接入凭据不等于人对后续工具动作的授权，内部上下文标识更不等同于外部精确返回地址；按实际信任关系分别裁决这几项要素，才能既避免因权限捆绑过粗而无法对外开放，又防止因默认继承目标特权而越权。
3. **忙时与跨重启处置取决于输入意图对在途现场的依赖度。** 修正当前活跃步骤的输入依赖明确的安全注入边界与活跃轮次校验（原轮次已变或已重启则失效拒收或置 `discarded`）；自足的后续工作或结果交接则适合回合间排队，并在收发主体与授权仍有效时支持跨重启恢复。
4. **回执粒度与结果关联须与协作契约相称。** 单向提醒只需确认写入传输；多轮委托与多发送者共享同一目标会话时，则需要幂等提交标识与请求级因果关联，使调用方能区分“仅传输写入”“已接纳待执行”“已进入运行”与“已产出关联结果”。

**5.2 成熟做法的适用边界与强行改变的代价**

在匹配条件下保留轻量成熟做法，比一刀切建成常驻全双工会话网关更优：
- **单向事件提醒与低频通知**（如构建告警进入当前打开的编码终端）：采用类似 Claude `--channels` 的轻量通知注入与忙时成批处理即可满足目的；若强行改为逐条持久建轮并要求终态回执，会增加额外配置与无谓的模型轮次消耗。
- **单一父进程独占驱动内嵌执行器**（如特定 IDE 或批处理管线拉起专属子进程）：基于 `stdio` 的 ACP 或子进程 RPC 免去了本地端口、守护进程保活与跨进程鉴权；强行改成常驻后台服务反而引入额外运维负担与本机暴露面。
- **跨服务黑盒任务委派**：当接收方不希望公开内部对话历史与中间步骤时，采用 A2A 式的任务级接口比开放会话级直写更利于边界封装。

**5.3 面向高可靠跨智能体协作的常见短板、成因与可检验改进空间**

当产品目标不仅是单向提醒或专属子进程嵌入，而是支撑**跨会话、跨智能体的可靠多轮协作**时，现有实践仍有三处常见短板可作针对性改进与验证：

> **设计独立审查标准（定稿）**
>
> 1. **基石定位准确，会话交流闭环。** 方案紧扣会话级通信与外部消息接收这一底层基石：知行内部另一会话、同机可调用知行入口的外部智能体（及本地调用方），在需要新开对话时能明确发起，指定既有对话时能准确进入该对话原有上下文继续交流并取得对应结果，需要答复时能与原交流准确对应，且协作双方可自由决定配合方式。通信沿用产品既有使用与执行边界，每项机制均对应本需求的真实问题；偏离会话级通信基石、捆绑固定协作角色或流程、凭空增设无关门槛，或只能每次新建孤立对话而无法进入指定既有对话的，不予通过。
> 2. **契合顶层指引，架构简洁卓越。** 方案符合[愿景](../vision.md)与[架构演进方向](../architecture/evolution-direction.md)这一唯一顶层标准：模型如何组织协作保持轻量可演进，会话状态与运行支撑归属清晰稳固，外部接入方式可独立替换——在通信语义不变时，更换或新增一种外部接入方式，既有会话状态和运行语义仍然成立，影响收敛在接入边界内。以目标结构倒推审视[现行核心架构](../architecture/overview.md)及生产实现（现行架构仅作现状参照而非上位约束）：保留、局部演进或更大范围的渐进升级均有真实问题与维护代价依据，职责契约清晰到可直接指导实现；同一事实分两处平行维护、迁就现状打补丁留结构债务，或脱离本需求空谈全局重构的，不予通过。
> 3. **边界结果可信，运行稳健有序。** 在目标不明确、对话空闲、正在运行、会话未激活、后台宿主未启动或空闲停机，以及多方并发、连接中断、重试或重启等真实情形下，系统所报的消息去向与处理结果均有事实依据：运行中来信在不意外改变原对话在途工作的前提下可靠衔接；调用方能据实区分消息已被接收、已完成并产出结果，不能交付或尚不能确认时也能拿到真实且可处理的结果，结果归属准确。出现未知或歧义目标误投暗建、消息静默丢失、把未确认报成成功、单次重试意外触发重复执行、并发结果串线，或非交互调用遇异常与待确认事项无期限卡死的，不予通过。
> 4. **产品体验一流，开箱省心自然。** 产品与用户体验贯彻以人为本、释放生产力的目标，把复杂度留在系统内部，首次接入与日常多轮交流均达到简明顺畅的世界一流水准：在产品正常可用、调用方具备常规工具调用能力的条件下，凭知行提供的原生入口与用法即可找准目标、使多行与带前导符号的正文按原意传达而不意外拆轮或误作命令执行、干净取得结果或状态；知行模型可按需自然通信；日常协作无需用户自行编写维护专用桥接、切换窗口、从混杂终端输出中剥离正文或逐轮人工传话，后台通信不打扰当前前台操作，需要查看时来源去向与状态清楚。演示虽能跑通，但正常使用仍把专用胶水或中转负担留给用户与调用方的，体验不予通过。
> 5. **达到世界一流，取舍有据可验。** 架构、系统、产品与用户体验整体达到世界一流水平，不满足于“仅能调通”：放入同一真实高要求协作场景，对照知行现状与调研中适用的一流做法，按具体机制判断预期交流效果、使用负担、可靠性与长期维护代价——已有做法确实优秀且适合知行的，有据保留同样通过；在其他条件相当时，若仍有明显更省事或更易维护的可靠做法而未采用，或仅以功能堆砌与空泛措辞自称最优，均不予通过。每项关键判断与核心承诺均须具备可观察的预期结果，以及足以推翻该方案的明确失败判据。
>
> **【通用原样必留·高权重】** 跳出“为解决当下问题而解决问题”的局部视角，站在宏观与长时间尺度审视：只做直击本质、经得起时间检验且长期有价值的设计；凡当下看似自洽强大、长期反而成为系统负担的，坚决不做。
>
> 以上五项标准及上述最高权重准则须同时满足，方可通过设计审查。双方对同一版设计分别对照首节需求、顶层指引与本标准独立记录依据和缺口，交换意见，实质缺口全部闭合后停下交用户审阅。

#### 方案总览

本节为基于 `develop@c1b4277e` 生产基线的待实施设计（文中凡属新增命令、RPC 方法与演进分支均明确标注）。核心设计选择是：**不把人类交互 REPL 管道充当机器协议，也不另起独立守护进程、跨产品回调协议或会话权限体系；而是在既有 `Conversation` 单写权威与核心宿主之上，补齐统一的跨作用域只读目标目录、双向隔离的外部独立运行准入与跨进程/跨迁主请求对账窄端口，并通过随包一等原生命令组 `zz conversation`（同时属于 `zhixing` 与 `zz`）及内部 `conversation` 工具向内外提供完备的会话级通信基石**——使内部跨会话协作与同机任意外部智能体接入均实现零专用胶水、零前台打扰、精确归属与耐久可靠。本轮交付止于设计定稿与用户审阅，未经明确授权不开始产品代码实现。

#### 1. 基石定位、能力范围与内外协同模型

本模块只解决**“消息如何准确进入指定对话（或显式新建对话）、可靠运行并使调用方拿到对应结果”**这一底层会话通信基石，严格区分纳入范围与不做事项：

- **内部跨会话通信（知行会话 `A` ↔ 知行会话 `B`）：** 沿用并补强现有[对话间通信](../modules/conversation/collaboration.md)机制。`A` 通过内置 `conversation` 工具按需发现目标（扩展为覆盖用户域主对话、渠道对话、工作场景对话及未初始化场景候选、可达设备本地对话）、显式新建目标对话（新增 `new` 动作）、读取历史（`read`）、发送消息（`send`）与查询状态（`observe`）。兄弟会话通信是异步消息而非同步 RPC 调用：`B` 空闲时启动 `Run`；`B` 正在运行普通人类/内部 `Run` 时，在当前 `Turn`（模型调用及其工具批次）完整结束后作为同一 `Run` 下一 `Turn` 的正式输入消费（若 `B` 当前正在执行绑定了外部程序专属回执的受信本机程序运行，内部来信则自动顺延为下一独立 `Run` 入队，既保留自身 `inputIdentity` 与正常回信，又不篡夺外部运行的专属答复）；`B` 的输出归属 `B` 自身，需回复 `A` 时由 `B` 依据来信 `inputIdentity.source.conversationId` 向 `A` 再次调用 `send`，回执本身不额外唤醒模型。
- **外部向知行会话通信（同机外部智能体或本地程序 `A` → 知行会话 `B`）：** 在知行已完成基础模型配置、调用方具备同机当前系统用户执行权限的正常条件下，`A` 直接调用知行原生入口 `zz conversation`（或对等本机窄 RPC `conversation.program.*`）：
  1. **定位既有目标或显式新建：** 通过 `list` 只读查找既有对话（及尚未创建对话的工作场景 `sceneId`），或通过 `new` 显式新建主对话/幂等初始化指定 `sceneId` 的工作场景主对话，取得精确 `conversationId`；
  2. **进入指定既有对话并获取专属结果：** 通过 `send <conversationId>` 将任意多行与带前导符号的完整正文原样送入 `B` 的既有上下文，排入 `B` 的**双向隔离独立 `Run`**（`B` 空闲即刻启动，`B` 正忙则顺序排队而不篡改 `B` 在途工作，执行期间亦不混入其他独立来信），默认在等待窗口内直接取回**本次提交专属的完整最终助手回复**；长耗时任务、进程中途中断或 `--no-wait` 异步投递，凭写出前即交付的票据（`ticket`）或 `(conversationId, requestId)` 随时通过 `result` 续等或取回原结果；
  3. **多轮持续交流与反向联络：** `A` 后续凭同一 `conversationId` 即可继续读取（`read`）或追问（`send`）；若异步协作中需要知行 `B` 主动联系另一款智能体，`B` 直接使用既有工具调用对方产品自身的入口，不在知行内部绑定对方产品的私有回调。
- **明确排除与边界守恒：** 通信层不预设角色分工、互评流水线或组队剧本；沿用知行既有的本机回环（`127.0.0.1` + `ZHIXING_HOME`）与已配对第一方设备边界及内核工具执行安全防线（`SecurityPipeline` + `Trust` + `AI Steward` + `Confirmation`），**不增设会话间授权表、鉴权握手、未核验外部自报品牌标签、外部邮箱或跨厂商推送网关**。

#### 2. 顶层架构推导与现行核心架构审视

**2.1 由顶层指引推导的目标结构与变化隔离检验**

依据[愿景](../vision.md)与[架构演进方向](../architecture/evolution-direction.md)，会话通信的目标架构按三层定责：

1. **轻量可演进的协作组织层（做轻）：** 多智能体之间采用同步问答、异步委托还是交叉审查，完全留在模型自主判断与按需加载的薄技能说明中，不向内核或通信协议写入任何协作流程状态机。
2. **稳固受控的会话与运行底座（做重）：** 会话身份与创建意向预留、单对话串行准入、按目标隔离的物理请求键与跨迁主基底对账、运行生命周期（排队、执行、提交、待消歧）、推进（`Advancement`）边界隔离、工具安全裁决与不可变运行正文存储，统一收归 `Conversation` / `Workscene` 领域与会话当前唯一 `owner` 掌管，不因调用来自终端、内部对话还是外部程序而产生第二事实源。

#### 3. 核心契约、运行状态与生命周期机制

**3.1 统一只读目标目录与显式幂等新建契约**

1. **最近活跃优先、带版本证据的有界只读目录（外部 `conversation.program.list` & 内部 `conversation.discover` 接口边界）：**
   - **内外接口清晰分层（保留既有兼容）：**
     - **外部 `conversation.program.list`**：独立返回判别联合分页对象 `{ entries, nextCursor?, partial, unreachableDevices? }`（不建第二个全网复制目录权威，单页 `limit` 范围 `1..100`）：
       - **已存在对话条目**：`{ entryKind: "conversation", canonicalKey, conversationId, scope: "main" | "workscene" | "channel" | "local", name, sceneId?, sceneName?, workspaceLabel?, active, busy, pendingCount, advancementStatus?, summary, summaryTruncated, lastActiveAt }`；
       - **尚未创建对话的工作场景候选**（`--scope all` 或 `workscene` 时包含）：`{ entryKind: "workscene-candidate", canonicalKey, scope: "workscene", sceneId, sceneName, workspaceLabel?, initialized: false, lastActiveAt }`——读取持久 `WorkScene.lastActiveAt`（[types.ts](../../packages/core/src/workscene/types.ts) 及场景活动投影，绝不虚填当前时间），与已物化 `ws:<sceneId>:primary` 共享同一逻辑身份 `canonicalKey = worksceneConversationId(sceneId, "primary")` 且只返回一种表示（候选不伪造 `conversationId`、不读历史文件）。
     - **内部 `conversation.discover` 全链路路由（保留旧无参兼容，统一覆盖单机无 Mesh 与多设备 Mesh）：** 无筛选/分页新参的旧请求 `{ action: "discover" }` 原样沿用 `discoverConversations` 返回 `{ conversations, partial }` 及其既有字段语义（涵盖已物化 `ws:<sceneId>:primary`，绝不塞入人造候选 `conversationId` 或静默截断原全集）；当模型显式传入筛选或分页参数（如 `{ action: "discover", query?, scope?, limit?, cursor? }`）时，从 [conversation-tools.ts](../../packages/cli/src/serve/conversation-tools.ts)（`inputSchema` 与键白名单）与 `validateConversationCommunicationRequest` 起，在**单机无 Mesh 分支（[command.ts](../../packages/cli/src/serve/command.ts) `routedCommunication`）与有 Mesh 分支（[mesh-runtime-assembly.ts](../../packages/cli/src/serve/mesh-runtime-assembly.ts) `routeConversationCommunication` / `bindConversationCommunication`）的共同路由入口**于旧 `discoverConversations` 无参重写前直接转入共享目录协调端，沿用真实内部主体 `conversation:<sourceConversationId>` 向各可达 `owner` 请求本地有界页（绝不再退化为无参广播），映射输出 `{ conversations, worksceneCandidates, nextCursor, partial }`（遇尚未支持扩展页查询的旧版 Mesh 对端明确识别能力缺失并置 `partial: true`，绝不当成空目录）。
   - **持久最近活跃排序、来源适配与有版本证据的实时键集游标（不虚称历史快照）：**
     - **单一默认排序规则：** 严格按**持久化排序元组 `(Date.parse(lastActiveAt) DESC, canonicalKey UTF-16 ASC)`** 排序（与 [directory-page.ts](../../packages/core/src/conversation/directory-page.ts) 及 [directory-index.ts](../../packages/core/src/conversation/directory-index.ts) 中每 UTF-16 码元 4 位十六进制的 `id_order` 完全同序，禁用 `localeCompare` 或跨时区字符串时间比较；**严禁使用 [application.ts](../../packages/core/src/conversation/application.ts) 中覆盖展示用的瞬时 `runtime.lastActiveAt` 参与跨 `owner` 排名或生成游标**）——确保无论中文命名对话、`ws:` 工作场景还是 `local-*` 对话，只要最近活跃即刻出现在第一页顶部；
     - **各来源截页前过滤与有界读取：** `--scope` 与 `--query`（匹配 ID、会话名、场景名）在各来源截页前生效；用户域复用 `directory-index.ts` 的 `visible` 索引与 `listPage`（`hidden/archived` 在 `LIMIT` 前排除；`listPage` 内部自行取 `limit + 1` 探测后继，传 `limit = 100` 时绝不向公开校验传 `101`）；场景子库适配器负责库内裸 `localId` 与全域 `ws:<sceneId>:<localId>` 游标变换；`localConversationOwner`（含混合宿主同机与纯 `executor` 节点的 `owned-list`）经有界 `ConversationDirectoryPageCollector` 选页（不假定纯执行端存在全局 SQLite 索引）；**仅对本页最终返回的 `<= limit` 条已物化对话按需读取最近摘要**，绝不扫描全量历史换首页；
     - **来源目录版本证据与 `cursor_expired` 诚实失效：** 通过窄扩展为各来源提供可验证的持久目录版本判据（`ConversationDirectoryIndex` 携带经核验的发布 `epoch + revision`，存在未发布 `pending` 行时一并绑定所见 `pending` 元数据确定性摘要正常签发游标；旧索引退回文件直读时与 `WorkScene`、`localConversationOwner` 一致，对实际可见持久目录元组按 `canonicalKey` UTF-16 全序排序后计算确定性摘要，绝不依赖 `fs.readdir` 或来源自然返回顺序，并在多源汇总前后复核）。`nextCursor` 绑定 `(filterDigest, reachableOwnersDigest, sourceVersions, after: { lastActiveAt, canonicalKey })`（取本页实际交付末项，未展示预取项绝不推进全局游标；**唯有证实当前视图已穷尽才允许退出码 `0` 且省略 `nextCursor`，凡仍有后继项却无法证成一致版本证据时，首页返 `temporarily_unavailable` 退出码 `3`、续页返 `cursor_expired` 退出码 `3`，绝不交付缺游标的伪完整页**）。流式 token、`busy`、`observerCount` 或瞬时 `runtime.lastActiveAt` 变化**不使游标失效**；页间一旦发生影响本视图的持久目录变更、成员或过滤变更导致无法再证同一读视图，立即诚实返回 `cursor_expired`（退出码 `3`）让调用方刷新首页（静态目录恰完整遍历一次，动态目录绝不一边静默漏项一边谎报翻页成功）。`partial: true` 仅表示存在不可达来源（纯 `executor` 在 `Anchor` 不可达时仍列本机可证 `current` 条目并置 `partial: true`；无任何可达来源报 `temporarily_unavailable` 退出码 `3`）。`--query` 查到多条同名亦绝不自动代选发送。
2. **按调用主体隔离的统一创建幂等契约与写命令边界（`conversation.program.new` & 内部 `conversation` 的 `new` 动作）：**
   - **参数职责边界：** `--name` 仅供新建用户域主对话自定义标题，工作场景名称归属 `Workscene` 权威（`workscene.rename`）；`--name` 与 `--scene` 显式互斥，同传在本地写出前即报参数冲突（退出码 `1`）。
   - **内部写命令隔离、路由直达 `Anchor` 与按 `(creatorPrincipal, requestId)` 索引的统一创建表：** 在 [communication-application.ts](../../packages/core/src/conversation/communication-application.ts) 中，只读 `CONVERSATION_COMMUNICATION_QUERY` 明确收紧为**仅接收 `discover | read | observe`**（严禁 `new` 透过只读查询写状态）；`conversation-tools.ts` 对 `action === "new"` 与 `send` 一样由 `{ turnId, lineage, toolCallId }` 派生确定性 `operationId`，增设独立 Product API 写命令并在 `routeConversationCommunication` 中于按 `conversationId` 寻址前直接路由至当前 `Anchor`（同时将 `routeAddressedConversationCommunication` 的主控归属判断对齐 `adoptedConversations`），绑定真实源对话 `creatorPrincipal = "conversation:" + sourceConversationId`（外部 `conversation.program.new` 绑定 `creatorPrincipal = "program:local"`，内外主体严格隔离互不撞键）。同一主体下跨 `main` 与 `ws:<sceneId>:primary` 共用 `Anchor` 同一创建幂等裁决，先原子记录规范化创建意图 `{ targetKind: "main" | "workscene", sceneId: sceneId ?? null, name: normalizedName ?? null }` 与结果，再幂等完成物化（严禁先调无键 `create()` 再补写映射）：
     - 无 `--scene` 时：在用户域 `IConversationRepository` 预留新主对话 ID 并初始化空转录壳，返回 `{ v: 1, conversationId, scope: "main", created: true }`；
     - 指定 `--scene <exactSceneId>` 时：经 `Workscene` 权威校验精确 `sceneId`（未知场景报 `not_found`；若场景正处移除/重置静默栅栏 `quiescePrefix` / `WORKSCENE_BUSY`，返回可重试 `temporarily_unavailable` 退出码 `3`，绝不向删除中场景写入），定位固定确定性主键 `ws:<sceneId>:primary`（`worksceneConversationId(sceneId, "primary")`）——若尚未初始化则经 `touchWorksceneSession`、会话账本 `session-meta` 与 `ensure` 原子初始化空会话（返回 `created: true`），若已存在则不重建（不同 `requestId` 并发或先后初始化同一场景均安全收敛至同一个 `ws:<sceneId>:primary`，首个初始化请求 `created: true`，后至异键请求 `created: false`），全过程不跑模型、不滞留连接观察者；
     - **同主体相同 `requestId` 重试、丢回执恢复与冲突规则：** 因 `new` 在返回 `conversationId` 前尚无目标对话票据，CLI 写出前先向 `stderr` 刷出 `requestId`；遇 `Anchor` 暂不可达或写出后响应丢失时返回可重试状态（退出码 `3`，保留原 `requestId`），调用方须以**原 `requestId`（`new ... --id <requestId>`）及原参数**重试（严禁换新号制造孤立空会话）——服务端不重复创建，原样重放首次提交记录的 `{ conversationId, scope, sceneId?, created }`（若目标此后已被删除则明确报 `target_deleted`，绝不暗中复活或另建新会话）；同主体同 `requestId` 跨模式混用或更改 `sceneId`/`name` 意图，明确报 `idempotency_conflict`。

**3.2 物理输入键映射、跨迁主对账与双向隔离准入**

1. **写出前预交付对账标识、调用端 `homeId` 边界与物理输入键映射：**
   - CLI 在本地参数、UTF-8 与多跳封包净荷上限预检通过后、**向连接写出 `send` 请求之前**，确定 `requestId`（显式 `--id <requestId>` 或生成 UUIDv4）并构造单行 URL-safe Base64url 票据 `zxt1.<payload>`（含 `{ v: 1, homeId, conversationId, requestId }`，`homeId` 绑定**发起调用端 `H` 的 `ZHIXING_HOME`** 而非权威所在设备），先向 `stderr` 刷出结构化恢复行（`ticket`、`conversationId`、`requestId`）再发出请求。进程即使在写出后、打印 `stdout` 前被 `SIGKILL` 强杀，调用端 `H` 在原 `ZHIXING_HOME` 下仍可凭 `zz conversation result <ticket>` 或 `zz conversation result --to <conversationId> --id <requestId>` 精确对账（即使旧 `owner` 设备 `O` 已关机、对话迁至新 `owner` 设备 `N`，`H` 持原票据经路由转发至 `N` 依然成立；而在另一 `ZHIXING_HOME` 直接运行 CLI 复用该票据则报 `invalid_ticket`，不会把票据变成跨 `home` 通行证，获准访问同一目标时可用 `--to <conversationId> --id <requestId>` 核对；若调用方既未传 `--id` 又丢弃了 `stderr`/`stdout`，则仅能 `read <conversationId>` 查历史）。
   - **规范物理输入键（防跨目标撞键）：** 服务端绝不将客户端原始 `requestId` 直接充当宿主级 `turnId`，而是按带域标签的字段规范编码确定性计算物理 `turnId = "prog-" + protocolDigest("ProgramConversationIngress", 1, { conversationId, requestId })` 作为 `ingress.ingressId`（原始 `requestId` 仅存于 `turnOrigin.triggeredBy`）。该物理 `turnId` 统一贯通准入控制信封、运行上下文、重试对账、`inputReceipt` 与迁主基底查询——保证向不同对话传相同 `--id 1` 完全独立不碰撞，且跨 CLI 重连与 `owner` 换代映射恒定不变。
2. **跨增量与迁入基底的统一对账及原子准入顺序：**
   - 在目标对话当前 `owner` 的同一串行临界区内按固定顺序执行：
     1. **先判基底就绪并核对当前增量与已验证迁入基底的既有收据：** 若目标正处 `frozen / importing` 或迁入基底尚未就绪（`unavailableTransfers`，此时无法核验该键是否已在迁入基底接纳），**无论 `result` 还是 `send`（含重放）一律保留票据并返回可重试 `temporarily_unavailable`（退出码 `3`，绝不把未就绪基底当成未提交新请求入账，也不返回 `admitted: false`）**；待完整权威视图就绪后，按同一物理 `turnId` 同时核查当前宿主增量（`controlAdmission` / `admittedByRun`）与已验证迁入基底（`conversation-base-domain.ts` 中的 `source/control/` 收据配对、`source/ingress-control/` 及迁入 `admittedByRun`）。命中同物理键时比对规范化正文摘要——摘要一致则幂等返回原 `runId`（不受此刻队列满、推进开启或宿主排空影响，**已确立 `accepted` 绝不降格为 `admitted: false`**），摘要不同则确定性报 `idempotency_conflict`；
     2. **完整视图证无旧收据后，再检业务/推进/容量门禁并耐久入账：** 唯有在完整就绪视图内证实本次 `requestId` 尚无已接纳收据后，才依次原子校验目标存在且未删除（否则 `not_found` / `target_deleted`）、未处于宿主排空（否则 `host_draining`）、**不存在任何未终结契约推进会话**（完整检查 `isOpenAdvancementSession`：`proposed | drafting | draft-failed | draft-uncertain | awaiting-rubric-confirmation | active`）或受限引导待决态（否则 `needs_attention`）、待处理普通运行未达 `maxPending`（默认 5，否则 `queue_full`），全部通过后写入耐久 `admitted` 记录（与已导入基底共享同一单调准入序列）。**仅此类在完整视图内被准入前门禁明确拒绝的新意图，才返回 `admitted: false` 与退出码 `1`**（且不污染原 `requestId`）。
   - **多跳单帧净荷上限预检：** 请求与各跳单页回包（目录页、历史页、单页 `answer + nextCursor`）均计入外层 JSON-RPC 与 `conversation.program` Mesh 信封编码开销，严格收敛在单帧 `1 MiB`（`MeshRequestChannel` 默认上限，含纯 `surface` 的 `maximumRequestSourceBytes` / `requestEncoded`）以内；发送正文超预算在本地写出前报 `payload_too_large`（`admitted: false`，退出码 `1`）。
3. **三字段受信程序来源判定、契约推进全周期隔离与双向 `Run` 隔离：**
   - **唯一受信程序来源谓词（防同名原生渠道误伤）：** 统一定义 `isProgramOrigin(ingress)` 为 `owner` 已接纳的 `ingress` **同时满足** `ingress.kind === "first-party" && ingress.surfacePrincipal === "program:local" && ingress.turnOrigin?.channel === "program"`（外部受管渠道扩展恒为 `ingress.kind === "channel"` 及渠道派生主体，即便实例名或 `channelId` 取 `"program"` 仍走原生渠道路径，绝不误匹配）。追加、推进、历史与确认四处统一消费该谓词，无需预留通道名或增设新权限。
   - **提交与恢复期的推进隔离：** 针对“外部运行 `P` 先入账，人工随后开启 `Advancement`，之后 `P` 才提交（含提交后、裁判前崩溃重启）”的交叉时序，全局与本机双 `owner` 的实时提交钩子、`advancement-recovery-index.ts` 候选归约以及 `recovery-maintenance.ts` 快索引与回扫分支，统一按 `isProgramOrigin(admitted.ingress)` 排除程序运行进入 `#reviewAcceptedRun`——保留正常运行提交维护与历史，既不消耗推进裁判轮次与 Token 预算，也不漏审后续真正的推进运行。
   - **反向内部插话隔离：** 单对话 `owner` 在 `decideInputControl` 判定 `run-input-appended` 时同步核验当前活跃运行的 `admitted.ingress`：仅非 `isProgramOrigin` 的普通运行允许兄弟会话在 `Turn` 边界追加；若当前活跃运行满足 `isProgramOrigin`，后到的内部 `conversation.send` 自动转为下一独立 `Run` 排队（保留其 `inputIdentity`）。显式由人类发起的停止（`abort`）保持原有管理语义。
   - **零协议破坏的持久来源索引：** 持久层仅写合法封闭键 `TurnOrigin = { channel: "program", triggeredBy: requestId }`；`ConversationReadIndex` 按 `isProgramOrigin(admitted.ingress)` 为该运行首条输入派生 `program-origin:<runId>` 持久索引（允许合法追加的普通内部运行中，后续追加消息仍按各自 `inputIdentity` 显示 `来自对话 <id>`；无来源证据的旧/导入记录不虚构来源）。

**3.3 快速准入、有界分片等待与当次读状态真值表**

为避免长耗时运行触碰 `RpcClient` 与 `MeshRequestChannel` 的 `30s` 单次请求硬超时或因等待中途断连丢失已接纳收据，**服务端 `conversation.program.send` 仅执行快速耐久准入并立即返回 `{ admitted: true, conversationId, requestId, runId }`；CLI 的 `--wait <秒>`（`send` 默认 `60` 秒，`result` 按需指定）由客户端以每次 `waitMs = min(剩余等待毫秒数, 15_000)` 的有界短切片循环调用 `conversation.program.result`**（服务端在单切片内先注册终态/修订唤醒观察，再核查增量与迁入基底收据及同一 `owner` 一致视图下的生命周期与 `run-outcomes / completion / body-page(runId)`，已完结或有进展立即唤醒返回；跨跳协调转发时逐跳扣除已消耗时间并透传取消信号，绝不每跳重新起算 `15s`）：

| 场景或阶段 | 权威判定依据 | 对外返回状态与可观察结果 |
| --- | --- | --- |
| **输入超限，或完整视图证实新 `send` 遇目标缺失、未知、已删除** | 提交前封包预检超限；或完整就绪权威视图证实无旧收据且 `exists === false` / `recoveryDeleted() === true` | 确定性未入账（`admitted: false`，`error.code = "payload_too_large" \| "not_found" \| "target_deleted"`，CLI 退出码 `1`），绝不回退默认对话或暗建新对话。 |
| **完整视图证实新 `send` 遇未终结推进会话（`isOpenAdvancementSession`）、宿主排空或队列已满** | 完整就绪权威视图内证实本次请求无既有收据，且被提议/起草/待确认/`active` 推进门禁、`closeExternalAdmission` 或 `maxPending` 准入前拒收 | 确定性未入账（`admitted: false`，`error.code = "needs_attention" \| "host_draining" \| "queue_full"`，退出码 `1`），不污染原 `requestId`，绝不干扰人类待审准则或在途推进闭环。 |
| **已耐久接纳，尚在排队、运行、取消收尾或提交索引/正文准备中** | 当前增量或迁入基底 `inputReceipt = accepted`，且 `run-outcomes` 为 `queued \| dispatched \| running \| cancel-requested`，或 `committed` 但 `completion` 索引/`body-page(runId)` 尚处 `preparing` | `state = "pending"`，返回 `{ v: 1, state: "pending", conversationId, requestId, runId, ticket, runState }`（CLI 退出码 `2`；索引或正文 `preparing` 绝不误报为空完成或异常失败；本地总等待到期或 `Ctrl+C` 仅结束本次观察并输出同一 `ticket`，不取消底层运行）。 |
| **运行正常提交且正文可读完结**（含工具经前置非交互即决拒绝后模型作答） | 同 `owner` 一致视图确认未被清空/删除、`run-outcomes = committed` 且经 `committedText` 读法（反向定位该 `runId` 末条 `assistant` 消息再从 `block: 0` 正向读完 `text` 块）完成读取 | `state = "completed"`（CLI 退出码 `0`）：文本模式跨页读齐整篇后输出末条正式 `assistant` 完整原始正文（保留块间换行与代码块，剔除思考与工具块；确无助手文本块时 `--json` 置 `answer: null, emptyReason: "no_assistant_text"`，绝不借用其他运行或内部插话文本）；`--json` 返回单帧 `< 1 MiB` 内的单页 `answer`、`answerTruncated` 与 `nextCursor`。 |
| **运行权威失败/已取消，或同视图拿到正面清空/删除证据** | `run-outcomes` 为 `failed \| cancelled \| expired`，或同 `owner` 一致视图证实 `deleted === true`（含迁入接管后在 `N` 上被删除）或 `session-lifecycle` 清空水位已覆盖该运行提交/准入位置（不单凭 `commitRevision` 缺席臆断） | 确定性非成功终态 `state = "failed" \| "cancelled" \| "cleared" \| "target_deleted"` 及原因（CLI 退出码 `1`），**严禁输出半截文本报退出码 `0`**，也绝不越过 `/clear` 泄露旧正文或把已接管后删除的目标转回旧设备。 |
| **读取中途遭遇 `ownerEpoch` 接管换代（无清空/删除正面证据）** | 分页或跨步读取期间配对设备完成接管使旧 `ownerEpoch` 失效（`reset === true`），但运行未清空未失败 | **绝不误报为失败、已清空或未接纳：** 文本模式丢弃未输出半截缓冲，凭同一 `ticket` 路由新 `owner`（查当前增量与已验证迁入基底）从首页重读完整正文（成功仍报退出码 `0`）；`--json` 续页游标失效报 `state = "cursor_expired"`（退出码 `3`，保留 `runState: "committed"`）。 |
| **写出后断连未知、目标设备离线未接管、迁主基底未就绪（`frozen/importing`）或运行落入 `uncertain`** | 写出后断连且尚未查到收据；目标 `local-*` 当前所属活跃成员暂时离线且 `Anchor` 无已提交接管事实；目标正处 `frozen / importing / fenced` 切换或迁入基底未就绪；或 `run-outcomes = missing \| unknown \| uncertain` | `state = "unknown" \| "temporarily_unavailable" \| "uncertain"`，**保留并输出同一 `ticket` 与 `requestId`**（CLI 退出码 `3`；绝不误报 `not_found` 或 `admitted: false`、不降格已接纳事实，也不盲目改号重投）。 |

**3.4 全角色装配接合、窄 Mesh 协调服务与边界守恒**

对照单机、主控兼执行混合节点（[command.ts](../../packages/cli/src/serve/command.ts)）、纯执行节点（[executor-role-runtime.ts](../../packages/cli/src/serve/executor-role-runtime.ts)）与纯表面节点（[surface-core-host-link.ts](../../packages/cli/src/runtime/surface-core-host-link.ts)）的真实生产装配：

1. **统一领域应用端口与本地 RPC 落点（防旧通用中继旁路）：**
   - 将 `conversation.program.{list,new,read,send,result}` 显式列入 `DEVICE_LOCAL_RPC_METHODS`（[index.ts](../../packages/server/src/rpc/methods/index.ts)，不自动收入 `CURRENT_ANCHOR_RELAY_METHODS`，也不经 `ExecutorFirstPartyRpcRouter` 静态截流）；
   - 具备本机宿主的节点在 `ServerContext` 中统一注入同一个 `ProgramConversationApplication` 窄端口：`command.ts` 按实际装配同时注入当前 `Anchor` 权威与可选本机 `localExecutor.owner`（同机双 `owner` 直接进程内调用，**单机无网格部署不建任何回环 Mesh**）；`executor-role-runtime.ts` 在 `createServerContext` 中显式注入绑定了本机 `localConversationOwner` 与向当前值班 `Anchor` 请求能力的同一端口。
2. **单例版本化窄 Mesh 服务 `conversation.program` 与纯 `surface` 窄切换：**
   - 因 `MeshServiceRegistry.register`（[service-registry.ts](../../packages/mesh/src/service-registry.ts)）禁止同名重复注册且 `authorize` 仅接收连接不接收载荷，启用 Mesh 的宿主每节点最多注册一次 `conversation.program`（`access: "write"`，`availability: "negotiated-version"`，`authorize` 先校验对端为 `currentTrust` 中的 `active` 成员），在处理器严格解码载荷后再按操作校验本机角色与对端身份：
     - `op: "entry"`（仅本机确为当次值班 `Anchor` 时受理，允许来自已配对 `active` 的 `surface | executor | anchor` 成员）：承接五项程序操作的协调入口；
     - `op: "owned"`（仅本机持有 `localConversationOwner` 且直接对端经核实为当次值班 `Anchor` 时受理）：仅开放本机持有分页 `owned-list` 及针对指定 `local-*` 的 `owned-send | owned-read | owned-result`，不含全局 `new`、任意 RPC 调度或内部 `RunInput`。
   - 纯 `surface` 角色无后台宿主，`CoreHostConnection` 经 `CurrentAnchorSurfaceRpcClient` 仅对 `conversation.program.*` 五项方法切换至该窄客户端（同步接通 `request`、`requestEncoded`、`maximumRequestSourceBytes` 并保留结构化可机读错误，不将业务错误压扁为通用离线异常）；其余既有方法的角色授权边界与内部 `conversation.communication` / `RunInput` 保持原样不变。
3. **`Anchor` 协调、已提交接管优先裁决、8 位前缀消歧与叶端单跳规则：**
   - 非 `local-*` 目标与 `new` 统一交当前 `Anchor` 处理；
   - 对 `local-*` 目标（注意 [conversation-transfer.ts](../../packages/owner-kernel/src/conversation-transfer.ts) 对从未见过的完整 ID 也会回落返回 `fallback/current`，故**严禁单凭“8 位前缀匹配本机 + `current`”在多成员同前缀下把仅存于另一成员的目标短路判为本机 `not_found`**）：①若入口宿主持有 `localExecutor` 且本机账本已有该完整 ID 的**正面创建或权威删除墓碑事实**——`current` 时直接在本机据实执行或返回 `target_deleted`（纯 `executor` 在 `Anchor` 离线时仍可正常读写自身已创建的 `current` 本机对话），`frozen | importing` 时返 `temporarily_unavailable`（退出码 `3`），`fenced` 时交当前 `Anchor`；②若本机无该完整 ID 的正面创建记录，仅在单机无网格或已验证 `currentTrust` 中本机是匹配该 8 位 `devicePrefix` 的唯一成员（且无迁出 `Anchor` 可能）时才可本地判 `not_found`，只要存在前缀歧义或需核对主控接管事实，一律交当前 `Anchor` 协调；
   - `Anchor` 协调 `local-*` 时，**先依据已提交的接管/迁入事实（[conversation-access.ts](../../packages/cli/src/serve/conversation-protocol/conversation-access.ts) 中的 `adoptedConversations` / `unavailableTransfers`，而非对删除取反的 `sessionExists`）判定权威归属**：①若迁入基底尚不可用（`unavailableTransfers` 或 `frozen/importing`），返 `temporarily_unavailable`（退出码 `3`）；②若 `adoptedConversations.has(id)` 为真，则权威已归 `Anchor`（即便该对话接管后已被删除，也由 `Anchor` 直接返回 `target_deleted` 退出码 `1`，**绝不因 `sessionExists === false` 把旧票误转回已关机的原设备 `O`**）；③仅当 `Anchor` 确无接管记录时，才在 `currentTrust` 成员中匹配 8 位 `devicePrefix`（[scope-id.ts](../../packages/core/src/conversation/scope-id.ts)）——无任何已知成员匹配时报 `not_found`（退出码 `1`）；唯一活跃 `executor` 匹配时单跳转发一次 `op: "owned"`（该成员暂时离线则返 `temporarily_unavailable` 退出码 `3`）；若存在多个同 8 位前缀的活跃 `executor` 成员，只读核对各候选对该完整 ID 的正面持有/删除墓碑事实，仅向唯一证实持有（含权威墓碑）且非迁移态的候选派发，任一候选不可达或处迁移态致归属不可唯一确认时零写入返回 `temporarily_unavailable`（退出码 `3`），绝不在多候选间猜投；
   - 叶端 `executor` 在串行门内复核 `currentAuthority(id)`：遇 `fenced | frozen | importing` 立即回传带原票的 `temporarily_unavailable`（退出码 `3`），**叶端绝不反向扇出或透明重发写入**。
4. **回环边界与跨版本诚实失败：**
   - `loopback === true` 仅在真实本机入口（本地 `/ws` 回环套接字或本机 CLI `surface` 进程）采集并沿受控宿主转发链传递，公开参数不接受任何自报主体、角色或路由提示；非回环外部直连一律拒绝，无需增设额外会话权限表。
   - **跨版本诚实裁决：** 仅在**确证本次请求未产生任何写入且未曾接纳**时（如连接旧版 `/ws` 宿主直接收到 `-32601`，或只读操作及确认未发出的新请求遇 `incompatible-version`），明确返回 `unsupported_host_version`（`admitted: false`，退出码 `1`）；凡请求已写出后响应未知，或 `send` 重放 / `result` 在跨跳路由中遇 `service-unavailable`、连接中断或超时等无法排除既往已接纳的情形，一律保留票据返回 `unknown / temporarily_unavailable`（退出码 `3`），严禁据此诱导调用方改号重发。

#### 4. 产品入口与三端使用体验

**4.1 原生 CLI 命令组契约（`zz conversation` / `zhixing conversation`）**

所有子命令支持 `--json` 输出版本化结构（`v: 1`）；未传 `--json` 时采用面向命令行与智能体零噪音约定（`stdout` **仅输出纯业务结果正文、精确 ID 或票据**，预刷恢复标识、进度提示与错误一律走 `stderr`）：

| 命令与参数 | 输入与行为约定 | `stdout` 输出与退出码（`0` 完成 / `2` 进行中 / `3` 待核对或暂不可读 / `1` 失败） |
| --- | --- | --- |
| `zz conversation list [--query <词>] [--scope all\|main\|workscene\|channel\|local] [--limit <N>] [--cursor <游标>] [--json]` | 只读按持久 `(lastActiveAt DESC, canonicalKey ASC)` 有界分页（`1 <= limit <= 100`）列出当次可达视图下的既有可通信对话及尚未创建对话的工作场景候选（含精确 `conversationId` 或候选 `sceneId` 及持久 `lastActiveAt`）；宿主未起时自动连接/只读查询，仅对当页已物化对话按需读摘要。 | 默认按最近活跃优先每行一条制表摘要（标明 `conversation` 或 `workscene-candidate`、精确 ID、作用域、场景名与标题；`partial` 时 `stderr` 提示离线设备；唯有证成视图穷尽才在退出码 `0` 省略 `nextCursor`）；`--json` 输出完整分页对象。成功退出码 `0`；页间持久目录/成员/过滤变更致 `cursor_expired`、仍有后继但版本证据暂不可证或无任何可达 `owner` 退出码 `3`。 |
| `zz conversation new [--name <标题> \| --scene <精确场景ID>] [--id <请求ID>] [--json]` | 在 `Anchor` 按 `(program:local, requestId)` 原子幂等创建新主对话，或幂等准备指定场景的固定主对话 `ws:<sceneId>:primary`（`--name` 与 `--scene` 互斥）；写出前 `stderr` 刷出 `requestId`；不跑模型。 | 默认 `stdout` **仅输出单行精确 `conversationId`**；`--json` 输出 `{ v: 1, conversationId, scope, sceneId?, created }`。成功退出码 `0`；`Anchor` 暂不可达或写出后丢响应退出码 `3`（凭原 `--id <requestId>` 与原参数重试，不换号）；参数冲突/未知场景/意图冲突/已删重放退出码 `1`。 |
| `zz conversation read <精确ID> [--limit <N>] [--before <游标>] [--json]` | 经当前权威只读读取指定对话最近 `N` 轮已提交消息（按持久来源索引区分内部对话与外部程序首条输入）及未入史待处理输入；不透明 `--before <游标>` 绑定 `ConversationBodyCursor`（`ownerEpoch, clearId, revision, message, block, offset` 及 `history`）复用 `body-page` 在 `< 1 MiB` 编码帧预算内切分单轮超长消息；不唤醒运行体、不改前台指针。 | 默认文本模式自动跨片段拼齐所求 `N` 轮（无 `--before` 遇换代自动重读当前权威）并按时间正序输出带清晰角色/来源分隔的原始消息正文；`--json` 输出单帧 `< 1 MiB` 分页结构与 `nextBefore`。成功退出码 `0`；目标活跃成员离线未接管、接管过渡/`preparing` 暂不可读或 `--before` 遇换代/清空失效（`cursor_expired`）退出码 `3`（绝不伪报空历史）；确证不存在/已删除退出码 `1`。 |
| `zz conversation send <精确ID> (--text <正文> \| --stdin \| --file <UTF8路径>) [--wait <秒> \| --no-wait] [--id <请求ID>] [--json]` | 命令登记 `cliLoggingMode === "none"`（不被误判为未声明日志写者），且仅在确认目标为 `conversation` 后按带值选项 arity 归一“选项 + 字面值”（不改动共享根 `program` 及其余命令解析）；三种正文输入严格三选一：`--text`（保留 `--text "--"`、`--text=--`、`--text "-V"`、`--text "--version"` 等全部字面值，不被剥离或被根级 `.version()` 截胡）、`--stdin`（读至 EOF 整段单条消息）与 `--file`（严格 UTF-8 读取本地文件，避开 Windows PowerShell 管道编码损坏与引号转义），原样保留全部换行、前导 `-`/`/`、`@file:` 字面量；空白、非法 UTF-8 或超单帧净荷上限在写出前拒收；写出前先向 `stderr` 刷出恢复 `<ticket>` 与 `requestId`。服务端 `send` 仅快速耐久准入即刻回执，默认 `60` 秒（或 `--wait`）由 CLI 按 `waitMs <= 15_000` 短切片循环调 `result`。 | 等待期内完成：默认自动跨页正反序读齐整篇（遇换代自动路由新 `owner` 重读首页）后，`stdout` **仅输出本次 `runId` 最终助手完整回复原文**（退出码 `0`）；`--no-wait` 或总等待到期仍在排队/运行/`preparing`：默认 `stdout` **仅输出单行 `<ticket>`**（退出码 `2`）；写出后断连未知、目标设备离线未接管、`frozen/importing/fenced` 暂不可核对或 `uncertain`：`stdout` 输出 `<ticket>`（退出码 `3`）；完整视图证实未入账拒绝、运行失败或正面证据确认已清空/已删除：`stderr` 报明原因（退出码 `1`）。`--json` 输出含单页 `answer`、`answerTruncated`、`nextCursor` 的完整对象。 |
| `zz conversation result (<ticket> \| --to <精确ID> --id <请求ID>) [--wait <秒>] [--cursor <游标>] [--json]` | 凭预交付 `<ticket>`（限同一发起 `ZHIXING_HOME`）或显式 `(--to, --id)` 向当前权威（含已验证迁入基底）核对准入与运行结果；默认立即返回当前状态，传 `--wait <秒>` 按扣减跳间耗时的 `<= 15s` 短切片阻塞续等；`--cursor` 仅供 `--json` 续读超大回复下一页（文本模式自动拼齐整篇）。 | `completed` 时文本模式自动拼齐整篇输出完整助手回复原文（退出码 `0`）；`pending` 输出 `<ticket>`（退出码 `2`）；`unknown / temporarily_unavailable / uncertain / cursor_expired` 输出 `<ticket>`（退出码 `3`）；运行失败/正面确认已清空或已删除（含接管后在 `N` 上删除）/跨 `home` 无效票据退出码 `1`。`--json` 输出单帧 `< 1 MiB` 结构化状态对象。 |

`zz --help` 与 `zz conversation --help` 内置可直接复制的四行最小示例（列目录含工作场景候选、文件/标准输入发多行正文、长任务凭票或 `--to + --id` 续查、按场景显式初始化对话），同机任何具备命令行工具的智能体首次调用即可零摸索上手。

**4.2 三端协同体验闭环**

- **外部智能体（如 Codex、Claude Code、Antigravity、OpenCode、Kimi Code）：** 无需知晓 `ZHIXING_HOME` 端口算法、无需读取 `server.token`、无需编写 WebSocket 状态机或维护专用胶水脚本。已知目标 ID 时一条 `zz conversation send <id> --file msg.md` 直接拿到干净完整答复；未知目标时先 `zz conversation list --json` 找准既有 `conversationId`（若目标工作场景尚未开对话，从 `workscene-candidate` 拿到 `sceneId` 执行 `zz conversation new --scene <sceneId>` 得到 `ws:<sceneId>:primary`），多轮追问全程复用同一 `<id>`；遇长任务、进程被强杀或目标对话迁主，在原调用 `ZHIXING_HOME` 下凭 `<ticket>`（或跨获准 `home` 凭 `--to <id> --id <reqId>`）随时取回专属结果。
- **知行自身模型与内部跨会话协作：** 内置“对话通信”技能（[builtin-skills.ts](../../packages/core/src/skills/builtin-skills.ts)）保持精简按需加载，更新说明覆盖三点：①无参旧 `discover()` 保持 `{ conversations, partial }` 兼容（纳入已物化 `ws:<sceneId>:primary`），显式筛选/分页发现可一并获取未初始化工作场景候选与 `nextCursor`，必要时经独立写命令 `new` 显式新建协作对话；②收到内部对话来信（`source.kind === "conversation"`）按需用 `conversation` 工具向源对话 `send` 回信；③收到满足 `isProgramOrigin` 的本机程序来信时，本轮正常助手回复即为调用方取回的返回结果，仅在异步协作明确约定主动回访外部智能体时才调用对方入口工具。
- **人类使用者：** 全程不必充当“人肉复制粘贴中转站”，也不必手动先开 `zhixing serve` 守护窗口。日常后台跨会话或跨智能体交流不抢占当前正在使用的 `zz` 终端焦点、不乱切当前对话指针、不在其他前台对话已有待确认操作时插队或闪出无归属确认卡片、也不干扰正在自主推进的 `Advancement` 任务；当用户主动打开或旁观该对话时，流式界面与历史记录清楚标明 `◇ 来自对话 <id>:` 或 `◇ 来自外部程序:`，前因后果与状态一目了然。

#### 5. 同高难场景对比与关键架构取舍

**5.1 高压场景正面对比**

**对比场景：** 同一宿主上用户正在前台对话 `F` 等待点击一条工具确认，同时工作场景对话 `B`（`ws:<S>:primary`）正在执行耗时任务；同机外部智能体 `A` 与 `C` 先后向 `B` 发来包含多行代码块与 `/exit` 字面量的独立协作问题，其中 `A` 在写出请求后进程被超时强杀（尚未读到响应），随后无人在线时 `B` 的外部运行实际执行到受控工具并完成落盘。

| 方案路线 | 实际交流结果与归属准确性 | 调用方与用户负担 | 安全可靠性与对在途/前台工作影响 |
| --- | --- | --- | --- |
| **知行现状**（非交互管道 `zz` 或裸调现有 `/ws`） | 管道把多行拆成多轮、`/exit` 直接退出场景、`stdout` 混杂横幅与历史；裸 `/ws` 虽可在拿到 `runId` 后调 `session.statusHistory`（`body-page`）按运行读正文，但 `session.list` 找不到 `B`（需调有写副作用的 `workscene.enter`），且 `A` 被强杀换进程（新 `client.id`）后无法凭 `session.inputReceipt` 找回原 `runId`。 | 必须手写专用 WebSocket 端口/令牌发现、宿主拉起、订阅与分页拼装桥接脚本，或由人跨窗口手工传话。 | `A` 断连后在单机或无其他本地连接、无渠道与启用用户定时任务时，`command.ts` `on-demand` 宿主约 2 分钟即启动排空停机；`B` 的待确认工具经 `ConfirmationHub` 走本会话交互确认队列，可向旁观端推送提示，无人响应或被同会话队首占用时会等待至超时。 |
| **调研标杆对照**（Kimi KAP / OpenCode / Codex App Server / OpenClaw / ZCode） | Kimi KAP 与 Codex/Pi 支持忙时排队保护原轮次，但 OpenCode 默认 `steer` 会介入当前运行；OpenClaw 靠常驻 Gateway 维护内存等待者，重启后同步等待者降级；ZCode 重启后未入执行输入置 `discarded`。 | Kimi KAP 需管理本地服务/Bearer 令牌与 HTTP+WS 组合查询；Codex `app-server` / Pi RPC 需常驻或独占子进程；OpenClaw 需配置常驻 Gateway 与策略。 | 各有强项，但直接照搬常驻网关或独立 HTTP 服务仍会把服务保活、令牌传递或并发运行归属复杂度外露给同机调用方。 |
| **本设计方案**（`zz conversation` + 统一只读目录 + 双向独立 `Run` + 物理键跨基底对账） | `A`、`C` 多行与 `/exit` 字面量原样接纳为 `B` 队列中的两个双向隔离独立 `Run`（`run_A`、`run_C`）；`A` 被强杀（乃至目标对话迁主）后，调用端凭预交付 `<ticket_A>` 或 `--to <B> --id <req_A>` 精确找回 `run_A` 完整回复，绝不与 `run_C` 或内部插话串线。 | **零专用桥接、零配置：** `A`、`C` 仅调随包 `zz conversation list/send/result`；按需宿主自动拉起并在 `Anchor` 与同机 `localExecutor` 的 `run_A`、`run_C` 完结落盘后才空闲退出（含纯 `surface` 经 Mesh 入站代数保护）。 | **零误扰、零挂死：** `B` 原任务先跑完再顺序跑 `run_A`、`run_C`，且 `F` 的前台待确认完好有效；`isProgramOrigin` 运行内的受控工具在 `beforeRequest` 落账后显式返回 `delivery: "non-interactive"` 直走 `non-interactive + afterResolved` 耐久拒绝收束，不弹窗、不被队首阻塞。 |

**5.2 三项关键内部架构取舍（为何不选看似相近的替代方案）**

1. **取舍一：现行 `/ws` 已支持按 `runId` 调 `session.statusHistory` 读正文，为什么不能直接拿 `session.send + session.statusHistory` 薄包一层 CLI 了事？**
   - **评估：** 复用 `session.statusHistory` 与 `committedText` 读链正是本方案保留的现成优势，因此绝不另建结果存储；但仅薄包 `session.send` 仍会在六处真实边界失效：①`session.inputReceipt` 绑死单次连接 `surfacePrincipal` 且未合并迁主导入基底，强杀或迁主后无法找回原 `runId`；②`session.list` 看不到工作场景对话与未初始化场景；③普通 `session.send` 会触发人类 `Advancement` 准则起草或打断在途推进会话；④外部运行执行中若被内部 `conversation.send` 追加输入会篡夺末条回复归属；⑤经 `ConfirmationHub` 挂载 `onRequest` 后落入本会话交互确认队列会向旁观端推送提示，且在无人响应（或同会话 `broker` 队首占用）时等待至超时；⑥`command.ts` `on-demand` 宿主在单机/无本地连接、无渠道与启用定时任务时，遇 `--no-wait` 退出或纯 `surface` 经 Mesh 入站会提前空闲停机。本方案保留既有正文读链，仅精准闭合这六处最小内核接合点，做到零冗余存储且边界全通。
2. **取舍二：为什么不额外在 `@zhixing-ai/server` 新建一套 HTTP REST + SSE 会话接口（仿 OpenCode / Kimi KAP）？**
   - **评估：** 若新建 HTTP REST，当 `on-demand` 后台宿主未启动或空闲退出时，外部 HTTP 请求直接报连接拒绝——调用方仍须自行实现端口计算、`server.token` 读取与守护进程拉起重试逻辑，未能真正消除外部胶水负担，反而让 `@zhixing-ai/server` 背上 WebSocket JSON-RPC 与 HTTP REST + SSE 双协议长期维护成本。以随包 `zz conversation` CLI（内聚 `CoreHostConnection` 自动拉起与认证）配合单一 `/ws` 窄 RPC，在更低复杂度下同时满足了命令行智能体零配置即用与常驻客户端接入。
3. **取舍三：为什么外部入口现阶段不开放 `--in-run`（强行并入目标正在运行的 `Run`），且反向也禁止内部来信并入外部 `Run`？**
   - **评估：** 内部兄弟会话 `conversation.send` 在普通运行间不返回目标回复正文，因此适合 `Turn` 边界追加；而外部请求的核心契约是取得**与本次提问严格一一对应的准确答复**。双向保持外部 `Run` 独立（外部不挤入在途 `Run`，活跃外部 `Run` 也不吸纳无关内部追加），以忙时合理顺序排队换取了 100% 的在途秩序保护、独立非交互确认边界与双向零串线结果归属。
