- 历史调查候选9898无诊断插桩，启动到真正可用 **40.182秒**；其中等待Host就绪 **35.205秒**，首次画面仅 **1.843秒**。当时主要问题在后台加载、恢复和读取，不能用首帧快代表启动快。

逐轮耗时账、改动与剩余卡点见[执行记录](terminal-startup-performance-record.md)。

## 交付目标与计时口径

**冷启动以重复运行的中位数稳定在约5～7秒为目标，允许单次波动，更快也接受。** 以当前可用Windows物理环境、真实构建入口验收；实现保持多平台，缺少其他实机不构成阻塞。

| 场景 | 目标 |
|---|---|
| 执行命令后的可见反馈 | 约1秒出现稳定、可响应的启动界面 |
| Host已运行，再次打开终端 | 通常1～2秒真正可用 |
| Host未运行，完整冷启动 | 同条件重复运行，中位数稳定在约5～7秒 |
| 已有大量历史的冷启动 | 同一标准，启动成本不能随全部历史持续放大 |

以上是体验目标，不是每次运行的硬截止线。验收可用同版本、同条件的一组约10次运行观察中位数；不要求每次都在5～7秒内，也不因一次超过7、8或10秒就判整版失败。保留各次耗时及范围供分析，不以最慢值替代中位数，不挑快样本；少量样本不足时不宣称已稳定。

**允许波动不等于接受严重等待。** 用户于2026-10-20明确：实测64.3秒冷启动是不可接受的严重缺陷，列为当前最高优先级并阻断交付，必须查清根因、与战略架构师共同确定方案并修复；不能以中位数规则、单次波动或留待最终采样为由放过。此要求不把5～7秒改成逐次硬截止线，也不另行推导用户未规定的秒数阈值。

起点是执行 `zz`／`zhixing`，终点必须同时满足：最近历史正确显示，输入、滚动和中断正常，首条消息能够实际接纳并推进，不再补跑启动必需准备。模型生成的网络耗时、用户填写首次配置的时间另计；完成配置后的程序准备时间仍须计量。

区分新配置、长历史、已有Host及构建后首开，不混算、不先清库或额外预热取得成绩。这里的冷启动指Host未运行，不冒称重启操作系统后的全冷缓存。测量不与构建或测试抢资源；父子阶段及并行耗时不能直接相加。

## 方法及适用边界

采用[完整链路、整轮推进耗时优化](../engineering/latency-optimization.md)。本问题起止明确、已有阶段日志和耗时账，该方法能减少零碎试错和重复构建，无需再建一套流程。

- **先攻关键路径。** 优先解释35.205秒Host等待及其波动，拆清模块加载、必要恢复、物理读取、排队和重复调用。阶段排名只是定位线索，须核实触发者与放大机制；不能把“缓存”“竞争”当作未经验证的根因。
- **整轮集中处理。** 先列全已识别卡点及其耗时、原因、优化价值；本轮有价值的卡点统一优化完，再做整轮功能和架构自审，之后才集中构建、运行和测试。禁止改一点、解决一个性能点就立即全量构建或跑启动。关键未知会导致大面积返工时，才允许最小定向取证，不借此恢复零碎重测。
- **避免方法反噬效率。** 不追求解释每一毫秒或证明理论极限，不为填表扩大范围；已无明确优化空间的节点保留结论，有新证据才重开。集中验证不等于每次修改或提交都重建隔离环境、重跑所有页面。
- **以同口径结果判断。** 复用已有耗时账，每版追加一列；新配置、长历史和已有Host分别记录，不混算。约10次的稳定性观察用于完成整轮优化的候选，不是每改一个点都跑10次；明显仍慢时先解释和改进，不为填表重复高成本运行。诊断数据与无诊断成绩分开。

## 保留有效的阶段版本

未达最终目标不等于本轮无效。例如从20～40秒改善到稳定约15秒，若收益有同口径证据、必要回归通过且未破坏整体要求，就保留为**新的稳定改进基线**，再从它继续下一轮。15秒是说明推进方式的例子，不是已取得的成绩，也不是新的最终标准。

每版记录实际改进、必要验证和剩余卡点；失败候选可撤回到最近稳定基线，已证明有效的改进不因尚未达到5～7秒而全部丢弃。阶段稳定版本与最终达标版本分开标记；前者不宣称整个迁移可交付，版本记录也不自动授权Git提交或推送。

**后续耗时优化必须保持已经验收关闭的增长约束。** 具体责任、回归处理与验证规则统一遵循执行计划[“已验收增长约束的持续保持（强制）”](terminal-migration-delivery-plan.md#已验收增长约束的持续保持强制)，不另设第二套放行标准。

## 架构与正确性边界

**需求与目标是约束，现有架构只是已选择的方案。** 本任务没有绑定必须保留的框架、运行时或进程划分。发现更合适的架构或技术选择时，基于需求覆盖、实测收益、实施成本和副作用进行比较，能够更好达成目标就调整或替换；不必先把旧方案优化到穷尽才允许比较。

不必要的全量历史遍历、重复恢复或全局初始化，应从读取、恢复、装配和生命周期解决。如果现有结构存在不满足目标的天然上限，不能在其上无限打补丁或降低目标；也不能仅凭一次慢样本无依据重写整个框架。

遵循[核心架构边界](../../research/design/architecture/overview.md)及[终端迁移合同](../workbench/terminal-architecture-migration.md)：保留完整功能、既有体验、唯一业务事实、安全与耐久；不得删历史、跳过校验、放宽容量或把必需工作推到首发来换取表面速度。配置应用等待、中断、退出、恢复和历史顺序作为直接影响面一起核验。
