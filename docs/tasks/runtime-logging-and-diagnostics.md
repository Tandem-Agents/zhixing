# 运行日志与问题追溯

## 一、需求梳理

知行需要一套面向真实运行环境的正式、统一的日志体系，覆盖系统不同来源、不同类型操作的运行过程及其关联，保留足以支持事后追溯的有效信息，并以清晰的存放位置、组织结构和访问方式，为用户、开发者及各类智能体提供可靠的数据基础。该体系应从整体产品与长期演进出发设计，具备稳定、清晰、可维护的架构，能够适应功能与架构变化。日志必须具备自动执行的保留与淘汰机制，综合信息价值、时间和存储体积明确约束数据增长，在保障有效追溯的同时防止无限膨胀。

---

## 二、产品设计

**让运行过程留下可信、可关联、可直接查阅的记录，并在长期使用中保持有界。**

1. **默认记录，覆盖完整运行。** 正常使用即留下必要记录，覆盖前台、后台及扩展的运行过程，包括启停、请求处理、模型与工具执行、外部交互和配置变更。成功、失败、拒绝、取消、重试与恢复均有记录，包含时间、来源、关键输入输出、阶段、结果及必要的版本和配置上下文。
2. **同一件事，能够连续追溯。** 操作及其记录有稳定身份，子步骤、不同尝试及跨会话、跨进程、跨设备交接可以相互关联，独立发生的运行活动也可定位。记录随过程发生形成；操作尚未结束、被中断或系统重启后，已保留的记录仍可查阅。
3. **入口清晰，人和程序都能使用。** 每台设备提供可发现的日志位置、统一组织方式和简明记录说明，支持普通文件工具读取及程序解析。可按时间、来源和操作身份查找，从概览展开过程与详情；单次结果有界，可继续翻查。记录地址可交给其他获准使用者继续查阅，主服务不可用时仍能读取本地记录。
4. **忠实记录，缺口可辨。** 区分请求、实际执行与确认结果，保留错误内容及其来源，结果未知时明确标识。补充信息不掩盖先前记录；截断、脱敏及已知缺口应说明原因，能够区分已淘汰、未采集和暂不可达，无法判定时明确证据不足。
5. **按价值保留，按预算淘汰。** 每台设备设置日志总容量上限与保留期限，正文、附属材料、索引及清理记录全部计入预算，单条大小和高频记录也受约束。优先保留近期关键过程及异常前后的关联信息，先削减重复、低价值细节；任何优先保留均不得突破总上限。占用空间、可追溯范围和清理规则可查看，轮转与淘汰自动完成。
6. **安全记录，受控查阅。** 凭据不进入日志，私人正文按必要性控制记录与展示，查阅遵守相应的数据访问权限。日志清理仅作用于本体系管理的记录，不改变用户历史、业务事实或恢复所需的数据。
7. **持续演进，长期可靠。** 功能、版本与运行位置变化后，日志仍遵循一致的组织和关联约定，尚未淘汰的旧记录及其引用仍能正确读取和解释。记录、读取与清理均有资源约束；记录受阻时状态可见，日志自身故障不拖垮正常运行。

**验收标准：** 从时间范围、操作身份或记录地址出发，人和程序均能找到相应的关联记录，查阅关键过程、结果、错误及信息缺口；中断、重启、版本变化、容量触顶和数据淘汰后，记录仍如实可读或明确说明缺失，存储仍受控。

## 三、架构设计

### 3.1 一套观测合同，一个设备本地存储

沿[核心架构](../../research/design/architecture/overview.md)与 [AE-001](../../research/design/architecture/evolutions/AE-001-companion-intelligence.md)的职责和依赖方向，**各运行责任者记录自己实际观察到的过程，日志模块统一保存、关联、读取和治理这些记录。** 业务结果与恢复仍以各自 Authority 为准；日志记录“已提交”必须发生在真实提交之后。

```text
领域 / Kernel / 工具与平台适配 / Host
  → 来源绑定：明确身份、关联、可记录字段与访问范围
  → Recorder：校验、脱敏、限额入队
  → LocalLogStore：受控追加、持久化、轮转与淘汰
  → LogApplication：授权、检索、定位、分页与状态
  → CLI / 产品 API / 模型工具 / 获准的外部读取程序
```

共同合同与日志应用放在 `@zhixing/core/logging` 的窄入口；文件存储为其独立适配，来源转换留在各模块边界。业务采集方只持类型受限的记录端口，不取得读取引擎；Host 注入端口并管理生命周期，Kernel 只接收通用记录上下文。CLI、RPC 与模型工具调用同一日志查询应用；离线 CLI 直接装配本地读取端口，不依赖服务进程。普通文件工具依据随产品提供的目录与格式说明读取。

### 3.2 稳定记录身份，显式关联过程

记录采用**小而稳定的公共信封＋来源拥有的版本化内容**。公共信封包含格式版本、记录身份、存储身份、进程实例与序号、发生及接收时间、来源、事件名、级别、关联引用和访问范围；内容保存阶段、结果、错误、必要上下文及详情引用。事件名按来源命名，新增来源不要求修改中央业务枚举。可借鉴 [OpenTelemetry 日志模型](https://opentelemetry.io/docs/specs/otel/logs/data-model/)的公共字段与扩展属性分离方式。

阶段与结果分开；表达结果时统一使用 `success / failure / unknown / refused / cancelled`，不把开始或执行中的记录强填为终态。结果针对所标识的操作或尝试；`unknown` 表示结果尚无确证，后续证据追加关联记录，不覆盖原判断。

- 日志目录在互斥下首次创建稳定的 `storeId`；设备身份尚未建立时也能记录启动过程，身份建立后附带真实 `deviceId`。复制记录保留来源身份，新设备建立自己的存储身份。
- 关联复用带类型的请求、会话、Run、工具调用、任务、投递、扩展操作等既有身份；独立活动可生成本次观测身份。子步骤与重试分别标识，通过父引用或关联引用连接。日志不将所有活动改造成模型 Run。
- 关联上下文在请求、任务交接、进程协议与跨设备传递处显式携带；进程内可用作用域上下文传递。重启后凭既有业务身份重新关联，PID、文件名、模型文本和线程局部状态不充当长期身份。
- 进程内序号说明观察顺序，单调时钟用于本进程耗时；跨进程先后依据显式交接关系，墙上时间只辅助检索，不伪造全局因果顺序。补充或更正追加新记录并引用原记录。

### 3.3 在责任边界采集，进入队列前控制内容

采集落在实际决定或执行的边界：入口接纳、运行阶段、模型请求与响应、工具及外部效果、权限决定、配置生效、提交、交付、恢复和资源释放。Harness 同时记录实际生效的模型、工具集、配置与实现版本，以及必要输入输出的安全投影。每类观测事实指定一个采集责任者；已有协议事件可作明确绑定的来源，不全量复制 EventBus、Provider chunk 或业务日志，避免直接记录与事件转录重复。

Recorder 的来源身份和访问范围由可信装配绑定，外部消息与扩展不能自报更高权限或冒充其他来源。字段先按来源合同选择，秘密字段排除，正文按访问范围及必要性投影，再统一脱敏、限制深度和大小；未知对象、请求头、环境变量和完整配置不得直接序列化。自由文本脱敏只是补充防线，不能代替字段选择。裁剪与省略带原因，不将任意模型或工具输出当作系统事实。

受管扩展通过既有 IPC 送达宿主可信边界后，重新校验与脱敏，并按实例限制入队量；各来源额度包含在进程总队列预算内，不能因增加来源而扩张总预算或挤占全部记录能力。

每进程使用按字节及条数限额的队列；采集调用只做有界处理与入队，文件 I/O 在后台批量执行。现有 EventBus 会等待异步监听器，日志监听器因此只入队、不返回写盘等待。压力下先合并高频重复记录、放弃细节，再拒绝无法容纳的记录；保留有界的丢弃计数与范围。关键记录优先调度，但入队不等于耐久，异常断电或强杀可能损失未持久批次。

来源投影、校验、脱敏和入队都在日志故障边界内：自身异常转为有界健康状态，不向业务调用抛出、不修改业务对象，也不吞掉原业务异常。实现不得依赖每个调用者自行包裹日志错误。

### 3.4 可直接读取的分段存储与崩溃恢复

首版采用本地 UTF-8 JSONL 分段文件，方便直接读取、增量追加和按段回收；逻辑记录与地址不依赖这一物理格式。`<ZHIXING_HOME>/logs/runtime/` 是新存储根，包含版本说明与元信息、记录段、附属详情、可重建索引及有界治理状态。日志应用只操作此存储及明确登记的日志文件。

同一数据根的所有进程共用 Store 写入协议，以**短时跨进程互斥**串行完成批量追加、预算检查、轮转和删除。锁不跨业务执行、网络、模型或用户等待；锁忙只影响有界日志队列。写入端不长期持有活动段文件句柄，轮转封闭旧段并创建新段，避免边复制边截断活动文件。清理只能处理 Store 拥有的普通文件，拒绝路径逃逸与链接替换。

批次完成后同步文件，段创建、封闭及治理元信息变更同步目录，再原子发布耐久水位；平台适配必须落实这些语义，同步失败或不受支持时不得冒称耐久。读取以完整记录及已发布水位为界；恢复在同一互斥下核对实际文件，处置不完整尾部、未完成轮转和未引用附件，不把索引更新成功当作记录已耐久。段内损坏如实标识；索引可删除重建，重建不生成新证据。

超出单条预算但值得保存的详情，经同样的内容检查后存为附属文件，归属一个记录段，引用携带长度和校验摘要；先持久详情再发布引用。附件写入失败时保留明确的不完整记录，发布记录前崩溃留下的孤儿由恢复回收。详情可先于主记录到期，读取明确返回已淘汰或缺失；附件不进入业务 ArtifactStore，也不获得独立的永久保留权。

记录端口先于业务入口可用；存储尚未就绪时使用同一有界队列和进程内健康状态。日志初始化有等待上限，单独的日志故障不阻止业务继续；后台按有限退避、可取消方式重试，不另开绕过预算的备用日志文件。正常退出先停止维护与重试，再在限定期限内排空队列，记录组件晚于业务排空关闭。

启动失败、进程异常由仍存活的入口或宿主记录实际证据；无法观察的最后阶段保持未知。日志故障通过限频的进程状态和终端提示暴露，恢复后补记可证实的缺口；通知本身同样受内容检查和失败隔离保护，不递归记录错误。

### 3.5 一个读取应用，地址与权限分离

稳定地址由 `storeId＋记录身份` 或 `storeId＋操作引用` 组成，独立于绝对路径、当前进程与段文件位置。CLI 提供本机日志位置和格式说明；地址中的来源可辅助选择设备，地址本身不授予访问权。跨设备关系通过引用连接，本地缺少远端材料时返回不可达状态，不把本机查询包装成全局完整视图。

LogApplication 提供查找、读取及策略/存储状态查询：按时间、来源、级别和关联身份筛选，从概览进入时间线及详情。各呈现形式来自同一记录集合，不另外保存模型生成的“诊断真相”。查询固定开始时可见的耐久上界，并同时限制扫描字节、返回条数、返回字节及执行时间；结果携带已覆盖范围和可继续读取的游标，后续新增记录另起查询。

游标绑定筛选条件、可见上界和授权范围，续页仍校验当前权限，失配时拒绝；扫描位置只能向前推进，不因缺索引反复扫描同一前缀。游标不锁定文件或复制数据，翻页期间发生淘汰时显式说明，不能静默跳过后宣称结果完整。离线读取不修改存储；索引不可用时有界扫描，重建由 Store 在互斥与预算内执行。

访问范围由受信任的调用上下文确定，不能由查询参数扩大。模型工具和 RPC 逐项过滤记录、关联信息和附件；无权访问时不泄露存在性，附件地址不能转换为任意文件读取。普通文件工具和外部程序直接读取原始目录，需要覆盖该存储的本机日志管理授权，不能等同于单条记录的读取权。

对只获部分记录权限的主体，既有 Security 裁决与运行工具投影必须阻止未隔离的文件或任意代码执行绕过查询边界；没有有效执行隔离时，不授予这类能力。Host 仅装配裁决后的能力，静态路径检查不能代替执行隔离；拥有原始存储管理授权的主体仍可直接查阅。

缺口使用统一的机器可读分类：`expired`（已淘汰）、`not-collected`（未采集）、`unavailable`（暂不可达）、`insufficient`（证据不足）；另行标注内容截断、脱敏及查询覆盖范围。查找未命中本身不产生 error 记录，也不证明已淘汰或未采集；无法确认原因时返回 `insufficient`，不无限保存每条已删除记录的墓碑。权限检查先于缺口解释，无权访问时不返回可推断记录存在的分类。

### 3.6 写入前守住总预算，淘汰后保持可解释

LogPolicy 定义总字节和文件数上限、保留期限与最长分段时窗、单条与附件上限、队列和查询预算，以及治理状态预留量。Configuration 提供配置，LogApplication 的配置应用动作携带预期版本，由 Store 串行校验并确认本机生效版本；普通写者只读生效策略，不能用启动快照覆盖它。减小上限时先回收至新预算，再确认生效；配置期望与生效状态分别可见，无法完成则报告受阻。

后台写入、索引重建和清理复用 device-capacity 的 `storage-background` 许可，控制内存、临时空间与 I/O；日志持久总额仍由 Store 治理。物理操作分为有界步骤，先取得资源许可再进入写互斥，持锁不等待资源，步骤结束即释放。进程入口提前装配本机资源端口并交给 Host 沿用，离线入口也本地装配，不能因主服务未就绪而绕过资源限制或无法查阅。

预算按**当前受管占用（含待回收）＋本批新增量＋临时写入峰值＋治理预留**计算，记录、附件、索引、临时文件、清理信息和登记的旧日志全部纳入。同一互斥内先核实容量、必要时回收，再允许新增。额度仅在数据空间确认回收后归还；文件被外部读者持有时，即使删除目录项成功也可能尚未释放空间，未确认部分继续计费。空间不足或维护受阻时停止相应新增，不能依赖“稍后轮转”维持硬上限。

记录按关键过程与高频详情分级，并分别成段；来源在发生时就将关键上下文列入必要记录，异常前后关联保留有界，不能事后恢复已放弃的细节。按期限与容量压力回收，先附件和低价值详情，再较旧记录；回收以封闭段为单位。正在运行、发生错误或结果未知只改变优先级，不形成无限保留例外。

活动段达到大小或最长时窗即封闭；段级到期以其中最早的 Store 接纳时间和该层保留期限计算，后续追加或来源自报时间不能推迟到期。期限到达时，即使段未满也先封闭再回收；新记录进入新段，长任务不能钉住旧段。

Store 在可写启动、写入前及周期到期检查中推进维护，无新日志也会唤醒。每进程只有一份可取消、不积压的维护循环，多个进程经同一互斥推进；资源或回收受阻时有界退避，并暴露超期未清理状态。所有产品进程停止后，由下次可写 Store 启动接续；离线查询仍保持只读。

回收按“持久登记淘汰范围与原因 → 回收文件数据空间 → 移除目录项并确认”推进；平台适配可对已淘汰文件截断并同步，但不能改写仍保留的记录。未确认回收的对象保持身份与占用账目，重启后继续；读取遇到整段失效须报告缺口，不能靠持有句柄取得保留权。治理状态使用固定预算并可合并已完成的历史范围，超过其可解释范围只报告未知。临时文件恢复、索引重建和清理自身同样受预算约束；清理不能依赖原对话、模型或外部服务继续存活。

### 3.7 演进与接入约束

公共信封和来源内容分别版本化：兼容新增字段不改变原含义，不兼容语义使用新版本；读取端保留仍在保留范围内的旧版本解释能力。未知来源保留公共信息并标识无法展开的部分。物理格式或目录迁移保留逻辑身份与地址解析，不以重写记录含义完成升级。

生产接入覆盖 CLI 启动与前后台入口、ApplicationHost、领域应用边界、Kernel/Harness、工具及 MCP、扩展进程和设备交接。现有 `diagnostics.ts`、LLM dump 与服务日志调用点接入同一采集、读取和预算合同；终端呈现仍由界面负责，后台 stdout/stderr 不再直连无界追加文件。切换经既有更新与排空边界停止旧直写进程，所有写者兼容且遗留占用受控后才确认新预算生效。旧文件以 legacy 格式只读识别并计入治理，不伪装成新的结构化证据。

依赖门禁约束业务采集方反向导入读取引擎，以及运行日志绕过统一入口新增独立文件；终端界面输出按其呈现职责保留。

实现验收必须覆盖多进程同时写满预算、错误风暴、低流量与无写入跨保留期限、长任务跨淘汰、外部读者持有被淘汰文件、追加/附件/回收中途崩溃、日志初始化及采集异常、服务启动失败、远端离线、受限主体的工具权限、持续写入与授权变化下的分页、离线缺索引、策略降额与旧写者切换，以及旧版本记录读取。通过这些场景证明记录、读取和治理合同，而不以日志文件存在或正常路径可读代替。
