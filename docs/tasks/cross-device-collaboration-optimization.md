### 一、底线问题：跨端到底怎么通信？成不成立？专家认可还是需要推倒？

**直接给结论：通信方案本身选型完全正确、主流且安全级别极高，绝对不需要推倒；但“跨公网双内网开箱连接”只做了一半，当前缺一个可部署的中继入口或打洞环节。**

#### 1. 为什么大厂靠中心服务端，而我们的方案在架构上完全成立？
大厂做跨端，手机和电脑都连大厂自己的云端中心服务器。知行是纯用户自部署、没有官方服务器，所以在代码里选的是**“用户自有值班节点（Anchor）做枢纽 + 出站双向 TLS 1.3 长连接 + 零信任盲中继 + 双平面分离”**：
- **连接方向**：干活的工作电脑不需要公网 IP、不需要开防火墙入站端口，统一通过 [`outbound-tunnel.ts`](../../packages/mesh/src/outbound-tunnel.ts) 主动向外发起强制双向证书认证的 TLS 1.3 长连接（[`handshake.ts`](../../packages/mesh/src/handshake.ts#L141-L220)），断线 `250ms–30s` 退避自动重连。
- **双通道设计**（[`bootstrap.ts`](../../packages/mesh/src/bootstrap.ts#L256-L285)）：同局域网或节点可达时走 **TCP 直连（`direct`）**；跨异地内网时走 **端到端加密盲中继（`blind-relay`）**——双端同时向中继发起出站连接，凭按天轮换的 HMAC 会合键配对，中继只做纯密文字节流桥接（[`blind-rendezvous.ts`](../../packages/mesh/src/blind-rendezvous.ts)、[`blind-relay.ts`](../../packages/mesh/src/blind-relay.ts)），外层再握端到端双向 TLS 1.3，中继自己完全解不开内容。
- **双平面分离**：任务准入和结果落盘走值班节点（控制面）；高频流式输出与权限确认在可达时直连执行电脑，不可达时经中继兜底，并靠本地磁盘缓冲与游标无损续流（[`lossless-data-plane-runtime.ts`](../../packages/cli/src/serve/lossless-data-plane-runtime.ts)）。

**专家视角评价**：在“不依赖厂商中心云后台”的自托管系统里（对标 Cloudflare Tunnel、Teleport、Tailscale DERP 兜底），**“内网节点纯出站 mTLS 隧道 + 零信任盲中继 + 可直连时直连”就是业界标准正统方案**，而且上层协议与底层帧传输（[`transport.ts`](../../packages/mesh/src/transport.ts)）完全解耦。任何分布式或网络专家来看，都不会说你底层通信方案选错了，更不存在需要推倒重来的问题。

#### 2. 但当前通信落地上的真实缺口是什么？（必须如实说清）
- **如果你有一台带公网 IP 的轻量云主机（VPS）当值班设备**（或两台电脑在同一局域网 / 挂了 Tailscale 虚拟局域网）：家里电脑和公司电脑都向这台公网值班机打 TLS 出站长连接，**今天代码就能稳定跑通**。
- **但如果你既没买 VPS、也没挂虚拟组网，只有“家里宽带内网电脑 + 公司内网电脑”两台裸机**：**今天直接用是连不通的**。原因有两个代码事实：
  1. 盲中继的核心匹配器 [`BlindRendezvousMatcher`](../../packages/mesh/src/blind-rendezvous.ts#L32) 写好了，但**CLI 里没有提供启动独立盲中继服务端的命令**（全仓只在测试文件里实例化过它），也没有集成 UDP NAT 打洞；
  2. `zz pair` 默认只抓本机网卡的局域网私有 IP（如 `192.168.1.x`，见 [`mesh-pair-command.ts`](../../packages/cli/src/serve/mesh-pair-command.ts#L2596-L2603)），而公网公布参数 `--listen / --advertise / --relay` 全被 `.hideHelp()` 隐藏了（[`index.ts`](../../packages/cli/src/index.ts#L355-L358)）。

### 二、能力与体验现状：假设网络已通，用户好不好用？功能正不正常？

顺着“我在家里电脑发任务，让公司电脑去干活”这条真实用户链路深查代码，结果是**“底层能力上限远强于 ToDesk，但上层用户交互存在真实的未闭环断点，目前用起来并不顺畅”**。

#### 1. 产品方向对比（原生跨端 vs 智能体操纵 ToDesk）
- 如果让智能体操控 ToDesk 等远程桌面，本质是看屏幕截图 + 模拟鼠标键盘：公司电脑不能锁屏、执行时抢占键鼠、每步截图极费视觉 Token 且延迟高、改代码跑命令远不如原生 Shell 稳，电脑关机就直接失败。
- 知行做成的原生跨端能力，在机制上确实解决的是真痛点：
  - **后台静默原生执行**：公司电脑以系统服务后台运行，直接调本地工作区、Shell、MCP 和系统凭据库跑完整运行时，不占桌面；
  - **关机排队与上线自动续跑**：公司电脑没开时任务在值班设备耐久排队，开机连上后自动恢复执行；
  - **防重复副作用与秘密隔离**：API Key、MCP 凭证和真实物理路径永不出本机；执行中途断网崩溃不会盲目重跑第二遍，而是进入 `uncertain` 待 `/resolve` 人工裁决。

#### 2. 但代码实查暴露出 3 个严重影响可用性的真实问题（以前没揭开的盖子）

1. **多台电脑同时在线时，普通主对话会直接撞“未实现选机交互”的报错！（功能断点）**
   - 看 [`selection.ts`](../../packages/core/src/environment/selection.ts#L166-L179) 与 [`setup-delivery.ts`](../../packages/cli/src/setup-delivery.ts#L1600-L1602)：当家里电脑和公司电脑都在线、且都开着默认的 `executor`（干活）角色时，如果你在**未绑定特定工作区的新主对话**发消息，路由器发现有 2 台可用电脑且无历史亲和，会抛出 [`ExecutorSelectionRequiredError`](../../packages/core/src/environment/selection.ts#L226-L242)（要求用户明确选哪台电脑执行）。
   - **但全仓前端 TUI 根本没有接这个错误的选机弹窗，也没有提供在对话里临时指定“这轮去公司电脑跑”的入口**（RPC 协议留了 `ExplicitEnvironmentSelection` 字段，终端 UI 没接）！结果就是两台电脑同时在线时，必须在绑定了某台电脑目录的 `/work` 工作场景里才能唯一定位设备，普通主对话新开直接报错卡死。
2. **在家里电脑上新建绑定公司电脑目录的工作场景不顺手（体验断点）**
   - 公司电脑必须先在公司本机敲命令行 `zz workspace create <名称> <路径>` 授权目录；之后你在家里电脑打开 `/work` 按 `Ctrl+N` 新建工作场景时，交互向导 [`workscene-create-assist.ts`](../../packages/cli/src/runtime/workscene-create-assist.ts#L105-L108) 只接了本机路径创建和空目录创建，**没把“直接从公司电脑已发布的工作区列表里点选绑定”接进向导**。
3. **首次配对操作偏重**
   - 第一次 `zz pair` 强制要求当场抄写长串恢复码并无回显逐字回读验证、跑完首份加密检查点才放行（[`mesh-pair-command.ts`](../../packages/cli/src/serve/mesh-pair-command.ts#L467-L550)），安全拉满，但对只想快速连两台电脑的用户来说门槛偏高。

### 三、架构设计评估、10 分制打分与最终定性

#### 1. 架构为什么做成了现在这样？
这套模块最突出的特征是**“极度头重脚轻”**：
- **底层分布式内核做得像银行账本一样硬**：单对话唯一 Owner + 单调 `epoch` 栅栏 CAS、执行账本三分续跑、无损游标续流、离线本地会话收编（`ConversationTransfer`）、值班计划迁居（`zz duty`）、离线恢复根灾备（`zz backup`）全用严密的状态机闭环了。
- **代价是两头受挤压**：一是体量与侵入性极重（仅 [`mesh-runtime-assembly.ts`](../../packages/cli/src/serve/mesh-runtime-assembly.ts) 2,809 行、[`mesh-pair-command.ts`](../../packages/cli/src/serve/mesh-pair-command.ts) 2,644 行，外加十几个近百 KB 的账本/迁移文件），把后续所有新业务都拖进了“单机 / 锚点域 / 本地域 / 迁居收编”的四重适配成本里；二是精力全消耗在极端容错和灾备上，反而把最表层的**“公网怎么轻松连上”和“终端里怎么顺手点选公司电脑”**留了尾巴。

#### 2. 客观打分（满分 10 分）

| 审查维度 | 得分 | 客观依据 |
| :--- | :---: | :--- |
| **1. 底层通信架构选型与传输安全** | **7.5 / 10** | 出站双向 TLS 1.3 + 零信任盲中继 + 双平面游标续流，方案正统强大、无需推倒；扣分在盲中继未交付独立服务端命令、无 NAT 打洞、公网配对参数隐藏。 |
| **2. 分布式一致性与副作用安全** | **9.2 / 10** | 单 Owner 栅栏提交、执行账本三分续跑防重复副作用、本机秘密与物理路径隔离，远超同类开源智能体的简单网关转发（OpenClaw 跨节点约 `7.2/10`）。 |
| **3. 跨端功能闭环与用户使用体验** | **6.0 / 10** | 同网+单执行机或已绑 `/work` 场景能跑通，但**双执行机在线时新主对话撞 `ExecutorSelectionRequiredError` 缺选机 UI、`/work` 向导未接远端工作区点选、首次配对过重**。 |
| **4. 架构边界与跨模块维护成本** | **5.5 / 10** | 分布式与迁居/收编状态切面深度侵入上层业务，显著放大了后期每个模块的开发工作量。 |

#### 综合评分：**`7.0 / 10`**

### 四、最终客观判断（对应你问的三档定性）

1. **用不用推倒重来？—— 绝对不用。** 最难的通信安全底座、帧传输抽象和防重复副作用的分布式账本都已经建得非常扎实，推倒是把最值钱的 9 分底座扔掉。
2. **能不能放着不管？—— 不能放着不管，它比运行核心（8.3 分）的问题更实际。** 运行核心主要是代码结构老旧、日常用着没硬伤；而跨端协作目前有**真实卡用户脖子的断点**（无 VPS 时双内网连不通 + 多台干活电脑同时在线时新主对话缺选机 UI 直接报错）。
3. **准确归档：属于“底座很硬不用推倒，但必须立项做一次『打通用户体验闭环 + 补齐跨网中继/连接入口 + 收敛耦合面』的专项优化”。**
