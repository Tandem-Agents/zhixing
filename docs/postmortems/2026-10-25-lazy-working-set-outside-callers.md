# 按键工作集漏掉事务外的同步读取

## 信号

把整份内存状态改成按键装入的工作集之后，领域用例与新旧差分全部通过，受影响全集里却出现“状态待装入”的错误直接抛给调用方（例如 `GovernorStateRequired: Resource governor state is being loaded`）。

## 经过

资源调控器的状态改为按键装入：读到未装入的键时报待装入，由日志锁内的视图或锁外的成批读取补齐，再在新的复制上重做。日志事务的决定函数和归约里的同步核对，都由日志自身的重做覆盖。

会话与作业两个日志的 `submitBundle` 有一个“已提交、按耐久记录重放”的分支，在日志事务之外同步核对用量终值。待装入错误在这里没有任何重做循环，直接漏给了调用方。调控器自己的用例和作业日志的差分用例都在热状态下走这个分支，没有一个是新建实例、未预热；只有一条经真实 Host 发布者重放提交的 cli 用例，在冷状态下走到了这里。

## 原因

自审只核对了一个问题：读取者会不会把缺载当成不存在。没有做的是列出每个同步读取方法的全部调用点，再分成两类：

- 在事务决定函数或归约里，由日志重做覆盖。
- 在事务之外，需要自带补齐。

冷实例的覆盖也只给了直接调用调控器的用例，没有经过日志的公开入口。

## 可复用的做法

- 把状态改成按需装入时，逐个列出每个同步读取方法的全部调用点并分类：事务决定函数和归约里的，由日志重做覆盖；事务之外的每一处，要么在锁外补齐后重做，要么证明不可达。
- 事务外的每一处，都配一个经公开入口、在新建且未预热的实例上走到的用例，再用撤回修复的变异确认它确实会失败。
- 姊妹领域（会话与作业、锚点与执行端）的同一分支通常成对存在，修了一处就去查另一处。

## 适用边界

只针对“缺载时报待装入、补齐后重做”的按键工作集。整份装载的状态没有这一类问题。
