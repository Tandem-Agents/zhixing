# 把单页上界当成整份容量：改呈现结构时以旧实现的可达内容为下限

## 信号

把一个列表页改成新的呈现结构（分节、两列、卡片等）后，测试被改成接受“另有 N 项未能显示”之类的省略；而旧实现在同一份输入下，全部条目都能看到。或者：窄屏下一行提示放不下，于是在末尾截断，键名只剩半个。

## 发生了什么

终端的几个信息页（用量、运行状态、命令帮助、任务推进）从“逐行文字”改为结构化分节。新结构的协议规定：一个区块最多 512 行，一页有字节上限。实现时，这两个上限被当成了整份内容的容量，于是写了一个裁剪函数：超出时从最长的列表尾部裁掉，并写明未显示的条数。

用 700 条子任务测试时，新实现只给出 512 条，并写“另有 188 项未能显示”。原有的分页用例因此失败，用例随后被改成断言这句省略说明。审查方拿改前的实现做对照：同一份输入只有约 79 KB，旧实现的文字分页把 700 条全部送达。新实现等于把原先能看到的明细截掉了，属于回退。

修正后，可增长的列表都经已有的多页通道分页：一页的上限只决定在哪里换页，整体容量（与安全页规则说明共用同一个常量）才决定是否省略；省略只在真实超过整体容量时出现，并写明条数。同一轮里，候选面板的键位整串交给信息行，窄屏时在末尾被截成“Ct…”。修正为由 N 按项给出键位，U 按实际宽度整项分配到信息行与面板底行，放不下的项不丢、不截半。

## 教训

- **改呈现结构前，先用旧实现给出可达内容的下限。** 拿同一份输入（含很长的列表）跑一遍旧实现，记下“哪些条目、哪些字段用户原本能看到”。新实现以此为验收下限，逐条对账可达性，而不只是字段名。
- **区分换页上界与整体容量。** 单页、单区块的上限只决定在哪里换页；只有整体容量才决定省略。省略必须写明条数，而且只在真实超过整体容量时出现。原有的输入上界（超过时明确失败）照旧保留。
- **改测试预期前，先判定是合同变化还是回退。** 旧用例失败时，先问它证明的用户能力（全部可达、末项可达、有下一页）在新实现里是否还成立。成立才改写断言的形式；不成立就是回退，修实现，不改预期。
- **提示放不下时按整项取舍。** 由数据方按项给出（键位、操作），界面按实际宽度整项排布到现有的固定区域（如面板底行）。不在字符中间截断，不默默丢掉某项操作。
- **对照用例要先能抓住回退。** 补上“700 条全部可达、末项可达、有下一页”和“窄屏每个键名完整可见”的用例后，把实现改回旧写法跑一遍，确认它们真的失败（键位改回整串时复现了实拍的“Ct…”）。
