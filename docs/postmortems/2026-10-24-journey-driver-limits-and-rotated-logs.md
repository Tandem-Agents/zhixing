# 扩展既有旅程驱动：参数上限、日志轮转与就绪判据

## 信号

在已验收的真实终端旅程驱动上加长会话造数后，长跑在中途被套件按寿命结束；改大寿命后套件启动即以退出码 64 退出；事后取冷启动阶段账，窗口内一行运行时日志都没有；某次冷启动“就绪”后首发被拒，等满超时才失败。

## 经过

造数段在原驱动上加了逐条发送、定期思考中断和一次压缩。三条试跑通过后直接跑 60 条，第 60 条和压缩完成后、第 61 条回复前，ConPTY 套件按默认会话寿命 450 秒到点结束会话。随后把寿命改为 3600 秒，套件参数检查要求寿命在 5～450 秒之间，启动即返回 64。已生成的会话数据可以复用，但两次运行都没有产出新的有效观测。

之后取这次长会话启动的阶段账，运行时日志只保留约 3 个 2MB 的段，长会话里每轮约写 100KB，启动窗口的行在两分钟内就被淘汰。

长会话 home 的冷启动中，底部提示在会话尚在准备时已经显示“Enter 发送”，驱动按这句提示判定就绪并立即发送，产品回“当前无法接纳输入，草稿已保留”。这是产品缺陷（启动态在中途的视图发布里丢失），也说明依赖该提示的旧样本需要逐项核对真实可接纳时刻，不能从这个反例推断所有样本的提前量。

## 原因

- 扩展驱动时只看了驱动本身的流程，没有读它调用的原生套件的参数检查与寿命语义，也没有先确认中途结束后能否复用 home 分段续跑。三条试跑只能说明流程能走通，说明不了长跑在套件寿命内放得下。
- 阶段账的取数默认日志一直在，没有考虑日志按段轮转的保留量与写入速率。
- 就绪判据用的是单条提示文字，没有和“产品此刻是否真的接纳输入”对齐，也没有逐帧核对启动阶段的画面切换。

## 可复用的做法

- 扩展既有驱动或套件前，先读它调用的每个外部程序的参数检查、寿命与退出码含义，按“预计时长 ≤ 寿命上限”拆分运行，并确认可复用 home 分段续跑；超限时分段，而不是改大参数。已知的上限写成驱动启动前的参数检查（ConPTY 套件寿命 5000～450000 毫秒），不靠每次记得：读过这条沉淀之后仍有一次按算术填了更大的寿命，套件立即以 64 退出。
- 运行中读取产品正在写的文件（跟随日志段、快照），用以全共享方式打开的读取（Node 的 readFile），不用 copyFile。Windows 上 copyFile 打开源文件的共享方式会让日志写入方的追加报共享冲突（NTSTATUS 0xc0000043），产品日志随之降级再恢复，观测本身成了干扰源。
- 需要事后分析的日志，在关注窗口结束后立即复制出来（驱动在就绪与首回完成后各快照一次），再按行 id 去重合并；不要假设长跑之后启动窗口的日志还在。
- 就绪判据对齐真实接纳：每个样本都排出启动画面的状态切换（提示文字、底部按键提示、消息行），发现“可发送”早于“已恢复/准备就绪”时先查产品，不在驱动里加等待掩盖。
- 修“提示与实际准入不一致”时，回归用例要同时驱动生产的准入入口（提交动作）和视图发布，并在可发送帧之后的每个异步步骤上设闸门；只断言显示投影会漏掉准入门的真实释放点。第一次修复只让提示保持“启动中”，可发送帧发出后启动仍在等待确认核对、准入门未交还，由总控用生产方法的受控时序反例指出，多返修了一轮。
- 新增或改动观测钩子时，先用最短的真实装配路径确认目标进程、目标文件路径、计数与输出都命中，再扩到活动后首冷等组合场景；独立进程里的自检只说明钩子本身能跑，不说明它进入了宿主。曾有一次三段运行全部白跑：钩子只加载进了入口进程，且路径匹配的正则被 sed 吃掉反斜杠。
- 已产出的数据与有效观测继续复用，不为修参数重做整段造数。
- 新写步骤文件时，每个等待模式先对照同一画面的已有截帧核一遍：它等的文字画面上是否真会出现（工具调用的输出默认折叠，只显示“调用 X 1 次”），以及它是否会被上一轮留在屏上的内容提前命中（第二轮的回执编号要排除第一轮的）。曾因 allow 一步只等折叠起来的工具输出文字，产品已完成这一轮，驱动仍等满 60 秒失败，白跑一轮。

## 适用边界

只针对在既有驱动上扩展新场景的长跑与事后分析；短的冒烟旅程仍按原驱动直接运行。
