# 公共 API 抽取中的兼容盲区

适用范围：承诺保持旧调用合同的跨包抽取与重构。本文记录历史审查失误，不表示当前仍存在该缺陷，也不要求已经明确退役的接口永久保留兼容层。

## 发生了什么

推进领域服务从 server 抽到独立包后，内部消费者、依赖方向和行为测试均已通过，但 server 根入口直接导出了新包接口。三个同名能力中，两个已有旧参数适配器却被根入口绕过，另一个没有适配器。旧调用方因此无法继续使用原合同。

这个缺口经过一次修复和一次自审才被发现，额外消耗了一轮审查与修复。

## 为什么没有一次解决

- 把“同名导出与新包实现恒等”误当成兼容，验证了符号存在，却没有验证旧调用合同仍可替换。
- 消费者扫描只覆盖仓库内已迁移代码，没有把包根入口和外部旧调用方视为独立消费者。
- 测试直接引用内部相对路径，证明了局部适配器可用，却没有证明公开根入口实际经过适配器。
- 修复围绕已发现的依赖倒置问题展开，没有先列出全部变更签名并逐一裁决“直接复用或兼容适配”。

## 教训

在保持旧调用合同的前提下，公共能力跨包抽取应核对：

1. 以抽取前声明为基线，逐项核对名称、参数、返回值和导出路径。
2. 签名与行为均保持合同的能力可以直接复用；签名变化时应在承诺保留的旧入口适配，不能用重导出冒充兼容。
3. 按实际公开面检查包根入口、子入口及仓库内外调用方式，不能只扫描已经迁移的内部消费者。
4. 验证公开声明能接受旧调用、真实公开入口连接到正确实现（需要适配时确实经过适配器），以及旧调用方式的运行行为；不能只测内部相对路径。
5. 未完成上述核对时，不得以“构建和现有测试通过”宣告兼容成立。验证限于受影响合同，复用必要的定向检查，不为此另建通用门禁体系。
