# 2026-05-14 · 确认面板输入消失：旧构建干扰验证与输入分流遗漏

这是一次 CLI 诊断与协议理解失败复盘，适用于源码和实际运行产物不一致、组件切换宿主后输入行为变化的场景。以下过程和成本来自历史记录；修复有效与底层时序原因已证实是两件事。

## 现象与失败轨迹

权限面板由 alt-screen 改为 chrome inline 后，“拒绝并说明原因”的输入模式不显示字符，但方向键和 Enter 正常。旧模式曾能输入，新模式失败；控制键正常不能证明文本输入链也正常。

| 阶段 | 当时动作与证据 | 能得出的结论 |
|---|---|---|
| 改动 A | 去掉 `if (key)` 守卫，试图接纳 `key=undefined` 的字符；运行测试和类型检查，却未构建 | 用户反馈无效不构成对 A 的有效反证 |
| 改动 B | 将 `onPaste` 从 no-op 改为输入模式接收文本 | 后续构建并验证后恢复，但不能仅凭恢复证明分流的全部成因 |
| 查运行产物 | 源码在 19:34 后修改，用户运行的 dist 仍是 19:24 版本；记录指出两次测试使用旧产物 | 验证回路被构建遗漏污染，不能把旧版本结果归因于新修复 |
| 反查协议 | 发现相邻调用者对 `onPaste` 分别采用接收和丢弃 | 相似组件并不具有相同输入职责，照搬 no-op 会遗漏文本路径 |

当时提出过“chrome 重画使 microtask 拥塞，导致多个字符被聚合为 paste”的解释。现存材料不足以证明这一精确时序链，也不足以独立排除改动 A 的影响；不把“同步输出抢占 microtask”作为已确认机制。可确认的问题是文本输入模式存在丢弃整条批量输入路径的实现，以及旧构建使假设验证失真。

## 协议理解与修复理由

`wrapKeypressHandler` 区分单次按键与批量/paste 输入，调用者按业务模式决定如何消费。其分流不等于用户一定进行了手动粘贴；具体聚合原因应通过事件轨迹确认。

| 调用者 | 当时处理 | 对新实现的启示 |
|---|---|---|
| `typeahead-input` | `finalizePaste(content)` 接收文本 | 文本输入不能漏掉批量路径，但不应照搬其所有处理细节 |
| 旧 `selectWithInput` | `onPaste` no-op | 旧模式曾能打字，不证明丢弃 paste 满足新组件需求 |
| 新 `SelectOperationRegion` | 初期照搬 no-op，后改为输入模式接收 | 应依据文本输入职责处理单次和批量路径，而非依据组件名称相似性 |

当前 [SelectOperationRegion](../../packages/cli/src/security/select-operation-region.ts) 的 `onPaste` 在未结束且处于输入模式时交给 `handlePasteInInput`；[typeahead](../../packages/cli/src/typeahead-input.ts) 的批量路径交给 `finalizePaste`。选择模式、已结束状态和文本输入模式具有不同边界，并非所有状态都无条件接收任意字符。现行输入职责见 [CLI 选择与确认](../modules/cli/selection.md)。

| 理由 | 可以支持什么 | 不能替代什么 |
|---|---|---|
| “猜测某时序让字符走了 paste” | 待取证的诊断假设 | 不能仅以修复恢复证明假设正确 |
| “文本输入模式必须处理合法的单次与批量文本” | 对真实遗漏路径进行修复的业务依据，不依赖特定宿主时序 | 不能以防御性设计之名扩建无关兜底，也不能免除定位和必要验证 |

## 成本与可复用教训

旧记录统计用户复现 4 次以上、重启至少 4 次、约 5 轮对话，其中两次测试被旧构建污染。用户在反复失败后主动要求定位并提供按键诊断手段。这里的浪费来自无效验证与证据不足，不是所有多轮诊断本身。

| 信号 | 应采取的动作及边界 |
|---|---|
| 修改后用户仍报告原现象 | 先核对实际命令入口、所运行的构建产物与构建结果，再判断假设是否失败 |
| 测试读源码，用户运行 dist | 两条验证链分别对齐；CLI 改动构建用 `pnpm cli:build`，上游改动按项目规则用 `pnpm build`，成功后再让用户验证 |
| 相同逻辑换了同步/异步、直写/队列等运行环境 | 对比输入路由、资源与调度差异；源码分析和实际事件观测结合，不因“跨宿主”就排除代码缺陷 |
| 同接口的相邻调用者处理不同 | 先识别调用者决策点、合法输入和状态边界，再决定复用哪部分 |
| 修复恢复，却说不清原因 | 分别报告观察结果、合同依据和未决假设，避免把合理修复包装成底层根因已证实 |

构建时间戳是线索，不是生效的唯一权威：旧安装路径、不同 checkout 或未重启进程仍可能运行其他版本。测试通过也不能代替用户实际入口的构建生效。

当前 [CLI 入口](../../packages/cli/src/index.ts) 通过 `--log` 配置 [按键诊断](../../packages/cli/src/security/keypress-dump.ts)及流诊断。需要取证时优先复用已有能力并控制敏感输入范围，不要求每次故障增加新日志系统。先取得有效运行版本和事件路径有助于减少返工，但“一次复现、一行修复”只是当时设想的更短路径，不是已验证保证。
