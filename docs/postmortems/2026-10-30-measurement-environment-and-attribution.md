# 测量环境与归因口径：冷启动波动的取证循环

## 信号

- 同一构建连续几次冷启动样本相差 50% 以上，而宿主各阶段自身的 CPU 用量相近，多出来的都是等待。
- 每次样本不达标，就换一个解释再跑一整条旅程，取证范围从“首次连通”一路扩到“复现波动、全机负载、进程归属”。
- 用阶段事件里的进程 CPU 字段推断“某一步自己用了多少 CPU”。
- 用一个较快的样本判断“没有回退”或“已进入目标区间”。
- 用全产物的计数或时间线上的先后，推断某个进程启动图的依赖，或推算“结构下限”。

## 发生了什么

1. **测量资料放在仓库工作区里。** 旅程的 home、运行目录、截图与日志快照都在 Git 工作区内，运行时高频写入。逐进程 CPU 采样显示，TortoiseGit 的状态缓存持续扫描并拉起 git 子进程，约占 1.2 个核；加上编辑器的文件监视等，运行期间外部进程合计占 3–4 个核，整机负载 90–100%。把测量资料整体移到工作区外后，整机负载降到 30–49%，该扫描不再出现。
2. **把“存在干扰”说成“不是回退”。** 同一构建出现一个与旧构建相当的快样本后，就推出“慢样本不是代码回退”。同构建能跑出快值，只说明可以达到；外部占用与等待重合，只说明存在干扰；产品与环境可能共同作用。没有能区分两者的对照时，结论只能是未决。
3. **把进程 CPU 当成单步 CPU。** 阶段事件的 processCpuUserMs/processCpuSystemMs 是整个进程各线程的合计，并行阶段会互相计入，不能直接归给某一步。
4. **重提已被否决的修法。** “先显示、后写显示存储”曾因“首屏后首个操作仍排在同一写队列后，只是挪等待”被否决；后来换个说法又送审了一次。
5. **复用夹具前没核它是否可搬。** 合成夹具里的配置和索引记着夹具自身的绝对路径，整体改名就会失配，只能按产品路径在新位置重造。
6. **用全产物计数代替目标进程闭包。** 协议块在整个程序包里被 55 个块引用，就被说成“在 N 启动图里被 55 个块引用，只改 N 的导入去不掉”。按 N 入口求静态闭包后只有 5 个块、为 4 个函数引用它。改成窄导入并构建后，它仍在闭包里：另有模块经整包入口导入，摇树后留下纯副作用导入，整包入口把全部协议块带了进来。这只有按入口跨包求闭包、并在构建后复核才看得见。
7. **把时间线上的先后当成依赖。** 热入里“两支汇合后再串行请求”被当作产品边界，据此推算出“即使跨会话预热也到不了 2 s”的下限。逐步核源码后发现，连接、选会话、首屏读写都不依赖 U 首帧，串行只来自“由 U 的 startup 请求触发”这一协议安排。把启动改为放行后由 N 发起，阶段顺序证实启动链起点移到了 U 首帧之前；不同运行之间的尾段差值另有环境成分，只作净结果报告。
8. **复用参数写错，整组悄悄换了条件。** 验证组本应复用已有夹具，参数写成了运行名而不是驱动要求的复用格式。驱动没有报错，而是为每次运行新建空 home，结果比基线快约 3.5 s，看起来像是大幅收益。记录起始状态的快照四次完全相同，这本身就是信号，但当时没有核对。
9. **合并没接到真实消费端，仍跑完整组。** 首发里的“结算＋释放”合并按函数名认定了调用方，只改了一个不在首发路径上的同类封装。验证组第一例跑完，只核了运行条件（home、起始状态、身份），没核这次改动应生效的机制事实（治理提交 6→4），于是整组跑完才发现合并没生效。之后沿真实入口查到真正的收尾点，补接后又重建、重跑。

## 做法

- 性能测量资料（home、运行目录、截图快照、日志快照、运行输出）一律放在 Git 工作区与编辑器工作区之外；首个样本同时记录全机逐进程 CPU，确认外部扫描已消失。不关闭他人的进程，也不调系统设置来制造更好条件。
- 夹具迁移前先在 home 里查自身绝对路径（配置、索引、转录）；有引用就按产品路径重建，并单列为资料转换。新资料不与旧资料作因果对比。
- 归因三栏照实写：原条件下的现象、在什么条件下正常、机制归因是否充分；不充分就保留未决，原始慢样本不删除、不归一化。
- 单个样本不能判定目标是否闭合，目标按同条件固定组中位验收；一个快样本也不能用来免除某项义务。
- 进程 CPU 字段只作整进程背景；要归到某一步，用剖析（按函数）或线程内计时。墙钟变长而 CPU 相近，只说明多出的是非 CPU 时间；导入、打包、文件布局的改动同样会改变等待，不能据此排除本批改动。
- 结构变化（执行顺序、依赖边界）用阶段顺序证明，净收益数值单独报告；两次不同运行的差值不作唯一归因。
- 归属类运行（剖析、钩子）开跑前，先查旧证据是否已经回答同一个问题：如果结果表里有一支可以由旧归属直接预见（例如同一阶段“无单一热点”已被多份剖析证实），就不跑，直接用旧结论推进到结构判断。候选或数值变了，本身不构成重做泛化热点调查的理由。
- 提修法前，先按题目检索信箱历史与作业方案里已有的审查结论；已被否决的路，只有补齐当时否决理由要求的完整设计后，才能并入整轮方案再交。
- 不把“再跑一组看看”当默认动作：新增整链运行之前，先写清两种结果分别会改变哪个实施取舍；改变不了，就不跑。
- 体积与依赖类结论，按目标进程入口跨包求静态闭包，不用全产物检索计数；改导入之后，构建完再用闭包工具复核一次。
- 算任何“下限”之前，逐条核对串行链上每一步在源码里是否真的依赖前一步，并找出触发它的是谁。时间线上的先后只是现状，不是边界。
- 运行命令按驱动的参数解析来写，不凭记忆拼。驱动对写错格式的复用参数要在建目录前直接报错，不能静默换成新资料。一组的第一例跑完先核三件事：运行实际用的 home 是否就是预期的复用对象、起始状态是否随运行变化、候选身份是否一致；任何一项不符就停组，不把“运行成功、结果很快”当作条件正确。改动类运行还要核预先写定的机制事实（如提交次数、帧内容）；未生效就停组、先定位接线。旅程运行闸要求结果表写“跑后先核：”。
- 改一条调用路径之前，从观测到的事实（某次提交、某个事件）沿真实入口、装配实例逐级找到调用点，不按函数名或形状认定。能用装配层直接反例证明“目标场景确实走到改动”的，先写这个反例，再构建、再跑旅程。样本标签按实际的构建与执行时间线写，例如“构建后首次执行”只给真正第一次执行该产物的运行。

## 适用边界

外部负载在用户真实环境里同样存在（编辑器、聊天客户端等），产品性能要在这些负载下达标；这里要排除的只是测试资料本身落在仓库里所引发的扫描，它不属于用户正常启动的成本。
