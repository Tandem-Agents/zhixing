# 一封没走 receive 的信压住了之后所有通知

## 信号

- 对方说已回信，本会话没有被唤起；监听进程活着，health 也在更新。
- status 里新信的 `notification` 是 `null`（从未尝试通知），而更早的某封信是 `submitted` 但 `received: false`。

## 经过

信箱监听修好崩溃之后，又出现一次接信中断：

1. 18:19，监理来信，通知送达（`submitted`）。
2. 负责人当时正在处理总控的信，用 `cat` 直接读了监理信的文件，没有走 `bridge.mjs receive`，这封信因此没有收件凭据。
3. 19:04，总控回信落盘。监听每 3 秒扫描一次，但 `notify` 有一条闸：收件人还有“已通知未收取”的信时，不再给任何新信发通知。
4. 于是总控回信一直不被通知，直到用户问起。重启到修好的代码后，新监听立即通知了这封信。

## 根因

1. **设计假设靠收件人的操作习惯成立**：闸的理由是“通知会排队、收件时一并读到全部待处理信”。这个理由成立的前提是收件人每次都走 receive；只要有一封信被看过却没留下收件凭据，闸就会无限期压住之后所有新信。
2. **两次事故是两个缺陷**：上次是监听进程崩溃（活性问题）；这次进程活着，是通知逻辑把自己锁死（策略问题）。上次的验证只证明了“进程不死、新信能送”，没有覆盖“有一封未收取的旧信时，新信还能不能送”。
3. **操作侧绕过了协议**：看通知后直接 `cat` 文件，等于在协议外收信。

## 做法

1. **新信总是通知一次**：已确认送达的信在本代次内不重复通知；失败和结果未知按退避重试。去掉“有未收取旧信就不通知”的全局闸，任何一封信的状态都不能挡住别的信。
2. **回归用例照事故原样**：第一封已通知、未走 receive，第二封必须照常通知；再扫描不重复。单元和真实监听进程两层都覆盖。
3. **收信只走 `bridge.mjs receive`**：读正文用 receive 的输出，或在 receive 之后再看文件，不直接读文件代替收件。
4. **怀疑没收到信时，按段核对，不猜**：信件是否落盘 → status 里 `notification` 是 `null` 还是 `submitted` → 是否有更早的 `submitted` 未收取 → `listener-events.log` 里有没有退出或异常。

## 适用边界

适用于所有“按对方状态决定是否通知”的长驻投递逻辑：任何一条“暂不通知”的条件，都要有不依赖对方配合的解除路径。
