# 静默漏跑、修前耗尽期限与偶发故障的定位顺序

## 信号

- 一批定向测试传了 8 个文件，结果“4 个文件全过、退出 0”，没有任何报错提示另外 4 个没跑。
- 修复前的证伪批次里，几个场景都跑满同一个网络重试期限（每个约 60 秒）才失败。
- 真实旅程里出现一次终端被关，随后几次同样操作都正常，想靠多跑几遍复现。

## 经过

- 定向批次的另 4 个测试文件路径写成了 `__tests__/` 下，实际在上一级目录。测试运行器把剩余参数原样当 vitest 过滤串，写错的路径只是“匹配不到”，批次照样通过。
- lost 回执的修前证伪有三个本机阶段，每个都让取回跑到 60 秒期限返回 stopped 才失败，一共 220 秒；它们共享同一个原因（目标只认 revoked/removed），第一个场景就足以证明。
- 终端被关那次，先读已有产物：画面从按下“验证连接”起一直停在“正在验证”，应用进程在按键后没有任何记录，而对照运行里保存后 0.4 秒就有落盘记录。据此提出“应用进程主线程被同步加载卡住”的假设，用只加载一个模块入口的心跳实验判别（主线程停顿等于加载耗时），再找到首次探测加载 MCP SDK 的链路。整个定位没有重跑那段旅程。

## 原因

- 运行器只校验自身选项，不校验位置参数是否存在。
- 修前证伪把“证明旧实现会失败”和“覆盖每个阶段”混在一起，让每个阶段都走完代价最高的等待。
- 偶发故障的第一反应是加跑次数，而现场已有的画面序列、各进程日志的静默区间和对照运行，已经足够区分原因。

## 可复用的做法

- 测试运行器对“形如测试文件、却不存在”的位置参数直接报错退出（scripts/test-source.mjs 已加，退出码 2，`-t` 的取值不受影响）。传文件列表前也可以先用 `ls` 核一遍。
- 修前证伪只取一个代表场景，并在第一个确定的错误或拒绝点受控结束；不要让多个同源场景各自耗尽同一个超时。修后覆盖不减。
- 偶发故障先读现场：失败前后的画面序列、每个进程最后一条记录和静默区间、同一操作的成功对照。从中提出一个能区分原因的观察问题，再用最小的独立实验回答（例如只加载一个入口、量主线程停顿）。补的观测要构建后确认进入目标进程；只有现场不足以区分时才重跑旅程。

## 适用边界

适用于定向测试批次、修前证伪与真实旅程里的偶发失败。全集与里程碑运行仍按既有放行规则执行。
