# 一帧滞后：先读逐帧布局值，夹具对齐真实结构

## 信号

界面状态切换后，只有一帧不对：正文下方留空、顶行横向错位，或者内容停在旧位置；下一帧就正确了。稳定后的截图与测试都看不出问题，只有逐帧读屏能看到。

## 发生了什么

终端界面在候选面板收起时，正文视口变高。实机逐帧读屏里先后出现两种一帧问题：

1. 正文停在旧位置，下方留空一段，下一帧才贴底。
2. 修完第一种后，新露出的几块在第一帧横向错位 3 列，下一帧才回到原位。

第一次修复没有先观察，按“滚动位置没跟上”的假设，在高度变化时提前设置滚动位置。原生用例显示滚动位置确实变了，第一帧却仍然只画出旧视口高度那几行。加一个探针，逐帧读出滚动框的视口高度、滚动位置与内容高度，立刻看出真因：滚动框的高度取自外层盒子的尺寸回调。这个回调在本帧布局之后才执行，所以滚动框本身就比外层布局晚一帧。改为在同一次布局里取高后，OpenTUI 按新视口收紧滚动位置，贴底的首帧就是对的。

第二种问题是在实机上才暴露的，原生用例的正文只有一块文本，不经过逐块挂载。实机正文由许多块组成，挂载哪些块由同样晚一帧的高度决定。视口一下子变高时，新露出的块在本帧布局之后才挂上，第一帧还没有布局位置。把用例改成多块正文后，原生环境里就复现了；挂载窗口按视口可能达到的上限预留之后通过。

## 教训

- **先读逐帧的布局值，再改。** 一帧问题先写探针：在目标帧渲染后、下一帧之前，读出相关渲染对象的尺寸、位置、滚动量，与稳定帧对照，确认是哪一个值晚了一帧。不要凭画面推断“哪一步没跟上”就改代码。
- **找滞后来源，而不是补校正。** 尺寸回调、帧后处理里写入的值，天然比本帧布局晚一帧。凡是要在同一帧生效的几何，都要在同一次布局里得到：用百分比或伸缩来取，不要拿回调量出的值再回填。
- **首帧比对的夹具对齐真实结构。** 测“第一帧就对”时，夹具要走与实机相同的渲染路径：多块正文、逐块挂载、相同的视口变化幅度。只比对末行位置不够，要整块比对首帧与稳定帧的整个区域。
- **用例要先在旧代码上失败。** 新的一帧用例先在未修改的代码上跑，确认它真能复现实机现象；修完再用撤回变异确认它能抓住回退。
