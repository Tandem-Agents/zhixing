# 屏幕顶行复读与诊断偏航

2026-05-09 的历史故障及协作复盘。旧全帧模型已被替换；本文保存现象、根因和可复用教训，当前设计以[屏幕渲染正文](../modules/cli/screen-rendering.md)为准，不把历史故障当作当前仍存在的问题。

## 现象与根因

流式长列表输出时，屏幕顶行反复进入回卷，原记录出现欢迎顶边超过 250 份。用户明确指出：“任何在屏幕上边界位置的内容都会重复，不仅是 welcome 块”。内容身份不是共同条件，物理位置才是。

当时 `freezeOverflowToScrollback` 按 tailBuffer 的逻辑行数判断是否超屏，但超宽内容会由终端自动换行；全帧重画的物理高度超过视口时，多余换行触发滚动，将顶行再次送入回卷。源码声明“不触发滚动”，实际计算却不能保证这个物理约束。

旧记录的定位依据包括用户运行日志、逻辑行计算与承诺的对照、列表路径未控制行宽，以及底部换行的机制分析；它没有提供可随本文重跑的完整终端实测材料。该材料不能证明跨终端兼容性。

## 处置与当前证据边界

处置方向改为 DECSTBM 输出区与固定区分离，活动段显式追踪位置，调用方控制可见行宽，避免重画全部历史。当前 `ScreenController`／`ScrollRegion` 已采用该结构；后续切屏及缩放协议另有演进，不能照抄当时的实施步骤。

结构替换消除了旧全帧模型，但物理换行、回卷和切屏仍受行宽合同及终端行为约束。

## 诊断偏航与可复用教训

原记录约五轮诊断、四轮设计讨论：先反复追“欢迎顶边为何重置”，直到用户多次提醒才检查物理滚动；设计又在已分层方案、区域隔离与旧模型补丁间摇摆。浪费来自未识别现象的共同条件，以及没有先核对明确的体验要求。

| 信号 | 应采取的行动 |
|---|---|
| 不同内容在同一位置出现相同故障 | 把位置／环境作为关键线索，检查外层机制，不锁死某个内容对象 |
| 注释或设计承诺与实现不一致 | 核实承诺是否仍有效，再定位差异；不能仅凭注释认定源码错误 |
| 多轮沿同一路径追踪无果 | 切换验证维度，做机制对照或最小复现，不把猜测交给用户选择 |
| 用户已有关键观察却仍反复提醒 | 重读并验证这些观察，把共性纳入假设约束；观察是高价值证据线索，不是免验证的绝对结论 |
| 方案靠牺牲固定输入区等核心体验省事 | 先守住有效合同，再选最简单的正确实现；既不以成本压掉正确性，也不以“最优架构”为由无限设计 |

这些方法应主动采用，不等用户触发。当前可直接检查[屏幕协调器](../../packages/cli/src/screen/screen-controller.ts)、[滚动区](../../packages/cli/src/screen/scroll-region.ts)和[行宽工具](../../packages/cli/src/tui/line-width.ts)，但历史函数名只解释旧根因，不作为当前源码导航。
