# 单条通信路线失败，被扩大为能力不可行

日期：2026-10-20。适用信号：某个CLI入口失败后，直接断言运行环境不支持需求；外围桥接反复重写，关键原会话入口却没有证据。

## 失败机制

用户需要Codex总控与已打开的Claude Code原会话自动通信，省去复制粘贴和反复发信号。早期调查集中于外部CLI续接；同一会话第二个驱动者会冲突，却被扩大为“面板打开就不能接收”。随后的分叉、界面操作和桥接尝试偏离原会话、低维护成本及用户省心的要求。

用户指出Reason Network后，才找到其利用宿主授予子进程的会话消息入口。架构师又提出宿主后台任务通知。这些证据说明选项空间曾被错误缩小；不意味着所有历史版本都支持同样能力，也不意味着找到API就已经完成本机通信。

另一个失败是把写文件、发送调用返回成功当作收发闭环，没有取得目标原会话的关联回复。双方共同判断也未消除盲区，因为没有独立挑战“没有入口”的前提。

## 改进

- 能力结论分为：已证可行、单条路线失败、尚未找到、有范围及版本依据的明确限制。后两种不能直接改写成整体做不到。
- 对新集成按问题核查宿主调度与通知、官方CLI、扩展点、会话IPC。先验证风险最高的原会话接收路径，再建设外围功能；成熟通道日常使用不重复调研。
- 需求或约束改变时，重新考虑此前排除的路线。人工阶段的约束不能自动成为自动化阶段的永久前提。
- 轻量看完整使用和维护成本。脚本短，但依赖模型反复记得续挂、要求用户经常救场，不符合省心要求。
- 分清代码存在、配置已安装、宿主已加载、通知提交、实际读取、关联回复及业务验收。真实往返验证使用普通无秘密标记，不提取凭据、不降低防护。

这些规则已落实于跨智能体通信技能。具体通道的实测状态留在通道登记；本复盘不把尚未完成的宿主集成写成成功经验，不再建设通用调查或观测平台。
