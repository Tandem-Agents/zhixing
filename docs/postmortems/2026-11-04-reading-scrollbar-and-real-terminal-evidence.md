# 会话滚动条重设计与实机取证的绕路

## 遇到的信号

- 方案经过多轮设计，用户一看就说“效果一点没变”。
- 需求写了“实现方式开放”，候选方案却全是在现有实现上换位置、换方向、换显隐。
- 实机驱动报出的失败，最后查明是驱动自己的问题。
- 计时结论先后反转：先判成漂移，后又全部归因于环境。
- 交审稿里声称“这一组是重叠样本”，事后发现重叠根本没有发生。

## 经过

会话正文的应用滚动条离窗口右缘有一段空隙。根因是 Windows Terminal 在可画网格外侧留了文本内边距和原生滚动条槽，应用画不进去，也关不掉。

设计阶段把“滑块长度和位置正确、原有功能保留”这条保底要求读成了“必须有一根可拖动的应用滚动条”，并把“全屏模式、应用自绘”当成不可改变的前提。于是所有候选都只是把同一根自绘竖条换个画法：
- 横过来；
- 悬停时才出现；
- 放进带框的局部区域。

鼠标移到最右时，每一种都仍然重现原图。调研已经查到同类产品的会话不自绘滚动条，这个结论却没被采用。最后的决定是会话里不画应用滚动条，滚轮、翻页、两端提示照常。

实施和取证阶段还有几次绕路：
- **驱动缺陷：**
  - 把读屏结果的字符串下标当成终端列号，行里有中文时点偏，被误报为产品缺陷；
  - 输入自检只看最后一行，长命令折行后误判，失败后还继续回车，一整批计时作废；
  - 多步旅程里残留的“/”草稿，让后面的探针消息变成了命令。
- **计时归因：**
  - 先后两组的热启动差，前一次用一组 A-B-A 判成“漂移”；
  - 后一次又按杀毒进程的 CPU 占用全部归因给环境。
  - 最终靠同时段交替块，加上把启动拆成三段比较，才得出可靠结论。
- **重叠样本：** 把“立即首发”当作“与预取重叠”的样本。实际上界面在输入框非空时不会启动预取，所以那一组没有重叠，据此算出的“撞车代价”也不成立。

## 教训

1. **“实现方式开放”时，现有架构不是前提。**
   - 先把用户的判断标准（这里是“顺手、不再有那段空隙”）写成可检验的画面条件。
   - 逐个候选放到原图那一刻核对。只要会重现原图，就淘汰，不论方案多完整。
   - 保底要求的本意是“别把现在好用的弄坏”，不能升格为头号约束，压过用户要的效果。
   - 调研结论和现有实现不一致时，先问“改成那样代价是什么”，再决定，不要只用一句话否掉。
2. **两个人在同一个错误前提下收敛，不等于方案正确。** 定稿前，由提出方把定稿画面和原图并排对照一次。
3. **实机驱动从读屏换算坐标，一律按显示宽度。** 中文占两格。新加的检查要在每种入口形态、每种行宽上先空跑一次；检查失败必须中止，不能继续执行。多步旅程里每次输入前，先确认输入框为空。
4. **计时差异先同时段交替，再分段，最后才归因。**
   - 先后跑的两组之间，同构建也可能漂移几百毫秒。
   - 按启动阶段拆开，看差异落在哪一段：落在不经过本次改动的阶段，说明与改动无关；落在改动所在阶段，才算作候选的成本。
   - 进程 CPU 只作背景，不能单独定因。
5. **声称“重叠／撞车”之前，先用时间线证明重叠确实发生。** 预取、准备这类后台工作通常有启动条件（输入框为空、空闲等），“立即操作”可能恰好把它挡住了。取证要分三种情形：缓存已备、被挡住、确有重叠。单样本只能给时间线，不能证明“阻塞为零”。
6. **字符换行改为按词换行时，要验证四件事：** 显示与测量共用同一规则；临界宽度的定向用例；撤回变异时用例会失败；跨软换行的复制得到原文。OpenTUI 的 word 模式已带中文标点和英文整词规则，超长串会退回逐字断开。
