# 准入链核查只看“有没有重试”，漏了重试的边界与实际预留

## 信号

同一条长链路（备份抓取 → 保留索引 → 物理读写 → 目标复制）在真实大数据上接连以背压失败。每修一处、构建一次，下一次真实运行又在同一条链的另一环失败。核查表里写着“这一环由 X 在区外重试”，失败却恰好出在这一环。

## 原因

核查只回答了“谁负责等待或重试”，没有核这两件事：

- 重试截止的起点。截止从整次驱动开始计时、有进展也不重置时，一个靠容量节奏推进的长任务必然超时，和“没有重试”的效果一样。
- 每次准入实际预留的预算。仲裁器要求余量不少于请求的原子预算，并在授予时先扣整份。整步预算被用在单次点查上（这里是预留 16,384 次 IO，实际只用约 3 次），实际消耗把余量压到半桶以下后，后面每一次准入都会被拒，重试也等不到。

此外，同一个错误可能在映射范围之外抛出，比如打开上下文时的索引追平；用户看到的仍是内部英文原文。

## 做法

- 逐环核准入时，每一环写清四件事：持有什么、谁负责等待或重试、**截止从何时起算、是否随进展重置**、**原子预算与实际用量各是多少**。不能只写“有重试”。
- 预算以真实的叶为准：读叶用读叶自己的上界（例如 durableProjectionReadBudget），整页、整步的预算只给整页、整步的操作。
- 错误提示的映射放在命令最外层，覆盖打开上下文、追平等前置环节，不只包住执行环节。
- 核查中每发现一处“可预见的同类义务”，就同批修完、同批验证，然后只构建一次；不要等真实重跑逐个暴露。
- 找不到错误出处时，先确认运行的是哪份代码。产物可能有自包含的 bundle 与外部导入的 dist 两套，诊断打点要打在实际被加载的那一份里，先用 stderr 确认打点生效，再下结论。

## 适用边界

适用于任何经设备容量仲裁、需要锁外重试的长任务：备份、追平、整理、迁移导出。一次性、短小、只准入一次的操作不必逐项列。
