# 全量测试提速：并发换不来吞吐（2026-10-23）

## 发生了什么

用户要求全量测试不能再是 70 分钟，并且要先“彻底、干净地”解决，再推进其他工作。

拆成快慢车道后，快车道（577 文件）从 872 秒降到 161 秒。慢车道（约 290 个重文件）按“先验合计 ÷ 并发数”估约 16 分钟，实测完全不是这样：
- 23 个重文件在 8 并发下墙钟 470～545 秒（预计 195 秒），单文件耗时是先验的 2～2.4 倍；
- 同时出现 24～32 个非确定失败，每轮失败的用例都不同。

此后为找原因先后做了五轮实验：
1. libuv 线程池扩容：只改善约 14%；
2. 计时器等待：实际触发的计时器可以忽略；
3. 换 forks 池：同样膨胀、同样失败；
4. 等待记账：膨胀主要在文件调用延迟（3～4 倍），其次是 CPU 被挤占；
5. 文件系统微基准：整机文件元数据吞吐基本不随并发扩展（C: 1 进程 177、8 进程 215 次循环/秒）。8 进程时 Defender 实时扫描约占 2.95 核，整机 CPU 100%。

## 根因

- 重测试的成本是“耐久层每个事务的文件新建/改名次数 × 实时扫描单价”。
- 扫描是整机共享的 CPU 成本。并发提高只会抬高单次延迟、挤占测试自身的 CPU，并触发产品的实时阈值（磁盘样本 250ms 新鲜度、日志存储期限），表现为非确定失败。
- 当时按样本估计慢车道约40～43分钟；随后里程碑实测1989秒（约33分钟），原估计不是下限。进一步提速的已识别方向是削减文件新建/改名次数；这同时是产品在 Windows 用户机器上的性能问题。

## 效率上的错误

0. **最大的浪费：没有及时做宏观取舍。** 每轮实验局部都有结论，但路线已经从“调整测试工具”扩大到“大半天的核心存储改造”，收益却只剩每次收尾省约 20 分钟。这时本应停下，重新对比它对一级主线的收益与成本。直到用户指出已投入约 4 小时才收口，而主线的三级任务本身都不值得花 4 小时。
1. 两次把理想下界当预计：16:27 和 17:26 都用“先验合计 ÷ worker 数”，后一次实耗 545 秒对预计 195 秒。先验来自不同运行方式（forks×6），不可比。
2. 逐个猜假设。线程池、计时器、池类型各试一轮，每轮 5～9 分钟。等待记账（活跃/空闲 + 文件调用延迟 + 实际触发计时器）一次对照就能指向文件 I/O；接着跑 1 分钟的微基准就定位到扫描成本。这两步本该最先做。
3. 内联脚本被 shell 转义弄坏至少 4 次，最后才装上 Bash 前置闸。
4. 停后台测试只用 TaskStop，残留的 node 子进程会污染下一轮。

## 可复用的做法

- 支线（尤其是工具与验证类）每过一个检查点，或者路线明显变重时，先算账：已投入多少，剩余还要投入多少，能换来多少对一级目标的收益。收益明显变小就收口，把真正需要的产品问题交给需要它的主线单元，不靠“每轮都有结论”推着走。
- 预计必须基于同运行方式下的可比实耗、实测并行度和最长文件拖尾；未知部分留区间。
- 原因不明时先做等待记账，把墙钟拆成活跃、文件调用等待、计时器等待，再针对最大项做单变量实验；每轮事先写可比基线、判定阈值和否定出口。
- 怀疑系统资源时，先用一分钟的微基准测它在 1 进程与 N 进程下的吞吐，确认是否随并发扩展，再决定加并发还是削减工作量。
- 依赖进程隔离的测试（chdir、RSS 等进程级读数）不能放进线程池；墙钟资源边界类测试要在没有并发负载时执行。
- 停后台测试后核对并清理残留子进程。

## 适用边界

- 吞吐数字只代表本机（Windows、Defender 实时保护开启、NVMe）。其他机器要重测微基准，不能照搬。
- 不通过调整 Defender 等安全设置来提速。
