# 阅读代次落地后的返回路径与异常分支

## 遇到的信号

- 新规则要求“视图声明的身份与正文身份相同才显示”。普通路径一次通过，审查却连续三轮退回，每轮都是另一条返回路径、失败分支或重复操作。
- 旧的异步请求在换了范围之后，仍替新范围读取、推进游标，最后只是把回复丢掉。
- 同一个重试按钮，第一次和第二次点击的语义不一样。
- 检查命令说“通过”，产物加载时却报语法错误。
- 冻结补丁里同一个文件出现两次，补丁无法反向应用。

## 经过

会话切换的修复把正文重建做成阅读代次：
- 每次重建先发完整基准；
- 视图声明期望的代次；
- 界面只在两者一致时显示正文。

普通切换、空会话、首次上翻在真实入口一次通过。审查随后按“共享显示存储被替换、用户回到哪一页”逐条走查，接连发现：
1. **旧请求读了新范围。** 取更早页的请求在两次等待之间换了范围，随后按“当前范围”排队读取，读的是新会话的源，推进的是新会话的游标。
2. **F2 返回后正文看不见。** 只读历史复用同一显示存储，返回断线会话时没有为它重建首页，返回页声明的代次永远等不到基准，正文一直隐藏。
3. **重建失败不可见。** 返回页重建读取失败时，错误只在只读历史页上提示；返回页什么也不显示，也不能离线重试。
4. **连点被当成在线恢复。** 本机重试按钮点击时就清掉了失败标记，第二次点击于是被解释成在线恢复；又因为占用了独占操作门，第二次还报了冲突。

另有两个工具问题：
- 插桩副本的转义写错。核对它的命令是 `node --check … | head && echo ok`，回报的是 head 的退出码，等于没核。
- 新增的测试文件已被暂存，`git diff HEAD` 本来就包含它，我又手工追加了一遍。

## 原因

- 新规则把“显示”变成了两侧的配对，我只核对了改动直接经过的路径：启动、切换、同 ID 重建。没有列出共享存储的全部写入方，也没有逐个追问“替换之后，用户回到的那一页由谁重建、失败时看到什么、重复或迟到的操作落在哪一代”。
- 异步工作绑定范围时只在入口取了一次，等待之后、排队之时又按“当前”重新取。
- 重试动作没有携带它所针对的失败身份；失败状态在动作开始时就清掉了。

## 以后怎么做

1. **改规则后先列写入方。** 引入“两侧身份一致才显示”这类规则时，交审前列出共享状态的全部写入方，逐个写清：
   - 替换后返回哪一页；
   - 那一页由谁重建；
   - 失败时如何可见、如何重试；
   - 重复、迟到、过期的操作落在哪里。

   每一项配一条定向用例和一次撤回变异。
2. **异步工作带着范围走。** 把最初绑定的范围一直传到队列，每个等待之后都核对；被取代就停手，不清新范围、不替新范围读取。“已作废”单独成为一种回复，不借用“有进展”或“原地踏步”。
3. **重试动作带身份。** 重试携带失败所属的身份（会话与代次）；在途期间不重复执行；失败状态在成功时才清除；不经过会与其他操作互斥的入口。
4. **检查命令不经管道判成败。** 需要看结果时用 `set -o pipefail` 或先保存退出码；改过的产物用实际导入或加载来核对，不只做语法检查。
5. **冻结补丁只生成一次。** 用 `git diff --binary HEAD -- <范围>` 生成（已暂存的新文件已经包含在内），生成后立即跑 `git apply --reverse --check`。
