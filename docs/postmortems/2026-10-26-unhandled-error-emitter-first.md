# 未处理 error 先确认发射对象

## 信号

- 测试只报 Unhandled Errors 或 Uncaught Exception，堆栈停在错误被创建的位置（例如 `AbortController.abort`），看不出是哪个对象发出的 error。
- 补了一处 error 监听，未处理错误照旧出现。

## 经过

停止一条经中继建立的 TLS 连接时出现两条未捕获异常。最初凭堆栈推断问题出在原始套接字的 abort 绑定上，先后试了两版修法：

1. 把 signal 收窄到套接字的打开阶段：引入回归，控制面停止从约 1 秒变成约 11 秒。等对端握手的中继入口原先靠这一绑定在停止时释放。
2. 给原始套接字挂吸收监听：两条错误照旧。

最后给 `EventEmitter.prototype.emit` 加了一个十来行的探针，记录“无监听时发出的 error”：对象构造名、监听数、有无父套接字、发射时的调用栈。这才看清两条都发在 TLSSocket 上：

- TLS 封装会把父套接字的错误转发到 TLSSocket；
- 握手失败路径在转发到达前已经摘掉了监听；
- 传输层只用 `once("error")`，接不住同一套接字的第二个错误。

## 教训

1. 未处理 error 的堆栈指向错误的创建处，不是发射处。先挂 emit 探针确认发射对象，再动修法。
2. 一个流可以发出不止一个 error：TLS 会转发父套接字的错误，`destroy(reason)` 自己还会再发一个。长期持有套接字的一方要持续监听 error，不要用 once。
3. Node 对带 signal 的流会经 end-of-stream 自带一个 error 监听，直到流结束。给这种原始套接字再挂吸收监听是多余代码，对应的变异会存活。
4. 改 signal 的生命周期之前，先查有没有调用方靠它释放正在等待的资源；停止耗时是这类回归最便宜的信号。

## 同轮另外两处浪费

- 把整读写进持锁事务的变异会重入锁而死锁，要等满用例超时才失败，抓住的是死锁而不是读数。变异应模拟退回旧写法的真实形态（在事务之前读）。
- 按“同类问题”扩查时越过了审查方已划定的范围，改完又撤回。扩查前先重读审查意见里的范围句；范围之外的同类问题只登记事实。
