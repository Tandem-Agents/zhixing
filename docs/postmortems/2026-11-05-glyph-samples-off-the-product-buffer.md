# 字形样张没在产品实际使用的屏幕缓冲区上做

## 现象

选中纹理的方案依据三组实拍样张定下规则：经典控制台在当前字体有 `░` 时使用它。依据是：Consolas 下的样张画对了，GDI 探测也说 Consolas 有 `░`。

实施后用实际产品验收，同样是“经典控制台、窗口临时设为 Consolas”的条件，选中行却是一串缺字方框。已写好、已构建的原生探测只好撤回，多了一轮原生与 CLI 构建，以及默认 Host 的停止与恢复。

## 原因

- 样张是在主屏幕缓冲区上直接打印的；产品界面用 `?1049h` 进入备用屏幕缓冲区后才绘制。
- 实测经典控制台的备用缓冲区不继承主缓冲区的运行时字体：主缓冲区是 Consolas，备用缓冲区仍是默认的新宋体。
- 启动时读到的“当前字体”因此不是界面实际用的字体；用 `CreateConsoleScreenBuffer` 新建的缓冲区反倒继承了 Consolas，也不能代表备用缓冲区。
- 样张证明的只是“这个字体能画出这个字”，并没有证明“产品绘制时用的就是这个字体”。

## 可复用的做法

- 字形、颜色、宽度的样张与探针，要在和产品相同的显示路径上做：同一种屏幕缓冲区（备用屏幕）、同样的 VT 模式、同样的宿主。最便宜的做法是样张脚本自己先进入备用屏幕再打印，并在停留期间读回字体与代码页。
- 依赖“启动前探测宿主能力”的设计，先核对探测对象与实际绘制对象是否同一个。核对不了，就按“无法确认”处理，走稳妥的后备。
- 方案定稿前的实拍，要覆盖“探测说可以用”的那一档，并用实际产品而不是样张去验收；只验证后备那一档，推翻不了主路径。
- 实拍文件名带上候选或轮次。这次最初出方框的那张实拍被同名重拍覆盖，首个反例只剩文字记录；瞬时异常（如入页闪动）还要把首个异常帧和稳定后的画面分开存。
