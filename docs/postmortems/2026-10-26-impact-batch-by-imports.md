# 影响面按引用关系选、8 路一次跑完

## 信号

- 单元收尾的“受影响全集”一跑就是二十分钟上下，一次跑出一串失败，分不清哪些是本轮回归、哪些是既有失败、哪些是负载超时，又要逐个单跑定性。
- 跑到一半已经看到需要改代码的失败，批次却停不下来。
- 同一类“昂贵确认拖慢单元”的问题，复盘与规则都写过，仍然复犯。

## 经过

一个单元（资产生命周期与场景删除）收尾时，按“是否 import 了改动文件”用 grep 求闭包，选出 112 个测试文件，没写并发，按 `test-source` 默认 8 路一次跑完：

- 墙钟约 1178 秒，单个重文件被拉长到数百秒；
- 14 个文件、23 个用例失败，里面混着本轮回归、既有失败和 8 路负载下的超时；
- 开跑后不久就出现了需要改代码的失败。后台任务的停止只结束了外层 shell，测试进程照常跑完。

事后按“本轮改了哪些既有合同”反查（派发准备拒绝场景不存在的会话、迁居重绑共用实例、写者入口在打开时追平并改了关闭顺序等 7 条），依赖这些合同的现有测试共 47 个文件：

- 14 个失败文件里有 9 个落在其中，另外 5 个在集合外，是否与本轮有关要按既有失败基线比对；
- 只看其中两条合同（各依赖 4 个文件），单跑就能命中 3 个失败；
- 112 个里有 46 个只是引用了改动文件，行为并未改变。

## 根因

1. **选择口径没有可执行的定义**。规则只写“按影响面选”“受影响包的全集”，作业方案模板写的是“直接消费者”，于是按 import 关系求召回。没有要求每组文件说明“改了什么行为、经哪个入口、哪个用例能检出”。
2. **证伪只盯新结构**。模板第 3 节为“新建或改动的结构”找反例，没要求列出“改了哪些既有合同”（新增拒绝或前置条件、去掉等待、改共享与所有权、改关闭顺序、改端口签名）。依赖这些合同的现有测试最有判别力、也便宜，却第一次在大批次里运行。
3. **并发结论没落到运行参数**。`test-source` 默认 8 路是为快车道调的；重 I/O 文件在本机的耐久吞吐几乎不随并发扩展，这有复盘可查，但规则没要求批量运行写明并发，运行时也没去查。
4. **批次启动即付全额**。失败详情要到结束才打印，后台停止又不能可靠终止子进程树，一次大批次没有中途止损的手段。
5. **结论超出证据**。事后把保守的 3～4 路说成“吞吐拐点”，把剩余结果说成“修完都要重跑”。

已有的复盘（[并发换不来吞吐](2026-10-23-test-speed-concurrency-floor.md)、[贵的确认跑在便宜的证伪之前](2026-10-25-confirm-before-falsify.md)）管的是“何时跑全集”和“并发能否提速”，没有管“确认批次里放什么、怎样分段、并发怎么定”，所以挡不住这次。

## 做法

1. **既有合同变更清单**：作业方案第 2 节逐条写本次改了哪些既有行为，grep 依赖它的现有测试与调用方，写到文件。这些测试放进第 4 节证伪单跑，不留到收尾确认。plan-guard 检查方案里有这一节，没有就不许改产品代码；没改既有合同的写“无”并给理由。
   - 检索在删改那一步做，不以方案初稿为准：方法按 `.名字(` 检索，含测试文件与经属性链的调用；登记、准备集合这类装配面按入口函数检索全部测试调用方。初稿凭记忆列出的依赖只是起点。5b 收尾第二段的 5 例失败就来自两处漏检：删除的方法仍有测试经属性链调用；固定登记加了投影，但 Host.ready 准备集合与经该入口打开写者的用例都不在初稿清单里。
   - 单元中途又改了一条合同时，补跑的口径是“最后一次运行早于这次变更”，不是“本单元还没跑过”。包7准入单元在层四把原任务执行身份改为派生，检索出了全部写入执行意向的测试，却只补跑了尚未跑过的；两个在层三跑过的文件（core store、owner-kernel session-state-adapter）夹具仍是旧身份，到收尾第一段才以 28 例失败暴露。
2. **收尾确认按行为选**：按“改动行为 → 实际装配入口 → 能检出回归的用例”逐组列文件并写理由。
   - 只引用了改动文件、行为不变的路径：复用未失效的证据，保留一个证明该边界不变的最小例。
   - 大范围引用闭包只在二级包收尾或里程碑跑一次。
   - 装配函数里新调用了某个端口的方法时，直接调用该装配函数的用例必须在批次里：用例常以 `as unknown as` 手写端口替身，类型检查发现不了替身缺方法。包6 返修曾给会话装配加了显现意图复核，按行为选批次漏了 conversation-surface，替身缺方法 4 例失败直到后一轮按 import 选才暴露。
3. **分段止损**：
   - 直接入口的高风险段在前；出现需要改代码的相关失败，就不再启动后续阶段。
   - 每段规模受控，因为批次启动后不能可靠中止。
   - 已完成且不受修改影响的结果照常复用。
4. **并发是写明的取舍**：
   - 批量运行显式写 `--workers`：重 I/O 批次先用保守的 3～4（不是测得的最优值），单跑复验用 1；
   - 目录级放行行写明“范围：”与同值的 `workers=N`；
   - script-guard 机械检查这两条（[监理机制](../engineering/supervision-mechanism.md#机械闸)）。
5. **只报证据支持的结论**：保守选择不说成测得的结论，复用与重跑按具体依赖判断。

## 适用边界

快车道的整车道运行仍可用 8 路，但同样要显式写出。单个或少数几个文件的定向运行不受这些约束。
