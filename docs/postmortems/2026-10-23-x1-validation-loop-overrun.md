# 既有失败清零超时：验证回路的结构性浪费

2026-10-23 终端迁移三级任务 X-1（既有失败清零）的效率复盘。数字为当天本机实测，机器为 i7-10710U 笔记本（6 核 12 线程）、Windows。借鉴重点是验证回路怎么组织；必要的诊断与修复本身不是浪费。

## 发生了什么

X-1 的目标是把全仓既有测试失败清零，为后续任务包提供干净基线，预期数小时。实际连续工作超过十小时仍未关闭。期间查出并修复了两项真实的存储层缺陷，也修好了大量过时的测试装配。但收尾全量又冒出 19 项新失败，全量验证本身一次要几十分钟，用户两次叫停追问效率。

这次复盘之前，[最终验证耗时失控](2026-08-06-final-validation-overrun.md)已经写过 executor 大文件慢、验证没有预算、无结果就换参数重跑。这些问题这次又出现了，因为开工前没有按信号查复盘。

## 实测时间账

| 项目 | 实测 | 说明 |
|---|---:|---|
| 统一构建（17 个包） | 111 秒 | 不是瓶颈 |
| core 测试，串行（所用别名配置写死 `maxWorkers: 1`） | 662 秒 | 各包自身脚本都是并行，串行是跑法问题 |
| core 测试，6 路并行 | 361 秒 | 只快 1.8 倍：耐久 I/O 受限，并发下单文件平均慢近 3 倍 |
| core 耗时分布 | 9% 的文件占 85% | 167 个文件各不足 1 秒，合计 19 秒 |
| executor 账本单文件 | 354 秒 | 225 个用例挤在一个文件，并行时只占一个 worker |
| 本机 fsync | 2～3 毫秒/次 | 磁盘本身不贵 |
| 日志单次提交 | 14.5 毫秒 | 一次提交 100 条也只要 14.3 毫秒；夹具逐条提交造数据，放大了两个数量级 |
| 对照：opencode、hermes-agent、gemini-cli 完整 CI | 6～15 分钟墙钟 | 拆片并行，快慢测试分离 |

## 失败轨迹与根因

1. **基线只建一半。** 开工只给 core/server/CLI 建了失败基线，其余 14 个包的失败到收尾全量才出现。收尾验证于是变成新一轮发现，“快结束”又退回到“还有一批没查”。
2. **测试运行器版本错配。** 仓库根目录没有 vitest，`npx vitest` 落到全局缓存的 5.0.5，仓库锁定的是 3.2.4。飞书 17 项假失败由此而来，此前用别名配置跑出的结果也都不是仓库运行器给出的。
3. **逐个串行、没有时间盒。** 每个失败都走“跑→读→注入诊断→跑→还原→改→跑”，一次几分钟，逐项排队；深挖时从不按时限停下复查方法。
4. **工具失误返工。**
   - 用 sed 改诊断脚本，把转义弄坏一次；
   - 反证脚本把调用写成未调用的函数，作废一轮；
   - 拿已含本轮改动的暂存区当“改动前”对照，结论作废。
5. **测试架构的结构性成本。**
   - 规模与耐久压测混在日常全量里；
   - 夹具走生产的逐条耐久写路径造数据；
   - 巨型单文件无法并行。

## 可复用的做法

- **领取先核实基线。** 先复用同候选且仍有效的基线，再对受影响范围补测；完整全仓基线限于确需新基线或里程碑，不为每个三级任务重复运行。动手前将已知失败分为装配过时、产品缺陷、环境或待定位并估时，避免收尾才开始建立基线。
- **对照用导出的 HEAD 树。** 判断“是否本轮引入”时，用 `git archive HEAD` 导出到证据目录，用目录联接复用 node_modules，测试配置改指向导出树。不用暂存区作对照。
- **用仓库锁定的运行器**（本仓库为 `node packages/core/node_modules/vitest/vitest.mjs`），全量按各包自身的并行度跑。
- **每项定时间盒**（一般 30 分钟），到点停下：写下已证事实，换方法或改定范围。
- **诊断注入统一走一种流程**：备份→注入→运行→还原→逐字节核对，脚本一律写成文件。
- **同类修正攒批**，改完一次重跑所有受影响文件。
- **测试体系分快慢车道**：规模与耐久压测只在收尾运行；夹具批量造数据；拆分巨型文件。本仓库由终端迁移 X-2 承接。

## 适用边界

- 不能因为求快而删减必要的耐久与崩溃验证，也不能把本应在当轮修的缺陷推给后续任务。快慢车道只改变运行时机，不改变覆盖范围。
- 只有 HEAD 树上运行的结果，才能作为“既有”的证据。
