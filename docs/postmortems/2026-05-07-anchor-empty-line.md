# 2026-05-07 · AI 回复起首空行：猜测替代输入观测

这是一次 CLI 诊断失败复盘，适用于实际输入不明、修复不断扩大处理范围的场景。过程、日志片段和成本来自当时记录，不代表当前故障；底层原因未经证实的部分不作为结论。

## 现象与失败轨迹

AI 回复偶发显示为“◆ 单独占一行，正文从下一行缩进开始”，预期锚与首段正文同行。Token 计数正常只能说明有输出活动，不能说明输出字符符合渲染预期。

| 轮次 | 当时动作 | 结果与教训 |
|---|---|---|
| 1 | 未观察原始输出，猜测零宽字符，将清理范围从空白扩至 ZWS、BOM、ZWJ 等 | 用户重启后仍复现；没有证据说明漏掉的字符是什么 |
| 2 | 扩大到 Unicode 格式控制类 `\p{Cf}` | 仍复现；范围更通用不等于原因已查清 |
| 3 | 提议以 `charWidth > 0` 寻找首个可见字符 | 用户质疑布局与影响范围；检查发现空格宽度为 1，宽度判断不能替代起首空白规范化，方案退回 |
| 4 | 用户建议先观察每次真实输出，才增加 raw chunk 与码点诊断 | 终于取得故障输入；本应由执行者主动识别证据缺口 |
| 5 | 根据 DEL 码点补全起首处理并增加对应回归测试 | 修复有了可复现输入，而非继续猜字符 |

当时日志记录的输入顺序：

```text
[+26606ms] text_delta len=1，码点 U+007F（DEL，属于 Cc）
[+26658ms] text_delta len=2，内容 "\n\n"
[+26720ms] text_delta len=2，内容 "你好"
```

当时起首清理仅覆盖空白和 Cf，未清掉 DEL，因而过早启动锚行，后续换行把正文推到下面。此处的缺陷是起首判定，不应把“不可见字符具有某个终端显示宽度”作为原因。

另一次记录在时间数字之间观察到 DEL 而非冒号；它说明收到的字符并不是冒号，但不足以确认 MiniMax 的 tokenizer/BPE 内部原因。CLI 不能据此凭空补写冒号。

## 历史实现演进与当前生产边界

历史修复使用过 `/^[\s\p{Cc}\p{Cf}]+/u`。仓库仍保留的旧 [TextStream](../../packages/cli/src/output/text-stream.ts) 后续改为：起首跳过空白、Cf 和 C0/C1 控制字符，**排除 ESC（U+001B）**，避免吞掉 ANSI 序列前缀后把其余部分显示成正文。这段处理仅在该类的起首阶段生效，不能推广成对全文任意删除控制字符。

视觉规范化与显示宽度计算职责不同：空格宽度虽为 1，起首仍可能需要清理；合法转义序列则不能按整个 Cc 类清除。但 `TextStream` 当前只有保留的导出与[单元测试](../../packages/cli/src/output/__tests__/text-stream.test.ts)，仓库内未发现生产代码实例化它；这些测试不能证明当前输出链已覆盖本案。

当前生产入口是 [OutputRenderer](../../packages/cli/src/output/output-renderer.ts) 创建并向 [MarkdownStream](../../packages/cli/src/output/markdown/markdown-stream.ts) 传递文本：建流前跳过 `trim()` 后为空的整块文本；随后按 render、strip 或 raw 模式处理，详见 [Markdown 流式渲染](../modules/cli/markdown-rendering.md)。这不是旧 `TextStream` 字符清理逻辑的接续调用，不能据旧修复宣称现行链路已处理 DEL，也不能仅据调用链变化断言当前仍有同一故障。

旧环境变量 `ZHIXING_RAW_DUMP` 不是现行入口。当前 CLI 通过 `--log` 配置 [LLM 流诊断](../../packages/cli/src/output/llm-chunk-dump.ts)，完整流日志按启用状态记录；错误现场记录另有独立行为，不能把“不启用完整流日志”理解成所有诊断均不落盘。本复盘不是要求开启日志或外发原始内容；取证应限定范围，避免泄露对话和凭证。

## 成本与可复用教训

旧记录统计用户复现 5 次以上、重启至少 5 次，其中至少 4 次被归为猜测验证成本。更有效的路径是先取得能区分原因的输入证据，再验证修复，但不能保证所有类似问题一次复现即可解决。

| 信号 | 应采取的动作及边界 |
|---|---|
| 同一故障反复试改，却没有新增证据 | 停止盲改，明确缺少哪项输入或执行事实；必要复现不因次数多就自动成为浪费 |
| 拟扩大 trim、parse 或 encode 范围 | 用真实失败输入和有效合同说明范围，检查合法输入是否会被误伤，补对应验证 |
| 看代码仍无法解释屏幕现象 | 对照真实输入、处理结果和显示结果，切换取证维度；不能据此断定一定是数据层 |
| 用户质疑“修修补补”或先提出关键观测方法 | 检查是否把本可自主完成的诊断转嫁给用户，解释已有证据与下一步能排除什么 |
| 想长期保留临时诊断工具 | 先看已有能力、复用价值、维护与隐私成本；不为一例自动建设整类诊断框架 |

复盘应如实记录失败路径、证据局限和用户成本，而非把偶然命中改写成准确定位。此处没有依据支持“视觉故障 70% 在数据层”等比例，也不能把固定追踪时长当作定位结论。
