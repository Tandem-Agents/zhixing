# 有界工作量返修：成本换位置的循环

日期：2026-10-23。任务：终端迁移包 2-1（G25，首轮提交不再建全量 runId 表）。

## 现象

首版交审后连续四轮复核不通过。后三轮的模式相同：每轮都把上一轮反例的指标压下去了，但随历史增长的工作量只是换了个位置：

| 轮次 | 被压下去的指标 | 增长转移到 |
|---|---|---|
| 第二轮 | 每次重开全量推导分片范围 | 补写回索引：每次重驱整份重写 index.json |
| 第三轮 | 整份重写索引 | 追加式定位记录文件 locator.jsonl |
| 第四轮复核 | — | locator.jsonl 每次冷重驱整份读取、物化（8/32 片：257/1050 字节） |

单轮返修只要 15 分钟左右，但四轮加上等待复核，总耗时超过原预算。每一轮都是“局部改好 → 完整验证 → 交审才发现换了位置”。

## 根因

交审前的工作量证明只沿用了上一轮反例的计数口径（`readShardLines` 调用次数），没有覆盖整条路径上的全部物理 I/O：新增文件的读取字节、解析物化、缺失探测和写入都没计。结构一换，新成本正好落在没计数的地方。

## 做法

1. 有界工作量合同交审前，先用一个通用计数器包住 `fs.promises` 的全部方法：按文件类别计读写字节与次数、ENOENT 探测和写入，另计 `JSON.parse` 次数。
2. 按阶段（打开 / 查询 / 新增）分开记，用两个规模（如 8 与 32）对照。凡是随规模变的项，逐项说明它是本轮新增、既有，还是一次性迁移。
3. 这一步放在构建和全量验证之前。计数显示有线性转移，就先改结构，不进入验证。
4. 一次性迁移（旧数据补键之类）和每次路径分开陈述：写清每会话最多几次、单次量级，以及为什么无法更低（例如判定所需信息的读取下限）。

第四轮按这个顺序做：结构定稿后先跑全 fs 计数，确认补键后冷重驱读 1 片、零写入且与规模无关，然后才冻结构建。同一阶段的自查还抓到两处同族缺陷：“已删 → 空”误判，以及空活跃片打开时推出偏小的 nextRunIndex。

## 复发：只数 API 调用次数（2026-10-27，日志历史积压）

日志存储的写步骤原先会对每份历史日志做两次 stat。修复后，每步 stat 从 8009 次降到固定的 17 次，名字列举从约 5 次降到 1 次，交审稿据此写了“剩余为常数”。监理对照源码指出，这一次列举仍然返回全部历史名字，随后的清点要逐个遍历；状态一有变化，又会把全部已登记条目序列化写回；名字总数超过 4096 时，日志存储直接拒绝工作。实测每步耗时也是 15 / 170 / 200ms（对应积压 0 / 1000 / 4000），并没有回到同一量级，与方案自己写的证伪标准相反，却被解释成了“常数”。

为什么这篇复盘没有拦住：方案文件是在上一个单元后面追加的，没有重写，也没有写模板里“已按 README 的信号查过”这一行，方案闸只检查整份文件里有没有出现过自审通过行。现在方案闸要求这一行落到具体条目的文件名（没有相关条目时写“无相关”并说明理由），只留模板占位或缺这一行都不放行。

补充做法：证明有界时，对每个关键调用列出四项：返回的数量和字节、之后的物化或遍历、写回的字节、缓存重建。只数调用次数不算证明。实测结果与方案里的证伪标准相反时，不能改用别的口径解释过去，直接按未达标处理。

## 适用边界

适用于凡是验收口径为“工作量与历史规模无关 / 有界”的改造：存储定位、索引、缓存、恢复路径。不适用于纯语义修复。计数器只用来证明结构，不必沉淀成平台。
