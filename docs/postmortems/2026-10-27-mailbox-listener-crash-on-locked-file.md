# 信箱监听在会话空闲时崩溃，回信滞留到下一条用户消息

## 问题信号

- 对方说已经回信，本会话却没收到通知；`bridge.mjs status` 里回信的 notification 时间晚于信件写入时间很多。
- `state/listener.json` 的 startedAt 恰好等于下一条用户消息的时间（监听是被那次 hook 重新拉起的）。

## 发生了什么

负责人会话 16:11 结束回合进入空闲。监听在 16:17:45 还做过一次巡检，之后自行消失。总控 16:35:46 写入回信时没有活着的监听，直到 16:45:28 用户发消息触发 UserPromptSubmit hook 才重新拉起监听并投递。

## 根因（已复现）

监听每 3 秒用“写临时文件再重命名”覆盖 `state/health.json`。Windows 上目标文件被其他进程短暂独占时重命名报 EPERM；扫描的错误处理又用同样方式写 health.json，再次失败就从 catch 里抛出，成为未处理的 Promise 拒绝，Node 24 直接结束进程。会话空闲时没有生命周期 hook，监听不会被重新拉起。

复现：在真实监听运行时独占打开 health.json 8 秒，监听进程退出。修复后同样操作，监听存活并记录两次 `health-write-failed EPERM`。16:17～16:35 之间是谁占用了文件无法追溯（当时没有日志）；修复覆盖任何占用者。

## 做法

1. 长驻辅助进程里，“报告状态”的写入失败只记录，不能决定进程生死；每轮工作的异常都要兜住，并有进程级兜底。
2. Windows 上的重命名覆盖对 EPERM/EBUSY/EACCES 做有界重试。
3. 外部状态（宿主注册文件）的瞬时缺失或读不出只跳过本轮；只有宿主进程退出或身份不符才永久关闭。
4. 长驻进程必须留下生命周期日志（启动、关闭原因、被兜住的异常），否则事后无法区分“被判关闭”与“崩溃”。本工具的日志在 `collab/mailbox/tool/state/listener-events.log`。
5. 先用最便宜的刺激在真实进程上复现，再改；改完用同一刺激复验，并把刺激写成回归用例（`bridge.test.mjs` 里“状态文件被独占、会话注册短暂缺失都不让监听退出”）。
