# 调研技能（草稿）

## 一、需求

建立一个适用于不同领域、不同形态研究对象的通用调研技能。它应帮助智能体在不预设结论的前提下，先明确调研要回答的问题、需要获得的信息与认识及成果用途，再据此确定合适的调研方法，形成准确、深入、有依据且符合目标的成果。

## 二、方案（待定）

### 核心规则

根据用途与对象特点，明确需要知道什么、能解释或判断什么，不预设答案。据此围绕关键内容、相互关系和成立条件选择理解角度与层次，形成研究问题。准确理解对象及其背景，以可核查依据形成和检验认识；区分事实、来源观点与自身推断，结论的确定程度和适用范围不超出依据。

### 工作流程

先确认研究对象与用途，按上述规则写明认识目标、问题框架和取证路径，再从认识目标反查问题设计是否覆盖所需的信息与联系；不足就修订框架。调查中记录认识及依据，随新发现修正框架和取证路径，保持与原用途一致。交付前仍依这些规则回到用途与对象，从其他相关角度检查问题框架与认识中的遗漏或偏差，核实关键判断是否得到依据支持，以及反例或其他解释是否要求修正结论。发现影响目标的缺口，就调整框架、补查或修正并重新审查，达标后交付；补查后仍因关键依据或授权限制无法达标时，说明未完成部分、原因和补齐条件。

## 三、Anthropic 原文调研结论

研究对象：[Building agents: When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)，Diane Sarkis，2026-10-22，Claude Resources；核对版本：2026-11-08。

### 原文主张

作者关注大型组织构建统一智能体时出现的五类问题：交接丢信息、子智能体重复膨胀、提示规则冲突、各自的局部评测成为决策依据，以及延迟增加。组织分工直接变成运行边界，是其重点批评的做法。[原文](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

作者判断，较新模型已能在同一循环中规划、执行并据结果调整，因而建议评估哪些子智能体可以合回主循环：专业流程通过技能按需加载，工具通过搜索按需提供，权限、审批及预算仍由程序执行。各领域团队维护技能、工具和评测，由中央团队负责系统提示词与整体质量。这些建议依赖较新Claude模型及按需加载、工具检索等能力；模型或平台能力不同时，需要重新验证。[原文](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

### 关键在于信息怎样共享与隔离

紧密依赖同一批信息的步骤，反复交给不同代理容易损失细节；能独立完成、只需返回少量结果的工作，则能通过独立上下文减少干扰。并行探索、独立验证、实际存在的工具选择困难或指令冲突，都是保留子智能体的理由。决定边界的是任务的信息依赖和实测效果，职责名称本身不足以决定拆分。[原文引用的多智能体指南](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)

按需加载也不保证运行中没有上下文负担：Claude Code曾让主智能体自行查阅文档，仍载入过多材料，随后采用独立查询代理。**我们的判断是，共享与隔离需要配合任务选择，不能由“是否使用技能”直接推出代理数量。**[工具设计案例](https://claude.dev/blog/seeing-like-an-agent/)

### 证据支持到哪里

这些效果观察来自Anthropic在Claude上的企业实践，包括一个客户约两倍提速的报告。我们查阅的原文及其[企业比较出处](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)没有给出足以复核这些匿名部署的完整比较方法与数据；这些经验支持开展针对性验证，不能据此确定普遍收益或把全部改善归因于代理数量。

配套工具包确有公开示例记录：一次折叠后，原本通过的订单查询在两次运行中有一次遗漏交货日期。记录还说明，当时仅有12个任务、每种方案重复两次，并存在链路未覆盖等限制。这说明迁移可能改变相邻任务的行为，也说明有限评测未发现退化，不等于全面等效。[示例说明](https://github.com/anthropics/single-agent-loop-kit/blob/release/examples/support-desk/example-run/README.md)、[基线记录](https://github.com/anthropics/single-agent-loop-kit/blob/release/examples/support-desk/example-run/results/baseline/results.jsonl)、[折叠后记录](https://github.com/anthropics/single-agent-loop-kit/blob/release/examples/support-desk/example-run/results/v1/results.jsonl)

### 双方共同判断

**认可文章对不必要拆分的诊断，以及逐项验证后决定去留的方法。**先建立能检查完整任务结果的评测，再逐项改变；检查哪些任务退化、必要步骤与硬限制是否仍成立，用覆盖相关路径的重复验证裁决。10个样例是起步建议，不能作为充分验证的固定标准。[配套迁移方法](https://github.com/anthropics/single-agent-loop-kit/blob/release/skill/steps/03-fold.md)

本文的价值在于提出了可解释、可检验的架构取舍：**减少没有收益的独立循环，保留能带来实际收益的隔离与并行，并对完整结果负责。**它没有证明多智能体协作普遍不好，也没有证明单主循环普遍最优。

### 博主的延伸观点

博主把架构问题进一步指向组织设计：人类难以直接共享完整上下文，因此依赖分工与交接；AI能够在共同上下文中贯通多个步骤，照搬岗位和部门边界，反而可能重新制造信息隔阂。他借“逆康威定律”强调，AI转型的关键在于围绕目标系统重塑工作流与协作方式，让业务团队贡献可复用的专业能力。曾用于弥补模型限制的固定流程，也应随能力变化重新审视，避免成为新的束缚。（据《忘掉多智能体：别把部门墙带进 AI》字幕提炼。）

## 四、核心提炼

**当同一项工作的各部分高度依赖同一批信息时，多主体分工会增加信息交接、理解同步和协调成本，由同一主体连贯完成反而可能更高效。**

## 五、职能体的专业化与独立性

**专业能力可以由同一主体组合运用；需要独立承担的复核与监督，不能仅靠切换视角替代。**

职能体的价值，在于围绕职责形成专业的思考方式、工作习惯和标准，并依据反馈持续改进履职能力。文档化、可迁移的角色内容，使这种专精不必绑定独立的执行实例。对于各部分高度依赖同一批信息的完整工作，由同一主体连贯执行、按需切换专业视角，保留上下文；方法与经验仍按职责积累。

- **职责分离（Separation of Duties，SoD）**：将不相容的职责或控制权交给不同主体，防止同一方独自控制本应相互约束的环节。[NIST 定义](https://csrc.nist.gov/glossary/term/separation_of_duty)
- **独立复核**：由实施者之外自主核验并形成判断，避免自我评价替代独立保证；需要持续发生的监督，还须能独立触发。[NASA 独立验证与确认说明](https://www.nasa.gov/ivv-overview/)

模型能力增强可以改善自查，但不会把自查变成独立复核。是否分开承担，取决于具体职责的独立性要求，而非专业名称。不同主体仍可共享事实、服务同一目标；分离的价值在于独立判断与相互约束。

## 六、DeepSeek Super-agent 调研结论

**Super-agent 要把多会话管理从用户手中交给系统：用户面对一个持续的协作者，后台能够并行推进多项工作，并保持任务联系与交互连续。**

研究对象是 DeepSeek Harness 团队的《Super-agent 设计探索：迈向更自主的 Agent 系统》及配套研究原型。文章讨论架构方向；官方组织发布的 `dsh-superagent-prototype` 是面向单个 GitHub 仓库、可接入飞书的主动编码原型，不是正式产品，也不等同于团队内部版本或文章的全部设计。[文章中文转载](https://blog2.eimoon.com/p/deepseek-super-agent-design/)、[官方原型说明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/README.md)

### 设计目标与工作方式

作者要同时保留跨任务联系和并发执行能力：Router 承接交互、关联和分派任务，避免被具体执行占住；Worker 在独立上下文中负责单项任务的组织与执行，内部仍可使用子智能体或团队。两层是职责划分，不等于固定两个会话。同层 Worker 通常不直接通信，所需联系可通过共享事件及 Router 传递。

各部分配合如下：

| 机制 | 作用 |
|---|---|
| 事件过滤与任务分派 | 群聊、PR、CI 等事件先经过程序准入，再由模型判断需要开展的工作；原型以带授权范围的工单承接执行。 |
| 订阅直通 | 已有任务的相关后续事件直接送达执行者，减少重复路由。任务与对话串可多对多关联；收到上下文不代表获得新的工作授权。 |
| 按需组织上下文 | 近期必要信息进入窗口，完整材料保留续读入口；用关联对象的引用逐步找回上下文，而非把所有任务历史堆进一个窗口。 |
| 主动准备 | 按允许的策略在后台尝试复现问题或准备方案，有价值时才交付，减少用户等待与无效打扰。 |
| 异步执行与适量反馈 | 长操作在后台推进，新输入在后续推理步骤处理；普通进度留在内部，需要人行动或结果可用时才对外沟通。 |
| 持久状态与外部巡查 | 保存任务与消息状态以支持恢复；文章进一步提出分离计算、状态和执行设备，并用外部 Watchdog 监测故障与任务进展。 |

原型通过来源事件、任务、订阅、授权和持久化队列承接这些机制。路由说明不得擅自添加需求或实施方案，执行者回到原始请求和既定规则理解工作。主动工作默认只记录拟采取的行动，启用相应策略后才执行。[领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/001-domain.md)、[授权规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/002-authorization.md)、[提示与交接](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/004-prompts.md)

### 实验说明了什么

文章报告的调度实验，每种配置运行 5 次，每次约 300 条消息、约 20 项工作请求；编码工作由仅消耗时间的工具代替，消息间隔与工作时长按 1/4 缩放，模型调用使用真实耗时。表中时间是**单项工作从请求到结果消息的耗时**，不代表真实编码质量，也不是整批任务的完工时间。

| 配置 | P50／P95（分钟） | 单次实验全部会话的读缓存 token |
|---|---|---|
| Super-agent | 12.4／15.7 | 2323 万 |
| Super-agent，去掉直通 | 12.6／15.5 | 3177 万 |
| 单会话＋子智能体工具，中性提示 | 20.4／29.5 | 605 万 |
| 单会话＋子智能体工具，优先委派提示 | 13.8／29.0 | 1082 万 |

作者记录，中性提示组 5 次均未委派，工作留在主会话中并被新消息反复打断；优先委派组 4 次进行了委派，另一次自行执行形成长尾。因此，这组差异也包含模型是否选择委派的影响，不能视为所有单会话方案的能力上限。

在这一负载下，双层方案的尾部完成时间较短，代价是更多缓存读取；直通机制减少了路由负担与缓存读取量，但没有显示出完成时间的改善。P50、P95 是分位数，不能说成“平均”“最慢”；缓存读取量也不能直接换算成总 token 或账单。批处理实验另显示，高到达率下合并事件能降低每个决定分摊的推理时间，但不能据此推断无限扩展能力。[原文实验及图表副本](https://telegra.ph/Super-agent-%E8%AE%BE%E8%AE%A1%E6%8E%A2%E7%B4%A2%E8%BF%88%E5%90%91%E6%9B%B4%E8%87%AA%E4%B8%BB%E7%9A%84-Agent-%E7%B3%BB%E7%BB%9F-10-31-2)

### 公开实现与结论边界

公开原型的主会话仍有 Bash、文件读取及后台作业管理工具，并设置等待限制；“不介入具体工作”也依赖提示规则，不能概括成“完全不给工具”。Worker 可以发起接单确认，普通答案、问题与结果仍经报告交给主会话；目录和会话分离也不等于操作系统级安全隔离。[会话工具限制](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/sessions.ts)、[执行者工具](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/tools/executor.ts)、[回复路径](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/replies.md)

原型已有状态持久化、投递重试与恢复机制，也给出了外部定时检查的部署安排；这不能证明文章描述的云端分离与完整智能巡查均已交付。[执行与恢复](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/003-execution.md)、[部署说明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/006-deployment.md)

更大规模或更强耦合的任务如何组织、Worker 之间何时需要直接通信、长期记忆、用户中途干预以及跨权限边界协作和安全，文章均保留为开放问题。[原文开放问题](https://blog2.eimoon.com/p/deepseek-super-agent-design/)

**现有证据支持的是一套连续交互、并发执行与状态管理相配合的设计，以及特定合成负载下的调度取舍；尚不足以证明它在真实业务质量、总成本或所有规模下普遍优于替代方案。**

资料核对日期：2026-11-09；原型提交：`8c32a9dc`。原始微信、知乎页面本轮未能直接读取，文章经注明出处的中文全文转载及图表核读，公开实现以官方仓库核验；未部署原型、重跑模型实验，也未找到足以复算全部统计的原始运行记录。

### 博主的延伸观点

博主把 Anthropic 与 DeepSeek 的讨论归为同一结论：多智能体的关键不在于给模型套用岗位头衔，而在于把面向人的接待协调与按任务独立执行分开。他认为，靠提示词嘱咐模型自觉分工终究不可靠，分工规则应写进系统结构，“不靠自觉，靠制度”。在他看来，这样用户始终只面对一个助手，不必自己在多个会话间切换、记住各自进度。（据《DeepSeek 的多智能体调度思路》字幕提炼。）

## 七、架构选择与协作边界

**我们选择采用 DeepSeek 的顶层分工，目前未找到值得替代它的整体更优方案。** 用户保持一个默认对话，入口负责接待与调度，每项完整工作由自己的主责执行者连续推进、保留上下文和状态；专业能力按需使用，不默认按岗位多人接力，必要的独立复核另行承担。持续交互与长时间执行并存时，分开两者的节奏与上下文可减少彼此挤占，这一职责边界因而有长期价值；不必固定模型或会话数量。

**此前多角色协作的总控组织多人完成同一项工作，Router 主要接待、协调和分派多项完整工作。** 前者因频繁处理内部交接而陷入局部，执行者也被转来的反馈反复拉离当前工作。普通进度不唤醒 Router、反馈按任务归属送达，减少了外层中转与跨任务打断；但共享事件和后续输入仍会进入执行上下文，任务内的多人协作并未因此解决，入口也有负载上限。内部重建高频接力、入口兼任深度负责人时，仍可能重现失焦与切换损失。

完整工作保持主责连续，反馈回到所属任务；是否改变当前行动，以反馈对目标的影响为依据。例如，无关反馈不打断当前工作，推翻当前依据的反馈及时处理受影响部分。监督与验收对照原目标和实际成果判断，不以巡查被触发或执行者自报完成代替达标。
