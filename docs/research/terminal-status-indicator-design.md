# 终端状态指示符：能力边界与设计方法

本文是可复用的设计参考，帮助任何设计者理解**现有运行状态条的动态指示符，以及消息、工具等位置的静态菱形标记**，掌握其使用需求、终端限制、设计思路与验证方法。子 Agent 标识、其他独立符号及其状态体系不在范围内。

正文区分生产现状与通用设计要求，不指定任何候选的名称、帧序列、节奏或动态占位。具体方案如需记录，单独放在文末分隔线之后，标明版本、反馈与验证状态；候选偏好不构成正文规则，也不代表已经定稿或落地。生产实现变化时应核实并更新现状，不把旧实现当作永久限制。

项目既有约束见 [CLI 视觉设计语言](../modules/cli/visual-language.md)，渲染机制见 [CLI 屏幕渲染与能力边界](../modules/cli/screen-rendering.md)。

## 1. 现状与真实需求

### 1.1 显示位置与代码落点

以下只列正常交互式 REPL 中与这两项设计直接相关的生产调用点。位置示意省略其他界面元素，不代表最终字形：

```text
正文／历史滚动区
  ◆ 助手正文……                  ← 正文身份标记，输出过程中就存在
  ⟡ 已使用若干工具……            ← 工具批次摘要
    工具明细……
  ◆ 失败工具……                  ← 红色标记，下一行说明原因

底部固定区
  [动态指示符] 当前阶段……        ← 运行中
  ◆ 用时……                      ← 正常结束后替换上面一行
  [输入框]
```

| 使用位置 | 当前实际表现与生命周期 | 代码入口 |
|---|---|---|
| 输入框上方的运行状态条 | 唯一的 REPL 循环动画：青绿色 `◇ → □ → ◈ → ▤ → ◆ → ▦ → ◈ → ▨ → ◇ → ▩`，300ms／帧、3 秒一轮。首次运行前不显示动画；普通阶段一行，子任务阶段的动画在两行状态区的第二行。研究对象是这个共用动画，不包含子 Agent 标识 | [verbs.ts](../../packages/cli/src/status-bar/verbs.ts)、[status-bar.ts](../../packages/cli/src/status-bar/status-bar.ts) |
| 同一状态条的正常结束标记 | 动画停止，换成弱化色 `◆ 用时…`。结果留在底部，后续运行时替换，不是新增一条助手消息，也不会自动作为消息写入历史 | [status-bar.ts](../../packages/cli/src/status-bar/status-bar.ts)：`renderDonePhase`、`dispose` |
| 助手正文前 | 白色 `◆` 在流式输出时就出现，结束后不变色。标在一个连续 Markdown 输出段的首个正文段落前；工具等边界之后可另起一段。不是每行一个，也不保证一轮只有一个；标题、列表、代码块等有各自排版 | [output-renderer.ts](../../packages/cli/src/output/output-renderer.ts)、[markdown-stream.ts](../../packages/cli/src/output/markdown/markdown-stream.ts) |
| 默认工具的成功结果 | 弱化色 `⟡` 标记一个成功工具批次；明细只展示最近若干条，不逐工具添加绿色 `◆`。每次结果到达可更新批次文本，字形本身不循环。工具执行中由底部状态条提示 | [tool-batch-coordinator.ts](../../packages/cli/src/output/tool-batch-coordinator.ts) |
| 工具失败／拒绝结果 | 红色 `◆` 和原因独立展示。用户拒绝也走这条展示路径，但文字明确写“已拒绝” | [tool-batch-coordinator.ts](../../packages/cli/src/output/tool-batch-coordinator.ts)、[tool-card-format.ts](../../packages/cli/src/tool-card-format.ts) |
| 最近记录中的助手消息 | 弱化色 `◆` 表示助手；没有回复时直接写“此轮未生成回复”，不显示这个标记 | [history-tail.ts](../../packages/cli/src/history-tail.ts) |

需要避免三个误读：

- **静态不等于已完成。** 正文 `◆` 是阅读锚点，消息尚在输出时也存在；工具批次中的成功事实也不表示整个请求已经完成。
- **当前并非所有工具都用不同颜色的实心菱形。** [speaker-state.ts](../../packages/cli/src/output/speaker-state.ts)虽然还定义了运行工具 `◇` 和绿色成功 `◆`，这两条目前没有生产调用；成功批次实际使用 `⟡`，失败使用红色 `◆`。部分独立工具结果采用其他符号，那些不属于本文范围。
- **按使用位置划范围，不按相同字符全局替换。** 其他来源、系统通知等位置即使出现相似字形，也不自动成为重设计对象。

### 1.2 哪些地方需要状态

不建立一套到处套用的“运行／成功／失败／取消／等待”图标清单。每个位置只表达它实际拥有的事实：

| 对象 | 必须保留的实际语义 | 设计要求 |
|---|---|---|
| 当前运行活动 | 思考、回复、工具调用、子任务、整理上下文、重试、流式静默后的自动取消倒计时 | 一套活动动画，具体阶段由文字说明；不为七个阶段分别设计动画。倒计时仍是进行阶段，不是“已取消” |
| 正常结束的菱形 | 本轮运行已结束 | 停止动画，弱化标记并保留耗时文字；不暗示用户目标一定已达成 |
| 助手正文／最近记录中的菱形 | 助手内容的阅读锚点 | 不需要给每段正文添加成功／失败状态；流式输出时同样成立 |
| 工具结果中的菱形 | 成功批次、失败原因、用户拒绝 | 常态弱化，异常可见，拒绝有明确文字。保持现有批次与独立失败的阅读层级；不为凑齐清单增加“等待／取消”等静态状态 |

中断、错误、达到轮次上限时，动画同样必须停止并交回现有结果展示；这些独立结果符号不重新设计。确认面板等既有交互继续沿用，不因指示符的视觉优化新增状态或改写流程。

### 1.3 实际可用的设计空间

| 使用面 | 当前占位 | 通用设计要求 |
|---|---|---|
| 底部活动动画 | 标记 1 列 × 1 行；左缩进 2 列、标记后空格 1 列，状态文字从第 5 列开始 | 可评估单行多列方案，但须说明横向代价并验证窄屏；不增加状态区行数。选定占位后，各帧宽度和文字起点保持稳定 |
| 正文／工具结果前的静态标记 | 通常为 1 列字形＋1 列间隔，前置缩进 2 列；正文续行等排版依赖这个宽度 | 保持 **单列、小体量、中性形状**；不因动态占位增大而同步放大，不扩大整片历史的缩进 |
| 正常结束的菱形 | 状态条原位置的一行静态结果 | 使用紧凑标记和文字；动静占位不同时可用留白保持文字起点，无需让静态图案填满动态区域 |

屏幕层接收整行状态文本，没有把动画锁死在单列容器中；可用宽度取决于状态文字与相邻内容，不能预设任意列数都放得下。状态行同时容纳耗时、token、任务和上下文摘要；窄屏必须先保证阶段／结果文字可读，再取舍附加信息。输入框下方的信息区承担独立的场景提示，不是动画的预留位置。

布局依据：[screen-controller.ts](../../packages/cli/src/screen/screen-controller.ts) 的 `buildChromeBytes`、[typeahead-input.ts](../../packages/cli/src/typeahead-input.ts) 的 `computeRender`、[text-stream.ts](../../packages/cli/src/output/text-stream.ts) 的悬挂缩进。布局机制允许扩展，不代表某个候选已经通过字体、窄屏和输入联动验收。

### 1.4 设计对象与共同要求

每个方案都应覆盖以下内容：

1. **当前活动指示符。** 设计可感知的动作、实际字符帧、节奏、占位、文字关系与停止行为。一处动画服务整个当前运行，不把历史和工具列表变成多个动画源。动画表示仍处于进行状态，不表示完成比例，也不能证明后台健康。
2. **紧凑静态菱形标记的优化。** 只覆盖 §1.1 列出的消息、工具与正常结束位置。以稳定、中性、单列的形态配合语义颜色和文字，不为每一种结果创造不同形状；不扩展为类别图标、子 Agent 图标或其他符号的设计。
3. **位置—含义—状态对应表。** 按 §1.1–1.2 逐项映射；没有该状态的地方不添加状态，有结果区别的地方不能丢失事实。无色时仍能凭内容、标签和层级读懂，不能让用户只靠记颜色猜。

动态与静态通过色彩角色、视觉重量、间距和整体气质形成一套系统，**不要求同形，也不要求共用轮廓**。动态可以富有运动特征；静态首先是密集文本中的阅读标记，须安静、紧凑、不抢正文。

静态标记不能以对勾、叉号等明显的结果形状作为所有状态的统一母形，避免把身份或内容暗示成成功／失败。现有单列 `◆` 可作体量与中性的对照；最终字形应依据阅读用途判断，不从动态帧机械推导。

活动指示与可量化进度的区别也见 [Carbon Loading](https://carbondesignsystem.com/patterns/loading-pattern/)。没有真实进度数据时，不借动画制造“快完成了”的暗示。

## 2. 先分清技术能力、项目现状与设计选择

### 2.1 终端实际提供什么

常规文字终端可以理解为：**字符格＋字符字形＋颜色／样式＋光标定位与重写**。应用安排每次输出什么、何时输出；终端与字体决定最终如何画出来。PowerShell、cmd、Bash 是 shell，不能据此判断实际终端宿主的显示能力。[Microsoft VT 控制序列](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)提供了这些基础操作。

| 能力或限制 | 对设计的实际影响 |
|---|---|
| 固定字符格 | 可以在一个或多个格中替换内容；格通常不是正方形，不能把字符矩阵直接当等比例像素图 |
| 字形由字体／宿主绘制 | 应用可选字符，但常规文本输出不能任意修改其轮廓、转到任意角度或做连续形变 |
| 字符宽度并非字符串长度 | Unicode 码点、字素簇与终端列宽不是一回事；每帧必须具有一致的占位，不能推动旁边文字 |
| 字体回退与缺字 | 同样占一列的字符，实际大小、笔画、基线和视觉重心仍可能不同；罕见字符还可能显示成缺字框 |
| 前景／背景色与文本样式 | 可用色数取决于环境；ANSI dim 不是连续透明度，粗体也不能当作稳定的轮廓变化手段 |
| 逐帧重写 | 可以设计帧序列、各帧停留时间与局部更新；不是只能四帧或每秒更新四次，也不保证每次写入都成为独立可见帧 |
| 普通 ANSI 不提供通用图形变换 | 网页的任意角度旋转、缩放、模糊、透明图层叠加，不会自动成为终端能力；若靠字符近似，需要重新设计帧 |
| 图片协议与特殊字体 | 某些终端确实能显示图像；依赖宿主、协议与配置，不能作为普通字符方案已可实现的证据 |

Unicode 的 East Asian Width 属性本身也不是现代终端列宽的完整答案；实际宽度需要结合实现处理，见 [UAX #11](https://unicode.org/reports/tr11/)。Windows Terminal 的字体、字号、字重均可由用户配置，见[外观设置](https://learn.microsoft.com/en-us/windows/terminal/customize-settings/profile-appearance)。因此“在网页和宽度函数里正常”不足以证明实机一致。

### 2.2 可用的表达空间不止一个几何字符

| 载体 | 可设计的内容 | 代价与边界 |
|---|---|---|
| 单格字形 | 轮廓、内部笔画、开口、疏密、方向与时序 | 最紧凑；只能从可显示字形中构造连续关系，不能任意补出所需角度 |
| 单行多格组合 | 笔画传递、局部生成／消退、相位错开、留白流动、前后呼应 | 能建立空间关系；占用更多横向位置，必须保持总宽不变并补偿字符格比例 |
| 块元素或盲文点阵 | 在有限网格中组合局部形态，不必局限于成套 spinner 字符 | 是粗粒度构形，不是任意像素画布；盲文每字符只有 2×4 个点位，且点间有空隙 |
| 多行字符画 | 更明确的轮廓、路径和形变 | 会增加状态区高度和视觉重量，不能为一个小指示符默认升级成大幅动画 |
| 颜色与明暗 | 强化层次、方向与动静差别 | 只能辅助；真彩色渐变在低色数环境可能变成跳变，失色后不能丢失状态信息 |

盲文字符的点位组合见 [Unicode Braille Patterns](https://www.unicode.org/charts/PDF/U2800.pdf)。它提供的是一套组合材料，不意味着任何小尺寸轮廓都能清晰表达。

必须准确表述做不到的条件：**所选字形若缺少运动所需的中间姿态，单靠调整帧顺序无法补出它**，但不能据此断言终端不可能显示该效果，更不能当作对所有字体和字符的穷尽结论。例如 [Windows Terminal 的 Sixel 支持](https://devblogs.microsoft.com/commandline/windows-terminal-preview-1-22-release/)和 [kitty 图形协议](https://sw.kovidgoyal.net/kitty/graphics-protocol/)属于另一类能力。本文的设计基线是字符与 ANSI，不以安装专用字体或引入图片协议获得效果。

“单格”可以是紧凑布局的取舍，但不应在构思前被误当成终端天花板。若最佳方向需要多格，应明确展示占位代价再决定，不能暗中扩大控件。

### 2.3 落地所用的现有机制

- 具体位置、调用关系和当前字形以 §1 为准。[status-bar.ts](../../packages/cli/src/status-bar/status-bar.ts)以定时重画及事件更新驱动状态条；现有帧数与 300ms 间隔是实现选择，不是平台限制。
- 固定区由屏幕控制层管理，运行结束或屏幕暂停时停止动画定时更新。设计应使用这条显示路径，不另外争抢 stdout 或移动输入光标，保持既有交互行为。
- 字形定义不是全部消费路径；不能只替换 spinner 数组或 `speaker-state.ts` 常量就宣称整套设计完成，也不能把拟定的统一静态标记误写成现状。
- [line-width.ts](../../packages/cli/src/tui/line-width.ts)提供项目的列宽估算；[style.ts](../../packages/cli/src/tui/style.ts)提供语义颜色。它们是实现入口，不是字体兼容性或视觉质量的证明。

## 3. 为什么有动画，却没有好的设计

视觉质量不取决于几何形状是否复杂。设计需要从**视觉目标推导到可见动作**；选字符、换顺序和调速度只是其中的手段。

| 容易陷入的做法 | 为什么不足 | 应改为 |
|---|---|---|
| 先选一组“好看的字符” | 每个单独成立，连续播放却可能像四个不同对象 | 先确定一个可感知动作，再找能保持对象连续性的材料 |
| 认为方形与菱形交替必然像旋转 | 两帧之间缺乏明确的方向线索；面积、空实也可能一起突变 | 检查轮廓对应与方向连续性；无法成立就换动作，不靠说明文字强行命名 |
| 用提高帧率补救缺失形态 | 更快重复不相关轮廓不会创造中间形态 | 先修空间连续性，再调时间；复制帧只能改变停留，不能补出轮廓 |
| 只加明暗呼吸 | 能表达持续活动，却未必带来形态辨识度或品牌特征 | 判断它是否服务明确的设计目标，不能把“能实现”当成“最好” |
| 用“旋转、呼吸、量子”等名字包装 | 概念成立不等于用户看到了那个动作 | 隐去名称与解释，按真实播放结果判断 |
| 同时交付许多细微变体 | 把设计师的筛选工作转嫁给用户，且难以看清改进 | 内部探索后只拿最有把握的一版与现状比较 |

逻辑上的“每步只变一个属性”不保证光学面积、重心和笔画重量稳定。应观察真实播放效果，区分连续运动与无关形态的切换；代码注释和设计命名不能代替视觉验证。

## 4. 应当怎样构思，而不被字符表限制

### 4.1 从动作与气质出发

先写一句没有字符名称的创作目标：希望用户看到怎样的活动，感受到怎样的气质。对知行，目标应承接安静、专注、可靠的整体视觉语言；不能靠持续催促、随机躁动或强烈闪烁表达“正在工作”。

然后选择**一个主动作**，并设计其连续过程。动作可以由线条如何出现、空间如何打开、局部如何传递构成，不必预先限定为整个图形旋转。

以下是探索维度，不是并列候选或必须叠加的效果：

| 维度 | 真正需要设计的关系 |
|---|---|
| 笔画与书写 | 哪一笔出现、延伸、交接、收束；让帧之间像同一动作的不同阶段 |
| 留白与开合 | 用缺口、间隙或负空间的变化形成运动，避免整块图形忽大忽小 |
| 局部与整体 | 主体哪些部分稳定，活动发生在哪里；稳定参照帮助用户看出变化方向 |
| 多元素协同 | 元素如何接力、错相、聚合与分离；不是复制多个同时闪烁的点 |
| 节奏与力度 | 什么阶段快、什么阶段慢，何处需要停留；一次循环有清楚的动作，而不是平均换页 |
| 动静协同 | 动态活动区和静态阅读标记如何保持一致的气质与层级；各自形态适合各自位置，停止后安定且易扫读 |

原创性来自轮廓、运动规则、节奏与界面关系的组合。使用圆、点或线并不自动撞脸，换一个 Unicode 字符也不自动形成原创。参考其他产品时分析其重心、节奏和注意力分配，不直接复刻其标志性帧序列。

[IBM 动效原则](https://www.ibm.com/design/language/animation/overview/)与 [Carbon Motion](https://carbondesignsystem.com/elements/motion/overview/)提供了按使用场景区分动效气质、安排时序的参考。这里借鉴其设计方法，不照搬网页的缓动参数或图形效果。

### 4.2 把动作变成真实可见的帧

1. **确定显示预算。** 指明几列、几行、常用字号、允许的字符与颜色能力。单格和多格的优劣在这里评估，不在方案完成后才发现放不下。
2. **确定视觉不变量。** 固定占位、文字起点、主要重心与笔画气质；若动作需要改变面积或重心，应有明确轨迹，不是字形切换带来的意外跳动。
3. **画关键姿态，再映射材料。** 先看动作的起点、转折与衔接是否成立，再选择字形或字符组合。绘图草稿只用于思考；映射到真实字符后必须重新审查。
4. **同时设计空间和时间。** 哪些轮廓出现、相邻变化多大，与每帧停留多久一起决定观感。少量有效帧可以成立，很多无关帧仍然失败。
5. **检查循环接缝。** 末帧到首帧也是一次运动。逐帧查看重心、墨量、方向与间距，再按正常速度判断是否突然回跳、闪一下或像卡住。
6. **设计任意时刻结束。** 真正的任务会在任意帧完成；状态条应立即呈现实际结果，文字不跳位，不依赖额外播完一段表演。正文前的身份标记不因此切成“成功”。

不能把所有帧都强行做成相同墨量：开合或书写本来可能改变面积。要求是变化有意图、可感知、可控制，而非机械守恒。

### 4.3 时间设计与运行行为

区分**独特姿态数、姿态停留时间、实际绘制频率**。它们不是同一个参数。终端不统一保证动画帧率，现有的 300ms 也不是设计标准。

- 用动作幅度、可用中间姿态和真实观看结果确定节奏；既不为“顺滑”盲目追求高帧率，也不把“慢”直接等同于优雅。
- 循环相位应由经过时间决定，不随 token 到达次数变化；额外重画不能让动画突然加速，繁忙后不应补播排队的旧帧。
- 同一运行阶段中的文字更新不反复重启动画；真正的结束、失败和等待用户优先于动画节奏。
- 只更新需要变化的区域，并与现有屏幕写入协调；暂停显示时停止无用刷新，不让视觉优化造成输入延迟、IME 干扰或历史污染。

这些是候选落地时应满足的行为，不是本研究要求新增一套动画框架。

## 5. 兼容性必须进入设计本身

| 条件 | 设计应有的答案 |
|---|---|
| 深色／浅色主题 | 正文与指示符都可读；低亮帧不能消失，成功、警告和错误色不被装饰性变色占用 |
| 16 色／256 色／真彩色 | 形态与文字独立成立；需要连续 RGB 的方案不能声称低色数下效果相同 |
| 禁用颜色 | 保留明确文字和可用的形态；“改成灰度渐变”仍在使用颜色控制，不等于无色模式 |
| 静态／减少动态 | 提供静态标记与实际状态文字；不把“关闭颜色”错误等同于“关闭动画” |
| 不同字体与字号 | 核对缺字、回退、笔画断裂、光学跳动和列宽；不以要求用户换字体来掩盖默认方案的问题 |
| 窄窗口、缩放、中文输入 | 占位稳定，关键状态文字优先，输入光标与组合文字不受动画影响 |
| 非 TTY、管道和重定向 | 输出必要的静态状态，不把刷新控制序列和循环帧写成大量普通日志 |
| 辅助技术 | 以有意义的状态变化提供文本，不把每帧当成新的消息；不能假定网页 ARIA 在终端有效 |

颜色冗余与减少非必要运动的原则分别参考 [W3C Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)和 [Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)。这是设计参考，不代表终端已经实现网页的无障碍机制，也不据此宣称符合某项认证。终端是否传递系统减少动态偏好需要单独核实。

## 6. 怎样验证“做得好”，避免反复试错

### 6.1 正确的验证顺序

1. **材料核实：** 在目标终端和正常字号下检查将使用的字符、列宽与颜色。先排除不存在、缺字、尺寸不一致等不可实现条件。
2. **动作核实：** 同时看逐帧图与正常速度循环。不看方案名，也能感知预期动作；不能只在慢放或放大后才看清。
3. **场景核实：** 放回真实状态行，与正文、工具输出和输入框同屏。边阅读、边输入时仍舒适，不能只在孤立图标展示区成立。
4. **状态核实：** 按 §1.2 验证活动阶段切换、动画停止与现有结果展示的衔接，以及正文、工具结果中的静态标记。分别看短任务、长等待及任意帧结束，不把全部状态套到每个标记上，不新增其他符号的验收项目。
5. **兼容核实：** 覆盖约定的目标终端、常用字体、明暗主题和静态／无色表现。只报告实际验证过的范围。

网页可以用于初筛，但必须只播放实际字符帧及可落地样式。应让网页与终端使用同一份帧序列、停留时间和状态映射；不能用 CSS 插值、旋转或滤镜补出终端不存在的中间效果。即使数据相同，字体与渲染器仍可能不同，最后一关必须看真实终端。

### 6.2 评审依据

| 维度 | 能够直接观察的判据 |
|---|---|
| 清楚 | 不看说明也知道在运行还是已经结束；结果含义不依赖颜色猜测 |
| 动作成立 | 用户看到的是设计所说的运动，而非不相关字符来回切换；方向和循环接缝自然 |
| 光学稳定 | 没有无意的重心跳动、粗细突变、邻接文字移动或残影 |
| 克制 | 看正文时不会持续被拉回指示符；静态历史易扫读，不被色块与符号淹没 |
| 辨识度 | 与整体视觉语言相符，有明确的形态或节奏特征，不只是给常见 spinner 换色 |
| 完整性 | 动态、静态、无色、减少动态及异常状态均成立，不只展示最好看的运行一刻 |
| 可信 | 预览与实际可实现的机制一致，结果变化不被动画延迟，不损害终端交互 |

不可实现、语义误导、输入受干扰属于直接淘汰项；审美取舍不能掩盖这些问题。其余维度需要结合真实观看判断，不用主观打分伪装成客观测量。

### 6.3 对外只交付一个有依据的推荐

设计者自行探索、筛选和修正，最后提供**现状与一个最佳推荐**的同场景对比。保留用户已有的对照，不擅自删除；内部变体不堆到用户面前。

每个推荐只需附最小设计规格：**使用位置、预期感受、占位、实际帧与停留时间、独立设计的静态标记、各位置的状态颜色与文字、兼容处理、真实终端验证范围**。预览只展示本文范围：底部动画及正常结束的菱形、正文菱形、成功工具批次与失败／拒绝的菱形。放回真实排版比较，不附带其他图标的设计。这些信息足以实现和评审，不需要给一个小指示符搭建庞大设计系统。

如果新方案在真实使用中没有明确改善，就不采用；若目标在选定载体下无法成立，先准确说明限制，再换表达路径。不能悄悄替换用户要看的效果，也不能把“代码能播放”当成“设计已经完成”。
