# IM 通道接入选型研究

用于评估新增 IM 入口，不是发布承诺、开发优先级或已支持平台清单。原研究始于 2026-04-19；2026-09-11 结合官方资料与仓库校准。平台能力不等于知行已经实现的能力；当前飞书实现见[飞书通道架构](../modules/feishu/architecture.md)。

## 选择依据

个人助手既需要即时问答，也需要在任务完成、提醒到期时主动联系用户。因此，应分别评估“收到消息后回复”与“没有近期用户消息时投递”，不能仅凭 Bot API 或流式效果判断可用性。只能被动回复的入口仍有价值，但不能承诺承担可靠提醒；需要其他已获授权的投递目标时，必须明确选择，不能静默跨通道发送。

| 维度 | 对知行的意义 |
|---|---|
| 接入门槛与连接方式 | 长连接通常减少入站公网部署成本，但不意味着无需出网、无需授权或全部交互都无需 HTTP 回调 |
| 主动投递、目标范围与会话窗口 | 决定能否承接定时结果和后台通知；“有发送 API”不等于可向任意用户无限期发送 |
| 文本、媒体、编辑与流式呈现 | 决定输出是否完整、过程是否可理解；须分别核实平台能力与适配器能力 |
| 确认交互与身份绑定 | 按钮或文本只是交互载体，不能替代知行的授权裁决 |
| 重投、限流、错误与恢复语义 | 决定如何避免重复执行、静默丢失和不安全重试 |
| SDK、协议与部署成本 | 优先稳定、独立可用且许可适合的接入方式，不按 stars、用户总量或竞品宣传排期 |

## 候选平台比较

| 平台 | 接入方式与呈现能力 | 主动服务与准入边界 |
|---|---|---|
| 飞书／Lark | 官方 Node SDK 提供 WebSocket 事件订阅与消息 API；官方 Channel SDK 展示流式、媒体与卡片能力 | 应用可向权限及可用范围内的目标发送；长连接免入站公网地址，仍有处理超时重推和非广播限制。知行适配器能力见模块正文 |
| 钉钉 | 官方 Stream 覆盖机器人消息、事件及卡片回调 | 文档区分回复与主动发送；目标权限、会话回复凭据期限、限流与具体交互能力须按账号确认 |
| 企业微信 | 官方 aibot Node SDK 提供 WebSocket、消息收发、流式回复和模板卡片 | 主体资质、主动投递范围及配额须按账号确认，不能笼统认定所有接入都必须企业认证 |
| 微信个人号 iLink | 历史研究记录扫码登录、长轮询、按对端绑定 context_token 的路线；现行官方合同依据不足 | 回复权限、主动发送、令牌期限与风控边界待核实；扫码接入不等于无限期主动投递 |
| 微信公众号 | 历史研究记录 HTTP 回调与会话回复窗口 | 账号类型决定消息权限；当前窗口与投递限制待核实，不能直接作为可靠提醒入口 |
| QQ | 历史研究记录 WebSocket 路线与群聊接入门槛 | 当前主体门槛、目标类型与主动消息政策待核实，不能笼统认定主动消息全部可用或全部取消 |

依据：[飞书官方 Node SDK](https://github.com/larksuite/node-sdk)、[飞书官方 Channel SDK](https://github.com/larksuite/channel-sdk-node)、[钉钉 Stream 概述](https://open-dingtalk.github.io/developerpedia/docs/explore/tutorials/stream/overview/)、[企业微信官方 aibot SDK](https://github.com/WecomTeam/aibot-node-sdk/blob/main/README.md)。资料核实仅覆盖上述明确陈述，不代表完成各平台生产接入验证。

## iLink 路线中仍值得核对的设计问题

若现行协议仍采用入站携带的对端上下文令牌，则必须按账号与对端隔离令牌，区分登录凭据有效性和对话回复权限，核实刷新、持久化与过期恢复；不能把收到 HTTP 成功响应直接当作消息已送达。长轮询应能随断开操作取消，媒体处理须核实当前上传下载及加密协议。

这些是接入时需要回答的问题，不是现行协议断言。主动发送、消息与媒体上限、扫码可用范围、回复窗口和速率限制均需当前官方依据。移动端或仅私聊本身不构成否决理由，关键是目标用户能否完成需要的交互。

## 飞书参考实现：交互与可靠性策略

以下为 2026-04-19 对 Hermes 的 feishu.py、OpenClaw 的 openclaw-lark 与 ZeroClaw Lark channel 的研究记录，未锁定 commit，不代表最新版。表中“未记录”与“记录为无”不同：前者是证据缺口，后者是当时观察，均不能推断产品永久不支持。

| 维度 | Hermes（Python） | OpenClaw Lark（TypeScript） | ZeroClaw（Rust） |
|---|---|---|---|
| 流式回复 | 记录为无流式 | CardKit 流式卡片 | 编辑消息模拟更新 |
| 消息去重 | 24 小时 TTL、LRU 与持久化 | 未记录 | 未记录 |
| 批次合并 | 文本 0.6 秒、媒体 0.8 秒 | 记录为无 | 记录为无 |
| 确认卡片 | 允许一次／会话／永久／拒绝四按钮 | 确认按钮 | 记录为无 |
| 每会话串行 | chat_id 对应 asyncio.Lock | createChatQueue | 记录为无 |
| Webhook 校验 | SHA256 签名、验证 token、IP 限流 | 验证 token | 未记录 |
| 多账号 | 记录为无 | accounts.<id> | 记录为无 |
| 接收回执 | 收到消息添加 OK 表情 | 可配置表情回执 | 按 locale 选择 |
| 群聊策略 | allowlist／blacklist／disabled | allowlist／open／disabled | allowed_users |
| 格式降级 | post 失败后回退 text | 未记录 | 卡片 Markdown 截断 |

**接收回执、执行进展、流式正文和最终结果是不同反馈，不能互相替代。** 卡片逐字更新解决回复呈现，每会话队列解决执行顺序，去重与确认解决重复及授权问题；它们需要协作，但不应由各适配器重复实现整套智能体权威。

研究当时还以 OpenClaw Lark Issue #384 为线索，区分默认分段发送与需另行开启的逐字更新；该问题未附完整来源定位，不能作为当前默认值依据。对“过程不可见、失败反馈粗糙、平台消息与内部排队状态脱节”的观察，构成知行选择“飞书里的 AI 助手工作台”而非仅返回最终文本的设计理由，不构成所有竞品都缺失这些能力的结论。有效体验要求及当前差异见[飞书通道架构](../modules/feishu/architecture.md)。

## 与产品架构的边界

平台连接与消息规范化由适配器负责；会话接受、执行、确认裁决和可靠投递由对应产品责任承担。能力缺失应如实暴露，不因接口同名假设不同平台的语义相同。具体飞书能力与原体验目标的差异由模块正文维护，本研究不复制架构合同。

主动服务能力与部署成本是平台选择的关键，平台列表不构成开发排期。使用官方协议也不等于没有合规或账号风险；公开服务方式须另行核查适用规定与平台条款。
