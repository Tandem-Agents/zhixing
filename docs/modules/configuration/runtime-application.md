# 运行期配置应用

## 产品合同

- `/config` 是基础配置主入口，不把“基础／偏好”等内部分类拆成用户必须理解的命令；只在已有明确职责或真实高频需求下提供专题入口，当前 MCP 管理由 `/mcp` 负责。
- 修改后由系统完成应用，高频配置应在后续消息中生效，不要求用户主动重启。低频且尚不支持即时应用的配置应明确告知“已保存，后续启动生效”，不能以一律要求用户重启代替正常应用。
- 正在进行的回答、对话持久事实与用户授权不能因改配置意外丢失；保存、应用与失败状态必须分别如实反馈，不泄露凭据。
- 不为配置更新原地篡改正在执行实例的配置。替换、恢复与释放归宿主生命周期，终端只负责编辑及反馈；不重复拥有业务运行体。

## 方案演进与仍有效的理由

| 旧选型 | 有效含义与当前处置 |
|---|---|
| 原地 mutable refs／getters 更新配置 | 容易使跨组件捕获值、提示与预算失去一致性；保留“运行实例使用确定配置”的约束，不禁止实例内部必要状态 |
| 要求用户敲回车重启 | 把内部生命周期成本交给用户，拒绝作为常规体验；系统内部重建本身并非禁止 |
| CLI 内 blue-green RuntimeSession | 曾通过构建新资源、替换引用、释放旧资源维持不可变装配；当前已由宿主换代替代，旧类、局部 diff、双轨命令注册不再是实施方案 |

旧设计对会话级授权归属、无变更不重建、通道不受无关配置干扰及失败不损坏现有工作提出的要求仍有价值，不能随旧类删除而丢弃；当前实现差异见下节。旧“零跨包 API 改动”、可选注入兼容桥、AgentRuntime 只靠 GC、未来扩展接口和旧分阶段实施步骤不作为现行约束。

## 当前生产链

统一[命令系统](../cli/command-system.md)调用[配置 handler](../../../packages/cli/src/runtime/config-command.ts)，并由 [REPL 接线](../../../packages/cli/src/repl.ts)提供宿主操作：

1. 检查交互终端能力；暂停 readline 与渲染，让编辑器接管输入。重新加载配置和凭据，不用启动时缓存作为编辑事实。
2. 编辑器仅“完成”才写入；取消返回原交互。`finally` 恢复 readline 与光标约束。秘密与编辑器保存语义见[首次引导与配置编辑](../secrets/onboarding.md)。
3. 完成后等待本终端 `activeTurnPromise` 到达终态。比较 enabledRoles 与 executorAutoStart，判断是否还需处理托管服务启动选择。
4. 请求宿主 `server.shutdown`，reason 为 config-reload、策略为 drain；随后通过 coreHost.reconnect 重新连接／拉起，角色启动选择变化时在换代前执行托管服务准备。
5. 等待重载状态，刷新本地视图、重新挂接当前会话观察者并同步任务列表。对话恢复消费持久事实，不能用终端本地消息数组恢复第二份权威。
6. 若启动选择变化，再执行托管服务收敛；重载与收敛分别记录成功或失败，失败之一不能掩盖另一项结果。成功后展示通道状态；整体结果未确认时明确提示检查当前运行状态。

本地 turn 等待只保护本终端，不代替宿主对其他入口工作的 drain。停止、投递排空与恢复边界沿用[统一宿主合同](../../../research/design/drafts/unified-core-and-access-surfaces.md)及[对话持久化](../conversation/persistence.md)，本模块不重建第二套状态机。

## 当前差异与失败边界

| 要求／旧保证 | 当前事实 |
|---|---|
| 配置与秘密一同保存 | 两次顺序写入，不是跨存储事务；沿用秘密模块已登记的差异 |
| 编辑与保存使用同一配置文件 | `/config` 按 `ZHIXING_CONFIG_PATH` 读取，但保存时传入其父目录 `homeDir`，使 `writeConfig` 固定写入该目录的 `config.jsonc`。指定其他文件名时读写分离，保存成功不能证明所选配置已更新；这是当前实现偏差，不改变单一来源要求 |
| 无变更不重建 | completed 路径仍请求宿主换代；当前比较仅用于启动选择，不是全配置 no-change 门 |
| 模型变更不重建未变通道 | 整体宿主换代会重新装配，不能承诺旧长连接保持不断 |
| 构建新资源失败时完整保留旧运行体 | 当前先请求旧宿主退出再重连，没有旧 blue-green 的新旧并存回滚保证 |
| 会话授权跨换代保留 | PermissionStore 的 session 规则仍为内存态；不能用持久对话恢复证明授权恢复，也不能照抄旧设计“复用同一 store”保证。现行授权作用域见[信任管理](../security/trust.md) |
| 改完立即生效、用户不承担内部概念 | 正常路径由系统自动换代；当前成功文案直说“核心宿主已按新配置重启”，失败文案要求 `zz status` 检查，与完全隐藏内部换代成本的体验仍有差异 |

停机请求失败时，`reloadCoreHostAfterConfig` 仍尝试重连；停机与重连都失败时聚合两项错误。重连失败不报告应用成功；重连和刷新成功但停机请求曾失败时仍上报该失败，不凭新连接猜测旧进程已退出。

编辑、保存、宿主应用和托管收敛是不同失败阶段。文件已保存不等于新配置已经生效，失败也不承诺“旧宿主一定还在”或“下次启动一定成功”。错误应保持可行动、不得包含秘密；本次迁移仅如实保留要求与差异，不实施代码整改。

## 范围与验证

本单元不新增文件 watch、通用热更新平台、额外字段快捷命令或 `/restart`，不恢复旧 RuntimeSession。旧稿附带的 `/resume`、`/new` 活动时间修复及退出清理，保留其“不丢最近对话、正确释放所拥有资源”的目的，具体合同分别由对话和宿主文档承担；普通退出接入面不等于关闭宿主，不能恢复旧的进程退出清理方案。

直接验证覆盖：编辑取消与输入恢复、写入失败不触发虚假成功、运行中回答与其他入口 drain、换代后模型／通道配置及活动会话恢复、授权状态、停机／重连／刷新各自失败、托管选择变更与独立收敛失败、不回显秘密。无变更和无关通道重建也须按上述差异核实；旧局部 swap 的 mock 或“文件写成功”不能证明当前端到端合同成立。
