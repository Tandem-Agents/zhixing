# SSP 采纳与集成边界

本文说明知行与 Stepped Skill Protocol（SSP）的关系、当前支持边界及未来集成方向，不定义协议本体，也不承诺当前产品已支持 SSP 分步执行。

## 采纳原则

SSP 将用户逐阶段交付给 agent 的工作方式表达为可分步读取、由模型推进的技能结构。知行将其视为外部可复用协议，而非私有功能：保持普通 Agent Skills 兼容性，不让知行内部实现反向约束协议的通用设计。

协议定义、metadata、step 与 manifest 契约、验证标准、工具及发布治理以[独立协议仓库](https://github.com/HJSunDev/stepped-skill-protocol)为权威。知行只维护自身的采纳关系、实现边界与集成决策，避免第二份协议权威造成漂移。

仓库已包含供开发协作者使用的 `.agents/skills/stepped-skill-author/`，其中有编写规范、检查表与模板。这些是开发辅助材料，不是知行产品的运行时实现，也不能以其存在证明产品已支持 SSP；本地参考材料不取代协议仓库。

## 支持层次与当前事实

以下是知行侧区分集成深度的方式，不作为 SSP 协议自身的版本或合规等级定义。

| 层次 | 含义 | 当前边界 |
|---|---|---|
| 普通 Skill 兼容（L0） | 不识别 SSP 结构，通过普通技能机制读取内容 | 已有普通技能加载，但不等于任意 SSP 包可完整执行；仅有入口而缺少步骤文件时不能完成工作 |
| 模型自驱（L1） | 模型从入口按 step 指针读取并推进 | 必须能访问步骤及资源，且依赖模型遵循文本；没有运行时级的当前步骤隔离。知行尚无完整的 SSP 包接入与分步执行保障 |
| 运行时原生（L2） | 识别协议结构，管理当前步骤、交接与执行事实 | 尚未实现；是原设计保留的长期集成方向，需单独设计，不是本次发布承诺 |

当前 `admit_skill` 的候选检查涉及目录树，但正式入库只保存 `SKILL.md` 正文；`load_skill` 从内容制品读取正文，没有 SSP manifest 解析或 step 执行控制。接入一个目录不能保证其中 `steps/` 与配套资源在之后仍可用。现状依据见[创作与接入](authoring-and-admission.md)及[技能领域应用](../../../packages/core/src/skills/catalog-application.ts)。

模型通过获准的通用读取工具访问完整本地包，与产品正式支持 SSP 是不同的事情；不否定这种使用方式，也不将其当作已经验证的协议支持。当前辅助编写规范要求入口保持简洁、步骤留在独立文件，因此不能假设入口内另有完整流程可供回退。

## 未来集成边界

若启动原生支持，应在技能模块内单独设计知行的实现，不复制协议规范，也不预建执行框架。需要明确：

- 技能包及资源如何保留、寻址，加载器与索引如何识别协议入口。
- 当前步骤如何选择和读取，handoff 如何捕获、传递与展示，如何映射既有 Run、Turn 和执行记录，而不另造冲突的生命周期。
- 当前步骤的内容可见范围如何与上下文管理配合；文本约定、内容选择与强安全隔离必须区分。
- 普通技能兼容与失败回退的条件：资源不可用或回退会改变任务、安全语义时，不能静默宣称已完成回退。
- 产品对实际支持层次如何作准确说明，不把内部协议复杂度交给用户维护。

原生支持可以增强执行控制，但需要证明其实际价值；模型自驱、普通兼容与原生控制不能混称。本文随采纳决策、生产支持范围或协议入口变化更新，不承担过程日志或协议副本职责。
