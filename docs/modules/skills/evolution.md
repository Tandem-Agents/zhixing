# 技能自主进化

本文承载尚未实现的技能管家设计：从工作中沉淀可复用做法，自主迭代与治理自产技能。它不是当前执行规格，也不构成本次发布或架构迁移的新增范围。现有能力以[技能架构](architecture.md)和[技能创作与接入](authoring-and-admission.md)为准。

## 目标与边界

自主进化的价值不是增加技能数量，而是让有用的方法得以积累，并避免重复产生、清理同一种噪音。只沉淀可复用的程序性做法、与做法相关的用户约定和实际踩坑；一次性任务与通用常识不进入技能库。拿不准是否有价值时不保存。

管家只能修改、合并、泛化和淘汰自己自主产生的技能。手写、用户在对话中要求 AI 创作、外部接入及官方技能均不属于管家的治理范围；不能根据所在目录或“由 AI 写成”推断治理权限。为避免重复产出可以读取既有索引与必要正文，但读取不授予修改权。

用户编辑并接管自产技能后，它退出自动治理范围；管家自身修订不能误触发接管。来源身份必须由可信触发路径确定，并在每次变更时校验目标权限，不能只靠模型遵守提示词或隐藏某个工具。

设计意图是默认自主保存、产生后轻量告知，不逐次要求确认；用户能识别自产内容、禁用、删除、固定或接管，并能停止自主运行。可选择“先提议、确认后保存”作为较温和的模式，具体配置尚未实现。该设计不取消现有对话创作的明确接受边界，也不授权管家绕过系统安全与提交规则。

## 产生与治理

### 产生

复盘应在一次工作结束后进行，不把每个模型工具轮当成一次任务完成，也不阻塞前台交互。原设计以成功完成为触发前提；中断、失败和达到迭代上限不直接触发此产生流程。接入时必须核实生产终态，不能将模型循环结束等同于结果已耐久提交。

判定输入包含必要的近期对话、当前模式技能索引与来源、自产内容的使用和用户反馈；不默认复制无限历史。输出分为：

- 不处理：没有可复用价值、证据不足，或已有用户／接入技能覆盖。
- 新建：存在尚未覆盖的可复用方法。
- 修订：已有自产技能覆盖，但需要纠正或补充。

模型负责内容判断；产生、修订与治理均使用 main 档，不交给 light，因为这些判断会持久改变技能资产，属于高副作用决策。权限、格式、脱敏和提交由系统守住。模式由产生时的产品上下文确定，不让模型猜测。自主路径与用户路径复用必要的内容处理和权威提交能力，但保留各自不同的授权语义。

### 治理

治理针对自产内容执行去重合并、特例泛化和失效淘汰。候选选择须有预算上限、能逐步覆盖全体，并能找到跨批次的相关技能；不能只处理碰巧落在同一批的重复项。

不得按“长期未使用”直接删除。用户固定、非自产、仍有近期使用的内容不进入淘汰；低频不等于无价值。自动淘汰应可恢复，误改与误合并也必须有发现和撤销的办法，不能把当前归档接口等同于满足这些要求。

产生与治理应受现有宿主生命周期、调度和资源控制约束：防止重复触发、递归触发与并发写冲突，停机与恢复不能造成失控补跑。后台执行不等于脱离宿主管理的任意异步任务，也不另建一套权威状态或调度主链。

## 反馈与安全

反馈必须回到产生判断，避免“持续产噪音—清理—再产”的循环。用户删除、禁用、固定与实际加载记录可作为判断材料；删除或禁用不必然证明内容错误，零命中也不单独证明无价值。反馈应结合上下文解释，而非强行转换成质量标签。

管家为了扫描、修订或治理而读取正文，不得增加正常使用计数。当前 `load_skill` 的命中只能说明加载发生，不证明方法被正确执行或改善了结果。反馈进入模型输入是一种候选改善机制，不保证判断必然越来越准；效果仍需验证。

所有自主新建和修订必须遵守同一内容安全底线，不能把对话中的凭证固化进反复加载的技能；脱敏器只是防线，不是“绝无泄漏”的证明。用户资产保护、预算、恢复与停止能力不能依赖模型始终判断正确。

## 当前基础与未实现部分

当前 Skill Catalog 由权威记录持有目录状态，正文以不可变 `ArtifactRef` 引用；运行内保存和使用事实通过 assignment 提交，管理动作走领域应用。后续设计应沿用这些责任，不恢复本地目录、索引文件或旧 Store 作为第二写入路径。

| 当前事实 | 对自主进化的影响 |
|---|---|
| `SkillCatalogEntry` 有 `own/linked`、模式、固定／禁用、使用度量与版本；没有自主创建者或治理游标 | `own` 不能当作自产许可，来源与接管规则尚需设计 |
| 已有保存、加载、接入及管理应用，没有技能管家生产入口或周期治理处理器 | 不能将现有对话创作视为自主进化已落地 |
| 归档移除活动目录项，没有面向用户的归档恢复合同 | 旧稿的“移动到归档目录即可恢复”不成立；自动治理的可恢复性尚未具备 |
| 技能索引由产品投影进入 Kernel 的注意力窗口 | 变更按既有窗口边界可见，管家不能直接改写窗口内系统提示或另建提示刷新机制 |

上述事实可分别由 `packages/core/src/skills/types.ts`、`catalog-application.ts`、`global-state-adapter.ts`、`packages/server/src/system-handlers.ts` 和 `packages/cli/src/runtime/skill-catalog-window-projection.ts` 核实。现有架构是接入基础，不等于所有扩展条件已齐备，也不保证只加几个字段即可完成。

## 候选机制与待解决问题

原设计中仍值得验证的机制：用教学／纠正信号粗筛、低频计数补漏，再由模型判定；按距上次完成的间隔治理；以审查时间轮转候选并查找相似邻居；将自产反馈送回判定输入。它们均不是已验证最优方案，具体事件、频率、阈值和状态表达不在此提前锁死。

实施前需要回答：

1. 怎样识别真正值得保存的方法，并证明改写没有降低原有价值？
2. 什么触发节奏与最小上下文能兼顾质量、成本和不打扰？
3. 技能应细分还是合并，怎样避免碎片化和过度泛化？
4. 来源、接管、并发提交、停止与恢复怎样在现有权威链中成立？
5. 怎样取得未被自身读取污染的反馈，并证明它实际改善后续产出？

验证应覆盖产生判定、越权拒绝、接管、治理预算、误删恢复、反馈污染、重复执行及窗口稳定。逻辑测试不能替代真实生产提交、生命周期和内容效果验证。

外部研究见 [Skill 系统比较](../../../research/source-analysis/skill-system-comparison.md)与 [Hermes Skill 研究](../../../research/source-analysis/hermes-agent/skill-system.md)。外部策略只作为参考，不在本文复制实现细节或据此承诺知行效果。
