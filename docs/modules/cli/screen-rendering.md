# CLI 屏幕渲染与能力边界

本文说明屏幕如何组织、为何这样选择，以及终端约束与当前实现边界。视觉语言见[视觉设计语言](visual-language.md)，输入形态见[输入区视觉](input-visual.md)；屏幕回卷不是[对话持久化](../conversation/persistence.md)。

## 核心取舍

主 REPL 使用主缓冲区与 DECSTBM 滚动区：对话输出在上方滚动，状态与输入区固定在底部，已滚出的内容交给终端原生回卷。这样保留长对话回看及终端复制体验，不必自建完整历史画面的滚动引擎；代价是应用不能直接接管已进入终端回卷的画面。

**缓冲区选择与渲染方式是两个独立维度。** 主缓冲区／备用屏幕决定终端如何保存画面；应用保留哪些内容、布局与交互状态，决定能重画什么。命令式 ANSI 输出不等于没有状态，也不意味着无法实现应用内滚动。

知行保留输入、配置面板、状态条和活动输出段等局部状态，但没有完整历史画面的可重建模型。不能把这一限制写成“全项目没有 UI 状态”，也不能把持久化对话数据当成已经实现的历史画面重排能力。

## 两种屏幕与职责

| 使用面 | 组织方式 | 责任 |
|---|---|---|
| 主 REPL | 主缓冲区：终端回卷 → DECSTBM 输出区 → 固定状态／输入区 | `ScreenController` 协调写入与生命周期；`ScrollRegion` 管滚动区、活动段和固定区布局 |
| 独占面板 | 备用屏幕（alt-screen），退出后返回主画面 | 配置编辑器等持有面板状态并重绘；使用 `Renderer` 管理 ANSI 输出和进退 |

备用屏幕没有主屏那样的原生历史回卷，但不禁止应用自己保存内容、按偏移重绘。滚动能力必须同时具备内容／布局模型与输入处理，不能只切换缓冲区就获得。

当前配置编辑器和技能管理器都有自己的渲染路径。旧技能编辑器已不在生产代码中；`composeViewport` 与 `writeFrame` 原语仍存在，但当前没有生产调用，不能据此宣称面板已具备统一视口或滚动能力。`composeViewport` 实际仅截断、填充并可提示折叠，未消费 `scrollOffset`。

## 当前生命周期与可见结果

- **首次接管：** `ScreenController` 在输入首次 attach 前缓冲输出；首次 attach 使用 `2J → 3J → 光标归顶` 清理视口及回卷，再建立滚动区与固定区。这会清掉启动前 shell 的可见输出，不等于删除 shell 命令历史。
- **局部更新：** 状态／输入区局部重画；活动段支持 replace／commit，不需要重画全部历史。已提交至终端回卷的内容没有通用的读取、修改或搬回接口。
- **独占切换：** `suspend/resume` 切入／退出备用屏幕，暂停主输出区写入；恢复时重新确认滚动区、固定区和光标。自管面板使用 `Renderer` 管理进退；两条路径不能被误写成同一套清屏动作。切换不应以清空主画面来为面板腾位置。
- **窗口缩放：** REPL 在 resize 稳定后调用 `rebuildAfterResize`，清理视口及回卷，按新尺寸重建固定区、欢迎内容和提示；不是把完整旧对话画面按新宽度重排。已存对话数据不由这条清屏路径删除，视觉历史消失与对话数据丢失必须区分。
- **退出：** 已接管时撤销滚动区、清视口并恢复光标，不清剩余回卷；从未接管时不清 shell。退出并非完整还原启动前的 shell 画面，期间已被首次接管或缩放清掉的回卷不会因此恢复。

## 能力边界

| 能力 | 当前结论 |
|---|---|
| 对话输出原生回看 | 主 REPL 依赖终端回卷；受首次接管与缩放清理边界影响 |
| 状态与输入固定 | 主 REPL 用 DECSTBM；独占面板自行布局 |
| 当前输入、面板与活动段重画 | 有局部状态与对应渲染路径，不是“完全无状态” |
| 完整已绘历史接管与缩放重排 | 未实现；不能以存在 transcript 或局部重画能力代替 |
| 独占面板的长内容滚动 | 按面板实际实现判断；没有通用滚动视口，方向键选择条目也不等于内容滚动 |

这些是实现取舍，不是要求改用声明式框架或重建渲染引擎。任何新屏幕需求应先判断它需要改变哪条边界，不能把“目前未实现”当成终端不可能支持。

## 协议约束与防错规则

- 滚轮回卷、方向键和鼠标事件不是同一机制。xterm 的 Alternate Scroll 模式（1007）可把备用屏幕滚轮转换为上下方向键；鼠标跟踪模式配合 SGR 编码（1006）则上报事件。两者仍需应用正确消费，并管理进入、退出及交接时的模式生命周期，避免转义序列落入普通输入。协议依据见 [xterm 控制序列](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)。
- 键盘交互不依赖滚轮上报，可作为面板操作基线；鼠标可用性须按终端宿主、版本与配置验证。PowerShell／Git Bash 是 shell 名称，不能据此断定宿主一定是 conhost；旧记录中的单环境结果不构成跨终端支持结论。
- 滚动区写入合同要求每个换行分段的可见宽度不超过 `columns - 1`；否则隐式换行会使逻辑行数与物理行数分离，破坏段位置与滚动计算。按可见列宽处理中文和 ANSI，不能只数字符。
- 清屏、清回卷、撤滚动区与切备用屏幕不是同一动作。`Renderer.clear()` 使用光标归顶后清至屏尾；首次接管／缩放与退出采用各自协议，不能为形式统一互换序列或调整顺序。

### 保留的故障经验：备用屏幕继承滚动区

旧记录中，技能编辑屏曾在进入备用屏幕后丢失顶行、内容自动上滚；记录的对照实验指出继承的 DECSTBM 区域会使满屏输出提前滚动，而非最初怀疑的满宽自动换行。

当前 `Renderer.enterAlternateScreen()` 仍在进入后立即发送 `CSI r`，将备用屏幕滚动区恢复为整屏；退出仅离开备用屏幕，不顺手重置返回后的主屏滚动区。`ScreenController.resume()` 则负责重新确认主 REPL 的区域与固定区。保留的是这一防错原因和责任边界，不是断言所有终端都以相同方式继承状态，也不把历史实验冒充本轮实测。

`writeFrame` 使用无尾换行的整帧输出，避免额外换行触发滚动；它仍不能代替对行宽和屏高的正确控制。
