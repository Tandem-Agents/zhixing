# 安全架构与防护边界

本篇定义工具执行的通用安全职责与当前实现边界；用户信任和规则管理见[信任、授权与管理](trust.md)，确认决定与表面交互见[确认交互](../confirmation/architecture.md)。

## 目标与取舍

知行是个人助手，安全不能只围绕代码仓库或 Shell 白名单设计。安全判断关注操作实际跨越的资源边界；新工具接入共享保护，业务特有约束仍由相应工具或领域负责。

安全保护用户免受智能体误操作、提示注入诱导的越权、敏感资源访问和失控执行；不把用户作为对手，也不承担杀毒软件或已失陷操作系统的防护职责。提示注入防护不是辨认每句恶意文本，而是让实际操作仍经过授权与资源保护。

| 设计选择 | 理由与边界 |
|---|---|
| 资源边界与操作影响分类，而非仅按工具名授权 | 同一工具可能只读也可能破坏数据；业务工具通过声明参与分类，不能靠名称获得信任 |
| 确定性规则、语义研判、用户确认分层 | 已知底线不交模型裁决；模型只处理规则未覆盖的灰色操作，不能取代所有授权 |
| 操作影响与用户信任分离 | 工作区内写文件仍有外部影响；便利来自有效授权，不来自把风险改名为低影响 |
| 应用层通用保护与工具专用保护分责 | 路径、执行限额与通用策略共享；收件人、业务额度等由所属能力约束，不塞入通用分类器 |
| 跨平台使用同一决策机制 | 不让用户承担平台架构概念；同一机制不等于不同操作系统具有相同隔离强度 |
| 保守解析，不把 Shell 识别当成完整沙箱 | 快捷放行需有明确依据；未知语法不能靠前缀匹配推定安全，应用层检查也不能约束任意系统调用 |

## 当前责任链

```text
Host 绑定产品上下文、规则来源与受保护路径
  → Kernel 工具执行入口：耐久执行验权、取得冻结权限（适用时）
  → SecurityPipeline：解析 → 策略 → 影响分类 → 信任分级 → 权限匹配 → 执行约束
  → 拦截 / 安全助理研判 / Confirmation Broker
  → 真实副作用前再次验权 → 带约束执行工具
```

- `core/security` 提供确定性安全机制，不调用 LLM、不拥有用户授权业务。运行时管线消费只读规则来源。
- `orchestrator/security/secure-executor` 连接管线、安全助理、Broker、审计与实际执行；不是用户规则的持久化 owner。
- Trust Administration 应用决定规则创建、沉淀、作用域与撤销。Host 通过有限 `KernelSecurityExecution` 绑定提供执行输入和批准效果；Kernel 不自行查找 Store 或决定产品上下文。
- 本机秘密路径由 Host 显式提供给策略机制；执行设备与锚点的签发、资产和租约属于分布式授权体系，本模块消费其验权结果，不另建权威。

## 决策机制

策略采用声明式数据模型：`SecurityRule` 描述匹配条件、动作、风险与提示，`MatchSpec` 表达路径、命令、网络、环境变量及组合条件，由统一 `PolicyEngine` 评估。已有匹配能力覆盖的新规则只需增加规则条目，不必为每条策略新增执行分支；新的匹配语义仍需实现匹配器。规则与机制分离，便于独立审查、测试和版本管理，不等于已经具备社区规则分发或产品级热加载。

| 顺序 | 机制 | 职责 |
|---|---|---|
| 1 | CommandAnalyzer、PathResolve | 提取命令访问事实，解析路径后供策略与信任判断使用；符号链接不能仅靠文本路径判为目录内 |
| 2 | PolicyEvaluator | 匹配内置策略及 Host 保护路径；`block` 直接终止，`confirm` 保留确认要求，`audit` 转为允许继续评估 |
| 3 | OperationClassifier | 只读为 `observe`；应用状态边界可为 `internal`；用户文件写入为 `external`；高危或未知边界可为 `critical`。external/critical 将原 allow 升为 confirm，不抹去已有策略确认 |
| 4 | TrustClassifier | 计算本次操作的信任等级，不直接放行；路径与场景规则见信任正文 |
| 5 | PermissionMatcher | 仅对 confirm 决策匹配用户／预置权限；deny 阻止，allow 不能覆盖 bypassImmune 确认；未匹配继续确认，不在此按会话是否交互直接拒绝 |
| 6 | ExecutionGuard | 计算超时、输出上限及频率限额；频率超限阻止，执行层消费剩余约束 |

不要把策略规则与权限规则混为一谈：前者判断威胁，后者表示授权。当前策略引擎按动作严格度选择结果；用户权限匹配先查用户规则池，再查工具预置池，同池 deny 优先，再比较匹配特异性。工具预置规则的注册、作用域和退场见[工具与权限集成](../tools/permission-integration.md)。

内置底线包含凭证、密钥、Git 内部写入、危险环境变量和 Host 指定秘密路径等保护；以 `builtin-rules.ts` 及 Host 注入的规则为准。`bypassImmune + block` 不可批准；`bypassImmune + confirm` 要逐次确认，不能被规则或安全助理跳过。它不是“所有受保护路径一律禁止任何访问”的同义词。

### 工具声明与 Shell

文件工具、Shell 使用专用影响分类，其余工具按实际边界声明分类；无有效边界声明默认 critical。第三方声明不是行为证明：当前没有通用的运行时监控来验证 MCP 实际系统调用均符合声明，也不能宣称所有业务工具已具备各自的频率、收件人等保护。

Shell 快捷只读识别采用明确命令及子命令、参数检查；链式操作、重定向与替换等不能仅因第一个词是只读命令便放行。路径解析和命令预解析降低已知绕过风险，但不是完整语言解释器；任意脚本、子进程行为与多步信息流不在此机制的完备证明范围。

## 执行、审计与真实局限

执行守卫产出约束，不能仅以管线计算成功证明约束已执行。`secure-executor` 在实际调用处应用超时与输出限制；通用超时会发出取消并结束等待，不配合取消的工具仍可能继续运行。环境处理、网络出口及子进程终止分别由相关工具与基础设施落实，不能描述成一个能自动改写所有危险命令的万能 ShellGuard。

安全审计由 run 级 `SecurityAuditor` 发射评估、安全助理裁决和规则沉淀等事件；`/security` 消费宿主快照，展示内置策略、用户规则、限额与确认累计。当前没有旧稿所画的完整历史审计仪表盘，也没有独立实现的 `/security audit` 查询。

用户应能理解为何拦截、为何自动放行以及如何撤销授权。不可解释的安全行为会削弱信任，诱使用户关闭保护；反馈应解释影响与可行操作，而非倾倒内部执行细节。

以下设计意图不能写成已实现保证：

- **critical 始终逐次确认**：当前分类器会升为 confirm，但 `PermissionMatcher` 对未命中 bypassImmune 的 critical 仍可按显式 allow 规则放行。安全助理不会裁决 critical；两者不可混淆。
- **策略来源覆盖与底线不可覆写**：生产默认装载内置规则与 Host 保护路径；引擎 `loadRules` 按同 ID 替换，不能据旧方案声称任意扩展加载下均强制保护 bypassImmune。项目／社区策略加载不是现行完整产品能力。
- **OS 隔离**：当前安全管线没有旧稿的 Seatbelt、bubblewrap 或 Docker 自动加固链。应用层守卫不是内核沙箱，不宣称“95% 威胁覆盖”或“完整保护”。
- **单次判断的边界**：没有通用多步泄露关联分析；路径检查也不等于消除检查到执行之间所有竞态。
