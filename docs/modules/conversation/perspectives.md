# 多视角评议

## 需求区

### 多视角发散收敛

- **本质需求**：复杂、关键、易误判问题需要一种内功能力：临时拉起多个隔离子 agent，从不同视角独立产出、交叉吸收，再收敛出唯一最终版本回主线。中间过程瞬时、不持久化、不污染主线。
- **地基**：以文件化可编排基础设施为基础——本需求的流程是固定的，产物是一份内置编排文档，不写死进代码。基础设施是公用的，绝不为本需求定制耦合；能力不足时（如节点级模型档位）从基础设施视角做通用增强。
- **唤醒**：`@` 行首后跟空格，或行中前后皆空格，后接问题正文即触发并发；`@` 后无正文不触发，避免误伤 `email@x.com`。并发数量写在自然语言问题里。手动 `@` 是第一阶段发起者，未来 AI 自动触发等多种发起方式复用同一机制，注意架构设计。
- **分配节点**：唤醒后先经分配节点，依据问题内容决定视角集合；用户未要求时默认 3 个，上限 5 个（提示词声明 + 系统层强制，超出按 5 处理）。提示词内置常见场景示例（思考需求、审查代码各有哪些视角）作分配参考。
- **模型档位**：main 必有、power 可选。仅 main 时列表全为 main；配置了 power 则以 main 起始与 power 交替。不同档位模型参与不同视角，用视角 × 档位双重多样性提高结果质量。
- **流程**：第一轮并发——各视角基于同一主注意力窗口只读快照独立产出；第二轮并发——每个节点拿到其余节点的结果（提示词告知这是他人结果），判断优劣并融合出自己的最优版本；收敛节点——从各最优版本收敛出唯一最终版本回主线。第二轮的 token 成本是明确接受的需求。

## 产品与架构

多视角评议是同一会话的一种回答方式，不是新会话或要求用户组装的工作流。多个隔离视角先独立判断，再交叉吸收，最后交付唯一答案；用户关注问题与结果，不承担编排概念。

通用基础设施见[文件化编排架构](../orchestration/architecture.md)。本篇负责触发、视角分配、模板选择、结果回主线及产品呈现；基础设施不定义视角、审查方法或收敛策略。

### 当前责任链

`CLI 输入 → session.send.engage → 会话应用与准入 → 多视角应用 → 分配/模板/runner → 正确性端口 → 会话提交与结果发布`

- CLI 负责触发解析与材料准备，wire 使用 `engage: { kind: "perspectives", question }`，不新增独立 RPC 方法。
- `core/conversation/perspectives-application.ts` 持有产品行为与内置模板；旧 server PerspectivesController 不是当前责任归属。
- CLI 宿主的 `conversation-perspectives-correctness.ts` 将运行、提交、安全快照和计量映射到会话 owner；应用不直接依赖其存储实现。
- 通用 runner 与 AgentNodeExecutor 负责执行已校验的 DAG，所有节点复用现有模型、工具、安全和资源路径。

### 输入与准入

触发符为前面是起点或空白、后面是空白的 `@`，且后方有正文；剥除标记保留两侧正文，不误伤邮件或 `@名称`。当前解析器接受空白字符，不仅是单个 ASCII 空格。

问题材料先经现有输入准备，`engage.question` 使用准备后的文本；server 不重新从原始输入推断问题。当前 CLI 明确拒绝图片等非文本材料；文件文本引用可以按材料输入链展开。用户输入与问题正文职责分离，不以节点提示替换用户表达。

该回答仍服从会话串行准入、busy、排队和 abort，不开带外主链。与推进职责的有效边界是：无推进会话时显式 engage 不应被自动准入分类取代；已有 active/awaiting 状态沿会话现有规则裁决，未获准执行时不强行启动评议，已提交结果照常进入后续推进判断。

### 分配与固定拓扑

在执行边界捕获一次 tail 窗口快照，随后：

1. main 模型根据问题与快照分配视角，输出经结构检查；默认 3 是提示引导，合法范围 2～5，超过 5 截取，少于 2 失败。
2. 应用按 main/power 交替安排视角模型；power 未配置时使用配置层解析后的 main 回落。收敛使用 power，交叉节点沿用本视角档位，分配使用 main。
3. 有界视角数组填入内置 JSONC 模板，展开静态 DAG，再走基础设施完整校验。
4. N 个独立节点共享快照，但不看彼此输出；N 个交叉节点依赖全部第一轮输出，明确识别自身与他人版本；一个收敛节点依赖全部交叉版本，给出唯一整体答案。

动态的是分配参数，不是执行中由模型决定拓扑。模板当前以字符串资产内置于应用文件，随代码构建；不是用户需要维护的磁盘流程文件，也不是代码临时拼接 definition 绕过校验。数组展开与模型角色由通用层承载，业务只负责其使用方式。

当前模板工具集合为空；它基于问题与快照思考，不自行查文件或联网。并发上限 5，运行 15 分钟、节点 5 分钟，快照上限 12,000 tokens；节点轮次与输入输出/token 另有有界策略并受 caps 校验。第二轮额外成本是明确接受的产品取舍，不能为了节省调用静默删除交叉阶段。

### 对话事实与耐久边界

成功输出包含用户输入与唯一最终 assistant 答案，附 definitionId、perspectiveCount 和汇总 usage；分配、独立版本、交叉版本不作为对话消息追加，主线 system prompt 不因评议改变。

当前耐久路径由 `correctness.runDurable` 进入既有 durable turn executor，转交授权与模型计量，应用返回 RunResult；不是应用自行写历史文件。成功提交后尝试发布 pending finals，发布暂缓不改写已经提交的成功结论。非耐久模式仍有 `recordLegacyTurn` 分支，不能把它漏写成已不存在。

“中间过程不持久化”指不保存各节点思考版本为对话内容，不排除父运行的权威记录、用量、安全及恢复事实。DAG 不具备节点级跨重启续跑能力，父运行恢复由现有耐久协议负责。

失败或中止不提交半成品答案。当前失败 RunResult 仍带用户消息与用量交给父协议，不能将旧稿“主线零残留”解释为所有失败运行零记录。一次节点失败采用 fail-fast，全场失败；不自动增加重试或保存可续跑的中间版本。

### 事件与体验

复用本次 EventBus 的 orchestration 事件与 RPC 投影；CLI 已有 run_start/node_start/run_end 消费者及历史 perspectiveCount 来源投影。用户应看到评议进度、最终答案或失败环节，不必理解 DAG；未来其他触发面复用同一应用行为，不复制流程。

事件桥随执行清理，busy 在执行 finally 中释放。实时进度不是最终提交证据；用户最终看到的答案与历史应以同一已提交结果为准。帮助说明、触发边界、失败呈现和历史标记属于此能力的产品维护范围。
