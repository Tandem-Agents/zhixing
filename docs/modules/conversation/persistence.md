# 对话持久化与注意力窗口架构

本文说明历史原文如何保存、模型工作窗口如何恢复，以及两者如何协作而不互相改变职责。它不是新的独立模块：存储与接受责任属于会话，窗口算法属于[上下文管理](../context/architecture.md)；术语见[生命周期概念](../../architecture/lifecycle-concepts.md)，扩展钩子见[运行体生命周期](runtime-lifecycle.md)。

## 一、产品目标与设计由来

知行是个人助手。进入交互环境应接续既有对话，没有对话才创建；恢复既要让模型接上工作，也要让用户看到最近的历史，不能出现“模型已有上下文、用户面对空屏”的断裂。恢复不应等待用户先发消息，也不应为了生成启动摘要再调用一次模型。

早期实现把历史文件直接当作模型上下文，压缩窗口便截短原文，下一次运行又从文件重建全部工作消息。这混淆了两个不同的问题：磁盘如何长期受控，模型当前需要看什么。模型能接收的最大容量也不等于能稳定工作的有效容量。

因此保留两条独立规则：

- **历史保存原始对话事实，不因模型、上下文容量或摘要决策删除原文。** 存储增长由自身的分片和保留策略处理。
- **注意力窗口是可重建的工作视图，不是历史本体。** 它按模型注意力阈值折叠，保留足够的工作连续性，不追求装满容量。

“不因压缩删除”不是“永久保存”：明确的用户删除和存储保留期是独立边界。摘要是有损材料，不能充当原文证明。

## 二、当前责任与数据流

| 对象 | 唯一职责 |
|---|---|
| 会话身份与目录 | 管理对话身份、名称、工作场景及查找；身份变化不重写内容日志 |
| 会话 owner 与权威日志 | 接受运行结果、裁决提交与恢复；模型已输出不等于已经提交 |
| Transcript 分片 | 保存、读取原始 run 记录；耐久提交路径中是权威日志的幂等投影 |
| 注意力窗口 | 会话持有的模型工作视图；执行内核消费它，不取得会话写权 |
| 段摘要快照 | 保存已有摘要及覆盖位置，辅助启动；不替代原文或提交事实 |
| Host 存储适配与维护入口 | 装配具体存储并提供有限端口；不另设一套会话业务或清理算法 |

```text
已提交原文 ──启动恢复──→ 会话窗口 ──发送视图──→ 模型—工具循环
                                                    │
                                                    ↓
原文投影、窗口推进、派生摘要快照 ←──owner 权威提交──运行结果
用户 clear ──独立控制提交──→ 清空读取边界、重置窗口
存储维护 ──物理保留规则──→ 回收过期非活跃分片与旧快照
```

两层的协作仍收敛在三个触点：建窗时读取历史与已有摘要；接受 run 时追加原文并推进窗口；接受折叠结果后保存派生摘要。窗口的被动维护不在每个 run 重新拉取全量历史，压缩不反向改写原文。用户历史浏览是另一消费者，不受“建窗读取一次”的限制；未来显式检索也不应被这条规则禁止，但本设计不预建检索或记忆能力。

分布式运行后，“原文事实权威”与“分片文件”不能画等号：耐久 run 经 owner 的 AuthorityCommitLog 提交，再驱动投影。分片索引又只是文件读取的派生元数据。快照、索引、分片和提交日志承担不同层次的恢复职责，不能互相冒充。

## 三、原文记录与接受边界

记录单位是完整 Run，而不是一次 LLM Turn。内容字段 `messages` 保存用户原文与本 run 的协议消息序列；最终回复、工具调用展示从它派生，不另存重复正文。输入注入只改发送视图，不污染用户原文；没有最终回复时，不在原始记录中伪造回复。

`runId` 标识跨执行与提交边界的同一运行，`runIndex` 标识记录顺序。普通分片追加由 store 分配序号；权威提交投影携带已经确定的身份和序号，要求连续，重复记录必须身份与载荷一致，冲突拒绝，不能靠重复追加冒充恢复。

接受顺序是原文持久化成功后再推进窗口；瞬态会话先进入 pending 队列，再推进窗口，转为持久会话时按序发布。耐久路径先裁决提交，再幂等应用投影；投影失败不撤销既有提交，也不能宣布整个运行需要重新执行。未裁决结果不得先污染窗口或文件。

窗口跨 run 保留用户／最终回复配对，run 内完整工具协议消息不无限累积到工作窗口；启动恢复可以把原文中的工具过程渲染成可读材料，两者不要求消息形态相同。中断记录在窗口中配空回复只是配对规则，不改变原文。

段切换产出 `windowCompact`，由会话层接受后应用；摘要替换旧装填／摘要与被覆盖配对，并保留未覆盖部分。段元数据在 durable assignment 内暂存为 `segment-append`，提交后物化，失败或取消不能提前发布，uncertain 等待裁决。手动 compact、clear 走各自控制入口，不伪造 assignment。段判断、摘要调用与失败降级的唯一说明在[上下文管理架构](../context/architecture.md)。

## 四、启动与恢复

### 有效需求

启动只需少量高信号材料恢复连贯，把大部分有效窗口留给接下来的工作。选择最近原文不是按固定“七组”，而是按 token 预算；启动时尚无用户 query，不做猜测式检索。

- 预算基准取模型 `optimalMaxTokens / 4` 与 24,000 token 的较小者；optimal 是具体工程阈值，不是标称容量的固定百分比。
- 连贯底线是最近一组对话与一条已有有效摘要；基准预算不足时允许为这条底线适度提高预算，而不是直接丢弃最近对话。过大的单组保留压缩核：开头意图、结尾结论与最近原话，不能硬塞超大工具输出。
- 摘要小而精，保留 facts／state／active 的关键含义；其余预算给最近原文。展示顺序为摘要在前、近期原文按时间正序在后。
- 只取 clear 之后、覆盖位置严格早于本次原文起点的有效快照，避免摘要与原文重复覆盖；没有快照就只用原文，不现场生成摘要。
- 装填内容成为窗口起始条目，以系统元信息及配套回执标识，不改写当前用户消息。首个 run 失败不丢装填，之后持续可见，直到被折叠替代。

1/4、24K 与摘要长度是工程取值，不是跨模型永恒常数。原文要求超出有效窗口的单组降为压缩核；当前通用装填器在单组超过启动预算基准时就降为压缩核，比原设计更早裁减，不能把两者描述为完全等价。

### 当前装配与差异

[存储适配](../../../packages/cli/src/serve/conversation-storage-infrastructure.ts)把 `loadHistory` 接到[通用装填器](../../../packages/core/src/context/bootstrap/build-startup-bootstrap.ts)，消费分片倒读与 SnapshotStore；会话 owner 持有恢复后的窗口，不再由 CLI 和 server 各自维护一套 canonical 回灌逻辑。

但[本机 owner](../../../packages/cli/src/serve/local-conversation-owner.ts)的 `loadHistory` 当前通过会话权威端口读取全部分页记录，展平后取最后 100 条消息渲染装填，未接入上述 token 预算与段摘要快照选择。它没有完整落实本节统一恢复要求；不能用通用装填器已存在证明所有拓扑都已覆盖。

## 五、分片、读取与 clear

分片投影目录位于相应会话目录内：

```text
meta.json                  身份及会话元数据投影
transcript/index.json      分片索引
transcript/000001.jsonl    header + run／clear 记录
transcript/000002.jsonl
snapshots/<timestamp>.json 段摘要及覆盖位置
```

存储适配按用户／工作场景身份路由；对话不因启动 cwd 自动分裂。这里的文件布局只描述分片适配，不代表本机 owner 的全部权威日志布局。

- 每个对话有一个活跃分片；“活跃”指后续写入目标，不是用户最近是否使用。
- 默认 7 MiB 是换片判断点，不是截断单个 run 的硬上限。当前片达到阈值后，下一个新 run 才开新片；单个巨大 run 因此仍可能超过阈值。
- 索引先登记新片，分片首次追加时创建；读取容忍尚不存在的新片和已清理的旧片。索引由写入侧维护，GC 不写索引。
- 分片倒读返回 run 与位置游标，启动按 token 预算消费，UI 按条数分页；不能因为读取目的不同就另建相互冲突的原文。

**clear 是逻辑读取边界，不是压缩，也不是立即销毁原文。** 有效要求是所有正常历史消费都止于最近 clear，包括恢复、计数、历史分页和未来显式检索；重启不能把用户清空的历史灌回。分片侧以 ClearRecord 表达边界，索引 `lastClearAt` 是快照退役的派生元数据；权威路径由会话控制提交表达 clear，再更新各读面。

当前[分片倒读](../../../packages/core/src/transcript/shard/reader.ts)从指定游标所在片开始扫描，遇 clear 即停；传入 clear 之前旧分片的游标时，不先检查之后分片的 clear，因此该原语本身尚不能保证跨 clear 的旧游标隔离。正常从尾部读取与这个反例不同，不能以其正常行为证明全部分页路径满足要求。

## 六、存储保留与快照

磁盘治理不认识模型、不调用 AI、不以是否压缩作为删除条件。算法内聚在[持久化维护](../../../packages/core/src/transcript/retention.ts)，调度器只负责触发。当前 Host 给 anchor 调度装配 `__transcript-gc`，每日 cron 调用存储维护端口；不能沿用旧稿“任意 CLI 自有写者＋启动必拉起 GC”的装配描述。

维护属于系统内部工作，不进入用户任务视图、用户投递和产品事件流；结果仅供内部运维查看，不打扰用户。

分片默认保留期为 27 天。删除只针对**非活跃且封笔时间已过期**的整片；封笔以后一片的创建时刻判定，不按本片创建时间误删仍在增长的新数据。活跃片不删，索引只剩一片时不删，无后继的异常非活跃片保守保留。真删除、不入垃圾桶；占用或权限失败报告 warning，后续再试，单个对话失败不拖垮全部清理。

摘要快照按自身创建时间老化，最新且未被 clear 退役的快照受保护；旧快照超期才删。快照覆盖的原文已过期，不等于快照也失去价值；反之，clear 前快照不能借“最新”永久保留在用身份。清理只读分片索引、不打开分片正文；判断快照需读取快照元数据，不能宣称整个维护过程完全不读文件内容。

保留期外被删除的原文细节不可再召回。在用摘要可以延续工作线索，却不能恢复被删原文；摘要也丢失时只能从仍保留的原文降级恢复。27 天是该分片维护策略，不是所有权威日志已经统一按此期限删除的证明。

原方案把长期记忆提炼与滚动摘要共同视为删除的安全垫。Memory 已退场，不能再保留“记忆库兜底”的理由，也不能据此恢复记忆功能。当前分片清理仍执行 27 天规则；原要求“削弱蒸馏能力时连带复核删除强度”仍须保留，不能把尚未证明的长期信息保障写成既成事实。

## 七、失败与恢复边界

- 分片内容采用追加；索引可重建。索引缺失／损坏时，从现存分片恢复索引与 clear 元数据，不能直接当成空对话。
- owner 打开时检查活跃片尾部，修补“ClearRecord 已追加、lastClearAt 未更新”的中断状态；记录读取跳过解析失败行，不代表权威提交允许静默丢失。
- 索引写入使用临时文件替换；当前 Windows 实现是 unlink 后 rename，并非单次原子替换。目标缺失时尝试恢复残留临时文件，必要时从分片重建；这不是对任意断电零丢失的承诺。
- 普通 run 的完整记录与耐久运行的日志恢复不能混为一谈：权威已提交但投影未完成时，恢复应继续幂等发布，不能沿用旧稿“崩溃丢整个 run，重发即可”的统一结论。
- 段摘要快照写入失败不撤销已接受原文，只降低恢复材料质量。只读降级入口在内存中恢复索引，不借历史查询取得磁盘写权。
- 瞬态会话可以保留内存 pending 记录，但不能伪造耐久提交；是否持久化与后续晋升由会话生命周期决定。

旧单文件 `transcript.jsonl`、CompactMarker、压缩后 canonical 回灌和 MemoryFlush 均不作为现行路径保留。只继承职责分离、提交顺序和失败可恢复的设计，不保留旧迁移步骤与临时桥。

## 八、实现核对入口

- [会话接受与投影](../../../packages/owner-kernel/src/conversation-manager.ts)、[会话权威与恢复](../../../packages/owner-kernel/src/conversation-assignment.ts)：提交、原文身份、窗口推进及控制操作。
- [存储装配](../../../packages/cli/src/serve/conversation-storage-infrastructure.ts)、[本机 owner](../../../packages/cli/src/serve/local-conversation-owner.ts)：实际拓扑与恢复消费链。
- [分片存储](../../../packages/core/src/transcript/shard/store.ts)、[倒读](../../../packages/core/src/transcript/shard/reader.ts)、[文件替换](../../../packages/core/src/transcript/serializer.ts)：追加、幂等、clear、索引恢复。
- [启动装填](../../../packages/core/src/context/bootstrap/build-startup-bootstrap.ts)、[窗口](../../../packages/core/src/context/window/attention-window.ts)、[快照](../../../packages/core/src/transcript/snapshot/store.ts)、[保留维护](../../../packages/core/src/transcript/retention.ts)：预算、接受、覆盖锚点与老化。

核查应区分：原文不变与窗口改变、已提交与已投影、普通尾读与跨 clear 的旧游标、通用装填器与真实拓扑装配、分片保留与权威日志保留。上述实现差异是当前事实，不是修改需求或宣告功能全部通过的依据。
