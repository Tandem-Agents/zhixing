# 对话间通信：产品与架构设计

## 产品理念

这一洞察来自用户对实际使用体验的独立理解，而非外部产品的官方定义：**不直接设计“多智能体产品”，而是提供独立对话之间的通信能力，让多智能体协作从这些能力的使用中自然形成。**

**用户可以组织协作，但不必亲自维持协作。** 找到对话、了解背景、发送消息、接收回复与继续交流由知行运用基础能力完成，不要求用户搬运内容、盯着窗口或反复催促。沟通的目的和方式由用户与模型决定，不由底层预设。

这是具有长期价值的产品方向：交流与上下文独立是稳定需求，角色、分工和流程则会变化。底层越不绑定某种合作方式，就越能承接新的使用方式和更强的模型。

### 设计边界：独立对话，通过普通消息沟通

**A 给 B 发消息后，可以结束当前运行；B 在自己的上下文中正常处理，需要回信时再给 A 发消息，A 收到后正常继续。** 回复就是再次发送，不需要 A 保持运行或登记等待，也不要求系统自动回传 B 的输出。对话之间没有因此形成主从关系、共同任务或共享运行额度。

用户让 A 访问自己已有的 B，直接通过对话工具完成，不额外建立对话间授权关系或审批流程。沿用产品既有边界，不为通信另造一套权限或隐私系统。架构只负责让这些基础操作正确成立，不预设协作方式，也不把可选的等待工具升级为通信前提。

## 产品设计

### 对话平等，通信可组合

用户已有的对话使用同一套通信能力，不因对话类型、创建者、所用模型或所在设备被预设为主从。各对话保有自己的上下文；发送消息不切换当前对话，也不自动合并双方历史，需要背景时按需读取。

| 基础能力 | 含义 |
|---|---|
| 发现 | 找到对话，取得名称、摘要和可用状态，确定通信对象。 |
| 读取 | 按需读取历史与输出；可先读摘要，再定位原文，明确分页与截断。读取本身不启动对方。 |
| 发送 | 向指定对话发送消息；空闲时启动处理，运行中在当前 Turn 结束后接收为下一 Turn 的输入。回信使用同一能力。 |
| 观察 | 按需查询消息是否接纳及对话运行状态，不要求发送方持续在线或等待。 |

这些能力可组合成咨询、审查、并行工作或其他合作方式，但协议不为这些用途增加专用角色、任务类型或流程。新建、恢复、分支和停止运行属于对话自身的管理能力；通信不要求重新创建对话，也不要求通信双方存在创建或父子关系。

用户能看到消息来源、去向与真实状态，也能沿现有入口介入或停止运行。正常通信不要求打开目标窗口，不自动改变用户当前界面。这里定义的是目标能力，不表示已经全部实现。

### 来源可辨，处理一致

应用层区分用户消息与其他对话发来的消息；后者记录源对话，界面显示“来自某某对话”。两者沿同一条正常消息处理链执行，接收模型不必识别来源或采用另一套任务规则。

来源是消息的结构化事实，不是正文前缀；历史读取与恢复后仍可辨认。这为追溯、统计等用途保留事实基础，本次不扩展这些功能。

### 内置技能：让模型知道并会用

提供内置技能“对话通信”，在模型需要联系其他对话、了解其进展或处理来信时使用。模型通过技能索引发现能力，按需加载简洁中文说明，再使用通信工具；不要求用户先安装、教授用法或指定技能名。

技能只说明如何定位目标、读取必要背景、发送与回信，以及如何理解接纳和处理状态；不规定谁负责执行、谁负责审查，也不要求每条来信都回复。技能负责使用方法，工具与运行系统负责实际收发。

### 运行中的来信

沿用[生命周期定义](../../architecture/lifecycle-concepts.md)：一个 Run 包含多个 Turn，一个 Turn 是一次模型调用及其请求的工具执行。

| B 的状态 | 来信处理 |
|---|---|
| 空闲，没有正在执行的 Run | 接纳消息，启动正常 Run。 |
| 正在执行一个 Turn | 先接纳；当前 Turn 连同工具执行完整结束后，以来信作为同一 Run 下一 Turn 的新输入，不等整个 Run 完成。 |
| Run 已正常结束 | 消息启动后续 Run，不丢失、不回写已经结束的 Run。 |

来信不打断当前模型调用或工具，不改写旧消息，不重置 B 正在做的事；B 在下一 Turn 结合原有任务与来信继续判断和行动。

## 架构设计

### 核心：可寻址的对话，可靠的消息，独立的执行

通信层只理解**对话地址、消息与处理状态**，不理解业务目标、分工、验收或交付责任。通信层不解释消息为什么被发送，也不据此规划下一步。

沿用 [AE-001](../../../research/design/architecture/evolutions/AE-001-companion-intelligence.md) 的领域所有权与薄内核边界：

| 责任 | 归属 |
|---|---|
| 通信语义 | Conversation 提供发现、读取、发送和观察端口；模型工具与界面共用这些端口。 |
| 消息事实与恢复 | 接收对话的权威负责逐条消息及其来源、接纳、去重、待处理状态与 Run 关联，复用 Owner／Journal；发送方记录工具调用及返回结果，不复制对端运行状态。 |
| 技能发现与加载 | Skill Catalog 提供内置技能索引与正文；通信模块维护使用说明，Host 绑定所需工具，不另建技能加载机制。 |
| 智能执行 | Conversation 决定来信交给当前还是后续 Run；Kernel 通过通用输入端口在 Turn 边界取得追加输入，不识别对话间协作关系，不管理协作流程。 |
| 接入与部署 | Product API 组合合同，工具、CLI、RPC 等负责绑定；Host 只装配。本机直调和远端传输遵循同一语义，不以网络化作为架构前提。 |

### 内置技能接入

复用[技能架构](../skills/architecture.md)的 builtin 注册、索引投影和 `load_skill`：将“对话通信”注册为包内方法，覆盖现有 main/work 对话模式，随产品分发，不创建用户技能资产。窗口索引提供名称标识与适用描述，正文按需加载；不把整份方法塞进常驻提示词。

通信工具在对话运行体装配时绑定到 Conversation 应用端口，技能加载只返回用法，不承担工具安装或动态改写工具集。新增／修改提示使用简洁中文，无关既有英文保持不变；不植入固定协作剧本。

### 消息与处理

消息具有稳定 ID、目标对话地址、内容及来源元数据。来源区分“用户／对话”，对话来源另存源对话 ID；由实际用户入口或发送工具的调用上下文确定，不接受模型自报来源。来源逐条记录，不放在 Run 级标签中，因为同一 Run 可以接收不同来源的消息。

来源随消息贯通耐久接纳、正式记录、恢复及历史／界面投影，不由正文反推。它不改写消息正文或改变模型输入的处理规则；需要回信时，可通过通信工具取得来信的源对话地址。界面根据元数据呈现来源，不另建来源账本或对话间授权流程。

发送经 Conversation 应用端口耐久接纳；只有接收方确认后才报告已接纳。同一发送操作的重试沿原消息 ID 核对、去重，避免重复入队。接纳不等于模型已经读到，实际消费关联到所属 Run；不为每条运行中来信预建一个新 Run。

来信作为正常消息输入处理，同时保留真实来源。B 的输出属于 B 的对话；需要回复 A 时，由 B 调用发送工具。发送成功不表示工作已经完成；回执和状态查询不自动触发新一轮模型执行。

双方运行独立：A 的工具调用计入 A 的运行，B 收到消息后使用 B 自己的运行额度，回信后 A 仍按自身规则运行。不继承发送方预算、不建立跨对话预算树；停止和恢复也沿用各自的运行控制。

目标不存在、不可达或无法接纳时，返回真实结果，不报告虚假成功、不擅自创建或替换目标。

### Turn 边界消费

当前 Turn 完整结束、工具结果收齐后，循环在发起下一次模型调用前，通过输入端口取得已接纳的来信，按顺序追加为下一 Turn 的正式输入。仍在 B 的同一个 Run 中继续，不中断当前 Turn，不重置运行计量或既有终止条件，也不另启并行 Run。

来信原文与来源元数据进入所属 Run 的正式消息记录，不走 `TurnContextInjector` 的临时发送视图，不修改历史消息或系统提示。待处理消息、消费关联与恢复由接收方权威维护，不能只存在于进程内队列。

正常收尾前检查待处理来信：已有来信则进入下一 Turn；若 Run 已结束，则交由后续 Run 处理。接纳与收尾由同一权威协调，避免消息落在两者之间被遗漏或重复处理；中断、错误和运行限制仍按既有终止规则处理。

若已接纳的来信因输入关闭或 Run 终止而未消费，权威将其投递状态标为“已停止、未消费”，常规读取仍返回原文与来源；Run 完成不代表其中每条来信已处理。恢复和原操作重试不自动重新入队、重开终态或重置额度。

### 与已有架构的衔接

[Conversation 应用](../../../packages/core/src/conversation/application.ts)提供目录、历史和运行准入，[准入适配](../../../packages/owner-kernel/src/conversation-agent-turn-admission.ts)连接耐久接纳链。单元 1 已接通通信应用端口、本地 Run 的 Turn 边界消费及消息记录／恢复；通信工具、内置技能与本地／远端产品接入由单元 2 完成。

实现需补齐内置技能与工具绑定，并在 Conversation／Owner 和[模型循环](../../../packages/core/src/loop/agent-loop.ts)之间贯通 Run 内追加输入及其记录、恢复。保持同一条生产处理链，不另建通信执行引擎；现有实现不符合上述职责时在所属层修正，不在工具层叠加旁路。

不将现有专用任务交接流程改名为通用通信，也不搬入其业务规则。其他模块可以消费通信能力，但通信层不依赖它们；本设计不要求重写或淘汰这些模块。是否合作、如何合作与何时完成，始终留在通信层之外。

研究依据：[方向思考](../../research/agent-concepts-and-multi-agent-direction.md) · [跨会话能力调研](../../research/codex-cross-thread-collaboration.md)。
