# 轻量工具循环

## 定位与取舍

轻量工具循环供程序发起的小型任务使用：调用方给定目标、工具和轮数上限，模型自主选择调用顺序，程序接收经过校验的结构化结果。它避免 MCP 接入、工作场景创建等场景各自实现一套决策循环。

### 与其他 LLM 使用形态的关系

| 形态 | 发起方式 | 模型轮次与工具来源 | 运行职责与适用边界 |
|---|---|---|---|
| 单发文本调用（`callText`／宿主 `llm.complete`） | 程序提交明确的文本任务 | 单次模型完成，不调度工具 | 独立文本判断或生成，不自行推进多步工具任务 |
| 主对话运行循环 | 产品用例提交对话输入，宿主启动运行 | 多轮；工具由运行配置与装配决定 | 持续对话与任务执行，接入权限、确认、上下文、运行提交及会话恢复链 |
| Task 子 Agent | 主 Agent 通过 Task 工具委派子任务 | 多轮；从父工具集中按子 Agent profile 筛选 | 复用完整 Agent 循环，受父子生命周期、权限、资源与结果回收约束，不等同于独立用户会话 |
| 轻量工具循环（本原语） | 程序给定目标、工具和结果合同 | 多轮，每轮至多一个工具；工具由场景显式注入 | 有限的小型工具任务；框架负责调度，场景负责业务校验、确认与实际效果，不自行管理会话历史、压缩或运行提交 |

只需一次文本判断时用单发调用；需要有限工具步骤与结构化结果时用本原语；需要完整 Agent 执行与会话责任时用主循环，由主 Agent 委派的子任务走 Task。工具由场景注入，不使用完整 `ToolDefinition` 的执行上下文；这不是绕过安全规则的理由，副作用必须由场景在真实执行前保护。

核心原则是把事实约束与模型判断分开。模型负责搜索策略、相关性和何时收尾，程序执行工具并回灌真实返回；最终内容是否有依据，必须由场景验证，不能仅靠提示词保证。约束无依据的编造，不用硬编码流程穷举搜索与判断策略，使有真实材料支持的判断能够受益于模型能力提升。真实返回也不等于外部内容可信，不能将工具文本提升为程序权限或事实权威。

## 合同与职责

入口为 `@zhixing/core/tool-loop` 的 `runToolLoop(spec, deps, signal)`，不依赖具体 Provider、MCP 或工作场景业务。

| 合同 | 责任 |
|---|---|
| `ToolLoopTool` | 名称、描述、输入 Schema 与 `run(input, signal)`；名称唯一由调用方保证 |
| `ToolLoopSpec` | `goal`、工具集、`maxRounds` 和 `parseFinal`；目标只含模型完成任务需要的信息 |
| `ToolLoopDeps.complete` | 注入文本完成能力；框架拼装多轮提示，不要求 Provider 原生工具调用 |
| `parseFinal` | 校验业务结果，返回通过或拒绝理由；拒绝回灌下一轮，不能把模型自行声明当作验证 |
| `onProgress` | 报告轮次及 deciding/calling；文案由场景翻译，同步回调异常被忽略，不影响循环 |

工具执行与 `parseFinal` 可共享场景私有状态：工具积累实际获取的数据，最终校验只接受其中允许的项。框架负责调度和纠错，不内置候选包名、目录、工作场景等业务规则。

## 当前执行与终态

每轮请求由目标、工具描述及 Schema、JSON 决策格式和此前历史组成。模型输出 `{"call":{"tool":"名称","input":{}}}` 或 `{"final":...}`；框架用 core 的 `extractJsonObject` 提取 JSON。当前同时出现两者时优先 final，不是严格互斥校验。

1. 无法解析时回灌格式提示；未知工具回灌可用名称，继续下一轮。
2. 每轮至多执行一个工具，真实结果或工具抛出的错误回灌历史。工具失败不是框架 error；调用方负责验证参数，`inputSchema` 当前只进入提示词，框架不执行通用 Schema 校验。
3. final 经 `parseFinal` 通过后返回 `done`，包含结果与轮次；拒绝则回灌原因，消耗一轮后重试。
4. 达到 `maxRounds` 仍未通过时返回 `exhausted`；`complete` 抛错返回 `error`。调用方应提供有效有限轮数；轮数上限不等于单次调用或整次任务的时间上限。

`done`、`exhausted`、`error` 是正常结果协议，不是所有异常都会被包装的保证：`parseFinal` 当前不在 try/catch 中，其抛错会直接拒绝 Promise，场景应按合同返回拒绝结果。

历史保留本次循环的全部已积累条目；成功工具调用的输入和返回分别截断到 4,000 字符。当前没有“仅保留最近历史”、统一总 prompt 上限或历史摘要，错误及拒绝理由也不受该单条截断逻辑保护。不能把有限轮数说成完整 token 预算。

## 取消与副作用

框架向 `complete` 与 `tool.run` 传递 signal，在轮首、完成模型请求后、执行工具前及工具成功返回后检查取消。它没有中止竞争或统一超时，不响应 signal 的在途依赖仍可能继续；不能承诺调用取消立即终止底层模型或工具。

工具抛错后先回灌，下轮才检查取消；若恰在末轮，可能返回 exhausted。场景不能仅依赖结果 kind 判定用户取消。通用循环不会撤销已经发生的副作用。

注入写工具时，场景须在执行前取得用户确认，提供单次性或幂等保护，并将取消作为明确结果处理；不得因模型重试而重复执行，也不得把取消变成另一条写入路径。通用循环不替代产品用例、权限、资源或持久化提交边界。

## 当前消费者

- **MCP 搜索引导**：CLI 配置命令将 main 角色的宿主 `llmComplete` 注入 `mcp-discovery`。场景工具维护真实搜索结果集合，`parseChoices` 拒绝不在集合中的包名及超过五项的候选；这不证明模型写出的摘要和推荐理由都正确。选择后的配置提取由另一阶段处理，不由通用循环完成。业务正文见 [MCP 接入与管理](../mcp/onboarding-and-management.md)。
- **工作场景智能创建**：REPL 将 main 角色的宿主文本调用注入 `runWorksceneCreateAssist`。场景负责澄清、创建前确认、已创建结果保护及取消处理，真实写入走工作场景用例；不是另一个常驻 Agent。业务正文见[工作场景管理](../workscene/management.md)。

两条路径通过管理接口调用宿主，不再由 CLI 直接持有旧 `AgentRuntime.callText` 接线。通用原语只要求文本完成端口；模型角色与连接规则由[模型角色](../providers/model-roles.md)负责。客户端停止等待、循环放弃结果与宿主取消请求是不同边界，不能仅凭 signal 参数存在就宣称贯通取消。

当前提供串行工具调用、文本 JSON 决策、固定轮数与结构化步骤进度；没有并行工具、token 流、原生 tool_use 转换、置信度终止或历史摘要能力。
