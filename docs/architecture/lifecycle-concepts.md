# 生命周期概念定义与规范

本文是知行生命周期术语的共同参照，只定义概念、起止与相互关系，不展开模块实现，也不把社区中不同的 Run／Turn 用法视为同一标准。新增概念须先与用户对齐，既有定义须与真实生产边界一致。

## 一、概念与边界

### Turn（轮）

Turn 是模型—工具循环中的一轮：一次模型调用及其请求的工具执行。工具结果回灌后，下一次模型调用属于下一轮；因此，一条用户消息可以引发多个 Turn，并非“一条用户消息就是一轮”。

正常情况下，请求的工具全部执行完成后结束本轮；未请求工具时，随最终回复结束。中断或错误可能提前终止，不能把清理未执行工具所生成的协议占位结果当作工具已执行。`turn_complete` 标示循环的轮边界，`turnCount` 不是用户消息数，也不是 Provider 的重试次数。

### Run（运行）

Run 是一次输入引发的完整智能执行；主对话中对应一次 `runtime.run()`，通常是一条用户消息的完整往返，内部驱动连续的 Turn，直到最终回复、中断、错误或运行限制使其终止，并返回运行结果、收束本次资源。

Run 的执行结束不等于结果已被会话 owner 权威接受或耐久提交；执行、接受与持久化不能混为同一边界。模型调用也不都构成独立 Run，例如段摘要调用服务于上下文重构，不是新的一次用户往返。

### 注意力窗口（Attention Window）

注意力窗口是供模型持续工作的上下文视图，不是历史对话存储本体；按模型的优质注意力尺寸维护，而非等到物理容量耗尽才处理。持久会话启动或恢复时，从持久层重建首个窗口；随后由已接受的运行结果推进，压缩只折叠视图，不删除历史原文。

段切换或有效压缩完成时，旧窗口结束、新窗口开启；`/clear`、`/resume` 等操作也会触发对应窗口的重建。窗口开启不必等待第一条新用户消息，运行体销毁则关闭末个窗口。

窗口内保持稳定前缀，允许对话继续追加；不等于消息数量、动态发送材料或整个请求永远不变。窗口边界允许按需重建上下文，工具集仍受运行体装配约束。具体发送与压缩机制见[上下文管理架构](../modules/context/architecture.md)。

### 相互关系

- 一个 Run 包含连续的 Turn；注意力窗口与 Run **交错，而非严格嵌套**：窗口可以服务多个 Run，一个 Run 也可因中途切段跨越多个窗口。
- 会话身份、历史记录与派生窗口分离；换窗不是新建会话。
- 运行体实例与窗口不是同一生命周期：同一实例可以经历多个窗口；实例创建与销毁分别承接首窗开启与末窗关闭。

## 二、生命周期介入需求

| 边界 | 需要承接的工作 | 当前对应入口 |
|---|---|---|
| 窗口开启 | 为新窗口准备或重建稳定上下文 | `onWindowOpen` |
| Run 开启 | 在本次执行前准备输入及所需工作 | `onBeforeRun` |
| Run 结束 | 消费本次结果，发现并总结经验，记录与收尾 | `onAfterRun` |
| 窗口结束 | 收束旧窗口；实例销毁时完成末窗收尾 | `onWindowClose` |

注册单位是运行体实例，触发单位是窗口或 Run；订阅集合在装配时确定，不因每次触发重新注册。上述边界提供介入机会，不承诺自动学习等额外能力，也不赋予钩子越过 owner 提交权威状态的权限。同一职责应由统一入口承接，不保留语义重复的新旧路径。
