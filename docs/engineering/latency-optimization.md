# 按完整链路、整轮推进耗时优化

适用于有明确起止的耗时场景；持续运行的系统先选定一次操作或一个处理窗口。目标是改善用户实际等待，并减少零碎修改、反复构建和无依据试错。

**完整测量 → 分阶段拆到可解释节点 → 逐项优化 → 整轮审查 → 集中构建验证 → 逐版本对照。**

## 先建立完整耗时账

明确起点、真正可用的终点、输入规模、环境和验收要求；冷启动、已有服务等不同场景分开记录。复用现有日志，缺什么补什么，先取得完整基线，再优化。

先分阶段，再把异常或不可解释的阶段拆到具体节点，区分执行、I/O、排队、重试及必要等待；保留调用次数。不能只记录几个已知热点，把其余等待留在账外；也不为无关细节建立庞大观测系统。

父阶段包含子节点，不能重复相加；并行工作按依赖和关键路径解释端到端时间。记录节点的自身耗时与包含子步骤的耗时，未解释部分明确标为“待定位”。诊断开销与无诊断成绩分开。

用一张持续更新的表呈现过程，每个版本新增一列，不覆盖旧值：

| 阶段 / 节点 | 基线 V0 | V1 | V2… | 原因与优化空间 | 本轮处理 / 预计收益 | 状态、依据及重开条件 |
|---|---|---|---|---|---|---|
| 完整场景 | 样本量、中位 / 最大值 | 同口径实测 | … | 当前瓶颈 | 预计总耗时区间 | 整体验收结论 |
| 阶段与节点 | 时间、次数、包含关系 | 同口径实测 | … | 异常在哪里，是否可减少或移出关键路径 | 方案与节点收益区间 | 待定位 / 可优化 / 已实现待测 / 已达当前优化边界 |

预计节点收益与预计版本总耗时必须标明是估计及其依据；按依赖推算，不能把所有节省相加或把估计当成绩。尚未测量写“未测”，不填猜测值。

## 一整轮处理完，再付出整体验证成本

1. **逐项判断，集中攻破。** 先列全已识别卡点，记录耗时、原因和优化价值；把本轮有价值的卡点集中处理完。每个节点持续推敲至当前约束下无尚未处理的明确有效方案；不能改一点、解决一个性能点就立刻构建或跑完整场景。
2. **已有结论不反复推倒。** “已达当前优化边界”须有测量、必要工作量或约束依据，表示当前条件下无明确有效的继续优化空间，不是证明理论极限。后续轮次不再钻研；依赖、实现、负载变化或新证据推翻判断时才重开。
3. **整轮功能与架构审查。** 所有本轮可优化节点处理后，统一检查是否还有可消除的重复、串行等待、过早加载和放大开销，并检查功能、资源、安全、耐久和失败恢复。发现有效空间继续处理，不能靠延后用户必需工作、隐藏等待或削弱校验换取成绩。
4. **集中构建和验证。** 整轮实现与上述审查结束，才构建完整候选、运行必要测试和真实路径测量；避免逐节点全量构建、全流程复测。只有关键假设无法由现有证据判定且会造成大面积返工时，才提前做最小定向验证，不借此恢复零碎重测。用户实际运行的必须是本轮构建产物。
5. **保留有效版本，驱动下一轮。** 把完整场景、各阶段及节点的同口径实测填入新版本列，对照预计收益。只要有可验证收益、必要回归通过且整体要求未退化，即使尚未达到最终目标，也保留为下一轮稳定基线，不因未达标全盘丢弃。没有改善或成本转移，先解释原因；失败候选可撤回最近稳定基线。下一轮只处理仍可优化、尚未查清或被新证据重开的节点。

阶段稳定与最终达标必须分别标记，版本记录不等于自动提交或发布。若任务目标是区间或统计值，应依约用同条件重复样本判断，允许正常波动，不擅自改成逐次硬阈值；具体数值和样本口径归任务文档。需求不绑定实现方案，现有架构限制目标时应比较替代方案，不能把维护既有选型变成目标。

中断后先把半途的写入、退出、资源释放等必要事项收束到安全边界，再切换方法；不丢已有成果，不把必要收尾扩大成重跑旧计划。两人协作时，审查和修复仍按完整轮次交接，方法不改变任务方向。

**停止条件是既定产品目标与必要验证达成，范围内明确缺陷处理完成。** 达标后仍可进一步提速，不自动构成继续工作的理由；不把追求所有节点的理论最小值、维护表格或完善测量工具变成新任务。方法长期保留；具体场景的数值、状态和版本列放在该任务的执行记录中，与[阶段式交付](staged-delivery.md)配合使用。
