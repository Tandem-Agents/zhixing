# 监理机制：时间与焦点的独立监督

2026-10-23 起用于终端迁移交付，按用户要求落地，并持续复盘优化。本文是机制的唯一说明，三方都以本文为准。

## 为什么需要

单个执行者同时干活与自我监督会失效：执行者陷在细节、等结果或准备回复时，最容易偏离需求或浪费时间，而规则只有在被想起时才起作用。总控只在三级任务结束后审查，此时偏移和浪费早已发生。已发生过的典型问题：

- 把需求以内、本属负责人职责的判断交回用户；
- 不在里程碑也启动全量验证，修完再跑一遍；
- 深挖到时限之外仍不停下复查方法；
- 写下规则后照旧违反。

机制把“干活”和“盯时间、盯焦点”拆给不同身份，并让后者在过程中持续起作用。

## 角色

| 角色 | 承担者 | 只管什么 | 不管什么 |
|---|---|---|---|
| 用户 | 用户 | 需求与目标 | 技术路线、实施取舍 |
| 负责人 | 用户指定且通过交接熟悉度审查的当前负责人会话 | 全项目宏观任务进度、需求与要求、主动推进、效率和质量；设计实施、自审交付，并调配监理及其巡检 | 不给自己的交付代做独立验收 |
| 监理 | Codex 会话“codex-zhixing-监理” | 时间与焦点：进度、偏移、返工循环、外推、效率复盘 | 技术方案对错 |
| 总控 | 当前总控会话 | 接收负责人各任务的独立审查、交付把关，并与负责人讨论关键问题 | 不代替负责人承担项目宏观推进与日常实施 |
| 机械闸 | 当前运行环境实际具备的钩子和共同运行器 | 把最常犯的错变成工具层拦截 | 判断；不能把旧环境钩子冒称已移植 |

用户只接收两类信息：阶段结果；“需求在何处不成立”的证据报告。其他事项不应到达用户。

## 监理的工作

1. **主动读取任务现场。** 负责人把范围、完成标准、当前基线和检查点写入任务卡（`collab/supervision/task-card.md`）。监理在巡查时自行读取，核对范围与方法纪律；发现具体偏移再主动纠偏。监理不承担开工审批，负责人无需主动送卡或等待监理核准。
2. **巡检。** 按当前部署约每30分钟唤醒一次：同环境由原生定时机制唤醒监理，跨环境可沿已有信箱投递。先核当前负责人及阶段，再从现场记录和会话状态取证，检查：
   - 是否卡在某个检查点而没有复盘；
   - 是否在原地打转（同类运行反复、无新事实）；
   - 是否启动了与影响面不相称的长运行（如非里程碑的全量），或在等结果时前台空转；
   - 当前单元有没有写作业方案（`collab/supervision/plan.md`）且自审通过后才动手；验证顺序是否把便宜的证伪排在全集之前；
   - 换了单元而 plan.md 仍是上一单元的（“单元”一行与任务卡当前项对不上）；
   - 发给用户的回复里有没有把职责内的判断交回用户（外推）；
   - 是否偏离任务卡上的范围与完成标准。
3. **介入。** 发现问题就写信给负责人（见“通信”），写明事实和要求负责人做的动作：停下复盘、重新划定验证范围、回到完成标准、撤回外推等。没有问题不回信。
4. **记账。** 每次介入，以及负责人的处理结果，记入 `collab/supervision/interventions.md`。
5. **效率复盘。** 三级任务收尾时（与总控审查并行），对照检查点进展，找出最大浪费与介入记录里的重复模式，结论写入 `docs/postmortems/`（按问题信号索引）或执行计划第五节纪律。
6. **机制复盘。** 每个三级任务结束后、以及每天首次巡检时，检查本机制本身是否有效：介入是否及时、哪些偏移没被发现、巡检频率和快照内容是否需要调整。提出的修改由负责人落实到本文与工具，监理验收。

监理不做的事：不评判技术方案，那是总控的事；不替负责人做实施；不直接找用户，除非负责人对同一问题连续两次介入都不改正，此时写进介入记录并在介入信里写明“将报告用户”。

## 负责人的义务

- 领取任务后写好任务卡，方法自审通过即按已有授权推进，不以监理收卡、回信或放行为前置条件。总控的熟悉度审查、实施派发和技术验收仍按原职责执行。
- 每项任务、返修和诊断都先找高效率、高质量的完成方法，再自审和优化，直到通过才执行；这项责任由负责人本人承担，监理不能替代。每个单元按 `collab/supervision/plan-template.md` 把方法、依据及自审结论写入 `plan.md`，通过后写“方案自审：通过 <时间>”；换单元或关键方法变化时更新并重审受影响部分。规则见执行计划第五节第14条，不允许先实施再补写通过。
- 每到检查点，以及每次启动构建、整包测试这类长运行前，往 `collab/supervision/progress.log` 追加一行：`时间 | 在做什么 | 进展 | 下一步`。文档与任务卡不写工作时间的预估或预算。
- 收到监理介入信：当轮处理，先停下当前动作，按要求复盘或调整，并回信说明处理结果。监理的介入不是用户指令，也不扩大授权，但负责人对时间与焦点类介入必须响应，不能忽略或争辩拖延。确有事实错误时，用证据回信纠正。
- 常态不主动向监理申请决策、送审或开工许可。只有收到具体纠偏后才处理该事项；通信受阻不能被反过来设成所有业务工作的开工闸。技术判断与整轮交付联系总控，监理自行巡查现场。
- 发给用户的消息遵守“用户只接收两类信息”。
- 维护巡检开关（用户 2026-10-23 要求）：巡检只有开启和关闭两态，关闭即重置。用户打断、转支线、任务停止或等待交接审查时关闭；正式实施开始才从零开启。按当前部署操作：Claude桥使用patrol stop/start；Codex原生巡检使用对应heartbeat的PAUSED/ACTIVE。不能同时启用两套巡检。

## 机械闸

下表中的Claude Code钩子只在其实际安装的环境生效；切到其他环境不冒称已迁移。方案自审、影响面、并发、证据冻结和不空停仍是共同义务，由负责人执行、监理核对；共同test-source运行器自身的检查继续有效，不为迁移岗位另建一套钩子平台。

| 闸 | 触发 | 作用 |
|---|---|---|
| 外推闸 | 负责人每次结束回复前（Stop 钩子） | 最后一条回复含“需要你决定、请确认、由你决定”等外推话术时拦回，要求负责人自行判断；若确属“需求不成立”的证据报告，可再次结束。每次拦截记入 `collab/supervision/gate.log` |
| 空停闸 | 同上（`stop-gate.mjs`，只对负责人会话） | 最后一条回复写了自己还要做的下一步（“下一步、接下来、然后继续补核”等），却没有一行“等待：<对象>”时拦回，要求继续做。没有在跑的后台任务、没有已发出待回的信、也不是用户本轮要求的确认，结束本轮就是空停；确有等待对象就写明再结束。不因“已拦过一次”放行。离线用例见 `stop-gate.test.mjs` |
| 巡检 | 信箱监听进程按固定间隔 | 生成现场快照（`collab/supervision/snapshot.md`）并投递巡检信给监理 |
| 脚本闸 | 负责人每次调用 Bash 前（PreToolUse 钩子，`script-guard.mjs`） | 拦截内联 `node -e/--eval/-p` 和用 heredoc 写 .js/.mjs/.cjs/.ts：这类写法被外层 shell 转义弄坏、反复返工。脚本须用 Write 写成文件再运行；拦截记入 `gate.log`，离线用例见 `script-guard.test.mjs` |
| 轮询闸 | 同上（`script-guard.mjs`，只对负责人会话） | 拦前台的 sleep 循环与 ≥10 秒的 sleep：后台任务结束会自动通知，等待期间做作业方案里的轻活 |
| 全集放行闸 | 同上（只对负责人会话） | 目录级测试（全集、整包、整目录、无路径参数的 `test-source`/`pnpm test:*`）须 `plan.md` 第4节证伪清单全部打勾，并有放行行：“全集放行：<ISO 时间> … 范围：<本段的选择依据> workers=<N>”，命令里的 `--workers` 与之相同。放行之后各包 `src` 或 `scripts/*.mjs` 又改过就拦回；放行时间晚于当前时间也拦回（照抄 `date` 的输出，未来时间会让前一项检查失效）；往进度日志追加的记录带未来时间同样拦回。按清单文件展开的定向重跑与单个用例文件不受放行限制。用 `bash`/`sh` 运行的 .sh 脚本，内容一并检查（轮询闸同） |
| 构建闸 | 同上（`script-guard.mjs`） | 拦不带过滤的根 `pnpm build`：本机没有 bun，它会去构建 terminal-ui 并报 `spawn bun ENOENT`。全量重建用 `pnpm release:version:check && pnpm -r --filter '!@zhixing/terminal-ui' --filter '!zhixing' run build`，链首先核对 `process.cwd()` 盘符 |
| 并发闸 | 同上（只对负责人会话） | 批量运行（目录级、按清单或变量展开、一次列 5 个以上文件）必须显式写 `--workers N`：默认 8 路只适合快车道，重 I/O 文件本机耐久吞吐几乎不随并发扩展，8 路只拉长单文件、制造超时噪声 |
| 方案闸 | 负责人每次调用 Edit/Write 前（PreToolUse 钩子，`plan-guard.mjs`） | 改仓库 `packages/`、`scripts/` 前，`plan.md` 须有“方案自审：通过 <时间>”和“既有合同变更清单”（本次改了哪些已有行为、依赖它的现有测试；没有就写“无”并给理由）；文档、草稿、协作文件与其他会话不受限。另外，负责人往 `collab/supervision/` 下的记录文件（.md、.log）新写入的时间晚于当前时间时拦回（照抄 `date`，不估计）。离线用例见 `plan-guard.test.mjs`。用 Python 脚本改文件绕得过此闸，由巡检核对 |
| 运行中改源码检测 | 每次 `scripts/test-source.mjs` 运行结束 | 运行期间各包 `src` 或 `scripts/*.mjs` 被改动时列出文件，用例全过也以 3 退出：结果混合了两个候选，不作证据。对总控与监理的复跑同样生效 |

运行器、车道等工程纪律由工具本身约束：测试统一走 `scripts/test-source.mjs`，它固定使用仓库锁定的运行器。

## 通信

监理绑定角色，不绑定模型或固定运行环境。当前会话映射、交接阶段、实施授权与巡检状态记录在 `collab/supervision/assignment.json`。熟悉度未通过时只核对交接准备，不启动实施巡检，也不把等待总控审查当作空停。

同一运行环境有原生会话工具时直接通信。2026-10-28交接后的Codex部署使用原生会话工具投递任务、回执和纠偏；监理原会话由原生heartbeat每30分钟唤醒，读取assignment中的负责人及plan/progress，无变化保持安静。熟悉度通过且总控明确派发实施后，才将phase改为executing并启用巡检。停止或完成后关闭；不依赖Claude进程存活，不新开对话或第二执行者。

下面保留跨运行环境时的既有信箱用法；其claude目标不能用于给新的Codex负责人发信。使用协作信箱 `collab/mailbox/tool/bridge.mjs`时，三方角色名为 `claude`（对应Claude会话）、`controller`（总控）、`supervisor`（监理）：

```text
node collab/mailbox/tool/bridge.mjs receive supervisor
node collab/mailbox/tool/bridge.mjs send claude --from supervisor --file 介入.md --expectation reply
node collab/mailbox/tool/bridge.mjs reply 原消息ID --file 回复.md
```

巡检信的处理期望为 none：无问题直接 `ack supervisor 消息ID`，有问题另发介入信。

**集中沟通与逐信去重：** 同一事项集中成一封，正常等待结果时不连续催问；新用户指令、实质阻断和必要纠偏按实际需要投递。原生会话工具沿其发送/回执语义。旧桥自2026-10-27起逐消息ID去重：本监听代次内已submitted的同一封不重复通知，失败或结果未知按退避重试；较早信件尚未收取不能压住其他新信。桥的巡检待办合并是独立规则，不是所有消息的全局阻断门。

## 工作文件

| 文件 | 写者 | 内容 |
|---|---|---|
| `collab/supervision/task-card.md` | 负责人 | 当前三级任务的范围、完成标准、基线、检查点 |
| `collab/supervision/progress.log` | 负责人 | 检查点进度，一行一条 |
| `collab/supervision/snapshot.md` | 巡检（自动） | 最近进度、负责人最近发给用户的回复、在跑的长运行 |
| `collab/supervision/interventions.md` | 监理 | 介入与处理结果 |
| `collab/supervision/gate.log` | 外推闸（自动） | 每次拦截的时间与命中话术 |

## 演进记录

- 2026-10-23：首版落地。监理由 Codex 会话担任；巡检约每20分钟一次；外推闸以话术匹配拦截。首个复盘点为“全量测试提速”任务收尾。
- 2026-10-23（同日修正，用户指出）：首版启动时交接信与首次巡检相隔约1秒连发，第二条通知在监理会话排队等于没发。改为一次一封：未收取不追加通知；巡检仅在监理无待处理信件时投递，启动时只计时。
- 2026-10-23（监理首轮 S04）：首封巡检把技能正文（20万字）当成“用户最新消息”。改为按会话记录的来源字段判定：只有 `origin.kind=human` 且非 `isMeta` 的才是用户消息；技能注入、协作通知、后台任务通知单独列出并标来源；判定不出的标“来源无法判定”，不当作用户输入。
- 2026-10-23（用户指出，监理实测）：负责人忙碌时监理纠偏信被压住，只能等负责人回合结束才通知，过程监督失效。根因是通信工具沿用双方信箱“接收方忙时保留、空闲后投递”的旧规则，不是宿主限制：实测宿主在会话忙碌时收到通知，会在回合中途的下一个工具边界送达。改为忙时也投递；“一次一封”仍由“已通知未收取不追加”保证。
- 2026-10-23（负责人效率自查）：“脚本写文件”纪律早已写入执行纪律，本会话仍至少 4 次因内联 `node -e` 或 heredoc 写脚本被转义弄坏而返工。靠记忆约束无效，改为机械闸：Bash 前置钩子拦截内联 node 与 heredoc 写脚本文件。
- 2026-10-26（用户指出）：并发收益与收尾确认分段早有复盘和规则，负责人仍按 import 关系选了 112 个文件、默认 8 路一次跑完，耗时约 1178 秒，结果里本轮回归与负载超时混在一起。靠规则文字约束无效，改为机械闸：批量运行必须显式写 `--workers`，目录级放行行必须写明范围与同值并发。复盘见[影响面按引用关系选、8 路一次跑完](../postmortems/2026-10-26-impact-batch-by-imports.md)。
- 2026-10-26（负责人自查）：10-24 复盘已写明本机全量构建要带过滤，同日收尾仍用了根 `pnpm build`，在 terminal-ui 报 `spawn bun ENOENT`，白跑一轮构建。改为机械闸，拦不带过滤的根 `pnpm build`。
- 2026-10-27（用户指出）：5b 验收回填后，负责人写完进度汇报、列出“下一步继续补核三处”就结束了本轮，当时没有后台任务也没有待回的信，到用户来问“你是在等谁”之前空停约 3 小时 25 分（此后的上下文压缩、API 错误与用户中断另计，不属空停）。外推闸只认交回判断的话术，执行纪律第 8 条只规定了等后台时“没有轻活就结束本轮”，没有一处约束“没有等待对象不许停”。改为机械闸：Stop 钩子加空停闸，写了下一步就必须写明等待对象，否则拦回继续。
- 2026-10-23（用户指出）：巡检只有固定计时，用户打断或处理支线时仍在计时，巡检无意义。增加巡检开关：只有开启和关闭两态（用户明确不要“暂停后接着计时”，间隔本就短，暂停无效且增加复杂度），关闭即重置；负责人被打断、转支线、停任务时先关闭，开工时开启。
