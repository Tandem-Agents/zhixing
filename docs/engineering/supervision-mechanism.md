# 监理机制：时间与焦点的独立监督

2026-10-23 起用于终端迁移交付，按用户要求落地，并持续复盘优化。本文是机制的唯一说明，三方都以本文为准。

## 为什么需要

单个执行者同时干活与自我监督会失效：执行者陷在细节、等结果或准备回复时，最容易偏离需求或浪费时间，而规则只有在被想起时才起作用。总控只在三级任务结束后审查，此时偏移和浪费早已发生。已发生过的典型问题：

- 把需求以内、本属负责人职责的判断交回用户；
- 不在里程碑也启动全量验证，修完再跑一遍；
- 深挖到时限之外仍不停下复查方法；
- 写下规则后照旧违反。

机制把“干活”和“盯时间、盯焦点”拆给不同身份，并让后者在过程中持续起作用。

## 角色

| 角色 | 承担者 | 只管什么 | 不管什么 |
|---|---|---|---|
| 用户 | 用户 | 需求与目标 | 技术路线、实施取舍 |
| 负责人 | Claude（本仓库 Claude Code 会话） | 需求以内的全部技术判断与实施 | 自我监督（交给监理和机械闸） |
| 监理 | Codex 会话“codex-zhixing-监理” | 时间与焦点：进度、偏移、返工循环、外推、效率复盘 | 技术方案对错 |
| 总控 | Codex 总控会话 | 技术正确性审查（三级任务收尾；关键架构点可被请求） | 过程节奏 |
| 机械闸 | 负责人会话的钩子 | 把最常犯的错变成工具层拦截 | 判断 |

用户只接收两类信息：阶段结果；“需求在何处不成立”的证据报告。其他事项不应到达用户。

## 监理的工作

1. **审任务卡。** 负责人领取任务时写任务卡（`collab/supervision/task-card.md`）：范围、完成标准、当前基线、检查点。监理核对检查点是否与完成标准匹配、是否先建了基线；有问题当场退回。
2. **巡检。** 每次收到巡检信（约每30分钟一次，由负责人会话的信箱监听进程自动投递，附现场快照），检查：
   - 是否卡在某个检查点而没有复盘；
   - 是否在原地打转（同类运行反复、无新事实）；
   - 是否启动了与影响面不相称的长运行（如非里程碑的全量），或在等结果时前台空转；
   - 发给用户的回复里有没有把职责内的判断交回用户（外推）；
   - 是否偏离任务卡上的范围与完成标准。
3. **介入。** 发现问题就写信给负责人（见“通信”），写明事实和要求负责人做的动作：停下复盘、重新划定验证范围、回到完成标准、撤回外推等。没有问题不回信。
4. **记账。** 每次介入，以及负责人的处理结果，记入 `collab/supervision/interventions.md`。
5. **效率复盘。** 三级任务收尾时（与总控审查并行），对照检查点进展，找出最大浪费与介入记录里的重复模式，结论写入 `docs/postmortems/`（按问题信号索引）或执行计划第五节纪律。
6. **机制复盘。** 每个三级任务结束后、以及每天首次巡检时，检查本机制本身是否有效：介入是否及时、哪些偏移没被发现、巡检频率和快照内容是否需要调整。提出的修改由负责人落实到本文与工具，监理验收。

监理不做的事：不评判技术方案，那是总控的事；不替负责人做实施；不直接找用户，除非负责人对同一问题连续两次介入都不改正，此时写进介入记录并在介入信里写明“将报告用户”。

## 负责人的义务

- 领取任务先写任务卡，经监理核对后开工。
- 每到检查点，以及每次启动构建、整包测试这类长运行前，往 `collab/supervision/progress.log` 追加一行：`时间 | 在做什么 | 进展 | 下一步`。文档与任务卡不写工作时间的预估或预算。
- 收到监理介入信：当轮处理，先停下当前动作，按要求复盘或调整，并回信说明处理结果。监理的介入不是用户指令，也不扩大授权，但负责人对时间与焦点类介入必须响应，不能忽略或争辩拖延。确有事实错误时，用证据回信纠正。
- 发给用户的消息遵守“用户只接收两类信息”。
- 维护巡检开关（用户 2026-10-23 要求）：巡检只有开启和关闭两态，关闭即重置。用户开口打断、转去处理支线、任务停止时，第一动作是 `bridge.mjs patrol stop`；开发任务开始时执行 `bridge.mjs patrol start`，从零计时。

## 机械闸

| 闸 | 触发 | 作用 |
|---|---|---|
| 外推闸 | 负责人每次结束回复前（Stop 钩子） | 最后一条回复含“需要你决定、请确认、由你决定”等外推话术时拦回，要求负责人自行判断；若确属“需求不成立”的证据报告，可再次结束。每次拦截记入 `collab/supervision/gate.log` |
| 巡检 | 信箱监听进程按固定间隔 | 生成现场快照（`collab/supervision/snapshot.md`）并投递巡检信给监理 |
| 脚本闸 | 负责人每次调用 Bash 前（PreToolUse 钩子，`script-guard.mjs`） | 拦截内联 `node -e/--eval/-p` 和用 heredoc 写 .js/.mjs/.cjs/.ts：这类写法被外层 shell 转义弄坏、反复返工。脚本须用 Write 写成文件再运行；拦截记入 `gate.log`，离线用例见 `script-guard.test.mjs` |

运行器、车道等工程纪律由工具本身约束：测试统一走 `scripts/test-source.mjs`，它固定使用仓库锁定的运行器。

## 通信

使用协作信箱 `collab/mailbox/tool/bridge.mjs`，三方角色名为 `claude`（负责人）、`controller`（总控）、`supervisor`（监理）：

```text
node collab/mailbox/tool/bridge.mjs receive supervisor
node collab/mailbox/tool/bridge.mjs send claude --from supervisor --file 介入.md --expectation reply
node collab/mailbox/tool/bridge.mjs reply 原消息ID --file 回复.md
```

巡检信的处理期望为 none：无问题直接 `ack supervisor 消息ID`，有问题另发介入信。

**一次一封：** 发出一封信后，等对方回信或处理完再发下一封。对方会话里的通知是排队的，连发的第二封等于没发。工具层面同样约束：收件人还有已通知、尚未收取的信时，不追加通知；巡检只在监理没有待处理信件时投递，监听进程启动时只开始计时。

## 工作文件

| 文件 | 写者 | 内容 |
|---|---|---|
| `collab/supervision/task-card.md` | 负责人 | 当前三级任务的范围、完成标准、基线、检查点 |
| `collab/supervision/progress.log` | 负责人 | 检查点进度，一行一条 |
| `collab/supervision/snapshot.md` | 巡检（自动） | 最近进度、负责人最近发给用户的回复、在跑的长运行 |
| `collab/supervision/interventions.md` | 监理 | 介入与处理结果 |
| `collab/supervision/gate.log` | 外推闸（自动） | 每次拦截的时间与命中话术 |

## 演进记录

- 2026-10-23：首版落地。监理由 Codex 会话担任；巡检约每20分钟一次；外推闸以话术匹配拦截。首个复盘点为“全量测试提速”任务收尾。
- 2026-10-23（同日修正，用户指出）：首版启动时交接信与首次巡检相隔约1秒连发，第二条通知在监理会话排队等于没发。改为一次一封：未收取不追加通知；巡检仅在监理无待处理信件时投递，启动时只计时。
- 2026-10-23（监理首轮 S04）：首封巡检把技能正文（20万字）当成“用户最新消息”。改为按会话记录的来源字段判定：只有 `origin.kind=human` 且非 `isMeta` 的才是用户消息；技能注入、协作通知、后台任务通知单独列出并标来源；判定不出的标“来源无法判定”，不当作用户输入。
- 2026-10-23（用户指出，监理实测）：负责人忙碌时监理纠偏信被压住，只能等负责人回合结束才通知，过程监督失效。根因是通信工具沿用双方信箱“接收方忙时保留、空闲后投递”的旧规则，不是宿主限制：实测宿主在会话忙碌时收到通知，会在回合中途的下一个工具边界送达。改为忙时也投递；“一次一封”仍由“已通知未收取不追加”保证。
- 2026-10-23（负责人效率自查）：“脚本写文件”纪律早已写入执行纪律，本会话仍至少 4 次因内联 `node -e` 或 heredoc 写脚本被转义弄坏而返工。靠记忆约束无效，改为机械闸：Bash 前置钩子拦截内联 node 与 heredoc 写脚本文件。
- 2026-10-23（用户指出）：巡检只有固定计时，用户打断或处理支线时仍在计时，巡检无意义。增加巡检开关：只有开启和关闭两态（用户明确不要“暂停后接着计时”，间隔本就短，暂停无效且增加复杂度），关闭即重置；负责人被打断、转支线、停任务时先关闭，开工时开启。
