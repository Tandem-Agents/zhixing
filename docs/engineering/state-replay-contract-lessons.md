# 状态、重放与合同一致性的工程经验

本文仅供处理共享状态重写、动作重复执行、同一合同多处判定这三类问题时参考，不是全局架构规范或所有模块必须采用的模板，不替代项目哲学与有效模块合同。应用前核实问题、适用条件和成本，选择最简单的完整方案；不得仅为遵循本文引入日志、代际、去重机制或通用框架。

## 只追加与代际换代

共享状态反复清空或整体重写，且面临并发、崩溃或重放时，优先评估能否用追加记录或代际换代消除破坏性推进，而非仅给原地重写叠加守卫。需要锁或备份本身不是设计错误，是否换代取决于状态语义和成本。

- 追加模式以日志表达变更，当前状态按明确的归约规则重建；只有覆盖型记录才适用按键 latest-wins，不能把所有事件都当覆盖值。
- 换代模式先完整、耐久地建立新代，再切换当前指针。代际身份固定，当前代内容可推进，切换后旧代封存；用 epoch、generation 或 attempt 拒绝过期写入，不靠删除旧代推进状态。
- 恢复须具备坏尾识别、明确的提交边界，以及原子指针替换或可检测的失败停机。只追加不自动保证幂等、原子性或无锁：仍需稳定去重键，并在追加端建立单写者、CAS 或适用的并发控制与栅栏。
- 保留窗内历史可用于审计与恢复；GC 按保留义务独立回收，不成为业务状态推进路径。必须定义投影重建与回收关系，不能用无限堆积替代状态治理。

高频小字段的原地更新不必整体换代；巨型状态频繁换代须权衡空间和重建成本。保证只覆盖遵循写入协议的路径，不能据此宣称越界删除不可能发生。

项目依据：[对话持久化](../modules/conversation/persistence.md)分离原文与注意力窗口，clear 推进读取边界，GC 不争写索引；[分布式运行时规格](../../research/design/modules/distributed-runtime/specification.md) §4.1、§2.1、§1.1/§6 分别定义 AuthorityCommitLog、信任事件链与换代栅栏；[工作台重置复盘](../postmortems/2026-07-14-compaction-replays-destructive-reset.md)说明代际登记如何替代清空进场。这些路径仍有各自的提交与恢复条件。

## 可重放动作的身份与消费记录

可能重复到达且重复执行会改变结果的控制动作，必须有稳定身份和耐久消费判据；无法安全重放的动作应移出自动重放路径。网络重试、渠道重投、崩溃重驱、Outbox 重发及对话压缩后的交接都可能形成重放。

- 身份来自同一次授权动作，例如目标编号与代次；不能用随处理进度变化的内容指纹代替身份。同键绑定同一规范载荷：同键同载荷复用原结果，同键异载荷明确冲突，不静默吞并或覆盖。
- 在本地权威提交域内，生效记录、权威变更和可回放结果应共同提交，避免“已生效却无消费记录”。需要独立接受语义的协议先耐久记录 received，再将 applied 与变更共同提交；不强迫所有动作增加两阶段流程。
- 执行前提仍成立，不等于动作尚未执行。恢复应查耐久消费事实，不以摘要中的祈使句或“目标仍有内容”推断应再次执行。
- 外部副作用不因本地日志而获得 exactly-once。须依赖外部幂等键、结果核对或明确的不确定状态处理；未知结果不构成自动重试授权。

纯读及天然幂等动作不必额外建去重机制。键过粗会吞掉合法的新动作，过细会失去去重；合法重开应取得新的动作身份。把动作交给另一会话并不自动消除重放风险，隔离必须同时限制自动执行与确认授权。

项目依据：[分布式运行时规格](../../research/design/modules/distributed-runtime/specification.md) §5.1/§4.3 的 `(surfacePrincipal, ingressId)` 与 ControlRequestJournal 接受／生效合同；[工作台重置复盘](../postmortems/2026-07-14-compaction-replays-destructive-reset.md)中的 `(unitId, generation)` 登记。两者共享消费判据思想，不代表文件登记拥有数据库式原子提交。

## 合同谓词单源

同一合同在多个执行点生效时，共享判定谓词或声明数据，各点仅适配自身可得的数据；发现合同分叉，应合并判定而非复制另一份检查。

- 适用信号是在线入口与重放、生产端与消费端、完整与轻量投影分别判断同一条件。已知第二消费者时先抽取共同谓词；没有实际第二消费者时不预建抽象。
- 单源的是判定，不是调用栈。结构、字段封闭、域绑定可用纯数据谓词；前态与伴随事实按各点的数据条件组合，不制造携带大量可选依赖的巨型 validator。
- 无序的身份绑定、同批伴随关系适合声明数据；顺序与前态转换保留状态机函数，不造吞并状态机的通用验证引擎。
- 查实分叉后，一次核对该合同的全部执行点，以与风险相称的检查或测试证明覆盖完整；不适用处须有事实依据。代码注册或参数化测试可用于重复性较高的核对，不是强制手段；不为对账新增框架、填满无关组合或维护重复权威。

业务语义不同的检查不能强行合并。在线业务拒绝与恢复时损坏判定可以有不同反馈，但确属同一合同的判定应复用；修复范围只覆盖该合同，不借机重建全项目校验体系。

项目依据：[分布式运行时规格](../../research/design/modules/distributed-runtime/specification.md) §5.2/§5.3 要求 owner 与 executor 共用 `matchManifest`、`validateDispatchBinding`；[单元 13 记录](../../research/design/workbench/unit-review-ledgers/unit-13.gen-1.md) U13-40 记录在线入口、完整 reducer、轻量 guard 多轮逐点补漏的反例及收敛方式。
