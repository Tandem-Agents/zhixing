# 多角色协作体系设计方法

用于按任务设计或调整协作体系，不预设角色数量与分工。目标是缩短完整交付时间、提前暴露关键阻塞、准确反映进度；需求与质量要求保持不变。

1. **从真实损失找原因。** 还原“事实出现→判断→决定→行动→验收”，区分必要工作、等待、重复和返工。查清信息何时已足够行动，以及什么职责、权限或依赖阻止了行动。
2. **从用户结果确定主线。** 列出完整使用流程、完成证据与关键依赖；优先验证判断错误会导致大面积返工的未知，不按文件或岗位完成量安排进度。
3. **从工作流反推角色。** 明确每步的负责人、决策权、输入、交付物、接收者和阻塞处置。每个角色与交接都须有不可替代的价值；保留独立验收，消除无必要的审批与中转。
4. **同步设计质量与结束条件。** 明确必要证据、阻断条件、重审触发和停止条件；复用有效证据。区分整体验收与提交边界，按目的完整、可回滚的适当单元持续交付。
5. **用真实失败检验方案。** 回放停滞、提交积压和阻塞晚发现等事件，回答“谁在什么时点，依据什么信息，会采取什么不同动作”。若仍依赖个人临时想起，机制尚未成立。
6. **用实际交付验证效果。** 在下一个完整单元检查交付耗时、等待、返工和风险发现时机。整体进度须有稳定的范围、权重及完成证据，不以忙碌、文件数或测试数代替；只保留能改善决策的规则与记录。

**通过标准：** 能说明如何减少主线等待、提前发现关键阻塞并据实报告进度，且不增加无必要的前置工作、不降低质量。推演通过只代表可试行，提效须由实际交付证明。

## 实验方案 A · 终端迁移协作（2026-10-06）

**状态：已落地为 v4，提效待验证。** 本节保留实验方案摘要，上方方法可复用；执行规则以[正式工作方案](../workbench/terminal-architecture-migration-collaboration.md)为唯一权威，角色接收和恢复状态见本机任务索引。落地不自动恢复暂停中的工作。

**针对问题：** 普通排障被拆成多轮审批与交接，真实主链阻塞暴露偏晚，进度缺乏一致依据。

### 角色与责任

四个持续交付角色、两个按需专家；围绕完整、可运行的用户流程协作。

| 角色 | 结果责任与边界 |
|---|---|
| 总控 | 范围、优先级、投入取舍、冲突裁决和最终交付；不审批普通实验，不重复核验全部证据 |
| 集成交付 | 提前组织真实主链验证，负责构建、资源排程、批次拆分、提交和唯一交付清单；不改生产代码、不自批验收 |
| 工程实现 | 连续完成批准单元内的定位、实现、自测与修复；多人协作时指定唯一接合负责人，不自批验收 |
| 独立验收 | 独立检查正式设计与完整实现候选，集中报告缺陷并复验；不参与被审实现，不逐次审批诊断 |
| 产品，按需 | 处理需求、流程、体验及范围歧义，维护产品依据 |
| 架构，按需 | 处理技术合同变化、重大方案及被反证的架构假设，维护技术依据 |

### 五项机制

1. **单元内连续执行。** 一次明确目标、写入边界、验证范围、资源限制和结束条件；普通排障自主推进。改变合同、扩大授权或触及安全边界才另行裁决；资源排队不承担技术审批。
2. **真实主链前移。** 必要接合具备即验证“启动→操作→结果→退出后可用”；影响入口或接合的变化及时复查。主链阻塞优先修复，无关工作继续，局部测试不代替链路通过。
3. **探索与验收分开。** 开发中连续取证修复，交付时冻结完整候选独立整轮审查，再统一修复。复用有效证据；新增检查须对应当前义务或可达风险。
4. **提交与进度同账。** 开工前划分目的完整、依赖齐全、可回滚的适当批次；构建及独验通过后按授权提交，不等整个模块。清单区分实现、验收、提交；整体百分比按固定交付范围、权重和独验结果计算。
5. **事件触发干预。** 预计失约、主链失败、重复无新信息、成熟成果等待或验证成本明显增加时，负责人直接通知总控和接续者；总控在继续同类投入前裁决路线、优先级、资源或无效前置。

**试行检验：** 沿用已有成果，以一个完整交付单元检查等待与返工是否减少、关键阻塞是否更早暴露、进度是否对应完成证据。保留产品范围、架构要求和独立整体验收；规则发布不算提效成功。
