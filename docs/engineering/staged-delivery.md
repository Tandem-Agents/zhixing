# 复杂任务的阶段式交付思路

适用于大型需求从零开始，也适用于任务进行中重新组织剩余工作。核心是：**按完整成果划分阶段，用待办列表使过程可视化；在阶段内连续开发、集中审查和修复，通过后再按实际变更拆分提交。**

## 解决什么问题

开发尚未展开就锁死提交清单，会使计划不断随实现变化重排；按零碎改动反复交审，会放大交接、重复验证和返工成本；把全部工作积压到最终审查，又会失去可控边界。三者的共同问题，是把任务目标、审查范围和提交粒度混成同一种单位。

只有计划、没有可持续查看的执行状态，也无法判断工作推进到了哪里、为何停留、还差什么。阶段划分提供工作边界，待办列表让边界内的实际进展和完成依据可见。

| 层次 | 决定什么 |
|---|---|
| 整体任务 | 最终要交付什么、必须满足什么要求 |
| 阶段 | 一次连续完成、能够完整审查和收尾的成果范围 |
| 提交 | 阶段通过后，实际变更如何形成清楚、连贯、可回滚的历史 |

## 阶段如何划分

- **从当前事实到最终结果。** 区分已有有效成果、明确待改实现、待补验证和仍未知的修复量，再判断阶段体量；不能把一张核对清单当作等量的开发工作。剩余实现、迁移、问题修复、验证和退役一并纳入，已有有效成果不重做。
- **按成果及依赖划边界。** 紧密耦合的实现和直接消费者放在同一阶段，不按文件、技术层或角色机械拆分。每阶段只需明确交付成果、包含范围、依赖和完成条件；各阶段合起来覆盖整个目标。
- **平衡连续性与可审查性。** 太小会重复支付审查和交接成本；太大会扩大在制变更、返工与提交整理成本。一个阶段以按提交规范合理拆分后约十个提交的体量为参考，不提前锁定提交清单或数量，也不为凑数拆分；最终以成果内聚、风险和整轮审查成本判断。
- **范围明确，内部方案可变。** 开发中允许调整实现及预计提交构成。发现阶段实际过大或边界错误时重新划分，明确已有成果和剩余归属，不靠不断扩面拖延收尾。

## 用待办列表呈现执行过程

具体任务将全部阶段按依赖顺序写成待办列表。它既是计划，也是持续更新的执行记录，让任何接手者能直接看清：**已完成哪些、当前在哪一阶段及环节、还有什么未完成，以及判断依据。**

可复用的方法文档长期保留并纳入版本控制；具体任务的阶段待办另建文档，在首部明确入库或临时不提交的约定。要求可见但不提交的临时计划不加入忽略规则，正式提交时明确排除；是否暂存不受此约定限制，不能把暂存等同于提交。

- 每阶段保留成果范围、完成条件、当前状态和剩余事项；状态区分待开始、开发中、审查中、修复中、待提交、已完成。遇到阻塞写明原因和下一动作。
- 状态随实际进展更新；只有开发、独立审查与修复、提交全部闭合，才勾选阶段完成，不能用“代码写完”代替。
- 保留关键范围调整、整轮审查结论、问题关闭依据和最终提交引用，使阶段能够追溯和恢复；只记影响推进与判断的信息，不堆操作流水或复制测试日志。

## 阶段怎样闭合

**连续开发与必要自测 → 独立完整审查 → 整轮汇总问题、统一修复 → 再次完整审查直至通过 → 按实际变更拆分并完成提交 → 下一阶段。**

连续开发不等于最后才接合或验证；关键依赖和真实使用路径应尽早验证。独立审查覆盖整个阶段的目标、实现及关联影响，不发现一条问题就停止交回。复审保持完整视角，复用仍有效的证据，只对行为变化、受影响路径和明确缺口追加必要验证，不机械重复全量构建。

阶段通过后，按实际变更及项目的[提交与拆分规范](../../.agents/skills/git-commit-generator/SKILL.md)确定提交边界和提交信息：优先按功能拆分，必须共同生效的合同及实现、直接消费者、必要测试与文档同行，不能留下靠后续提交补救的中间状态。体量参考不凌驾于拆分规范。

拆分若改变依赖组合或引入新的风险，补对应检查，不把每个提交重新变成一次阶段验收。阶段通过后完成提交再推进，防止已验收成果继续混入后续开发。

## 如何判断有效

进度按阶段成果与完成证据判断，区分开发完成、审查通过和提交完成，不用忙碌程度、文件数或提交数代替。最终还须核对整体目标及跨阶段接合，不能用各阶段局部通过代签整体完成。

这套思路是否有效，取决于是否减少等待、重复验证和返工，使成果及时闭合；不能为了维护阶段划分本身增加流程负担。具体角色、阶段数量和任务待办由各任务决定，不固化在本方法中。
