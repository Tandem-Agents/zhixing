# 项目文档体系维护

## 维护原则

本 Skill 描述的是随项目按需生长的目标结构，不是项目初始化清单。

以职责清晰、内容可发现和长期可维护的最优文档架构为目标，不以改动量最小为目标；避免无价值扩展，不限制为实现合理结构所必需的重组。

- 仅当任务涉及文档的新建、归属判断、位置选择、移动、重命名、拆分、合并或归档时使用；目标文件及其职责已经明确的普通内容修改不使用本 Skill。
- 不得因为进入项目、发现目录不完整或认为结构可以更整齐，就主动创建整套目录、空文档或占位文件。
- 未经用户授权，不得批量移动、重命名、拆分或重组既有文档。既有文档位置不理想时，最多说明建议，不得动手。
- 不得为了符合目录形式而改写文档内容、扩大当前任务或顺手整理无关文件。
- 新文档与既有权威职责重复时，优先建议更新既有文档，不得制造第二份权威。

## 愿景

构建一套顶级、经得起时间检验的项目文档体系。

## 目录结构与职责

本结构不是最终版本，将在长期使用中持续迭代。

现有目录职责无法合理承接文档时，暂停该文档的安置，说明职责缺口并提出符合本 Skill 维护原则的结构调整方案，以文档用途和检索场景确定归属及相邻职责边界，不为少改目录而混合不同职责；经用户确认后，先更新本 Skill 的目录树与职责说明，再安置文档。不得硬塞、擅自扩树或先搬后补；在既有职责下创建具体模块等已允许的目录，不属于扩树。

仅在对应文档真实出现时创建所需目录：

```text
<project>/
├─ README.md                            — 项目入口
├─ AGENTS.md                            — AI常驻行为规则
└─ docs/
   ├─ README.md                         — 文档入口
   ├─ philosophy.md                     — 项目全周期的顶层哲学，指导产品、架构、体验与安全取舍
   ├─ origin/                           — 需求起点-用户原话、原始输入和需求证据
   ├─ research/                         — 研究文档
   ├─ product/                          — 产品需求唯一权威：定位、范围、能力、原则和关键质量属性，只说明“要什么”
   ├─ architecture/                     — 全局架构
   ├─ engineering/                      — 开发规范、代码偏好、安全和质量底线
   ├─ delivery/                         — 当前版本的交付边界、验收条件和结束条件
   ├─ incidents/                        — 重要事件调查：经过、证据、处置和未决问题
   ├─ postmortems/                      — 失败复盘与可复用教训：指导后续诊断、决策和执行
   ├─ tasks/                            — 有独立目标、约束和完成边界的阶段性任务
   ├─ records/                          — 关键工作留痕：关键进展、决策与问题解决，只增不改并按卷维护
   ├─ workbench/                        — 人与agent协作的工作台文档
   └─ modules/                          — 按业务聚合的模块目录
      └─ <module>/
         └─ README.md                   — 模块入口
```

## 放置规则

1. 创建用户当前需要的文档时，只创建它所需的直接父目录，不补齐结构中的其他目录或文件。
2. 按主要用途区分 `incidents/` 与 `postmortems/`，不按是否出现“教训”章节分类。`incidents/` 保留有事实依据且值得留存的重要事件调查，允许根因未决，不接收纯担忧或普通过程日志；`postmortems/` 必须说明真实失败机制、可识别的类似信号及有适用边界的改进方法，以减少后续质量与效率损失。两者不重复存放同一正文，必要时互相引用。
3. 独立于事故仍有价值的工程规范或经验归入 `engineering/` 等对应权威；复盘保留原因与案例并引用，不重复定义。
