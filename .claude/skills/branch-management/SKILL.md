# 分支管理

## 分支与版本流转

### 常驻分支

- **main：最新正式版。** 只接收已验证且确认发布成功的版本，与固定的版本标签、发布包对应。
- **develop：下一版集成线。** 接收已完成并验证的功能、架构改动和修复。

### 工作分支命名

采用 `<type>/<description>`，`type` 为分支类型，`description` 为分支的简短描述。

| 类型 | 用途 |
|---|---|
| `feature/` | 新功能开发 |
| `bugfix/` | 修复 bug |
| `hotfix/` | 紧急修复 |
| `release/` | 版本发布 |
| `docs/` | 文档更新 |

示例：`feature/简短描述`、`bugfix/login-error`。

### 工作分支生命周期

按需创建工作分支，明确负责人、交付目标和结束条件；在分支中提交变更，小批量集成。并行工作隔离各自可变状态。一次中间合入不等于任务结束。

| 交付目标 | 创建起点 | 工作分支 | 结束条件 |
|---|---|---|---|
| 随下一版交付 | `develop` | 功能、架构用 `feature/<description>`；修复用 `bugfix/<description>`；文档用 `docs/<description>` | 验收并合入 `develop`，必要的修复同步已完成；不必等下一版发布 |
| 单独更新正式版的补丁 | `main` | `bugfix/<description>` 或 `docs/<description>`；紧急修复用 `hotfix/<description>` | 发布确认成功，`main`、版本标签和发布包对应正确；本次修正已同步至所有适用的受支持版本、开发线及候选并验证 |
| 新版本发布候选 | 从 `develop` 选定待发代码 | 候选需专属修改时创建 `release/<description>` | 发布确认成功，`main`、标签和发布包对应正确；候选期间适用的修正已回流开发线并验证 |

- **暂停与恢复：** 保存代码、恢复所需的数据和续办信息，写明负责人及恢复条件，释放不用的运行资源。恢复时先确认需求仍成立，再核对基线与依赖变化；复用仍有效的证据，只补验受影响部分。
- **取消：** 明确成果是移交、妥善保存还是放弃；保留成果须可恢复，并写明位置和归属。
- **清理：** 任务完成或取消后，确认没有未处置成果或仍在使用的依赖，及时清理本地、远端工作分支及临时环境；保留已合入代码、正式版本标签和发布包。清理受阻时记录待办，无使用影响的残留不阻塞发布。
- **收尾核对：** 发布与维护轮次收尾时，核对未结分支的负责人和保留理由，不按闲置天数自动删除。

### 集成与发布

- 同步目标的最新变化、解决冲突后，验证实际合入结果；验证后基线变化，补验受影响部分。
- 同一系列串行发布。合并完成不代表发布成功。

### 长期自动化维护

保留工作台、问题记录和排查工具，不另设永久维护分支。每轮在独立工作区检查固定版本，修复按交付目标归入开发或补丁路径。

### 运行隔离

正式版与开发版分开安装、运行；日常使用固定发布包，不链接开发目录。

## 代码分支管理的核心原则

1. 按准入政策保留必要的长期代码线，明确权威集成位置。
2. 小批量、及时集成，每次合入完整且可验证。
3. 用实际目标版本和有效证据把关合入、移植与发布；公共基线失效时先恢复，暂停无关合入。
4. 大改动优先渐进集成，隔离机制明确边界、同步方式和退出条件。
5. 发布固定、可追溯、可重建的基线；已发布内容不改写，变更另发新版本。
6. 稳定维护按兼容义务、实际收益和回归风险准入，不夹带无关演进。
7. 修复覆盖所有适用的受支持版本与后续开发目标，逐个验证并记录；补齐前不结束任务。
8. 按实际影响优先恢复正常使用；回退前核实数据与协议兼容性。
9. 分支创建时明确责任人、去向和结束条件；退役前确认成果已集成、保留或明确放弃。
10. 隔离开发、验证与生产的可变状态和写入影响；只读工具与不可变制品可共用。

### 适用边界

分支名称、数量、集成方式和修复起点可依据上述原则与实际条件调整，但须满足[完整文档中的需求与适用边界](references/branch-management.md)。
