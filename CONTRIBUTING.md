# Contributing to Zhixing

Thank you for helping improve Zhixing. Issues and pull requests may be written in English or Chinese.

## Choose the right path

- For a reproducible defect, open a [bug report](https://github.com/Tandem-Agents/zhixing/issues/new?template=bug_report.yml) with a minimal reproduction and sanitized environment details.
- For a new capability or a broad behavioral change, open a [feature request](https://github.com/Tandem-Agents/zhixing/issues/new?template=feature_request.yml) to agree on the problem and scope before implementation.
- Small, well-scoped corrections such as typo fixes can go directly to a pull request.

Do not put credentials, tokens, SecretStore data, private file contents, personal information, or unreviewed full logs in an issue or pull request. Suspected vulnerabilities must not be disclosed publicly; follow the current [security policy](./SECURITY.md).

## Development environment

The repository requires:

- Windows 10/11 x64 for the currently supported full product and packaging path;
- Node.js `>=24.0.0`;
- pnpm `10.8.0`, as declared by the root `packageManager` field.

Clone, install, and perform the initial full workspace build:

```powershell
git clone https://github.com/Tandem-Agents/zhixing.git
Set-Location .\zhixing
pnpm install --frozen-lockfile
pnpm build
```

The initial build is required before `pnpm cli` or cross-package verification because workspace package exports resolve files under `dist/`, and those files are not stored in Git or generated by `pnpm install`. After that first build, rebuild only the affected dependency closure when possible; use the full `pnpm build` again when package outputs or several package boundaries are involved.

This is the contributor workflow. End users should install `@zhixing/cli` from npm after a public release and follow the [user guide](./README.en.md); a source checkout is not the supported user installation path.

## Develop and verify

After the initial build, run the CLI from its source entry:

```powershell
pnpm cli
```

For later changes that broadly affect package outputs or cross several package boundaries, rebuild the workspace:

```powershell
pnpm build
```

Start with the narrowest test that exercises the changed behavior. On Windows, run core Vitest files through the package-local Node entry because the pnpm wrapper can report a false failure after the tests finish:

```powershell
Push-Location .\packages\core
node node_modules/vitest/vitest.mjs run src/__tests__/paths.test.ts
Pop-Location
pnpm --filter @zhixing/core exec tsc -p tsconfig.json --noEmit
```

The test path above is relative to the core package root; choose an existing focused test in the affected package rather than copying that path for unrelated changes. If an upstream package changed, build it before running downstream tests so the consumer does not read stale `dist` output. Broader root tests, packaging checks, and release verification are required only when the change actually affects those boundaries or a maintainer asks for them. Follow the [verification runbook](./research/design/workbench/verification-runbook.md) for Windows command, resource, and retry rules.

## Change discipline

- Keep each change focused on one outcome and avoid unrelated cleanup.
- Follow the surrounding TypeScript and documentation style; add or update the narrow test that can detect a behavioral regression.
- Preserve public contracts, durable data, security boundaries, and user-visible behavior unless the accepted change explicitly updates them.
- Update the authoritative documentation when the change alters a user command, product contract, architecture boundary, or release procedure.

Recent history uses concise Conventional Commit-style subjects such as `fix(skills): ...`, `refactor(runtime): ...`, and `docs(workflow): ...`. Match that form and describe the outcome rather than the editing steps.

## Pull requests

Use the pull request template to state the problem, scope, user impact, and exact validation performed. If a relevant check was not run, say why instead of implying it passed. Link the related issue when one exists, and keep reviewable changes separate from unrelated formatting or refactors.
